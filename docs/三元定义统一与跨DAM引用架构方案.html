CMX 平台架构方案

三元定义统一与跨 DAM 引用架构

把 数据字典（DCT）、业务单据（DOC）、弹性组合（FLX）三类定义统筹为一套元数据体系，并解决跨 域/应用/模块（DAM）的互联引用。
状态：设计草案（评审用） 日期：2026-07-10 运行时引擎不改 存储/解析层演进 向前兼容

01背景与目标

平台已有三类元数据定义，各自独立演进，缺少统一模型与跨 DAM 引用能力。本方案把它们统筹为一套体系。

DCT

数据字典定义

主数据/参照值目录。存 dictionaryTables；被单据/弹性组合以 refDict 引用。例：科目、成本中心、币种。

DOC

业务单据定义

事实表 + 主从结构 + 状态机 + 校验。存 voucherTables/voucherStatusFlow/validationRules。例：总账凭证。

FLX

弹性组合定义

在单据事实表上，按上下文（锚点）决定列的编辑/显示/计算/校验。例：科目→辅助核算。

目标

  1. 统一模型：三类定义共享一套「表 / 字段集 / 字段」词汇与校验，消除三端命名/属性分裂。
  2. 跨 DAM 引用：一个应用的单据/弹性组合，能安全引用另一个域/应用/模块的字典或单据——今天做不到。
  3. 单一事实源：字典、单据列各存一份；FLX 引用而非拷贝（承接 flexible-combination-overlay-design.md）。
  4. 可治理：引用可解析、可诊断、可视化依赖图；断引用/循环/越权引用在保存期拦截。
  5. 不破坏运行时：JS/Rust 引擎、grid/form 联动、缓存零改动；旧档案继续可用。

02三元命名：DCT / DOC / FLX

你提到「CTX 缩写不一定合适」。确实——现有代码里 CTX（context）指的是「弹性组合字段端」，但它和 DCT/DOC 不在一个语义层级（一个是"上下文"，两个是"定义类型"）。建议正名。

候选展开评价
CTXContext现状。与 DCT/DOC 不同维度（上下文 vs 定义类型），易误解；语义偏"运行时"。
FLXFlexible combination推荐。直译"弹性"，与 DCT/DOC 同为"定义类型"三字母，辨识度高。
CMBCombination次选。强调"组合"，但弱化了"弹性/上下文"这一核心特征。
OVLOverlay贴合 overlay 设计，但对业务人员偏技术黑话。
命名结论
三类定义统一记为 DCT（数据字典）· DOC（业务单据）· FLX（弹性组合），统称 元定义（MetaDef）。
代码内 kind 枚举：DCT | DOC | FLX；存储根 meta/definitions（DCT/DOC）与 meta/flexible-combination（FLX）本方案 §6 统一为单一 meta/defs 根下按 kind 分。

03现状盘点与四类断裂

3.1 DAM 存储现状

DAM = Domain / Application / Module 三级寻址。存储按 <root>/<domain>/<app>/<module>/<file> 落盘（源自 dam/store.rs · DAM_TREE_ROOTS）：

meta/definitions/ meta/flexible-combination/ ├─ base/ └─ fi/cmxfico/gl/ │ ├─ base_dct_meta_v1.json ├─ account.json (FLX) │ └─ base_doc_meta_v1.json ├─ trade.json (FLX) ├─ fi/cmxfico/gl/ └─ travel-expense.json (FLX) │ ├─ gl_md_dct_meta_v1.json (DCT) │ ├─ gl_md_doc_meta_v1.json (DOC) ← DCT/DOC 与 FLX 分处两个存储根（不一致 ①） │ └─ … ├─ fi/sap/sap_gl/ fi/ebs/ebs_gl/ fi/kingdee/kingdee_gl/ fi/yonyou/yonyou_gl/ （多套 ERP 各一份 DCT/DOC）
断裂①：FLX 与 DCT/DOC 存储根不同，工具/API 各写一套

3.2 引用欠限定 —— 核心病灶

三类定义之间的每一种引用都缺 DAM 限定，全靠"同应用同模块"的隐式约定解析。这就是"跨应用引用做不到"的根因：

引用出现处现状写法携带的 DAM问题
字段引字典 refDict DOC 列 / FLX 字段 "refDict":"cost_center" 无 裸 code，只能在当前模块找同名字典
弹性组合引单据 docRef FLX 档案 {domain,module,file} 缺 app account.json 的 docRef 没有 app 段，跨应用即断
引基础字段集 baseDctMetaRef DCT/DOC 顶层 {file} 无 只有文件名，约定落在 base/ 根
扩展维度绑定 ext_dim* DOC 事实表 注释"由 gl_ext_dimension 绑定" 无 纯注释，无可解析引用
病灶
引用是裸标识 + 隐式同域同应用同模块。因此："不同应用、模块间互相引用的字典/单据"在当前模型里无法表达——不是没实现，是标识符里根本没有存放目标 DAM 的位置。

3.3 拷贝式复用（量化）

因为无法安全引用，现有做法是拷贝。以 account.json（FLX，1305 行）为实证：

FLX 规则 = DOC 事实表逐列深拷贝

fi-cash 规则的 20 列（entry_id, amount, direction, profit_center_id … ext_dim5, remark）与 voucher_detail 物理表逐列 id/顺序/类型全同。根因：_docColumnToField 的 JSON.parse(JSON.stringify(col))。

FLX 维度 = DCT 字典重复

10 个字典维度（gl_account/cost_center/…）在 gl_md_dct_meta_v1.json 均有定义，FLX 又各抄一份 dict 取数块（≈300 行）。

断裂②：引用欠限定 断裂③：拷贝式复用→快照漂移 断裂④：三端字段属性/命名分裂（P7/P8 已部分统一）

05DRN —— 跨 DAM 引用标识

核心新增。把所有裸引用升级为一个可跨 DAM 定位、可版本化、可解析的统一资源名：DRN（Definition Resource Name）。

5.1 语法与解析

# DRN 完整形态 drn:<domain>/<app>/<module>/<kind>/<name>[@<version>][#<table>[.<field>]] # 例：跨应用引用——总账应用的弹性组合，引用「共享主数据应用」的成本中心字典 drn:fi/shared-md/masterdata/DCT/cost_center@1 # 例：定位到单据某表某列（FLX overlay 的 ref 目标） drn:fi/cmxfico/gl/DOC/gl_md_doc_meta#voucher_detail.cashflow_item_id # 简写：省略段 = 继承"当前定义所在 DAM"（兼容旧的裸 code） cost_center → drn:{当前domain}/{当前app}/{当前module}/DCT/cost_center DCT/cost_center → 当前 DAM 下的 DCT ../shared-md/masterdata/DCT/cost_center → 相对：换 app/module，同 domain
段必填省略时说明
domain—继承当前业务域，如 fi
app—继承当前应用，如 cmxfico/shared-md。这是今天 docRef 缺失的段
module—继承当前模块，如 gl
kind是*按上下文推断DCT|DOC|FLX|BASE
name是—定义逻辑名（去掉 _v<n> 后缀）
@version—default 版本对齐现有多版本（_v2）机制
#table.field—整份定义深链到表/列，供 overlay ref 用
与现有存储零冲突
DRN 是标识层，直接映射现有落盘路径 <root>/<domain>/<app>/<module>/<name>_v<version>.json。裸 code 是"全部段继承当前"的退化 DRN——旧档案不改即为合法 DRN。

5.2 imports —— 显式声明跨 DAM 依赖

为避免"引用散落在深处、无法总览一个定义依赖谁"，每个定义顶层增加可选 imports，把跨 DAM 依赖提前声明并起别名（类比代码的 import）：

// gl_md_doc_meta（DOC）顶层 { "imports": [ { "alias": "cc", "drn": "drn:fi/shared-md/masterdata/DCT/cost_center@1" }, { "alias": "cur", "drn": "drn:fi/shared-md/masterdata/DCT/currency" } ], "voucherTables": [{ "tableName": "voucher_detail", "fields": [ { "id": "cost_center_id", "refDict": "@cc" }, // 用别名引用跨应用字典 { "id": "currency_id", "refDict": "@cur" } ] }] }

@cc = 引用 imports 里别名 cc。裸 cost_center 仍合法（本地）。别名让"这个单据依赖哪些外部定义"在顶层一目了然，也是依赖图（§8）与打包/迁移的数据来源。

5.3 可见性与导出（防止越权引用）

跨应用引用一旦可行，就必须治理"谁能被谁引用"。每个定义（或其中的表/字典）声明可见性：

visibility可被谁引用典型场景
private仅本模块内模块内部技术表
app同应用跨模块应用内共享
domain同域跨应用域内主数据（如 fi 域共享科目）
public全平台公共字典（币种、国家）
解析期校验
解析 DRN 时，若目标 visibility 不覆盖引用方所在 DAM → 报 REF_VISIBILITY_DENIED（error）。默认 public（兼容现状：现在所有引用都是隐式全可见），可按需收紧。

06统一注册表与解析服务

三类定义共用一个 MetaDef 注册表 与一个 DRN 解析器——这是"统筹考虑"的落点。

统一存储根

把 meta/definitions（DCT/DOC）与 meta/flexible-combination（FLX）收敛为单一根 meta/defs，按 kind 区分（消除断裂①）：

meta/defs/ └─ <domain>/<app>/<module>/ ├─ DCT/<name>_v<n>.json ├─ DOC/<name>_v<n>.json └─ FLX/<name>_v<n>.json

DAM_TREE_ROOTS 只需把两根合一。旧路径保留读兼容（软链/回退）。

MetaDef 注册表（索引）

启动/保存时扫描，建立 DRN → {path, kind, version, visibility, exports, updatedAt} 索引。提供：

  • resolve(drn, fromDam) → 定义句柄（+ 可见性校验）
  • resolveField(drn#t.f) → 具体列（overlay 编译用）
  • listByKind/DAM → 编辑器下拉数据源
  • dependents(drn) / dependencies(drn) → 依赖图

解析流程

1
归一化：裸 code / 别名 / 相对 DRN → 绝对 DRN（补全继承段、展开 @alias、解析 ..）。
2
版本选择：无 @version → 取该逻辑名的 default 版本（对齐现有多版本机制）。
3
可见性校验：目标 visibility 是否覆盖引用方 DAM，否则 REF_VISIBILITY_DENIED。
4
命中缓存 / 读盘：按 path 读定义（复用现有 loadMetaBatch 批量 + base 字段集去重）。
5
深链：若含 #table.field，展开字段集后定位到列，返回列句柄。
双端一致的关键
解析器与 overlay 编译层放服务端一处（Rust cmx-model/store.rs 或 Node 保存链路）。JS 与 Rust 两套运行时引擎收到的都是已解析、已展开的定义 → 天然一致，不必各写一遍解析逻辑。

08依赖图与真实引用

用真实档案画出统一后的引用关系。左侧为现状（同 DAM 内隐式、跨 DAM 断裂），右侧为目标（DRN 显式跨 DAM）。

现状（fi/cmxfico/gl 内，全部隐式同 DAM）

FLX account DOC gl_md_doc_meta DCT gl_md_dct_meta ├ docRef ───────────▶ voucher_header/entry/detail │ (缺 app 段) ├ refDict:"cost_center" ─┐ (裸 code) ├ dimensions{} ├ refDict:"gl_account" ──┼─▶ dictionaryTables{ │ (拷贝 DCT 10 份) ├ refDict:"currency" ────┘ cost_center,gl_account, ├ fi-cash.fields └ ext_dim1..5 ("由 gl_ext currency,… } │ (拷贝 voucher_detail _dimension 绑定"—注释) │ 20 列) base_doc_meta ◀─ baseDocMetaRef{file} (仅文件名) └ 全部靠"同域同应用同模块"约定解析；跨应用无法表达

目标（DRN 显式，可跨 DAM）

FLX drn:fi/cmxfico/gl/FLX/account ├ docRef: drn:fi/cmxfico/gl/DOC/gl_md_doc_meta@1 ← 补全 app 段 ├ detail.ref: drn:…/DOC/gl_md_doc_meta#voucher_detail.cashflow_item_id │ + over:{edit:{required:true}} ← 引用+增量，不拷贝 └ dimensions: 引用 DCT，不再拷贝 DOC drn:fi/cmxfico/gl/DOC/gl_md_doc_meta ├ imports: [{alias:"cc", drn:drn:fi/shared-md/masterdata/DCT/cost_center}] ← 跨应用！ ├ voucher_detail.cost_center_id.refDict: "@cc" └ baseDocMetaRef: drn:base/_/_/BASE/base_doc_meta@1 DCT drn:fi/shared-md/masterdata/DCT/cost_center (visibility: domain) └ 一份定义，被 fi 域下 cmxfico/其他应用共享引用
这就解决了你的核心诉求
"不同应用、模块间互相引用的字典/单据"——通过 imports + DRN 显式表达：fi/cmxfico/gl 的单据引用 fi/shared-md/masterdata 的字典，解析器按 DRN 定位、按 visibility 授权、按依赖图校验。

09引用治理与诊断

跨 DAM 引用打开后，治理是安全网。复用现有 flexible-combination-validator + _clientDiagnostics 框架，新增引用类诊断码：

code级别触发
REF_TARGET_NOT_FOUNDerrorDRN 解析不到目标定义
REF_FIELD_NOT_FOUNDerror深链 #table.field 的列不存在（单据删列）
REF_VISIBILITY_DENIEDerror目标可见性不覆盖引用方 DAM（越权引用）
REF_CYCLEerrorDRN 依赖成环（A→B→A）
REF_MISSING_IMPORTwarn用了跨 DAM 裸 DRN 但未在 imports 声明（可自动补）
REF_VERSION_FLOATINGwarn跨应用引用未钉版本，default 漂移有风险
REF_DANGLING_ON_TARGET_CHANGEwarn被引用定义变更，下游 overlay 可能失配（依赖图广播）
变更影响分析
因为有 dependents(drn)，修改一个被广泛引用的公共字典时，可在保存前列出所有下游 DOC/FLX，提示影响范围——这是拷贝式模型永远做不到的。

10后端 API 设计

在现有 /api/definitions/* 与 /api/flexible-combination/* 之上收敛出统一的 /api/defs/*（旧路由保留代理）：

方法 · 路由用途
GET/api/defs/list?kind&domain&app&module&visibleFrom按 DAM/kind 列定义；visibleFrom 过滤可引用项（编辑器下拉）
GET/api/defs/resolve?drn&from解析单个 DRN → 定义（含可见性校验、版本选择）
POST/api/defs/batch批量解析 DRN 列表 + base 去重（复用 loadMetaBatch）
GET/api/defs/compile?drn&anchorFLX：解析+overlay 编译→运行时 inline（运行页调用）
GET/api/defs/deps?drn&direction依赖图：dependencies/dependents（可视化 + 影响分析）
POST/api/defs/validate保存前全量校验（结构 + 引用治理 §9）
PUT/api/defs/<drn>保存（写库前跑 validate；overlay 存储形态）

11迁移路线

每步独立可验证、可回退；运行时全程零改动。

1
DRN 解析器 + 注册表（读侧）
地基 · 低风险
实现归一化/版本/可见性/深链解析；建 DRN 索引。裸 code = 退化 DRN → 现有档案零改动即合法。
验证：对现有全部定义建索引，逐一 resolve 现有引用，结果与当前隐式解析一致。
2
存储根合一 meta/defs
低风险
DAM_TREE_ROOTS 两根合一，按 kind 分子目录；旧路径读兼容。
验证：新旧路径双读一致；编辑器列表无缺项。
3
imports + 可见性 + 引用治理
中风险
顶层 imports 与 visibility 落地；§9 诊断码接入保存链路；补 @alias 展开。
验证：构造跨应用引用/越权/断引用/成环用例，断言拦截。
4
Overlay 编译器（承接上一方案）
中风险
FLX ref/use/pick 编译：DOC 列 ⊕ FLX 增量 → inline；DCT 维度引用替代拷贝。
验证：account.json 转 overlay，/compile 结果与现状 diff 等价。
5
编辑器统一：DRN 选择器 + 依赖图
中风险
三个编辑器共用「DRN 跨 DAM 选择器」（按 visibility 过滤）、imports 面板、依赖图视图。
验证：在 FLX 编辑器里跨应用选一个字典，保存、编译、运行页联动通。
6
存量批量迁移
中风险 · 可选
工具识别"与 DOC/DCT 逐键相等"的拷贝字段 → 折叠为 DRN 引用 + overlay；抽取共享字典到 shared-md 应用。
