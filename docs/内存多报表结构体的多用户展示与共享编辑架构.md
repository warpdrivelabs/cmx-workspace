## 一、先分清两件事：文档模型 vs 协同引擎

两个常被混为一谈的概念：

- **文档模型（document model）**——前面设计的那套结构体，是"某一刻表格长什么样"的内存表示。
- **协同引擎（collaboration engine）**——"多个用户并发改它、还要各自看到一致结果"的那套机制。

> **现有结构体是一个相当好的文档模型，但它本身不是协同引擎。**
> 多用户共享编辑能不能做，取决于愿不愿意在它**之上加一层**。

---

## 二、三种能力的可行性

| 能力 | 可行性 | 说明 |
|------|--------|------|
| 内存里承载多张报表（每张一 sheet） | ✅ 现成 | `Workbook.sheets: SlotMap<SheetKey, Sheet>` 已是多 sheet 容器，稀疏存储省内存 |
| 多用户**只读**展示 | ✅ 容易 | 一份共享文档 + 向各前端广播；不复制整表给每个用户 |
| 多用户**共享编辑** | ⚠️ 可行但需加层 | 缺并发控制、操作模型、冲突解决、增量重算——见后文 |

> 关键：**内存里只存一份文档实例**（不是每个用户一份拷贝），内存占用是"每文档"而非"每用户"，稀疏设计让大表也扛得住。

---

## 三、稳定身份设计恰好是协同的优势

这套结构选了"稳定身份行列"，在协同场景里这是**红利**而不是负担：

- cell 用 `(RowKey, ColKey)` 句柄寻址。用户 A 编辑某格，即使用户 B 同时在上面插了一行，A 的编辑**仍然指向正确的格**——句柄不变。
- 公式用 `CellRange{RowKey,ColKey}` 引用，插删行后引用天然不破。

如果当初用的是"位置坐标 (row_index, col_index)"，协同会变噩梦：每次有人插行，所有在途的编辑操作都要做坐标平移变换（OT 里最难写的部分之一）。

> **结论：稳定身份的底子，让这套结构体先天适合协同。**

---

## 四、为协同需要补的四样东西

现有结构体是个"快照"，协同还缺：

### 1. 操作模型（Operation）

编辑必须变成一等公民、可序列化、可传输：

```rust
pub enum Op {
    SetCell  { sheet: SheetKey, at: (RowKey, ColKey), value: CellValue, formula: Option<String> },
    InsertRow{ sheet: SheetKey, after: Option<RowKey>, new: RowKey },   // 显式带新句柄
    DeleteRow{ sheet: SheetKey, row: RowKey },
    SetStyle { /* ... */ },
    // ...
}
```

前端不直接改结构体，而是**发 Op**；服务端应用 Op、广播 Op。

### 2. 并发控制

`SlotMap / HashMap / Vec` 写都要 `&mut`，多用户并发必须串行化（见第五节两种模型）。

### 3. 冲突解决

- 同格双改 → 末写胜（LWW）还是合并？
- 同位置双插行 → `Vec<RowKey>` 的顺序谁先谁后？

这是 `Vec` 顺序表的薄弱点，需明确策略。

### 4. 增量重算

远端改了一格，依赖它的公式要重算。需要依赖图（前文 `cell_dependency`）+ 从变更格出发的增量传播，再把"缓存值变化"广播出去。

### 额外：不该进文档的两样东西

- **视图状态**（滚动位置、选区、筛选）——每连接临时态。
- **presence**（光标/选区高亮）——每连接临时态。

> 这两样放连接层，**别塞进共享 `Workbook`**。

## 五、两条落地路线

### 路线 A：服务端权威 + 单写者（actor 模型）— 推荐默认

```
前端们 ──Op──> [单 task 拥有 Workbook] ──广播 Op/结果──> 前端们
                  顺序处理：应用→重算→分配序号→广播
```

```rust
// 一个 task 独占 Workbook，所有 Op 走 channel 串行进来
let (tx, mut rx) = tokio::sync::mpsc::channel::<(ClientId, Op)>(1024);
tokio::spawn(async move {
    let mut wb = Workbook::new();
    while let Some((who, op)) = rx.recv().await {
        let seq = wb.apply(op.clone());        // 串行 = 天然定序，插行顺序冲突自动消解
        let changed = wb.recalc_from(&op);     // 增量重算
        broadcast(seq, who, op, changed).await; // 广播给所有人
    }
});
```

**优点：**

- **单写者天然串行化**——并发插行的顺序冲突在这里被"谁先到 channel 谁先插"自动解决，不必上 OT/CRDT。
- 这个串行点也是**分配版本号、做重算、记操作日志**的天然位置。
- 没有锁竞争、没有 `RwLock` 中毒问题。
- 对"一个团队几人到几十人共享一张报表"的业务场景，**这就够了**。

**代价：** 所有写经过单点（吞吐有上限，但表格编辑不是高频写，通常不是瓶颈）；离线编辑支持弱。

> 也可以用 `Arc<RwLock<Workbook>>`：读多写少时可行，但要注意**别在持读锁时序列化整张大表**（会饿死写者）——取完需要的区域立刻放锁再序列化。总体不如 actor 干净。

### 路线 B：CRDT — 仅当需要离线/P2P/弱网并发

把文档改造成 CRDT：

- cell 值用 LWW-Register；
- 行列顺序用**序列 CRDT**（分数索引 / RGA / Yjs 那类）；
- 每个站点本地可改、最终收敛。

**适用：** 离线编辑后合并、点对点、超大规模并发。

**代价：** 复杂度高一个数量级，`Vec<RowKey>` 要换成 CRDT 序列，撤销/重做、墓碑回收都得自己处理。

> **没有离线/P2P 硬需求就别上。**

## 六、还要想清楚的几个点

- **slotmap key 的线路传输**：`RowKey` 是进程内稳定，但服务端重启/重载后会重新生成。给前端的协议**不能直接用 slotmap key**，要用自己的稳定 ID（数据库 `id`），或把 slotmap 一起持久化并保证重载后 key 一致。
- **广播的是 Op/diff，不是整表**：每次改都把整个 `Workbook` clone 给所有人会爆。只广播操作或受影响单元格的增量。
- **撤销/重做在协同下是"选择性撤销"**：撤我自己的 Op、不撤别人的——这在 actor + 操作日志上要按用户过滤，比单机难。
- **重算放大**：一格改动可能引发大量公式重算（如 `=SUM(整列)`）。要靠依赖图做增量，并对"巨范围依赖"做节流/批处理。

## 七、结论

| 需求 | 可行性 | 方案 |
|------|--------|------|
| 多 sheet 内存承载 + 多用户**只读展示** | ✅ 现有结构体直接胜任 | 一份文档 + 广播 |
| 多用户**共享编辑** | ✅ 可行 | 补 Op 模型 + 单写者串行化 + 增量重算 + presence 分离 |
| 业务级团队共享编辑 | 推荐 | **路线 A（服务端权威 actor）**，性价比最高，不碰 OT/CRDT |
| 离线 / P2P / 弱网并发收敛 | 仅此场景 | **路线 B（CRDT）** |

**核心判断：**

1. 现有"稳定身份"结构体先天适合协同——cell 句柄寻址、公式句柄引用，插删行不破在途编辑。
2. 它是文档模型，不是协同引擎；共享编辑需在其上加一层（操作模型 + 并发控制 + 冲突解决 + 增量重算）。
3. 绝大多数业务场景用**服务端权威 + 单写者 actor**即可，单写者天然消解并发冲突，无需 OT/CRDT 复杂度。
