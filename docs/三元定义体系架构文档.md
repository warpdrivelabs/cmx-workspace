## 0. 术语与仓库结构

### 0.1 核心术语对照

| 中文 | 术语缩写 | 含义 |
|---|---|---|
| 数据字典 | **DCT** (Dictionary) | 主数据/配置项的定义与实例（如：会计科目、币种、客户） |
| 业务单据 | **DOC** (Document) | 可录入、可流转的多层业务单据（如：会计凭证） |
| 弹性组合 | **FLC** (FlexibleCombination) | 在维度组合锚点上挂载可细分明细 schema（如：科目→辅助核算行） |
| 基础字段集 | **BASE** | 跨模块复用的字段集合，被 DCT/DOC/FLC 引用 |
| 域/应用/模块 | **DAM** | Domain/Application/Module 三级命名空间 |
| 定义资源名 | **DRN** | 跨 DAM 定位、可版本化、可深链的资源标识 |

三元的分工：

| 维度 | DCT | DOC | FLC |
|---|---|---|---|
| **回答什么** | 「有哪些主数据/配置项」 | 「业务单据长什么样、怎么存」 | 「某行数据要展开哪些明细列」 |
| **物理表前缀** | `cf_*` | `cv_*` | （无独立表，规则驱动 DOC/字典列） |
| **表关系** | 扁平 / 自分级 / 关系 | 多层父子树（upper_id 应用指针） | 规则 → CmxColumn[]（不落库） |
| **定义键** | `dictionaryTables[]` | `voucherTables[]` + `voucherSchema` | `dimensions{}` + `rules[]` |
| **前端入口** | 数据字典定义菜单 | 业务单据定义菜单 | 弹性组合管理菜单 |
| **运行期组件** | `<cmx-dict-select>` | `CmxMasterSlave` + grid | `CmxFlexibleCombination` |

## 2. 共享基础设施

三元定义共享一套基础设施，理解它们是阅读后三章的前提。

### 2.1 DAM 命名空间

所有定义按 **Domain / Application / Module** 三级目录组织，对应物理路径：

```
data/meta/definitions/<domain>/<app>/<module>/<kind>/<name>_v<N>.json

例：
data/meta/definitions/fi/cmxfico/gl/DOC/cmxfico_doc_meta_v1.json
data/meta/definitions/fi/cmxfico/gl/DCT/cmxfico_dct_meta_v3.json
data/meta/definitions/base/_/_/BASE/base_doc_meta_v1.json   （BASE 落共享根）
```

DAM 段合法性：`[a-zA-Z0-9_-]{1,64}`（与 `cmx-portal/src/dam/store.rs::is_dam_id` 一致）。

### 2.2 DRN 跨域引用标识

DRN（Definition Resource Name）把三元之间原本「裸 code + 隐式同域」的引用，统一为可跨 DAM、可版本化、可深链的资源名。

**语法**：

```
drn:<domain>/<app>/<module>/<kind>/<name>[@<version>][#<table>[.<field>]]

例：
drn:fi/shared-md/masterdata/DCT/cost_center@1                 跨应用引用字典（v1）
drn:fi/cmxfico/gl/DOC/cmxfico_doc_meta#voucher_detail.cashflow_item_id   深链到列
```

**简写**（省略段 = 继承引用方所在 DAM，兼容既有裸 code）：

```
cost_center          → 全 DAM 段继承 + kind 由上下文推断
DCT/cost_center      → 当前 DAM 下的 DCT
@cc                  → imports 别名（由 normalizeDrn 展开）
```

**核心 API**（`packages/cmx-data-comp/src/lib/drn.js`，纯函数；Rust 端在 `cmx-model` 有对端实现）：

| 函数 | 作用 |
|---|---|
| `parseDrn(input)` | 解析为结构化对象（不补全、不展开别名） |
| `normalizeDrn(input, ctx)` | 补全继承段 + 展开别名 → 绝对 DRN |
| `formatDrn(abs)` | 绝对对象 → 规范字符串 |
| `drnToPath(abs, {withVersion})` | → 落盘相对路径 |
| `drnVisibleFrom(vis, targetDam, fromDam)` | 可见性判定（private/app/domain/public） |
| `effectiveDictId(raw, ctx)` | refDict/dictId 归一为有效 dictId（兼容裸 code） |

`kind` 取值固定为四元：`['DCT', 'DOC', 'FLC', 'BASE']`（`DRN_KINDS`）。

### 2.3 base 字段集（跨模块复用）

`data/meta/definitions/base/` 下有两份基础字段集，业务模块通过 `baseDctMetaRef` / `baseDocMetaRef` 引用其中的 `fieldSets`，避免每张表重复定义审计列、层级列等公共字段。

#### base_dct_meta_v1.json（字典基础）

`metaCode: "base_dct_meta"`，定义 9 个可复用 fieldSet：

| fieldSet | 用途 | 代表列 |
|---|---|---|
| `dictionaryCommonFields` | 字典共用列（有 id） | `id`(BIGINT PK), `code`, `name`, `sort_no`, `status` |
| `dictionaryCommonNoIDFields` | 字典共用列（code 作 PK，如 cf_currency） | `code`(PK), `name`, `sort_no`, `status` |
| `dictionaryHierarchyFields` / `...NoIDFields` | 自分级层级列 | `parent_id`/`parent_code`, `full_path`(512), `level_no`, `is_leaf` |
| `dictionaryAuditFields` | 审计列 | `create_by`, `create_time`, `update_by`, `update_time` |
| `dictionaryScopeFields` | 组织范围隔离 | `scope_type`, `entity_id`(refDict=acct_entity) |
| `dictionaryEffectiveFields` | 生效期 | `effective_from`, `effective_to` |
| `dictionaryDisableFields` | 停用信息 | `disabled_reason`, `disabled_time` |
| `dictionarySystemFields` | 系统预置标识 | `is_system` |
| `hierarchyClosureFields` | 自分级闭包表 | `dict_code`, `ancestor_id`, `descendant_id`, `depth` |
| `relationCommonFields` | 关系字典基础列 | `id`, `code`, `name`, `hierarchy_node_*`, `business_data_*` |

每个字段对象包含：`dataType` / `fieldLength` / `nullable` / `intDigits` / `decimalDigits` / `id` / `name` / `caption.{zh_CN}` / `dimType` / `isPrimaryKey` / `edit.mode`，可声明 `refField`/`displayField`/`refDict` 跨字典引用。

#### base_doc_meta_v1.json（单据基础）

`metaCode: "base_doc_meta"`，定义 6 个 fieldSet：

| fieldSet | 用途 | 代表列 |
|---|---|---|
| `documentTechnicalFields` | 技术主键 + 审计 + 逻辑删除 | `create_by`, `create_time`, `update_by`, `update_time`, `delete_flag` |
| `documentIdentityFields` | 单据业务标识 | `doc_date`, `doc_type_id`(dimension), `doc_no`, `entity_id`(dimension) |
| `documentSourceFields` | 来源/引用/冲销单据 | `source_doc_id`, `source_doc_no`, `ref_doc_id`, `reverse_doc_id` |
| `documentLifecycleFields` | 生命周期 + 附件 + 备注 | `doc_status`, `business_status`, `attach_count`, `remark` |
| `documentCommonFields` | 上述全集组合（`includeFieldSets`） | — |
| `documentLevelFields` | **层级核心三列** | `id`(PK), `upper_id`(父指针), `line_no`(行号) |

> **`documentLevelFields` 是 DOC 层级模型的根基**：`upper_id` 是应用层单层父指针，**不落 DB 外键**，由 `DocLoader` 按它组装嵌套树、`DocSaver` 按它逐层 UPSERT。

### 2.4 模型中心：定义 → 物理表编译

模型中心（`cmx-api/src/handlers/portal/model_center.rs`，2105 行）负责把定义 JSON 编译成 `TableDefine`，再用 `cmx-metadata` 的 `PgTableDefineExecutor` 在目标库 `CREATE TABLE` / `ALTER TABLE`。

**编译入口**（`compile_definition(kind, ...)`，line 455）：按 `kind` 分派：

```
compile_dct(doc, base) -> Vec<TableDefine>   line 202
compile_doc(doc, base) -> Vec<TableDefine>   line 390
```

**列合并规则**（以 `compile_dct` 为例）：每张物理表的列 = 本表 `fields[]` + 七个 `*FieldSet` 引用合并（base/hierarchy/scope/effective/disable/audit/system，外加兜底任意 `*FieldSet` 键），**按列名去重保序**，提取 PK + `uniqueKeys` 唯一索引。

**部署流程**（SSE 流式进度）：

| 端点 | 阶段 |
|---|---|
| `GET /api/model/db-state` | 查询目标库已部署模块与版本 |
| `POST /api/model/init[-plan-stream|-stream]` | 数据库初始化（建模型中心台账表） |
| `POST /api/model/deploy[-plan-stream|-stream]` | 模块部署（编译定义 → 建表 → 灌种子） |

**变更策略**：`table_change_plan()`（line 660）采用 **additive-only**（只加列不删列），避免误删生产数据。模型中心还会维护台账表 `cmx_model_meta` / `cmx_model_module` / `cmx_model_deploy_history` / `cmx_model_source` / `cmx_model_registry`，记录每个定义文件的编译快照、checksum、版本。

## 3. DCT 数据字典定义

### 3.1 定位

DCT 解决「主数据/配置项如何定义、如何存储、如何检索选择」的问题。它有**两套并行的后端服务**，分别对应「配置型字典」与「业务主数据字典」两种场景。

### 3.2 元模型（定义 JSON）

以 `cmxfico_dct_meta_v3.json` 为权威样板（参考 SAP 会计凭证 32 张字典）：

```jsonc
{
  "docMeta": {
    "metaCode": "FICO",
    "metaName": "cmx-fico 会计凭证数据字典元数据",
    "metaKind": "DCT",
    "version": 3,
    "designStyle": "separate-dictionary-tables",
    "isDefault": true
  },
  "baseDctMetaRef": {
    "file": "base_dct_meta_v1.json",
    "version": 1,
    "fieldSets": ["dictionaryCommonFields", "dictionaryHierarchyFields",
                  "dictionaryAuditFields", "dictionaryEffectiveFields", ...]
  },
  "dictionaryTables": [
    {
      "dictMeta": {
        "dictCode": "client",
        "dictName": "客户端",
        "dictKind": "CLASSIFY",          // ★ 5 种字典类型之一
        "selfHierarchy": false,           // ★ 是否自分级
        "tableName": "cf_client",
        "idField": "id", "codeField": "code", "labelField": "name",
        "codeLength": 3
      },
      "fields": [ /* 本表自有列，可带 refDict/refField/displayField 跨字典引用 */ ],
      "baseFieldSet": "dictionaryCommonNoIDFields",
      "auditFieldSet": "dictionaryAuditFields",
      "codeRule": { "mode": "...", "pattern": "...", "uniqueCheck": true },
      "uniqueKeys": [["code"]],
      "permissionScope": { ... }
    }
  ]
}
```

#### 5 种 dictKind（字典类型）

| dictKind | 含义 | 典型例 |
|---|---|---|
| `BUSINESS` | 业务字典（主数据） | 客户、供应商、币种、银行 |
| `CLASSIFY` | 分类字典 | 客户端、科目类别 |
| `GROUP` | 分组字典 | 科目组 |
| `RELATION` | 关系字典（多对多） | 客商-科目关系 |
| `ENUM` | 枚举字典 | 凭证类型、单据状态 |

定义见 `documents/20260825_dct_数据字典分类分组分级设计方案.md` 与 `portal-definition-manager.js:148` 的 `DICT_KINDS`。

### 3.3 后端：两套并行服务

#### 服务 A：轻量检索引擎（`/api/portal/dict/*`）

**实现**：`cmx-container/crates/libs/cmx-model/src/dict/`，**JSON 文件存储**（`data/dict/registry.json` + `data/dict/entries/<DAM>/<dictId>.json`）。

适用场景：配置型/枚举型字典、需要全文模糊检索/SCD 停旧启新/多字典联查的场景。

| 文件 | 职责 |
|---|---|
| `dict/schema.rs` | DictSchema 注册表（dictId/hierarchical/idField/parentField/labelField/fullTextFields） |
| `dict/repo.rs` | 条目仓库 + 内存检索引擎（树形过滤 + 通配符正则 + SCD 有效性 + CJK fuzzy + Levenshtein + 分页） |
| `dict/write.rs` | 写入服务（upsert 时拓扑计算 level/path/fullText；SCD deactivate/supersede） |
| `dict/tree.rs` | 结果转换（平铺 hits → 树形 forest） |
| `dict/multi.rs` | 多字典联查（递归 exec_node + join_children，分批 MAX_JOIN_BATCH=200） |
| `dict/api.rs` | 路由编排薄封装 |

#### 服务 B：物理表 CRUD（`/api/portal/dct/*`）

**实现**：`cmx-container/crates/libs/cmx-api/src/handlers/portal/dct.rs`（1115 行），**直读/写 `cf_*` 物理表**（tokio-postgres 驱动）。

适用场景：业务主数据字典（会计科目、成本中心等），数据量大、需要事务/乐观锁/列级校验。

核心结构：

```rust
DctQuery { domain, application, module, file, dict }   // 共用坐标
DictView {
  dict_code, dict_name, table_name,
  id_field, code_field, label_field, parent_field, self_hierarchy,
  columns: Vec<DictColumn>,
  pk,
  spec: Arc<TableSpec>,    // 列级校验规范
}
```

`resolve_dict(q)` 读 DCT 定义 + base fieldSet，合并 own fields + 七个 `*FieldSet`（去重保序），构建校验 `TableSpec`。

#### 两套服务对照

| 维度 | `/dict/*`（服务 A） | `/dct/*`（服务 B） |
|---|---|---|
| 存储 | JSON 文件 | PG 物理表 `cf_*` |
| 适合 | 配置型/枚举型 | 业务主数据 |
| 检索 | 全文/CJK模糊/Levenshtein/树形/多字典联查 | ILIKE 模糊 + parentId 树过滤 |
| 高级能力 | SCD 停旧启新/铸号 | 事务回存/乐观锁/列级校验/changeset |

## 4. DOC 业务单据定义

### 4.1 定位

DOC 解决「可录入、可流转、可多层嵌套的业务单据如何定义、如何装载、如何回存」的问题。典型实例是**会计凭证**（4 层：批→头→科目行→辅助行）。

### 4.2 元模型（定义 JSON）

以 `cmxfico_doc_meta_v1.json` 为权威样板：

```jsonc
{
  "docMeta": {
    "metaCode": "FICO",
    "metaName": "cmx-fico 会计凭证单据元数据",
    "metaKind": "DOC",
    "version": 1,
    "designStyle": "separate-dictionary-tables",
    "organizationDict": "comp_unit",
    "keyDicts": "gl_account",
    "documentTypeDict": "doc_type",
    "versioning": { "enabled": true }
  },
  "baseDocMetaRef": {
    "file": "base_doc_meta_v1.json",
    "version": 1,
    "fieldSets": ["documentIdentityFields", "documentSourceFields",
                  "documentLifecycleFields", "documentTechnicalFields", "documentCommonFields"]
  },
  "voucherCommonFieldSet": "documentTechnicalFields",
  "voucherSchema": {
    "schema": [
      [ {"id":"cv_batch",     "level":"L1", "levelName":"凭证批"} ],
      [ {"id":"cv_header",    "level":"L2", "levelName":"凭证头"} ],

      // 6 币种金额逐层上卷
    ]
  },

      "fields":[ /* 本层业务字段 */ ],

      "summaries":[ /* 汇总表 */ ] }
    // ... cv_header / cv_acc_line / cv_aux_line
  ]

```

#### 关键设计

- **层级模型**：节点层级 = `单据(document) → 层/表(level/table) → 字段(field)`。`schema` 是二维数组，外层按 level 排序，内层允许同层并列表（如 L4 的 cv_aux_line + cv_cyzb_line）。
- **父子关系**：通过 `upper_id`（应用层单层父指针）组装嵌套树，**不落 DB 外键**，避免硬耦合。
- **聚合上卷**：`aggregations` 声明子层字段 sum 到父层（如科目行借贷额上卷到凭证头）。
- **状态机**：可选 `statusFlow` 声明单据状态流转。
- **校验规则**：`validationRules` 透传到后端，保存期由 `rule.rs` 引擎执行。

#### 4.2.1 单据级字典角色声明（organizationDict / keyDicts / documentTypeDict）

`docMeta` 里除了模块元信息，还有三个"单据级字典声明"：

```jsonc
"docMeta": {
  "organizationDict": "comp_unit",      // 组织字典
  "keyDicts": "gl_account",             // 关键字典（逗号分隔可多选）
  "documentTypeDict": "doc_type"        // 单据类型字典
}
```

这三个字段容易跟"字段上的 `refDict`"混淆，必须把概念层次分清楚。

**概念层次：字典类型分类 → 字段级 refDict → 单据级角色声明**

| 层次 | 字段 | 含义 | 粒度 | 谁消费 |
|---|---|---|---|---|
| ① 字典类型分类 | DCT 的 `dictMeta.dictKind` | 这本字典"是什么性质"（业务/分类/分组/关系/枚举） | 一本字典 | DCT 定义中心 Tab 分组 |
| ② 字段级引用 | 字段的 `refDict` | 这一列"引用哪本字典"存外键值 | 一个字段 | 下拉、显示翻译、依赖图、FLC 维度识别 |
| ③ 单据级角色 | `organizationDict` / `keyDicts` / `documentTypeDict` | 整张单据"核心业务维度是什么" | 整张单据 | 定义中心标注（后端预留扩展点） |

第①层在 §3.2 已讲（5 种 dictKind）。第②层贯穿 DCT/DOC/FLC 三端（见 §3.5 refDict）。本节专讲第③层。

**三个角色的业务语义**

| 声明 | 业务含义 | 凭证实例 |
|---|---|---|
| **组织字典** | 单据的业务隔离边界——按谁分账、谁的权限范围 | `comp_unit`（公司代码）：凭证按公司分账，跨公司不混账 |
| **单据类型字典** | 单据的分类驱动——决定编号规则、状态流分发 | `doc_type`（凭证类型）：收/付/转凭证走不同编号段与审批流 |
| **关键字典** | 单据的核心分析轴——围绕什么维度展开 | `gl_account`（会计科目）：凭证一切行围绕科目展开 |

**与字段 refDict 的关系：角色声明是 refDict 的"提纯"**

单据可能有几十个字段都带 `refDict`（科目、客户、供应商、币种、部门…）。单据级角色声明做的事情是：**从这片字段引用里，挑出扮演特殊角色的那几个**，给它们贴上"主角"标签。普通字段引用是"群众演员"，这三个是"主角"。

关键约束：**候选来源 = 字段已引用的字典**。定义中心（`portal-definition-manager.js:779` `_docReferencedDictCodes`）扫描单据所有层的字段 `refDict` 去重后作为候选——不能凭空指定一个单据里没有任何字段引用的字典当主角：

```js
// portal-definition-manager.js:778-796 —— 候选 = 扫描所有层字段的 refDict 去重
_docReferencedDictCodes () {
  const tables = this._doc?.voucherTables || []
  for (const t of tables) {
    for (const fsName of (t.documentFieldSets || [])) {
      for (const f of (this._baseFieldSets?.[fsName] || [])) add(f.refDict)  // base 字段集引用
    }
    for (const f of (t.fields || [])) add(f.refDict)                          // 本层字段引用
  }
  return out
}
```

这保证了一致性：不会出现"组织字典声明了 X，但单据里没有任何字段引用 X"的悬空声明。

**字典关联闭包传播（二阶价值）**

`_docRelatedDictCodes`（`portal-definition-manager.js:805-821`）在"直接引用"基础上做闭包传播：A 字典引用 B、B 引用 C，则 A 关联 C。这让定义中心能展示"这本单据涉及的完整字典网络"，而不只是表面那几个：

```js
// 闭包算法：related 集合反复扩散直到不动点
while (changed) {
  for (const code of Object.keys(this._dictRefMap || {})) {
    const refs = this._dictRefMap[code] || []
    if (related.has(code) || refs.some(r => related.has(r))) {
      related.add(code); refs.forEach(r => related.add(r))
    }
  }
}
```

**后端消费现状：纯设计期标注，预留扩展点**

`organizationDict` / `keyDicts` / `documentTypeDict` 在 cmx-container 后端**零引用**（`cmx-biz::doc` 和 `model_center` 都不读）。它们目前纯粹是定义中心的配置标注，但设计意图是给运行期框架留扩展点：

- `organizationDict` → 数据权限隔离（运行期按组织过滤可见数据）、多账簿切换
- `documentTypeDict` → 编号规则路由（不同单据类型不同编码段）、状态流分发
- `keyDicts` → FLC 弹性组合的锚点候选、BI 多维分析的核心维度

现在只是把"角色"记下来了；等运行期框架需要时，读这三个字段就能拿到角色，不用再回头扫描字段定义。属于"先声明、后接线"的前瞻性设计。

## 5. FLC 弹性组合管理

### 5.1 定位

FLC 解决「某行业务数据，按其维度组合，要展开哪些可录入的明细列」的问题。它是**领域无关的元数据驱动框架**——财务的「科目 → 辅助核算行」、交易的「交易类型 + 产品类型 → 行项目」都只是它的实例。

> FLC 的规则**不落独立物理表**，它在运行时把 rule 编译成 `CmxColumn[]`，写入目标 `CmxColumnModel`，驱动 DOC/字典的明细 grid。

### 5.2 元模型

```
Dimension（维度）──< Attribute（属性）          Measure（度量）
   │ 携带一组属性                                   │ input | computed
   ▼
DimensionTuple（维度组合 = 锚点 anchor）
   财务 [account]  /  交易 [txType, productType]
   ▼
SubdivisionRule（细分规则）  anchor(match) ──► detail.fields[]
                                                 ▼
                                         FieldSpec（三态字段）
                                         + display + edit + formula + validations
```

| 实体 | 含义 | 关键字段 |
|---|---|---|
| Dimension | 一条核算/分析轴 | `code`, `name`, `valueType`, `valueSourceId`, `attributes[]` |
| DimensionTuple | 维度的有序组合 = 锚点 | `dimensions: string[]` |
| SubdivisionRule | 锚点 → 明细 schema 映射 | `id`, `anchor{dimensions, match}`, `detail{fields}` |
| FieldSpec | 明细中一列，三态之一 | `code`, `kind`, `caption`, `dataType`, `source`, `defaultFrom`, `edit`, `formula`, `dependsOn`, `validations`, `display`, `unitField`, `column` |

#### 字段三态（FieldSpec.kind）

| kind | 取值来源 | 典型例 | edit.mode | 进公式 |
|---|---|---|---|---|
| `dimension` | 从维度主数据选一个值 | 客户/供应商/产品/币种 | `ref`/`select`/`tree-ref` | 属性可被带出 |
| `attribute` | 从已选维度值自动带出 | 产品→规格、产品→计量单位 | `readonly`（或带出后可改） | 可作输入 |
| `measure` | 数值，输入或计算 | 单价/数量（input）；金额（computed） | `input`/`computed` | 是 |

FieldSpec 统一结构：

```jsonc
{
  "code": "amount", "kind": "measure", "caption": "金额", "dataType": "number",
  "valueSourceId": "customerMaster",          // kind=dimension：值主数据
  "source": { "dimension": "product", "attribute": "spec" },          // kind=attribute：从哪带出
  "defaultFrom": { "dimension": "product", "attribute": "price" },    // measure 默认值来源
  "edit": { "mode": "computed", "required": false },
  "formula": "unitPrice * quantity",
  "dependsOn": ["unitPrice", "quantity"],
  "validations": [ { "expr": "quantity > 0", "message": "数量须大于 0" } ],
  "display": { "decimals": 2, "thousand": ",", "zeroBlank": true, "negativeColor": true, "align": "right" },
  "unitField": "uom",
  "column": { "width": "120px", "frozen": false, "agg": "sum" }     // 透传到 CmxColumn
}
```

### 5.5 运行时核心引擎（cmx-data-comp）

#### FlexibleCombinationEngine（`src/lib/flexible-combination-engine.js`，693 行）

领域无关的核心引擎，将「锚点维度组合 → 细分明细架构」元数据解析为 `CmxColumn[]`。

```js
new FlexibleCombinationEngine({ dimensions, rules, docTables?, dictOf?, from?, imports? })

resolveRule(anchorValues)              // 单条最具体 rule（精确值>维度属性>默认）
resolveMergedRule(anchorValues)        // ★ 生产默认：合并所有命中规则字段
buildColumns(rule)                     // -> CmxColumn[]
buildMembers(rule)                     // -> (CmxColumn|CmxColumnGroup)[]  含分组
buildColumnModel(rule, combination)    // -> CmxColumnModel
buildAllFieldSets(rule, combination)   // 多套表字段集（多表 FLC）
onPickDimension(row, fieldCode, code, rule)  // 选维度后带出属性 + 默认度量
recompute(row, rule)                         // 按 dependsOn 拓扑序重算 computed measure
validate(row, rule)                          // -> { valid, errors:[{code,message}] }
```

**匹配评分**（`specificity = score*100 + 锚点维度数`）：精确等值（score 3）> 维度属性匹配（score ~1）> 通配兜底（score 0）> 不符淘汰（score -1）。

**字段合并语义**（`resolveMergedRule`）：所有 score≥0 的命中规则全部参与，字段按 `code` 合并：同名字段取 specificity 高者胜出；同分取规则定义顺序靠前者；输出按「首次出现」排列（布局稳定）。

## 6. 后端处理逻辑详解

> 本章深入 cmx-container 后端的真实算法、SQL 构造与流程实现。所有引用均为 `cmx-container/` 仓库内的 `file_path:line_number`。
>
> **核心设计思想**：后端是「元数据驱动」引擎——定义 JSON（dataType/fieldLength/nullable…）既是建表 DDL 的源，也是落库前列级校验的源（`validation::field_to_spec` 与 `model_center::field_to_column` **同源同规则**），故「按定义校验」等价「与真实表列一致」。

### 6.0 两条独立的后端链路

DCT 有两条并列后端链路，务必区分：

| 维度 | JSON 检索引擎（`/api/dict/*`） | PG 物理表（`/api/dct/*`） |
|---|---|---|
| 代码 | `cmx-model/src/dict/{repo,write,multi,tree,schema}.rs` | `cmx-api/handlers/portal/dct.rs` |
| 存储 | `data/dict/entries/*.json` + `registry.json` | PG `cf_*` 物理表 |
| 检索 | 全量读入内存 + retain 过滤 + CJK/Levenshtein 模糊 | 参数化 SQL `ILIKE` + LIMIT/OFFSET |
| 铸号 | `next_surrogate_id`（max+1，软） | `cmx_utils::next_pk_id`（52 位雪花） |
| SCD | deactivate/supersede（status/valid_from-to） | backfill status=1；乐观锁 update_time baseline |
| 校验 | 无（JSON 宽松） | `validate_insert_row/update_fields` |

DOC 只有 PG 物理表一条链路（`/api/doc/*`）。FLC 不落业务物理表，规则存 JSON 档案，运行时编译成 `CmxColumn[]`。

### 6.1 DCT 后端：JSON 检索引擎

代码：`cmx-model/src/dict/repo.rs`。面向 `dict/entries/*.json` + `registry.json`，**全量读入内存后逐行 retain 过滤**。

#### 6.1.1 DAM 分层路径解析（兜底逻辑）

`entries_path_candidates`（repo.rs:73-86）：
1. 先构造扁平路径 `entries/<dictId>.json`
2. 若 schema 带 DAM（domain/app/module 三者齐全）→ 构造分层路径 `entries/<domain>/<app>/<module>/<dictId>.json`
3. 返回顺序：**schema 带 DAM → [分层, 扁平]（分层优先）；否则 → [扁平]**

`load_entries`（repo.rs:89-96）按候选顺序依次尝试，首个返回数组的即采用；都 miss → 空数组。`save_entries` 只写候选路径首项（schema 决定的主路径）。

#### 6.1.2 检索主流程 `search`（repo.rs:227-364）

步骤（顺序敏感，每步在前一步结果上 `retain`）：

```
1. load_entries 全量读入
2. 元数据兜底（idField 默认 id；hierarchical 默认 false；parentField 默认 parentId）
3. 显式主键查询识别：filters[idField] 有非空值 → explicit_key_lookup=true（按主键取码时放宽 SCD 过滤）
4. 树形过滤（仅 hierarchical）：
     parentId IS NULL → 保留根级
     parentId = 值   → 保留直接子节点
     ancestorId      → 保留 row.path 数组中含该值的行
5. 属性过滤 filters：
     值为数组   → IN 语义（值在集合内）
     值含 '*'   → glob 正则（*→.*，其余元字符转义，不区分大小写）
     否则       → 等值
6. SCD 有效性过滤（!explicit_key_lookup 时）：
     给 as_of → 保留 valid_from <= as_of && as_of < valid_to（闭-开，缺侧判 true）
     否则 !include_inactive → 今日基准：status==1 && (valid_to 缺 || today < valid_to)
7. 全文/模糊（q 非空）：每行算 row_full_text（fullText 字段或拼全部值小写化），然后
     子串包含 → 命中
     cjk_ratio >= 0.5 → fuzzy_match_cjk
     term 长度 2~8 → levenshtein <= 2
8. 排序（默认 sortKey 升序，desc 反转）
9. 分页（from=(page-1)*pageSize, skip+take）
```

#### 6.1.3 CJK 子序列模糊匹配 `fuzzy_match_cjk`（repo.rs:186-206）

```
if text.contains(term) → true
if term 字符数 < 2 → false
对 term 每个位置 i：构造「去掉第 i 个字符」的子串 sub（允许漏掉一个字）
  若任一 sub 是 text 的子序列（is_subsequence 双指针）→ true
否则 false
```

`cjk_ratio`（repo.rs:158-168）：CJK 区间 `\u4e00-\u9fff` + 扩展 A `\u3400-\u4dbf` 字符数占比。

#### 6.1.4 Levenshtein 距离（repo.rs:129-155）

带早停的滚动数组 DP：

```
快速命中：text.contains(pattern) → 返回 0
若 pattern.len() > text.len() → 返回 pattern 长度
经典双行 DP：prev/curr 滚动，curr[j] = min(匹配+0, 删+1, 插+1)
两处优化：
  ① text 截断到前 300 字符防爆
  ② 早停：每行算完若 min(curr) > 2 → 直接返回 3（调用方只关心 <=2）
```

调用处不取具体距离，只判 `<=2` 作命中阈值。

### 6.2 DCT 后端：字典写入与 SCD（write.rs）

#### 6.2.1 upsert 主流程（write.rs:45-108）

```
if rebuild=true（全量重建）:
  big_query(page_size=99999, include_inactive) 拉全量
  merge_by_id（existing 在前、incoming 覆盖，保持 existing 顺序）
  build_tree_fields 全量拓扑
  upsert_entries

else（增量）:
  建 batch_map: id → entry（本批）
  收集本批非空 parentId，减去本批 id → external_parent_ids（父不在本批）
  对 external_parent_ids 跑一次 search（filters[idField]=数组），把父行塞进 enriched_map
  enrich_batch 递归补树字段
  upsert_entries
```

#### 6.2.2 拓扑计算 `build_tree_fields`（write.rs:133-208，全量 DFS+记忆化）

```
visit(id):
  已 visited → 返回
  取 parentId：
    非空且在 map 中 → 递归 visit(parentId) 得 (plevel, ppath)
                       本节点 level = plevel+1, path = ppath ++ [id]
    否则 → (1, [id])（根）
  写入 computed[id] = (level, path)
回写每节点：level / path（数组）/ pathStr = path.join("/") / sortKey / fullText
```

增量 `enrich_batch`（write.rs:211-288）**带循环保护**：先在 enriched_map 插入 `id → None` 占位，再递归父；若依赖链绕回自身，第一步直接返回占位 None（视为无父→根），打断循环。

#### 6.2.3 SCD 停用 `deactivate`（write.rs:304-329）

```
get_by_key（按 code 精确匹配）找不到 → 404
valid_to 缺省 = 今日
patch：status=0, valid_to=vt, 可选 successor_code
upsert_entries 写回
```

#### 6.2.4 SCD 停旧启新 `supersede`（write.rs:332-399）

```
old==new → 400；get_by_key(old) 找不到 → 404
cut = as_of 或今日
新码构造：已存在则沿用；否则 clone_business(old_row)（剥主键/树辅助/生命周期字段）
新码 patch：status=1, valid_from=cut, valid_to=null, predecessor_code=oldCode
新码铸号：is_new 且 id 非数字 → next_surrogate_id 回填
旧码 patch：status=0, valid_to=cut, successor_code=newCode
落库：新码 upsert（先 strip_tree_aux 重算树字段）；旧码 upsert_entries
```

#### 6.2.5 代理键铸号 `next_surrogate_id`（write.rs:401-412）

```
拉全量 → 找 id（i64）最大值 max
max==0 → 起点 1000000，否则 max
返回 max+1
```

> 注意：这是 JSON 字典的「软」铸号（非分布式安全）；PG 物理表链路用 `cmx_utils::next_pk_id`（52 位雪花）。

### 6.4 DCT 后端：PG 物理表 CRUD（dct.rs）

#### 6.4.1 `resolve_dict` 合并 own + 七个 *FieldSet（dct.rs:75-223）

4. pk 判定：① isPrimaryKey 标记列 ② 否则 idField ③ 否则 codeField
5. 构建校验规范 TableSpec（缓存键 spec_key(domain,app,module,file,table,version)，

> `compile_dct`（建表侧）与 `resolve_dict`（运行时侧）的列合并**同源同规则**，但 compile_dct 多一个「兜底扫描任意 *FieldSet 键」的前向兼容逻辑。

#### 6.4.2 `build_search_sql`（dct.rs:415-494）

```sql
SELECT "col1","col2",... FROM "<tableName>"
 [WHERE "<parentField>" IS NULL                       -- parentId 显式 null
        AND "<filterCol>" = $1                         -- filters 等值（null→IS NULL）
        AND ("<codeField>" ILIKE $p OR "<labelField>" ILIKE $p)   -- q 模糊（同一 $p 绑两处）
 ]
 [ORDER BY "sort_no", "<pk>"]                          -- 有 sort_no 列时双排序
 LIMIT <pageSize> OFFSET <offset>
-- 计数：SELECT COUNT(*) AS cnt FROM "<tableName>" [WHERE ...]
```

拼装规则：
- **列白名单**：所有动态拼列名先过 `valid_col`（view.columns 含该列名才合法），**防 SQL 注入**
- **q**：trim 后非空，code & label 都合法时，同一个 `$p` 绑定两处 `ILIKE '%kw%'`
- **排序**：有 sort_no 列 → `ORDER BY "sort_no", "pk"`；否则单 pk
- **分页**：page 默认 1，pageSize 默认 500、clamp(1,5000)，offset=(page-1)*pageSize

#### 6.4.3 铸号 `mint_ids_for_inserts`（dct.rs:307-338，两遍）

```
pk_is_generated：pk 列 dataType 含 "INT" → 需铸号；code(VARCHAR) 作 PK 的 NoID → 不铸号
is_temp_id：None/Null/空串/非纯数字串 → 临时；纯数字 → 真号

第一遍（铸号）：
  对每行，pk 当前值 is_temp_id → cmx_utils::next_pk_id()（52 位雪花，JSON 安全 < 2^53）
  row[pk] = new_id；旧值能转 key → id_map[oldKey] = new_id
  已带真数字 id 的行不重铸（编辑/重存，幂等）

第二遍（自引用修正）：
  对每行 parentField 值，若在 id_map 中 → 替换为父的真号（同批新建父子行的自引用修正）
  指向已存在父的不变
```

#### 6.4.4 `build_upsert_sql`（dct.rs:758-837）—— INSERT ... ON CONFLICT DO UPDATE

```sql
INSERT INTO "<tableName>" ("col1","col2",...,"create_time","update_time","sort_no","status",...)
VALUES ($1, $2, ..., NULL, now(), 0, 1, ...)        -- null 用字面量 NULL，常量列用 SQL 字面量
ON CONFLICT ("<pk>") DO UPDATE SET "col1" = EXCLUDED."col1", ..., "update_time" = now()
                                   -- 无可更新列时 DO NOTHING
```

构造规则：
1. **列筛选**：`valid_col && !is_server_managed_col`（create_time/update_time 拒绝客户端值）
2. **逐列**：
   - null 值 → placeholder 用字面量 `NULL`（**不占参数位**）。**原因**：tokio-postgres 无法为裸 NULL 参数推断列类型，会报 "error serializing parameter"；用字面量让 PG 按列定义取 NULL。典型：自分级根级 parent_id=null
   - 非 null → `$i`（i 递增），push 参数
   - 非 pk 列 → updates 追加 `"col" = EXCLUDED."col"`
3. **backfill 常量列**（`provided` 未给的才补）：
   - `create_time=now()`（仅 insert）、`update_time=now()`（insert+update 都刷）
   - `sort_no=0`、`status=1`、`is_system=0`、`is_leaf=1`、`level_no=1`、`effective_from=CURRENT_DATE`
   - 仅当 `valid_col(name)` 才补（表里没这列不硬塞）
4. **full_path 兜底**：表有 full_path 列、未提供、且有 code 值 → 用 code 值再绑一个参数
5. updates 空 → `DO NOTHING`；否则 `DO UPDATE SET ...`

#### 6.4.5 常量

- `SERVER_FILLED_COLS`（dct.rs:740-751）：`create_by/update_by/sort_no/status/is_system/is_leaf/level_no/effective_from/full_path/delete_flag` —— 校验 NOT NULL 时跳过（row 未给时服务端 backfill），但用户给了值仍校验类型/长度
- `SERVER_REPLACED_COLS`（dct.rs:754）：`id/create_time/update_time` —— **完全跳过值校验**（id 是铸号占位、时间是 backfill）

#### 6.4.6 `dct_save` changeset 事务回存（dct.rs:888-1099）

body：`{ saveMode:"merge", changes: { <dictCode|tableName>: { inserted, updated:[{id,fields,baseline}], deleted:[ids] } } }`

```
1. 分桶（dictCode 或 tableName，单桶取第一个）
2. 开事务前校验：dct_validate_bucket 一次回报全部 violation → 有则返 422
3. 开事务：get_transaction_context().begin(db_id)
4. dct_save_apply：
   deleted：逐 id DELETE FROM "t" WHERE "pk" = $1
   inserted：铺平 → mint_ids → 逐行 build_upsert_sql
   updated：
     set_parts 只收白名单列（排除 pk + 服务端托管时间列）
     有 update_time 列 → 塞 "update_time" = now()
     乐观锁：row 带 baseline 且表有 update_time → AND "update_time" = $i
     SQL：UPDATE "t" SET ... WHERE "pk" = $pk [AND "update_time" = $baseline]
     冲突判定：加了 lock_clause 但 n==0 → conflict=true（→409）
     成功且有 update_time → SELECT "update_time" WHERE pk=$1 回读新值塞 updatedAt[] 供前端刷新基线
5. 成功 commit；异常 rollback
```

### 6.5 列级校验引擎（cmx-biz/src/validation/mod.rs）

#### 6.5.1 结构体

- `ColumnSpec`（mod.rs:31-50）：name、caption、field_type、raw_type（TINYINT/INT/BIGINT 用于范围）、length、precision、scale、nullable、is_primary_key
- `TableSpec`（53-61）：table、columns（HashMap）、order（保序）
- `ValidateOptions`（211-223）：`server_filled`（仅影响 NOT NULL）、`server_replaced`（完全跳过）、`check_unknown`、`check_not_null`（insert true / update false）

#### 6.5.2 `validate_insert_row`（mod.rs:228-294）

```
1. server_replaced 列（id 铸号、时间戳）完全跳过
2. 逐列校验值 validate_value（replaced 跳过；未知列 check_unknown 时报错；否则 validate_value）
3. check_not_null 时：遍历 spec.order，跳过 nullable/pk/filled 列；
   row 缺失/Null/空串 → NotNullViolation（空串视作未填）
```

`validate_update_fields`（mod.rs:297-338）：只校验出现的列，不做整表 NOT NULL；非空列显式设 null → 报错。

#### 6.5.3 `validate_value`（mod.rs:341-480）单值校验

| 类型 | 校验 | 错误码 |
|---|---|---|
| String/Text | `chars().count() > length` | ValueTooLong |
| Int | 解析 i128；`int_range(raw_type)`：TINYINT -128~127、SMALLINT ±32767、INT i32、BIGINT i64 | NumericOutOfRange / TypeMismatch |
| Float | 解析 f64 | TypeMismatch |
| Decimal | `decimal_digits` 算整数位/小数位；`frac > scale`→DecimalScaleExceeded；`int > precision-scale`→NumericOutOfRange | |
| Date | NaiveDate::parse(%Y-%m-%d) | InvalidDate |
| DateTime | RFC3339 / `%Y-%m-%dT%H:%M:%S` / `%Y-%m-%d %H:%M:%S` / 带小数秒 | InvalidDate |
| Bool/Json/Uuid/Binary | 不强校验（DB 兜底） | — |

#### 6.5.4 缓存

### 6.7 DOC 后端：DocSaver 回存（saver.rs）

代码：`cmx-biz/src/doc/saver.rs`（1984 行）。这是 DOC 后端最复杂、最核心的模块。

#### 6.7.1 核心结构体

```
SaveMode { Merge, Replace }                    // merge=增量changeset / replace=先删后插整树
SaveCtx { actor_id, actor_name, doc_file, op_override }
SaveResult { ok, mode, affected, updated_at: Vec<UpdatedBaseline>, id_map }  // 乐观锁基线刷新 + 临时id→真id
AuditCtx { actor: i64, now: DateTime<Utc> }    // 服务端权威时间戳
```

#### 6.7.2 save() 整体流程（saver.rs:142-180）

```
1. mm.get_transaction_context() 获取事务上下文
2. ctx.begin_with_guard(db_id) 开启事务，拿到 guard + txn_id
3. apply_and_version()（事务内一体：写入 + 版本快照 + 算基线）
4. 成功 → guard.commit()；失败 → guard.rollback()
```

#### 6.7.3 apply_and_version（saver.rs:283-325）

```
1. 构造 AuditCtx（now=Utc::now()，本单据全程共用一个时间戳）
2. 后端首次存储铸号（仅 merge）：
   收集本单据全部 childKey（去重）：meta.relations 的 child_key + upper_id
   mint_ids_for_changeset(changes, &child_keys) → (改写后 changeset, idMap)
3. 按模式分派：Merge → apply_merge；Replace → apply_replace
4. record_versions（仅 versioning_enabled 时记版本快照）
5. new_root_baselines（算本次已更新根行的新基线）
```

#### 6.7.4 apply_merge（saver.rs:329-408）—— ★ 关键顺序：父先插更、子先删

```
1. assert_all_keys_matched（H1 静默零写防护）：changes 每个 key 必须能对上某一层
2. validate_changeset（落库前列级校验）：逐层 inserted 整行 + updated 字段；违规 → BizError::validation（→422）
3. 父先：按 layer_order 正序
   每层 inserted → upsert_rows；updated → update_rows（乐观锁仅根层 idx==0 传 oplock=true）
4. 子先：按 layer_order 逆序
   deleted → delete_ids（幂等，不纳入严格对账）
5. 对账（H1/H2）：write_affected < write_expected → 报错回滚（UPDATE 命中 0 行 = id 不存在/被并发删）
```

#### 6.7.5 apply_replace（saver.rs:412-477）—— 先删子树再全量插

```
从 snapshot 收集 rootId（根层 rows 的 id）
先删：子先父后，沿 upper_id 链圈定 rootId 子树，调 delete_subtree_layer（方案 E：子查询链，零预 SELECT）
再插：父先，按 snapshot 各层 rows 批量 insert_rows
```

#### 6.7.6 delete_subtree_layer 子查询链算法（saver.rs:739-797）

对 layer_order 中第 i 层，构造 WHERE 子查询链上溯到根层：

```sql
-- 根层（第 0 层）
DELETE FROM L0 WHERE id = ANY($1)
-- 第 i 层（自内向外构造）
DELETE FROM Li WHERE ck_i IN (
  SELECT id FROM L(i-1) WHERE ck_(i-1) IN (
    ... WHERE id = ANY($1)
  )
)
```

`ck_k` = 第 k 层相对其父的 childKey（默认 upper_id）。**零预 SELECT、无 id 物化**（避免并发漂移），往返数 = 层数。

#### 6.7.7 临时id→真id 映射算法（saver.rs:1110-1169，两遍改写）

```
全局 id_map: HashMap<String, i64>

第一遍（铸号）：
  遍历所有层 inserted，对每个 is_temp_id 行：
    is_temp_id 判定：None/Null/空串/非纯数字串（如 "t3"）→ 临时；纯数字 → 真号
    new_id = next_pk_id()（52 位 JS 安全）
    row.id = new_id；id_map[oldKey] = new_id
    已带真数字 id 的行保留（导入既有真号/重存，幂等）

第二遍（父外键重指向）：
  遍历所有 inserted 行的每个 childKey 外键（upper_id 或命名如 header_id）
  两处都查：① 顶层外键 ② fields 内命名外键
  若指向某临时父 id → 换成父的真号（查 id_map）
```

**跨层父子**（父在 L1、子在 L2）因用同一张 map，天然连对，与层序无关。

#### 6.7.8 乐观锁（B2）算法（saver.rs:613-729）

```
带锁 UPDATE（仅根层 + 行带 baseline + 表有 update_time 列）：
分组键 = (排序后变更列名, 是否带基线锁)，保证带锁/不带锁不混批

SQL 模板（build_multi_update_sql）：
UPDATE "table" SET "c1" = v."c1", "c2" = v."c2"
FROM (VALUES ($1, $2, $3), ($4, $5, $6)) AS v(id, "c1", "c2", __oplock)
WHERE "table".id = v.id AND "table"."update_time" = v."__oplock"

  baseline = 装载时的 update_time（前端回传，WHERE 比旧值）
  SET update_time = audit.now（服务端写新值）

冲突判定（got < expected）：
  补 SELECT id WHERE id = ANY($1)
  有 id 仍存在却没更新成功 → 基线陈旧 → 409 Conflict
  全部 id 不存在 → 非冲突，报「行不存在」业务错（H2）
```

#### 6.7.9 审计列填充（方案 C，saver.rs:1198-1262）

```
apply_audit_insert：
  先 remove_cols 剔除既存审计列（防重复列名把多值 INSERT 拼炸）
  按列存在性追加（通用单据不一定每张表都有全套审计列）：
    create_by=actor, create_time=now, update_by=actor, update_time=now, delete_flag=0

apply_audit_update：
  只强制注入/覆盖 update_by, update_time，不碰 create_*

ON CONFLICT 不可变审计列：
  CREATE_AUDIT_COLS = ["create_by", "create_time"]
  UPSERT 撞已存在 id 时，ON CONFLICT DO UPDATE SET 排除 id（冲突键）与 create_by/create_time（创建审计不可变），
  但 update_by/update_time 仍随 EXCLUDED 刷新

多值 UPSERT SQL 模板（build_multi_insert_sql）：
INSERT INTO "table" ("id", "c1", "c2") VALUES ($1, $2, $3), ($4, $5, $6)
ON CONFLICT (id) DO UPDATE SET "c1" = EXCLUDED."c1", "c2" = EXCLUDED."c2"
-- （排除 id 与 create_by/create_time；仅 id 列时 ON CONFLICT DO NOTHING）
```

#### 6.7.10 版本快照事务内一致性（B1，saver.rs:488-534）

```

1. if !meta.versioning_enabled() { return }（通用存储层不强制版本化）

### 6.8 DOC 后端：装载（loader / zmc_loader / zmc_loader_sqlx）

#### 6.8.1 装载算法（按层广度优先，父批量驱动子，避免 N+1）

```
load_txn 流程：
1. 取根层 root_layer()
2. query_root：build_layer_select(layer, &lq, None) 查根层 DataSet（富条件/排序/分页/游标）
3. descend 递归下钻（沿 layer_groups 推导父子层），max_depth 由 query.depth 控制

descend(parent_ds, depth)：
1. collect_ids(parent_ds) 收集父层 id 值集
2. child_key = meta.child_key_for(parent.id)
3. child_layers：
     include_siblings=true → meta.child_layers（下一层组全部兄弟表）
     否则只取组内主表（is_primary_in_group）
4. 对每个 child_layer：
     ★ 事务内非主兄弟表套 SAVEPOINT（cmx_sibling_sp），失败 ROLLBACK TO 复活事务再跳过
     query_children_by_key：build_layer_select(layer, &lq, Some((child_key, parent_ids)))
       WHERE 加 child_key = ANY($1)
     兄弟表容错：非主表装载失败（元数据定义了但物理表未部署）→ 跳过 + warn，不中断整单
     孙层仅从主表继续下钻（is_primary）
     attach_children 挂载

attach_children 分桶：
  buckets = HashMap<parent_id_str, Vec<Row>>
  for row in child_ds.rows: buckets[row[child_key]].push(row)
  for prow in parent_ds.rows: prow._children[child_id] = DataSet(buckets[prow.id])
```

#### 6.8.2 三种装载器实现差异

| 装载器 | 驱动 | 内存模式 | 子集挂载 | 出口 |
|---|---|---|---|---|
| DocLoader | sqlx | 老 DataSet（全拷贝） | `add_child`（按 child_key 分桶建子 DataSet 复制行） | ColumnarCodec::encode JSON |
| ZmcDocLoader | tokio-postgres | ZmcDataSet（持原始 Row 零拷贝） | `add_child_group`（ZmcChildGroup 记录父 id，编码时分桶不复制行） | encode_columnar_binary/msgpack 或 json |
| ZmcDocLoaderSqlx | sqlx | ZmcDataSet\<SqlxPgRowSource\> | 同 Zmc | 同 Zmc |

**Zmc 关键差异**：`build_child_group` 逐子行取 childKey 列的父 id 字符串，构造 `ZmcChildGroup { child_key, child, parent_ids }`，由列式二进制编码器在编码时按父 id 分桶（不复制行）。

#### 6.8.3 流式 stream 装载（doc.rs:320-402）

超大扁平结果零内存 chunked 传输：
```
1. 单层扁平大结果（不下钻），目标层由 body.layer 指定否则根层
2. build_layer_select 生成参数化 SQL
3. 背压 channel（容量 8）：tokio::sync::mpsc::channel::<bytes::Bytes>(8)
4. producer task 独占一条连接跑 query_sql_zmc_stream_chunks，逐帧发到 channel（满则 await，受下游网络速度节流）
5. Body::from_stream over receiver，axum 逐块 flush（chunked），服务端峰值内存 O(单行)
6. header 帧列名先于结果流发出，空结果也收尾
```

### 6.11 DOC 后端：校验规则与公式引擎（rule.rs + formula.rs）

#### 6.11.1 validationRules 结构（rule.rs:18-25）

```
每条规则：{ code, name?, level?, expr, message, severity? }
  expr：表达式字符串（如 total_dr == total_cr）

#### 6.11.2 formula 表达式求值引擎（formula.rs，591 行，自研安全求值器，不用裸 eval）

**语法**（递归下降）优先级（低→高）：
```
expr := or
or   := and (|| and)*
and  := cmp (&& cmp)*
cmp  := add (> < >= <= == !=)*
add  := mul (+ -)*
mul  := unary (* /)*
unary:= (- | !) unary | primary
primary := Num | Str | Bool | Null | ( expr ) | Ident | Ident ( args )
```

**求值**：
- 字段引用：`scope.get(name)`，缺失按 `FValue::Num(0.0)`
- 逻辑短路：`&&` 左假则右不求；`||` 左真则右不求
- `+`：任一为 Str 则字符串拼接，否则数值加
- `/`：除零返回 0.0（不报错）

**函数白名单**：`ABS, ROUND(x, digits?), MIN(...), MAX(...), SUM(...), IF(cond, a, b), AND(...), OR(...), NOT(x), ISEMPTY(x), COALESCE(...)`

**FValue 类型**：`Num(f64) / Str(String) / Bool(bool) / Null`

### 6.12 FLC 后端：运行时引擎（engine.rs）

代码：`cmx-model/src/flexible_combination/engine.rs`（1191 行）。Rust 端与前端 JS `FlexibleCombinationEngine` 对端实现。

> ⚠️ engine.rs 头部声明（engine.rs:5-7）：运行时闭包（calcFormula/onPickDimension/recompute）在 JSON 序列化时为 null，Rust 端不实现这些运行时回调，只产出**静态可序列化**的结构。

#### 6.12.1 规则匹配评分算法 —— ★ 核心

`matched_rules`（engine.rs:151-179）：

```
for r in rules（记 order 递增）:
  ① dims = r.anchor.dimensions
  ② 若 !dims.all(|d| anchor.contains(d)) → continue          // 锚点维度不全则跳过
  ③ score = score_match(r.anchor.match, anchor)
  ④ 若 score < 0 → continue                                  // 不匹配
  ⑤ specificity = score * 100.0 + dims.len()                 // ★ 评分×100 + 锚点维度数
  ⑥ 收集 (rule, specificity, order)
排序：specificity 降序；同分 order 升序（保持定义顺序）
```

`score_match`（engine.rs:181-206）：match 必须是 Object 且非空，否则 0.0；逐 (dim, cond) 累加 score，任一返回 -1.0 则整条规则作废。

#### 6.12.2 `score_condition` 单条件评分（engine.rs:209-260）—— 精确值 > 维度属性 > 通配兜底

| cond 形态 | 分值 | 说明 |
|---|---|---|
| `"*"` 字符串 | **0.25** | 通配兜底（最低） |
| `null` | **0.25** | 同通配 |
| `Array` | 命中 **1.5**，未命中 -1.0 | 枚举包含 |
| `Object` 含 `$` 操作符 | `score_operator_condition` | `$exists/$eq(3.0)/$ne/$in(1.5)/$nin` |
| `Object` 无 `$`（属性条件） | 逐属性累加；属性命中记 1.0 | 维度属性比对 |
| 标量 | 相等 **3.0**，不等 -1.0 | 精确值（最高） |

**评分梯度**：精确值(3.0) > $eq(3.0) > Array/$in(1.5) > 属性命中(1.0) > 通配/null(0.25)。

#### 6.12.3 `resolve_merged_rule`（engine.rs:325-445）—— 多规则合并

```
matched = matched_rules(anchor); 空 → None
单条命中 → 直接返回克隆
多条合并：
  ① by_def = matched 按 order 升序
  ② 字段合并：
     for (rule, score, _) in by_def:
       for f in rule.detail.fields:
         id = f.id
         by_code[id] 不存在 → 插入 (f, score, pos=递增)
         存在 (_, prev_score, prev_pos):
           若 score > prev_score → 覆盖值，保留 prev_pos（位置取首现）
     // 语义：位置取首现，值取高分（同分保留先到）
     field_entries 按 pos 升序排序 → fields
  ③ 分组 groups：按定义顺序拼接（不去重）
  ④ columnModel 合并：cm_order = matched 按 score 升序（低分先写、高分后写覆盖）
  ⑤ 锚点维度并集
  ⑥ id = 各规则 id 用 "+" 拼接
```

**合并语义总结**：字段同名取高分（同分取定义顺序先到）、位置取首现；columnModel 高分覆盖低分（同分靠前者赢）；分组按定义顺序拼接。

#### 6.12.4 `fields_depending_on_dimension`（engine.rs:908-960）—— onPickDimension 依赖图

```
direct = fields 中：
  - dimType=="attribute" 且 source.dimension==dim_code   // 属性来源维度
  - dimType=="measure" 且 defaultFrom.dimension==dim_code // 默认度量来源维度
downstream = 有 formula 且 dependsOn 命中 direct 集合的字段  // computed measure 级联
去重保序（direct 在前）
```

这构成 `onPickDimension` 的联动集合（选某维度 → 带出其属性字段 + 默认度量 + 依赖它们的计算度量）。

### 6.13 FLC 后端：overlay 编译器（overlay.rs）

代码：`cmx-model/src/flexible_combination/overlay.rs`（309 行）。把「引用 DOC 列 + 只写增量」展开成 inline `detail.fields`。**DOC 列由调用方以闭包 `table_cols(table) -> Option<Vec<Value>>` 注入，模块自包含、可单测、不做 IO**。

#### 6.13.1 `deep_merge`（overlay.rs:21-58）—— 核心合并语义

```
match (base, over):
  (Object, Object):
    for (k, v) in over:
      ① k 以 '+' 结尾 → 数组追加：取 base[k] 数组（空兜底），v 是数组→extend，否则 push；写入 key.strip_suffix('+')
      ② v is Null → out.remove(k)                // 删除语义
      ③ (base[k]是Object, v是Object) → 递归 deep_merge
      ④ 否则 → out[k] = v                         // 标量覆盖
  否则 → over.clone()                              // 非对象由 over 决定
```

三语义：**null=删除、`key+`=数组追加、对象=递归合并、标量=覆盖**。

#### 6.13.2 三种取列入口 `expand_detail_fields`（overlay.rs:125-172）

```
取 detail.table 作 default_table
若注入了 table_cols 闭包：

                      展开 + over 补丁
  pick:[{ref,as,over}]：按声明顺序，每项调 expand_ref_field(ref_str, over, as_name, table, tc)；as 重命名
fields:[…]：恒等直通（纯逻辑列），无论闭包是否注入都追加
```

#### 6.13.3 `expand_ref_field`（overlay.rs:74-121）—— 单列展开

```
1. split_ref("table.column" / "column") → (table, column)
2. cols = table_cols(table)?; col = cols.find(id==column)?   // 找不到返回 None（悬空引用）
3. base = col.clone()
4. 若 col.nullable == false → base.edit.required = true      // DOC 非空列默认必填
5. merged = over ? deep_merge(base, over) : base
6. as_name: Some → id/name = as_name；None → 若无 name 则补 name=id
7. Some(merged)
```

#### 6.14.2 `detect_formula_cycles`（validator.rs:804-865）—— DFS 三色标记环检测

```
by_code = {field_id: field} for computed fields（有 formula 的）
visiting = {}（灰，当前 DFS 栈）
visited = {}（黑，已完成）
stack = []（路径栈）

visit(field):
  ① id 空 或 visited 含 id → return
  ② visiting 含 id → 发现环：
     start = stack 中 id 的位置
     cycle = stack[start..] + [id]
     error(FORMULA_DEPENDENCY_CYCLE, "计算公式存在循环依赖：" + cycle.join(" -> "))
     return
  ③ visiting.insert(id); stack.push(id)
  ④ for dep in field.dependsOn:
       if by_code 含 dep → visit(dep)   // 递归
  ⑤ stack.pop(); visiting.remove(id); visited.insert(id)

for f in computed: visit(f)   // 每个计算字段作 DFS 入口
```

### 6.17 模型中心：DDL 编译与部署

#### 6.17.1 定义编译总流程（model_center.rs）

```
compile_definition(kind, domain, app, module, file)：
1. read_def 读主定义
2. base_file = doc[baseDocMetaRef/baseDctMetaRef].file ?? 默认
3. base = read_base(base_file) ?? {fieldSets:{}}
4. kind=="DOC" → compile_doc(doc, base)；否则 compile_dct(doc, base)
5. 返回 Vec<TableDefine>
```

**字段类型映射** `map_field_type`（model_center.rs:63-78）：VARCHAR/CHAR/STRING→String，TEXT/CLOB→Text，INT 族→Int，DECIMAL/NUMERIC/NUMBER→Decimal，FLOAT/DOUBLE→Float，DATE→Date，DATETIME/TIMESTAMP→DateTime，BOOL→Bool，JSON/JSONB→Json，UUID→Uuid，BINARY 族→Binary，其它→String。

**列合并去重保序**（compile_dct model_center.rs:229-284 / compile_doc_table model_center.rs:314-385）：HashSet `seen` 按列名去重，`ord` 全局递增保序，首现优先。own fields + 七个固定 *FieldSet + 兜底任意 *FieldSet 键。

#### 6.17.2 增量 DDL 计划 `table_change_plan`（model_center.rs:660-722）—— ★ additive-only

```
1. exists = table_exists(db_id, table)   // information_schema 内省
2. 不存在 → action:"create_table"，addedColumns = 全列
3. 存在：
   before = table_columns(db_id, table)   // HashMap<col_name, DbColumnSnapshot>
   for c in def.columns:
     desired = desired_column_snapshot(c)
     match before[c.name]:
       None → added.push(...)                         // ★ 新增列
       Some(old):
         diffs = column_shape_changes(old, desired)   // 逐字段比对 dataType/length/precision/scale/nullable/default
         空 → unchanged.push(name)
         非空 → modified.push(...)
   // ★ 不处理 before 有但 def 无的列（不删列）
   action = added/modified 都空 ? "no_change" : "upgrade_table"
```

#### 6.17.3 DDL diff 安全策略（cmx-metadata/src/ddl/diff.rs:296-404）—— 只加不删

```
CreateTable → CREATE TABLE + COMMENT + INDEX
DropTable   → ★ 仅 info! 日志，不生成 DROP（防数据丢失）
AlterTable:
  AddColumn  → ADD COLUMN DDL
  DropColumn → ★ 仅 info! 日志，不生成 DROP COLUMN（防数据丢失）
  AlterColumn → ALTER COLUMN TYPE / SET NOT NULL / SET DEFAULT
  AddIndex → CREATE [UNIQUE] INDEX
  DropIndex → DROP INDEX IF EXISTS
```

**这是 additive-only 的核心**：删表/删列只记录日志不执行，保证不丢数据。

#### 6.17.4 DDL 执行器 `PgTableDefineExecutor`（cmx-metadata/src/executor.rs）

```
create_or_upgrade_table（executor.rs:80-86）：
  if create_table(define).is_ok() { return Ok(()) }
  upgrade_table(define)                        // 先尝试建表，失败则升级

upgrade_table（executor.rs:437-476）：
  1. current = query_current_table_define(define)   // 内省现有表结构（5 步 information_schema + pg_catalog 查询）
  2. dialect = PostgresDdlDialect { prefer_db_type: true }   // ★ round-trip 模式，保留 db_type
  3. stmts = DdlDiff::diff_to_ddl(&dialect, &[current], &[define])
  4. 空 → 无变更；非空 → execute_statements(stmts)
```

#### 6.17.5 CREATE TABLE SQL 模板（cmx-metadata/src/ddl/postgres.rs:92-138）

```sql
CREATE TABLE "<schema>"."<table>" (
    "col1" VARCHAR(32) NOT NULL DEFAULT 'x',
    "col2" BIGINT,
    PRIMARY KEY ("id")
) TABLESPACE "<ts>";
-- 索引
CREATE [UNIQUE] INDEX "<idx_name>" ON "<schema>"."<table>" ("col1", "col2");
-- 注释
COMMENT ON TABLE "<schema>"."<table>" IS '表注释';
COMMENT ON COLUMN "<schema>"."<table>"."col" IS '列注释';
```

类型映射（`map_column_type`）：String→VARCHAR(len)/TEXT，Int→BIGINT，Decimal→NUMERIC(p,s)，Float→DOUBLE PRECISION，DateTime→TIMESTAMP WITH TIME ZONE，Bool→BOOLEAN，Json→JSONB，Uuid→UUID，Binary→BYTEA。

#### 6.17.6 部署流程 `deploy_with_events`（model_center.rs:1648-1977）

```
对每个 item：
1. 前置：read_meta 必须已初始化
2. 写 deploy_history 锚点（status='executing'）
3. 编译：compile_definition(kind, ...) → (defs, src)
   失败 → fail_history + error 事件 + continue
4. 建表（DDL 自动提交，txn_id=None）：
   executor = PgTableDefineExecutor::new(db_id, None)
   for def in defs:
     change = table_change_plan(db_id, def)          // 内省 diff
     executor.create_or_upgrade_table(def)            // additive-only
     失败 → fail_history + error + continue
5. 台账 DML（单事务）：
   a) cmx_model_source：旧版 is_current=0，插新版（source_json + compiled_json）ON CONFLICT 更新
   b) cmx_model_module UPSERT：{kind}_version=version, {kind}_status='current'
   c) cmx_meta_table_define + cmx_meta_table_define_version：check-then-upsert
   d) deploy_history：status='success', to_version, object_count, ddl_summary(JSON), duration_ms
   失败 → rollback + fail_history + continue
6. commit
返回 {ok, batch_id, results, db_state}
```

#### 6.17.7 SSE 流式事件

事件结构 `{ kind: "connect"|"step"|"progress"|"done"|"error", data: Value }`：
- `init_db_stream`：connect(SELECT 1 探测) → 逐条 INIT_DDL 进度 → 事务写 meta+history → done（附 db_state）
- `init_plan_stream`：只读探测，不执行 DDL，生成计划供审核
- `deploy_stream` / `deploy_plan_stream`：每模块每表发 progress

#### 6.17.8 模型中心台账表（`INIT_DDL`，model_center.rs:1116-1125）

4 张表（全部 `CREATE TABLE IF NOT EXISTS` / `CREATE [UNIQUE] INDEX IF NOT EXISTS`，幂等加性）：

| 表 | 职责 |
|---|---|
| `cmx_model_meta` | 库级元信息（meta_version/status/initialized_at/engine_version） |
| `cmx_model_module` | 模块台账（dct_version/dct_status/doc_version/doc_status/def_checksum/archived） |
| `cmx_model_deploy_history` | 部署历史（batch_id/kind/action/from_version/to_version/status/ddl_summary JSONB/duration_ms） |
| `cmx_model_source` | 源 JSON 留档（source_json/compiled_json/checksum/is_current） |

#### 6.17.9 `scenario_of` 部署场景推导（model_center.rs:807-828）

```
status=="failed" → "retry"
(None, Some) → "create"
(None, None) → "none"
(Some, None) → "current"
(Some a, Some l):
  a<l → "upgrade"; a>l → "downgrade"
  a==l && status=="drift" → "drift"
  else → "current"
```

## 7. 三元协作场景：会计凭证端到端

以「会计凭证录入」为例，展示 DCT/DOC/FLC 三元如何协作：

   → POST /api/flexible-combination/config 保存

### 7.2 运行期装载与录入

```
① 用户打开凭证录入页（CMXHTMLDesigner 产出）

   ↓ loadByAnchor({account:'1122'})

   ↓ engine.buildColumns(rule)
   → CmxColumn[] 写入辅助行的 CmxColumnModel

④ 用户在明细行录入
   选 dimension（客商）→ onPickDimension 带出属性 + 默认度量
   改 input measure（数量）→ recompute 拓扑重算（金额 = 单价 × 数量）

⑤ 用户点保存
   ↓ engine.validate 跑字段校验
   ↓ ChangeSetCollector 收集 {inserted, updated, deleted}
   POST /api/doc/save {saveMode:'merge', changes}
   ↓ DocSaver 事务内逐层 UPSERT + 跑 validationRules + 写 cmx_doc_revision
   返回 SaveResult（含新 id_map + 乐观锁基线）
```

## 9. 扩展点与二次开发指引

### 9.1 新增一本字典（DCT）

1. 在对应模块的 `*_dct_meta_v*.json` 的 `dictionaryTables[]` 加一项 `dictMeta` + `fields[]` + 引用的 `*FieldSet`
2. 设计期 UI：「数据字典定义」菜单 → 新建/编辑 → 保存（`POST /api/definitions/config`）
3. 模型中心 deploy → 自动 `CREATE TABLE cf_<name>`
4. （可选）准备种子条目 → `POST /api/dict/<dictId>/entries` 或 `POST /api/dct/entries`
5. 运行期：在 DOC fieldSet 或页面字段声明 `refDict`/`type:'dict-select'` 即可挂接

### 9.2 新增一种单据（DOC）

1. 编写 `*_doc_meta_v*.json`：定义 `docMeta` + `baseDocMetaRef` + `voucherSchema`（schema 层级 + relations + aggregations）+ `voucherTables`（各层 fields + documentFieldSets）
2. 设计期 UI：「业务单据定义」菜单 → 新建 → 保存
3. 模型中心 deploy → 自动 `CREATE TABLE cv_*`
4. 运行期：`CmxMasterSlave` 按 `/doc/meta` 动态建多层 grid；`loadDocData`/`saveDocData` 走 `/api/doc/*`

### 9.3 新增一个弹性组合场景（FLC）

1. 「弹性组合管理」菜单 → 新建 scenario（如 `account`、`trade`）
2. 定义锚点维度 `anchorDimensions` + 维度目录 `dimensions{}` + 规则 `rules[]`
3. 每条规则：`anchor.match`（精确值/维度属性/通配）+ `detail.fields[]`（三态字段）
4. （可选）用 overlay 引用 DOC 列：`detail.use:"*"` + `over` 打补丁，或 `detail.pick:[{ref}]`
5. 保存 → 运行期页面用 `<FlexibleCombination>` 模型按锚点懒加载 rule → `buildColumns` 写入目标 columnModel

### 9.4 跨域引用（DRN）

- 同 DAM 内引用：裸 code（如 `cost_center`）或 `DCT/cost_center`
- 跨 DAM 引用：`drn:fi/shared-md/masterdata/DCT/cost_center@1`
- 深链到列：`drn:.../DOC/cmxfico_doc_meta#voucher_detail.cashflow_item_id`
- 别名：在档案顶部 `imports:[{alias:'cc', drn:'...'}]`，引用处写 `@cc`
- 可见性：被引用方声明 `visibility: private|app|domain|public`

### 9.5 字段级覆盖（field-override / flc-overlay）

当不想改源定义、只想在某场景微调列时，用 overlay：

- DOC 场景：`normalizeFieldOverrides` / `effectiveField` / `materializeTable`（`field-override.js`）
- FLC 场景：`detail.over.{colId:{...}}` 打补丁，`null`=删除列，`key+=`数组追加（`flc-overlay.js::deepMerge`）
