# 业务单据数据「装载 → 前端模型 → 编辑显示 → 回存」全链路方案

> 版本：设计稿 v1（2026-07-03）｜状态：**纯方案，不改任何代码**
> 目标：把某个已定义的**业务单据（业务单据 = DOC）**在 PostgreSQL 中的多层业务数据，端到端装入前端 `CmxDataSet / CmxRowSet / CmxMasterSlave` 模型，在 `cmx-revo-grid / cmx-ui5-form` 中编辑与显示，并可再次存回后端相关数据表。
> 两条硬约束：**（A）后端尽量零拷贝；（B）传输到前端的数据包尽量小。**

---

## 0. 一句话结论

后端 `cmx-core::DataSet` 与前端 `CmxMasterSlave` 是**天生的结构孪生**：两者都是「`schema/id` + 扁平行 `rows` + 按名挂载的子数据集 `children`」的递归主从树。系统**已就绪**的能力有：业务单据元数据（`voucherTables/voucherSchema/relations/aggregations`）、`DdlDialect` 建表引擎、`ResultConverter` 把 PG 行装成 `DataSet`、`Arc<Schema>` 共享、前端 `CmxDataSet` 的**列式序列化**（`exportColumnar/fromJSON`）与**零拷贝视图**（`CmxDataSetView`）。**唯一缺口**是：没有任何代码「按单据定义的 `upper_id` 层级，把多张物理表的扁平行组装成一棵嵌套 `DataSet`，再列式小包传前端；也没有把前端改动按层拆解回写各表」。本方案补上这条链路，并在其上叠加**零拷贝**与**小包**两项优化。

本方案新增 **2 个后端服务端点** + **1 套列式小包协议** + **1 个前端装配/拆解适配层**，**不改**已有的建表引擎、元数据存储、CRUD 宏。

## 1. 现状勘察：可复用 vs 缺口

### 1.1 可直接复用（已就绪）

| 能力 | 位置 | 说明 |
|---|---|---|
| 业务单据元数据 | `data/meta/definitions/<domain>/<app>/<module>/*_doc_meta_v1.json` | `voucherSchema.schema`（L1..Ln 层级）+ `relations`（`parentKey→childKey`）+ `aggregations`（上卷）+ `voucherTables[]`（每层字段） |
| 层级基础字段集 | `data/meta/definitions/base/base_doc_meta_v1.json` → `documentLevelFields` | `id`(BIGINT 主键) + `upper_id`(BIGINT 父指针) + `line_no`(INT 行号) |
| 定义 → 物理表编译 | `crates/libs/cmx-api/src/handlers/portal/model_center.rs` | `compile_doc()` 把 `voucherTables[]` 编译成 `Vec<TableDefine>`；`field_to_column()` 映射 `dataType/fieldLength/decimalDigits` |
| PG 建表引擎 | `crates/libs/cmx-metadata/src/ddl/postgres.rs` + `executor.rs` | `PostgresDdlDialect::map_column_type` + `PgTableDefineExecutor::create_or_upgrade_table`（内省 + 增量、**只加不删**） |
| DB 行 → DataSet | `crates/libs/cmx-infra/cmx-database/src/executor/mod.rs:308` | `ResultConverter::convert_postgres_rows(rows, dataset_id) -> DataSet`（列信息推断 Schema） |
| 查询/执行/事务 | `crates/libs/cmx-infra/cmx-database/src/transaction/api.rs` | `query_sql(db_id,txn_id,sql,dataset_id)->DataSet`、`execute_sql_with_datavalues(...)`、`begin/commit/rollback` by `txn_id`、按 `db_id` 多库池 |
| 后端主从数据容器 | `crates/libs/cmx-core/src/model/data/dataset/rds.rs` | `DataSet{ id, schema:Arc<Schema>, rows:Vec<Row>, inserted/updated/deleted }`；`Row{ values:Vec<DataValue>, children:HashMap<String,DataSet> }` |
| 前端主从协调器 | `packages/cmx-data-comp/src/lib/cmx-master-slave.js` | `setDataSet/setFlatData`、`bindTable/bindForm`、`relations/aggregations`、递归监听 |
| 前端列式编解码 | `packages/cmx-data-comp/src/lib/cmx-data-set.js` | `exportColumnar()/toJSON()` → `{columns, rows:[[...]], childRows}`；`fromJSON()` 还原 |
| 前端零拷贝视图 | `packages/cmx-data-comp/src/lib/cmx-data-set-view.js` | `CmxDataSetView` 仅存主集 `CmxRowSet` 引用，内存 ≈ O(命中行) 指针 |
| 网格/表单编辑回写 | `cmx-revo-grid.js:1004` / `cmx-ui5-form.js:1137` | `afteredit → model.set(prop,val)`；`_commit → this._row.set(key,value)` |

### 1.2 必须新增的缺口

1. **单据数据「装载」服务**：读单据定义 → 按层生成参数化 SQL → 按 `upper_id` 组装嵌套 `DataSet` → 列式小包 → 前端。目前 `convert_postgres_rows` 只产**单层扁平** `DataSet`，主从嵌套需手动 `Row::add_child`，且**无人**按元数据自动做。（后端 metadata/model agent 明确指出此缺口。）
2. **单据数据「回存」服务**：接收前端 changeset（inserted/updated/deleted，按层），在**一个事务**内逐层 upsert/delete 回各物理表；子表通过 `upper_id = 父行 id` 维系。目前只有单表 CRUD 宏与 WASM 插件裸 SQL，无「按单据整树回写」。
3. **小包 + 零拷贝的传输层**：现状是**行式 JSON、键名逐行重复、不跳 null、无压缩**（`RowRef` 逐行 `{field:value}`，`SKIP_NULL_IN_SERIALIZE=false`，`CompressionLayer` 已编译但未挂载）。需要列式协议 + 可选 MessagePack + 压缩中间件。

### 1.3 三个必须规避的现状坑

- **坑 A — 前端模型无脏标记**：`CmxRowSet` 没有 `_dirty/_isNew/_state`，"脏"只体现为 `row-changed/ds-row-added/ds-row-removed` 事件流。→ 回存需要**在适配层自建 changeset 收集器**（订阅事件），或依赖后端 `DataSet.inserted/updated/deleted` 语义在前端镜像一份。
- **坑 B — `DataSet` 的变更池不序列化**：`rds.rs` 的 `Serialize` 只输出 `id/schema/rows`，`inserted/updated/deleted` **不过线**。→ 回存协议要**显式定义** changeset 字段，不能指望复用 `DataSet` 默认序列化。
- **坑 C — `upper_id`/层级从不进 DB 外键**：`compile_doc` 生成的 `upper_id` 只是普通 nullable `BIGINT` 列，`relations/level` 不读、不建 FK（additive-only 引擎连 DROP 都不执行）。→ 层级关系**由应用层（本方案的装载/回存服务）保证**，不能依赖数据库 FK 级联。

```
                ▼                                              │
┌────────────────────────────────────────────────────────────┴───────────────┐
│  后端 单据数据服务（新增，cmx-biz/cmx-service 内）                                 │

│   ⑤ ms.setDataSet(dsMap)（零拷贝接管，不再二次转换）                              │
│   ⑥ ChangeSetCollector：订阅 row-changed/ds-row-added/ds-row-removed 收集变更     │

                ▼                                              │
┌────────────────────────────────────────────────────────────┴───────────────┐
│  可视化组件（已就绪）                                                            │
│   cmx-revo-grid（每层一张网格，主选中→子级联）/ cmx-ui5-form（绑定当前行）          │
```

**核心洞察**：后端 `DataSet` 与前端 `CmxDataSet` 是同构的——两端都是 `{ schema/id, rows(扁平值), children(按名子集) }`。因此「后端组装嵌套 `DataSet` → 列式序列化 → 前端 `fromJSON` 还原 → `ms.setDataSet`」是一条**无阻抗**的直通路，中间没有模型翻译损耗。

## 3. 业务单据元数据与层级模型（`id` / `upper_id`）

### 3.1 单据定义结构（DOC）

以 `data/meta/definitions/fi/cmxfico/gl/cmxfico_doc_meta_v1.json` 为例，一份 DOC 定义的关键块：

```jsonc
{
  "docMeta": { "metaKind": "DOC", "metaName": "...", "version": 1 },
  "voucherSchema": {
    "schema": [
      [ { "id": "cv_batch",    "kind": "list", "level": "L1", "levelName": "凭证批" } ],
      [ { "id": "cv_header",   "kind": "list", "level": "L2", "levelName": "凭证头" } ],
      [ { "id": "cv_acc_line", "kind": "list", "level": "L3", "levelName": "科目行" } ],
      [ { "id": "cv_aux_line", "kind": "list", "level": "L4", "levelName": "辅助行" } ]
    ],
    "relations": [
      { "parent": "cv_batch",      "child": "headers",       "parentKey": "id", "childKey": "upper_id" },
      { "parent": "headers",       "child": "account_lines", "parentKey": "id", "childKey": "upper_id" },
      { "parent": "account_lines", "child": "aux_lines",     "parentKey": "id", "childKey": "upper_id" }
    ],
    "aggregations": [
      { "from": "cv_header.account_lines", "to": "cv_header", "field": "entered_dr", "toField": "total_dr", "agg": "sum" }
    ]
  },
  "voucherTables": [
    { "level": "L1", "tableName": "cv_batch",  "tableAlias": "凭证批",
      "fields": [ /* 本层特有字段 */ ],
      "documentFieldSets": [ "documentLevelFields", "documentTechnicalFields" ] },
    { "level": "L2", "tableName": "cv_header", "...": "..." }
  ]
}
```

- **节点类型**：`单据(document) → 层/表(level/table) → 字段(field)`。每个 `voucherTables[i]` 就是一层一张物理表；`voucherSchema.schema` 描述层顺序，`relations` 描述父子键，`aggregations` 描述上卷。
- **主从即多级树**：这是**主从（主从/master-slave）**，与「细分/弹性组合 CTX」是两回事（`flexible-combination-engine.js` 已废弃为 `FlexibleCombinationEngine` 的壳）。

### 3.2 层级身份字段（`documentLevelFields`）

`base_doc_meta_v1.json` 中的共享字段集，是层级模型的身份契约：

```jsonc
"documentLevelFields": {
  "remark": "业务单据层级基础字段集:id(主键) + upper_id(上级单据主键,单层父指针,联动用) + line_no(行号)",
  "fields": [
    { "id": "id",       "name": "id",       "dataType": "BIGINT", "fieldLength": 20, "nullable": false, "isPrimaryKey": 1, "caption": {"zh_CN":"主键ID"} },
    { "id": "upper_id", "name": "upper_id", "dataType": "BIGINT", "fieldLength": 20, "nullable": true,  "dimType": "attribute", "caption": {"zh_CN":"上级单据主键"} },
    { "id": "line_no",  "name": "line_no",  "dataType": "INT",    "fieldLength": 11, "nullable": false, "dimType": "attribute", "caption": {"zh_CN":"行号"} }
  ]
}
```

- **`id`**：BIGINT 主键（`isPrimaryKey:1`）。
- **`upper_id`**：BIGINT 父指针（可空，根层为空）。**从扁平行重建树的唯一依据**：`child.upper_id === parent.id`。
- **`line_no`**：INT 行内序号。

### 3.3 两种父子链方言

| 方言 | 父指针 | 代表 | 说明 |
|---|---|---|---|
| **通用单指针** | `upper_id`（每层共用一列，来自 `documentLevelFields`） | cmxfico（4 层） | `relations.childKey = "upper_id"` |
| **命名外键** | `header_id` / `entry_id` / `batch_id`（各层显式声明） | SAP / 用友 / 金蝶 / EBS | `relations.childKey = "header_id"`，字段 `dimType:"relation"` |

> 本方案的装载/回存服务**读 `relations` 拿 `parentKey/childKey`**，因此两种方言统一处理，不写死 `upper_id`。文中以 `upper_id` 为默认示例。

### 3.6 后端 Rust 中如何访问这些元数据（现状：弱类型 JSON 透传）

**一句话**：单据元数据在后端**不是 Rust 结构体，而是磁盘上的 JSON 文件**；后端把它当 `serde_json::Value` 读进来、用 `.get("...")` 逐字段取值。这正是本方案「缺口」的根源——后端对单据元数据是**弱类型透传**，没有 `VoucherMeta`/`DocMeta` 强类型，也没有任何代码遍历 `voucherSchema.relations` 的层级。

**唯一入口**：`cmx_portal::definitions::store`（实现在 `crates/libs/cmx-model/src/definitions/store.rs`）。元数据存放于 `data/meta/definitions/<domain>/<app>/<module>/<file>.json`（`base` 域特例为 `data/meta/definitions/base/<file>.json`）。

| 函数 | 作用 | 返回 |
|---|---|---|
| `get_definition(&DefRef)` | 读单个定义文件（原样 JSON） | `serde_json::Value` |
| `get_definitions_batch(&Value)` | 批量读 + 一次性附带各定义引用的 base 字段集（去重） | `Value`（`{ items, bases, basePaths, errors }`） |
| `list_definitions(kind, domain, app, module)` | 递归扫描列表（按 `metaKind` 分 DCT/DOC/BASE） | `Value` |
| `save_definition / set_default_version / delete_definition` | 写 / 设默认版本 / 删（base 不可删） | — |

`DefRef` 是文件坐标：`{ domain, application/app, module, file/id }`。

**标准范例**（`model_center.rs`，后端目前**唯一**真正读单据元数据的地方——编译成建表 `TableDefine`）：

```rust
// ① 读定义文件全文（弱类型 Value）
let r = DefRef { domain: Some(domain.into()), application: Some(app.into()),
                 app: Some(app.into()), module: Some(module.into()), file: Some(file.into()), id: None };
let doc = cmx_portal::definitions::store::get_definition(&r).await?;    // → serde_json::Value

// ② 读它引用的 base 字段集（domain = "base"）
let base_file = doc.get("baseDocMetaRef").and_then(|r| r.get("file")).and_then(|v| v.as_str());
let base = read_base(base_file).await?;

// ③ 用 .get(...).as_array()/.as_str() 逐字段访问，遍历 voucherTables → 每层一张表
let tables = doc.get("voucherTables").and_then(|v| v.as_array())?;
for t in tables {
    let table_name = t.get("tableName").and_then(|v| v.as_str()).unwrap_or("");
    if let Some(own) = t.get("fields").and_then(|v| v.as_array()) { /* 本层字段 */ }
    // documentFieldSets 引用 base 里的共享字段集：base["fieldSets"][name]["fields"]
    if let Some(sets) = t.get("documentFieldSets").and_then(|v| v.as_array()) {
        for s in sets { let fields = base_fieldset(&base, s.as_str()?); /* 展开合并 */ }
    }
}
```

**现状要点（及不足）**：

- **合并 base 字段集要自己做**：一层的完整字段 = 本表 `fields` + `documentFieldSets` 每个名字到 `base["fieldSets"][name]["fields"]` 的展开。`get_definitions_batch` 会顺带把 base 文件一并返回，省一次 IO。
- **层级从不被读**：`compile_doc` 只读 `voucherTables` 建表，**`voucherSchema.relations`（`parentKey/childKey/upper_id` 那套层级）没有任何 Rust 代码读过**。要在后端问「这个单据的父子层级」，得自己 `doc.get("voucherSchema").get("relations")` 解析。
- **每次请求读磁盘、无缓存**：`get_definition` 每次 `read_json`；`list_definitions` 每次 `tokio::fs::read_dir` 递归遍历整个目录树。单据数据装载会**频繁读同一份定义**，这是性能与一致性隐患。
- **弱类型 `.get(...).as_str()` 满地散落**：易错、无编译期保障、无 IDE 补全。

### 3.7 改进一：定义访问缓存（与 §7 `Arc<Schema>` 缓存合并）

`DocLoader`/`DocSaver` 每次装载/回存都要读同一份单据定义并解析层级——应加一层进程内缓存，键为 `domain/app/module/file@version`（版本取自 `docMeta.version`），值为**已解析的强类型元数据 + 各层 `Arc<Schema>`**：

```rust
// 进程内缓存：docKey → Arc<解析后的单据元数据>
static DOC_META_CACHE: OnceLock<DashMap<String, Arc<DocMetaView>>> = OnceLock::new();

async fn load_doc_meta(domain,app,module,file) -> Result<Arc<DocMetaView>> {
    let key = format!("{domain}/{app}/{module}/{file}");
    if let Some(hit) = cache().get(&key) { return Ok(hit.clone()); }   // 命中：零磁盘、零解析
    // miss：get_definitions_batch（一次拿定义 + base）→ 解析为 DocMetaView（§3.8）→ 建各层 Arc<Schema>
    let view = Arc::new(DocMetaView::parse(doc, base)?);
    cache().insert(key, view.clone());
    Ok(view)
}
```

- **失效策略**：`save_definition`/`set_default_version`/`delete_definition` 成功后按 `docKey` 逐出（或带版本号天然免失效——版本变则键变）。
- **与 §7 合并**：`DocMetaView` 内直接持有 `Vec<Arc<Schema>>`（每层一个），装载时 `DataSet` 直接引用这些 `Arc<Schema>`，一处缓存同时服务「元数据解析」与「零拷贝 Schema 共享」两个目标。

### 3.8 改进二：强类型只读投影层（`DocMetaView`）

不改存储格式（仍是 JSON），只加一层 `serde::Deserialize` 投影，把「满地 `Value.get()`」收敛成一次反序列化，让 `DocLoader`/`DocSaver` 拿到强类型层级模型。投影结构体字段名与真实 JSON **逐一对齐**（`#[serde(default)]` 容错未知/缺失键，`extra` 兜底透传）：

```rust
/// 单据元数据的只读投影（从 DOC 定义 JSON 反序列化；未知键忽略）
#[derive(Debug, Clone, Deserialize)]
pub struct DocMetaView {
    #[serde(rename = "docMeta")]      pub module_meta: ModuleMeta,
    #[serde(rename = "voucherSchema")]   pub schema: VoucherSchema,
    #[serde(rename = "voucherTables")]   pub tables: Vec<VoucherTable>,
    // 解析后自建（非 JSON 字段）：每层 tableName → Arc<Schema>，供装载零拷贝
    #[serde(skip)]                       pub layer_schemas: HashMap<String, Arc<Schema>>,
}
#[derive(Debug, Clone, Deserialize)]
pub struct ModuleMeta { #[serde(rename="metaKind")] pub meta_kind: String, pub version: u32 }

#[derive(Debug, Clone, Deserialize)]
pub struct VoucherSchema {
    pub relations: Vec<RelationDef>,
    #[serde(default)] pub aggregations: Vec<AggDef>,
    // schema 是 [[{id,level,levelName}]] 嵌套数组，解析层序用
    #[serde(default)] pub schema: Vec<Vec<LevelNode>>,
}
#[derive(Debug, Clone, Deserialize)]
pub struct RelationDef {                        // ← 层级父子链的强类型化（现状无人读）
    pub parent: String, pub child: String,
    #[serde(rename="parentKey", default="id_default")] pub parent_key: String,  // 默认 "id"
    #[serde(rename="childKey")]  pub child_key: String,                          // "upper_id" 或 "header_id"
}
#[derive(Debug, Clone, Deserialize)]
pub struct AggDef { pub from:String, pub to:String, pub field:Option<String>, #[serde(rename="toField")] pub to_field:String, pub agg:String }
#[derive(Debug, Clone, Deserialize)]
pub struct LevelNode { pub id:String, #[serde(default)] pub level:String, #[serde(rename="levelName",default)] pub level_name:String }

#[derive(Debug, Clone, Deserialize)]
pub struct VoucherTable {
    #[serde(rename="tableName")]  pub table_name: String,
    #[serde(rename="tableAlias", default)] pub table_alias: String,
    #[serde(default)] pub fields: Vec<serde_json::Value>,           // 字段仍留 Value（属性太多，按需取）
    #[serde(rename="documentFieldSets", default)] pub field_sets: Vec<String>,
}
fn id_default() -> String { "id".into() }
```

**收益**：

- `DocLoader` 可直接 `view.schema.relations` 拿到父子键、`view.tables` 拿到层表，无需再 `Value.get("voucherSchema").get("relations").as_array()` 层层解包。
- `view.layer_schemas["cv_header"]` 直接给出该层 `Arc<Schema>`，装载时 `DataSet::new(id, schema.clone(), rows)` 零拷贝复用。
- `RelationDef.parent_key/child_key` 让「通用 `upper_id`」与「命名外键 `header_id`」两种方言统一成同一强类型，装载/回存逻辑不写死列名。
- 字段级仍保留 `Vec<Value>`（字段属性多达 30+，且 DCT/DOC/CTX 三端共享 schema），按需 `.get()`，不强行全类型化——**强类型化只覆盖"层级骨架"，字段"血肉"仍透传**，取得类型安全与灵活性的平衡。

> 落地归属：`DocMetaView` + 缓存放在新增的 `DocLoader` 所在 crate（建议 `cmx-biz` 或新建 `cmx-doc`）；**不改** `definitions::store`（它继续做纯 JSON 读写），投影层是它之上的消费者。

## 5. 装载：DB → 后端 `DataSet` → 前端模型

### 5.1 后端 `DocLoader`（新增服务）

**入参**：`{ db_id, domain, app, module, docFile, rootId?, filter?, page? }`（`filter` 作用于根层，如按凭证号/期间/组织）。

**算法（按层广度优先，父批量驱动子）**：

```
1. 读定义：definitions::store::get_definition(docFile) → doc JSON；按 baseDocMetaRef 合并 base
2. 解析层序与父子键：从 voucherSchema.schema 得 [L1..Ln]；从 relations 得每层 (parentKey, childKey)
3. 编译各层 Schema：voucherTables[i] 展开 documentFieldSets → cmx-core::Schema（字段名/类型/label）
   —— Schema 用 Arc 包裹并【按层缓存】（同一单据定义所有请求共享，见 §7 零拷贝）
4. 查 L1（根）：
     SELECT <L1列> FROM cv_batch [WHERE <filter>] [ORDER BY id] [LIMIT/OFFSET]
     → query_sql(db_id, None, sql, "cv_batch") → DataSet(schema=Arc<L1Schema>)  ← 直接零拷贝装配
   收集 rootIds = [row.id ...]
5. 逐层下钻（i = 2..n）：
     parentIds = 上一层所有 id
     SELECT <Li列> FROM <tableI> WHERE upper_id = ANY($1) [ORDER BY upper_id, line_no]
       参数 $1 = parentIds（一条 SQL 取全部子行，避免 N+1）
     → DataSet(schema=Arc<LiSchema>)
     按 upper_id 分桶：group_by(row.upper_id)
     挂载：对每个父行 pr，pr.add_child(childKey_i, 子桶DataSet)   ← Row.children
6. 返回根层 DataSet（已是完整嵌套主从树）
```

**关键点**：

- **一层一条 SQL、`WHERE upper_id = ANY($parentIds)`**：整棵树最多 n 条查询（n=层数），彻底避免 N+1。命中 §4.4 的 `upper_id` 索引。
- **`ANY($1)` 数组绑定**：走 `execute_sql_with_datavalues` / sea-query 参数化，`DataValue::Array` 承载 id 列表；SQL 注入免疫。
- **组装即 `Row::add_child`**：复用 `rds.rs` 现成能力，产出的就是 `DataSet{ rows:[Row{ values, children:{ "headers": DataSet{...} } }] }`——后端主从树。
- **Schema 共享**：同一层所有行共用一个 `Arc<Schema>`；同一单据定义跨请求共用（缓存），是零拷贝的核心（§7）。

> 与现状差异：`ResultConverter::convert_postgres_rows` 只产**单层**、且 Schema 从 SQL 结果**推断**（label 空）。`DocLoader` 改为 Schema 从**单据定义**来（带 label/caption/类型精度），并**按 upper_id 嵌套**。可以复用 `convert_postgres_rows` 拿单层，再自行 `add_child` 组树；也可以直接用「定义 Schema + 逐值填充」以获得精确类型。

### 5.2 列式小包协议（`ColumnarCodec`，新增）

后端把嵌套 `DataSet` 序列化为**列式包**（对齐前端 `CmxDataSet.fromJSON` 已识别的结构）：

```jsonc
// GET /api/doc/data 响应 data 字段
{
  "datasetId": "cv_batch",
  "columns": ["id", "upper_id", "line_no", "comp_unit_id", "doc_no", "doc_status", "total_dr"],
  "rows": [
    ["20260003", null, 1, "1000", "PZ-0007", "posted", 1130000.00]
  ],
  "childRows": {
    "20260003": {
      "headers": {
        "datasetId": "cv_header",
        "columns": ["id","upper_id","line_no","fiscal_period_id","total_dr","total_cr"],
        "rows": [ ["1000000007","20260003",1,"2026-06","1130000.00","1130000.00"] ],
        "childRows": {
          "1000000007": {
            "account_lines": { "datasetId":"cv_acc_line", "columns":[...], "rows":[[...],[...]], "childRows":{...} }
          }
        }
      }
    }
  }
}
```

**为什么这样最省**（对齐 §8 小包）：

- **键名只出现一次**（`columns`），行是**纯值数组** `rows:[[...]]`——消灭现状「逐行重复键名」的最大浪费。
- **子层按父 id 挂 `childRows`**——精确复原主从，且父子只传各自的列。
- 前端 `CmxDataSet.fromJSON(json)` **原生识别** `{columns, rows, childRows}`（`cmx-data-set.js:362`），逐层递归还原，零适配。

### 5.3 前端装配（新增适配层，页面 host 上）

```js
// ④ 列式包 → { rootId: CmxDataSet } 树
const pkg = await host.loadDocData({ docFile, filter });     // fetch → JSON.parse 或 msgpack decode
const C   = globalThis.__cmxDataComp || host.__cmxClasses;
const rootDs = C.CmxDataSet.fromJSON(pkg);                    // 逐层递归还原（含 childRows）
const dsMap = { [pkg.datasetId]: rootDs };

// ⑤ 交给协调器（零拷贝接管：ms 直接持有这些 CmxDataSet 与其 _children，不再复制）
const ms = new C.CmxMasterSlave({
  schema:       docSchema,        // 由定义 voucherSchema.schema 生成（id + children 嵌套）
  relations:    docRelations,     // 由定义 relations 生成（parent/child/parentKey/childKey）
  aggregations: docAggregations,  // 由定义 aggregations 生成（from/to/field/toField/agg）
});
ms.bindTable('cv_batch', batchGrid);
ms.bindTable('cv_batch.cv_header', headerGrid);            // 注意：路径用 schema 的 child id
ms.bindTable('cv_batch.cv_header.cv_acc_line', accGrid);
ms.setDataSet(dsMap);                                      // 装载 + 预热聚合 + 首行级联点亮
host.__cmxMs = ms;
```

> `ms.setDataSet(dsMap)`（`cmx-master-slave.js:292`）会**递归接管**每个 `CmxDataSet` 的 `_children`，给每层注册 `row-changed/cursor-changed/ds-row-added/ds-row-removed` 监听，并 `_primeCursors()` 定位各根首行、自上而下点亮子层视图。**无需**再手动转换或二次拷贝。

### 5.4 装载时序图


## 5A. 维度解析：单据列引用数据字典，如何显示 name/属性（不牺牲性能）

### 5A.0 问题定义

单据的很多列存的是**字典的 id 或 code**（如 `comp_unit_id=1000`、`gl_account_id="2221"`），但界面要显示**对应的名称或字典某属性**（如「江苏销售分公司」「应交税费」）。元数据已声明这层引用：

```jsonc
// 字段元数据里的引用三件套（真实存在）
{ "id":"gl_account_id", "dataType":"BIGINT",
  "refDict":"gl_account",   // 引用哪个字典
  "refField":"code",        // 用字典的哪个键匹配本列值（id 或 code）
  "displayField":"name" }   // 显示字典的哪个属性（name / 或任意属性）
```

**朴素做法（后端 JOIN 字典）的性能陷阱**：一张单据几十列引用十几个字典，每次装载都 `LEFT JOIN` 十几张字典表 × 多层 × 多行——JOIN 爆炸、且**本系统字典条目当前多以 JSON 文件存**（`data/dict/entries/<dictId>.json`），后端甚至没有可 JOIN 的 SQL 表，只能读文件循环匹配，更慢。**逐行逐列去查字典 = N×M 次点查**，联机装载不可接受。

> 你提的「把解析值存到与单据关联的表」是可行方案之一（下文 **L2 伴生宽表**），但不是所有场景的最优。下面给一套**分层组合**：按「字典规模 / 变更频率 / 是否需服务端搜索排序」选层，用**元数据 `resolveStrategy` 参数**控制，兼顾性能、通用性、可扩展性。

### 5A.1 四层解析策略（决策矩阵）

| 层 | 名称 | 解析发生地 | name 存哪 | 适用 | 代价 |
|---|---|---|---|---|---|
| **L0** | **前端整典缓存 + 本地映射**（默认首选） | 前端 | 不落库，前端内存 Map | 中小字典（≤ 数千条）、被多单据共用 | 首次拉整典；字典改了要失效 |
| **L1** | **装载期后端解析 → 派生列**（瞬态） | 后端 DocLoader | 不落库，随包传 `xxx__name` 派生列 | 大字典、单据少、要即取即显 | 每次装载解析（有缓存则廉价） |
| **L2** | **伴生宽表（反范式落库）** | 保存期写 | 落库：单据伴生表 `<doc>_disp` | 需服务端按 name 搜索/排序/导出、报表 | 冗余存储、字典改名要重刷 |
| **L3** | **物化视图 / 触发器** | DB 维护 | 落库：物化视图列 | 超大数据量、name 相对稳定、重查询 | DB 运维复杂、刷新延迟 |

**核心思想**：**解析值是"派生数据"，谁最省就放谁那**。多数列用 L0（前端 Map，零后端成本、零冗余）；只有「需要在后端按 name 过滤/排序/分页/导出」的列才升到 L2 落库。**同一单据不同列可用不同层**——由元数据逐列声明。

### 5A.2 元数据扩展（逐列声明解析策略，纯叠加）

在字段现有 `refDict/refField/displayField` 上，加一个可选 `resolveStrategy`（缺省 = `frontend`，即 L0）：

```jsonc
{ "id":"gl_account_id", "refDict":"gl_account", "refField":"code", "displayField":"name",
  "resolveStrategy": "frontend",          // "frontend"(L0默认) | "backend"(L1) | "persist"(L2) | "view"(L3)
  "displayAs": "gl_account_id__name",     // 派生/落库列名（L1/L2 用；缺省 = <id列>__<displayField>）
  "displayFields": ["name","category"] }  // 可选：一列值带出字典多个属性（to attribute 通用化）
```

- **通用性**：`displayField` 单属性、`displayFields` 多属性（同时带出 name + 分类 + 助记码…），覆盖你说的「to name / to code / to attribute」全部形态。
- **可扩展性**：新增字典引用列 = 加一段字段元数据，`resolveStrategy` 选层，**零代码**。解析引擎读元数据驱动，不硬编码任何字典。

### 5A.3 L0：前端整典缓存 + 本地映射（默认，零后端 JOIN）

**机制**：前端在装载单据后，收集单据用到的所有 `refDict`，**一次性批量拉这些字典的全量条目**（复用现成 `POST /api/dict/batch-data`，`batch_data_endpoint` 已支持一次多典），在前端建 `dictId → Map<key, entry>` 缓存；渲染时用 `CmxColumn` 的显示模板把 `id → entry[displayField]`。

```js
// 装载后：一次批量拉全部引用字典（整典缓存，被所有单据/所有行共用）
const dictIds = collectRefDicts(docMeta);            // 从元数据收集 ["gl_account","comp_unit",...]
const dicts   = await host.dictBatchData(dictIds);   // POST /api/dict/batch-data → { gl_account:[...], ... }
host.__dictCache = buildKeyMaps(dicts, docMeta);     // { gl_account: Map<code, {name,category,...}> }

// 渲染：CmxColumn 显示模板 id→name（cmx-revo-grid / cmx-ui5-form 已支持 cellTemplate/显示映射）
col.display = { kind: 'dict', dictId:'gl_account', keyField:'code', labelField:'name' };
// 组件内：const label = host.__dictCache['gl_account'].get(row.gl_account_id)?.name ?? row.gl_account_id
```

- **性能**：字典**整典只拉一次**（不是逐行逐列点查），之后全在前端内存 O(1) 查表。一张单据几百行×十几列全部本地解析，**零后端 JOIN、零逐值往返**。
- **小包**：单据数据包**只传 id/code，不传 name**（name 由前端 Map 补），传输量最小——与 §8 小包目标一致。字典包可独立缓存、跨单据复用、`ETag`/版本号协商增量。
- **失效**：字典改动 → 版本号/`updatedAt` 变 → 前端按版本重拉该典（只重拉变的典，不影响单据数据）。
- **已就绪度高**：`batch_data_endpoint`、`cmx-dict-data-source.js`（`keyField/labelField/loadByKeys`）、combo/列显示模板都已存在，L0 主要是"串起来 + 加缓存层"。

### 5A.4 L1：装载期后端解析 → 派生列（大字典、即取即显）

当某字典**太大不宜整典下发**（如百万级科目/客户），但该列**需随单据立即显示**：在 `DocLoader` 装载时，后端**只对本页出现的 id 集**批量解析（`WHERE key = ANY($ids)` 一次取回，或查后端字典缓存），把 name 作为**瞬态派生列**塞进列式包，**不落库**：

```
DocLoader 装载 cv_header 后：
  收集本层某列去重 id 集：ids = distinct(rows[].gl_account_id)
  批量解析：SELECT code,name FROM cf_gl_account WHERE code = ANY($ids)   // 一次，非逐行
            （字典存文件时：读该典缓存 Map 批量取；见 5A.6 后端字典缓存）
  回填派生列：row["gl_account_id__name"] = map[row.gl_account_id]
  列式包 columns 增列 "gl_account_id__name"（瞬态，前端直接显示，不参与回存）
```

- **性能**：每列**一次 `ANY($ids)` 批量查**（命中字典主键索引），而非逐行 JOIN；配合 §5A.6 后端字典缓存可完全免 DB。
- **小包权衡**：派生列会增大包体（name 进包）。故 L1 只给「大到不能整典下发」的少数列用；能 L0 的仍走 L0（不进包）。
- **不落库**：派生列是"读时计算"，`displayAs` 列只出现在响应，`ChangeSetCollector` 忽略它（不回存）。

### 5A.5 L2：伴生宽表（你提的方案——反范式落库，服务端可搜可排）

当某些列的 name **需要在后端参与搜索 / 排序 / 分页 / 报表导出**（如"按科目名称模糊查单据""按客户名排序"），此时必须让 name **在库里可查**——落一张**与单据一一对应的伴生显示表**：

```sql
-- 伴生宽表：与主表(每层可各一张)行一一对应(共享主键 id)，只存"解析出来的显示值"
CREATE TABLE cv_header_disp (
    id            BIGINT PRIMARY KEY,          -- = cv_header.id（一一对应，非新主键）
    upper_id      BIGINT,                      -- 冗余父指针，便于按树清理
    gl_account_id__name   VARCHAR(200),        -- 解析值：科目名
    comp_unit_id__name    VARCHAR(200),        -- 解析值：公司名
    comp_unit_id__category VARCHAR(64),        -- 解析值：公司分类（to attribute 通用化）
    _resolved_at  TIMESTAMPTZ DEFAULT now()    -- 解析时点（判过期）
);
CREATE INDEX idx_cvh_disp_acc_name ON cv_header_disp (gl_account_id__name);  -- 支持按名搜索/排序
```

- **写入时机（复用 §6.4 保存链路）**：`DocSaver` 保存主表行的**同一事务**内，对标了 `resolveStrategy:"persist"` 的列，解析 id→name 后 UPSERT 进 `<table>_disp`（`merge`/`replace` 两模式一致处理）。**装载时**主表 `LEFT JOIN <table>_disp ON id`（一对一、走主键、代价极低，**不是** JOIN 十几张字典表）即可连 name 一起取回。
- **通用性**：伴生表由**元数据自动生成**——扫描单据各层带 `resolveStrategy:"persist"` 的列，用 §4 的 `TableDefine`/DDL 引擎建 `<table>_disp`（`<id列>__<displayField>` 为列名，类型取字典 `displayField` 的类型）。加一列引用列 → 重新 deploy → 伴生表自动加列（additive）。
- **一致性（字典改名）**：字典条目改了 name，旧单据伴生表里的 name 会过期。三种刷新策略（可配）：
  1. **懒刷**：装载时比对字典版本 > `_resolved_at` 则该行现解析并回写（读时自愈）。
  2. **批刷**：字典改名触发后台任务，按 `refDict` 反查所有引用它的 `_disp` 表批量更新（可离线/限流）。
  3. **不刷（快照语义）**：单据要的就是"当时的名称"（如历史凭证按当时科目名），过期即正确——ERP 常见。
- **代价**：冗余存储 + 维护刷新——**故只给"真的要服务端按 name 检索/排序/导出"的列用**，不是所有引用列都落库。

### 5A.6 L3 与后端字典缓存（超大数据 / 通用底座）

- **L3 物化视图**：数据量超大、name 稳定、以查询为主时，用 PG 物化视图把「主表 + 伴生显示」物化，定期 `REFRESH`。属重查询/报表专用，运维成本高，按需启用。
- **后端字典缓存（L1/L2 的公共底座）**：无论字典存文件还是物理表，后端都应有一层 `dictId → Arc<HashMap<key, entry>>` 的进程内缓存（与 §3.7 定义缓存同构，`DashMap` + 版本失效）。L1 解析、L2 保存期解析都优先命中它，**把"JOIN/查库"降为"内存查表"**——这是"不牺牲性能"的公共保障。

### 5A.7 组合推荐与决策流程

```
对单据每个"引用字典的列"，按元数据 resolveStrategy 决定：
  ├─ 默认 frontend(L0)：字典中小、被多单据共用          → 前端整典缓存 Map，包里只传 id（最省，首选）
  ├─ backend(L1)：字典超大、不宜整典下发、要即显         → 装载期 ANY($ids) 批量解析成派生列（不落库）
  ├─ persist(L2)：要在后端按 name 搜索/排序/分页/导出     → 伴生宽表 <table>_disp，保存期写、装载期一对一 JOIN
  └─ view(L3)：超大量 + name 稳定 + 重报表查询            → 物化视图，定期刷新
公共底座：后端字典缓存（内存 Map，版本失效）——L1/L2 解析都命中它，杜绝逐行查库。
```

**为什么这套优于"全部落一张表"**：
- **性能**：绝大多数列走 L0（前端 Map，**零后端成本、包里不带 name 最小化传输**）；只有少数"需服务端检索"的列才落库（L2），避免全量冗余与全量刷新负担。
- **通用性**：解析引擎**读 `refDict/refField/displayField/displayFields/resolveStrategy` 元数据驱动**，不硬编码任何字典；单属性/多属性/id 匹配/code 匹配全覆盖。
- **可扩展性**：新增引用列 = 加字段元数据选层，**零代码**；伴生表由 DDL 引擎按元数据自动建/加列（additive-safe）。
- **一致性可选**：L2 提供懒刷/批刷/快照三策略，适配"实时名称"与"历史快照名称"两类业务语义。

> 落地优先级：**先做 L0**（覆盖 80% 列、纯前端+复用现成 batch-data，见 §11 阶段 1.5）→ 需要服务端检索时再对特定列上 **L2**（复用 §6.4 保存链路 + §4 DDL 引擎）→ 超大场景才评估 L3。

### 6.3 前端 changeset 收集（`ChangeSetCollector`，新增）

装载后，适配层给协调器管理的**每层 `CmxDataSet`** 挂一层轻量监听，把变更累积成**按层的 changeset**：

```js
// ⑥ 订阅事件累积变更（不改模型，纯旁路记账）
const cs = new ChangeSetCollector(ms);   // 内部：Map<path, { inserted:Set<id>, updated:Set<id>, deleted:Set<id> }>
// ds-row-added(row)   → inserted.add(row.id)（若之前在 deleted 则抵消）
// row-changed(row)    → 若非新增，updated.add(row.id)
// ds-row-removed(row) → deleted.add(row.id)；若之前在 inserted 则纯抵消（净零，不回后端）
```

保存时导出**最小 changeset**（只含动过的行，且只含变更列可选）：

```jsonc
// POST /api/doc/save 请求体
{
  "db_id": "primary", "docFile": "cmxfico_doc_meta_v1.json",
  "changes": {
    "cv_batch":     { "updated": [ { "id":"20260003", "fields": { "doc_status":"posted" } } ] },
    "cv_header":    { "updated": [ { "id":"1000000007", "fields": { "total_dr":1130000.00, "total_cr":1130000.00 } } ] },
    "cv_acc_line":  {
      "inserted": [ { "id":"100000000703", "upper_id":"1000000007", "line_no":3, "fields": { "gl_account_id":"2221", "entered_cr":130000.00 } } ],
      "deleted":  [ "100000000702" ]
    }
  }
}
```

> **对齐后端语义**：`cmx-core::DataSet` 本就有 `inserted/updated/deleted` 三池（`rds.rs:394`），只是**不默认序列化**（坑 B）。本协议把它们**显式过线**，后端可直接映射回 `DataSet` 的三池语义处理。**小包**：只传动过的行 + 可选只传变更列。

### 6.4 后端 `DocSaver`（新增服务）：两种保存模式，参数控制

前端改完单据后，回存需支持**两种模式，由请求参数 `saveMode` 控制**：

| 模式 | `saveMode` | 语义 | 前端传什么 | 适用场景 |
|---|---|---|---|---|
| **增量更新** | `"merge"`（默认） | 按 changeset 精确 `INSERT/UPDATE/DELETE` | 最小 changeset（§6.3） | 常规联机编辑：保主键/审计、写入最小、可乐观锁 |
| **先删后插** | `"replace"` | 对涉及的父行子树，先 `DELETE` 旧子行，再全量 `INSERT` 当前子行 | 整棵（或整子树）当前全量数据 | 批量重算/导入/"覆盖式提交"：前端难以精确 diff，图省心与绝对一致 |

**两模式共性**（都遵守）：**同一 `txn_id` 单事务** + **按 `relations` 拓扑序（插/更父先、删子先）** + **参数化 `execute_sql_with_datavalues`**。差异只在"如何把前端状态落到每层表"。

**请求信封**（`saveMode` 顶层控制，可按层覆盖）：

```jsonc
// POST /api/doc/save
{
  "db_id": "primary", "docFile": "cmxfico_doc_meta_v1.json",
  "saveMode": "merge",              // "merge"(默认) | "replace"，全局默认
  "rootId": "20260003",            // replace 模式必带：界定"要覆盖哪一（几）棵树"的根
  "layerModes": { "cv_aux_line": "replace" },  // 可选：按层覆盖全局（混合模式）
  "changes": { /* merge 用：见 §6.3 */ },
  "snapshot": { /* replace 用：整树/子树当前全量，结构同 §5.2 列式包或 exportKeyValue */ }
}
```

#### 模式一：增量更新（`merge`）

```
txn = begin(db_id)
try:
  for 每层 layer（父先，L1→Ln）:
    for row in changes[layer].inserted:                 // 幂等 UPSERT
      exec(txn, "INSERT INTO <t>(id,upper_id,line_no,<cols>) VALUES($1,...)
                 ON CONFLICT(id) DO UPDATE SET ...", [...])
    for row in changes[layer].updated:                  // 只更变更列
      exec(txn, "UPDATE <t> SET <col=$..> WHERE id=$1", [...])
  for 每层 layer（子先，Ln→L1）:                          // 删子先，不留孤儿
    if changes[layer].deleted:
      exec(txn, "DELETE FROM <t> WHERE id = ANY($1)", [deletedIds])   // 批量删
  commit(txn); return { ok:true, mode:"merge", affected:{...}, idMap }
except e: rollback(txn); return { ok:false, error:e }
```

- **保主键与审计**：更新走 `UPDATE`，行 id 不变，`update_time/update_by` 连续。
- **写入最小**：只动 changeset 里的行/列。
- **可乐观锁**（可选）：`UPDATE ... WHERE id=$1 AND version=$old`，`rows_affected=0` ⇒ 并发冲突，回滚报错。
- **依赖前端 changeset 准确**（坑 A/§6.3）——这是它唯一的前提。

#### 模式二：先删后插（`replace`）

```
txn = begin(db_id)
try:
  # 1) 先删：按 rootId 圈定的整棵子树，自底向上删（子先父后）
  for 每层 layer（子先，Ln→L1）:
    # 沿 upper_id 链把"属于 rootId 这棵树的本层旧行"全删掉
    exec(txn, "DELETE FROM <t> WHERE upper_id = ANY($parentIds_of_this_layer)")
    # 根层：DELETE FROM <L1> WHERE id = ANY($rootIds)
  # 2) 再插：按 snapshot 自顶向下全量 INSERT（父先，保证子 upper_id 有父）
  for 每层 layer（父先，L1→Ln）:
    for row in snapshot[layer]:
      exec(txn, "INSERT INTO <t>(id,upper_id,line_no,<cols>) VALUES($1,...)", [...])
  commit(txn); return { ok:true, mode:"replace", idMap }
except e: rollback(txn); return { ok:false, error:e }
```

- **删除范围界定（关键）**：`replace` **必须**由 `rootId`（+层级 `upper_id` 链）**严格圈定**"要覆盖的那几棵树"，`DELETE` 只作用于这些根的子孙，**绝不** `DELETE FROM <t>`（无 WHERE）误删他人单据。先查各层 `WHERE upper_id IN (上层被删 id)` 得到本层待删 id 集，逐层下推。
- **前端简单**：不需精确 diff，把整棵（子）树当前状态发过来即可，无遗漏风险。
- **代价**：行 id 与审计连续性中断（除非 snapshot 保留原 id 做"删同 id 再插同 id"）、写放大、并发下"整树覆盖"易冲掉他人改动——**故 `replace` 建议配合悲观锁或"我方独占编辑"语义**。

#### 两条硬护栏（两模式共用）

- **删除边界**：无论哪种模式，`DELETE` 一律带 `WHERE`（`id = ANY(...)` 或 `upper_id = ANY(...)`），**永不无条件删表**；`replace` 的删除集必须由 `rootId` 树形圈定。
- **id 生成**：新增行 id 建议**后端生成**（雪花/序列），保存后回 `idMap`（前端临时 id → 后端正式 id）前端回填，避免临时 id 泄漏进 `upper_id`（见 §12 风险 4）。

**回存后可选回读**：保存成功后按需 `DocLoader` 重取该单据（或仅回传 `idMap`），前端 `ms.setDataSet` 刷新——保证前后端一致。

### 6.5 保存时序图（双模式）

```
前端 保存按钮
   │  merge:   cs.export() → 最小 changeset      →┐
   │  replace: ms.exportColumnar()/整树 snapshot →┤  POST /api/doc/save { saveMode, rootId?, changes?/snapshot? }
   ▼                                              │
后端 DocSaver（begin txn）
   │  ┌── saveMode = "merge" ──────────────┐   ┌── saveMode = "replace" ─────────────┐
   │  │ L1→Ln upsert(inserted)+update       │   │ Ln→L1 DELETE(按 rootId 子树圈定)     │
   │  │ Ln→L1 DELETE id=ANY(deleted)        │   │ L1→Ln INSERT(snapshot 全量)          │
   │  └─────────────────────────────────────┘   └──────────────────────────────────────┘
   │  commit(txn)
   ▼
前端 收 { ok, mode, idMap } → cs.reset() → （可选）重载或按 idMap 回填新 id
```

## 6A. 单据版本化 / 历史 / 审计追溯（单据级开关，开启后支持）

### 6A.0 需求与设计目标

有些单据需要**每次数据变化都被记录、可查询、可追溯、可审计**——这是单据的一项**设置**，开启后生效（不开则零开销）。目标四件事：

- **可记录**：每次保存产生一个不可变的历史版本（append-only，永不改写）。
- **可查询**：能列出某单据的全部版本、取任一历史版本的完整数据。
- **可追溯**：能对比任意两版差异（哪几行、哪几列、旧值→新值、谁改的）。
- **可审计**：每次变更记录 who / when / what / why（操作人、时间、动作、备注/单号）。

> 复用现成范式：后端已有 `cmx_model_source`（**append-only + JSONB 快照 + `is_current`**，模型中心用）与 `cmx_audit_log`（操作级审计流水，`details` JSON）。本方案把这套成熟模式**平移到业务单据数据**，不新造机制。

### 6A.1 单据级开关（`docMeta.versioning`）

版本化是**逐单据**能力，落在单据定义的 `docMeta` 上（与现有 `version/designStyle/voucherStatusFlow` 并列，纯叠加）：

```jsonc
"docMeta": {
  "metaKind": "DOC", "version": 1,
  "versioning": {
    "enabled": true,                 // 总开关：关闭则整套版本化零开销
    "granularity": "document",       // "document"(整单快照,默认) | "row"(行级历史)
    "store": "jsonb",                // "jsonb"(单表快照,默认) | "shadow"(每层影子表) | "both"
    "diff": true,                    // 是否同时落"字段级变更明细"（可查询/审计强）
    "retention": { "keep": 50, "days": 3650 },  // 保留策略：最多 50 版 / 10 年（可选）
    "reason_required": false          // 保存是否强制填变更原因
  }
}
```

- **`granularity`**：`document` = 每次存整单一个快照版本（ERP 主流：能完整回看"某版单据长啥样"）；`row` = 逐行历史（细到行的时间线，适合极少数需要"某行的演变"的场景）。默认 `document`。
- **`store`**：`jsonb` = 一张版本表存整单 JSONB 快照（简单、可回滚、可整版取回）；`shadow` = 每层物理表配一张 `_hist` 影子表（可 SQL 查询/按列追溯/报表）；`both` = 两者兼得。默认 `jsonb`，需强查询时上 `shadow`。
- 关闭（`enabled:false` 或无 `versioning`）→ `DocSaver` 完全跳过版本逻辑，与非版本化单据**零差异、零开销**。

### 6A.2 存储设计

#### 方案 A：JSONB 整单快照表（`store:"jsonb"`，默认）

一张**通用**版本表（所有开启版本化的单据共用，非每单据一张），存整单列式包快照：

```sql
CREATE TABLE cmx_doc_revision (
    id            BIGINT PRIMARY KEY,          -- 版本记录主键（雪花）
    doc_file      VARCHAR(200) NOT NULL,       -- 单据定义（哪种单据）
    root_table    VARCHAR(100) NOT NULL,       -- 根层表名（如 cv_batch）
    root_id       BIGINT       NOT NULL,       -- 单据根行 id（哪一张单）
    rev_no        INT          NOT NULL,       -- 版本号：该单第几版（1,2,3...）
    is_current    SMALLINT     DEFAULT 1,      -- 是否当前版（1/0，同 root 仅一行为 1）
    op            VARCHAR(16),                 -- create / update / delete / restore
    snapshot      JSONB        NOT NULL,       -- ★ 整单列式包快照（§5.2 结构，含各层各行）
    change_summary JSONB,                      -- 可选：本版变更摘要（§6A.3 diff）
    reason        VARCHAR(500),                -- 变更原因（reason_required 时必填）
    actor_id      VARCHAR(64),  actor_name VARCHAR(100),   -- who
    created_at    TIMESTAMPTZ  DEFAULT now(),  -- when
    biz_status    VARCHAR(32)                  -- 冗余当时单据状态（draft/audited/posted，便于按态检索）
);
CREATE UNIQUE INDEX uk_doc_rev ON cmx_doc_revision (doc_file, root_id, rev_no);
CREATE INDEX idx_doc_rev_cur   ON cmx_doc_revision (doc_file, root_id, is_current);
CREATE INDEX idx_doc_rev_time  ON cmx_doc_revision (root_id, created_at);
```

- **append-only**：每次保存 `rev_no+1` 追加一行，旧版永不改写（`is_current` 翻旧为 0、新版置 1）。
- **`snapshot` 直接复用 §5.2 列式包**：`ColumnarCodec.encode(整单DataSet)` 的产物直接进 JSONB——**零额外序列化代码**，回滚时 `CmxDataSet.fromJSON(snapshot)` 直接还原。
- **通用**：一张表服务所有版本化单据，加新单据无需建表。

#### 方案 B：每层影子表（`store:"shadow"`，需强查询/追溯时）

每层物理表 `<t>` 配一张 `<t>_hist`，列 = 原表列 + 版本维度列（由 §4 DDL 引擎按元数据自动生成）：

```sql
CREATE TABLE cv_header_hist (
    _hist_id   BIGINT PRIMARY KEY,       -- 历史行主键
    _rev_no    INT NOT NULL,             -- 属于该单第几版
    _op        VARCHAR(16),              -- I/U/D（本行在这版的动作）
    _valid_from TIMESTAMPTZ NOT NULL,    -- 该版生效时点（时序：valid_from/valid_to 双时区间）
    _valid_to  TIMESTAMPTZ,              -- NULL = 当前有效
    id         BIGINT NOT NULL,          -- 原行 id（+ 原表所有业务列...）
    upper_id   BIGINT, line_no INT, /* ...原表全部业务列... */
    _actor_id  VARCHAR(64)
);
CREATE INDEX idx_cvh_hist_row ON cv_header_hist (id, _rev_no);
```

- **可 SQL 追溯**：`SELECT * FROM cv_header_hist WHERE id=$1 ORDER BY _rev_no` 得某行完整演变；`_valid_from/_valid_to` 双时区间支持"某时刻单据是什么样"（temporal 查询）。
- **代价**：每层一张影子表 + 写放大，故仅在 `store:"shadow"/"both"` 时启用。

#### 方案对比

| 维度 | A · JSONB 快照 | B · 影子表 |
|---|---|---|
| 建表 | 1 张通用表（零维护） | 每层 1 张（DDL 引擎自动建） |
| 取整版数据 | 直接（`fromJSON`） | 需按 rev 拼各层 |
| 按列/行 SQL 追溯 | 弱（JSONB 内查） | 强（原生列） |
| 时序查询（某时刻） | 需自解析 | 原生 `valid_from/to` |
| 存储/写入成本 | 低（一行一版） | 高（各层各行） |
| 回滚 | 极简（整包还原） | 需逐层重建 |
| **推荐** | **默认** | 需报表/合规级追溯时叠加 |

### 6A.3 字段级变更明细（`diff:true`，审计增强）

除整版快照外，可同时落**字段级变更明细**（回答"这版到底改了什么"），复用 §6.3 的 changeset + 现成 `cmx_audit_log` 语义：

```sql
CREATE TABLE cmx_doc_change (
    id         BIGINT PRIMARY KEY,
    rev_id     BIGINT NOT NULL,          -- → cmx_doc_revision.id（属于哪一版）
    root_id    BIGINT NOT NULL,
    layer      VARCHAR(100),             -- 层表名（cv_header/cv_acc_line...）
    row_id     BIGINT,                   -- 变更的行
    op         VARCHAR(8),               -- I/U/D
    field      VARCHAR(100),             -- 变更字段（U 时逐字段一行；I/D 时可空）
    old_value  JSONB, new_value JSONB,   -- 旧值→新值
    actor_id   VARCHAR(64), created_at TIMESTAMPTZ DEFAULT now()
);
CREATE INDEX idx_doc_change_rev ON cmx_doc_change (rev_id);
CREATE INDEX idx_doc_change_row ON cmx_doc_change (root_id, row_id, field);
```

- **数据来源**：`merge` 模式下前端 changeset 已含 inserted/updated/deleted + 变更列；`updated` 的 `fields` 里每个键 = 一条 `U` 明细（`old_value` 从上一版快照取）。`replace` 模式后端 diff 新旧快照生成明细。
- **可查询/可审计**：`SELECT field,old_value,new_value,actor_id,created_at FROM cmx_doc_change WHERE root_id=$1 AND field='total_dr'` → 某字段的完整变更史（谁在何时把金额从多少改成多少）。

### 6A.4 与保存链路（§6.4）的咬合——快照在保存事务内产生

版本化**不是独立步骤**，而是嵌进 §6.4 的 `DocSaver` 同一事务（保证"数据写了、版本也记了"原子一致，规避半保存）：

```
DocSaver.save(changes/snapshot, saveMode):
  txn = begin(db_id)
  try:
    ── 若 versioning.enabled ──
    1. 读当前版（is_current=1）快照 → prevSnapshot（供 diff 与 old_value）
    2. 按 §6.4 merge/replace 写主表各层（同事务）
    3. 重新装配"保存后的整单 DataSet"（内存现成，无需回查）
    4. rev_no = prev.rev_no + 1
       UPDATE cmx_doc_revision SET is_current=0 WHERE doc_file=? AND root_id=? AND is_current=1
       INSERT cmx_doc_revision(... rev_no, is_current=1, op, snapshot=ColumnarCodec.encode(整单),
                               change_summary, reason, actor, biz_status)
    5. 若 store∈{shadow,both}：各层变更行按 _op/_rev_no 追加进 <t>_hist；旧当前行 _valid_to=now()
    6. 若 diff：把 changeset 展开成 cmx_doc_change 明细（U 逐字段，old 从 prevSnapshot 取）
    7. 可选：写一条 cmx_audit_log（operation="doc.save", target=root_id, details=摘要）
    ── 版本化结束 ──
    commit(txn)
  except e: rollback(txn)   // 数据与版本一起回滚，绝不半保存
```

- **零拷贝复用**：第 3 步"保存后整单 DataSet"就是内存里那棵树，`ColumnarCodec.encode` 直接产快照（与 §5.2 同一序列化器、§7 借用式），不重查库、不重序列化。
- **维度解析（§5A）**：快照存**原始 id/code**（不含解析 name），保持小且稳定；回看历史版时同样走 §5A 的 L0/L1 解析显示——**历史版天然按"当时值"或"现值"两种语义可选**（存 id 用现值解析、若要"当时名称"则快照连 `_disp` 一起存）。

### 6A.5 查询 / 追溯 / 回滚 API（新增端点）

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/api/doc/revisions?docFile&rootId` | 列某单全部版本（rev_no / op / actor / created_at / biz_status / reason），倒序时间线 |
| GET | `/api/doc/revision?docFile&rootId&rev` | 取某历史版**完整数据**（返回该版 `snapshot` 列式包，前端 `fromJSON` 直接渲染） |
| GET | `/api/doc/diff?docFile&rootId&from&to` | 对比两版差异（读 `cmx_doc_change` 或现算两快照 diff）：逐层/逐行/逐字段 old→new |
| GET | `/api/doc/changes?docFile&rootId&field?` | 字段级变更史（审计：谁何时把某字段从 X 改成 Y） |
| POST | `/api/doc/restore` | `{ docFile, rootId, rev }` 把某历史版**恢复为新当前版**（`op="restore"`，走 §6.4 `replace` 写回 + 追加新版，**不删历史**） |

- **回滚语义**：`restore` 不是"删掉后面的版本回到过去"，而是"把旧版内容作为一个**新版本**写入"（op=restore）——历史完整不丢，可审计"谁在何时回滚到了第几版"。
- **前端**：历史版查看直接 `ms.setDataSet(CmxDataSet.fromJSON(该版snapshot))` 只读渲染（复用全部可视化组件，零新增 UI 逻辑）；diff 视图按 `cmx_doc_change` 渲染新旧对照。

### 6A.6 版本化时序图

```
保存（versioning.enabled）
   │  POST /api/doc/save { saveMode, changes/snapshot }
   ▼
DocSaver（begin txn）
   │  ① 读 prevSnapshot(is_current=1)
   │  ② 写主表各层（merge/replace，§6.4）
   │  ③ encode(保存后整单) → snapshot
   │  ④ rev_no+1；旧版 is_current=0；INSERT cmx_doc_revision(is_current=1)
   │  ⑤ (shadow) 各层 _hist 追加；(diff) cmx_doc_change 逐字段；(audit) cmx_audit_log
   │  commit(txn)  ← 数据+版本原子一致
   ▼
追溯：GET /revisions（时间线）→ /revision?rev（取某版）→ ms.setDataSet(fromJSON) 只读回看
      GET /diff?from&to（版本对比）  POST /restore（旧版→新当前版，历史不丢）
```

### 6A.7 通用性、可扩展性、性能

- **通用性**：一套机制服务所有单据；`cmx_doc_revision`/`cmx_doc_change` 是**通用表**（按 `doc_file+root_id` 区分），加新单据零建表；`shadow` 影子表由 §4 DDL 引擎按元数据自动生成/加列（additive）。
- **可扩展性**：新增单据只需在 `docMeta.versioning` 打开开关选粒度/存储；保留策略、diff、原因必填都是声明式参数。
- **性能**：
  - 关闭时**零开销**；开启时快照复用内存 DataSet + §7 借用序列化，**不重查库**。
  - 快照存 JSONB（PG 原生、可 GIN 索引）；`is_current` 索引让"取当前版"O(1)。
  - 历史读写与主表**物理分离**（版本表/影子表独立），不拖慢联机主表的装载/保存热路径。
  - 保留策略（`keep/days`）定期归档/清理超期版本，控制增长。

> 落地优先级（见 §11 阶段 4.5）：先做 **A·JSONB 快照 + restore + revisions/revision 查询**（复用列式包与保存事务，改动最小即得"可记录/可查询/可回滚/可追溯整版"）→ 需字段级审计时开 `diff`（`cmx_doc_change`）→ 需报表级 SQL 追溯/temporal 时再上 `shadow` 影子表。

## 7. 后端零拷贝（约束 A）

现状（transport/model agent 证实）：`axum::Json` 每次 `serde_json::to_vec` 新分配 `Vec<u8>`；无 `Cow`、无 `rkyv`/`arrow`；仅 `Arc<Schema>`（模型级共享）与 `bytes::Bytes`（下载用）。因此"零拷贝"是**渐进增强**，分三层落地：

### 7.1 Schema / 元数据零拷贝（立即可得）

- **`Arc<Schema>` 全程共享**：`DocLoader` 里同一层所有行、同一单据定义跨请求，**共用一个 `Arc<Schema>`**（`rds.rs` 已是 `schema:Arc<Schema>`）。用 `OnceLock`/`DashMap` 建「`docFile+version → Arc<Schema>[]`」缓存，请求间零重建、零拷贝。
- **列名/字段名 `Arc<str>` 或 `&'static`**：列式包的 `columns` 来自缓存 Schema 的字段名，序列化时借用而非克隆。

### 7.2 值层零拷贝（中等）

- **`SmolStr` 短串内联**：`DataValue::ShortStr/LongStr`（`cell.rs`）已是小串优化，状态码/币种/编码等不堆分配。
- **借用式序列化**：列式编码走 `RowsRef/RowRef` 式**借用序列化器**（`rds.rs` 已有先例），不物化中间 `Vec`。列式包的 `rows:[[...]]` 由 `serialize_seq` 流式吐值，值直接 `&DataValue` 借用。
- **`Bytes`/`BytesMut` 复用**：响应体用可复用缓冲，避免每请求新 `Vec`。

### 7.3 传输零拷贝（进阶，可选）

- **流式响应**：大单据用 `axum` 的 `Body::from_stream`，边组装边发，不在内存攒完整包（SSE 先例已在 `portal/handler.rs`）。
- **`rkyv`/列式二进制（远期）**：若要真·零拷贝反序列化，可引入 `rkyv`（当前**无**该依赖，需评估）；或直接用 Arrow IPC 列存（同样是新依赖）。**本方案默认不引入**，仅列为演进路线——因为「列式 JSON + msgpack + 压缩」已能满足小包目标，性价比更高。

> **务实取舍**：约束 A 的"尽量零拷贝"在本方案中= **①`Arc<Schema>` 共享 + ②借用式列式序列化 + ③`Bytes` 复用/流式**，不改数据面为 rkyv/arrow（避免伤筋动骨）。这三条都是在现有 `rds.rs`/`axum` 能力上叠加。

## 8. 传输小包（约束 B）

现状：**行式 JSON、键名逐行重复、不跳 null、无压缩**（`CompressionLayer` 已编译未挂载）。四级递进优化，**逐级叠乘**：

### 8.1 一级：列式化（最大结构收益）

行式 `[{id,upper_id,line_no,doc_no,...}, {...}, ...]`（每行重复 7+ 键名）→ 列式 `{columns:[7个键], rows:[[7值],[7值]]}`（键名 1 次）。**键名开销从 O(行数×列数) 降到 O(列数)**。对宽表/多行单据，裸 JSON 体积常降 **40%~60%**。前端 `fromJSON` 已原生支持，**零前端改造**。

### 8.2 二级：跳 null + 稀疏优化

- **跳 null**：把 `SKIP_NULL_IN_SERIALIZE`（`rds.rs:526`）语义引入列式编码——稀疏列的 null 不占位（列式下用「缺失即 null」或位图）。会计辅助行等稀疏结构收益显著。
- **只传变更列（保存侧）**：changeset 的 `updated` 只带动过的字段（§6.3），不回传整行。

### 8.3 三级：MessagePack（二进制编码）

- 后端已用 `rmp-serde`（WASM 边界），**扩到 HTTP**：按 `Accept: application/x-msgpack` 内容协商，`rmp_serde::to_vec(&columnar)` 出二进制。
- 前端引入轻量 msgpack 解码（如 `@msgpack/msgpack`），`res.arrayBuffer()` → `decode()`。
- msgpack 对数字/短串比 JSON 文本更紧（免引号、免逗号、变长整数），叠加列式再降 **15%~30%**。

### 8.4 四级：HTTP 压缩（一行中间件，最省力）

- `tower-http` 的 `compression-full` **已在依赖里**，只需在 `web-server/src/main.rs` 中间件栈加 `CompressionLayer`（br/gzip）。
- 对列式 JSON（大量重复结构、数字文本）压缩比极高，**通常再降 70%~85%**。这是**当前桌上最大、最省力的杠杆**。

### 8.5 组合收益（示意）

| 阶段 | 相对体积 | 手段 |
|---|---|---|
| 现状（行式 JSON、无压缩） | 100% | `RowRef` 逐行键名 |
| +列式 | ~50% | `ColumnarCodec` |
| +跳 null | ~42% | 稀疏优化 |
| +gzip/br | ~8%~12% | `CompressionLayer`（一行） |
| +msgpack 替 JSON 再压 | ~6%~9% | 内容协商 |

> **落地优先级**：先挂 `CompressionLayer`（1 行、立竿见影）→ 再上列式编码（前端零改）→ 视需要加 msgpack。三者独立、可分期。

## 12. 风险与护栏

1. **`upper_id` 非 DB 外键**：删父不会 DB 级联，`DocSaver` 必须应用层保证「子先删/连带删」（§6.4），否则留孤儿。
2. **前端无脏标记（坑 A）**：changeset 完全依赖 `ChangeSetCollector` 正确订阅事件；聚合回写（`aggregate` 改 `toField`）也会触发 `row-changed`，需甄别「用户改」vs「聚合改」——建议聚合写用 `row[key]=v` 直写（不经 `set`，不进 changeset），或在收集器里按来源打标。
3. **`cmx-tabulator` 回写死支**：`_onCellEdited` 判 `this._ds.set`（`CmxDataSet` 无 `set`，只有 `CmxRowSet.set`），若用 Tabulator 作可编辑主从视图，编辑不回模型。→ 主从可编辑场景**优先 `cmx-revo-grid`**。
4. **id 生成**：新增行 id 由前端临时生成（`r<base36>`）还是后端雪花？建议**后端生成**、保存后回 `idMap` 前端回填，避免临时 id 泄漏进 `upper_id`。
5. **大树内存**：整单大树全量装载。超大单据用根层分页（`filter/page` 作用于 L1）+ 子层按需（选中父行再拉子——可扩展为「懒下钻」变体，`DocLoader` 支持 `depth` 参数）。
6. **维度解析一致性（§5A）**：L2 伴生宽表的 name 会因字典改名过期——按业务语义选懒刷/批刷/快照三策略之一，勿默认"永远实时"。L0 前端缓存需版本协商失效，避免旧 name 长驻。`_disp` 表的 `DELETE`/UPSERT 必须与主表回存**同事务同拓扑序**，否则显示值与主数据不一致。
7. **版本化开销与增长（§6A）**：仅对开 `versioning` 的单据生效，务必默认关闭、按需开启。快照与主表回存**同事务**——若快照写失败必须回滚主数据，绝不"数据成功、版本丢失"。JSONB 快照随版本累积增长，必须配 `retention`（keep/days）归档清理；高频保存的单据慎开 `shadow`（写放大）。历史/影子表与主表物理分离，勿让版本写入拖慢联机热路径。

## 14. 查漏补缺：单据生命周期与横切关注点

前面 §1–§13 覆盖了「装载→模型→编辑→回存→维度解析→版本化」主链路。最后一轮审视发现：真实 ERP 单据还有一批**横切关注点**，其中数条**直接影响正确性**（不做会错），另一些是**必须明确的设计约定**。好消息是——经核对源码，所需的后端能力**大多已存在**，方案只需「串联 + 声明」。

### 14.1 【正确性】单据状态机约束保存/编辑（`voucherStatusFlow`）

**问题**：单据定义里已有完整状态机——`voucherStatusFlow.states` 声明每状态 `editable`（如 `draft.editable:true`、`audited/posted/reversed.editable:false`），`transitions` 声明 `action/from/to/guard`（权限守卫）。**但主链路的 §6.4 `DocSaver` 完全没读它**：过账（posted）的凭证在 ERP 里绝不能再改，这是铁律，漏了就是数据事故。

**方案**：
- **保存前置校验**：`DocSaver` 保存前读该单当前 `stateField` 值（如 `doc_status`），查 `voucherStatusFlow.states[当前状态].editable`；为 `false` 则**拒绝保存**（除非本次是合法的状态流转，见下）。
- **状态流转是独立动作，非普通保存**：审核/过账/反冲走**专门端点** `POST /api/doc/transition { docFile, rootId, action }`，后端校验 `transitions` 里 `from==当前态` 且 `action` 合法、跑 `guard`（权限 + 业务条件），通过才改 `stateField` 并（若版本化开启）记一个版本（`op=transition`）。
- **前端联动**：装载时前端据当前状态的 `editable` 决定网格/表单可编辑性（`ms.setEditable(false)` 已就绪，§6.1）；不可编辑态只读展示 + 只显可用的 `transition` 按钮。
- **字段级可编辑**：叠加 §字段元数据的 `edit.editableWhen/readonlyWhen`（已有），做到「同一单据，此状态下这几列可改、那几列锁死」。

### 14.2 【正确性】后端二次校验（`validationRules`，前端校验不可信）

**问题**：单据定义有 `validationRules`（跨层业务规则，如"凭证本位币借贷必须平衡""记账期间未打开"，带 `expression/message/scope`）。前端有 `formula-eval.js` 能算，但**前端校验可被绕过**（改请求直发）。经核对，**后端目前没有对应的表达式求值器**——这是真缺口。

**方案**：
- **后端表达式求值器（新增）**：在后端实现一个与前端 `formula-eval` **语义对齐**的安全求值器（同一套操作符/函数白名单），`DocSaver` 保存前对 `validationRules` 逐条在**保存后的整单 DataSet**上求值，任一 `severity:error` 不通过则**回滚 + 返回 `message`**。
- **契约一致**：前后端共用同一份 `validationRules`（元数据驱动），表达式语法一致——前端即时反馈体验、后端最终把关正确性，**双端一套规则不重复定义**。
- **性能**：规则在内存 DataSet 上求值（数据已在手，无需回查库），代价极低；仅在保存点跑一次。

> 若短期不想实现后端求值器，**至少**对最关键的少数规则（借贷平衡等）写死后端硬校验兜底——但通用做法是补齐求值器，与前端对齐。

### 14.3 【正确性】并发控制（乐观锁 / 悲观锁，防覆盖）

**问题**：两人同时打开同一张单据编辑，后保存者会**静默覆盖**前者——§6.4 目前无并发保护。经核对，后端**已具备** `SELECT ... FOR UPDATE` 悲观锁能力（`cmx-database/README.md:334` 有范例）。

**方案（两级，按单据设置选）**：
- **乐观锁（默认，联机编辑）**：主表加 `row_version INT`（或复用 `update_time`）；`merge` 模式 `UPDATE ... WHERE id=$1 AND row_version=$expected`，`rows_affected=0` ⇒ 版本冲突，回滚并返回「单据已被他人修改，请刷新」。装载时把 `row_version` 一并下发，保存时带回。
- **悲观锁（强占用场景）**：编辑前 `POST /api/doc/lock { rootId }` → 后端对根行 `SELECT ... FOR UPDATE`（或写一张 `cmx_doc_lock` 记录 actor+过期时间），他人只读；`replace` 整树覆盖模式（§6.4）**建议强制悲观锁**，避免整树冲掉他人改动。
- 与版本化（§6A）协同：冲突检测失败不产生新版本；成功保存才 `rev_no+1`。

### 14.4 【正确性】软删除 vs 物理删除（`delete_flag`）

**问题**：base 字段集已有 `delete_flag`（逻辑删除，remark 明确"逻辑删除字段"）。但 §6.4 的 `DELETE`/`replace` 写的是**物理 DELETE**——与系统的逻辑删除约定冲突，且物理删会破坏版本化/审计追溯（删了就查不到了）。

**方案**：
- **单据设置 `deletePolicy`**（`docMeta`）：`soft`（默认，`UPDATE SET delete_flag=1`）| `hard`（物理删）。
- **软删语义**：`merge.deleted`/`replace` 的删除改为 `delete_flag=1`；装载 `DocLoader` 一律带 `WHERE delete_flag=0`（或 `IS NULL`）。删除也进版本历史（`op=delete`），可追溯、可恢复。
- **`replace` 模式**：软删时不是物理清空子树，而是把「不在 snapshot 里的旧行」标 `delete_flag=1`——保留历史。
- **护栏叠加**：与 §12 的「DELETE 必带 WHERE、rootId 圈定」共同保证不误删。

### 14.5 【设计约定】单号生成（`doc_no` 谁生成、防重、按段流水）

**问题**：base 有 `doc_no`（单据编号）字段，但**无生成规则**——谁在何时生成？并发下如何防重号？按公司/期间/单据类型分段流水？主链路未提。

**方案**：
- **后端生成（保存时）**：单号由后端在保存事务内生成（前端只占位），避免临时号泄漏、避免前端并发重号。
- **规则元数据化**：`docMeta.numbering { field:"doc_no", pattern:"PZ-{entity}-{yyyymm}-{seq:6}", scope:["entity_id","fiscal_period_id"], resetBy:"month" }`——声明式定义前缀/变量/流水位数/分段维度/重置周期。
- **并发防重**：流水号从 DB 序列或一张 `cmx_doc_seq(scope_key, next_val)` 表 `UPDATE ... RETURNING`（原子自增）取，`scope_key` = 分段维度值拼接；单号列建唯一索引兜底。
- 生成时机与 §14.1 状态流转协同：常见「保存草稿用临时号，审核/过账时才分配正式号」——由 `numbering.assignOn:"save"|"transition:audit"` 控制。

### 14.6 【设计约定】数据权限（行级 who 能看/改哪些单据）

**问题**：§9 API 只按 `db_id` 选库，没提**行级数据权限**——A 公司的人不能看 B 公司的凭证。经核对，后端**已有** `CmxSvrContext`/`SVRContext`（含 `tenant_id`、`has_permission/require_permission`）和权限中间件。

**方案**：
- **装载注入范围过滤**：`DocLoader` 从 `CmxSvrContext` 取当前用户的数据范围（组织/公司/租户），自动给根层 SQL 追加 `WHERE entity_id = ANY($allowedOrgs)`（数据范围由 IAM 规则解析）。**不信前端传的过滤**——范围在后端强制注入。
- **操作权限**：保存/删除/状态流转前 `ctx.require_permission("gl:voucher:edit")`（`init_dml.sql` 里已有 `gl:voucher:add/audit/post/delete` 等权限点）。
- **审计带 actor**：§6A 的版本/审计记录的 `actor_id/actor_name` 从 `CmxSvrContext` 取（不信前端传），保证追溯真实。
- **多租户隔离**：`app_id`/`tenant_id` 作为所有单据表的隐式过滤维度（现有表已普遍带 `app_id`），装载/回存自动带上。

### 14.7 【设计约定】附件与大字段（`attach_count` 背后的附件本体）

**问题**：base 有 `attach_count`（附件张数），但**附件本体**（发票扫描件、合同 PDF）如何随单据装载/回存？直接进 `DataValue::Binary`（BYTEA）会让单据数据包爆炸，违背 §8 小包。

**方案**：
- **附件与单据数据解耦**：单据行只存**附件引用**（`file_id`/`storage_key`，指向对象存储——系统已有 `cmx-storage` crate），不存二进制本体。
- **装载**：单据包只带 `file_id` + 元信息（名/大小/类型），附件本体**按需懒加载**（用户点开才 `GET /api/storage/{file_id}` 拉），保持单据包小。
- **回存**：附件先独立上传（`cmx-storage` 已有上传端点）拿 `file_id`，再随单据行保存该引用；单据删除时附件按策略级联（软删只解引用、hard 删可清理孤儿附件）。

### 14.8 【设计约定】统一错误契约 & 部分失败语义

**问题**：装载/回存/校验/锁冲突各种失败，前端需要**可编程区分**（是校验错？锁冲突？无权限？），而不是笼统 500。现有 `ApiResp{code,msg}` 是基础，但需约定单据域的错误码。

**方案**：
- **单据错误码族**（`ApiResp.code` 非 0 时）：`DOC_VALIDATION_FAILED`（带 `details:[{layer,rowId,field,message}]`）、`DOC_STATE_LOCKED`（不可编辑态）、`DOC_VERSION_CONFLICT`（乐观锁）、`DOC_PERMISSION_DENIED`、`DOC_LOCK_HELD`（被他人锁）。前端据此精准提示/高亮出错单元格。
- **保存原子性**：单据保存是**全或无**（单事务），不存在"头存了、明细没存"的部分失败——任一层任一校验失败整体回滚。
- **批量装载的部分失败**（如首页要拉多张单据）：借鉴现成 `get_definitions_batch` 的 `{items, errors}` 模式——成功的照常返回、失败的进 `errors[]`，不因一张坏单整批失败。

## 15. 配置驱动的可扩展机制：用配置适配个性化，而非改代码

§14 的单号、校验、状态、权限……在真实 ERP 里**千变万化**：A 单据借贷平衡、B 单据要调税务系统核验；甲公司单号按年重置、乙公司按月分段。**若每种个性化都改代码，平台会被业务淹没。** 本节确立贯穿全方案的**架构原则**：所有可变业务规则**由元数据配置驱动 + 命名扩展点承接**，新增/变更单据行为 = 改配置（多数）或注册一个命名扩展（少数），**不动平台代码**。

### 15.0 核心张力与解法：三层表达力阶梯

纯配置有个陷阱：**声明式配置能表达 80% 的规则，但剩下 20% 真正复杂的逻辑（调外部系统、多表事务、复杂算法）配置表达不了**——硬塞会把配置退化成"图灵完备的丑陋 DSL"。正确解法是**分层**：按规则复杂度选表达层，**每层都是配置声明，只是指向不同的执行器**。

| 层 | 表达方式 | 覆盖 | 举例 | 谁执行 |
|---|---|---|---|---|
| **T1 声明式表达式** | `formula-eval` 表达式字符串 | ~80% | `"debit == credit"` | 内置求值器（前后端各一，语义对齐） |
| **T2 命名策略 + 参数** | `{ strategy, params }` | ~15% | `{strategy:"period_open", params:{dict:"fiscal_period"}}` | 平台内置策略库（参数化） |
| **T3 扩展点 → 服务/插件** | `{ handler:"service:key" }` | ~5% | `{handler:"service:gl.validateTax"}` | 服务编排 / WASM 插件（业务方实现） |

- **T1** 覆盖绝大多数「字段间算术/比较/逻辑」规则——纯配置字符串，零代码。前端 `formula-eval.js` 已支持 40+ 函数（`ROUND/IF/SUM/CONCAT/DATEADD/COALESCE...`），后端补一个**语义对齐的孪生求值器**即可（§14.2）。
- **T2** 覆盖「有固定模式但需参数化」的规则——平台预置一批**命名策略**（如"期间开闭校验""按段流水号"），配置只填策略名 + 参数。加新策略是平台演进（低频），但用策略是配置（高频）。
- **T3** 覆盖「真正复杂、每家不同」的逻辑——配置里写一个 `handler` 指向**命名扩展点**（服务编排 `service_key` 或插件函数），业务方在扩展里写任意逻辑。**平台只认 handler 名，不关心里面干什么**。

> 关键：**三层都是"配置里声明"**，区别只是 T1 声明表达式、T2 声明策略名、T3 声明 handler 名。业务复杂度上升时从 T1→T2→T3 平滑升级，**平台核心代码不变**。

### 15.1 落点已就绪：命名扩展点注册表（`ServiceRegistry`）

T3 的"命名扩展点"**不需凭空造**——后端已有现成宿主（§核对）：

- **`GlobalServiceRegistry` / `ServiceRegistry`**（`cmx-service`）：`service_key → ServiceDefinition`、`plugin_id → Vec<service_key>` 缓存——**这就是扩展点注册表**。
- **Orchestrator 服务编排**：`POST /api/service/execute { service_key, input }` 按 key 找到编排 Flow（JSON 定义的节点图）执行。
- **WASM 插件**：`{ plugin_id, function_name, input }` 调用业务方沙箱逻辑。

所以 T3 的 `handler:"service:gl.validateTax"` 落地 = 解析 `service:` 前缀 → 查 `ServiceRegistry` → `Orchestrator.execute("gl.validateTax", { doc, ctx })`。`handler:"plugin:acme.numbering"` 则走插件调用。**平台侧只需一个"handler 解析分发器"**，把 `service:`/`plugin:`/`formula:`/`builtin:` 前缀路由到对应执行器。

### 15.2 统一规则引擎：一套 `RuleSpec`，服务所有横切点

单号/校验/状态/默认值/权限……表面各异，**抽象后都是"在某时机、按某条件、执行某动作"**。用一个统一的 `RuleSpec` 配置结构 + 一个 `RuleEngine` 分发器承接全部：

```jsonc
// 统一规则规格：单号/校验/状态/默认值/联动 全部复用
{
  "id": "voucher_balance_check",
  "on": "before_save",              // 时机：before_save/after_save/before_transition/on_field_change/on_load...
  "when": "doc.total_dr > 0",       // 条件（T1 表达式，可选；真则执行）
  "do": {                           // 动作：三层表达力择一
    "tier": "formula",              // "formula"(T1) | "strategy"(T2) | "handler"(T3)
    "expr": "sum(lines.local_dr) == sum(lines.local_cr)",   // T1
    "message": "凭证本位币借贷必须平衡",
    "severity": "error"             // error 阻断 / warn 提示
  },
  "scope": "cv_header"              // 作用层（可选）
}
```

- **`on`**（时机）+ **`when`**（条件）+ **`do`**（动作）三段式，是所有横切规则的公共骨架。
- `do.tier` 选表达层：`formula` 内联表达式、`strategy` 命名策略+params、`handler` 扩展点 key。
- **`RuleEngine`**：在各生命周期钩子点（load/save/transition/field-change）收集命中 `on` 的规则，按 `when` 过滤，逐条 `do` 分发到 T1/T2/T3 执行器。**这一个引擎 + 一个分发器**，就把 §14 所有可变点统一了——加规则 = 加一段 `RuleSpec` 配置。

### 15.3 各横切点如何落到这套机制（配置示例）

#### 单号生成（§14.5）→ T2 命名策略为主，T3 兜底

```jsonc
"numbering": {
  "field": "doc_no", "on": "transition:audit",   // 审核时分配正式号
  "do": { "tier":"strategy", "strategy":"segmented_sequence",
          "params": { "pattern":"PZ-{entity}-{yyyymm}-{seq:6}",
                      "scope":["entity_id","fiscal_period_id"], "resetBy":"month" } }
}
// 特殊编码（如需调外部编码中心）→ 换一行：
"do": { "tier":"handler", "handler":"service:acme.docNumber" }
```
平台预置 `segmented_sequence`/`daily_sequence`/`uuid` 等命名策略（T2）；遇到平台没有的编码逻辑，配置改指 `handler`（T3），业务方实现，**平台不改**。

#### 数据校验（§14.2）→ T1 表达式为主，T3 接外部系统

```jsonc
"validationRules": [
  { "on":"before_save", "do":{ "tier":"formula", "expr":"total_dr==total_cr", "message":"借贷不平", "severity":"error" } },
  { "on":"before_save", "do":{ "tier":"strategy", "strategy":"period_open", "params":{"periodField":"fiscal_period_id"}, "message":"期间未打开" } },
  { "on":"before_post", "do":{ "tier":"handler", "handler":"service:gl.taxValidate" } }   // 调税务系统
]
```
借贷平衡（T1 纯表达式）、期间开闭（T2 平台策略）、税务核验（T3 外部服务）——**三种复杂度同一套配置结构**，各选其层。

#### 状态机（§14.1）→ 状态/流转/守卫全配置

```jsonc
"statusFlow": {
  "stateField": "doc_status",
  "states": [ {"code":"draft","editable":true}, {"code":"posted","editable":false} ],
  "transitions": [
    { "action":"post", "from":"audited", "to":"posted",
      "guard": [ { "tier":"formula", "expr":"total_dr==total_cr" },          // T1 条件守卫
                 { "tier":"handler", "handler":"service:gl.checkFundsPost" } ],// T3 复杂守卫
      "permission": "gl:voucher:post",                                        // 权限点（§14.6）
      "effects": [ { "tier":"handler", "handler":"service:gl.postToLedger" } ]// 过账副作用（记账）
    }
  ]
}
```
状态、可编辑性、流转条件、权限、副作用——**全声明式**。加一个"冲销"动作 = 加一段 `transitions` 配置；冲销逻辑复杂 = `effects` 指 handler。

#### 默认值 / 字段联动 / 数据权限 → 同一 `RuleSpec`

```jsonc
{ "on":"on_load", "scope":"cv_header",
  "do":{ "tier":"strategy", "strategy":"default_from_context", "params":{"field":"entity_id","from":"ctx.currentOrg"} } }
{ "on":"on_field_change", "when":"field=='gl_account_id'",
  "do":{ "tier":"handler", "handler":"service:gl.loadAccountDefaults" } }
{ "on":"on_load", "do":{ "tier":"strategy", "strategy":"data_scope", "params":{"field":"entity_id","scopeType":"org"} } }  // 数据权限注入(§14.6)
```

### 15.4 配置的载体与治理

- **配置落点**：这些 `RuleSpec`/`numbering`/`statusFlow`/`validationRules` 全部进**单据定义元数据**（`docMeta` 及各层），复用 §3.6 的 `definitions::store` 读写、§3.7 缓存、§3.8 强类型投影——**与单据定义同源、同版本、同部署**。改规则走现成的定义保存链路（`POST /api/definitions/config`），无需发版。
- **设计器可视化**：规则是结构化 JSON → 可在单据设计器里做**可视化编辑**（下拉选 `on`、表达式编辑器写 `when/expr`、策略选择器选 `strategy`、扩展点选择器从 `ServiceRegistry` 列出可用 `service_key`）。业务顾问配规则，不写代码。
- **版本化协同**：规则是定义的一部分，随定义版本走（§6A 是数据版本，这里是**定义版本**）；某单据"改了校验规则"可追溯到定义版本。
- **扩展点契约**：T3 handler 有统一 I/O 契约——入参 `{ doc: DataSet快照, row?, ctx: SvrContext, params }`，出参 `{ ok, message?, patch?, value? }`（校验返 ok/message、单号返 value、默认值返 patch）。业务方按契约实现，平台按契约调用，**双方解耦**。

### 15.5 前后端一致：同一份配置，两端执行

- **T1 表达式**：前端 `formula-eval` 即时校验/联动（体验），后端孪生求值器最终把关（正确性）——**同一份 `expr` 字符串**，前后端各跑一遍，规则不重复定义。
- **T2 策略 / T3 handler**：默认后端权威执行（涉及库/外部系统）；纯 UI 类（如前端默认值填充）可前端也接一份策略实现。**配置声明"什么规则"，前后端各自决定"在我这端跑不跑"**。
- 这直接兑现 §14.2 的"双端一套规则"，并推广到所有横切点。

### 15.6 为什么这套满足「通用 + 可扩展 + 不牺牲性能」

- **通用**：一个 `RuleEngine` + 一套 `RuleSpec` 服务所有横切点（单号/校验/状态/默认值/联动/权限），不为每种需求写专用代码。
- **可扩展**：三层阶梯让简单规则纯配置（T1/T2）、复杂逻辑挂扩展点（T3），**复杂度增长时平台核心零改动**；扩展点复用现成 `ServiceRegistry`/编排/插件，新扩展 = 注册一个 `service_key`。
- **个性化即配置**：不同单据/不同租户/不同场景 = 不同的 `RuleSpec` 集合，随定义元数据走，改配置不发版。
- **不牺牲性能**：T1/T2 在内存 DataSet 上求值（数据已在手，§7 零拷贝复用），代价极低；仅 T3 外部调用有网络开销，且只在真正需要的少数规则上用；规则集随定义缓存（§3.7），不重复解析。

### 15.7 落地优先级

| 阶段 | 内容 |
|---|---|
| **先做** | `RuleEngine` 骨架 + T1 求值器（后端孪生 `formula-eval`）+ `RuleSpec` 的 `on/when/do` 三段式；把 §14.2 校验、§14.1 状态守卫先跑起来 |
| 紧随 | T2 命名策略库（`segmented_sequence`/`period_open`/`data_scope`/`default_from_context` 等平台内置）+ 设计器可视化编辑 |
| 按需 | T3 handler 分发器（`service:`/`plugin:` 前缀路由到 `ServiceRegistry`/编排/插件）+ 扩展点 I/O 契约 |

> **一句话**：把 §14 的每个"可变点"都改造成"`RuleSpec` 配置 + 三层执行器"，平台提供**引擎与内置策略**，业务提供**配置与少量扩展**——个性化需求 99% 落在配置，1% 落在命名扩展，**平台代码保持稳定**。这才是能长期适配无穷业务变化的架构。

## 16. 运行形态决策：Rust 原生 vs 后端 WASM

一个常被问到的架构问题：这套方案是**用 Rust 原生运行**，还是**编译成后端 WASM 运行**？结论不是二选一，而是**分层**——**平台引擎必须 Rust 原生，WASM 只承接 §15 的 T3 业务扩展点**。这个结论不是偏好，是被方案的两条硬约束（零拷贝、小包）和代码库的真实边界共同锁定的。

### 16.0 结论先行

> **平台引擎（装载/回存/DDL/版本/校验求值器/内置策略）= Rust 原生；业务个性化扩展（§15 T3 的 handler）= WASM 插件。**
> 让每层跑在最适合它的运行时：核心引擎要极致性能 + 事务/内存直接访问 → 原生；业务扩展要隔离 + 热插拔、且不在热路径 → WASM。

### 16.1 为什么主体必须 Rust 原生（而非编译成 WASM）

#### 理由一：方案依赖的核心能力全部是 host 原生 crate

经核对，`DocLoader`/`DocSaver` 要用的每一样东西都在宿主侧原生运行，**没有一个是 wasm 目标**：

| 能力 | 所在 crate | 形态 |
|---|---|---|
| 事务 `begin/commit`、连接池、`FOR UPDATE` | `cmx-database` | host 原生 |
| DDL 引擎、`create_or_upgrade_table` | `cmx-metadata` | host 原生 |
| `DataSet`/`Arc<Schema>`/`ColumnarCodec` | `cmx-core` | host 原生 |
| `query_sql → DataSet`、`convert_postgres_rows` | `cmx-database` | host 原生 |

WASM 沙箱**够不到这些**——它没有数据库连接、没有文件系统（字典 JSON 文件在 `data/dict/entries`）、拿不到 `Arc<Schema>` 的共享引用。编译成 WASM 等于自断双臂。

#### 理由二：WASM 边界直接违背方案的两条硬约束（最致命）

WASM 插件访问 DB 的唯一方式是 host_call，每次调用都强制序列化 + 反序列化 + 内存拷贝（真实代码 `host_calls.rs`）：

```rust
let bytes = rmp_serde::to_vec(&request)?;       // 序列化(拷贝)
// ... 跨线性内存边界进 host ...
let response = rmp_serde::from_slice(&result)?; // 反序列化(拷贝)
```

- **违背零拷贝（§7）**：方案花大力气做 `Arc<Schema>` 共享 + 借用式序列化，而 WASM 边界**强制每次进出全量序列化 + 内存拷贝**——`Arc` 跨不过线性内存边界，零拷贝设计当场作废。
- **违背小包 / 大单据（§8/§12）**：插件/gRPC 消息有 **4MB 上限**（`cmx_plugin_data.proto` 明确注"大包建议 HTTP 模式"）。方案要支持大单据 + 版本快照，快到边界就爆。

#### 理由三：WASM 无法真正参与 host 事务——破坏 §6.4/§6A 原子性

`txn_id` 只是个字符串跨边界传（`wasm_types/database.rs`），事务实体 `sqlx::Transaction` 在 host 侧。方案的核心正确性保证——"主 + 各层明细 + 版本快照在**同一事务**内全或无"（§6.4、§6A、§14）——依赖直接持有事务句柄。WASM 侧拿不到，只能靠字符串来回传，跨多次 host_call 有一致性风险，且 §14.3 的 `FOR UPDATE` 悲观锁跨不过沙箱。

#### 理由四：热路径上多一层沙箱纯亏

装载/回存是高频热路径。WASM 化平白加上：线性内存拷贝、序列化开销、沙箱调用开销、wasmtime（`39.0.1`）的 JIT/解释开销。方案追求的性能全被这层吃掉。

### 16.2 WASM 该用在哪——正好是 §15 的 T3 扩展点

现有架构本就是**「host 原生引擎 + WASM 业务插件」**分层（`cmx-plugin-demo` 是 `cdylib`/wasm，但 `cmx-service` 编排、`cmx-database` 数据在 host）。这个分层**恰好就是 §15 三层阶梯的物理落地**：

| §15 层 | 运行形态 | 理由 |
|---|---|---|
| **T1 表达式求值** | **host 原生**（后端孪生 `formula-eval`） | 高频、在内存 DataSet 上跑，必须零开销 |
| **T2 命名策略** | **host 原生**（平台内置策略库） | 平台代码，原生最快 |
| **T3 业务扩展点** | **WASM 插件** ✅ | 每家不同的个性化逻辑，需沙箱隔离、热插拔、独立部署 |

**WASM 的价值在 T3 完美体现**：业务方写的 `service:gl.taxValidate`（调税务系统）、`service:acme.docNumber`（特殊编码）这类**个性化逻辑**，正需要 WASM 的：

- **沙箱安全**：第三方/租户代码不能碰核心；
- **热插拔**：不重启、不发版就能上新业务规则（呼应 §15"改配置不发版"）；
- **多租户隔离**：每家的定制逻辑互不干扰。

而它们**调用频率低**（§15 说 T3 只覆盖 ~5% 规则）、**单次数据量小**（传一行 + 校验结果，远小于 4MB），**WASM 边界代价可接受**。用 extism（`1.4`）+ 现成 `db_query`/`db_execute` host_call 即可。

### 16.3 边界速查表

| 判据 | Rust 原生 | 后端 WASM |
|---|---|---|
| 直接持有 `sqlx::Transaction` / 连接池 | ✅ | ❌（只能传 `txn_id` 字符串） |
| `Arc<Schema>` 零拷贝共享 | ✅ | ❌（跨边界必拷贝） |
| 大数据量（>4MB 单据/快照） | ✅ | ❌（消息上限） |
| `FOR UPDATE` 悲观锁 / 直接文件访问 | ✅ | ❌ |
| 沙箱隔离第三方/租户代码 | ❌ | ✅ |
| 不发版热插拔业务逻辑 | ❌（要重编译） | ✅ |
| 热路径性能（装载/回存） | ✅ 极致 | ❌ 多层开销 |
| 适配对象 | 平台引擎 + T1/T2 | 业务个性化 T3 |

### 16.4 落地形态

- **`DocLoader`/`DocSaver`/`ColumnarCodec`/`RuleEngine`/T1 求值器/T2 策略库** → 作为 **host 原生服务**落进 `cmx-biz`/`cmx-service`，直接用 `cmx-database`/`cmx-metadata`/`cmx-core`。
- **T3 handler** → 通过现成 `ServiceRegistry` + 服务编排 / extism 插件调用链路触达；I/O 走 §15.4 的统一契约（入 `{doc快照, row?, ctx, params}`、出 `{ok, message?, patch?, value?}`），数据量天然小、在边界代价可接受的范围内。
- **迁移含义**：若历史上有把这类数据处理放进 WASM 的尝试，应**上移回 host 原生**（与 `docs/node-to-rust-migration-cutover.md` 的原生化方向一致）；WASM 保留给真正需要隔离/热插拔的业务扩展。

> **一句话**：不是"原生还是 WASM"，而是"**引擎原生、扩展 WASM**"——核心走原生拿性能与事务/零拷贝，个性化走 WASM 拿隔离与热插拔，两者用 §15 的 `handler` 契约衔接。
