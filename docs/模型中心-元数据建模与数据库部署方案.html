CMX Platform · 方案设计

模型中心：元数据建模与数据库部署方案

将 CMXPortalManager 的五项元数据能力统一收编为「模型中心」，支持在模型定义完成后向指定数据库执行创建 / 升级，并在元数据版本变化时再次升级到目标库。
范围：方案设计（不改代码） 日期：2026-06-28 核心结论：建表引擎已就绪，主要工作量在「编译器 + 编排 + UI」

01背景与目标

CMXPortalManager 当前以「定义中心」名义提供五项元数据维护功能。它们目前只是 JSON 设计态编辑器——能定义，但定义完无法落到任何真实数据库。本方案将这五项功能归并为模型中心，并补齐「定义 → 应用到数据库 → 版本升级」的闭环。

归入模型中心的五项功能

序号功能本质是否产生物理表
①字典基础元数据 BASE-DCT公共字段集模板（被字典表复用）否（仅被合并）
②单据基础元数据 BASE-DOC公共字段集模板（被单据表复用）否（仅被合并）
③数据字典定义 DCT一组字典表 dictionaryTables[]，每表含 tableName+fields[]是
④业务单据定义 DOC多层单据表 voucherTables[]（L1批/L2头/L3行/L4辅助）是
⑤弹性组合管理 CP场景化字段/列规则（运行时驱动 UI），引用 ③④否（运行态配置）
目标（用户原话拆解）
  1. 归并：五项功能统一进入「模型中心」，形成一致的建模工作台。
  2. 应用/创建：模型定义完成后，可创建到某个具体数据库（生成物理表 + 种子数据）。
  3. 升级：当元数据版本变化时，可再次升级到指定数据库（增量 ALTER，不丢数据）。
  4. 以上「应用 / 创建 / 升级」全部属于模型中心的职责。

02现状盘点（基于代码勘察）

本节区分「已有可复用资产」与「能力差距」。结论先行：最难的建表/升级引擎已经存在且经过插件安装链路验证，本方案绝大部分是把现成能力接起来，而非从零造轮子。

2.1 前端五大功能现状

已具备
  • 五项功能均已有成熟编辑器：portal-definition-manager.js（①②③④）与 portal-flexible-combination-manager.js（⑤）。
  • DCT/DOC 定义中每张表已携带 tableName 与 fields[]，字段含 dataType / fieldLength / nullable / intDigits / decimalDigits / caption 等——这正是建表所需的全部信息。
  • DCT/DOC 已有「SQL schema 视图」标签页（dct-def-schema / doc-def-schema），具备展示 DDL 的位置。
差距
  • 全工程 grep "模型中心" = 0 命中：模型中心尚不存在。
  • 所有「应用 / apply」按钮都只是表单/JSON 提交到内存，无任何「落库 / 建表 / 升级」语义。
  • 无目标数据库选择、无版本对比、无部署历史。
  • 前端目前仍打到 Node 服务（/api/definitions/* 等，vite 代理到 127.0.0.1:8080），尚未接入 Rust 容器的 /api/portal/*。

2.3 能力差距：只缺三块

缺口 A · 编译器

Portal 的 DCT/DOC 定义（dictionaryTables[]/voucherTables[] + 字段集引用）尚无转换为 cmx-core TableDefine 的代码。这是必须新写的核心。

缺口 B · 编排与版本

把「选库 → 预览 DDL → 执行 → 记版本 → 再升级」串成一个对外 HTTP 服务（插件链路是内部的，需提炼为模型中心的部署服务）。

缺口 C · 模型中心 UI

新的导航分区「模型中心」，统一五项编辑器，并新增「目标库选择 / DDL 预览 / 部署 / 版本历史」交互。

03核心概念模型

统一术语，避免「定义/版本/目标库/部署」混淆。模型中心围绕四个名词运转。

模型 Model

一个可建模的元数据单元。三类「物理模型」会产生表：
• 字典模型（DCT，1 个定义 = N 张字典表）
• 单据模型（DOC，1 个定义 = 多层单据表）
其余两类是共享资产（BASE-DCT/BASE-DOC 字段集模板）与运行态配置（弹性组合 CP，不建表）。

模型版本 ModelVersion

模型定义在某一时刻的不可变快照。复用既有 moduleMeta.version（整数，默认 1）。每次发布生成一个快照（含编译后的 TableDefine[] 与种子数据指纹），作为「升级」的对比基线。

目标库 TargetDatabase

由 db_id 唯一标识的物理库（DbRegistry 已注册，dev.toml [[databases]] 配置，可运行期新增）。一个模型版本可部署到多个目标库（开发/测试/生产）。

部署 Deployment

「把某模型版本应用到某目标库」的一次动作及其结果。落到既有台账 cmx_meta_table_define(_version)：记录 db_id × table × version × ddl_status。据此判定下次是创建还是升级。

04总体架构

分层清晰：前端模型中心 → 模型服务（编译/版本/部署编排）→ 既有 cmx-metadata 引擎 → 目标库。新增代码集中在「编译 + 编排 + UI」，引擎层尽量零改动。

设计原则
  • 引擎不重写：编译产物严格对齐 cmx-core TableDefine，下游直接复用 executor / diff / seed / 台账。
  • 对齐插件先例：部署编排照搬 cmx-plugin/service/utils.rs 的「锁 + 事务 + 台账」骨架，仅把数据来源从「插件 JSON」换成「Portal 定义编译产物」。
  • 前端复用编辑器：五项编辑器组件不动其内核，只在外层包一个「模型中心」工作台与部署交互。
  • 幂等优先：建表用 create-or-upgrade、种子用 UPSERT，重复部署安全。

注 · TINYINT/INT 的精度细化
cmx-core FieldType::Int 默认映射 BIGINT。若需保留 TINYINT(1)→SMALLINT、INT(6)→INTEGER 的语义，编译器可在 ColumnDefine.db_type 写入精确类型字符串，引擎已支持 prefer_db_type 模式（round-trip）直接采用 db_type。这是一个明确的实现开关，无需改引擎。

5.2 字段集展开（关键合并逻辑）

DCT/DOC 表的完整列 = 该表自有 fields[] + 所引用的公共字段集（来自 BASE-DCT/BASE-DOC）。编译器必须先做字段集展开。

// 真实样例：cf_comp_unit 字典表引用了多个公共字段集 { "dictMeta": { "tableName": "cf_comp_unit", "idField": "id", "codeField": "code" }, "fields": [ /* 表自有业务字段：company_id, vat_reg_no … */ ], "baseFieldSet": "dictionaryCommonFields", // ← 含 id(PK)/code/name/sort_no/status "auditFieldSet": "dictionaryAuditFields", // ← create_by/create_time/update_* "effectiveFieldSet": "dictionaryEffectiveFields", // ← effective_from/to "uniqueKeys": [["code"]] // ← 唯一索引 }
1
解析引用：读取表上的 baseFieldSet / auditFieldSet / effectiveFieldSet / disableFieldSet / hierarchyFieldSet / documentFieldSets[] / includeFieldSets[] 等键，得到字段集名列表。
2
载入模板：从对应 BASE-DCT/BASE-DOC 定义（baseDctMetaRef.file 指向，如 base_dct_meta_v1.json）的 fieldSets{} 取出字段数组。
3
合并去重：公共字段集字段 + 表自有 fields[]，按列名去重（自有优先覆盖）。
4
推定主键：公共字段集中的 id 列（dictionaryCommonFields 提供）→ primary_keys=["id"]；DOC 多层表用 documentLevelFields 的层级主键语义。
5
生成索引：uniqueKeys[] → IndexDefine{kind:Unique}；refDict 外键列 → 普通索引。
6
产出：每张 DCT/DOC 表 → 一个 TableDefine{ table_name, columns, primary_keys, indexes, version, i18n, schema, comment }。
复用而非另造
Node 侧「SQL schema 视图」已实现过一版字段集合并逻辑（前端 portal-definition-manager.js 的 schema 标签页）。编译器是把这套合并规则权威化、后端化，作为唯一可信源（前端预览也调它），避免前后端两套实现漂移。

5.3 i18n 与索引

  • i18n 列：字段若带 i18n:true，编译时置 ColumnDefine.i18n=true 且 TableDefine.i18n=true；引擎 derive_i18n_table_define() 自动派生 {table}_i18n 伴生表（ref_id + locale 复合主键），无需编译器额外处理。
  • 注释：caption.zh_CN → 列注释、dictName/tableAlias → 表注释，建表时由引擎输出 COMMENT ON。
  • DOC 多层：voucherTables[] 的 L1/L2/L3/L4 各编译为独立 TableDefine；层间父子关系（upper_id/line_no 来自 documentLevelFields）作为列与索引体现。

06目标数据库注册

"应用到某个具体数据库" = 选定一个 db_id。该机制已存在，模型中心只需在其上提供选择与（可选）运行期登记。

已有：静态配置

# cmx-container/dev.toml [[databases]] db_id = "primary" db_type = "postgres" db_url = "postgresql://…@host:5432/cmx" default = true

启动即注册进 DbRegistry；执行器以 db_id 取连接池。

已有：运行期登记

DatabaseManager::register_data_source(DbConfig) 支持运行时注册新库，list_data_sources() 列出全部 db_id。

→ 模型中心可在「目标库」面板调用它，让用户填写连接串临时挂载一个部署目标，而不必改 toml 重启。

模型中心要补的薄层
  • GET /api/portal/model/targets —— 列出可部署目标库（封装 list_data_sources() + 每库连通性探测）。
  • （可选）POST /api/portal/model/targets —— 运行期登记新目标库（封装 register_data_source），连接串加密保存。
  • 权限：部署到非默认库属高危操作，必须有独立权限位（见 §13）。

07模型版本与快照

"版本变化时再次升级" 的前提是：每次发布都留下一个可对比的不可变快照。复用既有 version 字段与既有台账，不新造存储。

1
编辑态：用户在五编辑器里改定义，存的是「草稿」（沿用现有 /definitions/config 存储）。moduleMeta.version 标识当前版本号。
2
发布快照：点「发布版本 v=N」时，后端编译当前定义为 TableDefine[]，连同种子数据指纹一起冻结为一个 ModelVersion 记录。
3
部署到库：把某个已发布快照应用到目标库。台账 cmx_meta_table_define_version.metadata 存的正是该库当前生效的 TableDefine JSON 与 version。
4
升级：发布 v=N+1 后再次部署到同一库 —— 引擎 upgrade_table() 反查该库现状（或读台账里 v=N 的快照）与 v=N+1 目标做 diff，仅执行增量 DDL。
两条 diff 基线，二选一/互补
  • 库现状基线（引擎默认）：upgrade_table() 实时反查 information_schema。最真实，能纠正手工漂移。
  • 台账快照基线：读 cmx_meta_table_define_version 里上次部署的 TableDefine。可在执行前做「版本 N → N+1」的纯逻辑 diff 预览（无需连库），用于发布前评审。
建议：预览用台账快照（快、可离线评审），执行用库现状（安全、防漂移）。
台账字段来源用途
db_id部署目标区分「同模型部署到多库」。
table_name + version编译产物定位「某库某表当前版本」。
metadata (JSONB)serde_json(TableDefine)快照本体，作 diff 基线。
ddl_status部署编排pending→executing→completed/failed，驱动 UI 状态灯。
domain/app/module_codemoduleMeta按 DAM 维度归类与过滤。

08部署编排（创建 / 升级）

把插件安装链路（内部）提炼成模型中心的对外部署服务。骨架不变：锁 → 编译 → (预览) → 执行 → 种子 → 写台账，全程一个事务。

1
选择：用户选定「模型版本 × 目标库 db_id」与模式（create_or_upgrade 默认 / 强制 create / 仅 upgrade）。
2
编译：模型服务调用编译器 → TableDefine[]（含 i18n 派生、索引）。
3
预览 dry-run：对每张表用台账快照或库现状做 DdlDiff，只生成不执行 DDL 文本返回前端评审；高亮「将被忽略的 DROP」。
4
加锁：照搬 execute_ddl_with_lock，锁键 model:ddl:{model_id}:{db_id}，串行化同库部署。
5
事务执行：开事务 → create_or_upgrade_table() 逐表 → PgSeedDataExecutor 种子（UPSERT）→ 提交。
6
写台账：save_*_table_metadata 更新 cmx_meta_table_define(_version)：version、metadata 快照、ddl_status=completed。
7
回执：返回每表 created/altered/skipped、生成的 DDL、种子 success/failed 计数、耗时；失败则整事务回滚并记 ddl_status=failed。
天然幂等
  • 表：create-or-upgrade，重复部署=空 diff。
  • 种子：ON CONFLICT DO UPDATE。
  • 锁：try_lock 非阻塞，避免并发双写。
破坏性变更护栏
  • 引擎默认不执行 DROP TABLE/COLUMN，仅在预览中列为「需人工确认」。
  • 类型收窄（如 VARCHAR(64)→(32)）在预览标红警告。
  • 生产库部署要求二次确认 + 权限位。

09后端 API 设计（新增路由）

在 cmx-portal 既有 /api/portal/* 体系下，新增 model 子命名空间。沿用既有 ApiResp{code,msg,data} 信封。定义/字典/弹性组合的 CRUD 仍走既有路由，model 只承担「编译/版本/部署/目标库」。

方法 / 路径作用复用

  • SQL 预览标签：把现有 *-def-schema 视图升级为「调后端编译器 + diff」的真实 DDL 预览（当前是前端拼的，改为权威源）。

13风险与对策

风险影响对策
破坏性变更误执行（DROP 列/表、类型收窄）数据丢失引擎默认不执行 DROP；预览强制标红；生产部署二次确认+权限位；类型收窄前置告警。
前后端字段集合并逻辑不一致预览 DDL 与实际执行漂移合并逻辑唯一权威源放后端编译器；前端预览也调它，废弃前端自拼 schema。
TINYINT/INT 精度在 FieldType::Int 被统一为 BIGINT类型不精确编译器写 db_type 精确串 + 引擎 prefer_db_type 模式；无需改引擎。
并发部署同一库双写冲突复用插件分布式锁 try_lock，锁键含 db_id。
前端仍连 Node、Rust 容器未接通部署能力够不着阶段 0 优先解决接线（代理/前缀/认证），先于功能开发。
生产库连接串安全凭据泄露运行期登记目标库的连接串加密存储；目标库列表对前端只暴露 db_id 与可用性，不回传凭据。
种子数据与既有数据冲突覆盖业务数据种子用 UPSERT 且仅限模型自带初始化数据；部署面板可选「不应用种子」。
跨库类型差异（未来非 PG）方言不兼容引擎已是 DdlDialect trait 设计；当前锁定 PostgreSQL，其他方言后续按 trait 扩展。

14验收标准

功能验收

  • ✅ 五项功能在「模型中心」统一入口可达。
  • ✅ 选定 DCT 模型 + dev 库 → 一键创建出物理表（结构、注释、索引、i18n 伴生表、种子数据正确）。
  • ✅ 修改字段后版本+1 → 同库升级只执行增量 ALTER，存量数据零丢失。
  • ✅ DOC 多层单据模型可整体部署。
  • ✅ 部署前可预览将执行的 DDL 与破坏性警告，且预览不触碰库。
  • ✅ 同一模型可部署到多库，UI 正确显示各库当前版本与状态。

质量验收

  • ✅ 重复部署同版本 = 无变更（幂等）。
  • ✅ DROP 类操作默认不执行，仅提示。
  • ✅ 部署失败整事务回滚，台账记 failed，UI 可见原因。
  • ✅ 编译器对真实 cmxfico_dct/doc 样例有单测覆盖。
  • ✅ 生产库部署需权限位 + 二次确认。
  • ✅ 并发部署同库被锁串行化。
