# 业务单据数据方案 — 落地实现路线图

> 配套设计文档：`业务单据数据装载与前端模型映射方案.md`（19 章）
> 本文把 19 章设计**映射为可编译、可验证、增量交付的实现相序**。原则：每个 Phase 独立编译通过（`cargo check`）、可单测、按依赖自底向上、不破坏现有工作区。

## 运行形态（§16 已定）

- **平台引擎**（Phase 1–5、7–10 的后端主体）= **Rust 原生**，落 `cmx-core` / `cmx-biz` / `cmx-api`。
- **T3 业务扩展**（Phase 10 的 handler）= WASM 插件，走现成 `ServiceRegistry` + extism。
- 前端（Phase 6）= `cmx-data-comp`（Lit）。

## 依赖拓扑（决定相序）

```
cmx-core (ColumnarCodec)          ← Phase 1（最底层，零外部依赖，先做）
   ▲
cmx-biz (DocMetaView→DocLoader→DocSaver→RuleEngine)  ← Phase 2,3,5,9,10
   ▲   └─ 依赖 cmx-database(事务/查询) + cmx-portal(definitions/dict store)
cmx-api (路由 /api/doc/*)          ← Phase 4,5,8
   ▲
web-server (CompressionLayer)     ← Phase 4
   ▲
cmx-data-comp (前端适配层)         ← Phase 6（可与后端并行）
```

- `crates/libs/cmx-api/src/handlers/portal/doc.rs` — 6 个 HTTP 端点

- `docs/sql/migrations/20260703_001_doc_revision.up.sql` — 版本化表
- cmx-biz/Cargo.toml +cmx-utils（雪花 id）

**前端（JS/Lit）**
- `packages/cmx-data-comp/src/lib/cmx-doc-source.js` — loadDocData/saveDocData/ChangeSetCollector
- `packages/cmx-data-comp/src/lib/cmx-dict-cache.js` — L0 维度解析
- `packages/cmx-data-comp/src/index.js` — 导出

**API 端点（`/api/doc/*`）**
- `GET  /doc/data`      装载列式包
- `POST /doc/save`      回存双模式（含保存前校验）
- `GET  /doc/revisions` 版本时间线
- `GET  /doc/revision`  取某版快照
- `POST /doc/restore`   回滚为新版

## 里程碑

- **M1（Phase 1–4）**：装载链路通——能把库里单据装成列式包传前端。**最小可见价值**。
- **M2（Phase 5–6）**：编辑回存闭环——前端改、后端存、双模式。
- **M3（Phase 7–8）**：显示增强 + 版本化——name 显示、历史追溯。
- **M4（Phase 9–10）**：可配置平台 + 正确性护栏——规则引擎、状态/校验/并发/权限。

## 验证纪律

1. 每个 Phase 结束必跑对应 `cargo check` / `cargo test` / `npm test`，绿了才进下一 Phase。
2. 不改现有执行代码的行为；新增为主，改动现有文件只在"注册路由/加中间件/加 pub 访问器"等最小必要处。
3. 迁移 SQL 走 `docs/sql/migrations/`（Phase 8 建版本表），不动现有表结构。
4. 每个 Phase 提交前 `cargo check -p <目标crate>` 必须 EXIT 0。
