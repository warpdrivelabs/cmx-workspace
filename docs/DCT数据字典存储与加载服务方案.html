§0结论速览

DCT 的"定义"与"建表"其实已经存在大半，缺的是面向真实 cf_* 字典表的存储回写与零拷贝装载服务 —— 即 DOC 侧 /api/doc/data/* + /api/doc/save + /api/doc/meta 的 DCT 对等物。本方案把这块补齐，几乎是把 doc/ 这套管线机械地"复刻 + 降维"（字典是扁平/自分级，不是多层主从），最大化复用。

已就绪

设计期定义 JSON（/api/definitions/*，已识别 baseDctMetaRef）、建表编译器（compile_dct→TableDefine→PgTableDefineExecutor）、部署台账（cmx_model_module.dct_version/dct_status）、前端定义编辑器（portal-definition-manager）。

部分存在

旧的 /api/dict/* 检索引擎 —— 但它读写的是 JSON 文件（data/dict/entries/*.json），不是 cf_* 物理表；含 CJK 模糊检索、多字典 JOIN、SCD 停旧启新。保留、后期桥接。

缺口（本方案）

DB 支撑的 DCT 数据服务：/api/dct/meta、/api/dct/data/*（六驱动×内存×传输 + children + stream）、/api/dct/save[/batch]、可选 /api/dct/revision*，以及新 crate 模块 cmx-biz/src/dct/。

一句话
DOC 装的是"一棵单据树"（batch→header→line→aux，靠 upper_id 外键逐层下钻）；DCT 装的是"一批相互独立的字典表"（cf_client、cf_gl_account…），每张要么扁平分页、要么自分级成树（parent_id 自引用）。SQL 生成、零拷贝列式编码、msgpack 出口、事务回存全部照抄 DOC；只有"层级遍历"从"跨表 BFS"降为"单表 flat / 自引用 tree"。
本次追加需求 → §8
"左树右表：左侧一棵树、右侧一张表、右表随左树选中节点刷新、可 CRUD" 有两种绑定来源、同一套实现：① 自分级字典（同表 parent_id 自引用，本次需求）；② 分类字典（classifyRegistry 跨表，上一版）。两者右表过滤都归约成加载器已有的 WHERE fk = ANY($ids)（parent_scope）谓词，前端同一个组件按配置区分。不新增端点，只在 DctMetaView/DctQuery/DctSaver 做小增量。详见 §8 左树右表。

§2目标与非目标

✔ 目标（In Scope）

  • DCT 显示元数据服务 GET /api/dct/meta —— 返回字典目录（各字典表的 code/名称/kind/是否自分级/列 caption·类型），供前端通用页动态建表。
  • DCT 数据装载 /api/dct/data/* —— 复刻 DOC 的六种"驱动×内存×传输"组合 + 懒下钻 children + 真流式 stream，读 cf_* 表。
  • DCT 数据回存 /api/dct/save[/batch] —— merge/replace 双模式、审计列服务端强填、乐观锁；自分级字典保存后服务端重算 full_path/level_no/is_leaf（可选重建闭包表）。
  • 后端 crate 模块 新增 cmx-biz/src/dct/，镜像 doc/。
  • 前端运行期数据源 cmx-dct-source.js + 字典栏位数据源，接入 grid / 主从。

✘ 非目标（Out of Scope）

  • 不重写设计期定义编辑器 —— portal-definition-manager 已支持 DCT，沿用。
  • 不重写建表/部署 —— compile_dct + model deploy 已就绪，本服务只消费其产物（cf_* 表）。
  • 不删除旧 /api/dict/* —— 仍被 AI 工具、弹性组合依赖；本期并行，后期可把其数据源从 JSON 文件切到 /api/dct/data（见 §11）。
  • 本期不做 CJK 模糊检索 —— 新服务先落地 DB 级精确/glob/范围过滤；模糊检索留作增强或暂用旧引擎。
  • 不改 cmx-database / cmx-database-pg / cmx-rowsource —— 直接复用其零拷贝能力。

§4存储方案

存储层的表结构已由 B 层（compile_dct + 部署）建立。本节明确本服务读写的表形态、自分级两种树形维护策略、以及可选的版本/种子机制 —— 不新增建表逻辑，只规定"服务如何用这些表"。

4.1 物理表：cf_* 字典表

每个 dictionaryTable → 一张 cf_<dictCode> 表，列 = base fieldSet 合并列 + 该表 fields[]。例：

-- 由 compile_dct → PgTableDefineExecutor 建立（本服务只读写，不建表） cf_client (id, code, name, sort_no, status, logical_system, system_id, client_role, …) cf_gl_account (id, code, name, …, parent_id, full_path, level_no, is_leaf, -- selfHierarchy coa_id, acct_group_code, pl_bs_flag, …, create_by, create_time, …) cf_comp_unit (id, code, name, …, scope_type, entity_id, effective_from, effective_to, …)
命名/坐标约定（与 DOC 一致）
schema.id == tableName（沿用 cmxfico 约定）。字典定位坐标 = {domain, application, module, file, dict}：前四者定位定义文件（哪套字典元数据），dict = dictCode 定位其中哪张字典表。目标库由请求头 db_id 决定（多库支持，复用 get_db_id_from_header）。

4.2 扁平字典 vs 自分级字典

扁平字典 selfHierarchy=false · 32/35

就是一张普通表。装载 = 单表分页查询（可带过滤/排序/游标）。直接复用 build_layer_select(layer, lq, None)（无 parent_scope 分支）。回存 = 单表 UPSERT/DELETE。等价于"DOC 的一层，去掉子层下钻"。

自分级字典 selfHierarchy=true · 3/35

表内 parent_id 自引用成树（cf_gl_account、cf_fs_version、cf_cons_org）。三种装载模式：

  • 整树：查全表 → 按 parent_id 组装森林（或按物化路径 full_path 排序直出）。
  • 懒下钻：WHERE parent_id = ANY($ids) —— 直接复用 build_layer_select 的 parent_scope 分支，把 child_key 设为该表 parentField（自引用）。
  • 祖先/子树：走闭包表 cf_<dict>_closure（dict_code/ancestor_id/descendant_id/depth）做深度查询。
关键复用点
自分级字典的"懒下钻"与 DOC 的"子层下钻"在 SQL 层完全同构 —— 都是 WHERE <child_key> = ANY($parent_ids)。区别仅是 DOC 的 child_key 指向父表的 id，DCT 自分级的 child_key（parent_id）指向本表的 id。故 sql_builder::build_layer_select 一字不改即可服务两者。

4.3 树维护：物化路径为主，闭包表可选

策略列读写取舍
物化路径（默认）full_path·level_no·is_leaf子树 = full_path LIKE '$path.%'；排序天然移动子树需批量改 full_path零额外表，读简单；深移动写放大
闭包表（可选，深层用）cf_<dict>_closure祖先/后代/depth 精确 O(1) join增删节点维护闭包行查询强，多一张表 + 维护成本

两套字段 base 都已提供（dictionaryHierarchyFields / hierarchyClosureFields）。默认只用物化路径；仅当某字典明确需要频繁祖先链查询时，才在其定义里挂闭包表。写路径统一由服务端保存器重算（见 §5.4），前端不传这些派生列。

有效期 · 停用 · 组织范围 · SCD

装载默认按有效性过滤（status=1 且 effective_from ≤ asOf < effective_to），可用 includeInactive/asOf 覆盖 —— 沿用旧引擎语义，但下推到 SQL WHERE。"停旧启新"（deactivate/supersede）由保存器实现：停旧行置 status=0+effective_to，启新行分配代理键 + effective_from，与旧 dict::write 语义一致，只是落 DB 而非 JSON。

4.4 版本台账（可选） · 种子数据

版本化 Phase 后期

镜像 cmx_doc_revision 建 cmx_dct_revision（dict_file, dict_code, root_id, rev_no, is_current, op, snapshot(JSONB), …），保存器在事务内 append 快照。字典变更频率低，可后置。

种子数据 已有台账位

部署台账 cmx_model_module 已含 seed_version/seed_status。初始字典项（如国家、货币枚举）可作 seed 由部署流程灌入；本服务负责其后的增删改查。

5.2 DctMetaView 解析

解析入口对齐 DOC 的 DocMetaView::parse(doc, base)：读定义 JSON + 其 base fieldset，产出强类型只读视图。降维后骨架：

pub struct DctMetaView { module_code: String, version: u64, dictionaries: Vec<DictView>, // 平铺，不是层树 } pub struct DictView { dict_code: String, dict_name: String, dict_kind: DictKind, table_name: String, // cf_* self_hierarchy: bool, id_field: String, code_field: String, label_field: String, parent_field: Option<String>, // 自分级时 = parent_id columns: Vec<ColumnView>, // base fieldSet 合并列 + 自身 fields，复用 doc::ColumnView unique_keys: Vec<Vec<String>>, code_rule: Option<Value>, hierarchy: Option<HierarchySpec>, // {path_field, level_field, leaf_field, closure_table?} schema: Arc<Schema>, // cmx-core 物理 schema，喂 sql_builder }

ColumnView、Schema、map_field_type、base fieldSet 展开逻辑全部复用 doc 侧（base_dct_meta 的 fieldSets 与 base_doc_meta 结构同形）。/api/dct/meta 投影镜像 project_doc_meta，输出 { metaCode, version, dictionaries:[{dictCode,dictName,dictKind,tableName,selfHierarchy,idField,codeField,labelField,parentField,columns[],uniqueKeys,hierarchy}] }。可带 ?dict= 只投影一张。

定义读取零改动
definitions::store 的 infer_base_file 已经按 metaKind 分流 —— DCT→baseDctMetaRef.file。resolve_dct_meta() 只是把 resolve_doc_meta() 的 DocMetaView::parse 换成 DctMetaView::parse，读定义/读 base/缓存三步骨架照抄。

5.3 加载器：复用与差异

1
解析坐标 → resolve_dct_meta(d,a,m,file) 得 Arc<DctMetaView>，定位 DictView（by dict）。骨架复用
2
按 mode 生成 SQL：flat → build_layer_select(dict_as_layer, lq, None)；tree(整树) → 同上取全量后组装；children → build_layer_select(…, Some((parent_field, ids)))；subtree/ancestors → 闭包表 join。sql_builder 复用
3
执行 + 零拷贝编码：tokio 走 query_sql_zmc_with_datavalues → ZmcDataSet::encode_columnar_binary；自分级 tree 用 ZmcChildGroup 挂子行（与 DOC 子层同机制，parent-id 记字符串，编码期分桶）。rowsource 复用
4
出口：msgpack 信封 encode_envelope_ok 或 JSON 列式 encode_columnar_json；大扁平字典走 tokio-zmc-stream 分帧。出口复用

唯一实质差异：DOC 加载器有一段"用 meta.child_layers() 跨表向下 BFS"的循环；DCT 扁平字典没有这段，自分级字典把它替换为"对同一张表按 parent_id 自引用下钻"。数据访问方法（DatabaseManager 两种驱动）、参数绑定、类型分派全部不变。

5.4 回存与自分级重算

DctSaver::save(mm, db_id, dict_view, mode, changes, ctx) 镜像 DocSaver：

  • merge：按 changeset {inserted[], updated[], deleted[]} 逐行 UPSERT/UPDATE/DELETE；审计列（create_by/time·update_by/time）服务端强填；乐观锁以 update_time baseline，冲突返 409。apply_audit_* / 多值 SQL 复用
  • replace：删该字典（或指定子树）后批量插入快照。
  • 自分级重算 DCT 特有：insert/move 后，服务端按 parent_id 链重算受影响节点的 full_path/level_no/is_leaf（有闭包表则同事务重建其行）。前端不传这些派生列，避免不一致。
  • codeRule / uniqueKeys 校验：保存前校验编码 pattern、唯一键；失败带字段级 Violation 返回。
  • SCD 停旧启新：/api/dct/<dict>/supersede 等价语义落 DB（见 §4.3）。

事务经 mm.get_transaction_context().begin_with_guard(db_id)；批量 /api/dct/save/batch 支持 atomic。

§8左树右表：自分级 & 分类字典的编辑与查询

左侧一棵树、右侧一张表、右表随左树选中节点刷新、可直接 CRUD —— 这是字典维护里最常用的一种界面形态。它有两种绑定来源，但是同一个 UI、同一套后端谓词：① 自分级字典（一张表内 parent_id 自引用，左树右表是同一张字典）；② 分类字典（classifyRegistry，左树是分类字典、右表是被它分类的另一张目标字典）。本节先讲①（本次需求），再讲②（承接上一版），最后给统一的后端/前端/契约。

8.1 统一抽象：一个 UI，两种绑定，同一条谓词

把两种形态抽象到一起，实现上只有"过滤列是谁""树和表是不是同一张"两个参数不同，其余全共用：

维度① 自分级字典 本次需求② 分类字典 上一版 §8
左树字典自己（selfHierarchy=true，如 cf_gl_account）分类字典（classifyDict，如 account_category）
右表同一张字典（展开选中节点的下级）另一张目标字典（targetDict，如 gl_account）
过滤列本表 parentField（parent_id）目标表 bindField（外键）
过滤谓词WHERE <过滤列> = ANY($选中节点及其子树 id 集) —— 完全相同
范围直接子级 或 整棵子树（deep）该分类 或 含子类（inheritUp）
新建默认新行 parent_id = 左树选中节点新行 bindField = 左树选中分类
"移动"改 parent_id（+ 服务端重算 full_path）改 bindField
这就是为什么代价极低
两种形态的右表过滤 WHERE fk = ANY($ids)，和加载器早已存在的子层下钻 parent_scope 分支（§5.3）是同一个形状。前端也是同一个左树右表组件，只是配置"过滤列 = parent_id 还是 bindField、右表 = 本字典还是目标字典"。所以本次自分级需求，后端几乎零新增（自分级装载 §4.2 已在方案里），主要是前端组件 + 一个可选的"deep 子树"参数。

8.2 自分级字典：同表 parent_id（本次需求）

目标：selfHierarchy=true 的字典（cmxfico 里 cf_gl_account/cf_fs_version/cf_cons_org，gl_md 里 acct_entity/gl_account/cost_center/… 多张），左树展示层级，右表展示选中节点的下级，可增删改查。

装载（读）

  • 左树：loadDctData({dict, mode:'tree'}) 装整棵（物化路径 full_path 排序直出森林），或大树时 mode:'children' 惰性展开。§4.2 已有
  • 右表：选中节点 → {dict, mode:'children', parentIds:[节点id], deep:false} → 后端 WHERE parent_id = ANY($ids)。parent_scope 复用
  • deep 开关：deep:true 时右表显整棵子树（不只直接子级），后端用 full_path LIKE '$path.%' 或闭包表。query 小增量

CRUD（写）

  • 新增：右表加行，parent_id 默认 = 左树当前选中节点；保存时服务端算 full_path/level_no/is_leaf（父的 is_leaf 置 0）。§5.4 重算
  • 编辑：普通列走 changes；改 code 且被引用时按 uniqueKeys/引用完整性校验。
  • 删除：叶子直接删；非叶需选策略（禁删 / 级联 / 提升子级到祖父）—— 见 §8 风险。
  • 移动：拖拽子树到另一节点 = 改 parent_id + 服务端批量重算子树 full_path（事务内，注意写放大 R2）。
// 右表：装"1001 流动资产"节点的直接下级科目 POST /api/dct/data/tokio-zmc-msgpack?...&file=cmxfico_dct_meta_v1.json { "dict": "gl_account", "mode": "children", "parentIds": ["1001"], // 左树选中节点 id（自引用 parent_id 过滤） "deep": false, // true=整棵子树(full_path LIKE)；false=仅直接下级 "orderBy": ["sort_key", "code"], "limit": 500 } // 新增子节点：parent_id 默认填左树选中节点，full_path/level_no/is_leaf 由服务端算 POST /api/dct/save?...&dict=gl_account { "saveMode":"merge", "changes":{ "cf_gl_account":{ "inserted":[{ "id":"new-1", "fields":{ code:"100101", name:"库存现金", "parent_id":"1001" } }] } } }
与 §4.2 的关系
§4.2 已经把"自分级字典怎么装载/存储"（物化路径 vs 闭包表、children 懒下钻、派生列服务端重算）讲透了。本节不重复那些，只补"左树右表这个界面形态怎么用那套能力"：左树=整树装载、右表=children 过滤、CRUD=§5.4 保存器 + parent_id 默认值。唯一新增是右表的 deep（子树 vs 直接子级）开关。

8.3 分类字典：跨表 classifyRegistry / groupRegistry

形态②：左树是分类字典（如"科目类别""伙伴分类"），右表是被它分类的另一张目标字典，选中分类节点 → 右表只显归属该分类（含子类）的数据。这套关系元数据里已声明，不需发明新约定。

约定已经在元数据里了
gl_md_dct_meta_v1.json 顶层已声明 classifyRegistry[] 与 groupRegistry[]，把"哪张分类字典 × 过滤哪张目标字典 × 靠哪个绑定列"讲得一清二楚。服务/前端只需消费这两个注册表。
// gl_md_dct_meta_v1.json 顶层（真实存在） "classifyRegistry": [ { "classifyMeta": { "classifyCode": "account_category", "classifyName": "科目类别", "targetDict": "gl_account", // 右侧网格：被过滤的目标字典 "classifyDict": "account_category", // 左侧树：分类字典（自分级则成树） "bindField": "account_type", // 目标表上的外键列（存所属分类 code/id） "multiAttr": false, // 单选归类（一条数据一个分类） "leafOnly": false, // 是否只能归到叶子分类 "inheritUp": true // 选父类时是否含所有子类数据（子树过滤） } } ], "groupRegistry": [ { "groupMeta": { "groupSchemeCode": "report_group", "targetDict": "gl_account", "groupDict": "report_group_dict", "multiValue": true, // 多对多：一条数据进多个分组 "relationTable": "dict_group_rel", // 中间关系表 "inheritDown": true } } ]
字段含义驱动的行为
classifyDict左树用哪张分类字典（dictKind=CLASSIFY，常 selfHierarchy=true）左侧调 /api/dct/data mode:'tree' 装该字典（即 §8.2 的左树能力）
targetDict右表用哪张目标业务字典右侧调 /api/dct/data 装该字典，带分类过滤
bindField目标表上存"所属分类"的外键列过滤谓词 WHERE bindField = ANY($categoryIds)
inheritUp选父分类是否连带其子分类的数据true → 先展开分类子树取 id 集合，再 ANY 过滤（同 §8.2 的 deep）
leafOnly / multiAttr只能归叶子 / 是否多分类写校验：非叶报错 / multiAttr→走 group 关系表

多对多分组（groupRegistry，形态②的变体）

一条数据可进多个分组，经中间关系表 dict_group_rel（relationCommonFields：分组节点 × 业务数据双向冗余）。右表过滤 = JOIN 关系表 WHERE group_id = ANY(...)；写 = 增删关系行（groupChanges）。这是唯一需要"新 JOIN 分支"的形态，其余都复用 parent_scope 谓词。后置实现。

样例数据存在不一致 —— 落地前需对齐
抽查 gl_md_dct_meta_v1.json 发现 registry 与实际表对不齐，实现时以"表结构 + registry 语义"为准并修数据：
① classifyMeta.classifyDict="partner_category_dict"，但实际字典 dictCode 是 partner_category（后缀 _dict 多余）；
② account_category 的 bindField="account_type"，但 gl_account 的 fields 里没有 account_type 列（有 account_category_code）——绑定列名需校正；
③ groupRegistry.relationTable="dict_group_rel" 未作为 dictionaryTable 声明（不会被 compile_dct 建出），多对多形态需先补关系表定义（可复用 relationCommonFields）。

§11关键决策与风险

已定决策

D1DCT 数据服务读写 cf_* 物理表（B 层部署产物），不走旧 data/dict/entries/*.json。与 DOC 的 cv_* 对称。
D2端点、模块、命名逐一对标 DOC（/api/doc/*→/api/dct/*，doc/→dct/），最大复用、最低认知负担。
D3自分级树默认物化路径（base 已含 full_path/level_no/is_leaf）；闭包表仅按需挂载。派生列一律服务端重算。
D4旧 /api/dict/* 检索引擎本期保留并行（AI 工具、弹性组合仍依赖），不删；后期桥接。
D5sql_builder 不 fork，扁平字典与自分级下钻共用 build_layer_select。
D6左树右表是一个统一形态：自分级（同表 parent_id）与分类（跨表 bindField，消费既有 classifyRegistry）共用同一前端组件 + 同一 parent_scope 谓词，不新增端点，只在 meta/query/saver 做增量。
D7先做自分级 + 单属性分类（parent_id/bindField 都是普通列，走 changes，覆盖绝大多数场景）；多对多分组（groupRegistry + JOIN 关系表）后置，需先补 dict_group_rel 表定义。

待确认 / 风险

Q1关系字典（RELATION）装载形态：是当普通两列冗余表（走 flat），还是需要 JOIN 双方名称？建议先 flat（relationCommonFields 已冗余 name），JOIN 留增强。
Q2旧引擎的 CJK 模糊检索是否需求？新服务先做 DB 精确/glob/范围；若前端下拉强依赖模糊，短期仍走 /api/dict，或后端加 ILIKE/pg_trgm。
Q3子树展开（deep/inheritUp）放哪：后端展开（前端只传选中节点 id，推荐，逻辑内聚）还是前端传全子树 id 集？建议后端，用物化路径 full_path LIKE 一次取全集。自分级与分类形态同此。
Q4右表默认范围：自分级右表默认显直接子级还是整棵子树（deep）？分类右表默认仅本类还是含子类（inheritUp）？"未分类/未挂靠"数据是否加虚拟节点（WHERE fk IS NULL）浏览？需产品确认交互。
R1组织范围/多租户：scope_type/entity_id 过滤需 handler 拿到当前组织上下文；DOC 侧 data handler 目前基本忽略身份，DCT 若要按组织隔离需显式下推，别遗漏。
R2自分级移动子树写放大：物化路径下移动深子树会批量改 full_path；大字典（如科目表）需在事务内做，注意锁范围。
R3seed 与运行期写冲突：is_system=1 系统预置项禁删、部分禁改，保存器需校验。
R4自分级删除策略：删非叶节点如何处理其子树——禁删（有子级报错）/ 级联删 / 子级提升到祖父？默认禁删非叶最安全；级联/提升需产品确认并在保存器实现（含 full_path 重算）。
R5样例元数据不一致（见 §8.3 红框）：classifyDict 后缀 _dict 对不上 dictCode、bindField 列在目标表不存在、dict_group_rel 未声明为表。落地前需修数据 + 加 registry 校验（引用的 dict/列必须存在）。
方案对标既有实现：后端 DOC = cmx-container/crates/libs/cmx-biz/src/doc/ + cmx-api/.../portal/doc.rs；前端 DOC = CMXPortalManager + packages/cmx-data-comp/src/lib/cmx-doc-source.js。DCT 定义/建表/部署已就绪（definitions::store · model_center::compile_dct · cmx_model_module），本方案补齐 cf_* 物理表的存储回写与零拷贝装载服务。定义样例见 data/meta/definitions/**/*_dct_meta_*.json 与 base/base_dct_meta_v1.json。
