DCT / DOC · bigint 主键 ID 生成与导入导出免撞方案

如何为 DCT 数据字典 / DOC 业务单据的 bigint id 列生成取值：既全局唯一，又能整包导入他系统而无需改号、且不产生重复。
先不动代码 · 仅方案 2026-07-11 范围 cf_* / cv_* 物理表 · 元数据 & 数据行 默认建议：保留段 + 雪花双车道 配套 DCT/DOC 服务方案

00摘要 & 结论先行

一句话：把 63 位正整数空间切成两条车道——低段放「标准交付/确定性」内容（各系统里 id 恒等，导入即幂等 upsert），高段放「运行期自建」内容（每个部署一个 node id 的雪花号，天生跨系统不撞）。两段用一条数值边界自动隔离，任何导出包直插目标库都不用改 id、不会重复。

唯一性

雪花 = 时间 + 部署号 + 序列，单调递增且跨部署不重叠；保留段由厂商单点铸号或按业务键确定性推导。

导入免改号

导出包里的 id 本就全局唯一，INSERT 时原样保留；自引用/外键（parent_id、category_id、bindField）同包搬运，无需重映射。

不重复

标准内容按 id 做 UPSERT（幂等）；自建内容因号段不重叠不会撞库；撞号只可能来自「同一 node id 被两处复用」——由分配登记杜绝。

最先要知道的一条坑
本仓库前端是 JS。63 位雪花 id 会超过 Number.MAX_SAFE_INTEGER = 2^53-1 ≈ 9.007e15（真实时间下雪花值约 1e17 量级），一旦以 JS Number 解析 JSON/msgpack 就会静默丢精度、id 变号，直接击穿 ChangeSetCollector 按 row.id 记键的逻辑。两条出路：① id 全链路当字符串传（推荐，范围无损）；② 改用 §4.2 的 52 位 JS 安全布局。详见 §8。

01问题定义与三条硬约束

DCT 字典与 DOC 单据的字段集里都有一列 id bigint（由 compile_dct / compile_doc 从 baseFieldSet/systemFieldSet 合并生成，落到 cf_* / cv_* 物理表作主键）。问题是：这一列的取值从哪来？ 取值必须同时满足三条：

C1
唯一性（Uniqueness） — 同一张表内绝不重复；理想情况下跨库、跨系统、跨厂商也不重复。
C2
导入免改（Transplantable） — 从 A 系统导出的一批行，导入 B 系统时 id 原样不动，包括其自引用/外键指向也不用改写。
C3
不重复（Idempotent / Non-colliding） — 导入不会与 B 已有数据撞车；对「同一逻辑对象」重复导入是幂等的（不会插出两条）。

1.1 为什么自增序列（serial / bigserial / IDENTITY）直接出局

撞号

A 库 id=1..100、B 库也 id=1..100。把 A 的「银行存款 id=3」导入 B，B 早有 id=3（库存现金）→ 主键冲突或覆盖错行。违反 C1/C3。

要重映射外键

为避撞号，导入时得给 A 的行重新分配 B 的新 id，随即级联改写所有引用（parent_id、单据行→头、category_id…）。工程量大、易错。违反 C2。

结论
序列适合「单库内部、永不外迁」的数据；一旦有跨系统导入导出诉求，主键必须在全局命名空间里生成。下面比较的所有候选，本质都是「如何把全局唯一性塞进 64 位」。

03推荐：双车道 63 位空间划分

把 bigint 的 63 个可用位（符号位恒 0，保证正数）沿一条数值边界切成两条车道。内容按「谁拥有这个号」进入不同车道，边界保证两车道的取值范围永不交叠。

0符号位·恒 0
低段 < 2^52保留 / 确定性（标准交付）
高段 ≥ 2^56雪花（运行期自建，按部署分 node）
车道 A · 保留 / 确定性段（低段）

放什么：随产品交付的标准内容——标准字典（币种、国家、标准科目模板）、标准单据类型、以及所有元数据定义自身的身份（字典 code、单据 docType 的对象 id）。

怎么铸：两种方式二选一——① 手工/单点铸号：厂商构建期集中分配小整数，随数据发布；② 确定性哈希：id = hash63(自然键) & 0xF_FFFF_FFFF_FFFF（截到 ≤52 位），同一逻辑对象在任何系统算出同一个 id。

为什么免撞/不重复：低段范围由厂商独占，客户运行不会在此段铸号；导入即按 id 做 UPSERT，天然幂等。

车道 B · 雪花运行段（高段）

放什么：运行期由用户新建的数据行——字典明细（cf_gl_account 新科目）、单据实例（cv_* 头/行）、及一切「哪个部署造的」有意义的行。

怎么铸：标准雪花 (ms<<22)|(node<<12)|seq；每个部署/租户/权威源一个 node id（见 §4.3）。

为什么免撞/不重复：不同部署的 node 段不同 → 号段天然不重叠；导出的 id 全局唯一，导入原样 INSERT，不可能与目标库已有雪花号撞车。

边界为何能「自动」隔离
雪花值 = ms_since_epoch << 22。取 epoch=2025-01-01，则运行一年后 ms ≈ 3.16e10 ≈ 2^34.9，左移 22 位后雪花号恒 ≥ 2^56 ≈ 7.2e16。只要把车道 A 限制在 < 2^52 ≈ 4.5e15，两段之间还留着 [2^52, 2^56) 的缓冲带，永不交叠——无需额外「车道标志位」，靠数值大小即可判别一个 id 属于哪条车道。
与本仓库 NoID 字典的关系
记忆记载：部分字典是 NoID（如 cf_currency 以 code 作 PK，没有 bigint id 列）。这类字典的「身份」本就是业务 code，天生跨系统稳定、导入免撞——它们不进本方案的号段体系，保持 code 主键即可。本方案只治理真正声明了 id bigint 主键的表（如 cf_gl_account、多数 cv_* 单据）。

04雪花布局（含 JS 安全变体）

4.1 63 位标准布局（吞吐优先）

1bit 63 · 符号=0
41 bit 毫秒时间戳相对 epoch，≈ 69.7 年
10 bit node1024 个部署/源
12 bit 序列4096 / ms / node
  • 时间戳：当前毫秒 − 自定义 epoch（建议 2025-01-01T00:00:00Z）。41 位可用约 69.7 年（到 ~2094）。
  • node：10 位 = 1024 个铸号点。可再切 5 bit 数据中心 + 5 bit 机器，或整体作「部署编号」由登记表分配。
  • 序列：同一毫秒内自增，满 4096 则自旋等下一毫秒。单 node ≈ 409.6 万/秒，对元数据/字典/单据量级绰绰有余。
  • 取值范围：真实时间下 ≈ 7e16 ~ 3e17，远大于 bigint 上限 9.22e18 的零头——安全，且正数（符号位不用）。
代价
该布局的 id > 2^53，不是 JS 安全整数。若采用，必须全链路以字符串承载 id（见 §8）。

4.2 52 位 JS 安全布局（本域推荐）

DCT/DOC 是低频元数据/字典/单据，不需要百万 TPS。用一个总位宽 ≤ 52 的紧凑布局，让 id 始终 < 2^53，从根上绕开 JS 精度雷区：

32 bit 秒级时间戳相对 epoch，≈ 136 年
8 bit node256 个部署/源
12 bit 序列4096 / 秒 / node
  • 总 52 位，最大值 ≈ 4.5e15 < 2^53-1 ≈ 9.007e15，留 1 位安全余量 → JS Number 直接安全，无需字符串化。
  • 256 个部署、每部署每秒 4096 号（够用；突发可退避到下一秒）。136 年时间跨度。
  • 依旧单调时间有序 + 跨部署不重叠，C1/C2/C3 全满足。
选型建议
若愿意让 id 全链路走字符串 → 用 §4.1（范围无上限焦虑，未来若挪作高频数据也不用换算法）。
若想保持 id 是纯数字、最省前端改造 → 用 §4.2（本域数据量完全够）。两者可共存：同一条边界之上，52 位雪花与 63 位雪花值域仍不交叠（52 位雪花 < 2^52，正好落在……）——注意此时需重新规划边界，见下方警示。
别把两种雪花布局混用在同一套系统
52 位雪花的取值 < 2^52，会落进车道 A 的保留段范围，与「低段=标准内容」的约定冲突。一套系统只选一种雪花布局：选 63 位→车道 A 用 <2^52；选 52 位→改用「显式 tier 高位」区分车道（见 §5 的 tier 位方案），不要靠数值大小自动隔离。

4.3 node id 分配 & 时钟回拨

node id 从哪来

  • 登记表：中央维护「部署/租户 → node id」映射，一处一号，永不复用（复用=撞号根源）。
  • 启动注入：node id 走配置（如 dev-local.toml 增 id_gen.node_id），进程启动读入。
  • 厂商标准源：预留 node=0 给「构建期铸标准内容」，客户侧从 1 起分配。

时钟回拨（clock skew）

  • 检测：记住 last_ms，若 now < last_ms 即回拨。
  • 小回拨（≤ 数十 ms）：自旋等待时钟追上再发号。
  • 大回拨：拒绝发号并告警，绝不「猜一个更大的号」（会与未来撞车）。
  • NTP 建议 slew 模式（平滑校时）而非 step（跳变）。

05保留段 & 确定性哈希段

车道 A 内部还可细分两个来源：手工保留（人指定小整数）与 确定性哈希（按业务键算）。两者都保证「同一逻辑对象在任何系统里 id 恒等」，从而导入幂等。

5.1 手工保留段（delivered 标准内容）

厂商在构建期为标准内容集中分配固定整数，随交付数据发布。适合数量少、语义关键、极少变更的对象——标准字典条目、标准单据类型、系统枚举。类比 SAP 的「标准命名空间 vs 客户 Y/Z 段」、Oracle 的 seeded data。

5.2 确定性哈希段

当「同一逻辑对象可能在多个系统被各自独立定义、事后需要按身份合并」时，用业务自然键推导 id：

// 自然键 = 稳定、跨系统一致的业务标识（不含随机/自增成分） // DCT 字典条目：domain · module · dictCode · entryCode // DOC 单据类型：domain · module · docType key = "fi/cmxfico/gl/gl_account/1002" // 64 位强散列（xxHash64 / SHA-256 取前 8 字节），再截到 ≤52 位并清符号位 h = xxhash64(key) id = (h & 0x000F_FFFF_FFFF_FFFF) // 保留低 52 位 → JS 安全、落在车道 A // 落库前查「碰撞登记表」：若 id 已被别的 key 占用 → 记录并加盐重算 assert registry.lookup(id) in {none, key}

好处

同键同值 → 重复导入是 UPSERT（不重复）；两系统独立建「币种字典」也得同一 id，天然对齐。无需任何发号中心。

代价 & 纪律

哈希有碰撞概率（52 位下，约数十万行时概率仍极低但非零）→ 需碰撞登记表兜底；且随机分布、非时间有序（对低频元数据的索引局部性影响可忽略）。自然键一旦选定不可改（改了 id 就变）。

若采用 52 位雪花（§4.2），车道用「显式 tier 位」而非数值边界
保留 63 位空间的最高 3 位作 tier：tier=0 保留段、tier=1 确定性段、tier≥2 雪花运行段。此时 id = (tier << 60) | body。但注意 tier>0 会让 id > 2^60 → 又不 JS 安全。所以「JS 安全」与「tier 位显式分车道」二者有张力：要么全链路字符串 + tier 位（最规整），要么放弃 tier、用数值边界 + 63 位雪花 + 字符串传输。这是本方案唯一需要产品/架构拍板的取舍点，见 §9。

6.2 外键 / 自引用「整包搬运」

关键洞察：因为每个 id 本身就是全局唯一的，它被谁引用也就全局稳定。所以导出时把「对象 + 其引用」放进同一个包，导入时连 id 带引用原样插入，引用自动命中——不需要「先插父、拿到新 id、再回填子」的重映射舞步。

// 一个自分级字典（gl_account）导出片段 —— parent_id 指向的也是全局唯一 id { "table":"cf_gl_account", "lane":"snowflake", "node":7, "rows":[ { "id":"720381947500000001", "code":"1001", "parent_id":null, "name":"库存现金" }, { "id":"720381947500000002", "code":"1001.01", "parent_id":"720381947500000001", "name":"现金-人民币" } ]} // 导入 B 库：两行原样 INSERT，parent_id 无需改写即命中父行。 // 分类字典同理：category_id / bindField 指向的分类行 id 也整包搬运。
这正是「导入无需修改」的技术根因
序列 id 做不到这点，是因为它只在单库内唯一 → 引用是「局部指针」，跨库必须重定位。全局唯一 id 把引用变成「全局指针」，搬到哪都指得对。DCT 的 parent_id 自引用、分类字典的 bindField、DOC 的行→头引用、乃至跨 DAM 引用，全部适用。

6.3 导入冲突决策矩阵

1
按 id 探测目标库 — 目标不存在此 id？→ 直接 INSERT，结束。
2
id 已存在 & 内容等价 — 视为重复导入 → 跳过（幂等）。
3
id 已存在 & 内容不同 — 分车道处理：
· 标准段：按版本决胜（厂商新版覆盖 / 或提示冲突留给部署选择）；
· 雪花段：本不该发生（号段隔离）→ 若真撞了，说明node id 被复用，立即告警并阻断，排查登记表。
4
记账 — 导入报告输出：新增 N / 幂等跳过 M / 冲突 K，绝不静默覆盖。

7.1 铸号发生在哪一层

层做法取舍

7.2 元数据侧

  • compile_dct / compile_doc：id 列声明 bigint + PRIMARY KEY，标注生成策略（默认策略键，如 idStrategy:"snowflake" / "deterministic" / "reserved"）。NoID 字典维持 code PK 分支不变。
  • 字段集：给 id 加元属性区分车道（供导入器判定 UPSERT vs INSERT）。
  • 迁移：新增「node id 登记表」+「哈希碰撞登记表」（若启用确定性段）；dev-local.toml 增 [id_gen] node_id=…, epoch=…, layout="js52"|"full63"。

7.3 传输链路（承接 §8 精度坑）

  • 选 63 位布局 → id 在 JSON/msgpack 里一律字符串；decodeMsgpack → pkgToRows 后 id 保持 string；grid/collector/context 全程 string 比较。
  • 选 52 位布局 → id 可保持 number，链路不改；仅需保证任何一环没把它塞进会溢出的运算。
  • 白名单/路由：导入导出端点（拟 /api/dct/export、/api/dct/import、DOC 对应）记得加 auth.whitelist，与既有 /api/dct 一致。

08关键坑（务必先读）

坑 1 · JS 2^53 精度天花板（本仓库头号风险）
Number.MAX_SAFE_INTEGER = 9,007,199,254,740,991 (2^53-1)。63 位雪花 id ≈ 1e17，远超此值。JS JSON.parse / msgpack 解出的 Number 会丢低位、id 变号且不报错。后果直击 ChangeSetCollector（按 row.id 记键）、grid moveToId、乐观锁 WHERE pk=$ → 改到别的行 / 冲突误报。
缓解：① id 全链路字符串（rmp 编码为 str、前端不 Number()）；或 ② 用 §4.2 的 52 位布局把 id 压回安全区。切勿用 63 位雪花却让 id 走 Number。
坑 2 · node id 复用 = 撞号唯一来源
两个部署/进程拿到同一 node id，同一毫秒就可能发出相同 id。登记表单点分配、永不回收；容器扩缩容时 node id 要随实例稳定（不能随机）。
坑 3 · 时钟回拨
NTP step 跳变致时间倒退 → 重号。检测到回拨宁可等待/拒发，不可猜号。见 §4.3。
坑 4 · 符号位 / 负数
PG bigint 有符号。布局务必保证最高位为 0（正数），否则排序、比较、前端展示全乱。63 位方案天然满足；自定义位宽时手动清高位。
坑 5 · 两种雪花布局混用
52 位与 63 位雪花值域会侵入车道 A。一套系统只选一种布局；若必须并存，改用显式 tier 位分车道（§5 末）。
坑 6 · 确定性哈希的自然键漂移
自然键选错列（含可变/本地成分）→ 换库 id 就变，幂等失效。自然键只能用跨系统恒定的业务标识，且一经发布不可改。
坑 7 · 导入静默覆盖
冲突时绝不默认覆盖客户数据。按 §6.3 出报告，标准段覆盖也要留版本审计。

09推荐取舍与决策表

默认建议（若不想纠结，照这个走）
  1. 运行期自建数据（cf_* 明细、cv_* 单据）→ 雪花，每部署一个 node id（登记表分配），服务端在 dct_upsert/dct_save insert 分支铸号。
  2. id 传输 → 采 63 位布局 + 全链路字符串（范围无忧、面向未来）；或若想少改前端，采 52 位布局 + 数字。
  3. 标准交付内容 → 保留段/确定性哈希，各系统 id 恒等，导入幂等 UPSERT。
  4. NoID 字典（cf_currency 等）→ 维持 code 主键，不进号段体系。
  5. 导入器 → 按 §6.3 分车道：标准 UPSERT、自建 INSERT 原样 id、冲突出报告不静默覆盖。
你的优先诉求选布局标准内容前端改造量
最省前端改造、数据量低（本域典型）52 位 JS 安全确定性哈希（≤52 位）小（id 仍是 number）
面向未来 / 可能挪作高频数据63 位标准保留段 或 确定性中（id 全链路字符串化）
强调「同名对象自动对齐合并」任一 + 确定性段权重高确定性哈希为主+ 碰撞登记表

唯一需要拍板的点
52 位数字（省前端） vs 63 位字符串（面向未来）——两条路都完整满足唯一/免改/不重复三约束，差别只在前端是否需要把 id 当字符串处理，以及未来可扩展性。建议按「本域数据量 + 团队对前端字符串化 id 的接受度」二选一，其余部分方案通用。
