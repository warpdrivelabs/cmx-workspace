# 企业本体拓扑架构方案：单一本体 vs 多本体

> **一句话结论**：既不要"一个巨型本体大一统"，也不要"N 个互不连通的孤立本体"，而应采用
> **联邦式单一本体（Federated Single Ontology）**——**一个逻辑本体、多个受限上下文（bounded context）、
> 按 DAM（领域/应用/模块）分区治理、核心共享主数据只定义一次、物理可分而语义统一**。
>
> 面向 `cmx-ontology`（Palantir-Foundry 式企业本体平台）落地。

---

## 0. TL;DR · 结论先行

| 维度 | 建议 |
|---|---|
| **逻辑上** | **一个本体**（一套统一语义、一个"客户/商品/科目"的唯一含义） |
| **组织上** | **按领域分区**（每个领域 = 一个受限上下文，独立建模、独立发布） |
| **划分键** | 复用系统 **DAM（Domain ▸ Application ▸ Module）** 三级命名空间 |
| **共享数据** | 主数据 & 参照数据下沉 **核心域（Kernel）**，全局只定义一次，各域引用 |
| **物理上** | 逻辑单一、**物理可分**（db-per-tenant / schema-per-domain），换取性能、隔离、合规 |
| **消费上** | 应用/项目只**组合**本体、不改定义（Workshop / OSDK） |

**为什么不是"一个大本体"**：会变成没有边界的"泥球"——人人可改、大图性能差、改一处牵动全局、团队无法并行。
**为什么不是"多个孤立本体"**：语义割裂——"客户"在财务、CRM、物流里是三个不能 join 的东西，主数据重复、跨域分析做不了，恰恰丢掉了本体最大的价值。

---

## 1. 问题的本质：不是"几个数据库"，而是"统一语义 vs 割裂语义"

很多人把这个问题理解成"建一个库还是建多个库"。**这是把物理存储和语义模型混为一谈了。**

本体（Ontology）的价值不在存储，而在**给企业一套统一的、机器可理解的"世界模型"**：一个"客户"就是同一个客户，无论它出现在销售订单、应收发票还是发运单里，都能被**连接（join）、追溯（search-around）、统一治理（权限/血缘）**。

所以真正的问题是：

> **在哪些地方需要"统一的语义"，在哪些地方需要"自治的边界"？**

- 需要统一语义 → **共享实体下沉核心，唯一定义**（客户、商品、组织、员工、科目…）。
- 需要自治边界 → **领域各自建模、独立演进**（财务的"凭证"、供应链的"发运单"…）。

物理分不分库，是**部署决策**（性能/隔离/合规），可以独立于语义决策做——**逻辑单一 ≠ 物理单库**。

## 2. 三种拓扑模式

{{FIG:three-patterns}}

### 2.1 模式 ①：单一大一统本体（Monolith）
把所有实体塞进**一个无边界的模型**。

- ✅ 语义天然一致（都在一个模型里）。
- ✕ **演进僵化**：无边界 → 人人可改、改动影响面不可控。
- ✕ **性能差**：对象类型一多，图/查询都拖不动（本平台的"分域折叠"正是为缓解这一点）。
- ✕ **治理难**：无法按域授权、无法并行开发。
- 适用：极小企业、单一业务、几十个对象类型封顶。

### 2.2 模式 ②：孤立多本体（Fragmented Silos）
每个系统/团队各建各的本体，**互不连通**。

- ✅ 领域自治、各自演进快。
- ✕ **语义割裂**："Customer"在财务/CRM/物流里是三个不同的东西，**无法 join**。
- ✕ **主数据重复**：同一个客户在 N 个本体里各存一份，口径不一。
- ✕ **跨域分析做不了**：端到端（下单→发货→回款）链路断裂。
- 这是**最常见也最危险的陷阱**——它把本体降级成了又一批数据孤岛。

### 2.3 模式 ③：联邦式单一本体（Federated Single Ontology）✅ 推荐
**一个逻辑本体，内部按领域切成受限上下文**：核心域承载共享语义，领域本体各自自治并**引用**核心。

- ✅ **统一语义 + 可跨域连接**（一个"客户"处处可 join）。
- ✅ **领域自治 + 分区治理**（各域独立建模/发布/授权）。
- ✅ **核心只定义一次**（主数据/参照/共享接口不重复）。
- ✅ **性能可分区**（默认收起、按域加载）。
- 这是 Palantir Foundry、以及成熟数据网格（Data Mesh）实践的共同答案。

## 4. 推荐方案详解：联邦式单一本体

### 4.1 分层架构

{{FIG:federated-arch}}

自上而下五层：

1. **应用 / 项目层（Application Scope）**——客户 360、关账工作台、风控看板等。**只组合本体、不改定义**，通过 Workshop（可视化搭建）/ OSDK（强类型客户端）消费。
2. **领域本体层（Domain Ontologies）**——财务、销售、供应链、生产、人力……每个域一个**受限上下文**，在自己的 namespace 下定义对象类型、关系、动作。域内自治，域间通过核心连接。
3. **核心域 / 企业内核（Kernel）**——**共享主数据**（客户/供应商/商品/组织/员工）、**参照数据**（币种/科目/单位）、**共享接口**。全局**只定义一次**，各领域引用。这是"单一语义"的锚点。
4. **数据集成层（O3 Funnel）**——外部 ERP/CRM/数据源经**映射 → 隔离区 → 同步**灌成对象实例。
5. **物理存储（Physical）**——`db-per-tenant` / `schema-per-domain`。**逻辑单一、物理可分**，换取性能、租户隔离与合规。

> 关键点：**核心不是"又一个领域"，而是所有领域的公共依赖**。领域可以厚（很多专有对象），核心要薄（只放真正被复用的）。

### 4.2 用 DAM 做命名空间划分（复用系统既有能力）

不需要发明新的划分机制——直接用系统已有的 **DAM（Domain ▸ Application ▸ Module）** 三级分类作为本体的**分区键**：

{{FIG:dam-namespace}}

- **Domain（领域）** = 顶层业务域（财务 fi、供应链 scm…）= 治理/授权的大边界。
- **Application（应用）** = 域内的应用（会计核算 cmxfico、仓储 wms…）。
- **Module（模块）** = **一个受限上下文 = 一个可独立演进的本体分区**（总账 gl、库存 inv…）。

一套 DAM 编码**同时驱动两件事**：
1. **治理**：按 Domain/Module 授权、划定变更影响面、支持并行开发。
2. **性能**：本体图**按 DAM 分域折叠**——默认只画少数域盒，点开某模块才渲染其子图，把"大一统本体"的性能问题从根上解决。

> 在 `cmx-ontology` 里，对象类型已带 `dam:{domain,application,module}` 字段，图/浏览器/设计台都按它分组。**分区能力已经就位**。

### 4.3 跨域连接：一个"客户"，处处可 join

这是联邦式相对"孤立多本体"的**决定性优势**：

{{FIG:cross-domain}}

- **核心实体唯一定义**：`Core.Customer #C-1024` 只有一个。
- **各域对象经共享主键 / 接口指向它**：`crm.Order.custId`、`scm.Shipment.customer`、`fi.Invoice.partner` 都解析到同一个客户。
- **Search-Around 一跳可达**：从任一域对象出发 → 到同一个客户 → 再钻取到它在其它域的一切（订单、发票、工单）。端到端可追溯，血缘天然连通。

实现手段（本平台均已支持或易于支持）：
- **共享主键引用**：领域对象的外键属性指向核心对象类型的主键。
- **接口多态（interface）**：核心定义 `IParty` 接口，客户/供应商实现它，领域对象引用接口而非具体类型。
- **组合 vs 关联**：单据内部层次（头/行/明细）用**嵌套复合属性**表达"一个整体"；跨域实体之间才用**关系（LinkType）**。二者不要混淆。

## 6. 选型决策：一个新实体/新需求，往哪一层落？

{{FIG:decision}}

**三条经验法则**：

1. **能被 ≥2 个领域复用的 → 下沉核心**（主数据、参照数据、共享接口）。宁可核心薄一点，也不要把专有对象塞进核心。
2. **本域专有的稳定业务对象/关系 → 建/扩领域本体**（在该域 namespace 下）。
3. **一次性拼装、项目专有的 → 只在应用/项目层组合**（Workshop/OSDK），不落本体定义。

> 拿不准时的默认动作：**先放领域本体**。等它被第二个领域需要时，再"上提"到核心——**从领域上提核心，比从核心下拆领域容易得多**。

## 7. 反模式警示

- **🚫 巨型泥球（Big Ball of Mud）**：一个无边界的大本体，人人可改，最终没人敢动。→ 用 DAM 划边界。
- **🚫 数据孤岛（Silos）**：每系统一个孤立本体，"客户"三个含义。→ 共享实体必须下沉核心、唯一定义。
- **🚫 核心膨胀（God Kernel）**：什么都往核心塞，核心变成新的巨石。→ 核心只放**真正被复用**的，从严准入。
- **🚫 过度拆分（Over-fragmentation）**：一个业务域拆成几十个碎本体，跨"域"调用满天飞。→ 域的粒度对齐**业务能力/团队边界**，不是越细越好。
- **🚫 把单据层次当成跨域关系**：订单头/行拆成两个对象 + 一条关系。→ 单据是**一个整体**，层次用嵌套复合属性表达（本平台已按此建模）。

## 8. 落地演进路径

{{FIG:roadmap}}

- **P0 · 核心内核**：先把客户/供应商/商品/组织/员工 + 参照数据定义好，约定共享接口。**1 个核心 namespace**。
- **P1 · 首个领域**：挑一个高价值域（如财务）建本体，**引用**核心；用 O3 灌真实数据；跑通 Search-Around。**core + 1 domain**。
- **P2 · 多域联邦**：横向扩销售/供应链/HR，各域独立发布，跨域链路打通。**core + N domains**。
- **P3 · 治理与联邦查询**：分域权限（O6）、版本发布、跨域联邦查询、血缘与影响分析。**governance**。

**不要一次建大**——先"核心 + 一域"跑通闭环，验证价值，再联邦扩张。

## 9. FAQ

**Q：多租户（每个客户企业）怎么办？**
A：租户隔离是**物理层**的事（`db-per-tenant`），与"逻辑单一本体"正交。每个租户拥有同一套本体**结构**的独立实例数据。

**Q：物理上非要一个大库吗？**
A：不。逻辑单一 ≠ 物理单库。可以 `schema-per-domain` 甚至跨库，只要**语义层（本体定义）统一**、跨域引用能解析即可。

**Q：核心域变更会不会牵动所有领域？**
A：会有影响，所以核心**从严准入 + 版本化发布 + 影响分析**。这正是"核心要薄"的原因——薄核心的变更面天然小。

**Q：领域之间要不要直接依赖？**
A：**优先经核心中转**（都引用 `Core.Customer`），减少领域两两耦合。确需领域直连时，用明确的关系类型，并纳入治理。

**Q：和微服务/Data Mesh 什么关系？**
A：高度一致。领域本体 ≈ Data Mesh 的"领域数据产品"，核心域 ≈ 共享的"多边治理"。本体额外提供了**统一语义层 + 可连接对象图**，是 Data Mesh 缺的那块"语义粘合剂"。
