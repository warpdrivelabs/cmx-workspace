§0结论速览

财务报表平台不是一个"新系统"，而是既有元数据平台的第三种建模对象。DOC 建模"业务单据"、DCT 建模"数据字典"，本方案新增 RPT 建模"报表"。三者共用同一条流水线：设计期 JSON 定义 → 模型中心编译建物理表 → tokio-postgres 并行装载 → ZmcDataSet 零拷贝列式管线 → 四区工作台渲染。报表所需的三样独有能力——Excel 式表样、灵活取数公式、多组织汇总合并——以最小增量挂接在这条链路的对应环节上。

一句话架构

核心洞察
报表 = 表样（grid） + 取数（formula → dataset） + 组织维度（rollup/consolidation）。表样是静态排版，取数是把单元格绑定到"从某些物理表按某些维度聚合出一个数"，组织维度是把同一套取数在组织树上复制并相加。三者中只有"取数"触及数据，而取数的底座——按维度从 cv_*/cf_* 表聚合——正是 ZmcDataSet 管线已经在做的事。报表引擎不自己读数据库，它把公式翻译成 DOC/DCT 已有的查询。

§2目标 · 非目标 · 设计原则

✓ 目标（本方案覆盖）

  • 自定义表样：任意行列、合并单元格、表头/表体/表尾、字体边框对齐等排版属性，所见即所得。
  • 灵活取数公式：单元格绑定取数公式，可视化配置"从哪张表、按哪些维度过滤、取哪个度量、做何聚合"。
  • 跨系统取数：财务、销售、HR、库存等不同域/应用的物理表，统一寻址取数。
  • 取数函数可扩展：内置财务函数库（期初期末/发生额/余额等）+ 用户自定义函数注册。
  • Excel 式操作：公式栏、单元格引用（B3、区域 B3:B10）、填充、函数向导，贴近会计习惯。
  • 数据落地：报表结果入库，可查历史、可留版本快照、可作为下游数据源。
  • 表间取数：一张报表引用另一张已落地报表的单元格（如利润表净利润带入资产负债表未分配利润）。
  • 多组织：模板跨组织共享；按组织树汇总（管理合并）；按法定口径合并（含抵消）。

✗ 非目标（本期不做 / 另案）

  • 通用 BI / 自助分析（Ad-hoc OLAP）：本方案面向"格式固定、口径固定"的法定与管理报表，不是拖拽式多维分析看板（那是 flexible-combination 的方向）。
  • 图表可视化引擎：柱图/饼图等留作报表输出的后续渲染层，先把"数"算准落地。
  • 完整 Excel 兼容：不追求 100% 复刻 Excel 全部 400+ 函数与 VBA；只做财务报表必需子集 + 可扩展入口。
  • 实时流式报表：报表是"某期间某时点"的快照式产物，非实时流。
  • 合并抵消的全自动推断：抵消规则需人工配置内部交易对手关系，引擎执行但不臆测。

设计原则

  1. 报表是第三类元数据，不是新孤岛。 一切能落到"metaKind:RPT + 走既有流水线"的，绝不新起炉灶。判据：若某能力 DOC/DCT 已有，报表只允许"加分支/加参数"，不允许 fork。
  2. 取数引擎不碰数据库，只生成查询。 公式编译的终点是一个 ZmcDataSet 查询描述，交给既有 DOC/DCT 装载底座执行。引擎层零 SQL 字符串拼接、零直连。
  3. 模板与实例严格分离。 表样+公式=模板（组织无关、可共享）；数据=实例（模板×组织×期间）。这是"多组织共享/汇总/合并"能成立的前提。
  4. 声明式优先。 表样、公式、数据集、抵消规则全部是 JSON 定义，可版本化、可 diff、可跨环境迁移，与 DOC/DCT 定义同库同管。
  5. 落地即契约。 报表一旦计算落地，其单元格值就是稳定的对外数据源，下游（表间取数、汇总、审计）依赖它，故必须有版本快照与留痕。
  6. 组织维度正交。 组织不进模板、不进公式，只在"实例化"和"汇总/合并"两个环节介入，保证同一模板在任意组织复用。

§3领域模型：模板 / 实例 / 单元格

在写任何结构之前，先把三个概念钉死：报表模板（组织无关的表样+公式）、报表实例（模板在某组织某期间的一次计算结果）、单元格（表样的最小单位，可以是文字、取数、计算或引用）。整个平台就是围绕这三者运转。

3.1 报表模板 vs 报表实例

📄 报表模板 Template（设计期产物）

一份 metaKind:RPT 的 JSON 定义。包含：

  • 表样 grid：几行几列、合并格、样式
  • 单元格 cells：每格的类型与公式
  • 数据集 datasets：取数指向哪些物理表
  • 参数 params：出表时要用户填的（期间、组织由上下文给）
组织无关
模板里绝不写死组织。"取本组织本期科目 1001 余额"——"本组织"是实例化时注入的上下文变量 @org，不是常量。这是共享的前提。

📊 报表实例 Instance（运行期产物）

模板 × 组织 × 期间 × 一次计算 = 一个实例。落地为 cr_report_instance 一行 + cr_cell_value 若干行。

实例主键 = tpl_id 资产负债表模板 + org_id 华东子公司 + period 2026-06 + scope single｜rollup｜consol

同一模板可派生无数实例：不同公司、不同月份、单体/汇总/合并口径各一份，互不干扰，可对比可追溯。

T
模板（设计一次）：资产负债表.rpt.json —— 61 行、若干取数格、组织无关
×
笛卡尔展开：模板 × {华东,华南,总部} × {2026-05,2026-06} × {单体,汇总}

3.2 单元格坐标系与区块

报表本质是一张二维单元格矩阵，坐标沿用 Excel 习惯：列 A/B/C…、行 1/2/3…、单元格 B3、区域 B3:D10。会计人员零学习成本。每个单元格有一个 cellType：

cellType含义示例求值方式
text静态文字（表头、项目名、行次）"货币资金"、"资产负债表"常量，不求值
fetch 取数格从物理表取数（本方案核心）=QM("1001") 取科目期末余额编译为聚合查询下推 DB
calc纯单元格算术（不碰 DB）=B3+B4-B5、=SUM(B3:B10)拓扑序内存求值
ref 引用格表间取数（引另一报表实例）=RPTREF('利润表','净利润')读 cr_cell_value
param参数回显（期间、编制单位）=@period、=@org.name上下文注入

区块（Block）：给坐标赋予业务语义

裸坐标（B3）对人不友好。模板可把矩形区域命名为区块并打标签，公式与样式按区块批量作用，也让"表头/表体/表尾"可被识别（打印分页、多组织汇总时"仅表体参与相加"）：

"blocks": [ { "id": "title", "range": "A1:F1", "role": "header", "merge": true }, { "id": "colhead", "range": "A2:F2", "role": "header" }, { "id": "body", "range": "A3:F60", "role": "body", "rollupSummable": true }, { "id": "footer", "range": "A61:F61", "role": "footer" } ]
对应既有概念
区块的 role/rollupSummable 与 DOC 里字段的 dimType/agg 是同一种设计手法——用元数据标注"这块数据在聚合时如何参与"。多组织汇总时，只有 rollupSummable:true 的取数格逐格相加，表头文字与合计公式不加（合计在相加后重算）。

3.3 扩展格：Excel 式动态展开

财务报表常有"明细行数不定"的场景——销售明细表、库存明细表、辅助核算余额表，行数取决于数据。Excel 靠人手拖动，报表平台靠扩展格（expand cell）：模板里画一行模板行，声明"沿某数据集的某维度纵向展开"，计算时按实际维度值克隆成 N 行。

// 模板第 5 行声明为扩展行：每个存货类别展开一行 "expands": [ { "id": "inv_rows", "anchorRow": 5, // 模板行（样式/公式的样板） "direction": "down", // down 纵向 / right 横向（如按月份铺 12 列） "overDataset": "inv_balance", // 沿哪个数据集展开 "byDimension": "category_id", // 每个不同维度值一行 "sort": "category_code asc" } ] // 扩展行内公式用 @row 指代"当前展开维度值" A5 = "=@row.category_name" // 类别名称 C5 = "=SUMQTY(@row.category_id)" // 该类别数量，取数按当前行维度过滤

横向扩展（direction:right）用于"按 12 个月/4 个季度平铺列"，本质相同。扩展是纯排版层能力，不改取数与落地模型——展开后的每格仍是普通 fetch/calc 格。

3.4 组织 / 期间 / 参数维度

报表实例由若干上下文变量确定。这些变量在模板里以 @ 前缀引用，实例化时注入：

上下文变量来源作用关联字典
@org工作台当前组织 / 汇总遍历取数的组织过滤、编制单位显示acct_entity（组织机构字典）
@period用户选择会计期间过滤（发生额、期末余额）fiscal_period
@currency参数 / 组织默认本位币 vs 原币，折算currency
@scope出表口径选择single 单体 / rollup 汇总 / consol 合并—
@params.*模板自定义参数如"是否含未过账"、"科目级次"各自绑定
为什么组织必须是变量而非模板字段
若把组织写进模板，则"华东资产负债表"和"华南资产负债表"要各存一份模板——违背"同一张表跨组织共享"。把 @org 作为注入变量，一份模板服务全集团，且"汇总"就退化成"对同一模板遍历组织树、把结果相加"，"合并"退化成"汇总再叠抵消"。组织正交是整个多组织能力的地基。

§4RPT 报表元数据结构

报表模板是一份 *_rpt_meta_v1.json，与 *_doc_meta_*.json、*_dct_meta_*.json 同目录、同存储机制、同 /api/definitions/* 入口。顶层 metaKind:"RPT"，可引用 base_rpt_meta_v1.json 复用通用字段集（编制单位/期间/审核状态等报表页眉字段）。

4.1 metaKind:RPT 顶层结构

4.3 datasets 取数数据集

取数格不直接写"从哪张表"，而是引用一个命名数据集。数据集是"物理表 + 可取度量 + 可用维度"的声明，把"表在哪、字段叫什么"与"公式怎么写"解耦——公式只认业务语义（科目、期末），数据集负责映射到物理列。这正是复用三元定义 dimType/refDict 的地方。

§5取数公式引擎

这是报表平台的心脏。用户要的"灵活取数"落到实处，就是：一条会计师能读懂的公式，被解析成 AST，再编译成一个按维度聚合的 ZmcDataSet 查询，下推到对应物理表执行。公式层只谈业务语义，物理细节全由数据集（§4.3）承接。引擎自己不写 SQL 字符串、不直连数据库。

5.1 公式语言与解析

公式是"Excel 语法 + 财务函数"的混合体。三种记号：单元格引用（B3、C3:C29）、算术运算符（+ - * / ()）、函数调用（QM('1001')）。解析产出标准 AST：

C3 fx =QM('1001', '2026-06') + QM('1002', '2026-06')
// 解析为 AST（引擎内部表示） Add( Call("QM", [Str("1001"), Str("2026-06")]), // 取数节点 → 待下推 DB Call("QM", [Str("1002"), Str("2026-06")]) ) // 节点分两类： // ① fetch 节点（QM/FS/SUMQTY...）→ 触达数据库，交 FetchPlanner 规划 // ② 纯算子（Add/Sub/CellRef/SUM...）→ 拓扑序内存求值
实现取向
公式解析器是小型 Pratt/递归下降解析器（几百行 Rust），无需引入完整脚本引擎。函数名大小写不敏感，参数支持字面量、单元格引用、上下文变量 @period。AST 缓存在模板编译产物里，运行期不重复解析。

5.2 内置财务函数库

取数函数分两族：取数函数（触达 DB，返回一个聚合值）和计算函数（对已有单元格值做运算，纯内存）。下面是财务报表必备的内置集，均通过函数注册表登记，每个函数声明它编译成什么样的聚合查询：

取数函数（fetch，下推 DB）

QC(account, [period], [dim...])科目期初余额。→ 对 gl_balance 按 account 过滤、取 begin 度量、sum
QM(account, [period], [dim...])科目期末余额（最常用）。→ 取 end 度量
JE(account, dir, [period])发生额。dir=D借方/C贷方/DC净额。→ 取 debit/credit
LJ(account, dir, [period])本年累计发生额。→ period 展开为年初至今区间
FS(account, dir, [period])科目对方发生额（对方科目分析）
SUMQTY(dim..., [ds])数量合计（库存/数量金额核算）。→ 取 quantity 度量
DGET(ds, measure, {filters})通用取数（万能）：任意数据集+度量+维度过滤，可视化配置的底层形态
CFITEM(item, [period])现金流量项目金额。→ 按 cashflow_item 维度聚合明细

计算/聚合函数（calc，纯内存）

SUM / AVG / MAX / MIN / COUNT(range)区域聚合，如 SUM(C3:C29)
IF(cond, a, b) / IFS(...)条件取值（如余额方向判断）
ROUND / ABS / MAX / MIN数值处理、进位、取绝对值
RPTREF(report, cell, [period])表间取数（§7.3），读另一报表实例
PY(cell) / PP(cell)同格上年同期 / 上期值（自动切 @period 重算或读快照）
RATE(a, b) / GROWTH(a, b)占比、增长率（管理报表常用）
"取数函数可自定义"的本质
每个取数函数不过是"对某数据集，取某度量，施加某组维度过滤，做某聚合"的一个命名快捷方式。QM('1001') ≡ DGET('gl_balance','end',{account:'1001', org:@org, period:@period})。所以"自定义取数函数"= 用户用 DGET 的能力封装一个业务别名。引擎只需认识 DGET 这一个原语，其余全是它的宏展开（§5.4）。

"从财务、销售、HR、库存等多个系统取数"在本架构里不是难题——因为所有系统的物理表都由同一个模型中心建在同一套库里，且跨 DAM 引用（domain/application/module 三段寻址）机制已存在。报表取数跨系统，就是数据集的 source 指向不同的域：

公式作者看不到"系统"这个概念，只看到数据集名（exp_by_dept、hr_headcount）。系统归属被封装在数据集的 source.domain 里。引擎按 domain 把取数分组，交给 tokio-postgres 并行执行——同库不同 schema 直接查，未来若某系统独立部署，只需数据集 source 增加连接标识，公式与引擎零改动。这正是 fico-ws 当年预留的"凭证服务器与元数据服务器分离时只改 service 配置"的同款解耦。

5.4 自定义取数函数

三个层次满足"取数函数可自定义"，由易到难、由配置到代码：

1数据集别名（零代码，配置级）
在模板 datasets 里定义新数据集，公式用 DGET('新数据集', ...) 即可。覆盖 90% 场景——"从哪张表取、能取哪些度量"都是配置。
2函数宏（低代码，声明式）
在函数注册表登记一个"宏函数"，声明它如何展开为 DGET。例：定义 费用(科目,部门) = DGET('exp_by_dept','end',{account:$1, dept:$2, org:@org, period:@period})。会计用中文函数名，引擎展开求值。宏定义本身是 JSON，可挂在租户/应用级共享。
3WASM 插件函数（全代码，沙箱）
复杂逻辑（如特殊税额计算、跨表勾稽、外部口径换算）写成 WASM 插件，通过既有 cmx-plugin 沙箱注册为函数。引擎在求值到该函数节点时，把参数与取数结果传入插件，取回标量。沙箱隔离、热插拔、多语言（Rust/AssemblyScript）。

5.5 取数底座：编译为 ZmcDataSet 查询

取数节点的终点，是构造一个与 DOC/DCT 查询同构的查询描述，交给既有装载底座。以 QM('1001') 为例：

1
宏展开：QM('1001') → DGET('gl_balance','end',{account:'1001', org:@org, period:@period})
2
绑定上下文：@org→华东 entity_id、@period→'2026-06'，得到具体过滤条件
3
查数据集：从 gl_balance 数据集查到 measure end→物理列 end_balance、维度 account→account_code（层级维度自动展开为科目区间）
4
构造查询描述：{table:cv_gl_balance, select:sum(end_balance), where:[account_code∈子树, entity_id=华东, period='2026-06', doc_status='posted']}
5
下推执行：交 tokio-postgres 并行执行 → ZmcDataSet 列式结果 → 取标量回填单元格 C3
与 DOC 装载同构、可直接复用的部分
第 4~5 步产出的"查询描述 + 列式结果解码"与 DOC 的 DocQuery / build_layer_select / ZmcDataSet 完全同一套。取数引擎只负责把公式翻译到第 4 步的查询描述；从查询描述到数据库到列式结果，一行新 DB 代码都不写，复用 cmx-database-pg + cmx-rowsource。层级科目维度展开为"科目子树 code 集合"，与 DCT 自分级懒下钻 WHERE key=ANY($ids) 是同一手法。

§6报表计算引擎

计算引擎接过一张模板 + 上下文（组织/期间/参数），产出全部单元格的值。核心是三步：建依赖 DAG → 规划取数（合并+并行下推）→ 拓扑序求值。这是 RPT 相对 DOC/DCT 唯一"全新"的一块引擎逻辑，但它调用的下层（DB、列式管线）全是既有的。

6.1 依赖 DAG 与拓扑求值

单元格之间由公式形成有向依赖：C30=SUM(C3:C29) 依赖 C3…C29；C3=QM('1001') 依赖取数结果（外部输入，无前驱）。把全部单元格连成有向无环图，拓扑排序后逐层求值——上游先算，下游后算。

取数格（DAG 的源，无前驱） 计算格（依赖上游） C3 = QM('1001') ──┐ C4 = QM('1122') ──┤ ... ├──▶ C30 = SUM(C3:C29) ──┐ C29 = QM('1601') ──┘ ├──▶ F61 = C30 + C45 （资产总计） F3 = QM('2001') ──────▶ F30 = SUM(F3:F29) ──┘ （负债+权益总计，用于平衡校验）
环检测
建 DAG 时若发现环（A 依赖 B、B 依赖 A），立即报错并高亮涉及单元格——设计期就拦住，避免运行期死循环。复用错误码库输出 violations，前端在网格上标红。
增量重算
编辑态改一个格，只需重算其下游子图（DAG 可达闭包），非全表重算——与 Excel 的依赖重算体验一致。运行期整表出表则一次全算。

6.2 取数下推 · 批量合并 · 并行

一张报表可能有几十上百个取数格。若每格发一条 SQL，会造成 N+1 查询风暴。FetchPlanner 在求值前把所有 fetch 节点收集起来，按"同数据集 + 同维度组合"归并成尽量少的批量查询：

1
收集：DAG 里所有 fetch 节点（如 60 个 QM，散落各行）统一收集，此刻还没查库
2
归并：同属 gl_balance、同 @org/@period、只是 account 不同的 60 个取数 → 合并为一条 WHERE account_code = ANY([...60个]) GROUP BY account_code 的批量查询
3
并行：不同数据集（gl_balance / sales / hr）的批量查询用 tokio-postgres 并行发出——正是并行 DB 层的主场
4
回填：ZmcDataSet 列式结果按 account_code 建索引，散射回各自单元格
// 朴素做法：60 格 × N 系统 = 上百条 SQL（慢、压库） // FetchPlanner 后： gl_balance: 1 条 SELECT account_code, sum(end_balance) ... WHERE account_code=ANY($1) GROUP BY 1 sales: 1 条 SELECT ... hr: 1 条 SELECT ... └─▶ 3 条查询并行 → 全表取数完成
这正是列式 + 并行架构的价值兑现点
"一张报表 = 少数几条批量聚合查询 + 并行" 把报表计算从"应用层循环取数"降为"数据库聚合一次成型"。归并键（同数据集同上下文维度）→ ANY($ids) 谓词 → 列式返回，三者都是既有 DOC/DCT 装载已验证的模式。报表引擎的性能上限由此锚定在数据库聚合能力上，而非应用层。

6.3 勾稽校验与平衡检查

报表算完要能自检。checks 段声明勾稽规则，与 DOC 的 validationRules 同一引擎、同一错误码库、同 level=error/warning 语义。求值完成后逐条校验，不平则弹专业对话框（复用 cmx-message-dialog + presentDocError）：

"checks": [ { "code":"bs_balance", "level":"error", "expr":"F61 == C61", // 资产总计 = 负债及权益总计 "message":"资产负债表不平衡：资产总计与负债权益总计不相等" }, { "code":"pl_tie", "level":"error", "expr":"RPTREF('利润表','净利润') == PP('未分配利润增额')", "message":"利润表净利润与资产负债表未分配利润变动勾稽不符" }, { "code":"cf_tie", "level":"warning", "expr":"现金净增加额 == 期末现金 - 期初现金", "message":"现金流量表勾稽差异，请核对" } ]

勾稽规则本身也可跨报表（RPTREF），这让"三大报表勾稽"（资产负债表↔利润表↔现金流量表）成为声明式规则，而非硬编码。

§7数据落地：cr_* 报表表

报表算完的结果必须入库，理由有三：① 历史可查（不必每次重算）；② 作为下游数据源（表间取数、汇总、合并都读它）；③ 审计留痕（谁在何时用何口径出的表）。落地模型由模型中心 compile_rpt 建三张 cr_* 物理表，与 cv_*/cf_* 同构、同铸号、同校验。

7.1 三张核心表

cr_report_instance · 报表实例头
一次出表一行。主键 = 铸号 bigint。列：tpl_id / tpl_version / org_id / period / scope(single|rollup|consol) / currency / status(draft|final|archived) / calc_at / calc_by / param_json / check_result。唯一约束 (tpl_id, org_id, period, scope) 保证同口径不重复。
cr_cell_value · 单元格值（报表数据主体）
一个实例的每个"有值单元格"一行（稀疏存储，text/空格不入库）。列：instance_id / cell_addr(如 'C3') / row_no / col_no / block_id / num_value(decimal) / str_value / formula_snapshot / drill_key(下钻回溯键)。这是表间取数、汇总、合并的读取对象。
cr_report_snapshot · 版本快照
正式发布/归档时，把该实例的全部单元格值 + 模板版本冻结成一个不可变快照。列：snapshot_id / instance_id / seq / snapshot_at / operator / frozen_cells(列式二进制 或 明细行) / signature。用于对比、审计、监管报送留底。
为何拆三表而非一张宽表
报表格数不定、稀疏、模板会演进——宽表（每格一列）不可行。"实例头 + 单元格长表 + 快照"是标准的元数据驱动落地范式，与 DOC 的"单据头 + 明细行"同构。cr_cell_value 用 (row_no, col_no) 数值坐标便于范围查询与汇总时逐格对齐。

7.2 版本快照与留痕

报表有"编制中 / 已定版 / 已归档"生命周期，复用 DOC 的状态流思想（voucherStatusFlow 同款）：

draft ──计算/重算──▶ draft // 可反复重算，覆盖 cr_cell_value draft ──定版 finalize──▶ final // 写 cr_report_snapshot，锁定，下游可安全引用 final ──归档 archive──▶ archived // 监管报送留底，不可变 final ──重开 reopen──▶ draft // 需权限；产生新快照 seq，旧快照保留
落地即契约（呼应 §2 原则）
一旦 final，该实例单元格值就是稳定契约，表间取数/汇总/合并可放心引用。重开会生成新 snapshot seq，旧值永久留痕——满足"报表数据可追溯、监管可倒查"。铸号、乐观锁基线、409 冲突处理全复用 DOC save 的既有实现。

7.3 表间取数（报表引用报表）

用户明确要求"表间还可以取数"。落地后，一张报表可用 RPTREF() 读另一张已落地报表实例的单元格。典型链条：利润表.净利润 → 现金流量表补充资料 / 资产负债表.未分配利润。

D45 fx =RPTREF('利润表', '净利润', @period, @org)
1
解析引用：RPTREF 目标 = (报表编码=利润表, 单元格/命名项=净利润, period=本期, org=本组织)
2
定位实例：在 cr_report_instance 找到 (利润表模板, @org, @period, scope) 的 final 实例
3
读取值：从 cr_cell_value 取该实例"净利润"命名项的 num_value（若引用未定版实例 → 触发按需计算或报错，按配置）
4
跨报表连边：RPTREF 在 DAG 里连一条跨报表依赖边，出表调度按报表级拓扑序（先出利润表，再出资产负债表）
命名项优于裸坐标
表间取数应引用命名项（如 '净利润'）而非裸坐标（'D45'）——否则被引用报表调版式（插入一行），坐标漂移导致引用错位。模板可为关键单元格声明 name，RPTREF 优先按 name 解析。这与 §6.3 勾稽规则用命名项是同一考量。跨报表引用同样要做环检测（报表 A 引 B、B 引 A 报错）。

§8多组织：共享 / 汇总 / 合并

用户诉求"同一张表在不同组织机构间可以共享、可以汇总、可以合并"。这三个词在财务语境里是三件不同的事，绝不能混为一谈。本方案把它们统一架在"组织正交"（§3.4）这一地基上：模板组织无关 → 共享天然成立；实例带组织 → 汇总是遍历相加；合并是汇总再叠抵消。

8.1 三个概念的严格区分

概念是什么作用对象口径典型场景
共享 share一份模板给多个组织复用模板（设计物）—集团统一资产负债表格式，各子公司套用
汇总 rollup子组织实例逐格相加为父组织实例（数据）管理口径事业部合计、区域合计、集团管理报表
合并 consolidation汇总 + 抵消内部交易实例（数据）法定口径合并资产负债表/利润表（对外披露）
一句话关系
共享是模板层（一对多复用），汇总与合并是实例层（多对一聚合）。且 合并 = 汇总 + 抵消。三者不是并列的三套机制，而是"组织正交"这一个设计的三种投影。想清这点，实现量骤减。

8.2 共享：模板组织无关

因为模板里组织是注入变量 @org（§3.4）而非常量，一份模板天然能被任意组织实例化——这就是"共享"，无需额外机制。共享的粒度与可见性借既有体系表达：

  • 跨 DAM 可见性：模板定义放在合适的 domain/app/module 层级，集团级模板放共享域，子公司专属模板放各自模块，复用"三元定义跨 DAM 引用"的可见性规则。
  • overlay 个性化：子公司若要在集团模板上微调（加一行本地指标），用既有 overlay 编译机制叠加，不改母版——与 DCT/DOC overlay 同款。
  • 组织适用范围：模板可声明 applicableOrgs（组织树某节点及其子树），限定哪些组织可实例化。

8.3 汇总 rollup（管理口径）

汇总 = 沿组织树，把子组织的同模板实例逐格相加得到父组织实例。这直接类比 DOC 的 aggregations 上卷（明细→分录→凭证头），只是这里沿的是组织树而非单据层级。

// 组织树 集团总部 ├─ 华东大区 ────┬─ 上海子公司 BS 实例(2026-06, single) │ └─ 杭州子公司 BS 实例(2026-06, single) └─ 华南大区 ────── 广州子公司 BS 实例(2026-06, single) // rollup：华东大区实例 = 上海 ⊕ 杭州（逐格） 华东.C3 = 上海.C3 + 杭州.C3 // 货币资金逐格相加 华东.C30 = 上海.C30 + 杭州.C30 // 但合计格：相加后按公式重算更稳妥（见下）
只加"可加格"
逐格相加只作用于 rollupSummable:true 的取数格（§3.2 区块标记）。文字格不加；合计/计算格相加后重算（先加子公司的明细格，父公司合计格用自身公式基于已相加的明细重算），避免"率类指标"（如毛利率）被错误相加。这与 DOC "measure 才 sum、attribute 不 sum" 完全一致。
两种实现路径
① 值汇总：读子实例 cr_cell_value 逐格相加（快，依赖子实例已落地）。② 源汇总：把 @org 直接绑定为"组织子树集合"，取数 SQL 一次 WHERE entity_id = ANY(子树) 聚合（一步到位，无需子实例先落地）。默认①用于报表体系，②用于即时汇总。②正是数据集 bindContext:@org 从"单值"扩到"集合"，SQL 层零改。

8.4 合并 consolidation（法定口径）

合并 = 汇总 + 抵消分录。子公司间的内部交易（内部购销、内部往来、母对子投资 vs 子公司权益）在集团视角不存在，必须抵消。抵消建模为一类特殊的抵消数据集，其值参与合并逐格运算：

"consolidation": { "eliminations": [ { "id": "intercompany_ar_ap", // 内部往来抵消：应收↔应付 "rule": "pair", "dataset": "ic_transactions", // 内部交易台账（标记 counterparty_org） "match": ["partner_org", "contract_id"], // 内部对手 + 合同配对 "eliminate": { "debit":"1122应收", "credit":"2202应付" } }, { "id": "equity_investment", // 长期股权投资 vs 子公司所有者权益抵消 "rule": "equity", "parentHolding": "invest_ledger", "subEquity": "sub_equity" }, { "id": "unrealized_profit", // 内部未实现损益（存货/固定资产） "rule": "custom", "fn": "wasm:consol-lib@2.0/unrealized" } ], "minorityInterest": { "enabled":true, "cell":"少数股东权益" } // 少数股东权益 }
1
汇总：先按 §8.3 得到子公司合计（rollup 结果）
2
抵消：逐条 elimination 计算抵消金额（配对内部往来、投资权益对冲、未实现损益）→ 生成抵消列
3
合并值：合并 = 汇总值 − 抵消值，逐格；少数股东权益单列
4
落地：写 scope=consol 实例；抵消明细留痕（可倒查每笔抵消来源）
抵消需人工配置，引擎不臆测（呼应 §2 非目标）
内部交易对手关系（哪笔应收对应哪家子公司的应付）必须由业务标记（counterparty_org）或抵消台账提供。引擎负责按规则精确执行抵消与留痕，但不猜测未标记的内部交易。复杂抵消（未实现损益、递延所得税）走 WASM 插件（rule:custom），与 §5.4 自定义函数同一套插件机制。
共享/汇总/合并的复用账
共享 = 0 新机制（组织正交 + 既有 overlay/DAM 可见性）。汇总 = 逐格相加 + 复用 DOC agg 语义 + 复用 ANY(子树) 谓词。合并 = 汇总 + 抵消数据集（唯一较重的新增，但抵消规则声明式 + 复杂项走插件）。三大能力真正的新代码集中在"抵消引擎"一处。

1

9.3 计算服务与调度

运行期出表由 RptService 编排，支持三种触发：即时（用户点计算）、批量（月结一键出全部报表）、定时（调度到期自动出）：

RptService::compute(tpl_id, ctx{org, period, scope, params}) -> ReportInstance { 1. load RptMetaView + 编译产物（AST/DAG） // 走 /api/definitions 缓存 2. FetchPlanner::plan(DAG.fetch_nodes) // 归并取数 3. Loader::exec_parallel(queries) // tokio-postgres 并行 → ZmcDataSet 4. Engine::eval_topo(DAG, fetched, cell_refs) // 拓扑求值 calc 格 5. Checker::run(checks) // 勾稽校验 → violations 6. 月结批量出表 = 对 (报表集 × 组织树 × 期间) 笛卡尔并行调度，天然可并行；报表间有 RPTREF 依赖的按报表级拓扑序编排（先利润表后资产负债表）。

范例二：部门管理费用与人均（跨系统 + 扩展行）

// expands: 第 5 行按部门展开（overDataset:dept_list, byDimension:dept_id） A5 calc "=@row.dept_name" // 部门名（展开维度） C5 fetch "=DGET('exp_by_dept','end',{dept:@row.dept_id})" // 财务：该部门费用 D5 fetch "=DGET('hr_headcount','cnt',{dept:@row.dept_id})" // HR：该部门人数 E5 calc "=ROUND(C5/D5, 2)" // 人均费用（跨系统计算） C99 calc "=SUM(C5:C98)" // 费用合计（扩展区求和）
一套引擎，全部覆盖
八类报表没有一类需要"特殊引擎"。差异全部落在声明式配置（数据集指向 / 函数选择 / 维度过滤 / 扩展维度 / 勾稽规则）里。这正是"元数据驱动"的价值：新增一张报表 = 新写一份 JSON 模板，零后端代码。取数系统再多（财务/销售/HR/库存/…），也只是数据集 source 的 domain 不同。

§14落地阶段

分五个里程碑，每阶段可独立验证、可演示。先打通"单表单组织"最小闭环，再逐层加取数灵活性、落地、多组织。

M1
元数据 + 编译（最小骨架）2-3 周
定义 RPT schema（grid/cells/datasets）+ base_rpt_meta；compile_rpt 建 3 张 cr_* 表 + 台账；/api/definitions 支持 metaKind:RPT。产出：能存一份报表模板定义。
M2
公式引擎 + 单表取数4-5 周
公式解析器 + 内置函数库（QM/QC/JE/SUM…）+ DAG 求值 + FetchPlanner；单组织单期间从 gl_balance 取数出资产负债表。产出：/api/rpt/compute 能算出一张真报表。
M3
前端工作台 + 落地4-5 周
report-grid 组件 + 公式栏 + 函数向导；cr_* 落地 + 快照 + 下钻；四区工作台接入 report 菜单。产出：会计能在界面出表、看数、下钻、存档。
M4
跨系统 + 自定义函数 + 表间取数3-4 周
跨 DAM 数据集（销售/HR/库存）；函数宏 + WASM 自定义函数；RPTREF 表间取数 + 跨报表勾稽。产出：管理费用/销售/HR/库存报表可出，三大报表勾稽。
M5
多组织汇总 + 合并抵消4-6 周
rollup 逐格相加（值汇总 + 源汇总）；consolidation 抵消引擎（内部往来/投资权益/未实现损益）+ 少数股东权益；批量月结调度。产出：集团汇总报表、合并报表。
阶段独立可用
M2 结束即有"能算的报表"，M3 结束即有"能用的产品"，M4/M5 是能力扩展。每阶段都建立在前一阶段的可运行产物上，风险前置、价值早现。与 DOC/DCT 落地"先最小闭环、后加维度"的节奏一致。

§15关键决策与风险

关键决策（需产品/架构确认）

议题选项建议
公式语言自研 Excel 式 DSL / 嵌 Lua / 嵌 Rhai 脚本自研小 DSL：财务函数语义强、需编译期校验与取数下推，通用脚本引擎反而难约束取数下推与安全
取数下推粒度逐格一 SQL / FetchPlanner 归并归并（§6.2）：必选，否则大报表 N+1 压库
汇总实现值汇总（读子实例）/ 源汇总（ANY 子树）两者都要：报表体系用值汇总（可留痕对账），即时查询用源汇总
快照存储列式二进制 / 明细行 / 双写列式二进制（复用 msgpack），大报表省空间；关键报表可选双写明细便于 SQL 审计
非叶科目取数末级汇总 / 存末级+汇总双份科目层级维度自动展开为末级 code 集合再聚合（复用自分级下钻），避免重复计
报表版式变更坐标引用 / 命名项引用表间取数与勾稽强制命名项（§7.3），坐标仅内部用

风险与缓解

性能：大报表 × 多组织 × 月结
集团几百家组织 × 几十张报表月结，计算量大。缓解：①FetchPlanner 归并 + 并行；②组织树汇总可增量（子实例已算则父实例只加不重算）；③批量调度错峰 + 结果缓存；④列式聚合把重活压给 DB。架构本身（列式+并行）就是为此设计。
正确性：勾稽与抵消易错
财务报表错一分钱都不行。缓解：①声明式勾稽规则强制校验（§6.3），不平不让定版；②抵消明细全留痕可倒查（§8.4）；③下钻到底层单据验证（§10 drill）；④快照留底支持期间对比发现异动。
跨系统：数据口径/时点不一致
财务已过账、销售未结账，取数口径可能错位。缓解：①数据集 defaultFilters 显式声明口径（如仅 posted）；②取数带 as-of 时点；③报表实例记录各数据源快照时点，可复现。
易用性：会计不会写公式
DSL 再简单也有门槛。缓解：①函数向导 + 可视化取数配置（§11.3）零公式出表；②模板由报表设计师预制，会计只填参数出表；③内置标准报表模板库（资产负债表/利润表等开箱即用）。
总结
财务报表平台以 metaKind:RPT 作为第三类建模对象，复用既有"定义→编译→ZmcDataSet 装载→四区工作台"全链路，新增智力集中在公式引擎、DAG 求值、抵消引擎、report-grid 四处。用户的全部诉求——自定义样式、灵活取数、自定义函数、Excel 操作、数据落地、表间取数、多组织共享/汇总/合并——都在本架构里有明确落点，且大部分是既有能力的组合与延伸，而非从零发明。这与 DOC/DCT 的成功落地是同一套方法论。
