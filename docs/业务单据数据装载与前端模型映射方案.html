业务单据数据「装载 → 前端模型 → 编辑显示 → 回存」全链路方案

把某个已定义的业务单据（DOC）在 PostgreSQL 中的多层业务数据，端到端装入前端 CmxDataSet / CmxRowSet / CmxMasterSlave 模型，在 cmx-revo-grid / cmx-ui5-form 中编辑显示，并可再次存回后端数据表。

两条硬约束：（A）后端尽量零拷贝 · （B）传输到前端的数据包尽量小。

版本 v1 · 2026-07-03 纯方案 · 不改任何代码 基于源码实证 Lit 前端 · Rust/sqlx 后端

0一句话结论

后端 cmx-core::DataSet 与前端 CmxMasterSlave 是天生的结构孪生。 两者都是「schema/id + 扁平行 rows + 按名挂载的子数据集 children」的递归主从树。系统已就绪：单据元数据（voucherTables/voucherSchema/relations/aggregations）、DdlDialect 建表引擎、ResultConverter 把 PG 行装成 DataSet、Arc<Schema> 共享、前端 CmxDataSet 的列式序列化（exportColumnar/fromJSON）与零拷贝视图（CmxDataSetView）。

唯一缺口是：没有任何代码「按单据定义的 upper_id 层级，把多张物理表的扁平行组装成一棵嵌套 DataSet，再列式小包传前端；也没有把前端改动按层拆解回写各表」。本方案补上这条链路，并叠加零拷贝与小包两项优化——新增 2 个后端端点 + 1 套列式小包协议 + 1 个前端装配/拆解适配层，不改已有建表引擎、元数据存储、CRUD 宏。

1.2 必须新增的缺口

  1. 单据数据「装载」服务：读定义 → 按层生成参数化 SQL → 按 upper_id 组装嵌套 DataSet → 列式小包。现状 convert_postgres_rows 只产单层扁平 DataSet，主从嵌套需手动 Row::add_child，且无人按元数据自动做。
  2. 单据数据「回存」服务：接收前端 changeset（按层 inserted/updated/deleted），一个事务内逐层 upsert/delete；子表靠 upper_id = 父行 id 维系。现状只有单表 CRUD 宏与 WASM 裸 SQL。
  3. 小包 + 零拷贝传输层：现状行式 JSON、键名逐行重复、不跳 null、无压缩（RowRef 逐行 {field:value}，SKIP_NULL_IN_SERIALIZE=false，CompressionLayer 已编译未挂载）。

1.3 三个必须规避的现状坑

坑 A — 前端模型无脏标记 CmxRowSet 没有 _dirty/_isNew/_state，"脏"只体现为 row-changed/ds-row-added/ds-row-removed 事件流。→ 回存需在适配层自建 changeset 收集器（订阅事件）。
坑 B — DataSet 变更池不序列化 rds.rs 的 Serialize 只输出 id/schema/rows，inserted/updated/deleted 不过线。→ 回存协议要显式定义 changeset 字段，不能复用默认序列化。
坑 C — upper_id/层级从不进 DB 外键 compile_doc 生成的 upper_id 只是普通 nullable BIGINT 列，relations/level 不读、不建 FK。→ 层级关系由应用层（装载/回存服务）保证，不能依赖 DB 级联。

核心洞察：无阻抗直通 后端 DataSet 与前端 CmxDataSet 同构——两端都是 { schema/id, rows(扁平值), children(按名子集) }。因此「后端组装嵌套 DataSet → 列式序列化 → 前端 fromJSON 还原 → ms.setDataSet」是一条没有模型翻译损耗的直通路。

3业务单据元数据与层级模型（id / upper_id）

3.1 单据定义结构（DOC）

以 cmxfico_doc_meta_v1.json 为例，一份 DOC 定义的关键块：

// 4 层主从：L1 凭证批 → L2 凭证头 → L3 科目行 → L4 辅助行
{
  "docMeta": { "metaKind": "DOC", "version": 1 },
  "voucherSchema": {
    "schema": [
      [ { "id":"cv_batch",    "level":"L1", "levelName":"凭证批" } ],
      [ { "id":"cv_header",   "level":"L2", "levelName":"凭证头" } ],
      [ { "id":"cv_acc_line", "level":"L3", "levelName":"科目行" } ],
      [ { "id":"cv_aux_line", "level":"L4", "levelName":"辅助行" } ]
    ],
    "relations": [
      { "parent":"cv_batch",      "child":"headers",       "parentKey":"id", "childKey":"upper_id" },
      { "parent":"headers",       "child":"account_lines", "parentKey":"id", "childKey":"upper_id" },
      { "parent":"account_lines", "child":"aux_lines",     "parentKey":"id", "childKey":"upper_id" }
    ],
    "aggregations": [
      { "from":"cv_header.account_lines", "to":"cv_header", "field":"entered_dr", "toField":"total_dr", "agg":"sum" }
    ]
  },
  "voucherTables": [
    { "level":"L1", "tableName":"cv_batch", "fields":[ /* 本层特有字段 */ ],
      "documentFieldSets":[ "documentLevelFields", "documentTechnicalFields" ] }
  ]
}
  • 节点类型：单据 → 层/表(level) → 字段(field)。每个 voucherTables[i] 就是一层一张物理表。
  • 主从即多级树：这是主从（master-slave），与「细分/弹性组合 CTX」是两回事（flexible-combination-engine.js 已废弃为壳）。

3.2 层级身份字段（documentLevelFields）

"documentLevelFields": {
  "remark": "业务单据层级基础字段集:id(主键)+upper_id(上级单据主键,单层父指针)+line_no(行号)",
  "fields": [
    { "id":"id",       "dataType":"BIGINT", "nullable":false, "isPrimaryKey":1 },
    { "id":"upper_id", "dataType":"BIGINT", "nullable":true,  "dimType":"attribute" },
    { "id":"line_no",  "dataType":"INT",    "nullable":false, "dimType":"attribute" }
  ]
}
  • id：BIGINT 主键（isPrimaryKey:1）。
  • upper_id：BIGINT 父指针（可空，根层为空）。从扁平行重建树的唯一依据：child.upper_id === parent.id。
  • line_no：INT 行内序号。

3.6 后端 Rust 中如何访问这些元数据（现状：弱类型 JSON 透传）

单据元数据在后端不是 Rust 结构体，而是磁盘上的 JSON 文件。 后端把它当 serde_json::Value 读进来、用 .get("...") 逐字段取值。这正是本方案「缺口」的根源——后端对单据元数据是弱类型透传，没有 VoucherMeta/DocMeta 强类型，也没有任何代码遍历 voucherSchema.relations 的层级。

唯一入口：cmx_portal::definitions::store（实现在 crates/libs/cmx-model/src/definitions/store.rs）。元数据存放于 data/meta/definitions/<domain>/<app>/<module>/<file>.json（base 域特例为 .../base/<file>.json）。

函数作用返回
get_definition(&DefRef)读单个定义文件（原样 JSON）serde_json::Value
get_definitions_batch(&Value)批量读 + 一次性附带各定义引用的 base 字段集（去重）{ items, bases, basePaths, errors }
list_definitions(kind, domain, app, module)递归扫描列表（按 metaKind 分 DCT/DOC/BASE）Value
save_definition / set_default_version / delete_definition写 / 设默认版本 / 删（base 不可删）—

DefRef 是文件坐标：{ domain, application/app, module, file/id }。标准范例（model_center.rs，后端目前唯一真正读单据元数据的地方——编译成建表 TableDefine）：

// ① 读定义文件全文（弱类型 Value）
let r = DefRef { domain: Some(domain.into()), application: Some(app.into()),
                 app: Some(app.into()), module: Some(module.into()), file: Some(file.into()), id: None };
let doc = cmx_portal::definitions::store::get_definition(&r).await?;   // → serde_json::Value

// ② 读它引用的 base 字段集（domain = "base"）
let base_file = doc.get("baseDocMetaRef").and_then(|r| r.get("file")).and_then(|v| v.as_str());
let base = read_base(base_file).await?;

// ③ 用 .get(...).as_array()/.as_str() 逐字段访问，遍历 voucherTables → 每层一张表
let tables = doc.get("voucherTables").and_then(|v| v.as_array())?;
for t in tables {
    let table_name = t.get("tableName").and_then(|v| v.as_str()).unwrap_or("");
    if let Some(own) = t.get("fields").and_then(|v| v.as_array()) { /* 本层字段 */ }
    // documentFieldSets 引用 base 里的共享字段集：base["fieldSets"][name]["fields"]
    if let Some(sets) = t.get("documentFieldSets").and_then(|v| v.as_array()) {
        for s in sets { let fields = base_fieldset(&base, s.as_str()?); /* 展开合并 */ }
    }
}

现状要点

  • 合并 base 要自己做：一层完整字段 = 本表 fields + documentFieldSets 展开 base["fieldSets"][name]["fields"]。get_definitions_batch 顺带返回 base，省一次 IO。
  • 层级从不被读：compile_doc 只读 voucherTables 建表，voucherSchema.relations（upper_id 那套）没有任何 Rust 代码读过。

两处不足

  • 每次读磁盘、无缓存：get_definition 每次 read_json；list_definitions 每次 read_dir 递归遍历整树。装载会频繁读同一份定义。
  • 弱类型 .get().as_str() 满地散落：易错、无编译期保障、无补全。

3.7 改进一：定义访问缓存（与 §7 Arc<Schema> 缓存合并）

DocLoader/DocSaver 每次装载/回存都读同一份定义并解析层级——应加进程内缓存，键为 domain/app/module/file@version（版本取 docMeta.version），值为已解析的强类型元数据 + 各层 Arc<Schema>：

// 进程内缓存：docKey → Arc<解析后的单据元数据>
static DOC_META_CACHE: OnceLock<DashMap<String, Arc<DocMetaView>>> = OnceLock::new();

async fn load_doc_meta(domain,app,module,file) -> Result<Arc<DocMetaView>> {
    let key = format!("{domain}/{app}/{module}/{file}");
    if let Some(hit) = cache().get(&key) { return Ok(hit.clone()); }  // 命中：零磁盘、零解析
    // miss：get_definitions_batch（定义 + base）→ 解析为 DocMetaView → 建各层 Arc<Schema>
    let view = Arc::new(DocMetaView::parse(doc, base)?);
    cache().insert(key, view.clone());
    Ok(view)
}
  • 失效策略：save_definition/set_default_version/delete_definition 成功后按 docKey 逐出（或带版本号天然免失效——版本变则键变）。
  • 与 §7 合并：DocMetaView 内直接持有 Vec<Arc<Schema>>（每层一个），装载时 DataSet 直接引用，一处缓存同时服务「元数据解析」与「零拷贝 Schema 共享」两个目标。

3.8 改进二：强类型只读投影层（DocMetaView）

不改存储格式（仍是 JSON），只加一层 serde::Deserialize 投影，把「满地 Value.get()」收敛成一次反序列化。投影字段名与真实 JSON 逐一对齐（#[serde(default)] 容错缺失键）：

/// 单据元数据的只读投影（从 DOC 定义 JSON 反序列化；未知键忽略）
#[derive(Debug, Clone, Deserialize)]
pub struct DocMetaView {
    #[serde(rename = "docMeta")]    pub module_meta: ModuleMeta,
    #[serde(rename = "voucherSchema")] pub schema: VoucherSchema,
    #[serde(rename = "voucherTables")] pub tables: Vec<VoucherTable>,
    // 解析后自建（非 JSON 字段）：tableName → Arc<Schema>，供装载零拷贝
    #[serde(skip)]                     pub layer_schemas: HashMap<String, Arc<Schema>>,
}
#[derive(Debug, Clone, Deserialize)]
pub struct RelationDef {                       // ← 层级父子链强类型化（现状无人读）
    pub parent: String, pub child: String,
    #[serde(rename="parentKey", default="id_default")] pub parent_key: String,  // 默认 "id"
    #[serde(rename="childKey")]  pub child_key: String,                         // "upper_id" 或 "header_id"
}
#[derive(Debug, Clone, Deserialize)]
pub struct VoucherTable {
    #[serde(rename="tableName")]  pub table_name: String,
    #[serde(default)] pub fields: Vec<serde_json::Value>,          // 字段仍留 Value（属性多，按需取）
    #[serde(rename="documentFieldSets", default)] pub field_sets: Vec<String>,
}
收益 DocLoader 直接 view.schema.relations 拿父子键、view.layer_schemas["cv_header"] 拿该层 Arc<Schema> 装载零拷贝；RelationDef.parent_key/child_key 让「通用 upper_id」与「命名外键 header_id」两方言统一，不写死列名。字段级仍留 Vec<Value>（属性 30+ 且三端共享 schema），按需 .get()——强类型化只覆盖「层级骨架」，字段「血肉」仍透传，取得类型安全与灵活性的平衡。
落地归属DocMetaView + 缓存放在新增的 DocLoader 所在 crate（建议 cmx-biz 或新建 cmx-doc）；不改 definitions::store（它继续做纯 JSON 读写），投影层是它之上的消费者。

ColumnDefine { name, field_type: ft, is_primary_key: name==id_field,

4.3 建表执行（已就绪，additive-safe）

幂等、安全 PgTableDefineExecutor::create_or_upgrade_table：先建；已存在则内省 information_schema/pg_catalog 反查现表 → DdlDiff 增量 ALTER。DROP TABLE/COLUMN 只记录不执行，天然幂等。部署入口 deploy_stream（SSE 进度）。
建表物理形态 一份 4 层单据 = 4 张独立物理表，每张都含 id(PK) + upper_id(普通 BIGINT) + line_no + 本层字段。层级不建 DB 外键，由应用层维系（坑 C）。

4.4 建议：两条非破坏性 DDL 增强（可选）

不改引擎，仅在编译期给每层 TableDefine 追加索引（走现有 IndexDefine，additive，零风险）：

  • upper_id 普通索引：CREATE INDEX idx_<table>_upper ON <table>(upper_id) —— 子表 WHERE upper_id = ANY(...) 批量取子集时命中（装载性能关键）。
  • (upper_id, line_no) 复合索引（可选）：子行按 line_no 有序返回，免前端再排序。

5装载：DB → 后端 DataSet → 前端模型

5.1 后端 DocLoader（新增服务）

入参：{ db_id, domain, app, module, docFile, rootId?, filter?, page? }（filter 作用于根层，如按凭证号/期间/组织）。

算法（按层广度优先，父批量驱动子）：

1. 读定义：get_definition(docFile) → doc JSON；按 baseDocMetaRef 合并 base
2. 解析层序与父子键：schema 得 [L1..Ln]；relations 得每层 (parentKey, childKey)
3. 编译各层 Schema：voucherTables[i] 展开 documentFieldSets → cmx-core::Schema
      —— Schema 用 Arc 包裹并【按层缓存】（同一定义所有请求共享，见 §7）
4. 查 L1（根）：
      SELECT <L1列> FROM cv_batch [WHERE <filter>] [ORDER BY id] [LIMIT/OFFSET]
      → query_sql(db_id, None, sql, "cv_batch") → DataSet(schema=Arc<L1Schema>)
    收集 rootIds = [row.id ...]
5. 逐层下钻（i = 2..n）：
      parentIds = 上一层所有 id
      SELECT <Li列> FROM <tableI> WHERE upper_id = ANY($1) [ORDER BY upper_id, line_no]
        参数 $1 = parentIds（一条 SQL 取全部子行，避免 N+1）
      按 upper_id 分桶 → 对每个父行 pr：pr.add_child(childKey_i, 子桶DataSet)
6. 返回根层 DataSet（已是完整嵌套主从树）

为什么快

  • 一层一条 SQL + WHERE upper_id = ANY($ids)：整树最多 n 条查询，彻底避免 N+1，命中 §4.4 索引。
  • ANY($1) 数组绑定走参数化（DataValue::Array），注入免疫。

为什么省

  • 组装即 Row::add_child，复用 rds.rs 现成能力，产出即后端主从树。
  • Schema 共享：同层所有行、同定义跨请求共用一个 Arc<Schema>——零拷贝核心。

5A维度解析：单据列引用数据字典，如何显示 name/属性（不牺牲性能）

5A.0 问题定义

单据很多列存的是字典的 id 或 code（如 comp_unit_id=1000、gl_account_id="2221"），但界面要显示对应的名称或字典某属性。元数据已声明这层引用：

// 字段元数据里的引用三件套（真实存在）
{ "id":"gl_account_id", "dataType":"BIGINT",
  "refDict":"gl_account",   // 引用哪个字典
  "refField":"code",        // 用字典的哪个键匹配本列值（id 或 code）
  "displayField":"name" }  // 显示字典的哪个属性（name / 或任意属性）
朴素做法（后端 JOIN 字典）的性能陷阱 一张单据几十列引用十几个字典，每次装载都 LEFT JOIN 十几张字典表 × 多层 × 多行——JOIN 爆炸；且本系统字典条目当前多以 JSON 文件存（data/dict/entries/<dictId>.json），后端甚至没有可 JOIN 的 SQL 表，只能读文件循环匹配。逐行逐列查字典 = N×M 次点查，联机装载不可接受。
思路：解析值是"派生数据"，谁最省就放谁那 「把解析值存到关联表」是可行方案之一（下文 L2 伴生宽表），但不是所有场景最优。下面给一套分层组合：按「字典规模 / 变更频率 / 是否需服务端搜索排序」选层，用元数据 resolveStrategy 参数逐列控制，兼顾性能、通用性、可扩展性。同一单据不同列可用不同层。

5A.1 四层解析策略（决策矩阵）

层名称解析发生地name 存哪适用代价
L0前端整典缓存 + 本地映射（默认首选）前端不落库，前端内存 Map中小字典(≤数千)、多单据共用首次拉整典；改名要失效
L1装载期后端解析 → 派生列（瞬态）后端 DocLoader不落库，随包传 xxx__name大字典、单据少、要即显每次装载解析(有缓存则廉价)
L2伴生宽表（反范式落库）保存期写落库：<doc>_disp需服务端按 name 搜索/排序/导出冗余存储、改名要重刷
L3物化视图 / 触发器DB 维护落库：物化视图列超大数据量、name 稳定、重查询DB 运维复杂、刷新延迟

核心：多数列用 L0（前端 Map，零后端成本、零冗余）；只有「需要后端按 name 过滤/排序/分页/导出」的列才升到 L2 落库。逐列由元数据声明。

5A.2 元数据扩展（逐列声明策略，纯叠加）

{ "id":"gl_account_id", "refDict":"gl_account", "refField":"code", "displayField":"name",
  "resolveStrategy": "frontend",          // "frontend"(L0默认)|"backend"(L1)|"persist"(L2)|"view"(L3)
  "displayAs": "gl_account_id__name",     // 派生/落库列名（缺省 = <id列>__<displayField>）
  "displayFields": ["name","category"] }  // 可选：一列值带出字典多个属性（to attribute 通用化）
  • 通用性：displayField 单属性、displayFields 多属性（同时带 name+分类+助记码…），覆盖「to name / to code / to attribute」全部形态。
  • 可扩展性：新增引用列 = 加字段元数据选层，零代码。解析引擎读元数据驱动，不硬编码任何字典。

5A.3 L0：前端整典缓存 + 本地映射（默认，零后端 JOIN）

前端装载单据后收集所有 refDict，一次性批量拉全量条目（复用现成 POST /api/dict/batch-data，batch_data_endpoint 已支持一次多典），建 dictId → Map<key, entry> 缓存；渲染时用显示模板把 id → entry[displayField]。

// 装载后：一次批量拉全部引用字典（整典缓存，跨单据/跨行共用）
const dictIds = collectRefDicts(docMeta);            // ["gl_account","comp_unit",...]
const dicts   = await host.dictBatchData(dictIds);   // → { gl_account:[...], ... }
host.__dictCache = buildKeyMaps(dicts, docMeta);     // { gl_account: Map<code, {name,category}> }

// 渲染：CmxColumn 显示模板 id→name（组件已支持 cellTemplate/显示映射）
col.display = { kind:'dict', dictId:'gl_account', keyField:'code', labelField:'name' };
// 组件内：host.__dictCache['gl_account'].get(row.gl_account_id)?.name ?? row.gl_account_id

性能 & 小包

  • 字典整典只拉一次（非逐行点查），之后前端内存 O(1) 查表。零后端 JOIN、零逐值往返。
  • 单据包只传 id/code、不传 name（name 前端补），传输最小——契合 §8。字典包独立缓存、跨单据复用、版本协商增量。

失效 & 就绪度

  • 字典改动 → 版本号/updatedAt 变 → 前端按版本重拉该典（只重拉变的典，不动单据数据）。
  • batch_data_endpoint、cmx-dict-data-source.js、combo/列显示模板都已存在，L0 主要是"串起来 + 加缓存层"。

5A.4 L1：装载期后端解析 → 派生列（大字典、即取即显）

当某字典太大不宜整典下发（百万级科目/客户），但该列要随单据立即显示：DocLoader 装载时只对本页出现的 id 集批量解析，把 name 作为瞬态派生列塞进列式包，不落库：

DocLoader 装载 cv_header 后：
  收集本层某列去重 id 集：ids = distinct(rows[].gl_account_id)
  批量解析：SELECT code,name FROM cf_gl_account WHERE code = ANY($ids)   // 一次，非逐行
            （字典存文件时：读该典缓存 Map 批量取；见 §5A.6）
  回填派生列：row["gl_account_id__name"] = map[row.gl_account_id]
  列式包 columns 增列 "gl_account_id__name"（瞬态，前端直接显示，不参与回存）
  • 性能：每列一次 ANY($ids) 批量查（命中主键索引），非逐行 JOIN；配合 §5A.6 缓存可完全免 DB。
  • 小包权衡：派生列增大包体，故 L1 只给「大到不能整典下发」的少数列；能 L0 的仍走 L0（不进包）。
  • 不落库：派生列是"读时计算"，只出现在响应，ChangeSetCollector 忽略它（不回存）。

5A.5 L2：伴生宽表（反范式落库，服务端可搜可排）

当某些列的 name 需在后端参与搜索/排序/分页/报表导出（"按科目名模糊查""按客户名排序"），必须让 name 在库里可查——落一张与单据一一对应的伴生显示表：

-- 伴生宽表：与主表行一一对应(共享主键 id)，只存"解析出来的显示值"
CREATE TABLE cv_header_disp (
    id            BIGINT PRIMARY KEY,          -- = cv_header.id（一一对应，非新主键）
    upper_id      BIGINT,                      -- 冗余父指针，便于按树清理
    gl_account_id__name    VARCHAR(200),        -- 解析值：科目名
    comp_unit_id__name     VARCHAR(200),        -- 解析值：公司名
    comp_unit_id__category VARCHAR(64),         -- 解析值：公司分类（to attribute 通用化）
    _resolved_at  TIMESTAMPTZ DEFAULT now()    -- 解析时点（判过期）
);
CREATE INDEX idx_cvh_disp_acc_name ON cv_header_disp (gl_account_id__name);  -- 支持按名搜索/排序
  • 写入时机（复用 §6.4 保存链路）：DocSaver 保存主表行的同一事务内，对标 resolveStrategy:"persist" 的列解析 id→name 后 UPSERT 进 <table>_disp。装载时主表 LEFT JOIN <table>_disp ON id（一对一、走主键、极低代价，不是 JOIN 十几张字典表）连 name 取回。
  • 通用性：伴生表由元数据自动生成——扫描各层带 persist 的列，用 §4 的 DDL 引擎建 <table>_disp。加引用列 → 重 deploy → 伴生表自动加列（additive）。
一致性（字典改名）三策略（可配） ① 懒刷：装载时比对字典版本 > _resolved_at 则该行现解析并回写（读时自愈）。 ② 批刷：字典改名触发后台任务，按 refDict 反查所有引用它的 _disp 表批量更新（可离线/限流）。 ③ 不刷（快照语义）：单据要的就是"当时的名称"（历史凭证按当时科目名），过期即正确——ERP 常见。

代价：冗余存储 + 维护刷新——只给"真的要服务端按 name 检索/排序/导出"的列用，不是所有引用列都落库。

5A.6 L3 与后端字典缓存（超大数据 / 通用底座）

L3 物化视图

数据量超大、name 稳定、以查询为主时，用 PG 物化视图把「主表 + 伴生显示」物化，定期 REFRESH。属重查询/报表专用，运维成本高，按需启用。

后端字典缓存（L1/L2 公共底座）

无论字典存文件还是物理表，后端都应有 dictId → Arc<HashMap<key,entry>> 进程内缓存（与 §3.7 定义缓存同构，DashMap+版本失效）。L1/L2 解析都优先命中它，把"JOIN/查库"降为"内存查表"——"不牺牲性能"的公共保障。

5A.7 组合推荐与决策流程

对单据每个"引用字典的列"，按元数据 resolveStrategy 决定： ├─ 默认 frontend(L0)：字典中小、被多单据共用 → 前端整典缓存 Map，包里只传 id（最省，首选） ├─ backend(L1) ：字典超大、不宜整典下发、要即显 → 装载期 ANY($ids) 批量解析成派生列（不落库） ├─ persist(L2) ：要在后端按 name 搜索/排序/分页/导出 → 伴生宽表 <table>_disp，保存期写、装载期一对一 JOIN └─ view(L3) ：超大量 + name 稳定 + 重报表查询 → 物化视图，定期刷新 公共底座：后端字典缓存（内存 Map，版本失效）——L1/L2 解析都命中它，杜绝逐行查库。
为什么这套优于"全部落一张表" 性能：绝大多数列走 L0（前端 Map，零后端成本、包里不带 name 最小化传输）；只有少数"需服务端检索"的列才落库(L2)，避免全量冗余与全量刷新。 通用性：解析引擎读 refDict/refField/displayField/displayFields/resolveStrategy 元数据驱动，不硬编码任何字典；单/多属性、id/code 匹配全覆盖。 可扩展性：新增引用列 = 加元数据选层，零代码；伴生表由 DDL 引擎按元数据自动建/加列（additive-safe）。 一致性可选：L2 三策略适配"实时名称"与"历史快照名称"两类语义。
落地优先级先做 L0（覆盖 ~80% 列、纯前端 + 复用现成 batch-data，见 §11 阶段 1.5）→ 需服务端检索时再对特定列上 L2（复用 §6.4 保存链路 + §4 DDL 引擎）→ 超大场景才评估 L3。

6.4 后端 DocSaver（新增服务）：两种保存模式，参数控制

前端改完单据后，回存需支持两种模式，由请求参数 saveMode 控制：

模式saveMode语义前端传什么适用场景
增量更新"merge"（默认）按 changeset 精确 INSERT/UPDATE/DELETE最小 changeset（§6.3）常规联机编辑：保主键/审计、写入最小、可乐观锁
先删后插"replace"对涉及父行子树，先 DELETE 旧子行，再全量 INSERT 当前子行整棵（或整子树）当前全量批量重算/导入/覆盖式提交：前端难精确 diff，图省心与绝对一致
两模式共性都遵守：同一 txn_id 单事务 + 按 relations 拓扑序（插/更父先、删子先） + 参数化 execute_sql_with_datavalues。差异只在"如何把前端状态落到每层表"。

模式一：增量更新（merge）

txn = begin(db_id)
try:
  for 每层 layer（父先，L1→Ln）:
    for row in changes[layer].inserted:                 // 幂等 UPSERT
      exec(txn, "INSERT INTO <t>(id,upper_id,line_no,<cols>) VALUES($1,...)
                 ON CONFLICT(id) DO UPDATE SET ...", [...])
    for row in changes[layer].updated:                  // 只更变更列
      exec(txn, "UPDATE <t> SET <col=$..> WHERE id=$1", [...])
  for 每层 layer（子先，Ln→L1）:                          // 删子先，不留孤儿
    if changes[layer].deleted:
      exec(txn, "DELETE FROM <t> WHERE id = ANY($1)", [deletedIds])   // 批量删
  commit(txn); return { ok:true, mode:"merge", affected:{...}, idMap }
except e: rollback(txn); return { ok:false, error:e }
  • 保主键与审计：更新走 UPDATE，行 id 不变，update_time/update_by 连续。
  • 写入最小：只动 changeset 里的行/列。
  • 可乐观锁（可选）：UPDATE ... WHERE id=$1 AND version=$old，rows_affected=0 ⇒ 并发冲突，回滚报错。
  • 依赖前端 changeset 准确（坑 A/§6.3）——唯一前提。

模式二：先删后插（replace）

txn = begin(db_id)
try:
  # 1) 先删：按 rootId 圈定的整棵子树，自底向上删（子先父后）
  for 每层 layer（子先，Ln→L1）:
    # 沿 upper_id 链把"属于 rootId 这棵树的本层旧行"全删掉
    exec(txn, "DELETE FROM <t> WHERE upper_id = ANY($parentIds_of_this_layer)")
    # 根层：DELETE FROM <L1> WHERE id = ANY($rootIds)
  # 2) 再插：按 snapshot 自顶向下全量 INSERT（父先，保证子 upper_id 有父）
  for 每层 layer（父先，L1→Ln）:
    for row in snapshot[layer]:
      exec(txn, "INSERT INTO <t>(id,upper_id,line_no,<cols>) VALUES($1,...)", [...])
  commit(txn); return { ok:true, mode:"replace", idMap }
except e: rollback(txn); return { ok:false, error:e }
删除范围界定（关键）replace 必须由 rootId（+层级 upper_id 链）严格圈定"要覆盖的那几棵树"，DELETE 只作用于这些根的子孙，绝不 DELETE FROM <t>（无 WHERE）误删他人单据。先查各层 WHERE upper_id IN (上层被删 id) 得本层待删 id 集，逐层下推。
  • 前端简单：不需精确 diff，把整棵（子）树当前状态发过来即可，无遗漏风险。
  • 代价：行 id 与审计连续性中断（除非 snapshot 保留原 id 做"删同 id 再插同 id"）、写放大、并发下整树覆盖易冲掉他人改动——故 replace 建议配合悲观锁或"我方独占编辑"语义。

两条硬护栏（两模式共用）

  • 删除边界：DELETE 一律带 WHERE（id=ANY(...) 或 upper_id=ANY(...)），永不无条件删表；replace 删除集必须由 rootId 树形圈定。
  • id 生成：新增行 id 建议后端生成，保存后回 idMap（前端临时 id → 后端正式 id）前端回填，避免临时 id 泄漏进 upper_id（§12 风险 4）。

回存后一致性

  • 保存成功后按需 DocLoader 重取该单据（或仅回传 idMap），前端 ms.setDataSet 刷新——保证前后端一致。
  • 两模式都在同一事务内，崩溃全回滚，绝不半保存。

6A单据版本化 / 历史 / 审计追溯（单据级开关，开启后支持）

6A.0 需求与设计目标

有些单据需要每次数据变化都被记录、可查询、可追溯、可审计——这是单据的一项设置，开启后生效（不开则零开销）。四件事：

可记录 · 可查询

  • 每次保存产生不可变历史版本（append-only，永不改写）。
  • 能列全部版本、取任一历史版完整数据。

可追溯 · 可审计

  • 对比任意两版差异（哪行/哪列/旧→新/谁改）。
  • 每次变更记 who/when/what/why。
复用现成范式后端已有 cmx_model_source（append-only + JSONB 快照 + is_current，模型中心用）与 cmx_audit_log（操作级审计流水，details JSON）。本方案把这套成熟模式平移到业务单据数据，不新造机制。

6A.1 单据级开关（docMeta.versioning）

版本化是逐单据能力，落在单据定义的 docMeta 上（与现有 version/designStyle/voucherStatusFlow 并列，纯叠加）：

"docMeta": {
  "metaKind": "DOC", "version": 1,
  "versioning": {
    "enabled": true,                 // 总开关：关闭则整套版本化零开销
    "granularity": "document",       // "document"(整单快照,默认) | "row"(行级历史)
    "store": "jsonb",                // "jsonb"(单表快照,默认) | "shadow"(每层影子表) | "both"
    "diff": true,                    // 是否同时落"字段级变更明细"（可查询/审计强）
    "retention": { "keep": 50, "days": 3650 },  // 保留：最多 50 版 / 10 年
    "reason_required": false          // 保存是否强制填变更原因
  }
}
  • granularity：document=每次存整单一个快照版（ERP 主流：完整回看"某版单据长啥样"）；row=逐行历史。默认 document。
  • store：jsonb=一张版本表存整单 JSONB 快照（简单、可回滚、可整版取回）；shadow=每层配 _hist 影子表（可 SQL 查询/追溯）；both=兼得。默认 jsonb。
  • 关闭（enabled:false）→ DocSaver 完全跳过版本逻辑，与非版本化单据零差异、零开销。

6A.2 存储设计

方案 A：JSONB 整单快照表（store:"jsonb"，默认）

一张通用版本表（所有开启版本化的单据共用，非每单据一张），存整单列式包快照：

CREATE TABLE cmx_doc_revision (
    id            BIGINT PRIMARY KEY,          -- 版本记录主键（雪花）
    doc_file      VARCHAR(200) NOT NULL,       -- 单据定义（哪种单据）
    root_table    VARCHAR(100) NOT NULL,       -- 根层表名（如 cv_batch）
    root_id       BIGINT       NOT NULL,       -- 单据根行 id（哪一张单）
    rev_no        INT          NOT NULL,       -- 版本号：该单第几版
    is_current    SMALLINT     DEFAULT 1,      -- 是否当前版（同 root 仅一行为 1）
    op            VARCHAR(16),                 -- create / update / delete / restore
    snapshot      JSONB        NOT NULL,       -- ★ 整单列式包快照（§5.2 结构）
    change_summary JSONB,                      -- 可选：本版变更摘要
    reason        VARCHAR(500),                -- 变更原因（reason_required 时必填）
    actor_id      VARCHAR(64), actor_name VARCHAR(100),   -- who
    created_at    TIMESTAMPTZ  DEFAULT now(),  -- when
    biz_status    VARCHAR(32)                  -- 冗余当时单据状态，便于按态检索
);
CREATE UNIQUE INDEX uk_doc_rev ON cmx_doc_revision (doc_file, root_id, rev_no);
CREATE INDEX idx_doc_rev_cur ON cmx_doc_revision (doc_file, root_id, is_current);
  • append-only：每次保存 rev_no+1 追加一行，旧版永不改写（is_current 翻旧为 0、新版置 1）。
  • snapshot 直接复用 §5.2 列式包：ColumnarCodec.encode(整单DataSet) 产物直接进 JSONB——零额外序列化代码，回滚时 CmxDataSet.fromJSON(snapshot) 直接还原。
  • 通用：一张表服务所有版本化单据，加新单据无需建表。

方案 B：每层影子表（store:"shadow"，需强查询/追溯时）

每层物理表 <t> 配一张 <t>_hist，列 = 原表列 + 版本维度列（由 §4 DDL 引擎按元数据自动生成）：

CREATE TABLE cv_header_hist (
    _hist_id   BIGINT PRIMARY KEY,       -- 历史行主键
    _rev_no    INT NOT NULL,             -- 属于该单第几版
    _op        VARCHAR(16),              -- I/U/D（本行在这版的动作）
    _valid_from TIMESTAMPTZ NOT NULL,    -- 该版生效时点（时序双时区间）
    _valid_to  TIMESTAMPTZ,              -- NULL = 当前有效
    id BIGINT NOT NULL, upper_id BIGINT, line_no INT, /* ...原表全部业务列... */
    _actor_id  VARCHAR(64)
);
维度A · JSONB 快照B · 影子表
建表1 张通用表（零维护）每层 1 张（DDL 引擎自动建）
取整版数据直接（fromJSON）需按 rev 拼各层
按列/行 SQL 追溯弱（JSONB 内查）强（原生列）
时序查询（某时刻）需自解析原生 valid_from/to
存储/写入成本低（一行一版）高（各层各行）
回滚极简（整包还原）需逐层重建
推荐默认需报表/合规级追溯时叠加

6A.3 字段级变更明细（diff:true，审计增强）

除整版快照外，可同时落字段级变更明细（回答"这版到底改了什么"），复用 §6.3 changeset + 现成 cmx_audit_log 语义：

CREATE TABLE cmx_doc_change (
    id BIGINT PRIMARY KEY, rev_id BIGINT NOT NULL,  -- → cmx_doc_revision.id
    root_id BIGINT, layer VARCHAR(100),          -- 层表名 cv_header/cv_acc_line
    row_id BIGINT, op VARCHAR(8),                 -- I/U/D
    field VARCHAR(100),                         -- 变更字段（U 逐字段一行）
    old_value JSONB, new_value JSONB,           -- 旧值→新值
    actor_id VARCHAR(64), created_at TIMESTAMPTZ DEFAULT now()
);
  • 数据来源：merge 模式前端 changeset 已含变更列（updated.fields 每键 = 一条 U 明细，old_value 从上版快照取）；replace 模式后端 diff 新旧快照生成。
  • 可审计：SELECT field,old_value,new_value,actor_id,created_at FROM cmx_doc_change WHERE root_id=$1 AND field='total_dr' → 某字段完整变更史（谁何时把金额从多少改成多少）。

6A.4 与保存链路（§6.4）咬合——快照在保存事务内产生

版本化不是独立步骤而是嵌进 §6.4 的 DocSaver 同一事务（保证"数据写了、版本也记了"原子一致，规避半保存）。
DocSaver.save(changes/snapshot, saveMode):
  txn = begin(db_id)
  try:
    ── 若 versioning.enabled ──
    1. 读当前版(is_current=1)快照 → prevSnapshot（供 diff 与 old_value）
    2. 按 §6.4 merge/replace 写主表各层（同事务）
    3. 重新装配"保存后整单 DataSet"（内存现成，无需回查）
    4. rev_no = prev.rev_no + 1
       UPDATE cmx_doc_revision SET is_current=0 WHERE doc_file=? AND root_id=? AND is_current=1
       INSERT cmx_doc_revision(... rev_no, is_current=1, op, snapshot=encode(整单), reason, actor, biz_status)
    5. 若 store∈{shadow,both}：各层变更行按 _op/_rev_no 追加进 <t>_hist；旧当前行 _valid_to=now()
    6. 若 diff：changeset 展开成 cmx_doc_change 明细（U 逐字段，old 从 prevSnapshot 取）
    7. 可选：写一条 cmx_audit_log（operation="doc.save", target=root_id, details=摘要）
    commit(txn)
  except e: rollback(txn)   // 数据与版本一起回滚，绝不半保存

零拷贝复用

第 3 步"保存后整单 DataSet"就是内存里那棵树，ColumnarCodec.encode 直接产快照（与 §5.2 同序列化器、§7 借用式），不重查库、不重序列化。

与维度解析（§5A）

快照存原始 id/code（不含解析 name），保持小且稳定；回看历史版走 §5A 解析显示——"当时值"或"现值"两种语义可选（要"当时名称"则快照连 _disp 一起存）。

6A.7 通用性、可扩展性、性能

通用 · 可扩展

  • 一套机制服务所有单据；cmx_doc_revision/cmx_doc_change 是通用表（按 doc_file+root_id 区分），加新单据零建表。
  • shadow 影子表由 §4 DDL 引擎按元数据自动生成/加列（additive）。
  • 新增单据只需在 docMeta.versioning 打开开关选粒度/存储；保留策略/diff/原因必填都是声明式参数。

性能

  • 关闭时零开销；开启时快照复用内存 DataSet + §7 借用序列化，不重查库。
  • 快照存 JSONB（PG 原生、可 GIN 索引）；is_current 索引让"取当前版"O(1)。
  • 历史读写与主表物理分离，不拖慢联机主表热路径。
  • 保留策略（keep/days）定期归档清理超期版本，控制增长。
落地优先级（§11 阶段 4.5）先做 A·JSONB 快照 + restore + revisions/revision 查询（复用列式包与保存事务，改动最小即得"可记录/可查询/可回滚/可追溯整版"）→ 需字段级审计时开 diff（cmx_doc_change）→ 需报表级 SQL 追溯/temporal 时再上 shadow 影子表。

7后端零拷贝（约束 A）

现状：axum::Json 每次 serde_json::to_vec 新分配 Vec<u8>；无 Cow、无 rkyv/arrow；仅 Arc<Schema>（模型级共享）与 bytes::Bytes（下载用）。因此"零拷贝"是渐进增强，分三层：

7.1 Schema / 元数据（立即可得）

  • Arc<Schema> 全程共享：同层所有行、同定义跨请求共用一个 Arc；OnceLock/DashMap 建「docFile+version → Arc<Schema>[]」缓存。
  • 列名用 Arc<str>/&'static，序列化借用而非克隆。

7.2 值层（中等）

  • SmolStr 短串内联（状态码/币种/编码不堆分配）。
  • 借用式序列化：列式编码走 RowsRef/RowRef 式借用序列化器（rds.rs 已有先例），rows:[[…]] 由 serialize_seq 流式吐 &DataValue，不物化中间 Vec。
  • Bytes/BytesMut 复用响应缓冲。

7.3 传输零拷贝（进阶，可选）

  • 流式响应：大单据用 axum Body::from_stream，边组装边发（SSE 先例已在 portal/handler.rs）。
  • rkyv/Arrow IPC（远期）：真·零拷贝反序列化需引入新依赖，本方案默认不引入——「列式 JSON + msgpack + 压缩」已满足小包目标，性价比更高。
务实取舍约束 A 的"尽量零拷贝"在本方案 = ① Arc<Schema> 共享 + ② 借用式列式序列化 + ③ Bytes 复用/流式，全部在现有 rds.rs/axum 能力上叠加，不改数据面为 rkyv/arrow（避免伤筋动骨）。

8传输小包（约束 B）

现状：行式 JSON、键名逐行重复、不跳 null、无压缩（CompressionLayer 已编译未挂载）。四级递进、逐级叠乘：

8.1 一级：列式化（最大结构收益）

行式（每行重复 7+ 键名）→ 列式（键名 1 次 + 纯值数组）。键名开销从 O(行×列) 降到 O(列)。裸 JSON 常降 40%~60%。前端 fromJSON 原生支持，零前端改造。

8.2 二级：跳 null + 稀疏优化

引入 SKIP_NULL 语义（稀疏列不占位）；保存侧 updated 只带变更字段。会计辅助行等稀疏结构收益显著。

8.3 三级：MessagePack（二进制）

后端已用 rmp-serde（WASM 边界），扩到 HTTP 内容协商（Accept: application/x-msgpack）。免引号/逗号、变长整数，叠加列式再降 15%~30%。

8.4 四级：HTTP 压缩（一行，最省力）

tower-http 的 compression-full 已在依赖里，只需在 main.rs 中间件栈加 CompressionLayer（br/gzip）。对列式 JSON 通常再降 70%~85%——桌上最大最省力的杠杆。

12风险与护栏

1 · upper_id 非 DB 外键删父不会 DB 级联，DocSaver 必须应用层保证「子先删/连带删」（§6.4），否则留孤儿。
2 · 前端无脏标记（坑 A）changeset 完全依赖 ChangeSetCollector 正确订阅事件；聚合回写（aggregate 改 toField）也会触发 row-changed，需甄别「用户改」vs「聚合改」——建议聚合写用 row[key]=v 直写（不经 set、不进 changeset），或在收集器按来源打标。
3 · cmx-tabulator 回写死支_onCellEdited 判 this._ds.set（CmxDataSet 无 set，只有 CmxRowSet.set），若用 Tabulator 作可编辑主从视图，编辑不回模型。→ 主从可编辑场景优先 cmx-revo-grid。
4 · id 生成新增行 id 由前端临时生成（r<base36>）还是后端雪花？建议后端生成、保存后回 idMap 前端回填，避免临时 id 泄漏进 upper_id。
5 · 大树内存整单大树全量装载。超大单据用根层分页（filter/page 作用于 L1）+ 子层按需（选中父行再拉子——可扩展为「懒下钻」，DocLoader 支持 depth 参数）。
6 · 维度解析一致性（§5A）L2 伴生宽表的 name 会因字典改名过期——按业务语义选懒刷/批刷/快照三策略之一，勿默认"永远实时"。L0 前端缓存需版本协商失效，避免旧 name 长驻。_disp 表的 DELETE/UPSERT 必须与主表回存同事务同拓扑序，否则显示值与主数据不一致。
7 · 版本化开销与增长（§6A）仅对开 versioning 的单据生效，务必默认关闭、按需开启。快照与主表回存同事务——快照写失败必须回滚主数据，绝不"数据成功、版本丢失"。JSONB 快照随版本累积增长，必须配 retention（keep/days）归档清理；高频保存单据慎开 shadow（写放大）。历史/影子表与主表物理分离，勿让版本写入拖慢联机热路径。

14查漏补缺：单据生命周期与横切关注点

§1–§13 覆盖了「装载→模型→编辑→回存→维度解析→版本化」主链路。最后一轮审视发现：真实 ERP 单据还有一批横切关注点，数条直接影响正确性（不做会错），另一些是必须明确的设计约定。好消息——经核对源码，所需后端能力大多已存在，方案只需「串联 + 声明」。

14.1 【正确性】单据状态机约束保存/编辑（voucherStatusFlow）

过账的凭证绝不能再改——主链路 §6.4 却没读状态机 单据定义已有 voucherStatusFlow.states（每状态 editable：draft.editable:true、audited/posted/reversed.editable:false）+ transitions（action/from/to/guard）。§6.4 DocSaver 完全没用它，漏了就是数据事故。
  • 保存前置校验：DocSaver 保存前读当前 stateField（如 doc_status），查 states[当前].editable；false 则拒绝保存（除非合法状态流转）。
  • 状态流转是独立动作：审核/过账/反冲走专门端点 POST /api/doc/transition { docFile, rootId, action }，后端校验 from==当前态 + action 合法 + 跑 guard（权限+业务条件），通过才改状态（版本化开启则记 op=transition 版本）。
  • 前端联动：装载时据 editable 决定可编辑性（ms.setEditable(false) 已就绪）；不可编辑态只读 + 只显可用流转按钮。叠加字段级 edit.editableWhen/readonlyWhen（已有）做到列级锁定。

14.2 【正确性】后端二次校验（validationRules，前端校验不可信）

前端校验可被绕过，后端目前无表达式求值器 单据有 validationRules（"凭证本位币借贷必须平衡""记账期间未打开"，带 expression/message）。前端有 formula-eval.js，但改请求直发可绕过；经核对后端没有对应求值器——真缺口。
  • 后端求值器（新增）：实现与前端 formula-eval 语义对齐的安全求值器（同套操作符/函数白名单），DocSaver 保存前对 validationRules 逐条在保存后整单 DataSet上求值，任一 severity:error 不通过则回滚 + 返回 message。
  • 双端一套规则：前后端共用同一份 validationRules（元数据驱动）——前端即时反馈、后端最终把关，不重复定义。规则在内存 DataSet 求值，代价极低。

14.3 【正确性】并发控制（乐观锁 / 悲观锁，防覆盖）

两人同编辑，后保存者静默覆盖前者 §6.4 目前无并发保护。经核对后端已具备 SELECT ... FOR UPDATE 悲观锁能力。

乐观锁（默认，联机编辑）

主表加 row_version INT（或复用 update_time）；merge 走 UPDATE ... WHERE id=$1 AND row_version=$expected，rows_affected=0 ⇒ 冲突，回滚返回「单据已被他人修改，请刷新」。装载下发 row_version，保存带回。

悲观锁（强占用）

编辑前 POST /api/doc/lock → 根行 FOR UPDATE 或写 cmx_doc_lock（actor+过期）；他人只读。replace 整树覆盖建议强制悲观锁，避免冲掉他人改动。

14.4 【正确性】软删除 vs 物理删除（delete_flag）

物理 DELETE 与系统逻辑删除约定冲突、破坏审计追溯 base 已有 delete_flag（逻辑删除）。§6.4 的 DELETE/replace 写物理删——删了就查不到，破坏版本化/审计。
  • 单据设置 deletePolicy（docMeta）：soft（默认，UPDATE SET delete_flag=1）| hard（物理删）。
  • 软删语义：删除改为标记；DocLoader 一律带 WHERE delete_flag=0。删除进版本历史（op=delete），可追溯可恢复。replace 软删时把"不在 snapshot 的旧行"标删而非物理清空。

14.5 【约定】单号生成（doc_no 谁生成、防重、按段流水）

  • 后端生成（保存时）：单号后端在保存事务内生成（前端占位），避免临时号泄漏与并发重号。
  • 规则元数据化：docMeta.numbering { field:"doc_no", pattern:"PZ-{entity}-{yyyymm}-{seq:6}", scope:["entity_id","fiscal_period_id"], resetBy:"month" }——声明式前缀/变量/流水位/分段/重置。
  • 并发防重：从 DB 序列或 cmx_doc_seq(scope_key,next_val) UPDATE ... RETURNING 原子自增；单号列唯一索引兜底。numbering.assignOn:"save"|"transition:audit" 控制"草稿临时号、过账才正式号"。

14.6 【约定】数据权限（行级 who 能看/改哪些单据）

已就绪后端已有 CmxSvrContext/SVRContext（含 tenant_id、has_permission/require_permission）+ 权限中间件 + init_dml.sql 里的 gl:voucher:add/audit/post/delete 权限点。
  • 装载注入范围过滤：DocLoader 从 CmxSvrContext 取用户数据范围（组织/公司/租户），自动给根层 SQL 加 WHERE entity_id = ANY($allowedOrgs)。不信前端传的过滤——后端强制注入。
  • 操作权限：保存/删除/流转前 ctx.require_permission("gl:voucher:edit")。
  • 审计 actor：§6A 版本/审计的 actor_id/actor_name 从 CmxSvrContext 取（不信前端），保证追溯真实。app_id/tenant_id 作隐式过滤维度。

14.7 【约定】附件与大字段（attach_count 背后的本体）

  • 附件与数据解耦：单据行只存附件引用（file_id/storage_key，指向对象存储——系统已有 cmx-storage crate），不存二进制本体（否则包爆炸，违背 §8）。
  • 装载：只带 file_id + 元信息，本体按需懒加载（点开才 GET /api/storage/{file_id}）。回存：附件先独立上传拿 file_id，再随单据行存引用；删除按策略级联。

14.8 【约定】统一错误契约 & 部分失败语义

  • 单据错误码族（ApiResp.code 非 0）：DOC_VALIDATION_FAILED（带 details:[{layer,rowId,field,message}]）、DOC_STATE_LOCKED、DOC_VERSION_CONFLICT、DOC_PERMISSION_DENIED、DOC_LOCK_HELD——前端精准提示/高亮出错单元格。

15配置驱动的可扩展机制：用配置适配个性化，而非改代码

§14 的单号、校验、状态……在真实 ERP 里千变万化：A 单据借贷平衡、B 单据要调税务系统核验；甲公司单号按年重置、乙公司按月分段。若每种个性化都改代码，平台会被业务淹没。 本节确立贯穿全方案的架构原则：所有可变业务规则由元数据配置驱动 + 命名扩展点承接，新增/变更单据行为 = 改配置（多数）或注册一个命名扩展（少数），不动平台代码。

15.0 核心张力与解法：三层表达力阶梯

纯配置的陷阱声明式配置能表达 80% 的规则，但剩下 20% 真正复杂的逻辑（调外部系统、多表事务、复杂算法）配置表达不了——硬塞会把配置退化成"图灵完备的丑陋 DSL"。正确解法是分层：按规则复杂度选表达层，每层都是配置声明，只是指向不同的执行器。
层表达方式覆盖举例谁执行
T1 声明式表达式formula-eval 表达式字符串~80%"debit == credit"内置求值器（前后端各一，语义对齐）
T2 命名策略 + 参数{ strategy, params }~15%{strategy:"period_open", params:{...}}平台内置策略库（参数化）
T3 扩展点 → 服务/插件{ handler:"service:key" }~5%{handler:"service:gl.validateTax"}服务编排 / WASM 插件（业务方实现）
  • T1 覆盖绝大多数「字段间算术/比较/逻辑」规则——纯配置字符串，零代码。前端 formula-eval.js 已支持 40+ 函数（ROUND/IF/SUM/CONCAT/DATEADD/COALESCE…），后端补一个语义对齐的孪生求值器即可（§14.2）。
  • T2 覆盖「有固定模式但需参数化」的规则——平台预置一批命名策略（如"期间开闭校验""按段流水号"），配置只填策略名 + 参数。加新策略是平台演进（低频），用策略是配置（高频）。
  • T3 覆盖「真正复杂、每家不同」的逻辑——配置里写 handler 指向命名扩展点（服务编排 service_key 或插件函数），业务方写任意逻辑。平台只认 handler 名，不关心里面干什么。
关键三层都是"配置里声明"，区别只是 T1 声明表达式、T2 声明策略名、T3 声明 handler 名。业务复杂度上升时从 T1→T2→T3 平滑升级，平台核心代码不变。

15.1 落点已就绪：命名扩展点注册表（ServiceRegistry）

T3 的"命名扩展点"不需凭空造——后端已有现成宿主
  • GlobalServiceRegistry / ServiceRegistry（cmx-service）：service_key → ServiceDefinition、plugin_id → Vec<service_key> 缓存——这就是扩展点注册表。
  • Orchestrator 服务编排：POST /api/service/execute { service_key, input } 按 key 执行编排 Flow。
  • WASM 插件：{ plugin_id, function_name, input } 调业务方沙箱逻辑。

所以 T3 的 handler:"service:gl.validateTax" 落地 = 解析 service: 前缀 → 查 ServiceRegistry → Orchestrator.execute("gl.validateTax", {doc, ctx})。handler:"plugin:acme.numbering" 走插件调用。平台侧只需一个"handler 解析分发器"，把 service:/plugin:/formula:/builtin: 前缀路由到对应执行器。

15.2 统一规则引擎：一套 RuleSpec，服务所有横切点

单号/校验/状态/默认值/权限……表面各异，抽象后都是"在某时机、按某条件、执行某动作"。用统一 RuleSpec + 一个 RuleEngine 分发器承接全部：

// 统一规则规格：单号/校验/状态/默认值/联动 全部复用
{
  "id": "voucher_balance_check",
  "on": "before_save",              // 时机：before_save/after_save/before_transition/on_field_change/on_load
  "when": "doc.total_dr > 0",       // 条件（T1 表达式，可选；真则执行）
  "do": {                           // 动作：三层表达力择一
    "tier": "formula",              // "formula"(T1) | "strategy"(T2) | "handler"(T3)
    "expr": "sum(lines.local_dr) == sum(lines.local_cr)",   // T1
    "message": "凭证本位币借贷必须平衡",
    "severity": "error"             // error 阻断 / warn 提示
  },
  "scope": "cv_header"              // 作用层（可选）
}
  • on（时机）+ when（条件）+ do（动作）三段式，是所有横切规则的公共骨架。do.tier 选表达层。
  • RuleEngine：在各生命周期钩子点（load/save/transition/field-change）收集命中 on 的规则，按 when 过滤，逐条 do 分发到 T1/T2/T3 执行器。一个引擎 + 一个分发器，把 §14 所有可变点统一——加规则 = 加一段 RuleSpec 配置。

  { "on":"before_save", "do":{ "tier":"formula", "expr":"total_dr==total_cr", "message":"借贷不平", "severity":"error" } },
  { "on":"before_save", "do":{ "tier":"strategy", "strategy":"period_open", "params":{...}, "message":"期间未打开" } },

借贷平衡（T1 纯表达式）、期间开闭（T2 平台策略）、税务核验（T3 外部服务）——三种复杂度同一套配置结构，各选其层。

状态机（§14.1）→ 状态/流转/守卫全配置

"statusFlow": {
  "stateField": "doc_status",
  "states": [ {"code":"draft","editable":true}, {"code":"posted","editable":false} ],

    { "action":"post", "from":"audited", "to":"posted",

状态、可编辑性、流转条件、权限、副作用——全声明式。加一个"冲销"动作 = 加一段 transitions 配置；冲销逻辑复杂 = effects 指 handler。默认值/字段联动/数据权限注入同样复用 RuleSpec（on:on_load/on_field_change + strategy:default_from_context/data_scope）。

15.4 配置的载体与治理

载体（与定义同源）

  • 所有 RuleSpec/numbering/statusFlow/validationRules 进单据定义元数据，复用 §3.6 definitions::store + §3.7 缓存 + §3.8 强类型投影——与单据定义同源、同版本、同部署。改规则走现成保存链路，无需发版。
  • 随定义版本走（§6A 是数据版本，这里是定义版本），"改了校验规则"可追溯到定义版本。

治理

  • 设计器可视化：结构化 JSON → 可视化编辑（下拉选 on、表达式编辑器写 expr、策略选择器选 strategy、扩展点选择器从 ServiceRegistry 列 service_key）。业务顾问配规则，不写代码。
  • 扩展点契约：T3 handler 统一 I/O——入参 { doc:DataSet快照, row?, ctx:SvrContext, params }，出参 { ok, message?, patch?, value? }。业务按契约实现，平台按契约调用，双方解耦。

15.5 前后端一致：同一份配置，两端执行

  • T1 表达式：前端 formula-eval 即时校验/联动（体验），后端孪生求值器最终把关（正确性）——同一份 expr 字符串两端各跑一遍，规则不重复定义。
  • T2 策略 / T3 handler：默认后端权威执行（涉及库/外部系统）；纯 UI 类可前端也接一份。配置声明"什么规则"，前后端各自决定"在我这端跑不跑"——兑现 §14.2 的"双端一套规则"并推广到所有横切点。

15.6 为什么满足「通用 + 可扩展 + 不牺牲性能」

三性兼得 通用：一个 RuleEngine + 一套 RuleSpec 服务所有横切点，不为每种需求写专用代码。 可扩展：三层阶梯让简单规则纯配置（T1/T2）、复杂逻辑挂扩展点（T3），复杂度增长时平台核心零改动；扩展点复用现成 ServiceRegistry/编排/插件。 个性化即配置：不同单据/租户/场景 = 不同 RuleSpec 集合，随定义元数据走，改配置不发版。 不牺牲性能：T1/T2 在内存 DataSet 求值（数据已在手，§7 零拷贝复用），代价极低；仅 T3 外部调用有网络开销且只在少数规则用；规则集随定义缓存（§3.7）。

15.7 落地优先级

阶段内容
先做RuleEngine 骨架 + T1 求值器（后端孪生 formula-eval）+ RuleSpec 的 on/when/do 三段式；把 §14.2 校验、§14.1 状态守卫先跑起来
紧随T2 命名策略库（segmented_sequence/period_open/data_scope/default_from_context 等内置）+ 设计器可视化编辑
按需T3 handler 分发器（service:/plugin: 前缀路由到 ServiceRegistry/编排/插件）+ 扩展点 I/O 契约
一句话把 §14 每个"可变点"改造成"RuleSpec 配置 + 三层执行器"，平台提供引擎与内置策略，业务提供配置与少量扩展——个性化需求 99% 落配置、1% 落命名扩展，平台代码保持稳定。这才是能长期适配无穷业务变化的架构。

16运行形态决策：Rust 原生 vs 后端 WASM

一个常被问到的架构问题：这套方案是用 Rust 原生运行，还是编译成后端 WASM 运行？结论不是二选一，而是分层——平台引擎必须 Rust 原生，WASM 只承接 §15 的 T3 业务扩展点。这不是偏好，是被方案的两条硬约束（零拷贝、小包）和代码库的真实边界共同锁定的。

结论先行平台引擎（装载/回存/DDL/版本/校验求值器/内置策略）= Rust 原生；业务个性化扩展（§15 T3 的 handler）= WASM 插件。让每层跑在最适合它的运行时：核心引擎要极致性能 + 事务/内存直接访问 → 原生；业务扩展要隔离 + 热插拔、且不在热路径 → WASM。

16.1 为什么主体必须 Rust 原生（而非编译成 WASM）

理由一：方案依赖的核心能力全部是 host 原生 crate

经核对，DocLoader/DocSaver 要用的每一样东西都在宿主侧原生运行，没有一个是 wasm 目标：

能力所在 crate形态
事务 begin/commit、连接池、FOR UPDATEcmx-databasehost 原生
DDL 引擎、create_or_upgrade_tablecmx-metadatahost 原生
DataSet/Arc<Schema>/ColumnarCodeccmx-corehost 原生
query_sql → DataSet、convert_postgres_rowscmx-databasehost 原生

WASM 沙箱够不到这些——没有数据库连接、没有文件系统（字典 JSON 在 data/dict/entries）、拿不到 Arc<Schema> 共享引用。编译成 WASM 等于自断双臂。

理由二：WASM 边界直接违背方案的两条硬约束（最致命）

WASM 访问 DB 每次强制序列化 + 拷贝（真实代码 host_calls.rs） 
let bytes = rmp_serde::to_vec(&request)?;       // 序列化(拷贝)
// ... 跨线性内存边界进 host ...
let response = rmp_serde::from_slice(&result)?; // 反序列化(拷贝)
  • 违背零拷贝（§7）：方案花大力气做 Arc<Schema> 共享 + 借用式序列化，而 WASM 边界强制每次进出全量序列化 + 内存拷贝——Arc 跨不过线性内存边界，零拷贝设计当场作废。
  • 违背小包 / 大单据（§8/§12）：插件/gRPC 消息有 4MB 上限（cmx_plugin_data.proto 明确注"大包建议 HTTP 模式"）。方案要支持大单据 + 版本快照，快到边界就爆。

理由三：WASM 无法真正参与 host 事务——破坏 §6.4/§6A 原子性

txn_id 只是个字符串跨边界传（wasm_types/database.rs），事务实体 sqlx::Transaction 在 host 侧。方案核心正确性保证——"主 + 各层明细 + 版本快照在同一事务内全或无"（§6.4、§6A、§14）——依赖直接持有事务句柄。WASM 侧拿不到，只能靠字符串来回传，跨多次 host_call 有一致性风险，且 §14.3 的 FOR UPDATE 悲观锁跨不过沙箱。

理由四：热路径上多一层沙箱纯亏

装载/回存是高频热路径。WASM 化平白加上：线性内存拷贝、序列化开销、沙箱调用开销、wasmtime（39.0.1）的 JIT/解释开销。方案追求的性能全被这层吃掉。

16.2 WASM 该用在哪——正好是 §15 的 T3 扩展点

现有架构本就是「host 原生引擎 + WASM 业务插件」分层（cmx-plugin-demo 是 cdylib/wasm，但 cmx-service 编排、cmx-database 数据在 host）。这个分层恰好是 §15 三层阶梯的物理落地：

§15 层运行形态理由
T1 表达式求值host 原生（后端孪生 formula-eval）高频、在内存 DataSet 上跑，必须零开销
T2 命名策略host 原生（平台内置策略库）平台代码，原生最快
T3 业务扩展点WASM 插件 ✅每家不同的个性化逻辑，需沙箱隔离、热插拔、独立部署

WASM 的价值在 T3 完美体现：业务方写的 service:gl.taxValidate（调税务系统）、service:acme.docNumber（特殊编码）这类个性化逻辑，正需要 WASM 的沙箱安全（第三方/租户代码不碰核心）、热插拔（不重启不发版上新规则，呼应 §15"改配置不发版"）、多租户隔离。而它们调用频率低（T3 只覆盖 ~5% 规则）、单次数据量小（传一行 + 校验结果，远小于 4MB），WASM 边界代价可接受。用 extism（1.4）+ 现成 db_query/db_execute host_call 即可。

16.4 落地形态

  • DocLoader/DocSaver/ColumnarCodec/RuleEngine/T1 求值器/T2 策略库 → 作为 host 原生服务落进 cmx-biz/cmx-service，直接用 cmx-database/cmx-metadata/cmx-core。
  • T3 handler → 通过现成 ServiceRegistry + 服务编排 / extism 插件调用链路触达；I/O 走 §15.4 统一契约（入 {doc快照, row?, ctx, params}、出 {ok, message?, patch?, value?}），数据量天然小。
  • 迁移含义：若历史上有把这类数据处理放进 WASM 的尝试，应上移回 host 原生（与 docs/node-to-rust-migration-cutover.md 原生化方向一致）；WASM 保留给真正需要隔离/热插拔的业务扩展。
一句话不是"原生还是 WASM"，而是"引擎原生、扩展 WASM"——核心走原生拿性能与事务/零拷贝，个性化走 WASM 拿隔离与热插拔，两者用 §15 的 handler 契约衔接。
