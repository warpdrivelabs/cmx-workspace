cmx 业务模块独立化方案

把 cmx-flow（流程）、cmx-rpt（报表）、cmx-doc（单据）、cmx-dct（字典）、cmx-model/meta（元数据）——像 cmx-rust-sheet / cmx-sheetwright 那样——从庞大的 cmx-container 单体里抽出来，成为独立、可单独部署、只吃公共 crate、不依赖庞大框架的组件 / 服务。

对标样板：cmx-rust-sheet（独立 workspace）+ cmx-sheetwright（薄传输壳）+ cmx-home-site（组件站） ·  抽离对象：cmx-container/crates/libs/{cmx-flow,cmx-rpt,cmx-doc,cmx-dct} + cmx-model/cmx-metadata ·  本文档：仅方案，不含实现代码

01背景与目标

cmx-container 是一个庞大的 Rust workspace：Cargo.lock 里 861 个 crate 版本，一次全量构建牵动整棵依赖树。业务能力（流程引擎、报表平台、单据、字典、元数据建模）都以 crates/libs/cmx-* 的形式住在里面，最终由一个统一的 web-server 把它们 merge 成一个巨型进程。

而在同一个 presentation/ 根目录下，已经有两套示范如何“独立活着”的项目：

  • cmx-rust-sheet：独立 Cargo workspace，只引十来个成熟 crate，不继承 cmx-container 的百级依赖树，纯库形态。
  • cmx-sheetwright：在 rust-sheet 外套一层薄壳（path 依赖引入），加协议层 + CLI + HTTP，变成一个“无头 Excel”服务。
  • cmx-home-site / cmx-mega-sheet：组件展示站，双语双主题、纯静态，把一个组件“讲清楚 + 可运行演示”。

本方案的目标：把 cmx-flow / cmx-rpt / cmx-doc / cmx-dct / cmx-model(meta) 也做成这个样子——每个业务域一个独立 workspace，可单独 cargo build、单独部署、只吃公共 crate、不背 cmx-container 的框架包袱；需要时再以 path/registry 依赖被别人引入，而不是反过来被大 workspace 绑架。

◆ 一句话范围
每个业务域的 model / engine / formula / store-pg 层原样带走（它们只依赖一条浅而自洽的“数据库脊柱”）；唯一强耦合框架的 -api 层（Router<CmxAppState>）替换成一个薄薄的 -service 壳（自带 axum server + 自建 DB 池 + 自己的配置），做法与 cmx-sheetwright 包 cmx-rust-sheet 一模一样。

为什么值得做

  • 可独立部署：报表挂了不拖垮流程；每个域自己的进程、自己的端口、自己的发版节奏。
  • 构建/依赖瘦身：单体 861 crate 版本 → 一个独立流程服务实测 12 内部 + ~15 三方 crate（见 §17-B）。编译、CI、镜像体积全线下降。
  • 可复用、可移植：任何一个 Rust 后端都能 path 引一个 cmx-flow-engine 当“流程算核”，不必吞下整个 cmx-container。
  • 已有活体证据：cmx-flow-demo 早就是一个自包含的 axum 服务（端口 8090，自己的 Router::new()、自建 DB 池、include_str! 前端），完全不碰 cmx-api / CmxAppState / web-server——它就是本方案的“可行性样机”。

02对标样板：sheet 三件套怎么独立的

先把可复制的“姿态”拆清楚——本方案对每个业务域，就是把这三件套复制一遍。

① 内核 workspace
cmx-rust-sheet

独立 Cargo.toml [workspace]，crate 分层（sheet-core → sheet-formula → sheet-io → 门面），只在门面/IO 层引三方 crate，core/formula 保持轻。纯库，零框架。

② 薄传输壳
cmx-sheetwright

以 path 依赖引内核，只加“对外的嘴”：协议层 + CLI + HTTP。spawn_blocking 隔离 !Send。内核零改，壳单独演进。

③ 组件站
cmx-home-site

纯静态双语双主题站：首页 / 方案 / 使用 / 演示，运行时原样拷自 demo。把“一个组件”讲清楚并可现场跑。

▶ 映射到本方案
①内核 = 各业务域已经切好的 model / engine / formula / store-pg 分层 crate（已存在，几乎不用动）。  ②薄壳 = 新写的 *-routes 库（替 -api）+ 宿主（共用 cmx-web-server 或各域 -service，见 §8）。  ③组件站 = 各域现成的 native-pages 工作台前端，从 cmx-container 抽出随服务发布。

03框架耦合解剖：“细腰”在哪

能不能独立，取决于耦合有多深。实测结论：耦合是一条很窄的“腰”——只有 -api 层碰框架，下面几层只依赖一条浅的数据库脊柱。

3.1 框架侧被用到的全部符号（这就是“腰”的全宽）

各业务域的 -api crate 对 cmx-api 的使用，收敛为这几个：

// 这是 -api 层 use cmx-api 的全部足迹——非常窄
use cmx_api::{ CmxAppState, Error, Result, ApiResp };
use cmx_api::routes::traits::ModuleRoutes;        // fn routes(self)->Router<CmxAppState>
use cmx_api::middleware::CmxSvrContext;             // 请求上下文（db_id / 租户）
use cmx_api::rest::header_parse::get_db_id_from_header; // 从 header 取数据源 id

没有别的了。CmxAppState 是共享状态、ModuleRoutes 是“交出一个 Router”的约定、CmxSvrContext/get_db_id_from_header 是“这次请求打哪个库”。这四样全都可以在 -service 壳里用几十行自造等价物顶掉（见 §8）。

3.2 web-server 的接线（要替换的就是这段）

// crates/web/web-server/src/routes.rs —— 单体把所有域 merge 进一个 Router
pub fn routes() -> Router<CmxAppState> {
    api_routes()
        .merge(ReportModule.routes()).merge(FlowModule.routes())
        .merge(DocModule.routes()).merge(DctModule.routes())
        .merge(JobModule.routes()).merge(ModelModule.routes())
}
// main.rs：全局 .nest("/api", api_routes) + 各前端 nest_service(prefix, serve)

独立化后，每个 Module.routes() 不再被这里 merge，而是各自的 -service 进程自己 Router::new() 挂载。

3.3 下面几层依赖什么（脊柱，而非框架）

model / engine / formula / store-pg 的依赖，全落在一条浅而自洽的基础设施脊柱上：

数据库脊柱（可整体带走，不含 cmx-api / web-server） cmx-database-pg ← tokio-postgres + deadpool 池；register_datasource / get_default_pg_db_manager DbConfig · DbType · ZmcDataSet（零拷贝读）· PgResultConverter · QueryBuilder cmx-core ← 基础类型 / 错误 cmx-utils ← 工具 cmx-rowsource ← ZmcDataSet 零拷贝行源 trait cmx-traits · cmx-buffer ← 叶子 cmx-model-meta ← 定义/元数据 resolve（metaKind DCT/DOC/FLX/RPT），只依赖 2 个叶子 cmx-biz「薄片」 ← 仅 validation(838行) + errcode(360行) + error.rs ≈ 1.2k / 7.3k 行
◆ 关键洞察
耦合是“腰”不是“网”。 越过 -api 这一薄层，剩下的全是纯逻辑 + 一条浅数据库脊柱。所以独立化不是“大重构”，而是“换掉腰、把脊柱打包带走”。这也是 cmx-flow-demo 能在完全不碰框架的情况下跑起来的原因。

04范围界定：每层保留 vs 替换

保留原样带走（可能仅去掉对 cmx-api 的引用） 下沉/切片只带走需要的一部分 替换框架专属，换独立等价物 新增独立化新写的壳

层去向说明
*-model（IR / 类型）保留纯数据结构，零框架依赖（个别依赖 cmx-core/biz 也在脊柱内）。直接带走。
*-engine / *-bpmn / *-formula保留流程执行、BPMN 解析、公式求值——纯逻辑，只依赖同域 model。核心竞争力，原样带走。
*-store-pg（PG 持久化）保留依赖 cmx-database-pg + cmx-core（+少量 biz/utils/meta），全在脊柱内。带走。
cmx-database-pg 等脊柱 crate下沉作为共享脊柱，一份被所有独立服务以 path 复用（见 §6）。
cmx-biz（7.3k 行）切片只需 validation + errcode + error（≈1.2k 行；符号 BizError::from_db_error / validate_insert_row / Violation）。抽成 cmx-biz-kernel 薄 crate，别把整包 7.3k 拖来。
cmx-model-meta保留DOC/DCT 解析定义要用；依赖极浅，带走。
*-api（Router<CmxAppState>）替换唯一强耦合框架的层。删掉对 cmx-api 的 4 个符号依赖，降级为 *-routes 库（无 state 的 Router）。
*-routes（无 state 路由库）新增域只“交出一段 Router<()>”+ 前端目录 + 数据源注册。可被任意宿主 merge。见 §8.1。
宿主 A cmx-web-server / 宿主 B *-service新增A：一个二进制按 config.modules 装载多域（共用）；B：每域一个瘦二进制（强隔离）。两者复用同一份 *-routes。见 §8.3-8.4。
native-pages 前端（工作台）随行各域现成四区工作台，从 cmx-container 抽出，随对应服务发布（见 §9）。

05关键决策（含推荐）

5.1  依赖策略：吃公共 crate，甩掉框架 已定

用户明确：不依赖庞大框架、可借助公共 crate。落地为两条纪律：

  • 甩掉的：cmx-api（CmxAppState/ModuleRoutes/CmxSvrContext）、web-server、以及只为大 workspace 服务的重依赖。
  • 带走的“公共 crate”：数据库脊柱（cmx-database-pg + 叶子）、cmx-model-meta、cmx-biz-kernel 薄片，以及三方生态（axum · tower-http · tokio · serde · tracing · async-trait）——正是 cmx-flow-demo 已在用的那一小撮。

5.2  每域一个独立 workspace，还是一个大 monorepo？

选项取舍
每业务域一个独立 workspace，与 cmx-rust-sheet 平级放在 presentation/ 根推荐 完全镜像 sheet 三件套的独立姿态：cmx-flow/ · cmx-rpt/ · cmx-doc/ · cmx-dct/ · cmx-meta/ 各自 Cargo.toml [workspace]、各自发版、各自 CI、各自 Docker。真正“可独立部署”。
一个 cmx-modules/ 大 workspace 容纳全部 共享 workspace.dependencies 省心，但又滑回“大 workspace 构建耦合”，与“独立可部署”初衷相悖。
脊柱怎么共享？ 把 cmx-database-pg 等脊柱 crate 抽到 presentation/cmx-shared/（或发到内网 registry），各域 workspace 以 path 依赖共引一份。见 §6。

5.3  库优先 + 可选服务/CLI 壳 已定

沿用 sheet 的“库优先”哲学：内核层永远是可嵌入的库；-service（axum daemon）与可选 -cli 只是“对外的嘴”，是后置里程碑。任何人都能只引内核 crate 当算核，不必起服务。

5.4  cmx-biz 只切片，不整包搬 已定

cmx-biz 7.3k 行里，独立服务真正需要的只有落库前校验 + 统一错误码（≈1.2k 行）。抽 cmx-biz-kernel 薄 crate，避免把整个业务库的其它耦合一起拖进独立世界。铁证：整包 cmx-biz 的依赖里赫然有 cmx-service + cmx-portal-base（服务框架 + 门户框架）——不切片就等于把要甩掉的框架又偷渡回来。全部公共 crate 的治理分类见 §6.1。

5.7  共用宿主 web-server，按配置装载不同域 已定·强化

这是对交付形态的关键强化，采纳用户提议。不把“每域一个独立二进制”与“共用一个 web-server”对立起来——它们是同一套域库之上的两种宿主。做法：让每个域只贡献一个不带 state 的 Router（fn routes() -> Router），谁来 merge、绑哪个端口、装哪几个域，全交给宿主决定。

宿主 A · 共用 cmx-web-server（新）

一个二进制，读配置文件 modules = ["rpt","flow","doc","dct"] 决定装载哪些域的 routes()，全 merge 进一个 Router、一个端口。正是今天 cmx-container 的 web-server 做的事——只是模块集由配置驱动、且不再背框架。

宿主 B · 各域自带 -service（原案）

每域一个瘦二进制，只 merge 自己那一个 routes()，独立端口/镜像/发版。适合“报表挂了不拖垮流程”的强隔离部署。

两种宿主共享同一份域库（*-routes crate），零重复代码。开发期用宿主 A 一个进程全装、方便；生产期按隔离需求选 A（省资源）或 B（强隔离），甚至混用（rpt 单独一个 B，其余挤在一个 A）。为什么几乎免费——见 §8：demo 里 DB 池是全局单例、引擎是 OnceCell，域的 Router 本就不带 state，天然可被任意宿主 merge。

5.6  脊柱是「货架」不是「全集」 已定

脊柱 cmx-shared 分两层：必备层（database-pg/core/utils/modql/api-types/biz-kernel/model-meta——人人 path 引）与可选货架层（cmx-iam · audit · auth · storage · ai · job-core · plugin-sdk——按需 path 引）。各业务 -service 只取自己要的那几格，不背全集。判据与逐 crate 归类见 §6.1。

5.5  分阶段：先垂直打通一个域，再横向复制

不五个域齐头并进。先拿 cmx-flow（已有 demo 样机，风险最低）打通“抽脊柱 → 写 -service → 前端随行 → Docker 部署”整条链，形成可复制的模板，再套用到 rpt/doc/dct/meta。

▶ 落地前需用户拍板
① 独立粒度：五域各一个 workspace（推荐），还是先只做 flow 一个试点？   ② 脊柱共享方式：presentation/cmx-shared/ 用 path（推荐，简单），还是发内网 registry？   ③ 交付形态：纯库、库+HTTP 服务（推荐）、还是再加 CLI？   ④ 宿主策略：共用 cmx-web-server（配置装载，推荐开发/中小部署）、各域 -service（强隔离）、还是两者都产出按需选（推荐，见 §5.7）？

◆ 依赖方向恒单向
cmx-shared/* 不认识任何业务域；每个业务 workspace 只向下依赖 cmx-shared 与三方 crate，域与域之间零横向依赖。这正是 sheetwright→rust-sheet 的单向姿态，放大到五个域。
⚠ 复用 cmx-container 的镜像源配置
各 workspace 复制一份 .cargo/config.toml（aliyun 镜像、registry="nora"），沿用 edition 2024。脊柱里绝大多数三方 crate 已在该镜像拉过，独立化不引入新的“拉不到包”风险。

6.1  全部公共 crate 的治理分类

把 cmx-container/crates/libs 下每一个 crate 按“独立世界里怎么办”归类。判据：脊柱进 cmx-shared，多域共用 可选脊柱按需进，非必带 切片只取一部分 留在单体是框架/门面/示例，独立世界不需要

基础设施叶子（全进脊柱——被 ≥2 域用、依赖极浅）

crate归类依赖 / 被谁用 / 理由
cmx-core · cmx-utils脊柱零/浅依赖的地基，人人都用。
cmx-traits · cmx-buffer · cmx-rowsource脊柱trait / 缓冲 / 零拷贝行源，database 与各 store 的底座。
cmx-database（抽象层）脊柱deps: buffer/core/rowsource/utils/traits/modql。doc/iam/biz/storage/metadata 都要。
cmx-database-pg脊柱PG 实现 + 全局池 + ZmcDataSet。所有 store-pg 的命脉。
modql (+ modql-macros)脊柱11 个 crate 在用的 SQL DSL；database/api-types/biz/iam/auth… 全靠它。必进。
cmx-api-types脊柱deps: modql/core/database。跨层 DTO，rpt-store/dct-store/storage/job-store/ai 都引。
cmx-model-meta脊柱定义/元数据 resolve；doc/dct 解析 metaKind 用。
cmx-web-kernel 新建脊柱替 cmx-api 的 4 个等价物（DbId extractor / ServiceError / 响应）；两种宿主 + 各域 *-routes 共用。约 100 行。见 §8.2。

crate归类依赖 / 判断

▶ 三条治理定律（从上表提炼）
①「core+store 进脊柱，api 壳自造」——凡是 X-core / X-store-pg / X-api 三段式（job 就是），前两段共享、第三段各服务重写。  ②「牵出 service/portal/rpc 的一律留单体」——plugin/form/rpc/nacos 是宿主平台能力，不是业务算核。  ③「biz 必须切片」——整包 biz 会把 service+portal 框架偷渡进独立世界，只带 biz-kernel。
◆ “可选脊柱”怎么落地
脊柱 workspace 里，把 iam/audit/auth/storage/ai/plugin-sdk/macros 做成独立 crate 但默认不被任何域引用——各业务 -service 的 Cargo.toml 按需 path 引。这样脊柱是“可取用的货架”，而非“人人背的全集”：flow 只取 database-pg 一线（连 biz-kernel 都不用），rpt 多取 job-core，需要登录的服务才取 iam 一带。

① biz-kernel 拆两半更精。 校验半（validate_*·TableSpec·Violation·ValidateOptions）与 错误半（BizError·from_db_error·errcode）可拆成 cmx-biz-validate + cmx-biz-error 两 feature/子 crate：flow 两半都不用、rpt 只用错误半、doc/dct 两半全用。建议先合成一个 biz-kernel 带 features=["validate"] 开关，rpt 关掉校验半即可。  ② model-meta 只有 dct 真需要。 doc 虽在 -api 声明了 model-meta，保留层零用量——独立后 doc-service 可不引 model-meta，只 dct 引。货架命中面比声明表更窄。

08域贡献 Router + 两种宿主（替掉 -api）

这是全方案唯一需要新写代码的地方，且已有 cmx-flow-demo 逐行可抄。核心是把“路由代码”和“运行它的进程”解耦：每个域产出一个*-routes 库（不带 state 的 Router），宿主负责 merge + 绑端口 + 上池。于是共用 web-server（宿主 A）与各域独立 -service（宿主 B）复用同一份路由代码。

8.1 域侧：每域一个 *-routes 库（无 state，可被任意宿主 merge）

这就是原 -api 的 handler，删掉对 cmx-api 的 4 个符号后剩下的纯路由。关键前提（demo 已验证）：DB 池是全局单例、引擎是 OnceCell，都不塞进 CmxAppState——所以域的 Router 是 Router<()>，天生可 merge。

// crates/flow-routes/src/lib.rs —— 域只负责“交出一段路由”，不关心谁来跑
pub fn routes() -> Router {                    // ← Router<()>，无 state
    Router::new()
        .route("/flow/definitions", get(list_defs).post(create_def))
        .route("/flow/instances/:id", get(get_instance))
        .route("/flow/tasks/:id/complete", post(complete_task))
        // … 20 条端点，handler 主体从 flow-api 原样搬
}
pub fn web_assets_dir() -> &str { "web/portal/flow" }  // 该域的前端工作台目录
pub async fn ensure_datasources() { /* 注册本域要的库；见 8.2 */ }

8.2 自造 4 个框架等价物（顶掉 cmx-api 的“腰”）——放在 cmx-web-kernel（宿主共享）

这 4 样是所有域和两种宿主共用的，抽到一个薄 crate cmx-web-kernel（进脊柱货架），域库和宿主都 path 引：

原 cmx-api 符号cmx-web-kernel 里的独立等价物
CmxAppState不再需要 state——域 Router<()>，池/引擎走全局单例。宿主 Router::new() 直接 merge。
ModuleRoutes::routes()退化成一个普通约定：域库导出 fn routes() -> Router。宿主按配置收集并 merge（见 8.3）。
CmxSvrContext / get_db_id_from_header薄 extractor DbId：从 header（X-Db-Id）取库名，缺省回落默认数据源。十几行，两种宿主共用。
ApiResp / Error / Resultenum ServiceError + impl IntoResponse；沿用各域 store-pg 的 from_db_error 优雅翻译。

8.3 宿主 A：共用 cmx-web-server，配置装载不同域

一个二进制，用编译期 feature + 运行期配置双重控制装哪些域：

# config.toml —— 运行期决定这台进程跑哪几个域
[server] port = 8080
modules = ["rpt", "flow", "doc", "dct"]     # ← 改这行就换服务组合
[db] fico = "postgres://…/fico"
      cmx  = "postgres://…/cmx"
// cmx-web-server/src/main.rs —— 配置驱动的装载器（对标今天 web-server 的 routes.rs，但不硬编码）
#[tokio::main]
async fn main() {
    let cfg = Config::load();  init_tracing();
    for (id,url) in cfg.db { register_datasource(&id,&url, id==cfg.default_db).await; }
    let mut app = Router::new();
    for m in &cfg.modules {                       // ← 按配置 merge
        app = match m.as_str() {
            "flow" => app.merge(flow_routes::routes()).nest_service("/flow/ui", serve(flow_routes::web_assets_dir())),
            "rpt"  => app.merge(rpt_routes::routes()).nest_service("/rpt/ui",  serve(rpt_routes::web_assets_dir())),
            "doc"  => app.merge(doc_routes::routes()),
            "dct"  => app.merge(dct_routes::routes()),
            _ => { warn!("unknown module {m}"); app }
        };
    }
    serve(TcpListener::bind(("0.0.0.0", cfg.server.port)).await, app.layer(CorsLayer::permissive())).await;
}
◆ 编译期也能裁剪（可选，进一步瘦身）
在 cmx-web-server/Cargo.toml 用 feature gate：features = ["flow","rpt","doc","dct"]，#[cfg(feature="flow")] 才把 flow-routes 编进来。这样“只跑报表”的镜像连流程引擎的代码都不编入——运行期配置管‘装不装’，编译期 feature 管‘编不编’，两级都可裁。默认全开，按部署需要关。

8.4 宿主 B：各域独立 -service（强隔离，原案保留）

#[tokio::main]
async fn main() {
    init_tracing();  flow_routes::ensure_datasources().await;
    let app = Router::new()
        .merge(flow_routes::routes())                // ← 同一个 routes()，只 merge 自己
        .nest_service("/", serve(flow_routes::web_assets_dir()));
    serve(TcpListener::bind(("0.0.0.0", env("PORT").unwrap_or("8181"))).await, app).await;
}
// ← 与宿主 A 调的是同一个 flow_routes::routes()。零重复代码。

8.5 全局 DB 池（两种宿主共用；抄 demo 的 register_datasource）

// 与 cmx-flow-demo 完全一致：进程启动时注册数据源到全局池管理器（不进 state）
async fn register_datasource(db_id:&str, url:&str, default:bool) {
    let cfg = DbConfig{ db_type:DbType::Postgres, db_url:url.into(),
        db_id:db_id.into(), db_schema:Some("public".into()), default,
        pool_config:Default::default(), health_check_interval:60, health_check_timeout:5,
        source_type:Some("default".into()), ..Default::default() };
    get_default_pg_db_manager().register_data_source(cfg).await.unwrap_or_else(..);
}
// 宿主 A 从 config.toml 的 [db] 段循环注册；宿主 B 从 env 注册。池是全局的，域 handler 直接取。

8.6 handler 几乎零改

-api 里每个 handler 主体（取 db_id → 调 store-pg / engine → 包 ApiResp）逻辑不变，只把 State<CmxAppState>/CmxSvrContext 换成 DbId extractor，把 ApiResp 换成 ServiceError。业务代码一行不动，且两种宿主下完全一致。

▶ 一句话：为什么“共用 web-server”几乎免费
因为域早已不依赖 CmxAppState（池/引擎是全局单例，demo 实证）。既然域的 Router 无 state，“谁来 merge 它”就无关紧要——今天硬编码在 web-server 的 routes.rs，明天由 config.toml 的 modules=[…] 驱动，改动只在宿主一侧，域库零感知。

10数据库与配置（独立自举）

  • 连库：每服务启动 register_datasource 注册自己需要的库。flow/rpt 主要 fico 库（cr_*/cmx_flow_*），可能附 cmx 库（IAM/org）。url 全走 env（FICO_PG_URL / IAM_PG_URL / PORT / X-Db-Id header）。
  • 建表：各 store-pg 已有 ensure_schema 幂等建表/补列（记忆里多处“幂等补列坑”已趟平），独立服务首启自建缺表。注意并发建表竞争用 ensure_schema 容错。
  • dev-local.toml 陷阱（记忆）：[portal] 段的 web_*_dist/data_root 必须在 [portal] 段下，错并到别的段会导致 /portal/* 全 404。独立服务用自己的极简 config，绕开该坑。
  • bigint 主键铸号（记忆）：DCT/DOC 的 id 在后端首次存储铸号（52 位 JS 安全算法 + 配置注入 node）。独立服务要把该配置注入保留，导入免改号契约不变。
◆ 库是共享的，进程是独立的
独立化拆的是进程与代码依赖，不是数据库。flow/rpt/doc/dct 仍可连同一个 PG 实例的同一批库（表前缀天然隔离 cmx_flow_*/cr_*/cv_*/cf_*），只是各自持有独立连接池。是否进一步拆库是后续运维选择，不在本方案强制。

14部署（Docker / 编排）

两种宿主 → 两种编排姿态，共享同一份域库，按部署规模选，甚至混用。

姿态 A · 共用宿主：一个 cmx-web-server 装多域（省资源，开发/中小生产）

# docker-compose：一个进程按配置装 4 个域 + 一个 PG
services:
  postgres: { image: postgres:16, environment: { POSTGRES_PASSWORD: postgres } }
  cmx: { build: ./cmx-web-server, ports: ["8080:8080"],
        volumes: ["./config.toml:/app/config.toml"] }   # modules=["rpt","flow","doc","dct"]
  # 换服务组合 = 改 config.toml 的 modules 一行，重启即可；无需重新编排

姿态 B · 独立宿主：每域一个 -service（强隔离，报表挂了不拖垮流程）

services:
  postgres: { image: postgres:16, environment: { POSTGRES_PASSWORD: postgres } }
  flow: { build: ./cmx-flow, ports: ["8181:8181"], environment: { FICO_PG_URL: "postgres://…@postgres:5432/fico", PORT: "8181" } }
  rpt:  { build: ./cmx-rpt,  ports: ["8182:8182"], environment: { FICO_PG_URL: "…fico", PORT: "8182" } }
  doc:  { build: ./cmx-doc,  ports: ["8183:8183"], ... }
  dct:  { build: ./cmx-dct,  ports: ["8184:8184"], ... }
  gateway: { image: nginx, ports: ["8080:80"] }   # 反代 /flow /rpt /doc /dct → 各服务

姿态 C · 混用（推荐生产）

把高负载/需独立扩缩的域（如 rpt 批量算表）单独起姿态 B，其余低频域挤进一个姿态 A 进程。因两者复用同一 *-routes，混用零额外代码——只是编排文件的选择。

共同要点：① 各宿主无状态（状态在 PG），可横向扩副本（rpt 若接 job-core 已有 SKIP LOCKED 抢占式 HA）；② 姿态 B 独立发版（报表升级不重启流程），姿态 A 改 config.toml 换组合；③ 健康检查 /health（新增约 30 行，两宿主共用）。

16风险与开放问题

议题程度应对
脊柱切分边界（哪些 crate 进 cmx-shared）中以“被≥2 个域引用”为纳入判据；cmx-database / -pg / core / utils / rowsource / model-meta / biz-kernel / api-types 明确进。IM-0 一次落定。
cmx-biz 切片（validation/errcode 是否自洽）中切 cmx-biz-kernel 时验证 from_db_error/validate_insert_row/Violation 的传递闭包是否只落在脊柱内；若牵出更多依赖，扩薄片或整包纳入。
rpt 的 cmx-job-core 耦合中试点先同步执行 compute/verify；确需长任务再把 job-core/store-pg 纳入脊柱（其 HA/持久化已实测）。
doc 依赖 cmx-database 抽象层低连同 cmx-database 一起纳入脊柱即可，非新代码。
前端 base / 菜单前缀随挂载点变低vite --base + cmx_menu.definition 各服务只带自身菜单；已有 cross-env 坑的成方。
IAM/org 跨域（flow 读 cmx_org、doc 铸号 node 配置）低按表名读、无 crate 依赖，天然可断；node 配置注入随 env 带走。
独立粒度（五域各一 / 先试点一个）待定见 §5.5 与决策 ①——需用户确认。
脊柱共享方式（path / 内网 registry）待定默认 path（简单）；发 registry 后置。见决策 ②。
宿主策略（共用 A / 独立 B / 混用）待定两宿主复用同一 *-routes，可都产出、按部署选。默认两者都做（A 便于开发+中小生产，B 供强隔离）。见决策 ④ / §5.7 / §8。
meta 是否需独立服务待定取决于是否要独立建模工作台；否则仅作脊柱库。见 §7-meta。
iam/身份是否进脊柱货架待定iam 可干净抽出（零框架依赖），但当前各域只按表名读 cmx_org、不 crate 依赖它。默认放「可选货架」，谁要登录/权限 API 才引。见 §6.1。
job 中心：先同步 or 直接接 core低job-core 仅依赖 utils、且 rpt-store 已引 → 直接进脊柱最省事；rpt-service 首版可先不接 SSE 端点（同步 compute），M-后置补 job-api 壳。
