cmx-docwright · 无头业务单据

在 cmx-hierarchy 层级引擎外面套一层「协议 + 传输」的壳，让它像无头浏览器那样被进程外驱动：装载 → 改行 → 逐层上卷 → 校验 → 过账落库 → 出单据。与 cmx-sheetwright 之于 cmx-rust-sheet 完全同构——那是无头电子表格，这是无头业务单据。

对标样板：cmx-sheetwright（无头 Excel：protocol/convert/server 三层） ·  引擎：cmx-hierarchy（已落地：hier-core/agg/store-pg + 门面，38 测试绿） ·  落点：presentation/cmx-docwright/（与 cmx-container 并列） ·  本文档：仅方案，不含实现代码
⚠ 方向修正（2026-08）：引擎已改为 cmx-container 叶子 crate
本方案写作时，引擎设想为独立 workspace cmx-hierarchy。后经用户澄清并已落地修正：后端主从协调器做成 cmx-container 叶子 crate cmx-master-slave（struct CmxMasterSlave + trait HierService），doc/dct 服务 impl 它、复用现成加载保存（服务依赖协调器，非协调器依赖服务）。
故本无头壳若落地，驱动应经 CmxMasterSlave::{load_via, save_via, expand_via} 打到某个 HierService 实现（DocHierService / DctHierService），而非本文所述的自造引擎门面。协议动词 / CLI / HTTP 三层设计仍适用，只是底座换成叶子 crate + 可换服务。

01为什么叫「无头业务单据」

前端 CmxMasterSlave 是业务单据的「有头」形态：浏览器里，一个主表单 + N 个子表格，选行联动、改值即时汇总反馈。但那颗「头」——DOM、视图、鼠标——只是交互外壳。单据真正的骨肉是：层级结构、逐层上卷、落库前校验、铸号、乐观锁、过账事务。

cmx-docwright 把这颗头摘掉，只留骨肉，用中性 JSON 脚本驱动：喂一串"动词"（装载/改行/上卷/保存），引擎在后端执行，吐出结果——不要浏览器、不要 CmxMasterSlave、不要人在场。

◆ 一句话
cmx-hierarchy 是引擎（骨肉），cmx-docwright 是让它进程外可驱动的那层壳（协议 + CLI + HTTP）。目的与 cmx-sheetwright 一字不差：后端无头运行业务对象——sheet 无头出报表，doc 无头过单据。

03引擎现状：已经有什么

骨肉已经落地（cmx-hierarchy，见其方案与代码）。壳能直接调的门面方法：

门面 API（HierManager）作用状态
load_tree(query)装载完整层级树（形状 A/B）已实现
expand(path, ids)懒加载子层 / 大树下钻已实现
save(changeset)铸号→校验→写时上卷→单事务落库→乐观锁→派生列重算已实现
rollup_read_only(tree) / rollup_in_place读时上卷 / 内存试算（不落库）已实现

底层：hier-core（树/schema/数值语义）· hier-agg（汇总引擎，成环拒）· hier-store-pg（两形状装载 + 变更集事务 + 铸号 + CTE 重算）。38 测试绿，clippy 干净。

04缺的只是「一层壳」

引擎是库——只能被 Rust 进程内 use。要"无头业务单据"，缺三样，全是壳的活，零引擎改动：

① 驱动协议

一套中性 JSON 动词（load/setCell/addRow/rollup/save/export）+ 批请求/响应。把 JSON「动词」一对一翻成门面调用。唯一真正的新设计。

② CLI

cmxdoc run script.json / post voucher.json。命令行喂脚本，无头过账、试算、导出。

③ HTTP

axum，POST /run 吃脚本、/save、/load。任何语言的调用方（含前端）都能驱动。

✅ 顺带解决前端互通
协议动词的 JSON 形状 = 前端契约：save 的 payload 正是 ChangeSetCollector.export() 的产出；load 的响应经 export 成列式包，正是 CmxDataSet.fromJSON 吃的。互通不是单独的活，是协议壳的自然产物（详见 §11）。

05三种壳形态

沿用 sheetwright 的三形态，按推荐度：

形态交付用途推荐
A · CLIcmxdoc 二进制批量过账、定时试算、单据迁移/导出；CI 里跑校验。首选
B · HTTPcmxdoc serve（axum）服务化：前端 / 其它语言 POST /run 驱动；与各业务服务解耦。次选
C · 库直接 use cmx_hierarchyRust 后端进程内嵌。已就绪（引擎本身）。已有

A/B 共享同一份 protocol 模块（动词→引擎的翻译），只是传输不同——与 sheetwright 一致。

06驱动协议：动词映射到引擎

唯一真正的新设计。一段脚本 = 一次会话的动词序列，服务端顺序执行，最后一并返回。对齐 sheetwright 的 Op 枚举 + RunRequest/RunResponse。

6.1 动词集（Op，#[serde(tag="op")]）

动词payload翻成引擎调用
load{ query: LoadQuery }mgr.load_tree(query) → 会话持有该树
expand{ path, parentIds:[] }mgr.expand(path, ids) → 并入会话树
setCell{ path, id, field, value }会话树内改一格（供随后 rollup/save）
addRow{ path, row, parentId? }会话树内插一行（temp id）
deleteRow{ path, id }会话树内删一行
rollup{ mode: "write"|"read" }rollup_in_place（试算）/ rollup_read_only
save{ changeset?, mode:"merge" }mgr.save(changeset)；缺省则用会话累积的变更集
read{ path, id?, field? }读会话树某格/某行（回执用）
export{ format:"columnar"|"nested"|"json" }会话树 → 列式包（喂前端）/ 嵌套 JSON

6.2 批请求 / 响应（RunRequest / RunResponse）

// 一次凭证过账：装载定义 → 改行 → 写时上卷 → 落库 → 回执
{
  "schema": { /* HierSchema：形状+layers+relations+aggregations */ },
  "dbId": "fico",
  "ops": [
    { "op":"save", "changeset": {
        "cv_header":   { "inserted":[{"id":"t1","voucher_no":"V001"}] },
        "cv_acc_line": { "inserted":[
            {"id":"t2","upper_id":"t1","local_dr":100},
            {"id":"t3","upper_id":"t1","local_cr":100} ] }
      }}
  ]
}
// 响应
{ "ok":true, "results":[
    { "op":"save", "affected":3,
      "idMap":{"t1":7001,"t2":7002,"t3":7003},
      "updatedAt":[/* 乐观锁新基线 */] } ] }
⚠ 补 serde + 两个字段（上一轮"互通"识别的接线件都在这里）
引擎侧的 ChangeSet/LayerChanges/SaveOutcome 目前只 derive 了 Debug/Clone。协议壳要给它们加 Serialize/Deserialize，并给 SaveOutcome 补 updated_at（收集各行新基线回传）。这是协议层的活，不侵入引擎逻辑。

07会话模型：async + Send（与 sheet 恰好相反）

这是与 sheetwright 唯一的实质差异，值得钉死。

维度cmx-sheetwrightcmx-docwright
引擎调用同步（Workbook 纯内存）async（HierManager 连 DB）
Send 约束Workbook 是 !Send（含 Rc/RefCell）引擎天然 Send（arena 树，无 Rc/RefCell）
会话状态无状态：每请求现造 Workbook，算完转 Send 产物即扔会话可短暂持有一棵内存树（HierTree 是 Send，可跨 .await）
并发纪律所有引擎调用关进 spawn_blocking直接 async，无需 spawn_blocking；DB 池本就异步
◆ 因此 docwright 的壳更简单
sheet 的壳要费力隔离 !Send；doc 的引擎本就是 async + Send，壳只是"把 JSON 动词 .await 到门面"。一次会话 = 装载出一棵 HierTree（Send，可跨 await），动词在其上累积，最后 save 落库。无状态模式（每请求自足）与有状态会话（多动词共享一棵树）都能支持——推荐单请求内有状态、跨请求无状态（一个 RunRequest 自带装载+变更+保存，服务端不留会话）。

08分层架构（壳不侵入引擎）

presentation/cmx-docwright/ # 无头壳，与 cmx-container / cmx-hierarchy 并列 │ 唯一领域依赖：path 引 cmx-hierarchy 门面（非 workspace 成员，独立项目） ├─ src/ │ ├─ protocol.rs ← 驱动协议：Op 动词枚举 + RunRequest/RunResponse │ │ + ChangeSet/SaveOutcome 的 serde（唯一新设计） │ ├─ session.rs ← 会话：持一棵 HierTree，动词在其上累积 → save │ ├─ convert.rs ← 无状态转换：单据树 ↔ columnar/nested/json（喂前端） │ ├─ server.rs ← HTTP 传输（serve 子命令，axum，async 直调） │ └─ bin/docwright.rs ← CLI 入口（clap） └─ docs/方案.html ← 本文档 依赖（path，单向，不并入任何 workspace）： cmx-hierarchy = { path = "../cmx-hierarchy/crates/cmx-hierarchy" } serde/serde_json · clap · tokio · axum
◆ 纪律：壳只翻译，不含业务逻辑
protocol 把 JSON 动词一对一 .await 到 HierManager 门面；校验/铸号/上卷/事务全在引擎里。壳零业务判断——换个业务域（采购单、BOM、组织树）不改一行壳代码，只换 schema。这与引擎的"业务无感知"底线一脉相承。

09HTTP 端点草案（形态 B）

端点请求 / 响应
POST /run吃完整 RunRequest（schema + dbId + ops[]），顺序执行，返回 RunResponse。主入口，一次自足。
POST /save便捷：{schema, dbId, changeset} → 校验+铸号+上卷+落库 → {affected, idMap, updatedAt}。校验失败 422 带 violations，冲突 409。
POST /load便捷：{schema, dbId, query} → 列式包（前端 CmxDataSet.fromJSON 直吃）。
POST /rollup便捷：{schema, tree} → 读时上卷结果（不落库，纯试算）。
GET /health存活探针（~10 行）。

全部无状态：每请求自带 schema + dbId，服务端不留会话。引擎 async 直调，无需 spawn_blocking（见 §7）。错误映射沿用引擎的 422/409/500 语义。

10CLI 草案（形态 A）

# 过账：喂一个 RunRequest 脚本（含 schema + 变更集）
cmxdoc run voucher-post.json --db fico

# 便捷过账：schema 与数据分开
cmxdoc post --schema voucher.schema.json --changes v001.json --db fico

# 无头试算：只上卷不落库，打印结果（借贷平衡校验、层间小计）
cmxdoc rollup --schema voucher.schema.json --data tree.json

# 装载导出：把某组织的单据树导成 JSON（迁移/对账）
cmxdoc load --schema voucher.schema.json --query '{"root_filter":{"org":"HQ"}}' --db fico > out.json

# 批量：目录下每个 *.json 过一遍（CI 校验 / 批量导入）
cmxdoc batch ./vouchers/ --schema voucher.schema.json --db fico
◆ 无头业务单据的真实用途（都无浏览器）
① 批量过账：一次几千张凭证，校验+铸号+逐层上卷+落库。② 无头试算：借贷平衡、层间小计现算不落库。③ 单据迁移/对账：装载一组织树 → 导 JSON → 灌另一库（铸号跨部署不撞，免改号）。④ CI 校验：把单据定义 + 样例数据跑一遍，回归结构/校验规则。

11前端 CmxMasterSlave 互通（顺带解决）

协议壳一旦成立，前后端往返自然接通——因为动词的 JSON 形状本就是前端契约。上一轮识别的 4 个接线件，全部落在协议层：

方向协议动词前端对接点
前端保存 → 引擎save 的 changesetChangeSetCollector.export() 产出 = save payload（同结构，补 serde 即通）
引擎装载 → 前端load / export{columnar}列式包 {datasetId,columns,rows,childRows} = CmxDataSet.fromJSON 直吃
保存回执 → 前端save 响应{idMap, updatedAt} → 前端 temp 行采用真 id + refreshBaselines 刷乐观锁
汇总规则 双向schema.aggregations前端 aggregations ↔ 引擎 AggRule（已逐字对齐）
✅ 互通是协议的产物，不是单独工程
做协议壳时给 ChangeSet/SaveOutcome 加 serde、写 HierTree → 列式包 编码器（底层 ZmcDataSet.encode_columnar_json 已存在）、SaveOutcome 补 updated_at——这三件正是协议动词 save/load/export 的实现内容。做完协议壳，前后端端到端往返即通：前端导出的 changeset 喂 CLI 过账，引擎装载结果喂回前端渲染。

13风险与取舍

  • 壳绝不含业务逻辑（底线）：protocol 只做 JSON 动词 → 门面调用的翻译；校验/铸号/上卷/事务全在引擎。任何"为某类单据在壳里加分支"都是架构倒退，必须拒绝——与引擎的业务无感知一脉相承。
  • 会话状态的边界：推荐单请求内有状态、跨请求无状态（一个 RunRequest 自带装载+变更+保存，服务端不留会话），避免分布式会话粘性。需要长会话（人工逐步编辑）时再评估有状态服务，但那更像"有头"，与无头定位相悖。
  • schema 从哪来：壳吃已解析的 HierSchema。DOC/DCT 的定义 JSON → HierSchema 的适配，放调用方还是壳带一个 adapter？倾向调用方（保壳中立）；可提供一个可选 hier-adapter 便捷件。
  • 与 sheet 壳的差异要记住：doc 引擎是 async+Send，不要照抄 sheetwright 的 spawn_blocking 隔离——那是为 !Send 的 Workbook 准备的，doc 不需要，直接 async 更简单（§7）。
  • 校验 TableSpec 仍是引擎侧待补：cmx-hierarchy 的 build_layer_spec 现返回空 spec。壳做 DOC/DCT 对拍前，引擎需从定义 JSON 的 fields 经 build_table_spec 构造并缓存（HM-5 一并做）。
  • 不过度统一：docwright 与 sheetwright 是同构而非同一——共享"引擎+无头壳+协议"的姿态，但动词集、产出、会话纪律各按领域定。别强行合并成一个壳。
▶ 落地前需用户拍板
① 壳落点：独立 cmx-docwright/（与 cmx-hierarchy 并列，对标 sheetwright，推荐）还是并进 cmx-hierarchy workspace 加 hier-cli/hier-service 两 crate？   ② 先做哪个形态：CLI（推荐，批量过账最实用）还是 HTTP？   ③ 会话模型：单请求自足（推荐）还是要跨请求长会话？
