报表两模式加载存储 —— ReportModel 单一事实源方案

设计版式（样式/属性/结构，Excel 兼容 BLOB）与报表数据（单元格取值）分离加载存储，统一收敛到一个 ReportModel；SpreadJS 组件只负责可视化与编辑。

0核心结论 · TL;DR

  1. ReportModel 是唯一事实源。报表的结构（sheet/区域/行/列）、版式（列宽行高/合并/样式/数字格式）、属性（报表/sheet/区域元数据）、数据（单元格取值）全部在一个 JS 模型对象里。SpreadJS 组件只是这个模型的渲染器 + 编辑器，不持有独立真相。
  2. 结构层级：Report ▸ Sheet ▸ Region ▸ Row×Col ▸ Cell。一个报表多 sheet，一个 sheet 多区域，行/列/单元格都定义在区域里——单元格 = 区域内 某行 × 某列（region_code + row_id + col_id）。不定义区域时，系统提供默认区域（覆盖整个 sheet）承载所有行列单元格。见 §1.2。
  3. 两种模式共享同一个 ReportModel，只是加载/存储的"层"不同：
    • 模式一 · 设计版式 加载/存储 meta + sheets[].{props,grid} + regions[].{rows,cols,cells(结构与样式,不含运行值)}。落地到 cr_report_fmt.doc_content（Excel 最新格式 BLOB）+ 关系表（cr_report_sheet / cr_report_region / cr_report_row / cr_report_col，行列表均以 region_code 为唯一键成分）。
    • 模式二 · 报表数据 在完整版式已加载的前提下，仅加载/存储单元格数据（cr_cell_data，按 org+period+region+row_id+col_id 维度），回填进同一个 ReportModel 的 regions[].cells[].value。
  4. Excel 最新格式 = SpreadJS 原生 SSJSON（workbook.toJSON()）存入 doc_content BLOB，兼具"完整可复原"与"可 xlsx 互转"；关系表是可查询的镜像投影（供取数引擎/报表列表按区域+行列检索），不是主真相。BLOB 为主，关系表为投影。
  5. 公式的定义与计算过程本方案不展开——模型里为公式预留字段（cell.formula / row.formula / col.formula / element 计算校验公式），加载存储链路原样透传，计算引擎另案（M2 已有 /api/rpt/compute 雏形）。
一句话架构：一个模型（ReportModel）· 两层加载（版式层 / 数据层）· 两处落地（BLOB 主 + 关系表投影）· 组件纯展示编辑。

1ReportModel 单一事实源

当前 designer.js 的 reportModel(st) 只造了一个演示骨架（title/编码/版本几个格）。本方案把它升级为承载全部报表信息的完整模型。组件 cmx-spreadjs-sheet 的 setReportModel() 消费它渲染，编辑事件回写它，getReportModel() / getWorkbook().toJSON() 导出它。

1.1 模型完整结构

// ReportModel —— 报表单一事实源（设计版式 + 数据 + 属性 全在此）
{
  meta: {                         // 报表级属性（↔ cr_report_list / cr_report_version）
    reportCode, reportName, version,   // 身份三元
    reportType, reportCategory,        // 类型/类别
    periodType, currencyCode, amountUnit, entityScope,
    dataSource, isStatutory, remark,
    versionStatus, isCurrent, effectiveFrom, effectiveTo,
    formatCode                         // 关联 cr_report_fmt
  },

  sheets: [ {                      // 每个 sheet（↔ cr_report_sheet，sheet_index 排序）
    id, name, sheetIndex,
    props: {                       // sheet 属性（↔ cr_report_sheet 各列）
      sheetType, tabColor, rowCount, colCount,
      headerRows, fixedRows, fixedCols,
      paperSize, orientation, fontFamily, fontSize,
      showGridline, isHidden, titleStyle, headerStyle
    },
    grid: {                        // sheet 级画布版式（列宽/行高/合并/样式类）——跨区域共享
      rows, cols,
      colWidths:{A:56,B:140,...}, rowHeights:{1:34,...},
      merges:['B1:E1', ...],
      styleClasses:{ title:{bold,fontSize,align,fillColor,fontColor}, label:{...} }
    },
    regions: [ {                   // ★ 区域是行/列/单元格的容器（↔ cr_report_region）
      code, name, type,                // 区域身份（region_code 在 row/col/cell 唯一键里）
      startCell, endCell,              // 区域在画布上的矩形范围（A1 坐标）
      startRow, startCol, endRow, endCol,
      direction, isRepeatable, isMerged, freezeFlag, dataSource,
      bgColor, borderStyle, style,
      isDefault,                       // ★ 是否系统默认区域（未显式定义区域时）

      rows: [ {                    // 行定义在区域内（↔ cr_report_row，含层级）
        id, code, name, rowNo, lineNo, rowType,
        parentId, fullPath, levelNo, isLeaf,
        formula, accountRange, balanceDir, indent, isBold
      } ],
      cols: [ {                    // 列定义在区域内（↔ cr_report_col，含层级）
        id, code, name, colNo, colLetter, colType,
        parentId, fullPath, levelNo, isLeaf,
        valueType, periodOffset, width, decimals, align, formula, isHidden
      } ],
      cells: {                    // 单元格 = 区域内 某行 × 某列 的交点（A1 键，相对/绝对）
        "B1": {
          type:'text|calc|fetch|ref',  // 单元格类型
          rowId, colId, cellRef,       // ★ 由区域内 row×col 决定（rowId/colId → 本区域行列）
          value: ...,                   // ← 模式二数据层回填（cr_cell_data）
          formula:'=QM("1001")',        // ← 公式（本方案透传，不计算）
          class:'title',                // 样式类引用（引 sheet.grid.styleClasses）
          style:{bold,italic,align,valign,fontColor,fillColor,format,border,fontSize,fontFamily,wordWrap},
          // —— 数据元素绑定（设计态；↔ cr_cell_element_map）——
          elementCode, valueType, dataSource, calcFormula, checkFormula,
          isEditable, numberFormat
        }
      }
    } ]
  } ],

  workbookJson: { ... }          // SpreadJS 原生 SSJSON（toJSON），Excel 最新格式的完整快照
}
★ 层级关系（本次修正）：报表 Report → Sheet(多) → Region(多) → 行 Row × 列 Col → 单元格 Cell。行、列、单元格都定义在区域里——一个单元格由"它所属区域内的某行 × 某列"确定（region_code + row_id + col_id，这正是 DB 里 cr_report_row/col/cell_data 唯一键的构成）。不定义区域时，系统提供一个覆盖整个 sheet 的默认区域（isDefault:true，如 region_code='__default__'），所有行列单元格挂在其下——语义与显式区域完全一致，保证"总有一个区域承载单元格"。
为什么 grid 仍在 sheet 级、而 rows/cols/cells 下沉到 region？grid（列宽/行高/合并/样式类）是 SpreadJS 画布属性，天然属于整个 sheet（一列的宽度不分区域）；而 rows/cols/cells 是业务结构，按区域切分（同一 sheet 上"资产区""负债区"各有自己的行列体系）。二者视角不同，不矛盾——区域的 startCell:endCell 把业务行列投影到画布网格坐标。
为什么同时保留结构化字段 与 workbookJson？结构化字段（region→row/col/cell）是业务视角（供关系表投影、取数引擎按区域+行列检索）；workbookJson 是渲染视角（SpreadJS 无损复原画布）。存储时两者都写：BLOB 存 workbookJson（主），关系表存结构化字段（投影）。见 §2.3。

1.2 结构层级 —— Report ▸ Sheet ▸ Region ▸ Row×Col ▸ Cell

Report (报表 · cr_report_list + cr_report_version)
 └─ Sheet ×N            (子表 · cr_report_sheet · sheet_index 排序)
     ├─ grid              (sheet 级画布：列宽/行高/合并/样式类 — 跨区域共享)
     └─ Region ×N        (★ 区域 · cr_report_region · 行列单元格的容器)
         │                  未显式定义 → 系统默认区域 __default__（覆盖整个 sheet）
         ├─ Row ×N        (行 · cr_report_row · 唯一键含 region_code · 可层级)
         ├─ Col ×N        (列 · cr_report_col · 唯一键含 region_code · 可层级)
         └─ Cell          (单元格 = 本区域内 某 Row × 某 Col 的交点)
              = region_code + row_id + col_id   ← cr_cell_data / cr_cell_element_map 唯一键
■ 一个报表 可多 Sheet ■ 一个 Sheet 可多 Region ■ 一个 Region 定义自己的 Row/Col 体系 ■ Cell 由 Region 内 Row×Col 决定 ■ 无 Region → 默认区域兜底
默认区域语义：当报表设计未划分区域时，系统隐式提供一个 region_code='__default__'、isDefault:true 的区域，其范围 = 整个 sheet（startCell='A1', endCell= 右下角）。所有行/列/单元格挂在它下面——落库时 cr_report_row/col/cell_data.region_code='__default__'，与显式区域走完全相同的读写链路。前端渲染/取数无需为"有无区域"分叉。

1.3 版式层 vs 数据层 —— 两模式的边界

模式一 · 设计版式层

"这张报表长什么样"——与组织/期间无关，一次设计多期复用。

  • meta（报表/版本属性）
  • sheets[].props（sheet 属性）
  • sheets[].grid（sheet 级画布：列宽/行高/合并/样式类）
  • sheets[].regions[]（★ 区域 = 行列单元格容器）
  • regions[].rows / cols（区域内行列设置，含层级、公式定义）
  • regions[].cells[].{type,formula,class,style,element绑定}（结构+样式+公式，不含运行值）
  • workbookJson（Excel 最新格式快照）
落地 → cr_report_fmt.doc_content(BLOB) + cr_report_sheet/region/row/col

模式二 · 报表数据层

"某组织某期间，各格实际是多少"——依赖组织+期间，每期一份值。

  • 单元格实际取值 cells[].value
  • 字符值 / 数值双存（text_value / num_value）
  • 数据状态（待取/已算/手工/锁定）
  • 数据元素绑定回读（element_code）
  • 计算时间、是否手工、币种、金额单位
落地 → cr_cell_data（org_code + period_code + 8 元唯一键）

前置：必须先加载模式一的完整版式，数据才有"格子"可落。

2.3 关系表 vs BLOB · 双写与职责

ReportModel
→
cr_report_fmt.doc_content
BLOB · 主真相 · 无损复原
+
cr_report_sheet/region/row/col
关系投影 · 可查询检索

BLOB（主）

  • 加载报表设计态：只读 BLOB → fromJSON，一次复原全部
  • 权威、无损、含 SpreadJS 内部细节
  • 对后端不透明（just bytes）

关系表（投影）

  • 取数引擎按 report+version+sheet+region+row+col 检索"哪格取哪个元素"
  • 报表设计资产统计（sheet/区域/行/列计数，已用于 property 面板）
  • 跨报表 RPTAREA 取区域（见既有方案）
  • 存储时从 model 派生写入；加载版式态不依赖它（BLOB 已够）
一致性规则：保存设计版式时事务内同时写 BLOB + 重建关系表投影（先 DELETE ... WHERE report+version 再批量 INSERT，幂等）。BLOB 写成功但投影失败 → 整事务回滚。BLOB 是真相，投影可从 model 重建，故投影损坏可由"重存一次"修复。

// designer.js —— 加载版式（model 中枢）
async function loadLayout(st){
  const {reportCode, version} = st.props
  const data = await apiJson(`/api/report-design/reports/${enc(reportCode)}/layout?version=${enc(version)}`)
  // data = { fmt:{doc_content, doc_format, content_hash}, meta, sheets, regions, rows, cols }
  const model = buildReportModel(st, data)   // 组装完整 ReportModel
  st.__model = model
  st.__contentHash = data.fmt?.content_hash    // 保存时做乐观并发校验
  const sheet = sheetElOf(root)
  if (data.fmt?.doc_content) {
    sheet.setWorkbookJson(decodeDoc(data.fmt))  // ← 优先：BLOB 无损复原（fromJSON）
  } else {
    sheet.setReportModel(model)                  // ← 回退：无 BLOB 时按结构化字段渲染（新报表）
  }
}
加载优先级：有 doc_content BLOB → fromJSON（快、无损）；无 BLOB（全新报表首次设计）→ 按 grid/cells 结构化字段 setReportModel 渲染初始骨架。两条路都产出同一个在屏模型。

// designer.js —— 保存版式（替换当前 saveDesign 的"本地下载占位"）
async function saveLayout(sheet, st){
  const wbJson = sheet.getWorkbook().toJSON({includeBindingSource:true})
  const model  = sheet.getReportModel()          // 结构化视角
  const payload = {
    version: st.props.version,
    fmt: {
      doc_content: encodeDoc(wbJson),               // ssjson (可 gzip→base64)
      doc_format: 'ssjson', mime_type:'application/json',
      content_hash: st.__contentHash                // 乐观锁：后端比对，冲突则 409
    },
    sheets:  deriveSheets(model),                    // → cr_report_sheet
    regions: deriveRegions(model),                   // → cr_report_region（含默认区域 __default__）
    rows:    deriveRows(model),                       // → cr_report_row（每行带 sheetCode+regionCode）
    cols:    deriveCols(model),                       // → cr_report_col（每列带 sheetCode+regionCode）
    cellMap: deriveCellElementMap(model)             // → cr_cell_element_map（region+row_id+col_id）
  }
  const res = await apiJson(`/api/report-design/reports/${enc(st.props.reportCode)}/layout`,
    {method:'POST', headers:{'Content-Type':'application/json'}, body:JSON.stringify(payload)})
  st.__contentHash = res.content_hash               // 更新哈希，供下次保存
  toast(root, '报表设计已保存', 'success')
}
复用现成：标题区"保存"按钮的 saveDesign() 已实现（当前是本地 JSON 下载占位）——只需把内部换成 saveLayout() 走后端端点。toast/事件广播已就绪。
derive* 的遍历与默认区域：四个 derive*() 遍历 model.sheets[].regions[].{rows,cols,cells}，为每条记录带上 sheetCode + regionCode（写进对应 cr_report_row/col 唯一键）。若某 sheet 无显式区域，model 里已有一个 isDefault:true 的 __default__ 区域兜底，遍历逻辑无需分叉——所有行列单元格都从"某个区域"派生，落库 region_code 恒有值。

4模式二 · 报表数据 加载/存储

在完整版式已加载（模式一产出的在屏 ReportModel）的前提下，选定组织 + 期间，加载该维度下各单元格的实际取值回填进模型；编辑后按同维度存储。

强前置依赖：数据层不能独立加载。没有版式（格子、区域、行列定义），单元格数据无处安放。UI 上：报表数据视图必须先有版式，再出现 [组织] [期间] 选择器。

// designer.js —— 加载报表数据（版式已在屏）
async function loadData(sheet, st, orgCode, periodCode){
  const rows = await apiJson(`/api/report-design/reports/${enc(st.props.reportCode)}/data/query`,
    {method:'POST', body:JSON.stringify({version:st.props.version, orgCode, periodCode})})
  // rows = [{cell_ref, sheet_code, region_code, row_id, col_id, text_value, num_value, value_type, data_status, element_code}]
  const valuesMap = {}
  for (const r of rows){
    const v = r.value_type==='number' ? r.num_value : r.text_value
    valuesMap[r.cell_ref] = v
    mergeIntoModel(st.__model, r)   // 定位 sheet→region→cells[cell_ref]，回填 value + 数据状态
  }
  sheet.setCellValues(valuesMap)     // 组件按 cell_ref(A1 画布坐标) 覆盖值（保留版式与公式）
}
画布坐标 vs 区域坐标：后端按 region+row_id+col_id 存值；回填时 mergeIntoModel 依 sheet_code+region_code 定位到 model 的对应区域，写进 region.cells[cell_ref]。而喂给组件的 setCellValues 用 cell_ref（A1 画布坐标）——因为 SpreadJS 画布是全 sheet 统一坐标系，区域只是它上面的逻辑矩形。region 的 startCell:endCell 是"区域行列 ↔ 画布 A1"的换算桥。
值覆盖 vs 公式：setCellValues 只覆盖取数格的显示值（如 QM 取数结果），不动纯公式格（SUM 等由 SpreadJS 原生重算）。这与既有 [[rpt-designer-mode]] 的"取数后端算、算术前端算"边界一致；本方案只搬运值，不触发计算。

4.2 存储链路

// designer.js —— 存储报表数据（按 org+period 落 cr_cell_data）
async function saveData(sheet, st, orgCode, periodCode){
  const model = sheet.getReportModel()
  const cells = collectDataCells(model)   // 遍历 regions[].cells，取有值/手工录入的格（带 sheetCode+regionCode）
  const payload = {
    version: st.props.version, orgCode, periodCode,
    cells: cells.map(c => ({
      sheetCode:c.sheetCode, regionCode:c.regionCode,
      rowId:c.rowId, colId:c.colId, cellRef:c.addr,
      elementCode:c.elementCode, valueType:c.valueType,
      textValue:c.text, numValue:c.num,
      dataStatus:c.status, isManual:c.isManual
    }))
  }
  await apiJson(`/api/report-design/reports/${enc(st.props.reportCode)}/data`,
    {method:'POST', body:JSON.stringify(payload)})
  toast(root,'报表数据已保存','success')
}
唯一键 UPSERT：cr_cell_data 8元唯一键 (org,period,report,version,sheet,region,row_id,col_id) → 后端 ON CONFLICT ... DO UPDATE，重复保存幂等；id BIGINT 代理键由后端铸号（见 [[bigint-id-backend-generation]]）。

5序列化契约 · 组件新增方法

组件需补两个方法承接 BLOB 存取（其余已在契约内，见记忆 [[rpt-spreadjs-designer-toolbar]]）：

方法签名实现状态

getReportModel()() → ReportModel已存 this._report；需扩展为回读画布最新版式（见下）扩展
getReportModel 的两种语义，需明确：
  • 浅回读（当前实现）：返回最后一次 setReportModel 的对象——不含画布上用户后续的编辑。
  • 深回读（本方案需要）：getWorkbookJson() 拿 SSJSON（含全部编辑）作为 BLOB；结构化字段（sheets/rows/cols）由 designer.js 的 derive*() 从 workbookJson + 属性面板状态派生。
结论：BLOB 走 getWorkbookJson()（权威）；关系投影走 designer.js 派生（业务字段大多来自属性面板，不是画布）。二者职责不重叠。

9实施阶段（建议顺序）

1ReportModel 定型 + 组件序列化：getWorkbookJson/setWorkbookJson/setCellValues 三方法 + buildReportModel。E2E 验证 toJSON→fromJSON round-trip 无损。纯前端

2模式一后端：GET/POST layout 两端点 + BLOB 存取（先攻克 bytea 写入风险点）。curl 验证 BLOB 落库/回读一致。后端

3模式一前端接线：loadLayout/saveLayout + derive*，saveDesign 改走后端。E2E：设计→保存→重开无损复原。

4模式二后端：POST data/query + POST data，cr_cell_data UPSERT。

5模式二前端接线：组织/期间选择器 + loadData/saveData + 值回填。E2E：选期间→数据回填→改值→保存→重载一致。

6关系投影 + 元素映射：保存版式时重建 sheet/region/row/col + cell_element_map（供取数引擎）。

后公式计算/校验引擎（M2 compute 扩展）—— 本方案外，模型已预留字段透传。
