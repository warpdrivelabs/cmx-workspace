cmx-hierarchy · 中立层级数据管理引擎

为前端 CmxMasterSlave 造一个 Rust 后端对等物：一个业务无感知、任意层级的层级数据管理引擎，吃下 DOC 的层级单据、DCT 的分级/分类/分组——乃至任何主从/树形结构。补齐三方共缺的服务端权威层间汇总。放在独立中立的 Rust 组件库，与 cmx-container 并列。

对标源：CmxMasterSlave（TS，1530 行，主从协调器） ·  落点：presentation/cmx-hierarchy/（独立 workspace，与 cmx-rust-sheet 平级） ·  吃下：DOC cv_*（异构 upper_id 树）+ DCT cf_*（自引用 parent_id 树） ·  本文档：仅方案，不含实现代码
⚠ 方向修正（2026-08，已落地实现，本文档部分内容被取代）
本方案初版把引擎做成独立 workspace（presentation/cmx-hierarchy）+ 自造新存储引擎 PgHierStore——方向错了。用户澄清："独立/中立" 是依赖意义的：前端 CmxMasterSlave 不依赖任何服务，是服务依赖它（箭头朝内）。
已修正落地：后端主从协调器做成 cmx-container 叶子 crate cmx-master-slave（struct CmxMasterSlave + trait HierService，数据集用 ZmcDataSet），由 cmx-doc-store-pg/cmx-dct-store-pg impl HierService 复用其现成加载/保存——不新造存储引擎。本文档的 hier-store-pg/独立 workspace 章节已作废；hier-agg 汇总引擎作为叶子 crate 的 agg 模块保留。初版代码已归档 _archive-cmx-hierarchy/。

01背景与目标

前端有一个久经验证的组件 CmxMasterSlave（packages/cmx-data-comp/src/lib/cmx-master-slave.js，1530 行）——"多张表的管家"：把主表 + 子表 + 孙表绑成一棵递归数据树，选行联动、改值自动层间汇总。它业务无感知，只认 schema 路径树 + aggregations 规则，不认"凭证/字典/订单"任何业务术语。

本方案要做的：为它造一个 Rust 后端对等物——一个可嵌入后端服务、可批量、可无头运行的任意层级数据管理引擎。它管的不只是"读一棵树"，而是这棵树的装载 / 校验 / 铸号 / 变更集保存 / 服务端权威汇总的完整生命周期，并且——像 CmxMasterSlave 一样——永不认识任何具体单据/字典。

◆ 一句话范围
造一个中立引擎 cmx-hierarchy：输入定义（层级 schema + 汇总规则）+ 数据（多层行），输出装配好的树 / 校验结果 / 已上卷的落库变更。它吃下 DOC 的 upper_id 异构树与 DCT 的 parent_id 自引用树，补齐三方共缺的服务端汇总，不碰任何 cv_*/cf_* 硬编码。

为什么现在做、为什么独立中立

  • 唯一实缺已被点名：cmx-container 内已有方案 统一建模平台-RPT范式推广到DOC与DCT方案.html 明确指出——DOC/DCT 后端骨架都已就位，唯一缺的是一个"定义声明、服务端权威、可落库"的层间汇总引擎 cmx-agg。三个后台代理逐行核实：该 crate 至今不存在，DOC/DCT 都有 agg/SummaryView/*_sum 元数据却无任何代码计算级联小计。
  • 你的需求 = 那份方案的超集：不止 rollup 子引擎，而是 CmxMasterSlave 的完整后端对等物（树管理 + 汇总）。
  • 独立中立（你的明确指示）：放 presentation/cmx-hierarchy/，与 cmx-container 并列，镜像 cmx-rust-sheet 的独立姿态——纯库、只引公共 crate、可被任何 Rust 后端 path 引入当"层级算核"，不并入大 workspace。
  • 低风险：声明格式前端在用、DOC 定义里有占位；计算语义前端 AGG_FUNCS+_cascade 跑了很久；铸号/校验/落库通道 DOC/DCT 已共用——真正的新代码只有"树抽象 + 拓扑汇总"一小核。

02三方实测：DOC / DCT / 前端怎么做的

下面每一条都经后台代理逐文件逐行核验（附 file:line）。这是本方案的事实地基。

前端CmxMasterSlave 的契约

要素实测
层级表达递归 CmxDataSet 树，经每行 _children:{tableId:CmxDataSet} 相连（非扁平数组、非行上 parent_id）。任意 N 层，无固定深度。
两个核心配置schema（点分路径树 head.items.taxes）+ aggregations（{from,agg,field,to,toField,scope?}）。
汇总引擎AGG_FUNCS=sum/avg/min/max/count（:33-39）；作用域解析 _resolveSourcesForTarget（:905-929）三种情形（to 是 from 祖先 / 共同 list 祖先 LCA / scope:'all'）；链式级联 _cascade 带环检测 + 深度 16 闸（:836-861）。
触发时机setData 预热一次；cell-changed（按 from 反向索引，命中才跑）；row-added/removed（前缀匹配）。
两种喂数据setData（树，自己管 CmxDataSet）/ setFlatData（平铺 + relations，自动建树）。
后端缺口汇总是纯前端；服务端权威重算引擎 cmx-agg 不存在。

DOC层级单据（异构 path-tree）

  • 层级列（每层相同骨架）：id BIGINT PK · upper_id BIGINT（邻接表父指针，可空）· line_no BIGINT（父内排序）· 审计列 create_by/create_time/update_by/update_time/delete_flag。无 parent_id（名字是 upper_id）、无 level/path/depth 列、无 DB 外键（应用层保证完整性）。
  • 层是异构表：主链 cv_batch→cv_header→cv_acc_line，同层还有兄弟表 cv_aux_line/cv_zycb_line（LevelGroup.table_ids，[0]=主）。level 是定义期概念（L1/L2/L3 标签），不落每行。
  • Rust 模型（cmx-doc-model/src/meta.rs）：DocMetaView{layer_order,layers,layer_groups,relations} · LayerView{table_name,level,parent_table,columns,summaries,agg_fields,spec} · RelationView{parent,child,parent_key="id",child_key="upper_id"}。行是运行时 DataSet/Row，经 Row::add_child 建树，非编译期类型。
  • 装载：BFS，每层一条 WHERE upper_id = ANY($parentIds)（无 N+1），attach_children 按 upper_id 分桶挂 _children。保存：单事务拓扑序 merge（按 id UPSERT）或 replace（子树删+重插），乐观锁 update_time 基线 → 409，事务内版本快照。
  • 汇总：agg:"sum"/SummaryView/*_sum 表都是元数据，无代码计算级联小计。

DCT分级 / 分类 / 分组（同构自引用）

  • 已是 schema 无关的动态 SQL 引擎：零静态 cf_* DDL、零按 flavor 分支。平级/分级/分类/分组不是三条代码路径，而是同一引擎的配置，只由 self_hierarchy+parent_field 两布尔量决定。
  • 层级列（一行内三种编码并存）：parent_id BIGINT（权威邻接）+ 服务端派生 full_path VARCHAR(512)（物化路径，点分 code）+ level_no TINYINT + is_leaf TINYINT。任意深度。
  • 四种 flavor 的真实差异：dictKind∈{BUSINESS,CLASSIFY,GROUP,RELATION} + selfHierarchy。但 dictKind/classifyRegistry/groupRegistry 后端存储层一行都不读——纯前端 UI 判别（决定用哪个工作台）。分类 = 目标表上一个指向另一字典的 FK 列；M:N 分组 = junction 表（已声明、未实现，对你是 greenfield）。
  • 层级重算：单条 WITH RECURSIVE CTE recompute_hierarchy_subtree（hierarchy.rs:145）在受影响子树上一次性重写 level_no/full_path/is_leaf，幂等。读是懒加载 WHERE parent_id=$ 逐层下钻，非递归读。
  • Rust 模型：DictView{table_name,id_field,code_field,parent_field:Option,self_hierarchy:bool,columns,pk,spec}——self_hierarchy 是引擎唯一读的 flavor 开关。
✅ 三方汇合于同一套原语
DOC 与 DCT 本就用同一套层级原语：邻接表父指针（DOC 叫 upper_id、DCT 叫 parent_id）+ 定义驱动 + 52 位 JS 安全铸号 + temp→real idMap + 变更集事务保存 + 乐观锁 + 缓存 TableSpec 校验 → 结构化 Violation。差别只在异构（DOC 每层一表）vs 同构（DCT 单表自引用）与汇总有无。这正是"一个引擎两种树形"可成立的根据（见 §3）。

03统一抽象：一个引擎两种树形

把三方差异收敛成两种拓扑形状 + 一个共享汇总核。引擎只认这两种形状，业务只是配置。

形状 A异构 path-tree（每层一表）

  • 层间异构：head/items/taxes 各是不同表、不同列集。
  • 父子经 FK：子行 child_key（默认 upper_id）指父 id。
  • 点分路径 a.b.c 唯一定位一层。同层可多兄弟表。
  • 对标：CmxMasterSlave 的 _children 树 / DOC。

形状 B同构自引用（单表 parent_id）

  • 层间同构：同一张表，行指行。
  • 父子经 自 FK：parent_id 指同表 id。
  • 深度不定，服务端派生 full_path/level_no/is_leaf。
  • 对标：前端 treegrid buildTreeFromFlat / DCT 自分级。
▶ 统一视角：形状 A 是形状 B 的"层间版"
两者都是邻接表——A 是"跨表邻接"（child 表.upper_id → parent 表.id），B 是"同表邻接"（row.parent_id → row.id）。引擎内部统一建模为一棵 Node{ layer, row, parent, children } 树；装载适配器负责把两种物理形状读成同一棵内存树，保存适配器反向写回。汇总引擎、铸号、校验、变更集只认这棵中立树，对 A/B 无感。

分类 / 分组 怎么归位（DCT 的第 3、4 种）

形态本质引擎怎么表达
分级（自分级）形状 B单表 parent_id 自引用树，服务端维护派生列。核心
分类（带分类）跨树引用目标树的行带一个 FK 列指向"分类树"的某节点——即两棵独立树 + 一条引用，非父子层级。引擎提供"引用完整性可选校验"，不作层级维护。
分组（M:N）junction 关系成员与组多对多，经 junction 表（member_id,group_id）。DCT 已声明 dict_group_rel 但未实现 → 引擎新增一个 RelationSet 原语承接（greenfield）。
平级（flat）退化形状 B 关掉 self_hierarchy = 无父子的单层列表。天然子集。

结论：层级 = 形状 A/B（引擎核心）；分类 = 树间 FK 引用；分组 = M:N junction。三者正交，可叠加（一棵分级树的节点又可被分类/分组）。

04关键决策（含推荐）

4.1  独立中立 workspace，与 cmx-container 并列 已定·用户指示

落 presentation/cmx-hierarchy/，镜像 cmx-rust-sheet：独立 Cargo.toml [workspace]、分层 crates/、Apache-2.0、只引公共 crate。不并入 cmx-container；需要接入时以 path/registry 单向引入。这既满足"独立中立组件库"的诉求，也让 DOC/DCT/RPT 乃至外部项目都能复用同一算核。

4.2  超集定位：不止 cmx-agg，而是 CmxMasterSlave 后端对等物 已定

cmx-container 那份方案的 cmx-agg 只是"拓扑排序 + 逐层重算"子引擎。本方案把它升级为完整层级管理引擎：树抽象（A/B）+ 装载/保存适配 + 铸号 + 校验 + 汇总。cmx-agg 成为其中一个 crate（hier-agg），而非全部。

4.3  纯库优先 + 存储适配器 trait 化 已定

引擎核心（树/汇总/校验）不绑数据库，经 trait HierStore 抽象存取；提供一个 hier-store-pg 实现（tokio-postgres，复用 cmx-database-pg 的 ZmcDataSet 零拷贝）。这样核心可单测（mock store）、可换库、可无头批量。可选 hier-service（axum）/ hier-cli 后置。

4.4  依赖策略：吃公共 crate，语义对齐但不搬业务 已定

复用脊柱级公共 crate：cmx-utils（Pk52Generator 铸号）、cmx-database-pg（池 + ZmcDataSet）、cmx-biz 的 validation/errcode 薄片（TableSpec/validate_*/Violation/CmxErrCode）。定义解析对齐 cmx-model-meta 的 resolve 语义，但引擎只吃已解析的中立视图（HierSchema），不直接依赖 DOC/DCT 的 DocMetaView/DictView——保持中立。

▶ 落地前需用户拍板
① 交付形态：纯库（推荐）／叠加 axum 服务／叠加 CLE？   ② 校验/铸号：直接 path 复用 cmx-container 的 cmx-utils/cmx-biz（推荐，零重造），还是在中立库里独立重铸一份 Pk52/校验（更纯粹但重复）？   ③ 汇总时机默认：写时上卷（推荐 DOC 凭证类）还是读时现算，作为库级默认？

门面 API 形态（对应 CmxMasterSlave 的数据类方法）

// cmx-hierarchy 门面：CmxMasterSlave 的数据类方法搬成纯 Rust（无视图/DOM/事件）
let schema = HierSchema::from_definition(def_json)?;   // 中立视图，A 或 B
let mgr = HierManager::new(schema, store);

let tree = mgr.load_tree(&scope, &query).await?;      // ← loadDoc / loadDict
let kids = mgr.expand(&node_id).await?;             // ← 懒加载下钻（形状B/大树）

let plan = mgr.stage_changeset(changeset)?;         // 校验 + 铸号 temp→real
mgr.rollup(&mut plan)?;                            // ← 层间汇总(写时)，服务端权威
let out = mgr.commit(plan).await?;                 // 单事务落库 + 乐观锁 → idMap

let v = mgr.rollup_read_only(&scope, &rules).await?; // ← 读时现算(不落库)

06核心数据模型（Rust）

把三方实测结构收敛成一组中立类型。命名对齐前端语义（path/from/to），字段对齐实测列。

// ── 层级定义（中立视图，由 DOC/DCT 定义 JSON 解析而来，引擎不认业务）──
pub struct HierSchema {
    pub shape:    Shape,               // PathTree(异构) | SelfRef(自引用)
    pub layers:   Vec<LayerDef>,       // 形状A：每层一表；形状B：单元素
    pub relations:Vec<RelationDef>,    // parent/child/parent_key/child_key
    pub aggs:     Vec<AggRule>,        // 汇总规则（可空）
}
pub enum Shape { PathTree, SelfRef{ parent_field: String } }

pub struct LayerDef {
    pub path:       String,             // "head.items.taxes"（A）/ "dict"（B）
    pub table:      String,             // 物理表名（引擎只透传，不硬编码）
    pub pk:         String,             // "id" 或 code 字段
    pub child_key:  Option<String>,     // 指父的 FK，默认 "upper_id"/"parent_id"
    pub order_key:  Option<String>,     // "line_no"/"sort_no"
    pub derived:    DerivedCols,        // full_path/level_no/is_leaf 列名（可空）
    pub spec:       Arc<TableSpec>,      // 复用 cmx-biz 校验规格
    pub agg_fields: Vec<String>,        // 承接汇总的列
}

// ── 内存树（装载后的中立结构，A/B 都装配成它）──
pub struct HierTree { pub roots: Vec<NodeId>, pub arena: Arena<Node> }
pub struct Node {
    pub id:       NodeId,               // 稳定键（真 id 或 temp id）
    pub layer:    usize,                // 层序（A 跨表 / B 深度）
    pub row:      Map<String, Value>,   // 行字段（JSON 值层，落库前）
    pub parent:   Option<NodeId>,
    pub children: Vec<NodeId>,
}

// ── 汇总规则（与前端 AggregationRule + 那份方案 AggRule 逐字对齐）──
pub struct AggRule { pub from: String, pub to: String, pub field: String,
                     pub to_field: String, pub agg: AggFn, pub scope: Scope }
pub enum AggFn { Sum, Avg, Min, Max, Count }   // 语义 = AGG_FUNCS
pub enum Scope { Siblings, All }

要点：行不做强类型 struct（对齐 DOC/DCT——运行时 Map<String,Value>，落库前在 JSON 值层校验），保中立与任意列。NodeId 兼容真 id 与 temp id（见 §9）。

07层级机制：邻接表 + 派生索引

两形状统一为邻接表权威 + 派生列可选——与 DOC/DCT 实测完全一致，直接移植。

机制形状 A（DOC）形状 B（DCT）
父指针子表 upper_id → 父表 id（跨表）行 parent_id → 同表 id（自引用）
排序line_nosort_no
层/深度定义期 L1/L2/L3（不落行）派生 level_no（落行）
路径无（点分 path 是逻辑定位）派生 full_path（物化，点分 code）
叶标记无派生 is_leaf
装载BFS，每层 WHERE upper_id=ANY($ids)，分桶挂 children（无 N+1）懒加载 WHERE parent_id=$ 逐层下钻
派生列重算不需要（无派生列）单条 WITH RECURSIVE CTE 在受影响子树一次性重写 level/path/leaf，幂等
完整性无 DB 外键，应用层保证同左；引擎可选做引用校验
◆ 直接移植的两段成方
① DCT 的 recompute_hierarchy_subtree（hierarchy.rs:145，递归 CTE 重写派生列）几乎原样搬进 hier-store-pg，只把列名参数化（derived 字段驱动）。② DOC 的 attach_children（按父键分桶挂 _children）搬成中立树装配。都是已跑通逻辑，非新造。

08汇总引擎（对齐前端 · 服务端权威）

这是唯一实缺的新造核——但语义已被前端验证多年，只需在 Rust 侧忠实复现并升级为"落库权威"。

8.1 声明（进定义 JSON，DOC/DCT/RPT 通用，前端同读一份）

"aggregations": [
  { "from":"cv_aux_line", "to":"cv_acc_line", "field":"local_dr", "toField":"local_dr", "agg":"sum" },
  { "from":"cv_acc_line", "to":"cv_header",   "field":"local_dr", "toField":"total_local_dr", "agg":"sum" }
  // 两条串联 = 辅助行→科目行→凭证头 逐层上卷（拓扑序自动推导）
]

8.2 三种作用域（与前端 _resolveSourcesForTarget 逐字对齐）

情形行为（前端已实现，Rust 复现）
to 是 from 祖先（case A）对每个 target 行，source 限定在它的子树沿相对路径展开。
from/to 有共同 list 祖先（case B）找到包含 target 的最近公共祖先 A 行（LCA + DFS 定位），从 A 沿相对路径收集。
scope:'all'整树聚合，忽略上下文。

8.3 执行（拓扑排序 + 逐层重算 + 链式级联）

// 保存前：按 (from→to) 建 DAG 拓扑排序，逐层把子层聚合回写父层承接字段
pub fn rollup(tree: &mut HierTree, rules: &[AggRule]) -> Result<()> {
    let order = topo_sort(rules)?;        // 子明细→明细→主表；成环即报错
    for rule in order {
        for target in resolve_targets(tree, &rule) {
            let src = resolve_sources(tree, &rule, target); // 三种作用域
            target.row[&rule.to_field] = apply(rule.agg, src, &rule.field);
        }
    }
    Ok(())   // 链式：本规则写出的字段是下条 from → 拓扑序天然承接（对齐前端 _cascade）
}
⚙️ 两种执行时机，一表一议
写时上卷（推荐 DOC 凭证类）：saver 落库前对整棵变更树 rollup，承接字段随子层一并 UPSERT——脱离浏览器也对，报表取数直接读到已上卷值。
读时上卷（可选，省存储）：装载时生成 SELECT SUM(...) ... GROUP BY upper_id 现算，不落库，适合纯展示维度。
两者共用同一份 AggRule 声明，只是消费点不同。
⚠ 服务端计算为权威（安全底线）
绝不信任前端上卷值直接落库（防篡改、防浏览器缺陷）。前端 addAggregation 是即时反馈，hier-agg 是落库前重算的最终裁判——语义对齐但后端说了算。汇总 DAG 必须拓扑可排（成环即拒），对齐前端 16 层级联安全阀。

09ID 铸号 + 装载 / 保存契约

DOC/DCT 已共用同一套铸号与保存契约，引擎原样承接（复用 cmx-utils）。

9.1 52 位 JS 安全铸号 + temp→real 重映射

  • 生成器：cmx_utils::Pk52Generator——[32位秒(epoch 2025-01-01) | 8位节点 | 12位序列]，恒 < 2^53−1，JSON→JS Number 无损（故意不用会截断的 63 位 snowflake）。节点号 per-deploy → 跨部署不撞、导出免改号。
  • 仅整型 PK 铸号：pk_is_generated（PK 类型含 INT）。业务 code 作 PK 的字典不铸号（code 是稳定跨系统键）。
  • 两遍重映射（DOC saver.rs:1147 / DCT lib.rs:320 已实现）：① 给 temp 行（缺失/null/非纯数字串如 "t3"）铸真 id，记 tempId→realId；② 回指所有子行的 upper_id/parent_id/命名FK（行顶层 + fields 内都查）→ 父真 id。返回 idMap 给前端，temp 行免 reload 采用真 id。已是真数字 id 的不重铸（幂等）。

9.2 装载 / 保存 / 校验（trait HierStore）

动作契约（DOC/DCT 实测，引擎统一）
装载形状A：BFS 每层一查 + 内存分桶装配；形状B：懒加载逐层下钻。都回中立 HierTree。可选 COUNT 分页（根层）。零拷贝走 ZmcDataSet。
保存变更集 {path:{inserted,updated,deleted}}，单事务拓扑序：父先 UPSERT，子先 DELETE；多行按列集分组 multi-value INSERT … ON CONFLICT(pk) DO UPDATE。"假成功"防护：影响行数须等于 N，否则回滚。
乐观锁更新带 baseline=update_time，… WHERE pk=$ AND update_time=$baseline；短影响 → 区分 409 冲突 vs 缺行。
校验落库前 JSON 值层：缓存 TableSpec（按定义版本键）→ validate_insert_row/validate_update_fields → 收集全部 Violation（type/length/precision/scale/nullable）→ HTTP 422 带 violations[] 供逐格高亮。服务端填充列（id/审计/派生）跳校验。
派生列重算形状B：删/插/改后，对受影响节点并集跑一次子树 CTE 重写 level/path/leaf。
审计服务端强制 create_by/create_time/update_by/update_time/delete_flag，覆盖客户端值；ON CONFLICT SET 排除 create_* 不可变。

10四种层级形态的落地映射

用户点名的"DOC 层级 / DCT 分级分类分组 / 任意层级"逐一落到引擎原语上。

来源形态引擎形状配置要点汇总
DOC 层级单据形状 AN 层异构表，child_key=upper_id，order_key=line_no；同层多兄弟表经多条 relation。写时上卷（六币种借贷逐层）
DCT 分级形状 B单表，Shape::SelfRef{parent_field:"parent_id"}，derived=full_path/level_no/is_leaf。可选（小计/计数上卷）
DCT 分类形状B×2 + 引用两棵独立树 + 目标树行上一个 FK 列指分类树节点；引擎可选做引用完整性校验。可选（按分类上卷）
DCT 分组RelationSet成员↔组 M:N，junction 表 {member_id,group_id}；新增 RelationSet 原语（DCT 已声明未实现）。可选（按组上卷）
DCT 平级形状 B（关 self_hierarchy）无父子的单层列表，天然子集。无
任意主从/BOM/组织树A 或 B业务只写 schema + aggregations，引擎无感。按声明
✅ 三者正交可叠加
层级（A/B）、分类（树间 FK）、分组（M:N junction）是三个正交原语：一棵分级树的节点，既可被分类（挂到某分类节点）、又可被分组（进若干组）。引擎分别提供，业务按需组合——不为任何组合写 if 分支。

11不变式（业务无感知底线）

不变式说明
① 引擎绝不认识具体业务层数/表名/列名/层间关系/汇总规则只存在于定义；零 cv_*/cf_* 硬编码、零"为某类单据加 if"。这是从 cmx-doc/cmx-dct 继承的铁底线，破则架构倒退。
② 一个引擎两种形状A/B 差异只在 store 装载/保存适配；core/agg 只认中立 HierTree。
③ 汇总语义与前端逐字对齐AggFn = AGG_FUNCS，三作用域 = _resolveSourcesForTarget，成环拒 = 16 层闸。同一声明前后端同读。
④ 服务端计算为权威前端上卷值绝不直接落库，hier-agg 落库前重算裁定。
⑤ 稳定键 + 幂等保存52 位铸号 + temp→real idMap；按 pk UPSERT，重存幂等；跨部署导出免改号。
⑥ 独立可移植纯库、只引公共 crate、与 cmx-container 单向 path 依赖；核心可 mock 单测、可无头批量。
⑦ 校验/错误码复用落库前列级校验 + 结构化 Violation + CmxErrCode，承接汇总字段天然纳入同一校验，不另起。

14接入方式（DOC/DCT 如何复用）

引擎中立，接入方各自把定义映射成 HierSchema，其余全由引擎接管。三种接入姿态：

① path 依赖引库

cmx-doc/cmx-dct 的 store-pg 以 path（或 registry）引 cmx-hierarchy，把现有 DocMetaView/DictView 适配成 HierSchema，删掉自家重复的装载/保存/铸号，改调引擎。汇总从"无"变"有"。

② 独立 hier-service

起 axum 服务，/load /save /children /rollup 端点，接入方经 HTTP 用。适合与主框架强隔离、或非 Rust 消费者。

③ 无头 CLI / 批量

hier-cli 批量校验/上卷/转换；rayon 一次并行处理几千棵树。适合离线对账、迁移。

◆ 与那份"统一建模"方案的关系
cmx-container 内 统一建模平台-RPT范式推广到DOC与DCT方案.html 的 P2「新 cmx-agg 中立 crate」= 本方案的 hier-agg；其 P3「DOC 接汇总」= 本方案 HM-5 的接入姿态①。本方案把它从"cmx-container 内一个 crate"升级为"独立中立 workspace 的一层"，并扩出完整树管理 + 分类/分组，契约与语义完全兼容——那份方案的路线图可直接嫁接为本引擎的消费方。
