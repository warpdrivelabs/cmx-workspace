## 一、实现总览：交付了什么

`cmx-data-auth` 是与 `cmx-container` 平级的**独立 workspace**，对标 `cmx-rulesengine` 的「一芯多壳」骨架构建。
核心主张一以贯之：**把"决策（谁能看什么）"与"执行（在哪里过滤）"解耦** —— PDP 部分求值产出语义中立的
**约束 AST**（残差谓词树），多个 PEP 后端各自把它编译成 SQL WHERE / 内存谓词 / ES 查询。数据库从"权威"
退化为"众多编译目标之一"。

| 阶段 | 能力 | 落点 | 状态 |
| --- | --- | --- | --- |
| D0 | 领域模型 + 约束 AST（9 节点）+ 智能构造化简 | core `ir/subject/def/eval` | ✅ |
| D1 | SqlCompiler 参数化 WHERE 下推（防注入） | core `compiler.rs` | ✅ |
| D1+ | 多后端：RowFilterCompiler / EsCompiler | core `compiler.rs` | ✅ |
| D2 | 层级维度展开（`WITH RECURSIVE` 下行闭包） | store-pg `expander.rs` | ✅ |
| D4 | 列脱敏义务（FULL/PARTIAL/HASH）+ FEEL 条件门 + 角色豁免门 | app `engine.rs` + cmx-rule-feel | ✅ |
| D4+ | 义务执行器：内存行集过滤 + 脱敏（archetype-③，不碰 DB） | core `mask.rs` + app `enforce` | ✅ |
| D5 | 基础 ReBAC 关系元组（`Relation` → `lookup_resources` → `In`） | store-pg + app | ✅ |
| D3 | 决策表作策略源（cmx-rulesengine 纯库复用） | app `policy_source.rs` | ✅ |
| D6 | PEP 中间件自动注入（业务 handler 权限无感，Deny→403） | app `pep.rs` | ✅ |
| L3 | 物化权限集缓存（空间换时间，再分配即刷新） | app `matcache.rs` | ✅ |
| — | 部分求值 PDP（超管/Deny/无授权/空维度四门 fail-closed） | core `pdp.rs` | ✅ |
| — | db-per-tenant（task_local 租户 scope + 懒备库）+ 决策审计 | app `tenant/tenancy` | ✅ |

**验证**：`cargo build/test/clippy` 全绿（39 单测，0 警告，离线 aliyun 镜像）；真机 `dataauth.sh` 端到端 **19/19**。

## 二、工程结构：一芯多壳四 crate

四个 crate 严格自下而上单向依赖：语义中立内核 `core` 零 DB / 零 `cmx-*` 依赖（可单测、可 wasm）；
`store-pg` 落 tokio-postgres 实现；`app` 是平台中立应用层（**handler 不绑 `State`**，故 `dataauth_routes::<S>()`
对任意 state 泛型成立）；`server` 是 `cmx-web-chassis` 骨架的独立可跑 bin（:8096）。基础设施与 FEEL 引擎
经**跨 workspace path** 复用 `../cmx-container` 与 `../cmx-rulesengine`，不重复造轮子。

{{FIG:impl-01-crate-layers}}

「一芯多壳」的价值在于：同一份 `cmx-dataauth-app` 既能被独立壳 `::<()>()` 装配成微服务，也能未来被平台壳
`::<CmxAppState>()` 内嵌进大单体 —— 应用逻辑一次编写，多种部署形态。

## 三、核心编排：decide 七步

`engine::decide(Subject, Resource) → Decision` 是全系统**唯一的 async 编排**（引擎无长驻状态、**无 poller**，纯请求驱动）。
它把七个步骤串成一条流水线：装策略 → 装授权 → 层级维度展开 → 部分求值 → 解析 ReBAC → 脱敏义务 → 审计。

{{FIG:impl-02-decide-pipeline}}

关键在于**职责分层**：所有 IO（装载、维度递归、关系查询、审计）都在 app 层完成，把展开好的值集喂给
`core::pdp::compose` 这个**纯函数**做部分求值。core 因此不碰任何数据库，可脱离运行时单测。
第 4 步的 `compose` 内建**四道 fail-closed 闸门**（超管→True、命中 Deny→False、无匹配策略→Deny、空维度→坍缩 False），
详见[第十三节](#十三fail-closed-安全语义)。

## 四、稳定中间表示：约束 AST

约束 AST（`core::ir::Constraint`）是整个引擎的**稳定中间表示（IR）**：PDP 部分求值吐出它，多个 PEP 后端各自
把它编译成具体查询语言。它用 `#[serde(tag="kind", rename_all="camelCase")]` 序列化为干净 JSON
（如 `{"kind":"in","field":"ou_id","values":[…]}`），既能落库（`constraint_json` 列），也能由外部规则引擎产出。

{{FIG:impl-03-constraint-ast}}

九种节点里，`In` 是**维度权限的落点**（`$dim:*` 占位展开后的值集），`Relation` 是 **ReBAC 桥**（编译前必须
经 `lookup_resources` 解析成 `In`）。智能构造器 `and()/or()/not()` 在构造时即做**代数化简**（摊平、坍缩常量、
单元素解包），这是 PDP 部分求值能把"已知主体维度"提前折叠、只留"未知资源字段"作残差的代数基础。

## 五、执行面：一个 AST，三个编译后端

这是本方案的灵魂：**同一个 `Decision.constraint` 可被多个后端各自编译**。`trait ConstraintCompiler` 统一契约，
新增一种执行环境只需再实现一次。

{{FIG:impl-04-multi-backend}}

- **SqlCompiler** → 参数化 `WHERE` 片段 + 有序参数。**防注入是硬约束**：字段名只允许来自资源白名单
  （维度绑定物理列 ∪ `row_ctx`），值永远走 `$n` 占位、绝不拼进 SQL 串；空 `In` 编译成 `FALSE`；
  未解析的 `Relation` 直接编译报错。支持 `start_at(n)` 在拼进更大 SQL 时右移参数序号。
- **RowFilterCompiler** → `Box<dyn Fn(&Map) -> bool + Send + Sync>` 运行时闭包，对每行就地判真。
  数值/字符串归一比较，`LIKE` 用经典 DP 实现（无需 regex crate）。用于 cmx-rowsource / 跨库 DataSet 后过滤。
- **EsCompiler** → ElasticSearch Query DSL：`In→terms`、`Cmp→term/range`、`And→bool.filter`、
  `Or→bool.should + minimum_should_match`、`Like→wildcard`。

## 六、持久化：6 张 cmx_dataauth_ 表

表前缀 `cmx_dataauth_*`（house 硬约束），**禁外键**（用索引替代）、**幂等 DDL**（`IF NOT EXISTS`）。多租户走
**db-per-tenant**：库即租户边界，故**表内不带 tenant 列**（租户维在连接路由解决，不进 WHERE）。

{{FIG:impl-05-db-schema}}

几处工程细节：主键统一 `BIGINT GENERATED BY DEFAULT AS IDENTITY` + `INSERT … RETURNING id`；老库平滑升级
靠 `ALTER TABLE … ADD COLUMN IF NOT EXISTS source`；脱敏表列名用 `column_name`（避开 SQL 保留字 `column`）；
`dimension_value` 用复合主键 `(dim_key, dim_value)` 而非自增 id，直接支撑递归展开。

## 七、层级维度：WITH RECURSIVE 下行闭包

维度权限的精髓是**层级继承**：授权"华东（1001）"应自动覆盖其全部子孙机构。`PgDimensionExpander::descendants`
用一条 `WITH RECURSIVE` 求某维度根值的**下行闭包（含自身）**。

{{FIG:impl-06-dim-expand}}

展开发生在 `decide` 第 3 步：对每个 grant 的每个根值求 descendants，按 `(dim_key, root)` 记忆化去重，再交
`compose` 回填 `$dim:*` 占位。两点值得注意：① **fail-safe** —— 维度树未登记该值时闭包为空，则至少含自身
（只授权自身节点，绝不因数据缺失放大权限）；② **方向差异** —— 数据权限求"我管辖谁"（下行 descendants），
与 cmx-flow 的 `DimensionResolver` 求"我归属谁"（上行 ancestors）方向相反，故不复用而自建。

## 八、列脱敏：双门过滤 + 投影层义务

列脱敏与行过滤**正交**：行过滤决定"哪些行可见"，脱敏决定"某列如何呈现"。`build_obligations` 装载脱敏规则后
过**两道门**才生成义务；`apply_masks` 在投影层逐行逐列改写**呈现值**，不碰数据库存储的原值。

{{FIG:impl-07-mask-obligations}}

- **门①角色豁免**：主体持有 `min_role` → `continue`（不脱敏），如 HR 对薪资列明文可见。
- **门② FEEL 条件**：`condition_expr`（如 `user.grade < 5`）经 cmx-rule-feel 求值；`true`→脱敏、`false`→跳过、
  **求值出错→fail-safe 脱敏**（宁可多脱不可漏脱）；条件为空则恒脱敏。
- 三种脱敏：`FULL`（→`****`）、`PARTIAL`（保留首尾 `{h}...{t}`，默认头 3 尾 4）、`HASH`（不可逆令牌化，
  M1 用稳定哈希、生产应换 HMAC-SHA256）。**空值不脱敏**（无信息可泄露）。

## 九、两种执行形态：PEP 中间件 vs 内存 enforce

同一份 `Decision` 有两条落地路径，共同证明"决策/执行解耦"。

{{FIG:impl-08-pep-and-enforce}}

- **D6 · PEP 中间件（SQL 下推）**：给业务路由挂 `pep::guard(ResourceSpec)` 层，中间件读 task_local 主体 →
  `decide` → **Deny 直接 403 短路** → `compile("sql")` → 把 `DataScope{where_sql, params, obligations}` 注入
  请求扩展。业务 handler **权限无感**：只声明 `Extension<DataScope>`，把 `where_sql`/`params` 拼进自己的查询，
  不 import 任何策略/授权/维度概念。
- **archetype-③ · 内存 enforce（不碰 DB）**：`POST /enforce {subject, resource, rows}` 由调用方给内存行集
  （CSV / 跨库 DataSet / API 结果），`decide` 后用 `RowFilterCompiler` 把**同一 constraint** 编译成谓词就地过滤，
  再 `apply_masks` 脱敏。全程不碰数据库 —— 无 DB 亦可执行数据权限。

## 十、L3 物化权限集缓存

对**枚举可穷尽的简单字典**（组织机构、成本中心、项目），授权时就把"某主体在该字典上可见哪些条目"预计算成
条目集合缓存，前端查字典时 O(1) 直取、可完全不碰库；权限**再分配**时刷新对应键。空间换时间。

{{FIG:impl-09-matcache}}

缓存按 principal 分桶（键 = `(tenant, dictCode, subjectType, subjectId)`），用户有效可见集 =
`cache[user:自身] ∪ cache[role:各角色]`（去重）。**给某角色重分配只失效一个键**，其全体成员下次查询自动取到
最新 —— 角色分桶天然扇出。物化复用 `decide` 第 3 步同一 `descendants` 展开逻辑；缓存值 `Arc<Vec<..>>` 零拷贝
共享。判据：仅小字典（大表集合会爆炸，仍走惰性下推）。载体 M1 进程内 `OnceLock<Mutex<HashMap>>`，生产换 Redis。

## 十一、D3 决策表作策略源

`source=decisionTable` 的策略，把 cmx-rulesengine 的 `DecisionBody` JSON 存进 `constraint_tpl`。`decide` 前用
主体事实（roles/dims/attrs + user/tenant）跑决策表，读输出列 `constraint`，得到一个**内联 Constraint 模板**，
再交给 `core::pdp` 的同一 subst/compose 管道。

{{FIG:impl-10-decision-table-source}}

这样 **`cmx-dataauth-core` 保持零 rule 依赖**：决策表求值只在 app 层发生（`policy_source.rs` 引 cmx-rule-engine/model），
产物退化为 D0 的内联模板。**fail-closed**：求值失败 / 无 `constraint` 输出列 / 无命中 → 回退 `{"kind":"false"}`（Deny）。
业务价值：数据可见范围可用决策表**动态维护**，无需改代码。

### decide → compile 实录

```
POST /decide  { subject:{userId:"u42", roles:["finance"]},
                resource:{kind:"voucher", dimBindings:{org:"ou_id"}, rowCtx:["owner","status"]} }
grant: u42 @ org=1001  →  维度树 1001 展开为 {1001,100101,100102}
→ constraint: ou_id IN [1001,100101,100102] AND ( owner='u42' OR status='public' )
→ effect: permitWithConstraint

POST /compile { …, backend:"sql" }
→ { whereSql: "(ou_id IN ($1,$2,$3)) AND ((owner = $4) OR (status = $5))",
    params:   ["1001","100101","100102","u42","public"] }
```

## 十三、fail-closed 安全语义

数据权限的默认必须是**拒绝**。系统在多处内建 fail-closed 闸门，宁可少给不可多给：

- **PDP compose 四门**：① 超管角色（superadmin/admin）→ `True` 全放行；② 命中 `Deny` 策略 → 立即 `False`；
  ③ 无任何匹配策略 → `Deny`；④ 空维度授值 → `In` 坍缩 `False`（在 AND 中拒绝整策略，在 OR 中被丢弃、
  保留其他分支如 public）。
- **维度展开 fail-safe**：维度树缺该节点 → 闭包退化为仅含自身，不放大。
- **脱敏 fail-safe**：FEEL 条件求值出错 → 默认脱敏。
- **决策表 fail-closed**：求值失败 / 无输出列 / 无命中 → `{"kind":"false"}`。
- **SQL 编译防注入**：字段名限白名单、值恒占位、未解析 Relation 报错。
- **PEP 短路**：Deny 决策在中间件层 403，业务 handler 永远拿不到越权数据。
- **防绕过纵深**：应用层下推为主力，高敏表可叠加 PG RLS 兜底（共用 `cmx_dataauth_grant` 配置）。

## 十五、非目标与后续

M1 有意留白，边界清晰：

- **D6 PG RLS DDL 生成兜底**：高敏表数据库层强制，防应用绕过。
- **递归 Zanzibar userset**：组→成员多跳的关系传递（当前 ReBAC 仅单跳 `Relation`→`In`）。
- **报表 / 流程 WHERE 注入接缝**：把 `DataScope` 接进 cmx-report / cmx-flow 的取数管道。
- **native pages + OpenAPI/Swagger**：设计器工作台与契约文档。
- **L1/L2 缓存**：决策结果缓存、编译产物缓存（Redis）；L3 载体从进程内换 Redis。
- **grant 主体扩展**：`ORG` / `POST` 主体类型（当前仅 `USER` / `ROLE`）。
