# cmx-agent 自动更新 · 下载失败自动重试与断点续传方案

> 2026-09-12 · 状态：**待评审**（方案稿，未实施）。
> 前置文档：`20260909_cmx-agent_自动更新方案.md`（已定稿，本文不重复其内容，
> 只在其 P0 骨架之上补「下载可靠性」一层）。

---

## 0. 一页总览

**问题**：安装包下载失败后，当前只 toast 一条「更新失败：xxx」，用户必须手动再点
标题栏「更新」按钮从头全量重下。弱网 / 门户抖动场景体验差。

**结论先行**：

- **P1 自动重试（纯客户端，先做）**：下载失败后退避自动重试（2s→5s→15s，共 4 次），
  最终失败弹重试窗；用户已确认过安装的，之后每 30 分钟 / 回前台自动再试。
  覆盖 ~90% 失败场景（瞬时断网、网关抖动），一次发版完成。
- **P2 断点续传（服务端 + 客户端，后做）**：服务端下载端点支持 Range；客户端绕开
  插件黑盒自己断点下载到本地缓存，再经 **127.0.0.1 回环流**喂给插件做验签安装——
  minisign 验签与三平台安装逻辑零改动。
- **建议节奏**：P1 先行上线，观察真实失败率后再决定 P2 是否值得投入
  （32MB 全量重下的代价若可接受，P2 可以缓做甚至不做）。

## 1. 现状与约束（决定方案形态的三个事实）

当前链路（`crates/cmx-agent-shell/src-tauri/src/update_common.rs` + 前端 `ui/js/update.js`）：

```
check_update(10s 超时) → Update 句柄入 PENDING_UPDATE 槽 → 前端弹窗
→ 用户点「立即更新」→ download_and_install(120s 超时，一次性)
  ├─ 成功：落 pending 上报标记 → install → restart
  └─ 失败：toast「更新失败」→ 用户手动再点标题栏按钮 → 全量重下
```

| # | 约束 | 出处 | 对方案的影响 |
|---|---|---|---|
| C1 | **tauri-plugin-updater 2.11.0 的 `download_and_install` 是黑盒**：全量下载 → minisign 验签 → 安装一气呵成，不支持 Range，无内置重试 | 插件 `updater.rs`（已在 2026-09 方案 §4 核对过源码行号） | 断点续传**不能在插件内做**；重试只能包在插件调用外层 |
| C2 | **服务端 `/agent-updates/download` 不支持 Range**：门户从存储服务整文件读入内存再回包（90s 总超时），无 206 语义 | `cmx-container/crates/libs/cmx-agent/cmx-agent-api/src/handlers/updates.rs:346` | 断点续传需要服务端改造（好在响应本就是全量 buffer，切片容易） |
| C3 | 包体 32MB（.app）/ 11MB（.dmg），主要失败源是瞬时网络抖动而非长时间断网 | 发布产物实测 | 自动重试收益 > 断点续传；续传是锦上添花 |

另一条**已否决**的路线：完全自研「下载→验签→安装」（绕开插件）。否决理由：Windows
NSIS 静默安装、Linux `pkexec dpkg`、macOS .app 替换的三平台安装逻辑重写风险高，
而回环流方案能让插件继续干它擅长的验签 + 安装。

## 2. P1：自动重试 + 失败保持（纯客户端）

### 2.1 壳层 `update_common.rs`（约 100 行）

`download_and_install` 内包重试循环：

```
for attempt in 1..=4:
    check() 刷新句柄            # 每轮重试前重新检查
      ├─ 无更新（版本已撤回）→ 停止重试，告知用户「更新已撤回」
      └─ 有更新 → 取新句柄
    download_and_install 一次
      ├─ 成功 → break（后续 install/restart 照旧）
      └─ 失败 → 若 attempt < 4：sleep 退避(2s/5s/15s) 后继续
               若 attempt = 4：最终失败
```

要点：

- **每轮重试前重新 `check()`**：句柄是一次性的（`PENDING_UPDATE.take()`），且重新检查
  免费获得「版本撤回即停」语义——服务端撤回后 latest.json 回 204，客户端停止重试并
  清标题栏按钮，不会撞已撤回的问题版本。
- **失败上报只在最终失败后发一次**（`failed_install` / `failed_verify` 口径不膨胀；
  中间轮失败不上报）。
- **进度事件加 `attempt` 字段**：`update_progress` payload 变为
  `{received, total, attempt}`。前端每轮百分比从 0 重来（不跨轮累计，避免制造
  「已经续传」的错觉——真续传是 P2 的事）。前端对旧 payload 兼容（`attempt` 缺省视为 1）。
- 120s 下载超时维持不变（每轮各自计时；4 轮 + 退避最坏 ~8.5 分钟，卡死场景仍可失败返回）。
- `INSTALLING` 防重入语义不变（重试发生在命令内部，对外仍是一次调用）。

### 2.2 前端 `ui/js/update.js`（约 60 行）

- **最终失败改弹自绘重试窗**（复用 `showUpdateDialog` 的模态样式）：
  「更新下载失败（已重试 4 次）」+ [重试] [稍后]。不再只 toast。
- **已同意安装的自动再试**：用户点过「立即更新」= 已同意该版本安装。失败后
  （点了稍后或弹窗被动消失）：
  - 每 30 分钟定时自动重试一次（`setInterval`，成功或版本撤回即停）；
  - 窗口 `visibilitychange` 回前台时若距上次尝试 >5 分钟也触发一次。
  - 自动重试静默进行，进度照常走标题栏按钮；再次最终失败只 toast 不再弹窗
    （避免打扰循环），标题栏按钮常驻可随时手动重试。
- 「稍后」的语义升级为「稍后自动再试」；30 分钟 snooze 标记机制（`cmx-update-snooze`）
  仍只管**弹窗**不重复，与自动重试互不干扰。

### 2.3 测试与验收

| 用例 | 期望 |
|---|---|
| 正常网络 | 行为与现状完全一致（一次成功） |
| 手动断网点更新 | 4 次重试全失败 → 重试窗出现；恢复网络点「重试」→ 成功安装重启 |
| 下载中途断网几秒后恢复 | 某一轮重试成功 → 正常安装（用户感知：进度条重来一次） |
| 服务端撤回版本 + 客户端在重试中 | 下一轮 check 拿到 204 → 停止重试、按钮消失、toast「更新已撤回」 |
| 弱网 120s 超时 ×4 | 最终失败只上报**一次** failed_install |
| 下载进行中再点更新按钮 | 防重入拒绝（现状语义不变） |

### 2.4 改动文件清单

- `crates/cmx-agent-shell/src-tauri/src/update_common.rs`（重试循环 + attempt 字段）
- `crates/cmx-agent-web/ui/js/update.js`（重试窗 + 定时自动再试；改完 `sync-ui.sh`）
- 不动服务端、不动插件、不动 `cmx-agent-app`

## 3. P2：断点续传（服务端 Range + 客户端回环流）

> 前置：P1 已上线且失败率数据表明「重试仍救不回」的场景可观（如长时间弱网、
> 大包慢速下载反复超时）才启动。

### 3.1 服务端：`/agent-updates/download` 支持 Range（~50 行）

`cmx-container` 的 `download_update` handler：

- 解析 `Range: bytes=<start>-[<end>]` 请求头；
- 响应 buffer 本就是全量在内存（`file.data`），切片返回：
  `206 Partial Content` + `Content-Range: bytes <start>-<end>/<total>` + 对应切片；
- 无 Range 头时行为不变（200 全量）；响应头加 `Accept-Ranges: bytes` 声明能力；
- 边界：`start >= total` 回 `416 Range Not Satisfiable`；多区间 Range（`a-b,c-d`）
  不支持，回 200 全量（客户端只用单区间，简单化）。
- 注意：每次 Range 请求服务端仍从存储服务读全量再切片——门户到存储这段没有省，
  省的是**用户最后一跳**。32MB 量级下门户开销可接受；若未来要优化，需存储服务
  层原生 Range 支持（另立课题）。
- latest.json 的平台项加 `size` 字段（客户端进度总量与完整性预校验用；登记版本时
  从产物取字节数写入）。

### 3.2 客户端：自研断点下载 + 回环流（~200 行）

```
用户确认安装
→ 自己 reqwest 下载（支持 Range）：
    缓存文件 <data_dir>/updates/<version>-<platform>.part
    已有 .part → 发 Range: bytes=<已下字节>- 续传追加
    每轮失败 → 重试退避（复用 P1 策略）；.part 保留
    服务端不支持 Range（旧门户）→ 自动降级全量重下（行为=现状）
    下载完成 → 长度对 latest.json size 校验 → rename 去掉 .part
→ 起 127.0.0.1 随机端口临时 HTTP 服务（仅本进程生命周期内）：
    GET /artifact → 200 + 本地文件流（带 Content-Length）
→ 构造「回环 endpoint」：check 的 latest.json 换成壳内拼接的同内容 JSON，
    其中下载 URL 指向 127.0.0.1 的 /artifact
→ 插件 download_and_install：从本机秒下 → minisign 验签 → 安装 → 重启（逻辑零改动）
→ 成功后删缓存目录、停回环服务
```

要点：

- **验签与安装完全留在插件内**（约束 C1 的绕行仅限「下载」这一步）；
  .part 被篡改/损坏的场景由 minisign 验签兜底（fail-closed，验签失败删缓存重下）。
- **回环地址仅 127.0.0.1 监听**、随机端口、服务随安装完成销毁——无对外暴露面。
- **缓存治理**：文件名带版本+平台，新版本天然不撞旧缓存；安装成功后清空
  `updates/` 目录；启动时顺带清理 30 天前的残留（防磁盘堆积）。
- **降级路径**：服务端 Range 探测（首次响应无 `Accept-Ranges` 头）→ 记住并走
  全量模式 = P1 行为，保证新旧门户/客户端任意组合可用。

### 3.3 测试与验收（增量）

| 用例 | 期望 |
|---|---|
| 下载到 60% 断网，恢复后续传 | 从 60% 处继续（日志可见 Range 请求），最终安装成功 |
| .part 被人为篡改 | 插件验签失败 → 删缓存 → 下一轮全量重下（不安装被篡改包） |
| 旧版门户（无 Range） | 自动降级全量，行为同 P1 |
| 服务端 416 | 客户端视为缓存失效，删 .part 全量重下 |
| 回环服务端口被占 | 随机端口重试；仍失败 → 降级全量直连 |
| size 与实际不符 | 删缓存重下，不进入安装 |

### 3.4 改动文件清单

- `cmx-container/crates/libs/cmx-agent/cmx-agent-api/src/handlers/updates.rs`（Range + size）
- `crates/cmx-agent-shell/src-tauri/src/update_common.rs`（断点下载器 + 回环流 + 缓存治理）
- `crates/cmx-agent-web/ui/js/update.js`（续传进度显示「已续传 xx%」样式，可选）

## 4. 决策点（评审时定）

| # | 决策 | 选项与倾向 |
|---|---|---|
| D1 | P2 是否做、何时做 | **倾向**：P1 上线后看 1-2 周失败上报数据（failed_install 量 + 客户端重试日志）再定；数据不大则缓做 |
| D2 | 自动再试的频率与上限 | **倾向**：30 分钟间隔 + 回前台 >5 分钟触发，不设总次数上限（版本撤回/成功即停）；可选加「当日最多 N 次」防打扰 |
| D3 | 自动重试是否弹窗 | **倾向**：手动触发失败弹重试窗；自动再试失败只 toast + 按钮常驻（避免弹窗疲劳） |
| D4 | P2 的服务端 Range 是否顺手支持多区间 | **倾向**：不支持（客户端只用单区间），文档注明 |

## 5. 风险清单

| 风险 | 缓解 |
|---|---|
| 重试循环与用户关窗/退出竞态 | 重试发生在 `download_and_install` 命令内，关窗即进程退出（a7da6b8 硬退出语义），无悬挂态 |
| 自动再试打扰（夜间挂机等） | 静默 + toast 单次；30 分钟间隔；回前台触发有 5 分钟门槛 |
| P2 回环流被本机其他进程访问 | 仅 127.0.0.1 + 随机端口 + 短生命周期 + 内容有 minisign 验签兜底 |
| P2 服务端切片增加门户内存压力 | 单请求本就全量读入（现状），切片不增；并发下载量小（内部团队规模） |
| progress 事件加字段破坏旧前端 | 前后端同包发布；字段缺省兼容（attempt 默认 1） |
