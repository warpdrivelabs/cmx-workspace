## 0. 一页总览

**问题**：安装包下载失败后，当前只 toast 一条「更新失败：xxx」，用户必须手动再点
标题栏「更新」按钮从头全量重下。弱网 / 门户抖动场景体验差。

**结论先行**：

- **P1 自动重试（壳层外环）**：`download_and_install` 命令内包重试循环
  （check 三态判定 → 4 次退避 2s/5s/15s），最终失败弹自绘重试窗；
  用户已确认过安装的，之后每 30 分钟 / 回前台（>5 分钟）自动静默再试。
- **P2 断点续传（同一次发版落地）**：服务端下载端点支持 Range（206/416）+
  latest.json 平台项补 `size`；客户端绕开插件黑盒**自研断点下载器**落
  `.part` 缓存，再经 **127.0.0.1 回环流**把本地文件喂给插件做验签安装——
  minisign 验签与三平台安装逻辑零改动。
- **架构简化（P1+P2 合并的自然结果）**：`download_and_install` 命令
  **自持化**——自己 check 拿元数据（版本/URL/signature/size），不再依赖
  `PENDING_UPDATE` 槽（槽随重试语义废弃，见 §2.1-R1）。
- **发版**：一个版本 **0.1.1** 全量落地（版本号用户拍板保持 0.1.1，实施记录见 §9）；服务端（cmx-container）先发、
  客户端（cmx-agent）后发，任意新旧组合可用（§4 兼容矩阵）。

## 1. 现状与约束（决定方案形态的四个事实）

当前链路（`crates/cmx-agent-shell/src-tauri/src/update_common.rs` + 前端
`cmx-agent-web/ui/js/update.js`，经 `sync-ui.sh` 同步到 `src-tauri/ui/`）：

```
check_update(10s 超时) → Update 句柄入 PENDING_UPDATE 槽 → 前端弹窗
→ 用户点「立即更新」→ download_and_install(120s 超时，一次性)
  ├─ 成功：落 pending 上报标记 → install → restart
  └─ 失败：toast「更新失败」→ 用户手动再点标题栏按钮 → 全量重下
```

| # | 约束 | 出处 | 对方案的影响 |
|---|---|---|---|
| C1 | **tauri-plugin-updater 2.11.0 的 `download_and_install` 是黑盒**：全量下载（返回 `Vec<u8>` 整载内存）→ minisign 验签 → 安装一气呵成，不支持 Range，无内置重试 | 插件 `updater.rs:680`（已核源码） | 断点续传**不能在插件内做**；重试只能包在插件调用外层 |
| C2 | **服务端 `/agent-updates/download` 不支持 Range**：门户从存储整文件读入内存再回包（90s 总超时），无 206 语义 | `cmx-agent-api/src/handlers/updates.rs`（b3fe3da3 加固后现状） | 断点续传需服务端加 Range；响应本就全量在内存（`file.data`），切片容易 |
| C3 | 包体：**Windows NSIS 实测 6.8MB**、macOS .app 32MB / .dmg 11MB、deb 10.5MB；主要失败源是瞬时网络抖动而非长时间断网 | 发布产物实测（2026-09-10 NSIS 6,840,827B） | 自动重试收益 > 断点续传；但两者合做后弱网大包（mac）也覆盖 |
| C4 | **`Update.raw_json` 携带服务端 latest.json 平台项原文**（含 url/signature/size），且 `Update` 句柄随 builder 的 endpoints 任意构造 | 插件 `updater.rs`（`pub raw_json: Value`） | 回环流可在壳内拼 latest.json 复用全部原始字段；命令可自持化 |

另一条**已否决**的路线：完全自研「下载→验签→安装」（绕开插件）。否决理由：
Windows NSIS 静默安装、Linux `pkexec dpkg`、macOS .app 替换的三平台安装逻辑
重写风险高，而回环流方案让插件继续干它擅长的验签 + 安装（C1 的绕行仅限
「下载」这一步）。

## 2. 合并架构：命令自持 + 外环重试 + 内环断点下载

### 2.1 壳层 `download_and_install` 重构（`update_common.rs`，主体改动）

```
#[tauri::command] download_and_install(app)          # INSTALLING 防重入不变
  for attempt in 1..=4:                              # ── P1 外环 ──
    ① check(app.updater_builder(), endpoints=[门户 latest.json 带 {{target}} 占位符],
            timeout=10s).check()
       ├─ Err(网络/超时)        → 本轮失败（见 ③ 失败处理）   # check 本身失败≠撤回！
       ├─ Ok(None)（204 无更新）→ **撤回即停**：emit `update_withdrawn`（前端 listener
       │    清 UPDATE_INFO / agreed 标记 / 标题栏按钮）+ toast「更新已撤回」、return Ok
       └─ Ok(Some(update))      → 取 raw_json：{version, url, signature, size?, force?}
    ② 断点下载（── P2 内环，单次尝试；失败抛给外环 ──）
       缓存目录 <data_dir>/updates/，文件 <ver>-<platform>.part + 同名 .part.meta
       a. 读 .part.meta {url, size}；与本次 raw_json 的 url/size 不符 → 删 .part/.meta
          （防「同版本重登记换产物」后续传出混合文件，对抗性审查 R10）
       b. **统一总是发 `Range: bytes=<当前.part长度>-`**（len=0 即 bytes=0-，R12）：
          ├─ 206 → 服务端支持续传：追加写 .part（进度 received 从 len 起跳）
          ├─ 200 → 服务端不支持（旧门户）：降级——清 .part 当全量响应重写（= P1 行为）
          ├─ 416 → .part 已完整（len==size）→ 直接进 ④；len>size 或无 size → 删 .part 下轮重下
          └─ 连接失败/超时(120s) → 抛本轮失败
          （统一带 Range 让「探测」消失：任何一轮响应即知服务端能力，且避免
            「首轮不带 Range 拿 200、次轮才发现不支持、降级丢已下字节」的浪费）
       c. 下载中每 256KB emit update_progress {received, total, attempt}
          （received=累计含续传偏移；total=raw_json.size ?? Content-Length）
       d. 完成：len != size（有 size 时）→ 删 .part 抛本轮失败；
          否则 fsync → rename .part → <ver>-<platform>.bin（Windows 锁重试 3×100ms）
    ④ 回环流（── P2，把本地文件喂给插件；服务生命周期=单轮，失败路径显式
       shutdown 防 fd 泄漏 ──）
       a. TcpListener bind 127.0.0.1:0（随机端口；bind 失败重试 3 次，仍败=本轮失败）
       b. spawn 单请求 HTTP/1.1 迷你服务（手写 ~60 行，零新依赖）：
          GET/HEAD /artifact → 200 + Content-Length + 文件全量字节 + Connection: close
       c. 构造回环 latest.json = raw_json 原文深拷贝，仅改 url → http://127.0.0.1:<port>/artifact
          （version/notes/signature/platforms 键原样保留——platforms 键 darwin-aarch64-app
            命中插件 {os}-{arch} 回退序列，不可改键名）
       d. app.updater_builder().endpoints([回环 url]) → check → 新句柄
          → 句柄.download_and_install(本机秒下 → minisign 验签 → install)
       e. **install 前落 pending 上报标记**（沿用原语义：install 可能中断进程，
          标记先于风险动作落盘；下载失败不写 pending——failed_download 即时报无需补报）
          → install 成功 → 停回环服务 → app.restart()
          （restart 即刻替换进程，缓存清理由**下次启动**承担，见 §2.3）
    ③ 失败处理：attempt<4 → sleep 退避(2s/5s/15s) → 下一轮（.part 保留，续传省流量）
       attempt=4 → 分类上报一次 + return Err（前端弹重试窗）
       ├─ ② 抛的下载失败        → "failed_download"（新增值域）
       └─ ④ 插件抛的验签/安装失败 → contains("signature"|"minisign"|"公钥") → "failed_verify"
                                     否则 → "failed_install"（沿用现状判定）
       验签失败（.part 被篡改/混合）→ 删 .part/.meta（下轮全量重下，fail-closed）
```

要点（对照旧稿的修正与新增）：

- **R1 去槽化**：`PENDING_UPDATE` 槽废弃删除。旧设计「check_update 存句柄、
  download_and_install 取」在一次调用语义下成立，在重试语义下是障碍（句柄
  一次性，外环每轮要新句柄）。`check_update` 命令保留但只服务前端展示
  （登录页首查 / 主窗兜底查 / 手动菜单查），两命令间不再共享状态；
  `INSTALLING` 仍是唯一并发守门。
- **R2 check 三态**（旧稿漏了关键分支）：check 抛错（断网/超时）是**本轮失败**
  继续退避，**不是**「版本撤回」；只有明确的 `Ok(None)`（204）才是撤回停止。
  断网时误判撤回会让重试环一秒放弃。
- **R3 重试统一在外环**：内环下载器只做单次尝试（可断点）。不在内环再嵌
  重试——两层重试会让退避时长与次数失控。
- **R4 上报口径**：中间轮失败不上报；`failed_download` 新增值域（服务端
  `insert_report` 是自由字符串透传，无需改表；维护页统计补该维度展示）。
- **R5 文件名 sanitize**：`.part` 文件名由 version+platform 拼接，二者来自
  服务端 JSON / 插件 target——构造文件名前白名单过滤 `[A-Za-z0-9._-]`，
  其余字符替换 `_`（防路径穿越，对抗性审查 R7）。
- **R6 元数据 sidecar**：`.part.meta`（JSON：url/size/版本）与 `.part` 同生共死；
  续传前核对，不匹配即弃（防同版本重登记换产物后续传拼出混合文件——那种
  文件只有 minisign 兜底会浪费整整一轮）。
- **R7 磁盘预检**：下载前查 `updates/` 所在盘可用空间 < size×1.1 → 直接报
  「磁盘空间不足」，不进重试环（重试也救不了磁盘满）。
- 4 轮最坏时长：4×(check 10s + 下载 120s) + 退避 22s ≈ **9.3 分钟**（旧稿
  8.5 漏算 check）。
- force 版本天然满足「已同意」语义（无稍后按钮）；外环对 force 与否行为一致。

### 2.2 前端 `ui/js/update.js`（+ login.html 内联路径）

- **最终失败改弹自绘重试窗**（复用 `showUpdateDialog` 模态样式）：
  「更新下载失败（已重试 4 次）：<原因>」+ [重试] [稍后]；重试=再调
  `download_and_install`（壳外环重新走）。不再只 toast。
- **已同意安装的自动再试**（仅主窗 index.html 挂载）：
  - 「已同意」标记落 `localStorage cmx-update-agreed {version, ts}`（跨窗共享、
    防页面刷新丢失；点「立即更新」即写入；成功 / 撤回 / 版本变化时清除）；
  - 每 30 分钟 `setInterval` 静默重试（WebView2 隐藏页定时器钳到分钟级——
    30 分钟间隔不受影响）；`visibilitychange` 回前台且距上次尝试 >5 分钟也触发；
  - 自动再试走同一命令（INSTALLING 防重入兜底并发）；再次最终失败只 toast
    不再弹窗（防打扰循环），标题栏按钮常驻可手动重试。
  - **自动再试的结果闭环（R14）**：invoke 返回 `Ok`（撤回 204 / 安装成功前的
    最后一帧）→ 清 agreed 标记；壳 `update_withdrawn` 事件 → 清 agreed +
    UPDATE_INFO + 按钮。两条路径保证标记不残留（否则 30 分钟空转一次后才自愈）。
  - 监听壳 `update_withdrawn` 事件（撤回时壳外环 emit，前端刷新按钮与标记）。
- **续传进度**：壳 emit 的 `received` 已含续传偏移、`total` 为完整大小，
  前端百分比公式不变（续传首轮显示直接从 N% 起跳，符合直觉）；新增
  `attempt` 字段仅用于前端识别「新一轮」（可选把按钮文案重置为「重试中…」），
  旧 payload 兼容（缺省视为 1）。
- **login.html（登录页）**：壳外环重试对它完全透明（同一条命令）；登录页
  「立即更新」失败仍走自己的 toast + 按钮态（弹重试窗是主窗行为）；用户
  登录进主窗后，主窗启动时读 agreed 标记恢复自动再试（标记同 origin 共享）。
- 30 分钟 snooze 标记（`cmx-update-snooze`）仍只管**弹窗**不重复，与自动
  重试互不干扰（两个 localStorage 键各司其职）。

### 2.3 缓存治理（壳层，挂启动路径）

- 安装成功后的清理**不在旧进程做**（NSIS 一启动安装器应用即退出，死进程
  什么都清不了——旧稿此处错误）：挂在**下次启动**，与 `report_pending_update`
  同一时机顺路执行：
  - 当前版本 == pending 标记 to_version（升级成功路径）→ 清空 `updates/` 整目录；
  - 顺带清理 30 天前的残留 `.part` / `.bin` / `.meta`（防磁盘堆积）。
- 新版本文件名含版本+平台，天然不撞旧缓存；`updates/` 目录不存在时自动创建。

### 2.4 服务端（cmx-container，`handlers/updates.rs`）

**download 加 Range（~50 行）**：

- 解析 `Range: bytes=<start>-[<end>]` 请求头（**只支持单区间开区间语义**；
  客户端续传只发 `bytes=N-`，带 end 也接受并截断到 total-1）；
- 响应 `206 Partial Content` + `Content-Range: bytes start-end/total` + 切片
  `file.data[start..=end]`；所有响应（含 200）加 `Accept-Ranges: bytes`；
- `start >= total` → `416 Range Not Satisfiable` + `Content-Range: bytes */total`；
- Range 头缺失 / 解析失败 / 多区间（`a-b,c-d`）→ 回退 200 全量（现状行为，
  旧客户端零影响）；D4 决策：多区间不做（客户端只用单区间）。
- 每请求仍从存储读全量再切片（门户到存储这段没省，省的是**用户最后一跳**）；
  6.8~32MB 量级 + 内部团队并发，可接受；存储层原生 Range 另立课题（不阻塞）。

**latest.json 平台项补 `size`（登记侧，~20 行）**：

- `register_version` / `reactivate_version` 落库前，对每个平台项按 `file_id`
  查 `cmx_file_detail.size` 自动补写 `size` 字段（**服务端自动取，不靠维护页
  手填**——手填错会触发客户端无谓的缓存弃用）；
- `latest_json` 下发原样带出；旧门户无此字段 → 客户端跳过长度校验（兼容）。

### 2.5 依赖与构建

- 壳 `Cargo.toml`：reqwest 补 `stream` feature（`bytes_stream()` 断点流式写）；
  回环流手写 TcpListener + tokio（full 已在），**零新增 crate**；
- tauri-plugin-updater 维持锁内 2.11.0（Cargo "2" 约束 + lockfile 钉住；
  大版本升级需回归本方案 C1 结论）。

## 8. 对抗性审查记录（2026-09-12，定稿前执行）

审查方法：按攻击面分类逐条挑战设计（安全 / 竞态 / 资源 / 兼容 / 失败模式 /
数据口径），发现即回填正文（标 R# 的均为审查产物）。结论与遗留如下。

### 8.1 已回填修复的发现（正文已含）

| # | 攻击/挑战 | 处置 |
|---|---|---|
| R2 | 断网时 check 抛错被误判「撤回」→ 重试环一秒放弃 | check 三态区分：Err=本轮失败退避，Ok(None) 才是撤回（§2.1） |
| R5 | version/platform 含 `../` 构造 .part 文件名路径穿越 | 白名单 sanitize（§2.1-R5，验收 T15） |
| R6 | 同版本重登记换产物 → 续传拼出混合文件，浪费整轮才发现 | `.part.meta` 元数据核对前置拦截（§2.1-R6，验收 T7） |
| R7 | 磁盘满时下载器写一半失败，重试 4 轮全浪费 | 预检可用空间 size×1.1，直接终止不上报（§2.1-R7，验收 T11） |
| R8 | NSIS 启动即退进程，「成功后停回环/删缓存」做不到 | 清理挂下次启动（§2.3，验收 T14） |
| R9 | `.part` 恰好完整时发 Range 得 416，误当失败重下 | 416 语义重定义：len==size → 直接进安装（§2.1-②b，验收 T8） |
| R10 | Windows 杀软短暂锁 rename → 误判下载损坏 | rename 重试 3 次；.part 保留下轮 416 短路（§6） |
| R11 | size 手填错误触发客户端反复弃缓存 | 服务端自动从 cmx_file_detail 取 size，不开放手填（§2.4） |
| R12 | 首轮不带 Range、次轮才发现服务端不支持 → 降级丢已下字节 | 下载器统一总是发 `Range: bytes=<len>-`（len=0 同理），206/200 即知能力，探测状态机消失（§2.1-②b） |
| R13 | 外环撤回即停后，前端按钮/标记无人清（壳返回 Ok≠前端感知撤回） | 壳 emit `update_withdrawn` 事件，前端 listener 统一清理（§2.2） |
| R14 | 自动再试 invoke 拿 Ok 后 agreed 标记残留 → 30 分钟空转 | 结果闭环：Ok 即清标记 + 事件双保险（§2.2） |
| R15 | pending 上报标记写盘时机歧义（下载前写会误统计 failed_download） | 下载失败即时报无需 pending；标记在 install 前落盘（进程中断保险）（§2.1-④e） |

### 8.2 审查后接受的风险（不再加码）

| 挑战 | 接受理由 |
|---|---|
| 下载走 http 明文（dangerouslyInsecureTransportProtocol） | minisign 签名对整包字节验签，中间人改一字节即拒装（P0 既有结论，非本方案新增面） |
| 每请求全量读存储再切片（门户↔存储没省） | 包体 ≤32MB + 内部并发小；优化需存储层原生 Range，另立课题 |
| 回环 latest.json 含 signature（公开物） | minisign 公钥体系下签名本就是公开分发的，无泄密面 |
| 自动再试 30 分钟在隐藏主窗仍会跑 | 壳层执行不依赖窗口可见；进度事件无人听，无害；WebView2 节流不改变 30 分钟语义 |
| 退出登录后（主窗 hidden）visibilitychange 不触发 | 自动再试退化为仅 30 分钟间隔路径，可接受（§2.2 已注明） |
| 去槽化后 check_update 与 download_and_install 各查一次（重复请求） | 幂等只读；10s 超时；换取架构简单，值得 |

### 8.3 遗留观察项（上线后跟）

- failed_download 上报量 —— 若长期为 0，说明弱网假设过强，P1 重试参数可放宽；
- `.part` 磁盘占用（用户数据根目录 updates/）—— 30 天清理是否足够；
- 回环流在 macOS App Sandbox / Linux 无头环境的 bind 行为（Windows 已验证路径为主）。
