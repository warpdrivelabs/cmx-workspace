> 关联：`documents/20260917_TrueMate_工程功能差距清单.html`（图片多模态输入 = P0 项，证据 `cmx-agent-core/src/model.rs:27`）。

## 一、背景与目标

cmx-agent 当前用户消息是纯文本（`ModelMessage::User { text: String }`），用户无法把截图、文件喂给模型。本方案补齐「粘贴/添加图片与附件 → 大模型」全链路。边界条件：

1. **模型两态**：当前模型可能是多模态（`input_types` 含 image）也可能是纯文本模型；
2. **辅助解析可有可无**：用户可能配置了一个"图片解析"MCP 工具（如接视觉小模型的 MCP server）帮文本模型看图，也可能没配；
3. **附件不限图片**：文本文件、PDF、Office 文档、任意二进制都要能作为附件发送。

目标体验：**任何模型、配不配解析服务，用户都可以随意贴图与加附件，永不失败**——多模态模型真看图，文本模型借解析服务看文字转述，什么都没有时明示降级。

## 二、业界调研

### 2.1 opencode（TypeScript，主对标）

#### 输入入口（`packages/tui/src/`）

| 环节 | 实现 | 证据 |
| --- | --- | --- |
| 触发 | 终端里按 `ctrl+v`（键位 `input_paste` 可配）触发 `prompt.paste` handler，**不是**监听终端粘贴事件 | `tui/src/config/keybind.ts:162`、`component/prompt/index.tsx:372` |
| 读剪贴板 | 按平台调系统命令取图：macOS `osascript`（PNGf）、Windows/WSL `powershell`（`Clipboard::GetImage` 存 PNG）、Linux `wl-paste` / `xclip`；全失败兜底读文本 | `tui/src/clipboard.ts:30-75` |
| 文本粘贴智能分流 | 粘贴的是**本地文件路径** → `readLocalAttachment` 判断文本/二进制，二进制（如 png）也转附件；粘贴 ≥3 行或 >150 字符 → 折叠成 `[Pasted ~N lines]` 占位 | `component/prompt/index.tsx:1183-1222` |
| 附件表示 | 输入框插入**虚拟占位符** `[Image N]`（extmark 高亮，不占真实文本），真实内容存 `FilePart`：`{ type:"file", mime, filename, url:"data:<mime>;base64,…" }` | `component/prompt/index.tsx:1224-1260` |

> 注：TUI 需要命令行读剪贴板是终端形态的限制。cmx-agent 双壳是 WebView，DOM `paste` 事件的 `clipboardData.items` 直接拿到图片 Blob，**这一整层复杂度对我们不存在**。

#### 图片规范化（`packages/opencode/src/image/image.ts`）

发送前统一 `normalize`，超限自动瘦身：

- 默认限额：最大 2000×2000 px、base64 ≤ 5 MB（配置 `attachment.image.{auto_resize,max_width,max_height,max_base64_bytes}`）；
- 超限 → photon(wasm) Lanczos3 缩放，按 0.75 比例逐档递减，每档尝试 PNG + JPEG 质量梯度 `[80,85,70,55,40]`，取**第一个达标**的组合；
- 全部档位仍超限 → 报 `SizeError`（用户可见）；
- 尺寸和体积都达标则原图直传。

#### 消息与发送（`packages/opencode/src/session/message-v2.ts`）

- 消息模型：`FilePart` 是 user 消息的一等 part（与 text part 平级）；
- 发送转换：file part → AI SDK file part（`{type:"file", url, mediaType}`），各协议层再降为各家格式：openai-chat → `image_url{url}`（`llm/src/protocols/openai-chat.ts:207`）、gemini → `inlineData`（`protocols/gemini.ts:188`）；
- **工具结果里的图**：OpenAI 兼容协议的 tool 消息只收字符串 → 把媒体抽出来**注入成后续独立 user 消息**（`message-v2.ts:296-313`），且仅当模型确实支持该类型，否则转用户可见错误。

#### 不支持图片的模型怎么处理（重点）

opencode 是**「乐观派」——不前置拦截，失败时错误可见**：

1. 能力元数据：models.dev 每个模型带 `attachment: boolean` 与 `modalities.input[]`（`core/src/models-dev.ts:72`），组装成 `model.capabilities.attachment / input.image`（`provider/provider.ts:1289-1300`）；provider 配置可覆盖（`v1/config/provider.ts:18`）。
2. 但**发送链路没有任何 `capabilities.attachment` 前置拦截**（全仓消费点只有插件模型定义与组装处）；TUI 贴图永远放行。
3. 真不支持时由**协议层 MIME 白名单**兜底：`validateMedia` 校验失败 → `invalidRequest("… does not support media type …")`，用户可见报错（`llm/src/protocols/shared.ts:174-206`）。白名单是**协议级**（openai-chat 只认四种图片 MIME），不是模型级——同协议下不支持视觉的模型会把图片透传给上游 API 挨批。
4. 另有 `stripMedia` 降级通路（图片→文本占位 `[Attached image/png: xxx]`，`message-v2.ts:212-217`），当前主链路**未启用**（无调用方传 true），属预留。
5. opencode **没有**"辅助模型/服务代看图"的机制——文本模型遇到图只能报错。

### 2.3 调研结论

| | opencode | codex | 取舍 |
| --- | --- | --- | --- |
| 输入侧拦截 | 不拦截，贴图永远放行 | 不拦截 | 采纳：乐观放行 |
| 支持图片 | data URL 进消息 part，协议层转格式 | 同 | 采纳 |
| 不支持图片 | 协议白名单报错（用户挨一次失败） | 发送前替换占位文本（永不失败） | **取 codex**：企业场景宁可降级不可炸；UI 同时给警示 |
| 图片瘦身 | 发送前缩放+降质梯度 | 无（原样 PNG） | 取 opencode（省 token 防超限） |
| 瘦身位置 | 服务端（CLI/内核分离所迫） | — | **改前端**（WebView Canvas，双壳共用一份，免 Rust 图像依赖） |
| 文本模型看图 | 无机制（报错了事） | 无机制（占位了事） | **自创：图片解析 MCP 辅助通路**（本方案 §4.7，两家都没有） |
| 文档类附件 | text/plain 转文本 part；PDF 依赖模型原生支持 | 无附件概念 | **自创：office crate 统一文本提取注入，模型无关** |

## 四、方案设计

### 4.1 总体决策（四方对齐）

```
┌─ 输入侧：乐观放行（opencode 式）—— 任何模型都可贴图加附件，不预判、不打断
│    贴图/选文件 → 前端预处理（图片压缩、文档读取元信息）→ 附件卡（可删）→ 随消息发送
│
├─ 发送侧：发送前按能力组装（codex 式降级兜底）—— 内核看当前模型 input_types
│    多模态   → 图片走 image_url parts 真发图
│    文本模型 → ① 配了图片解析 MCP：调解析服务得文字描述，以描述注入
│              ② 没配：替换占位文本「（图片内容已省略：当前模型不支持图片输入）」
│
├─ UI 侧：能力明示 —— 非视觉模型下贴图黄色警示「图将不直接发送」；
│    配了解析服务则显示「将由解析服务转述」；发送后回执区标注图的实际去向
│
└─ 辅助解析：图片解析 MCP 通路（自创，业界两家都没有）—— 文本模型也可"看"图
```

理由：opencode 的「报错可见」让用户白等一轮才失败；codex 的纯静默降级用户无感知、易误以为模型看到了图；两者叠加后贴图永不失败且去向透明。MCP 辅助解析补足中间态：**文本模型 + 有解析服务 = 降级但有转述**，覆盖"大模型可能是文本模型"的现实。

### 4.2 附件类型与处理矩阵（核心表）

| 附件类型 | 识别 | 多模态模型（input 含 image） | 文本模型 + 配了解析 MCP | 文本模型未配解析 |
| --- | --- | --- | --- | --- |
| 图片 png/jpeg/webp/gif | MIME 魔数 | `image_url` 直发（压缩后） | 调解析服务 → 描述文本注入 | 占位降级 |
| 纯文本 txt/md/源码/csv/json | MIME 或扩展名 | 内容注入 text part（围栏+文件名） | 同左 | 同左 |
| PDF / docx / pptx | 魔数/扩展名 | **office crate 抽取文本注入**（不依赖模型 PDF 原生能力，模型无关） | 同左 | 同左 |
| xlsx | 扩展名 | office crate 抽取（逐表文本化） | 同左 | 同左 |
| 其他二进制 | 兜底 | 文件名占位卡 + 路径提示（模型可用 fs_read 等工具自行处理） | 同左 | 同左 |

设计取向：**文档类统一走文本提取注入**而非依赖模型原生 PDF 输入——提取是确定性通路，模型无关、token 可控（截断），且 office crate 现成。模型原生 PDF 直发（Gemini/Claude）列期三可选优化。

### 4.3 消息模型扩展（serde 向后兼容）

```rust
/// 一张随用户消息发送的图片（引用落盘文件，不内联 base64）。
#[derive(Debug, Clone, Serialize, Deserialize, PartialEq)]
pub struct ImageRef {
    pub path: String,      // 相对数据根，如 "attachments/<session>/<hash>.jpg"
    pub mime: String,      // image/png | image/jpeg | image/webp
    pub bytes: u64,        // 压缩后字节数（展示用）
}

/// 一个随用户消息发送的文件附件。
#[derive(Debug, Clone, Serialize, Deserialize, PartialEq)]
pub struct FileRef {
    pub name: String,          // 原始文件名
    pub path: String,          // 相对数据根，同 ImageRef 规则
    pub bytes: u64,
    pub kind: String,          // "text" | "pdf" | "office" | "binary"
    pub excerpt: Option<String>, // 已提取的文本内容（截断后）；binary 为 None
}

pub enum ModelMessage {
    User {
        text: String,
        #[serde(default)]           // 旧会话日志无此字段 → 反序列化为空 vec，回放不炸
        images: Vec<ImageRef>,
        #[serde(default)]
        files: Vec<FileRef>,
    },
    ...
}
```

- `EventKind::UserMessage` 同步加 `#[serde(default)] images / files`；
- ⚠️ 已知坑（模型配置 ZCode 化方案踩过）：serde 内部 tagged enum 未声明字段会被静默丢弃——**新字段必须显式声明 + default**，不能指望透传。

### 4.4 附件存储

- 位置：`<数据根>/attachments/<session_id>/<sha256 前 16 位>.<ext>`；会话删除时顺带清理（与现有 sessions 治理同批）。
- 会话 JSONL 只存 `ImageRef` / `FileRef`（相对路径 + 元信息），**不存 base64 与全量文本**——JSONL 单行膨胀会拖垮整批单写的 store 与回放。
- 前端展示走新端点 `GET /api/attachment?session_id=…&path=…`（**挂既有登录门**，红蓝 P0 教训：新路由必须过鉴权；Tauri 壳同函数复用）。

### 4.5 前端收件与压缩（WebView，双壳共用一份）

**图片**（粘贴 `clipboardData.items` / 拖拽 / 附件按钮选文件）：

1. `createImageBitmap(blob)` 解码，超 2000px 等比缩到 2000px 内（Canvas drawImage）；
2. 压缩：先试 PNG 原格式，base64 超 5 MB 则转 JPEG 质量梯度 `[0.8, 0.7, 0.55, 0.4]` 取首个达标（对齐 opencode 梯度策略）；
3. 产物 base64 随发送请求走 body（`images:[{mime,data_base64}]`），**内核收到后立即落盘转 `ImageRef`**，后续回合从文件读——base64 只在传输与落盘瞬间存在，不进日志；
4. 拒收：非图片 MIME、解码失败、单张压缩后仍 >8 MB；单条消息图片上限 4 张。

**文件**（拖拽 / 附件按钮 / `input[type=file]` 多选）：单文件 ≤ 20 MB、单条消息附件总数 ≤ 8；前端只读文件名与大小，**不做内容提取**（提取在内核侧做，保证事件里 excerpt 与落盘内容一致）。

Rust 侧不做图像处理（免 image crate 依赖链），仅 fail-closed 校验：MIME 魔数（对齐 opencode `util/media.ts` 同款魔数判定）、大小、路径归一后必须落在 `attachments/<session_id>/` 内（防穿越）。

### 4.6 发送组装与降级（内核 `app.rs` + `openai.rs`）

发送时序（`send_streaming` 内，两壳共用）：

```
① 落盘：base64 → attachments/<session>/<hash>.<ext>，转 ImageRef/FileRef
② 落事件：UserMessage{ text, images, files } 进 JSONL（引用，非内容）
③ 文件提取：FileRef.kind ∈ {text,pdf,office} → office crate 抽取 → excerpt（≤32KB 截断）
④ 组 ModelMessage（按当前模型 input_types 分派，见下）
⑤ 发请求
```

`openai.rs` 组装：

- **视觉模型 + 图片**：content parts 数组 `[{"type":"text",...},{"type":"image_url","image_url":{"url":"data:..."}}, ...]`；
- **文本模型**：不产 image_url；图片按 §4.7 解析或 §4.1 占位；FileRef 有 excerpt → 以围栏文本并入 text part：
  `````
  [附件 文件名.txt]
  ```（内容，超 32KB 截断并注明）
  ````
  无 excerpt（binary）→ 占位行「[附件 name（未预览，路径 path，可用工具读取）]」。
- **占位降级**：图片替换为「（图片内容已省略：当前模型不支持图片输入，共 N 张）」（对齐 codex 文案语义），**原事件日志里的 images 保留不动**——回放仍见图卡（角标注明去向），换视觉模型后追问可重发历史图（文件在即复活）。

### 4.7 图片解析 MCP 辅助通路（自创，文本模型"看图"）

**触发条件**（发送时逐条消息判断）：`消息含 images && 当前模型 input_types 不含 image && 已配置解析工具` → 否则走占位降级。

**配置**：`providers.json` 顶层新增：

```json
{ "image_describe": { "server": "<mcp server 名>", "tool": "<工具名>", "prompt": "请详细描述这张图片的内容" } }
```

设置中心「模型」分区加「图片解析工具」下拉（枚举已启用 MCP server 的工具清单），留空 = 未启用。仅接受**返回文本**的 MCP 工具（`extract_text` 既有通路，MCP 载体零改动）。

**调用**：内核在 §4.6 第④步同步调用（复用现有 `McpTool.invoke`，10 秒超时），描述注入格式：

```
[图片 1 描述（由图片解析服务生成）]：<描述文本>
```

**缓存**：`sha256(图片字节) → 描述`，数据根 `cache/image-describe.json`（上限 200 条，超出淘汰最旧）——同一张图重复发送不重复解析、不重复烧解析服务 token。

**失败兜底**：超时/报错/空描述 → 自动退回占位降级，事件标注 `describe_failed`，UI 图卡角标「解析失败·未发送」，不阻塞消息发出。

**权限口径**：解析工具在配置时即被视为用户显式授权（用户在下拉里亲手选了它），发送前自动调用**不走回合内审批**，但落一条 `tool_invoked` 事件（标注 `internal:image_describe`）保持可审计；回合内模型主动调同一工具仍走正常审批。

### 4.8 UI（真源 `cmx-agent-web/ui/`，双壳自动共享）

- **输入态**：粘贴/拖入/选择 → 输入框下方附件卡条：图片卡（缩略图+尺寸+压缩后大小+✕）、文件卡（类型图标+文件名+大小+✕）；非视觉模型时条首黄色警示——未配解析：「当前模型不支持图片，图将不会发送」；已配解析：「图将由〈解析工具名〉转述后发送」；
- **发送态**：附件卡进入消息后即清空；发送瞬间若触发解析，输入框上方细进度行「正在解析图片…」（超时自动放行）；
- **回放态**：`renderHistory` 遇 `images/files` 渲染卡（图片点开大图浮层、文件可点击下载走 `/api/attachment`）；每卡角标注明实际去向：`已发送` / `已转述` / `未发送` / `解析失败`；
- **计费提示**：图片卡 hover 显示 token 粗估（宽高/750），防无感烧钱；
- 双主题通路照红线执行：色值全走 `var(--sap*, fallback)`，禁硬编码。

## 五、分期

### 期一（本期，全量闭环）：图片 + 附件 + MCP 解析

§4 全部：图片全链路、文本/PDF/Office 附件提取注入、图片解析 MCP 辅助通路、四态去向回放。理由：用户明示"图片、附件都要做"；MCP 通路是文本模型看图的唯一手段，与图片链路同根（同在 §4.6 分派点），拆开做反而返工。验收见 §七。

### 期二（P1）：通路扩展

1. **fs_read 读图**：视觉模型下 read 图片文件返回图片内容——OpenAI 兼容协议 tool 消息只收字符串，学 opencode 抽出来注入后续 user 消息（`message-v2.ts:296` 同款）；
2. @浮窗选中文件 → 直接入附件卡（替代现 `@path` 文本）；
3. IM 三通道（飞书/QQ/微信）收图收文件 → 走同一 `attachments` 落盘与分派逻辑；
4. 文档类附件反向出口：模型产出的文件（chart/导出）入附件卡可下载。

### 期三（P2）：多模态扩面

PDF 原生直发（Gemini/Claude `inlineData`，模型 pdf 能力判定）；视频/音频；粘贴长文本折叠占位（opencode `[Pasted ~N lines]` 同款）；图片本地脱敏（发送前马赛克选区）。

## 六、边界与坑

1. **serde default 必须**：tagged enum 新字段不声明会静默丢弃（模型配置方案已踩，§4.3）；旧会话回放、旧客户端发来的无 images 请求都必须无损兼容。
2. **MLamp 网关透传待实测**：`glm-5.2` 支持视觉，但网关是否原样透传 `content` parts 数组（不剥图）需真机验证；mock 网关 e2e 同步补「带图请求 → 断言 body 含 image_url」场景。若网关剥图，属基础设施问题，UI 明示「网关不支持」。
3. **JSONL 体积**：图片与文件只存引用（§4.4），严禁 base64 与全量提取文本进日志（excerpt 只进请求不进日志）。
4. **附件鉴权**：`/api/attachment` 必须挂登录门 + 校验 session 归属（路径穿越与越权读图双防）。
5. **解析 MCP 阻塞**：同步调用最长 10s——期间输入框禁重复发送（代际守卫已有 `_sendGen` 机制可复用）；解析服务不可达必须自动降级放行，不允许卡死发送。
6. **office 提取失败**：加密/损坏 PDF、奇异 docx → 提取异常按 `binary` 兜底（占位+路径提示），不让附件发送失败。
7. **桌面壳缓存**：UI 改动须重建桌面壳才可见（既有坑）；浏览器端强刷 `cache: reload`。
8. **删除语义**：会话删除连带 `attachments/<session_id>/` 清理；单卡 ✕ 仅移除待发送项，已落盘文件随会话生命周期回收。
9. **最大步数联动**：附件不消耗步数预算（是消息附件非工具调用）；解析 MCP 是发送前旁路调用，不计入回合 steps。
