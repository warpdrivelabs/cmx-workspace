# 审批入口与流程轨迹统一方案

> 2026-09-02 · 触发：待办办理页出现「双审批历史」（cr-form 内嵌审批历史卡 + 右侧属性面板流程轨迹），且变更申请单入口没有右侧轨迹。本文调研主流产品后给出统一方案。

## 一、现状问题

| # | 问题 | 位置 |
|---|------|------|
| 1 | **双审批历史**：同一页面上 cr-form 自带「审批历史」卡（分段时间线）与 property 面板的「流程轨迹」（task-form 全节点轨迹轴）内容重复 | 待办中心 → 办理（console='none' 的 MDM 任务） |
| 2 | **入口体验不一致**：变更申请单列表「详情/修改重提」经 openTab 只开单页 tab，无右侧轨迹、无三栏工作台 | `cr-todo.js` openTab |
| 3 | 动作位置两套并存：MDM 走表单内业务按钮（console='none'），通用流程走 property 平台控制台——此为有意设计（避免双口径），保留 | 全局 |

## 二、主流产品调研

- **钉钉 / 飞书审批**：**一个审批详情页**，多入口触达（待办任务、卡片快捷审批、消息、工作台）。详情页 = 表单 + 审批记录时间线 + **按当前用户权限渲染的动作区**（办理人见 同意/拒绝；发起人见 撤回；否则只读）。参见 [钉钉 OA 审批用户手册](https://alidocs.dingtalk.com/i/p/L4BYmaE53pwmNA8EYRBGveyKY5439mDA)、[流程中心接入：详情页出现同意/拒绝按钮 + 同步生成待办](https://open.dingtalk.com/document/orgapp-server/oa-approval-process-center-access-example)、[打开审批详情](https://open.dingtalk.com/document/development/open-approval-details)。
- **SAP Fiori My Inbox**：任务中心模式——待办详情 = 表单 + 右侧 approval timeline + 底部动作；业务单据（如采购订单）详情另有自己的审批历史块。两个视角内容有差异（任务链 vs 单据状态），但企业实践中普遍把"两处都像审批历史"视为认知负担。
- **Camunda / Flowable 任务列表**：表单 + 任务动作；流程图/历史是辅助视图（tab / 侧栏），不与表单内重复铺陈。

**业界共识提炼**（回答"是不是只有从待办进去的才有审批？"）：

1. **审批动作跟权限走，不跟入口走**——只要当前用户是开放任务的办理人（或发起人可撤回），无论从待办、单据列表还是消息进入，动作都出现；没有权限就只读。
2. **审批记录/轨迹跟单据走，任何入口都可见**，且**只呈现一份**。

## 三、方案 A（定稿）：轨迹统一在右侧属性面板，两个入口同一条轨迹

> 2026-09-02 评审定稿：用户确认希望"从变更申请单进入也用右侧的流程轨迹"。轨迹唯一落点 = 右侧属性面板（task-form 轨迹视图）；表单内不再画任何审批历史；列表「详情」改开与待办办理同款的三栏工作台。

1. **删表单内审批历史**：cr-form 移除「审批历史」卡（含其数据拉取）——重复的唯一来源被移除。
2. **待办入口（现状保持）**：办理打开三栏 worknode，property 挂 task-form 只读轨迹（全节点轨迹轴 + 意见，20260902 已升级）。
3. **列表入口（本次补齐）**：变更申请单「详情 / 修改重提」不再 openTab 单页，改走与 `todo-center.buildAndOpenTaskForm` 同构的 worknode 组装：content = cr-form（view/autoEdit 按状态），property = task-form 只读轨迹。打开前查一次 `review-context` 拿 `instanceId/taskId` 组装上下文（已有端点，无需后端改动）。
4. **动作跟权限**：审批动作保留在业务表单内（现有 canReview / canApply / canWithdraw 按钮组），非办理人从任何入口进入 = 同一页面只读。

**收益**：任何入口都是"表单（左/中）+ 流程轨迹（右）"的同一形态；轨迹全系统一份；列表入口不再缺轨迹。

**成本**：cr-form 删一块卡 + cr-todo 改 worknode 组装（小）；无后端改动。

## 四、备选方向（均不采纳）

- **B1 轨迹进表单页**（审批记录卡住 cr-form 页内、属性面板去流程化）：业务页与属性面板是两个挂载点，后续任何一方回归都会再出现双轨迹；且轨迹实现下沉为 MDM 私有。
- **B2 保持现状**：双审批历史 + 列表入口无轨迹，问题原样。

## 五、实施清单（批准后）

1. `cr-form.js`：删除「审批历史」卡渲染与 flow-history 拉取（审批历史数据统一由 property 的 task-form 轨迹视图经 comments 接口呈现）。
2. `cr-todo.js`：`详情` / `修改重提` 动作改为 worknode 组装（review-context → instanceId/taskId → content=cr-form + property=task-form 只读轨迹），与 `todo-center.js buildAndOpenTaskForm` 同构。
3. 回归验证：待办办理无双历史；列表详情右侧有同一条轨迹；退回单从列表进入可直接 编辑+保存并提交；非办理人只读。

## 六、后续增强（不在本方案范围）

- 待办卡片层快捷审批（同意/驳回一键，钉钉卡片模式）；
- 轨迹轴跳转流程图（design-viewer 全节点高亮当前令牌）。

## 七、实施修订（2026-09-02 晚，验证反馈后）

实施中发现两处需要修订，均已落地并实测：

1. **「删表单内审批历史」收窄为「工作台入口不画」**：worknode 组装失败/查不到实例时的**单页兜底入口**（openTab 直接开 cr-form）没有 property 轨迹区，页内审批历史卡全删会导致这类入口"什么都没有"。修订：审批历史卡**保留在 cr-form，仅在单页入口渲染**（`!flowApprove && !flowEdit && view 非编辑 && 非草稿`）；工作台入口（formMode=approve/edit）不渲染，轨迹唯一落点仍是右侧 property——两形态各自只有一份历史。
2. **worknode content props 必须带流程上下文**：content 视图 props 原来只传 `formCtx`（无 formMode），内容区 cr-form 按普通查看态渲染出页内历史卡，与右侧轨迹双历史复发。修订：content props = `{ ...formCtx, ...ctx }`。
3. **流程页首帧引导去 rAF 单依赖**（顺带修的健壮性缺陷）：task-form / todo-center 的 mount 原来把 `loadTodos/loadAll` 全押在 `requestAnimationFrame` 里；实测嵌入式浏览器面板在遮挡/后台时会**无限暂停 rAF**（页面 visible 但帧回调永不触发），轨迹/待办永远停在初始空态。修订：rAF 与 `setTimeout(0)` 双路竞速引导，谁先跑谁置位。这也解释了"轨迹有时是空的、刷新又好了"的偶发现象。

## 八、二次修订（2026-09-02 深夜，用户评审反馈）

用户对工作台形态的最终裁定：**取消右侧独立属性面板，流程轨迹与状态直接进表单页**，已办结单不显示操作栏；轨迹做成独立组件、与待办属性面板同款样式。

1. **`<cmx-flow-trail>` 自定义元素（组件化落地）**：数据驱动（`el.trail = { instance, definition, comments }`），内部完成全节点步骤构建（allnodes 口径）+ tf 系样式渲染，与待办属性面板轨迹同一外观。native-page 跨页不能 import 共享模块（Blob URL 限制），按「内联副本+同步注释」约定在 cr-form / task-form 各持一份，`customElements.get` 守卫保证同文档只注册一次。首版落地在 cr-form；task-form 属性面板暂沿用自身渲染（标记一致样式），后续可切换到同一元素。
2. **入口形态归一**：MDM CR 的详情/修改重提（cr-todo）与待办办理（todo-center，`console='none'` 且 `nativePage === 'portal.mdm.cr-form'`）一律开**纯内容工作台标签**（app.openNode，content-only，无 property）；其它 `console='none'` 但页内无轨迹的表单保留 worknode + property 只读轨迹，保证任何待办都有轨迹可看。
3. **cr-form 表单内轨迹卡**：右栏 = 操作卡（按状态给按钮，已办结/已作废不给卡）+ 流程轨迹卡（逐轮 `<cmx-flow-trail>`，多轮显轮次头）；**编辑态（含退回重办）也显示轨迹**——修掉"待办第一条（退回单编辑态）没有轨迹"的回归。数据源 flow-history（实例+意见）+ /api/flow/instances/{id}（tokens/tasks）+ /api/flow/definitions（节点轴）+ /api/iam/users/list（办理人显示名快照）。
4. **无权限/终态提示状态化**：已激活=「流程已办结，单据已激活落字典，无可用操作」；已驳回=「审批已驳回，可编辑修改后重新提交」。

## 九、三次修订（2026-09-02 深夜，轮次展示裁定）

用户裁定：**轨迹不再拆轮次**——待办属性面板只看当前实例、不分轮，表单页也不分，全入口统一「只看最新一轮实例」。

1. **ftLoad 只取最新实例**：flow-history 倒序第一条 → 补全量 tokens/tasks + 定义轴，不再 slice(0,5) 逐实例拉取（省 4 次实例接口）。驳回/撤回重提的旧轮实例与旧轮意见不展示（与待办面板同口径；当前轮内的退回证据仍可见——退回动作发生在当前实例内，意见卡正常显示）。
2. **flowTrailHtml 单份组件**：去掉「第 N 轮」头与 data-round 逐轮回填，右栏固定挂一个 `<cmx-flow-trail>`，bind 回填 `[0]`。
3. **清理死样式**：旧版内联轨迹渲染器的 `.fh-state/.fh-node/.fh-dot*` 等整块页内 CSS 删除（组件自带 shadow 样式），页内仅留容器 `.fh`。
4. **轨迹瘦身与栏宽对齐（同夜续裁）**：`<cmx-flow-trail>` 改纯时间线——删头部（单据号/流程名·状态）与四格摘要（流程/单据/当前节点/实例状态），表单页自身已有这些信息；「流程轨迹」卡标题**保留**（用户复裁：头上信息不要，标题得留）。右栏 `.action-panel` 240px → **300px**，对齐门户属性面板默认宽（`--property-width` 300px）。
5. **草稿也显轨迹**（同夜续裁）：mdm-cr-all 第三条为「提交过又撤回」的草稿，有已终止实例却被 draft gating 整卡隐藏。修订：view 态一律拉轨迹并显示——撤回草稿展示已终止轮次（撤回后 ftLoad 重拉而非清空），全新草稿走「提交后此处展示」占位卡；review-context 仍仅非草稿拉取。
6. **终止实例的轨迹语义修正**（同夜续裁，用户指出「主数据审批已完成但又退回」矛盾）：已完成节点的终局意见是退回/驳回/取回时，状态标签显示动作本身（退回 warn 色/驳回 rej 色）而非「已完成」——终止实例无活跃令牌，退回检测失灵，以意见结论为准；TERMINATED 实例时间线尾部补「流程已终止，后续节点未执行」提示（有后续节点时它们照常显示「未经过」）。此扩展仅在 cr-form 侧 ftBuildSteps（task-form 属性面板只渲染在办实例，用不到）。
7. **意见办理人统一显示名**（同夜续裁，用户问「为何两个制单两个退回」）：核查数据为真实历史（同一轮内 提交→退回→再提交→再退回，四条意见四个 taskId），非重复渲染；但意见记录里的 nickName 是写入时快照，同一用户改昵称后新旧意见显示成两个名字（Super Admin/admin），加剧重复感。ftActor 改为优先按 userId 查用户快照（__cmxFlowUsers）统一显示名，快照缺失才回退 nickName/userName。
8. **轨迹改事件流视图**（同夜定稿，用户提议 + 主流调研背书）：`<cmx-flow-trail>` 从「节点轴+节点下挂意见卡」改为钉钉/飞书「审批记录」口径的**时间正序事件流**——一条意见一条事件（节点名+动作徽标+办理人+时间+意见），退回重走同一节点出现多次；「发起」为人造首条（发起人+发起时刻取首条意见，实例全量无 startedBy/createdAt 字段）；尾部补当前等待节点（办理人=未办任务 assignee）与待重走/未到达节点（待处理）；TERMINATED 实例尾部不补节点、保留终止提示。构建函数 ftBuildSteps → ftBuildEvents（task-form 属性面板的节点轴口径不变，视图职责分工）。

## 十、组件上收 cmx-data-comp（2026-09-03，单一真源定稿）

用户裁定：三页内联副本虽运行时是同一组件（define-once 守卫 + 字节级同步），但每改一次须同步三份源码 + 两仓发布副本，仍非「一个组件改一处」——走上收共享组件库方案（方案 1）。

1. **组件归库**：`<cmx-flow-trail>` 定义移至 `packages/cmx-data-comp/src/components/cmx-flow-trail.js`（barrel 副作用 import 全局注册一次；package.json exports 增 `./components/cmx-flow-trail.js` 子路径）；导出 `CmxFlowTrail` 类 + `buildFlowTrailEvents` 纯函数。native 页 Blob 模块不能 import 共享代码的限制，由「页面内联副本」改为「库全局注册、页面只写标签」化解——§九的「三页同副本须同步」约定就此作废。
2. **三页删内联块**：mdm/cr-form.js 保留页面专属 ftDefinition/ftLoad 取数（去掉 ftUsers 预拉，用户快照改由组件内部兜底）；flow/task-form.js、flow/todo-center.js 整块删除（含各自持有的死副本 ftDefinition/ftLoad）。各页注释口径从「三页同副本」改为「cmx-data-comp 同一份」。
3. **组件能力微升**：办理人快照兜底拉取移入组件（模块级并发去重、失败可重试；页面 loadUserSnapshots 已填 __cmxFlowUsers 时零请求）；esc 换库内 escHtml；事件流构建/渲染逻辑与 §九.8 定稿版逐行等价。
4. **Neo 皮肤合规（新组件进库门槛）**：走 onboarding **A 写法**——基础样式仍由 `--sap*` 令牌派生（`data-cmx-skin="plain|none"` 回退即原视觉），默认 neo（门户注入 `__cmxDefaultFlowTrailSkin='neo'`）时强调色走 `--neo-cyan` 随 `data-cmx-skin-tone`（cyan/mint/violet/azure）切换，当前节点圆点加荧光；支持 `data-cmx-style-id` 页面级覆盖；圆点数字 ui-monospace。单测 9 例（注册/事件流/终止/空态/重绑/皮肤三态 + buildFlowTrailEvents 纯函数 3 例）全过；eslint 与存量组件同基线（innerHTML 警告与 panel/empty-state 一致）。
5. **文档同步**：cmx-components-guide 计数 96 → 97（= 35 显式 define + 63 ignite 映射 − 重叠 1）；SKILL.md 分类表/决策树、display-components.md 新增 §8 条目；AGENTS.md 计数同步。
6. **生效条件**：cmx-data-comp 从源码消费（main→src/index.js），**需重建 CMXPortalManager 才生效**（build 时机由用户掌握；设计器同依赖该库，建议双端构建验证）。构建前旧 bundle 无该元素定义，页面轨迹区渲染为空（未注册标签不报 JS 错），属预期过渡态。
