# cmx-agent 向用户提问工具（ask_user）方案

> 2026-09-14 初稿，同日经红蓝对抗交叉审核修订（R2，见 §8）。目标：给 cmx-agent 增加「执行过程中主动向用户提问、挂起等结构化回答后继续」的能力，交互形态对齐 ZCode 式提问卡片（header 标签 + 问题 + 单/多选项 + 自由输入 + 忽略/提交 + 多问题分页）。参考 opencode（`question` 工具）与 codex（`request_user_input` 工具）的实现逻辑。

---

## 1. 背景与现状缺口

cmx-agent 目前与用户的双向交互只有一条结构化通路：**工具审批（人在环，X4）**——高风险工具执行前挂起，前端弹审批卡，用户只能回答「允许/拒绝」二元决策。模型没有「向用户抛出开放问题并拿到结构化答案」的能力：

- `crates/cmx-agent-tools` 的工具清单里没有任何提问类工具；
- `EventKind`（`cmx-agent-core/src/event.rs`）没有提问事件；
- 模型只能在回复文本里"问一句"然后结束回合，等用户下一条消息——循环已停、无挂起、UI 无答题卡，体验上与"任务做完等指令"无异。

## 2. 对标调研结论（opencode / codex）

### 2.1 opencode（`question` 工具）

- **独立 first-class 机制**，不复用 permission（审批）代码，但结构平行：pending Map + Effect Deferred 挂起 + `question.asked/replied/rejected` 事件 + HTTP reply 端点。
- 工具入参：`questions: [{ question, header(≤30 字符), options: [{label(1-5 词), description}], multiple? }]`；**客户端自动附加"自己输入答案"选项（custom 默认 true），模型不得自供 "Other"**；推荐项放首位标 "(Recommended)"。
- 挂起：工具 execute 在 `Deferred.await` 上阻塞（agent 循环同 fiber 停转），**无超时**；回答以 tool result 文本回灌（`User has answered your questions: ...`）；reject 则 tool part 置 error 且 agent 循环停止。
- 事件/恢复：SSE 推 `question.asked`；`GET /question` 供断线恢复；会话 abort 经 fiber 中断清理 pending（`Effect.ensuring`）。

### 2.2 codex（`request_user_input` 工具）

- 同样**独立于审批**：`TurnState` 里 `pending_approvals` 与 `pending_user_input` 是两个平行 map，共用 oneshot-waiter 基础设施与中断清理路径。
- 工具入参：`questions: [{ id, header(≤12 字符), question, options: 2~3 个 }]`，`is_other` 强制 true（客户端自动追加自由文本），一次调用 1~3 问。
- 挂起：`Session::request_user_input` 注册 oneshot 到 `pending_user_input`，发 `EventMsg::RequestUserInput` 后 `rx.await`；回答经 `Op::UserInputAnswer{ id: turn_id, response }` 唤醒，**tool result 为 JSON**：`{"answers":{"<qid>":{"answers":["label","user_note: 自由文本"]}}}`。
- 超时/中断：core 阻塞式无超时；turn 中断 → sender drop → 模型收到 "cancelled before receiving a response"；空答案/忽略回灌空 map 继续。

### 2.3 两家共同点（即本方案的形状）

1. 提问是一个**模型可调用的普通工具**（非内核控制流），答案以 **tool result 回灌**继续回合；
2. 挂起-恢复用「pending 登记 + oneshot/Deferred + 会话绑定校验 + 中断清理」；
3. 与审批**机制独立、模式同构**；
4. schema 要素一致：`header` 短标签、`options: {label, description}`、自由输入由客户端附加、推荐项首位、限制问题数（1~3）。

## 4. 详细设计

### 4.1 核心类型与工具定义（cmx-agent-core + cmx-agent-tools）

**core 新增共享类型**（`cmx-agent-core`，事件/工具/服务共用）：

```rust
/// 一个提问选项。
pub struct AskOption { pub label: String, pub description: String }
/// 一个提问。
pub struct AskQuestion {
    pub id: String,        // snake_case 短 id，答案映射键
    pub header: String,    // UI 短标签（≤12 字）
    pub question: String,  // 完整问题
    pub options: Vec<AskOption>,  // 2~4 个
    pub multiple: bool,    // 多选（默认单选）
}
```

**工具 spec**（`crates/cmx-agent-tools/src/ask_user.rs` 新文件）：

- 名称 `ask_user`；JSON Schema 对应上述结构（`questions` 数组 1~3 项，`options` 每项 2~4 个）；
- guard：`requires_approval: Never` 且 **`idempotent: true`**（R2 修订：否则 `ApprovalPolicy::UnlessTrusted` 档下守卫会对提问本身弹无关审批卡——agent.rs:486-509 对非幂等工具强制审批，`GuardHints.idempotent` 默认 false）；
- **服务端硬规范化**（R2 修订：schema 只是给模型的建议，`tool.rs:86` 明示"M0 不做严格校验"，必须在 invoke 内强制）：`questions` 截断至 3、每问 `options` 截断至 4、字符串按字符数截断（question ≤200、header ≤12、label ≤30、description ≤100）；缺 `id` 补 `q1/q2/…`；**重复 `id` 改写为 `id_2` 等去重**（`serde_json::Map` 后写覆盖先写，不去重会静默丢答案）；规范化后 `options` 为空 → `ToolResult::err`；
- **并发防重**：调用 `service.ask` 前查 `service.has_pending(session_id)`，命中即返回 `ToolResult::err("已有待答提问，请等待用户回答")`；
- **工具描述（给模型的核心提示词，对齐 opencode question.txt 要点）**：
  - 仅当执行中遇到**真正需要用户决策/澄清**的分歧点才用；能用合理默认/从上下文推断就不要问；
  - 一次 1~3 问，别连续刷屏；`header` ≤12 字、`label` 1~5 词；
  - 客户端会自动提供自由输入，**不要添加"其他"类选项**；
  - 推荐项放首位并在 label 后加 `(Recommended)`；
  - 答案将以 tool result 回灌；用户忽略/超时返回 `dismissed:true`，此时不要反复追问，自行选择合理默认继续。

**执行逻辑**（事件发射已上移内核，见 §4.3，工具只负责规范化 + 挂起）：

```rust
async fn invoke(&self, input, ctx) -> Result<ToolResult, ToolError> {
    // 1. 硬规范化（截断/补 id/去重/空 options 报错）+ 同会话防重
    // 2. self.service.ask(&ctx.session_id, &request_id, questions, answers_rx).await
    //    （request_id 由内核生成并随 QuestionAsked 事件传入？否——见 §4.3 顺序说明）
    // 3. → Answered(map) | Dismissed；组 tool result JSON（见 §4.6）
}
```

> **request_id 归属**：由 `QuestionService` 生成（UUID，R2 修订：不用可枚举的原子计数），工具拿到后放进返回给内核的"附带元数据"？——不引入复杂机制：`QuestionAsked` 事件由内核在 pre 相落，事件里的 `request_id` 由服务在 `register()` 时生成并返回给内核（内核 pre 相调 `service.register(session_id, questions) -> (request_id, rx)`，再把 rx 与 request_id 通过 `ToolCtx` 扩展传入工具）。为避免 `ToolCtx` 膨胀，`ToolCtx` 增加的是 `session_id` 与 `question_channel: Option<&'a QuestionChannel>` 两个字段（`QuestionChannel` 为 core trait：`register/cancel_session/revoke_all`），由内核在 pre 相为 `user_interactive` 工具填充。工具与服务的具体接缝在实现时允许微调，但必须守住两条：**工具不触碰 `SessionLog`**；**事件只从内核写入会话日志**。

**服务注入方式**：`AskUserTool::new(Arc<QuestionService>)`——`QuestionService` 在 core（对齐 `Approver`，agent.rs:69-91 先例），tools→core 单向依赖成立。app 层 `builder.rs` 按门控装配（§4.5）；未装配时注册降级实例（`QuestionService::disabled()`，ask 直接返回 dismissed）。

### 4.2 QuestionService（cmx-agent-core/src/question.rs 新文件，R2 落位修订）

对齐 `InteractiveApprover`（`app/approval.rs`）的骨架：

```rust
pub struct QuestionService {
    pending: Mutex<HashMap<String /*request_id*/, PendingQuestion>>,
    timeout: Option<Duration>,   // 默认 Some(30min)；0 = 无限
}
struct PendingQuestion {
    session_id: String,
    questions: Vec<AskQuestion>,   // R2 修订：必须存，答案按 id 组装依赖它
    tx: oneshot::Sender<QuestionOutcome>,
}
pub enum QuestionOutcome {
    /// 按 question id 映射的答案；选项 label 与 "user_note: 自由文本" 混排。
    Answered(serde_json::Map<String, Vec<String>>),
    Dismissed,
}
```

- `register(session_id, questions) -> (request_id, rx)`：UUID 作 request_id；登记 pending；
- `answer(request_id, answers, session_hint) -> bool`：**session_hint 强制非空**（R2 修订：审批 `decide` 的空串放行是既有弱点，不再继承）；会话绑定校验（B 会话的决定不得作用于 A 会话挂起的提问）；命中则组映射（`answers.len() != questions.len()` 时按问题数补空数组/截断，不静默 zip）后 oneshot 唤醒；**`tx.send` 失败（接收端已死）同样摘除条目**（R2 修订：防幽灵 pending——IM 桥热重载 drop 回合 future 后，死对发送端残留会让后续 answer 永远 miss）；
- `dismiss(request_id, session_hint) -> bool`：同上校验与摘除；
- `has_pending(session_id) -> bool`：并发防重查询；
- `pending_in_session(session_id) -> Vec<PendingInfo>`：供 `ListPendingQuestions` 与前端在途恢复；
- `cancel_session(session_id)`：该会话全部 pending 逐一 dismiss——挂进 `cancel_session_turn` 与删除会话路径；
- `revoke_all()`：登出/换账号时全部 dismiss（挂进 `logout`，app.rs:563-565 现有 approver revoke_all 同点，一处覆盖登出+改密两条路径）；
- 等待侧：`register` 返回 rx 后由内核（或工具）await；超时按 `Dismissed` + `Note` 事件说明。

### 4.3 事件发射：内核落事件（R2 P0-1 修订，新增小节）

**事实约束**（审核确认）：`ToolCtx` 无日志句柄；session 每回合从 store 加载、回合结束即弃（app.rs:1253-1260），无常驻会话表；事件只有经过当前回合的 `SessionLog::append` 才会 (a) 落库（回合末 `session.log.events()[before..]` 切片，app.rs:1364-1366）、(b) 推达 ChannelSink（回合 SSE）与 BusSink（进程总线）。工具与服务都够不到它。审批事件的先例正是**内核**落的（agent.rs:578-603），不是审批者落的。

**设计**：

1. `ToolSpec` 新增门控位 `user_interactive: bool`（默认 false）——语义"该工具会挂起等待用户输入"，`ask_user` 置 true。内核不硬编码工具名；
2. 内核 `handle_tool_calls_as`（agent.rs:409 起）：
   - **pre 相**（执行前，agent.rs:479 审批判断之后）：对 `spec.user_interactive` 的调用，`service.register()` 生成 request_id、拿 rx，`session.log.append(QuestionAsked { request_id, questions })`（此刻即推 SSE/总线，前端弹卡），并把 `(request_id, rx)` 存入该调用的 pending 记录；
   - **回灌段**（agent.rs:540-565 串行回灌循环）：工具结果产生后，对 `user_interactive` 调用 append `QuestionResolved { request_id, answered, by }`（`by` 对齐审批：`user`/`canceled`/`timeout`）；
3. `QuestionAsked` 落日志即满足三通路：回合 SSE 实时达前端（ChannelSink unbounded，stream.rs:31-37，挂起期间 SSE 保持打开——web main.rs:256 spawn + keep-alive）、BusSink 达 Tauri 壳（shell main.rs:850-907 订阅转发）、回合末落库供重放；
4. 已知限制（R2 注记，不修）：`bus.rs:2` 注释声称的 `/api/subscribe` 在 Web 壳不存在（文档漂移），**Web 壳收不到 IM 来源回合的实时事件**——IM 答题本就属阶段二，桌面回合走回合流不受影响。

**模型上下文安全性**：`model_context`（session.rs:68-91）白名单投影仅 UserMessage/ModelMessage/ToolResult，新事件天然不回灌；问题内容模型本就可见（`ToolInvoked.call.input`），答案在 `ToolResult`——语义完备。

**tool_use/tool_result 配对不变量**（审核确认的关键乐观结论）：内核取消不走 abort、只走"oneshot 唤醒 → 工具返回 Dismissed → join_all 收敛 → 回灌段无条件 `push_result`"——每个 ToolInvoked 必有配对 ToolResult，不会产生孤儿 tool_call（对比：中断若用 `tokio::abort` 杀任务则回合整体蒸发于落库前，同样无持久断裂）。须以单测锁死两条红线：**清理只走 oneshot 唤醒，禁止对回合任务 abort**；**`model_context`/出站消息构造前对"无结果 ToolInvoked"补合成 err 结果**（防未来中途落库改造引入断裂，openai.rs:49-82 严格配对会 400）。

### 4.5 门控矩阵（R2 新增小节）

提问挂起的每一分钟都在占住回合与（Tauri 下的）blocking 线程，且挂起点不可被 `TurnCancel` 旗标中断（旗标只在模型步边界检查，agent.rs:328-436）——因此**挂起只允许发生在"用户看得见、答得了"的桌面交互回合**：

| 回合来源 / 策略 | ask_user 行为 | 依据 |
| --- | --- | --- |
| 桌面交互回合（Web 壳 / Tauri 壳，`interactive_approval=true` 装配） | 正常挂起等答 | 用户看得见答题卡 |
| IM 桥驱动的回合（`TurnPolicyOverride::FULL_ACCESS`） | 直接 dismissed | im tick 串行内联 await（im/lib.rs:266-375），挂起冻死全部 IM 通道；IM 用户无答题面 |
| `ApprovalPolicy::Never`（无人值守档） | 直接 dismissed | 对齐"宁拒不挂"既有语义（agent.rs:574-589），不能旁路 |
| task 子智能体回合 | 直接 dismissed | 子回合不传 TurnCancel（task.rs:133-136）、子会话事件不实时外送（task.rs:124 + builder.rs:307-314）、`cancel_session(父id)` 够不到 `subtask-*` 前缀的 pending——挂起即不可取消 |
| CLI / e2e-serve（`interactive_approval=false`） | 直接 dismissed（降级实例） | 无 UI，fail-open |

实现：门控判断放**内核 pre 相**（与 `register` 同点）：非交互来源（policy never / FULL_ACCESS 覆盖 / 子回合——子回合经 task 工具跑，`TURN_POLICY_OVERRIDE` 或专用 task_local 标记可判）时跳过 register、直接以 dismissed 结果继续。工具内 `service` 为 `disabled()` 实例时同样 dismissed（CLI 降级）。

### 4.6 前门协议（cmx-agent-app/src/protocol.rs）

```rust
/// 提问答复（答题卡「提交」）。
AnswerQuestion { request_id: String, answers: Vec<Vec<String>>, session_id: String },
/// 提问忽略（「忽略」按钮）。
DismissQuestion { request_id: String, session_id: String },
/// 列挂起提问（在途恢复主路径；可按会话过滤）。
ListPendingQuestions { #[serde(default)] session_id: Option<String> },
```

- `answers` 按问题顺序：每问一个字符串数组（多选 = 多个 label；自由输入 = 一条 `"user_note: …"`）；服务端按 `questions[i].id` 组装映射后唤醒；
- 响应统一 `{"resolved": bool, "request_id": ...}`——未命中 pending（已答过/已清理/幽灵）返回 `resolved:false`；
- 派发薄封装到 `AgentApp::answer_question / dismiss_question / list_pending_questions`，与 `resolve_approval_decision`（app.rs:316）平行。

**tool result 回灌格式**（对齐 codex，结构化 JSON）：

```json
// 已回答
{"answers": {"scene": ["编程开发", "工具与配置"], "budget": ["user_note: 500 以内"]}}
// 忽略/超时/门控降级
{"answers": {}, "dismissed": true}
```

**在途恢复主路径**（R2 修订）：前端启动/切会话时调 `ListPendingQuestions`（后端 pending 是进程内存态，刷新不影响挂起），有则在该会话渲染待答卡；`GetEvents` 重放负责**已完成回合**的问答卡（`question_asked` 有对应 `question_resolved` 渲染结果态）。两者的交叠场景（重放出 `question_asked` 且 `ListPendingQuestions` 也命中）以前者为准渲染结果态。

### 4.7 双壳 UI（crates/cmx-agent-web/ui/ 真源，双壳共享自动生效）

对齐截图形态，`render.js` 增 `question_asked` 分支（紧跟 `approval_requested` 的渲染模式）：

- **卡片结构**：左上 `header` 标签块 + 问题文本；右上分页 `‹ 1/N ›`（单请求内多问题切页）；选项列表（`multiple` 用复选框，否则单选 radio；每项 `label` 加粗 + `description` 灰字）；末行自由输入框（占位"输入你的回答…"）；底部提示行（按实际键盘支持写，P1 鼠标为主）；右下 `忽略` + `提交`。
- **转义红线**（R2 明写）：`header/question/label/description` 与答案回显全部是模型可控文本（可被 web_fetch/browser_read 抓取的页面内容间接操纵），**一律过 `esc()`**（bridge.js:64），含进 `data-*` 属性的 `request_id`（对齐审批卡 render.js:486-495 属性位转义习惯；仓内有 xlsx sheet 名注入修复前科 render.js:225）。
- **提交**：`session.js` 增 `answerQuestion/DismissQuestion`，走既有 `call({cmd})` 通道；提交后立即置"处理中"防重复点击；失败 toast + 恢复可点；**必须检查 `data.resolved`**（R2 修订：`Approve` 未命中返回 `ok:true, resolved:false` 而现状 `approveTool` 只看 `r.ok`——失效审批卡会永钉"处理中"；提问卡新写 resolved 分支，`false` 时降级为"已失效"态。顺手可修审批卡同款坑）。
- **已解决态**：`question_resolved` 事件到达后替换为答案摘要（"✓ 回答：编程开发、工具与配置" / "✕ 已忽略 / ⏱ 已超时"）。
- **挂起观感**（R2 补）：`question_asked` 到达时撤"思考中" shimmer 行、暂停/切换"已工作 X 秒"计时文案为"等待回答"（对齐 `approval_requested` 的 `hideTyping` 处理，session.js:426）——否则挂起期间 shimmer 与跳表持续，观感等同卡死。
- **与工具卡的关系**（R2 补）：`ask_user` 会同时有工具卡（转圈）+ 提问卡；提问卡出现时将对应 call_id 的工具卡折叠为一行状态（"等待用户回答…"），`tool_result` 到达后照常收口。
- **分页边界**（R2 补）：`HIST_PAGE=300` 尾加载可能把 `question_asked/resolved` 对切开——渲染分支容忍孤儿 resolved（只渲染 meta 行），与审批卡现状同病，不阻塞。
- **CSS**：`chat.css` 按审批卡既有风格扩展；**双主题通路兼容，色值一律 `var(--sap*, fallback)`，禁止硬编码**（全局红线 §四、5）。
- **资产机制注记**（R2 补）：只改 `render.js / session.js / chat.css` 三个既有文件则 Web 壳白名单零改动、Tauri 跑 `sync-ui.sh` 即生效；若实施中新增 js 文件，必须手动在 web `main.rs` 资产 match 表加臂（include_bytes 白名单），否则 Web 壳 404。
- Tauri 壳与 Web 壳共享 `ui/` 真源（`sync-ui.sh`），协议同走 `dispatch_json`——**做一份双壳自动都有**。

### 8.2 审核确认站得住的核心论断（双方一致，未改动）

1. `model_context` 白名单投影（session.rs:68-91）——新事件天然不回灌模型，session.rs 投影零改动；

5. 回合 SSE 挂起期间保持打开（unbounded channel + spawn + keep-alive），`QuestionAsked` append 后下一帧即达；

### 10.16 追加修复：审批/提问卡 hover 偷选——点击选中被鼠标路径覆盖（2026-09-14 第十三轮）

**用户反馈**（附截图）：审批卡上「鼠标点击选不中了，现在是 hover 变色，但是点击应该选中，不是 hover 选中」。

**根因**：`bindInteractKeys` 里 `mousemove` 监听会把 `.qsel` 选中态持续跟着鼠标走——点选「允许」后，鼠标移向「确认」的途中只要扫过「拒绝」，选中即被偷成「拒绝」，点确认就误拒。实测复现：点选后 qsel=「允许」，鼠标扫过第 3 行后 qsel=「拒绝」。此设计自交互槽轮引入，真实鼠标流下必现。

**改造**（render.js 一处）：删除 mousemove 改选中监听；悬停反馈交给既有 CSS `:hover`（chat.css:431 本就存在）；选中只认两条路——鼠标点击（click→setHi）与键盘 Tab/↑/↓。行为与提示语「使用 Tab / 上下键选择，回车确认」一致。

### 10.17 追加修复：中断后工具卡仍转圈、审批卡残留（2026-09-14 第十四轮）

**用户反馈**（附截图）：点中断按钮后，等待审批的工具卡还在转圈，交互槽的审批卡也不消失。

**改造**（session.js closeInterruptedTurn 一处）：中断时即时清场，口径与重放 settlePendingCards 一致——①`.tool.tcard.run` 落「已中断」终态（空结果体补「已中断：未收到回执」）；②`.iline.ap-wait` 落「⏸ 审批无回执（回合被中断）」；③交互槽内未决审批卡/提问卡就地撤除。
