## 1. 背景与目标（用户视角）

- 现状：会话聊得越久，发给模型的上下文越长——先是变慢变贵，最终某一步直接被模型以「超出上下文长度」打回，回合失败且无自救，用户只能新开会话从头再来。
- 目标（对齐功能文档承诺的「上下文快满时，系统自动做压缩：删旧的工具输出、总结旧对话」）：
  1. **看得见**：输入框旁常驻上下文用量（最近一次请求的真实 token 数），临近上限变色预警；
  2. **压得住**：旧内容自动总结成结构化摘要 + 更旧的工具输出清理占位，近期原文保留——会话可以无限聊下去；
  3. **救得回**：就算真撞上模型窗口上限（配置偏大或网关限长），自动压缩后原话重试一次，回合不废；
  4. **不惊扰**：压缩只在时间线里留一张可展开的边界卡，历史消息照常回看（压缩只影响发给模型的内容，**不动界面历史**）。

## 3. 参考实现调研结论

### 3.1 opencode（参考源码 `E:\Pansoft\cmx\agent\opencode`，新旧两代实现都在；2026-09-18 二次深审逐文件核对）

- **触发**（两代不同）：
  - 旧代 `packages/opencode/src/session/`：**真实 usage 驱动、回合内每步检查**——每步请求完成后若 `usage.total ≥ usable` 即插入压缩任务（`prompt.ts:1164`、`processor.ts:493` 置 `needsCompaction`）；请求直接报溢出错误时同样触发（`prompt.ts:1320`，`overflow: !finish`）。`usable`（`overflow.ts:8-34`）= 模型有 input 上限时 `input − min(20k, maxOutputTokens)`，无 input 上限时 `context − maxOutputTokens`。
  - 新代 `packages/core/src/session/compaction.ts:232-243`：**请求前粗估驱动**——整个请求体 `JSON.stringify` 后 ÷4 估算，超 `context − max(output, 20k)` 触发。本文 §4.2.3 公式与新代一致。
- **双层策略**：
  - **prune（轻，`compaction.ts:273-317`）**：从尾往前累计工具输出估算，保住最近 `PRUNE_PROTECT=40k` tokens；可剪量不足 `PRUNE_MINIMUM=20k` 不动手；`PRUNE_PROTECTED_TOOLS=["skill"]` 豁免。三条**结构守卫**：`turns < 2` 跳过（永不剪最新一个回合）、遇压缩摘要消息即停、遇已清理过的 part 即停。已在清理名单的输出投影为 `[Old tool result content cleared]`。**时序**：回合结束后异步 fork 执行（`prompt.ts:1338`），不做发送前同步判定。
  - **compact（重）**：尾部预算（`min(15k, max(2k, usable×25%))`，`compaction.ts:115-120`）之外的历史序列化成纯文本，连同**上一次摘要**发给一次独立摘要请求（`max_tokens=4096`）。新代另有 `DEFAULT_KEEP_TOKENS=8k` 的近段保留。
- **摘要模板**（`core/src/session/compaction.ts:16-55`，精髓，本方案照抄结构）：固定 Markdown——目标 / 重要细节 / 工作状态（已完成·进行中·受阻）/ 下一步 / 相关文件；规则：空节写 `(none)`、保留精确路径/符号/命令/错误串/URL、**不许提「被压缩过」**。有前次摘要走「合并指令」，完整要点：旧摘要信息**单向不丢**（对话未提及的目标/约束/决策/并行线一律延续，仅删「已完成且不再需要」项）；冲突以新对话为准；新进展补入；**已完成项从 Active 迁入 Completed**；blocker 解决后更新但保留仍需细节；目标与下一步随现状刷新。
- **序列化格式**（两代一致，`[User]:` / `[Assistant]:` / `[Assistant reasoning]:` / `[Assistant tool call]: name(json 参数)` / `[Tool result]:`（截 2000 字符）/ `[Tool error]:`；附件降级为 `[Attached mime: name]` 占位）——**reasoning 参与序列化**（摘要质量考虑）。
- **投影组装**（`message-v2.ts filterCompacted:519-577`）：已完成压缩的「压缩用户消息+摘要助手消息」对被投影隐藏，实际发给模型的重排为 `[压缩标记, 摘要, …保留尾部…, 其后消息]`；溢出场景把被打断的用户消息重放为新消息（媒体降级文字占位）并自动续跑；自动压缩无重放目标时注入合成消息「Continue if you have next steps…」续跑回合（回合内压缩的固有需要——我们边界压缩无此需要）。
- **摘要请求自溢出**：新代预检 `估算(摘要提示) > context − 摘要输出预留` 直接放弃（`:190`）；旧代摘要请求本身溢出时报 `Session too large to compact`（`:451-455`）。

### 3.2 codex（参考源码 `E:\Pansoft\cmx\agent\codex\codex-rs`，2026-09-18 深审）

- **触发**（`session/context_window.rs`、`protocol/openai_models.rs:385-527`）：真实累计 usage（每响应落 rollout 持久化）≥ 自动压缩阈值；阈值默认 **窗口 90%**（`auto_compact_token_limit` 缺省 = `context×9/10`，配置值再 clamp ≤90%）；另有硬顶 = 窗口 × `effective_context_window_percent`（**默认 95%**，为系统提示词/工具开销/输出预留）。阈值统计支持 `BodyAfterPrefix` 作用域：压缩后把摘要前缀记为基线，只统计其后的增量（防反复逼近阈值抖动）。
- **溢出救援**（`session/turn.rs:329-350, 692-718`）：PreTurn / MidTurn 两相位 `run_auto_compact(ContextLimit)` 后**同回合重试**，每步一次性重试标志防压缩无效死循环。
- **摘要请求**（`compact.rs:244-330`）：**不序列化**——摘要器直接吃整段原历史 + base_instructions；请求自身溢出时**从最旧历史项逐条丢弃重试**（`remove_first_item`）。摘要产出以 **User 消息**注入（固定 `SUMMARY_PREFIX` 前缀标识，`is_summary_message` 靠前缀识别）；模板是松散 handoff 风格（四条要点），结构化程度低于 opencode——本方案取 opencode 模板。
- **压缩后历史**（`build_compacted_history`）：初始上下文 + 按 `COMPACT_USER_MESSAGE_MAX_TOKENS=20k` 预算保留的**最近用户消息原文**（只保用户消息，助手/工具全部进摘要）+ 摘要消息。三家取舍对照：codex 只保用户原话（防走样）、opencode v1 保结构化尾部（预算内全保）、本方案 = 压缩点后全部原文（回合边界压缩天然如此，最简且最丰富）。
- **usage 口径**：`TokenUsage{input, cached_input, cache_write_input, output, reasoning_output, total}`；真实 usage 优先、不可得时 `recompute_token_usage` 用历史估算重算基线（`session/mod.rs:4583+`）——与本方案「真实优先 + 估算退化」混合口径一致。

### 3.3 ZCode（`D:\ZCode\resources\app.asar` 抽样 + 自身行为实证）

- `autoCompactThresholdTokens`：token 阈值自动触发；
- `compactBoundary` 边界消息（`messageId` + `reason`）留在消息流里作锚点（回放/分叉都以它为界）；
- 行为：「对话过长时部分或全部上下文被摘要，摘要 + 未摘要的尾部一起进入下一个上下文窗口」——与 opencode 同构。

### 3.4 四条共通铁律

1. 触发靠 token 阈值（用量判定依赖真实 usage 或粗估）；
2. 策略 = 「旧内容摘要 + 近期原文」双层，不做一刀切；
3. 压缩 = **投影层行为 + 落一个事件**，不改写历史；
4. 摘要用**结构化模板**，不是自由发挥。

## 4. 方案设计

### 4.1 用量感知

1. **类型**：`cmx-agent-core/src/model.rs` 新增 `ModelUsage { input: u64, output: u64, cached_input: Option<u64> }`；`ModelResponse` 加 `#[serde(default)] usage: Option<ModelUsage>`。
2. **解析**（`openai.rs`）：
   - `build_request_body`：流式请求体加 `"stream_options": {"include_usage": true}`（非流式响应自带 usage，不加）。若网关对未知参数报错（错误文本含 `stream_options`），自动剥掉该字段重试一次（**二轮核实**：剥参须从 `body` 移除键——`complete_streaming` 的 3 次断流重试复用同一 body，否则后续尝试仍带该参数；剥参重试挂在 `upstream_error_message` 返回后的即抛分支前，与断流重试是两条路径）。
   - `StreamAcc`：任意帧出现顶层 `usage` 即缓存（OpenAI 约定最后一个 usage-only 帧的 `choices` 为空数组，现有 choices 解析天然兼容）；`into_response` 填入。**二轮核实**：`apply_stream_chunk` 里 `choice?` 会把 usage-only 帧早退无害跳过——捕获点必须放在函数**帧顶**（`choice?` 之前），否则独立 usage 帧收不到。
   - `parse_response`：读 `v["usage"]["prompt_tokens"|"completion_tokens"]`；`cached_input` 兼容两种网关形态——`usage.prompt_tokens_details.cached_tokens`（OpenAI 新版）与 `usage.prompt_cache_hit_tokens`（DeepSeek 风格），都缺 = `None`（明细卡隐藏命中率行）。
3. **回合落库**：`TurnEnded` 事件扩展 `#[serde(default)] usage: Option<ModelUsage>`，取**本回合最后一次请求**的 usage（其 input 即当时的上下文规模，最能代表占用）；`TurnOutcome`（`agent.rs:188`）同步加字段带出。`#[serde(default)]` 保证旧日志回放兼容。
4. **估算器（分类分桶）**：core 新模块 `token.rs`：`est_tokens(s: &str) -> u64` = CJK 字符 ×0.6 + 其它字符 ÷4（向上取整）；`est_context(ctx: &ModelContext) -> ContextBreakdown`——把投影结果按明细卡的分类**分桶估算**：`messages`（用户+助手文本与工具调用参数）/ `tool_results`（工具输出）/ `tool_defs`（工具清单 JSON）/ `system`（系统提示词）/ `other`（余量），`total` 为合计。用途：① 无 usage 网关的显示退化；② 自动压缩触发判定；③ 明细卡「分类占比」直接取桶值算百分比。
5. **溢出识别**：`cmx-agent-model` 新增 `pub fn is_context_overflow(msg: &str) -> bool`（匹配 `context_length_exceeded` / `maximum context length` / `context window` / `too many tokens` 等中英文特征）；`error_friendly.rs` 补一类「上下文超限」人话话术。

### 4.2 压缩内核（core + app，agent 循环不动）

#### 4.2.1 新事件（`event.rs`，serde tagged enum——字段必须显式声明，防静默丢）

```rust
/// 上下文压缩完成：`up_to_seq`（含）之前的模型可见历史已被 `summary` 摘要替代。
Compacted {
    /// 摘要覆盖到的事件 seq（含）；投影仅保留其后的事件 + 头部注入摘要。
    up_to_seq: u64,
    /// 摘要正文（Markdown，结构化模板）。
    summary: String,
    /// auto_threshold | manual | overflow。
    reason: CompactionReason,
},
/// 旧工具输出清理登记：列出的 call_id 其结果在投影时替换为占位说明（append-only，不可改写原事件）。
ToolOutputsPruned {
    /// 本批被清理的 tool call id（多次事件取并集）。
    call_ids: Vec<String>,
},
```

#### 4.2.2 投影改造（`session.rs model_context`）

1. 扫描日志找**最后一条** `Compacted`：其 `up_to_seq` 之前的三类可见事件不再投影；`ToolOutputsPruned` 全部事件取并集，命中的 `ToolResult` 在投影时把 output 替换为占位 JSON（`{"pruned":true,"note":"较早的工具输出已清理（原约 N 字符）"}`，N 投影时现算）。
2. 有摘要时在消息头部（system 之后）注入一条 User 消息（codex 同款：其 `CompactionSummary` 也以 User 消息注入、固定 `SUMMARY_PREFIX` 前缀标识；opencode 用 assistant 消息承载摘要——两形皆可，取 codex 形态因与投影白名单的类型系一致）：

   ```
   [会话前段已被压缩，以下是截至当时的结构化摘要；其后为近期原文。]
   <compacted-summary>
   …summary…
   </compacted-summary>
   ```

3. 压缩点之后的原文照常投影——**「摘要 + 近期原文保留」由压缩点的位置天然实现**，不需要按预算反切尾部（比 opencode 的 tail 选择简单一档）。
4. 配对自愈（未闭合 tool_call 补合成结果）逻辑保持不变：只在回合边界压缩 ⇒ 摘要段内不会有未闭合调用。

#### 4.2.3 阈值与判定（app 层，`app.rs`）

```
DEFAULT_CONTEXT_WINDOW = 1_000_000        // 已拍板
COMPACTION_BUFFER      = 20_000           // 对齐 opencode 新代（core/compaction.ts:239 max(output, buffer)）
usable = window − max(max_output_tokens 配置值缺省 8_192, COMPACTION_BUFFER)
auto 触发 = 估算上下文 ≥ usable × 0.85
```

- 触发线参考系（深审补充）：codex = 窗口 90% 触发 / 95% 硬顶（`openai_models.rs:385,511`）；opencode 旧代 reserved=min(20k, maxOutput)、新代 max(output, 20k)。本方案取「usable×85%」偏保守（误压代价 = 摘要丢细节，宁晚勿早属方案既定取向），三家公式同族、数字在合理带内。

- 判定点：`app.send()` 派发用户消息**之前**（回合边界）；先做 prune、重估，仍超线再做 compact。
- 判定输入 = 估算器（`§4.1.4`）；有真实 usage 时取「上回合 usage.input + 本条新消息估算」校准。展示优先真实 usage，判定统一走估算，单一代码路径。**真实性口径（用户问询 2026-09-18）**：容量分子 = 服务端回传的真实 prompt_tokens（MLamp 已实测）；分母 = **配置值**（`context_window` 未配按 1M 默认——若与模型真窗口不符，百分比会失真，建议用户为常用模型填真值）；分类占比五项 = 纯估算（模型 API 不提供构成明细）。

#### 4.2.4 摘要生成

1. 序列化被压缩段（opencode 同款，深审定稿）：`[用户]: …` / `[助手]: …` / `[推理]: …`（**reasoning 参与序列化**，opencode 两代一致，利于摘要质量；仅投影层不回灌的约定不变）/ `[助手 工具调用]: name(args JSON)` / `[工具结果]: 输出截 2000 字符` / `[工具错误]: …`；图片等附件降级为 `[附件 image/png: 文件名]` 占位（为在途的图片粘贴方案预留格式）。
2. 提示词 = 中文结构化模板（目标/重要细节/工作状态·已完成·进行中·受阻/下一步/相关文件）+ 规则（空节写「（无）」；保留精确路径、符号、命令、错误串、URL；**不提压缩过程本身**）。有前次摘要时带 `<prior-summary>` 合并指令，完整要点（opencode `SUMMARY_UPDATE_INSTRUCTIONS` 对齐）：旧摘要信息单向不丢（对话未提及的目标/约束/决策/并行线一律延续，仅删已完成且不再需要项）；冲突以新对话为准并纠正；新进展补入；已完成项从「进行中」迁入「已完成」；受阻解除后更新但保留仍需细节；目标与下一步随现状刷新。
3. 请求：复用 `model.complete()`，合成 `ModelContext { system: None, messages: [User{prompt}], tools: [] }`，请求体附 `max_tokens = 4_096`。**二轮发现（缝缺口）**：`build_request_body` 与 `ModelProviderConfig` 目前**都没有 max_tokens 字段**（`test_connect` 的 `max_tokens:1` 是独立构造体不走该函数）——需给 `build_request_body` 加可选 `max_tokens` 参数（正常回合不传、维持现状，仅摘要请求传 4096），落点清单已同步。
4. **摘要请求自溢出防护**（深审补，codex `compact.rs:295` 同款思路）：先估算序列化文本；若 `估算值 > window − 4_096 − 余量`，**从最旧的序列化条目逐条丢弃**直至放得下（极端长会话的兜底；丢弃行为记入 `Compacted` 事件附注，审计可见）。
5. **失败降级**：摘要请求失败 → 追加 `Note`（审计）+ 不压缩，下回合重试；绝不因压缩失败丢历史。

#### 4.2.5 prune（工具输出清理）

- 清理对象：投影范围内（压缩点之后）的已完成 `ToolResult`，从尾往前保护最近 `40_000` tokens，更旧的进清理名单；可清理量不足 `20_000` 不动手；`skill` 类工具（技能加载，若姊妹方案二期引入 skill 工具）豁免。
- 三条结构守卫（opencode `compaction.ts:288-305` 对齐）：① **跳过最近一个回合**（本回合刚产生的工具结果永不清理）；② 只考虑最后一条 `Compacted` 之后的事件（等价「遇摘要即停」，旧压缩段本就不在投影内）；③ 已在 `ToolOutputsPruned` 并集里的不再重复估算/登记。
- 落库 = `ToolOutputsPruned` 事件（`§4.2.1`），不动原始事件。
- 时序说明：opencode 是回合结束后异步 fork 清理；本方案在**发送前同步**「先 prune、重估、仍超线再 compact」（确定性更强，边界设计配套），差异已知悉、属有意选择。

#### 4.2.6 溢出救援（兜底主路径，1M 默认下尤其重要）

- 位置：`app.rs` `execute_turn_locked` 内包裹对 `agent.run_turn_*` 的调用（二轮核实：`TurnStarted`/`UserMessage` 由 core `run_turn` 追加；出错路径已有「错误一致性」块补 `Note`+`TurnEnded(Error)` 落库广播，救援挂在其后顺理成章）。回合返回 `Err(AgentError::Model(msg))` 且 `is_context_overflow(msg)` 且本次输入尚未重试过 → 执行压缩（`reason=Overflow`）→ **原话重试一次**；再失败按现状报错收场。
- **压缩点语义（二轮定细节，防 UserMessage 重复）**：救援压缩的 `up_to_seq` 覆盖到失败回合的 `UserMessage` 为止（含失败回合全部已落事件）——重试走**正常 `run_turn`**（新 `TurnStarted`+`UserMessage`），原话被摘要吸收、投影里不重复出现。与 opencode 溢出路径同构（其 replay 把被打断的用户消息切出头段后重放为新消息，`compaction.ts:340-356`）。
- **无可压缩历史时跳过**：首回合即超窗（单条消息/附件本身超窗）→ 压缩头为空，救援无意义，直接按现状报错（错误一致性块已落失败行）。
- 重试是新回合（流式 observer 可能已画了部分增量）——与 ZCode 同款行为，时间线上表现为前回合失败行 + 压缩卡 + 新回合成功，可接受。

## 6. 验收清单（用户自测口径：看哪里、点什么）

> 构建 + `cargo check`/clippy 零告警 + `sync-ui.sh` 为前置；按既定分工 E2E 由用户真机验证。

1. **用量圆环与明细卡**：聊几轮 → 输入框工具行模型按钮左侧出现圆环，随对话增长逐渐填充；把它 `context_window` 配成小值（如 8000）再聊 → 圆环变金/变红；点圆环 → 明细卡显示容量（万单位）、分段进度条、分类占比（消息/工具结果/工具定义/系统提示词/其他）；网关不回传 cached_tokens 时命中率整行不出现。
2. **自动压缩**：小窗口模型（如 context_window=8000、max_output=512）下连聊数轮 → 出现「正在压缩上下文…」→ 时间线出现 🗜 边界卡 → 点开摘要含目标/工作状态/相关文件各节；**旧消息仍在时间线上可回看**。
3. **摘要生效**：压缩后问「我们刚才在干什么」→ 模型能按摘要口径回答（目标/文件路径说得出）。
4. **手动**：输入 `/compact 保留 XXX` → 卡片出现且摘要明显保留 XXX；
5. **prune**：长会话展开较早回合 → 老工具输出行带「🧹 已清理 · 原约 N 字符」，最近回合不受影响。
6. **溢出救援**：把 context_window 配得比网关真窗口大 → 聊到网关报超限 → 回合内出现「上下文超出模型窗口」→ 自动压缩 → 原话自动重试 → 正常收尾。
7. **兼容**：升级前的旧会话打开 → 回放正常、无压缩卡、明细卡容量退化为前端粗估或显示「—」。
8. **双壳**：Web 壳与桌面壳（重建后）形态一致；飞书里 `/compact` 可用、压缩事件不刷屏。
9. **降级**：断网/网关 500 时输入 `/compact` → 出现「压缩失败，已保留现场」类 note，会话照常可用。

## 7. 风险与注意

1. **serde tagged enum 老坑**：`EventKind` / `AppRequest` 新变体字段漏声明会**静默丢**；`TurnEnded` 新字段必须 `#[serde(default)]`；旧 `log.jsonl` 回放必须过测试。
2. **`stream_options` 兼容性**：个别网关不认该参数会 4xx——剥参重试路径必须有。**MLamp 网关已实测（2026-09-18 真实探测）**：`include_usage` 生效、`prompt_tokens` 真实回传；usage 帧两种形态并存（独立 usage-only 帧 / 与 finish_reason 同帧），`StreamAcc`「任意帧见 usage 即收」已覆盖；`prompt_tokens_details.cached_tokens` 字段存在但探测值 0（能否命中取决于网关 prompt cache 实现，命中率行按「有字段才显示」处理，0% 也是真实值）。另实测陷阱：响应里另有 `input_tokens` 字段但恒 0，取数必须用 `prompt_tokens`。
3. **估算误差**：CJK×0.6+其余÷4 属 ±20% 级粗估，触发线留了 15% 余量吸收；判定宁晚勿早（误压代价 = 摘要丢细节）。参考：opencode/codex 估算器都是纯 `len÷4`，对中文**低估**（一个汉字实际约 0.6 token，÷4 只算 0.25）——本方案 CJK 系数是为中文会话纠偏的改进，不是多余复杂度。
4. **prompt cache 尖峰**：压缩改变消息前缀，压缩后第一发全价——成本上有一次小尖峰，知晓即可。
5. **摘要丢信息**：靠模板硬规则兜底；合并指令保证旧摘要信息单向不丢（冲突以新对话为准）。
6. **回执折尾 × 压缩**：deferred 注入在回合内、压缩在回合边界，时序天然不冲突，但需一条组合测试（压缩后紧跟后台回执注入）。
7. **UI 回放坑**：`renderHistory` 映射不落最终 DOM 的前车之鉴——边界卡必须在回放与实时两条路径都验证。
8. **1M 默认 + 小真窗口模型**：自动压缩不触线属预期行为，溢出救援兜底（§0 已注明）。
9. **回合内不触发压缩（对参考实现的差异声明，深审补充）**：opencode（每步查真实 usage，`prompt.ts:1164`）与 codex（回合内 `token_limit_reached` 滚动压缩，`turn.rs:542-600`）都在**回合中途**即可压缩并续跑；本方案只在回合边界判定，「循环不动」是投影层设计的核心约束。连续几十步工具调用的超长回合中途触线时由溢出救援接住（表现为失败行+压缩卡+重试回合）；若实测长回合频繁走救援，二期再把判定挂到步边界（需要 agent 循环加回调，打破本约束，故一期不为）。
