# MDM 分发订阅多字典支持调研与完善方案

> 日期：2026-09-02 · 模块：cmx-mdm（分发订阅）/ portal native-page `portal.mdm.subscription-manager`
> 性质：调研 + 方案（**未批准实施**）
> 触发问题：订阅管理页"一次只能设置一条数据"（一条订阅只能绑一个字典/主数据类型）是否合理，如何完善。

---

## 一、现状还原（代码级）

### 1.1 数据模型

`cmx-container/docs/sql/v2/biz/init_ddl.sql` 中 `md_subscription`：

- `dict_code VARCHAR(64) NOT NULL` —— **单值列**，一条订阅只绑一个字典；
- 唯一索引 `uk_md_subscription (target_sys, dict_code, channel)` —— 同系统同字典同通道唯一；
- 通道凭证（webhook 的 url/secret/timeout）放在本行 `channel_config`。

### 1.2 扇出与匹配

`cmx-mdm-store-pg/src/dispatch_store.rs` 事件→订阅扇出为精确等值 JOIN：

```sql
FROM md_event_log e JOIN md_subscription s ON s.dict_code = e.dict_code
```

### 1.3 前端交互

`cmx-container/assets/mdm/web/ui-native/portal/mdm/subscription-manager.js` 编辑弹框四分区：
① 基本信息（字典 `cmx-combo-box` **单选**，数据源=激活映射 target_dict 去重）
② 事件与过滤（event_types created/updated/merged **已支持多选**，行级 filter 条件）
③ 通道配置（webhook：URL/秘钥/超时）
④ 投递参数与 field_map（include/rename/mask——**字段映射天然按字典语义**）。

现状库内 3 条订阅（id 5386457…）：target=crm-test / erp-test / wms-test，dict 全部=supplier，channel 全部=webhook。

### 1.4 后果（痛点）

目标系统要接 N 种主数据（如 ERP 接 供应商+物料+客户+科目）时：

1. **配置重复**：同一个 webhook URL/秘钥/超时/重试要在 N 条订阅里重复配 N 次；
2. **密钥轮换 N 处**：改一次签名秘钥要逐条编辑，易漏改造成半数订阅鉴权失败；
3. **运维碎片化**：列表 N 行平铺，"ERP 接了哪些主数据"要看 N 行才能拼出全貌；启停/测试逐条操作，无法"暂停 ERP 全部投递"；
4. **录入低效**：一次弹框只能选一个字典，建"ERP 全量接入"要连开 N 次弹框重复填凭证。

## 二、主流 MDM / 事件分发系统调研

| 系统 | 订阅/分发模型 | 与本问题的对照 |
|---|---|---|
| **SAP MDG（DRF 数据复制框架）** | 按**目标系统（逻辑系统）建复制模型**，**一个模型内可挂多个业务对象类型**（BP/物料/客户/供应商…），每个对象类型各自的出站实现与过滤 | 目标系统级聚合 + 对象类型级细配，两层分离 |
| **Salesforce Change Data Capture** | 自定义通道（Custom Channel）**聚合多个实体**，一个订阅收多实体事件；或 `/data/ChangeEvents` 标准通道收全部已启用实体 | 一个订阅多数据类型是官方推荐形态 |
| **Stripe Webhook** | **端点（endpoint）与事件选择分离**：端点配一次 URL+签名秘钥，`enabled_events` 数组多选或 `['*']` 收全部 | 凭证与订阅内容解耦，最贴近本痛点 |
| **Informatica MDM** | Topic 发布订阅（pub/sub）；按 Base Object 配 message trigger，目标落 Kafka/S3/文件 | 触发按对象类型、Topic 承载分发 |
| **Reltio** | 外部队列配置按实体类型过滤，多实体→多队列配置 | 与 CMX 现状同粒度（细粒度本身有先例） |
| **Stibo STEP** | Data Delivery 订阅者可按产品类型过滤后分发 | 同为"订阅者 × 数据类型 × 过滤"三元组 |

### 调研结论

1. **按数据类型细粒度配置过滤/字段映射是主流共识**——`field_map`/`filter` 天然是字典级的，CMX 现有"事件×订阅"投递实例、补发、监控按订阅隔离的骨架是健康的，与 Reltio 同粒度，**不应推翻**。
2. **主流系统都把"目标系统端点/凭证/通道"收敛为一份**：SAP 按逻辑系统建模型、Stripe 端点与事件解耦、Salesforce 通道聚合实体。CMX 把通道凭证与字典选择绑在同一行，是**配置承载层的错位**，不是扇出粒度错误。
3. 多选录入形态有直接先例：Stripe `enabled_events` 多选、Salesforce 通道勾选实体集合、SAP 模型内挂多对象类型。

**判定：现状"半合理"——扇出粒度合理，配置模型与录入体验不合理。**

## 三、完善方案（三选一，推荐 C）

### 方案 A：不动库，前端向导批量建（最小改动）

新建订阅改两步向导：第一步选目标系统+通道+凭证（一次），第二步**多选字典**并逐字典配事件/过滤/字段映射，保存时前端循环调既有 upsert 批量建 N 条订阅；列表按 `target_sys` 分组展示。

- ✅ 零迁移、零后端改动，一天可上线；
- ❌ 库里仍是 N 行、秘钥仍 N 份（轮换需批量编辑）；分组只是前端视觉。
- 适合：作为 C 落地前的过渡，或确认无密钥轮换诉求时。

### 方案 B：订阅本身含多字典（改表结构）

`dict_code` → 子表 `md_subscription_item(subscription_id, dict_code, filter, field_map, event_types)`；扇出 JOIN 改子表；`md_dispatch_log` 语义随之调整。

- ✅ 配置最彻底合并；
- ❌ 唯一索引、统计列（近24h成功率/积压）、补发、分发监控、rest_pull 游标全链路适配，改动面最大；
- ❌ 单字典订阅的简单场景被复杂化（监控/重试粒度被迫上浮到订阅级）。
- 不推荐：收益与风险比最差。

### 方案 C（推荐）：拆「目标端点」+「订阅」两实体（Stripe/SAP 式）

新增 `md_target_endpoint`：`id, target_sys, channel, channel_config(url/secret/timeout), retry_max, batch_size, name, active`——**目标系统级配置一份**。
`md_subscription` 瘦身为：`endpoint_id, dict_code, event_types, filter, field_map, active, name`——字典级细配。

- 扇出 JOIN 仅多一层端点关联（`md_subscription s JOIN md_target_endpoint t ON s.endpoint_id=t.id AND t.active`），投递实例 `md_dispatch_log` 结构不动；
- **密钥轮换只改端点一处**；启停支持端点级（级联停用其下订阅）与订阅级两档；
- `rest_pull` 天然契合：consumerId 即端点，游标本就按 `(consumer_id, dict_code)` 隔离，**零改动**；
- 迁移平滑：存量按 `(target_sys, channel)` 聚合生成端点行，订阅挂 `endpoint_id`，可回滚；
- UI：编辑弹框拆两处——「端点管理」（目标系统+通道+凭证）+「新建订阅」（选端点 → **多选字典** → 逐字典过滤/映射）；列表按端点分组，组头提供 批量测试/启停/补发。

实施量级：DDL 迁移 1 个 + store 层 endpoint CRUD + 扇出 SQL 两处 + handler 3~4 个 + 前端页面改造（向导与分组），预计 2~3 天。

### 不依赖方案的独立改进（可先行）

1. 编辑弹框字典改多选（`cmx-combo-box` 多选或复选组）——与 `event_types` 多选范式对齐；
2. 列表按目标系统分组展示 + 组级批量启停/测试；
3. 补发弹框的"订阅 id"改为下拉选择（现在要手填数字 id）。

## 四、附带发现（疑似 bug，待单独确认）

浏览器实测（直开深链 `http://localhost:5173/view/mdm-subscription-manager`）：页面渲染完整、数据可读，但「新建订阅」按钮**三种方式点击（元素 .click() / 完整鼠标事件序列 / 真实坐标点击）均无响应**，插桩确认 `openEditDialog` 的 `createElement('cmx-floating-dialog')` 未被调用——即 `bind()` 的事件监听未挂上（疑似与已知"深链首屏二次重绘"同源：`whenRendered` 在首次渲染节点上绑监听后，宿主重绘 DOM 致监听丢失）。经侧栏菜单导航进入的常规路径不受影响（库内既有 3 条订阅即正常创建）。建议后续在 `cmx-native-pages-host` 重绘时保证模块 `content()` 重跑，或 `bind` 改事件委托到宿主根。
