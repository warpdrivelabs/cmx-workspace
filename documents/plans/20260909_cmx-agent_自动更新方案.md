## 2. 架构与数据流

```
发布机（release 脚本）                          更新源 = 门户（D2 + D7，终版）
  │ ①各平台构建机出产物                          ├── /agent-updates/latest.json
  │   Win:  cargo tauri build（NSIS + 自动签名）     │     ← updates handler 从版本库渲染
  │   mac:  release-build-and-sign.sh               └── /files/...（存储服务免鉴权直出）
  │         （stapled .app 重打 tar.gz + minisign）        安装包 + .sig；URL 在 latest.json 下发
  │ ②门户维护页面：上传产物（/api/storage/upload）
  │   → 登记版本 → 发布（灰度/force/withdrawn 在版本库）
  ▼
┌──────────────── TrueMate 壳（三平台同一前端 UI）────────────────┐
│ 前端 ui/index.html（真源单份，已接线）                          │
│   「更新 x.y.z」按钮 / cmx 菜单「检查更新」                      │
│        │ invoke                                                 │
│        ▼                                                        │
│ update_common.rs（壳内胶水，已入库）                             │
│   check_update：updater_builder()                               │
│     .endpoints(portal_base() + "/agent-updates/latest.json")   │ ← D5 运行时注入
│     .header("Authorization", token)        ← P1 起，拿得到就带   │
│     .timeout(10s，仅检查；下载裕量见 K1) → check()               │
│   download_and_install：插件 download（进度 emit）→ 内置验签     │
│     → install（三平台差异见 §1 表）→ restart                     │
└─────────────────────────────────────────────────────────────────┘
```

**用户时序**（已实现，此处为验收基准）：

1. 启动 5s 后静默检查：无感；有新版 → 标题栏出现「更新 0.2.0」按钮（D3 不弹窗）。
2. cmx 菜单「检查更新」：弹「发现新版本 0.2.0，点标题栏按钮安装」或「已是最新」。
3. 点「更新」→ 按钮内联下载百分比 → 自动验签（失败只 toast，可重试，主功能不受影响）→ 安装 → 自动重启进新版。
4. Linux 额外一步：polkit 管理员密码框；取消 = 更新中止，应用保持运行并 toast。

## 3. 技术事实底座（已验证，照此实施）

> 本节每一条都核对过 `tauri-plugin-updater 2.11.0` / `tauri-bundler` / `tauri-utils 2.9.3` 源码（updater-v2.11.0 tag）。这是审查发现的「原稿与现实的偏差」清单的正源。

### 3.1 三平台安装路径（插件源码级）

- **Windows**（`install_inner` → Nsis 分支）：`ShellExecuteW` 运行新安装器，参数 = install_mode 参数（默认 **passive → `/P`**，不是原稿说的全静默 `/S`；conf `plugins.updater.windows.installMode` 可改 `quiet`→`/S`）+ `/UPDATE` + `/R`（装完重启）+ `/ARGS <原启动参数>`，随后插件 **`std::process::exit(0)`**——Win 上 `download_and_install` 永不返回。
- **macOS**：解包 .app.tar.gz → 备份/替换 .app（权限不足时 AppleScript 提权）→ `touch` → 返回。插件**不重启**，壳内显式 `app.restart()`（已实现）。
- **Linux**（`install_inner` → 按 `installer_for_bundle_type(bundle_type())` 分派）：
  - `bundle_type()` 是**编译期烙定**的：`tauri build` 打包时按 target 对二进制做 in-place 补丁（`__TAURI_BUNDLE_TYPE_VAR_DEB` 等；多 target 时逐个「备份未签名副本→补丁→打包→还原」）。**deb 产物里的二进制必然带 DEB 标记** → deb 安装的机器运行时 `bundle_type()==Deb` → 自动走 `install_deb`。
  - `install_deb`：`infer::archive::is_deb` 校验（非 deb 直接拒装）→ 写临时目录 → `pkexec dpkg -i`（polkit 图形密码框）→ 失败则 zenity/kdialog 取密码 `sudo -S dpkg -i` → 再失败终端 `sudo dpkg -i`。
  - **应用全程不退出**（安装是同步 `Command::status()`），失败同步返回 → 壳内 toast，无原稿 L1「退出后报错看不见」问题。
- 依赖缺失时 `dpkg -i` 失败（它不做网络依赖解析）——内网既有装机（0.1.0 装过 libwebkit2gtk/libgtk）不受影响；全新机器走门户手动安装，不归更新链路管（与原稿 L3 一致，保留）。

### 3.2 latest.json 平台键匹配顺序

插件先找 `{os}-{arch}-{installer}`，找不到再退 `{os}-{arch}`。**终版统一用带后缀键**（语义精确，杜绝 AppImage 之类异常安装形态误匹配）：`windows-x86_64-nsis` / `darwin-aarch64-app` / `linux-x86_64-deb`。

### 3.3 endpoint 占位符

`{{target}}`（如 `linux-x86_64`）、`{{arch}}`、`{{current_version}}`、`{{bundle_type}}`（如 `deb`），出现在 URL 任意位置（含 query）都会替换。D5 之后 endpoint 由代码拼，这四个占位符只在 P1 接口按需使用（服务端拿 `current_version` 可直接回答 204）。

### 3.4 「无更新」的正规表达

插件对 **HTTP 204 No Content** 直接返回 `None`（= 无更新）。P1 灰度未命中/已撤回版本就走 204，客户端零特殊逻辑。

### 3.5 传输安全定案：`dangerousInsecureTransportProtocol` 长期保留

团队门户是内网 http（`http://192.168.137.111:8080`，构建期烧录），该标志**必须保留**，不是待回收的临时项。安全性论证：更新包的真实性/完整性边界是 **minisign 签名**（端到端，与传输无关，篡改必被拒装）；明文 http 仅暴露包内容，而安装包本来就是门户公开分发的。除非门户上 TLS，否则「生产切 https 时回收」（原稿措辞）是空头承诺——终版直接写明这是**接受的权衡**。

### 3.6 .sig 文件与 latest.json 的 signature 字段

`cargo tauri signer sign` 写盘的 .sig 文件**本身就是单行 base64**（CLI 对 minisign 签名文本做了 `base64(...)` 再落盘）。latest.json 的 `signature` 字段 = **.sig 文件内容原样粘贴**（插件验签时先 base64 解码还原 minisign 文本再校验）。发布脚本生成 latest.json 时直接读文件内容填入，不要画蛇添足再编码。

### 3.7 UpdaterBuilder 能力清单（原稿 §7.4 spike 就此取消）

`UpdaterExt::updater_builder()` 暴露：`.endpoints()`（运行时覆盖 endpoint，D5 的落点）、`.header()`/`.headers()`（**逐请求动态 header——P1 带门户 token 的正解**，下载请求同样携带）、`.pubkey()`、`.target()`、`.version_comparator()`、`.timeout()`、`.proxy()/no_proxy()`、`.installer_arg()`（Win）、`.on_before_exit()`（Win）。

原稿的两个判断各对一半：`Update` 确实**不能**外部手动构造（`extract_path`/`context` 私有，「插件不吃外部 manifest」猜对了）；但「插件无法带动态 header」是错的——有 builder API，**P1 不需要自研 HTTP 检查**。

## 4. 客户端剩余改动

骨架已入库，剩余是三个小改动 + 一个 P1 预留，全部在 `crates/cmx-agent-shell/src-tauri/`：

| # | 文件 | 改动 | 阶段 |
|---|---|---|---|

| K2 | `tauri.conf.json` | 删 `plugins.updater.endpoints`（D5：conf 不再持有 endpoint）；保留 `pubkey` 与 `dangerousInsecureTransportProtocol: true`（builder 的 endpoints 校验读的就是 conf 里这个标志） | P0 |
| K3 | `tauri.linux.conf.json` | `bundle.targets` 从 `["deb", "appimage"]` 改为 `["deb"]`（D1：不引 AppImage，少产无用 updater 产物，也杜绝误走 appimage 更新分支） | P0 |
| K4 | `src/update_common.rs` | `check_update` 增加可选 token 注入：`.header("Authorization", format!("Bearer {token}"))`（token 从壳内登录态取；拿不到就不带——服务端把无 token 视为非灰度用户全量放行，见 §7.3）。force 从 `u.raw_json["force"]` 取（注意字段名是 `raw_json`，前端 `force:true` 时弹不可关闭模态） | P1 |

## 7. 更新源与门户接口

### 7.1 路径定案（客户端永不变）

```
http://<portal-base>/agent-updates/latest.json ← 检查：updates handler 从版本库渲染（灰度/force/204 内建）
http://<安装包 URL>                             ← 下载：存储服务的稳定直出 URL（latest.json 里下发）
```

- `<portal-base>` 客户端侧来自构建期烧录（D5）。**不引入任何新域名、新组件。**
- 安装包 URL 不是固定形态，而是存储服务上传后返回的 `file_info.url`（local 实例形如 `http://<portal>/files/uploads/agent-updates/.../<uuid>.exe`）。UUID 路径不可预测没关系——它由 latest.json 下发，客户端不猜；产物不可变 → URL 终身稳定；撤回版本只改版本状态，不删文件。
- latest.json 的 GET 挂根级、免鉴权：`build_router` 在 middleware layer **之后** merge 的路由不经过 `mw_auth`（`/files/**`、`/_mon`、dataauth console 均循此先例）；管理接口走 `/api` 带鉴权 + 权限。
- **「为什么还要 latest.json，不是直接入库吗」**：数据本来就直接入库——版本/灰度/状态全在平台库，latest.json **不是文件**，是 `GET /agent-updates/latest.json` 的**响应体**（handler 从库现渲，名字带 .json 只是沿用插件生态叫法）。它存在的唯一理由：检查-下载-验签-安装整条链是 tauri-plugin-updater 内建的，`check()` 的线格式契约就是这个 Tauri 规范 JSON 或 204——插件靠它做 semver 比较、平台键匹配、minisign 验签、按 url 下载；且 `Update` 结构体**不可外部构造**（§3.7），"绕过它直接查库"就只剩弃用插件、自研整条三平台安装链（原稿被推翻的路线）。handler 就是库与协议之间的翻译层。

### 7.2 安装包承载：门户文件存储服务（D7）

上传走既有存储域 HTTP 层（`cmx-infra/cmx-storage` + `cmx-apis/cmx-storage-api`，ModuleRoutes 已合并进 `/api`），**零新增存储代码**：

- **上传**：页面 `POST /api/storage/upload`（multipart：`file` + `object_type=agent-updates` + `object_id=<版本号>`），返回 `file_info`（含稳定 URL，原样落版本库）。**坑（实施实核）**：storage 的 `platform` 参数是**存储平台名**（local / minio，缺省走 toml `default_platform`），**不是更新器平台键**——传 `windows-x86_64-nsis` 之类会报「存储平台不存在」，页面不传该字段走默认。URL 组成已实核（`config.rs`）：local = `domain + path` 裸拼（`/files/**` 直出）；S3 = `domain + bucket_name + path`，同样是**裸公开 URL**——带过期的预签名只存在于独立 presign 接口，**不进 `file_info.url`**，latest.json 里的下载地址永不过期。`.sig` 同样上传，其**文本内容**登记进版本库（latest.json 的 signature 字段取库值）。`/api` 请求体上限 100MB，覆盖三平台包体；上传在服务端是全量读进内存（低频管理操作可接受，将来超限换分片接口 `multipart/init|part|complete`）。
- **免鉴权直出**：local 实例 `enable_storage + enable_access + path_patterns="/files/**"`（portal toml 已配）把存储根以 ServeDir 挂在 `/files/**`——免鉴权、裸文件直出，正是更新器要的形态。MinIO 实例（`storage_type="s3"`）则用对象存储直链，需给 bucket 的 `agent-updates/` 前缀配**公开读**（运维前置项）。
- **latest.json 为什么不放存储**：存储路径按 `{base_path}/{object_type}/{yyyyMM}/{uuid}.{ext}` 生成（`path_gen.rs`），含 UUID、**不可覆盖写**——latest.json 需要「固定 URL + 内容随发布变」，只能由 updates handler 从版本库实时渲染。这是 D7 里它例外的唯一原因。
- **部署注意（验收项）**：local 实例 toml 的 `domain` 当前是 dev 值 `http://localhost:8080/files/`——`file_info.url` 由它拼出，**生产必须配真实门户地址**，否则 latest.json 里嵌 localhost、客户端装不上。MinIO 模式要保证其地址对**用户网段**可达（用户机器直连下载，不经门户反代）。

联调期间开发者本机可用 `python3 -m http.server 8901 --directory ./updates` 顶替整个更新源（endpoint 由 K1 运行时拼，本地开发改 `CMX_AGENT_PORTAL_DEFAULT` 即可指到本地，**conf 不动**）。

### 7.3 updates 域模块接口（P0 起步：登记/渲染/撤回；P1 加灰度/上报/统计）

**客户端面**（落点已拍板 = cmx-container `crates/libs/cmx-agent/`，照既有 IM 绑定的双 crate 分工：**服务层** `cmx-agent/src/updates/`——entity/store/service 照 `binding/` 模式，承载版本表 + 灰度 + 上报的 SQL 与判定逻辑（三表 DDL 归**平台库**，按 sql-guide 规范落 `docs/sql/v2/platform/`：init_ddl + migrations 增量）；**HTTP 层** `cmx-agent-api/src/handlers/updates.rs`——管理面 ModuleRoutes + 一个边缘 routes 函数。**双挂载通道，别混**：管理面走 `ModuleRoutes`（合并进 `/api`，过 `mw_auth` 鉴权 + 权限）；`latest.json` 与 `report` 走**免鉴权边缘通道**——边缘 routes 函数在共享库 `build_router` 里于 middleware layer 之后 merge（dataauth `console_routes` 同区域同手法，见 §7.1）。**边缘 merge 必须带配置门控（终审实雷，附四 #1）**：`build_router` 为全部微服务共用，无条件 merge 会把这两个端点同时挂上其余七个引擎——照 console 先例**含其门控语义**（router.rs 实核：console 是 `dataauth_upstream()` 配置了才挂；`/_mon` 无条件属全局设施，不可类比），如 `[assets]` 段加 `agent_updates` 开关（命名实施时按 config-sync 定）、默认不挂、仅门户 toml 启用；此属共享库加法式小改，改后 portal + 一个引擎各跑 `cargo check`（下游验证纪律）。两个坑：把 latest.json 塞进 ModuleRoutes 会被鉴权拦住更新器；边缘通道响应是**插件契约原样**（Tauri JSON / 204），**不走 ApiResp 信封**——与本域管理面「HTTP 200 + `{code,msg}`」的信封约定不同（cmx-agent-api lib 头注释有载）。遵守工作区接口红线：新接口仅固定资源段 + GET/POST，无 PUT/PATCH/DELETE、无可变路径段）：

| 接口 | 说明 |
|---|---|
| `GET /agent-updates/latest.json`（根级，免鉴权） | Query：`current_version`（可选，占位符语义）。有更新返回 Tauri 规范 JSON；未命中灰度/版本已撤回返回 **204**（插件原生语义 = 无更新）。库内无 active 版本同样回 204（绝不 404/500）；active 版本不高于客户端版本时插件按 semver 判「无更新」，天然不降级。身份：读 `Authorization: Bearer`（客户端 K4 拿得到就带）；无 token = 全量放行。灰度命中判定：用户 > 部门 > 全局百分比；force 标记跟版本走 |
| `POST /agent-updates/report`（根级，免鉴权，与 latest 同通道） | 更新结果上报（审计）。Body：`from_version/to_version/target/arch/result(success\|failed_verify\|failed_install\|cancelled)`。匿名可报，带 token 落人；表按上限/周期清理，防匿名刷写。可推迟（壳端失败本就 toast，上报是锦上添花） |

| `POST /api/agent-updates/gray-config`（P1） | 灰度规则（用户/部门/百分比）、force 开关、**回滚 = 标记 `withdrawn`**（`GET latest` 对 withdrawn 版本回 204，未升级用户停在旧版不再提示问题版本；已升级用户不被强制回退）。~~原稿 `PUT /agent/updates/gray`~~ 违反接口红线，已改 POST |

### 7.4 latest.json 完整样例

```jsonc
{
  "version": "0.2.0",
  "pub_date": "2026-09-15T08:00:00Z",
  "notes": "修复 xxx；新增 yyy",
  "platforms": {
    "windows-x86_64-nsis": { "signature": "<.sig 文件内容原样>", "url": "<存储 file_info.url 原样，如 http://<portal>/files/.../<uuid>.exe>" },
    "darwin-aarch64-app":  { "signature": "<...>", "url": "<.../<uuid>.app.tar.gz>" },
    "linux-x86_64-deb":    { "signature": "<...>", "url": "<.../<uuid>.deb>" }
  }
}
```

- 平台键用带 `-installer` 后缀形式（§3.2）。有 Intel mac 再加 `darwin-x86_64-app`。
- `signature` = 各自 `.sig` 文件内容**原样**（§3.6）。mac 的 .sig 来自发布脚本重打包后的 tar.gz（不是 tauri build 自产那份）；Win/Linux 的 .sig 是 `tauri build` 自动签名产物；Linux 手动补签场景用 `signer sign -f`（命令速查）。
- 此 JSON 由 `GET latest.json` handler 按版本库渲染（D7 起 P0 即如此，无静态文件阶段），格式不变；url/signature 取登记值原样填入。

### 7.5 集群约束（红线叠加）

- 安装包走存储服务后节点一致性天然成立：MinIO 实例本就共享；local 实例适合单节点/共享盘部署——门户多节点且用 local 时，须换 MinIO 或把 `storage_path` 指到共享存储。
- 版本/灰度/上报状态放平台库（DB），禁止节点本地内存/文件态（无状态红线）；灰度判定每次请求实时查库，无需广播。
