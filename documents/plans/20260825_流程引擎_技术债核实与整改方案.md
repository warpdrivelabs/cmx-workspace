## 三、整改方案（按优先级分档，不动代码 · 供排期决策）

> 原则：先堵**安全/数据正确性**出血点（低成本高收益），再做**架构级**改造（高成本，需专项）。每档标注是否破坏性、依赖关系。

### P0 · 立即处理（安全出血，成本低）

**方案 1 — 凭据清理（对应 019，最紧急）**
- 三个 toml（flow-server / -dev / -local）真凭据改占位符模板，真值走 env / 部署密钥管理；对齐已有的 `flow-server.toml.example`（已是占位）与 `deploy/flow-server.docker.toml`（已用 `change-me`）。
- `flow-server-dev.toml` / `-local.toml` 从 git 移除跟踪（`git rm --cached`），确认 `.gitignore` 生效。
- **已泄露的 secret 必须轮换**：JWT secret `a7k9...`、API key `cmx_sk_dev_...`、DB 口令 `9lWsRQY4...`——git 历史里已存在，改文件不够,需轮换 + 评估是否清洗历史（`git filter-repo`）。
- 破坏性：低（仅配置）。依赖：无。**建议本周做。**

**方案 2 — SQL 注入面收口（对应 017）**
- `biz_link.rs` 读侧 ~25 处 `format!` 拼接全部改参数化 `$N`（与写侧 4 处对齐）;`keyword` 的 LIKE 过滤对 `%`/`_`/`\` 做转义。
- 破坏性：无（等价改写）。依赖：无。建议配 018 补查询单测一起做。

**方案 3 — auth 默认 off 改 opt-in（对应 004/003 的地基）**
- `AuthMode` 默认从 Off 改为 fail-fast：未显式配置即拒绝启动（而非静默放行 `X-Tenant`/`X-User` 头）。这是 003/004 所有越权面的总闸。
- 破坏性：中（现有依赖 off 的部署要显式配 auth）。需与接入方（MDM 等）协调。

### P1 · 近期专项（数据安全/正确性，中成本）

**方案 4 — 身份服务端化 + 参与方校验（对应 004 残余）**
- `/tasks/my`、`/todos/*`、`/withdrawable` 的用户身份从 query 改取服务端上下文 `current_user()`，query 参数降级为运维只读；claim/transfer/delegate/addsign/reject 校验 current_user 是否为任务 assignee/owner；`get_instance`/`variables`/`comments` 加参与方（initiator/assignee/candidate/cc）过滤。
- 对齐 complete 已落地的 T0b 模式，逐端点补齐。破坏性：中（curl 直调习惯要改）。

**方案 5 — 实例乐观锁（对应 007）**
- `cmx_flow_instance` 加 `version`/`rev` 列，save_snapshot 比对版本冲突即拒并重试;cc 已读、转签台账等「点对点」改独立表操作、从快照全删重插中剥离。
- 破坏性：中（DDL 迁移 + 保存路径改造）。是 008 集群化的前置。

**方案 6 — API Key 授权边界 + system 溯源（对应 003）**
- key 声明扩展为 `key:tenant:system` + `allowed_definition_keys` + 可调端点类别；`TenantCtx` 加 `system` 字段全链路透传（日志/事件/意见留痕）;`start_instance` 校验 definitionKey∈key 白名单;委托令牌验签失败对写端点降级为拒绝。
- 破坏性：中。与方案 1 的 toml 结构化改造合并推进。

**方案 7 — 事务边界收口 + 静默吞错消除（对应 009）**
- 发起+bizLink 合入单事务;补偿失败 error 日志+告警指标;意见留痕失败至少 warn+计数;TaskCreated emit 只针对本次 save 新建任务（对比前后任务集 diff 或加 !completed 过滤）。
- 破坏性：低。可与 013 观测性一起做。

### P2 · 架构级改造（高成本，需立项）

**方案 8 — 多租户/多系统数据模型统一（对应 005，牵动 006/010/011）**
- 运行态主表补 `tenant_id`（对齐已有侧表）+ 评估 `system_id`;`FLOW_DB_ID="fico-db"` 改配置项、默认值中性化（如 `flow-default`）+ 发布迁移说明;multi 模式补租户列对齐 + 查询过滤。
- 破坏性：**高**（DDL 迁移 + 存量数据 + 命名）。是 004 读取过滤、010 治理的数据基础。

**方案 9 — 单写者假设破除（对应 008，依赖方案 5）**
- boundaryTimer/中间定时器轮询对齐 async_job 的 `FOR UPDATE SKIP LOCKED`+lease;定义热装载改「内存缓存+版本号比对」或 Redis pubsub 失效广播;SSE 跨节点走 Redis pubsub 或客户端游标补偿。
- 破坏性：高。做完才能安全多副本部署（当前靠单副本规避）。

**方案 10 — 定义/表单归属治理（对应 006，依赖方案 6 的 system 字段）**
- definitionKey/formKey 接入命名约定（`<system>_<biz>` 前缀）+ DAM domain 归属校验;定义发布/删除/绑定加角色鉴权;form_key 删除前校验引用;评估「定义版本 pin 到实例」。
- 破坏性：中-高。

**方案 11 — 运行态生命周期治理（对应 010/011）**
- 终态实例延迟清理任务（N 天后删运行态行、只留 hi 表）;correlate 路径接入已建的 `find_catch_subscription`（去掉 500-scan 兜底）;incident 独立表 + `/incidents` 清单端点 + 可配置自动重试。
- 破坏性：低-中。P3 订阅表「有实现无接线」是唾手可得的收益点。

### P3 · 工程化与规范（低紧急，逐步偿还）

- **012 前端接入**：ops-console 补死信/作业/批量运维面板（端点已齐，纯前端）。
- **013 可观测性**：非阻塞失败点补日志+计数;评估业务指标接 /_mon 或补 Prometheus 端点。
- **014 demo 去痕**：seed 改空表或独立开关;summary 字段去硬编码;前端 FORM_MAP 仅 dev 保留;demo crate feature 门控。
- **015 双镜像**：ui-native 改构建产物、脚本从 core 生成 + CI 一致性校验;或运行时只读一份;menu-manifest 死档删除。**先止血**：把当前 8 对漂移合回一致。
- **016 API 规范**：存量冻结,新端点立即转 POST+body 风格;OpenAPI 生成从路由表派生（消除 28/88 手工缺口）;v2 整体规整时一次性收 Path Variable/DELETE + 分页。
- **018 测试**：handlers/biz_link/views 补单测（复用 cmx-flow-tests 的 PG 门控模式）;E2E 补 P2/P3 用例。
- **020 BPMN**：修正 `parse_start_event` 的 docstring/代码不一致（改为真报错或真支持）;静默忽略项统一改显式报错;评估通用活动类型映射 + signal/compensation 接入。
