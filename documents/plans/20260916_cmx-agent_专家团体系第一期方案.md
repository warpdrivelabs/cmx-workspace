# cmx-agent 专家团体系第一期方案（对标 WorkBuddy 专家·专家团）

> 2026-09-16 · 模块 `backend/cmx-agent` · 状态：**待指令**（说「改」即按 §七 顺序实施）
> 背景：对标腾讯 WorkBuddy（专家 / 技能 / 连接器三件套）与 Qoder（Quest Experts Mode / Custom Agent / Skills）的调研结论（§一）转化为落地设计。已拍板两个决策：**召唤 = 绑定人设的独立会话**；**首期直奔专家团**。本方案给出专家团先行的完整设计：数据格式、执行链路、壳端界面、内置种子与分期。

## 一、调研结论（产品对标）

### 1.1 WorkBuddy：三层能力市场

官方口径一句话分层：**"Skill 是能力 / 专家是能力+经验 / 专家团是多位专家+协作流程"**，连接器是三者共用的外部能力底座。

| 概念 | 实测机制（v5.5.6 桌面端 + 官方文档） |
| --- | --- |
| 技能 | Claude 风格 SKILL.md 能力包（Puppeteer 浏览器自动化、MarkitDown、PDF/PPT、Deep Research、handoff 等）；市场分 推荐 / SkillHub / 套件；三种获得方式 = 上传本地包 / 按描述查找 / 按描述 AI 现场生成；可随时开关（关 = 对话中不可调用） |
| 专家 | 卡片 = 头像 + 名称 + 作者 + 一句话描述 + 3 标签 + 可选"特邀"徽标 + 累计使用量；详情页 = 召唤按钮 + "团队帮你做"示例 prompt + 使用案例；**召唤 = 开一个绑定该人设的任务** |
| 专家团 | "有团长、有分工、有协作的多 Agent 团队"：描述即编排说明书，召唤后团长自动拆解、分配团员并行执行、整合交付；积分消耗为单专家的数倍 |
| 连接器 | MCP 生态：官方 20+（腾讯文档/会议/企微/飞书/钉钉/TAPD/QQ 邮箱/企查查/天眼查/北大法宝…），第三方 60+ 行业 SaaS；自定义连接器 = MCP 配置；元工具"连接器工坊"可探测 MCP 端点自动生成连接器 zip |

**专家团实拆**（交易分析团队详情页）：13 位角色分 5 阶段——"技术面/基本面/新闻面/情绪面数据采集 → 多空辩论 → 交易决策 → 三方风险评估 → 最终报告，输出 BUY/SELL/HOLD 建议"。成员网格 = 头像 + 中文人格名 + 职务，主理人带 🛡 徽标：何执舟·首席策略官（主理人）、牛正阳·多头研究员、熊正寒·空头研究员、甘为先·激进风险分析师、沈行远·保守风险分析师、钟允平·中性风险分析师、季本实·基本面分析师、涂一线·技术分析师、闻一新·新闻分析师、莫慌言·情绪分析师、严控风·风险主管、蔡定锋·研究主管、程交远·交易员——人名全为职务谐音梗，人格感是产品辨识度的核心来源。其他团队形态各异：软件开发团队 = PM 定需求/架构师拆任务/工程师写码/QA 验证 + "小需求走快速模式"；独董会 = 按案组建席位、交叉质询、保留异议、交付可追溯备忘录。

**元工具三层**（自增长关键）：创建专家不是表单，而是新建任务页预填内置技能 expert-manager 模板（"帮我创建一个 XXX 专家，擅长 XXXXX。我的经验是：[…]"）对话式生成；造技能有"技能创建指南"；造连接器有"连接器工坊"。

**运营层**：精选场景导流卡（把相关专家+团队打包）、分类 tab + 综合/最热/最新排序、积分体系、企业版"把调好的专家/技能/连接器沉淀到项目空间供团队复用"。

### 1.2 Qoder：同构逻辑（工程层更透）

| 概念 | Qoder 实现 | 关键机制 |
| --- | --- | --- |
| 专家 | Custom Agent：`~/.qoder/agents/*.md`（用户级）/ `.qoder/agents/*.md`（项目级） | frontmatter = `name` / `description`（自动路由依据）/ `tools` / `model` / `skills` / `mcpServers`，正文 = 系统提示词；语义自动选型 + `/name` 手动；`/create-agent` 元技能生成 |
| 专家团 | Quest Experts Mode | **Lead Agent（大脑，不可定制）** + 6 内置专家（Researcher / Full-Stack / QA / Code Reviewer / UI Operator / Debug Engineer）；先出结构化计划可改，确认后并行执行；UI = 任务列表（Pending/In Progress/Completed）+ Expert Team Canvas（每专家一卡：步骤/输出摘要/状态）；专家可单独换模型、加 Additional Prompt、挂 Skills & MCP；官方口径质量 +67%、更慢，简单任务留在 Agent Mode |
| 技能 | Skills：SKILL.md，用户级/项目级（项目级优先） | 与 Anthropic 官方 skills 仓直接互通（`npx skills add anthropics/skills`）；自动触发 + `/name` 手动 |

### 1.3 同构结论

两家是同一张图：`技能 = SKILL.md 能力包`、`专家 = 人设+技能+工具+模型的声明式档案`、`专家团 = 团长编排 N 个专家的执行拓扑`、`连接器 = MCP`。WorkBuddy 强在市场/运营层与人格化；Qoder 强在执行工程层（Lead 纪律、Canvas 可视化、计划确认门）。cmx-agent 的执行引擎（子代理派发/过程可视化/回执/队列/级联取消）已经齐了，**缺的只是把子智能体产品化为"专家团"的声明式档案层 + 门面层**。

## 三、现状地基（代码证据）

可复用的地基比预期厚，五条关键事实：

1. **子代理类型注册表已存在且形态就是"专家档案"**。`crates/cmx-agent-core/src/agents.rs` 的 `AgentSpec`：`name`（snake_case 唯一，task 工具 `subagent_type` 取值）/ `title`（显示名）/ `description`（选型描述）/ `tools: ToolSelection`（`All | Allow{names} | Deny{names}`，对父回合可见集求值，**只收紧不放宽**）/ `model: Option<String>`（专属模型）/ `system_prompt` / `enabled` / `builtin`。内置两条 `general-purpose`、`explore`（只读 8 件白名单）。热生效：app 层持 `Arc<RwLock<Vec<AgentSpec>>>` 与 task 工具共享，`TaskTool::spec()` 每步动态拼 `subagent_type` 枚举。
2. **`<data_dir>/agents.json` 读写完备**（`crates/cmx-agent-app/src/agents.rs` `AgentRegistry`）：custom + builtin 覆盖项；文件损坏先备份 `.bad` 再降级不炸启动；每次保存**先重读文件合并写入**（防桌面/Web 壳同数据根双开后写者抹掉先写者）；变更即热生效。
3. **task 工具按 spec 派发成员的一切语义已就绪**（`crates/cmx-agent-tools/src/task.rs`）：`:425` 派生子 Agent 时守卫/审批/提问服务/策略**全量共享父**，工具白名单是额外收紧；`:448-453` `spec.system_prompt` 非空则替换默认 `SUBAGENT_SYSTEM`；前台/后台两条路径、级联取消、审批卡父视图可见、回执折尾均已落地。
4. **会话级人设注入缝现成**。`SessionMeta.system: Option<String>` 字段已存在（`crates/cmx-agent-app/src/store.rs:17-35`）；`send_inner` 每回合用 `session_system_prompt(session_id)` 重建 system（`app.rs:1543-1557`），其实现 = `default_system` 基座 + 会话所属空间段落（`app.rs:1925-1944`）。**专家/主理人的人设 = 把"基座"换成档案提示词，空间段落逻辑原样保留**。
5. **展示层反查链路已验证**：回执卡标题三层反查（`.receipt-title` + `subTaskDesc`）是子智能体执行过程可视化方案的既有成果，成员名牌化直接复用——把回执/子任务卡标题从任务描述换成"牛正阳 · 多头研究员"即可。

**命名警示**：`crates/cmx-agent-connectors` 已被占用——它是"连 cmx 平台服务"的客户端 crate（auth/dataauth/im_binding），**不是** WorkBuddy 意义上的连接器。后续连接器概念落地时命名须避开（如 `cmx-agent-mcpmarket` 或并入 `cmx-agent-mcp`）。

## 四、概念模型与数据格式

### 4.1 四概念映射

| WorkBuddy 概念 | cmx-agent 落点 | 本期状态 |
| --- | --- | --- |
| 技能 | 已注册工具（`list_skills` = `tools.specs()`；`/斜杠 = 同名工具`约定已在系统提示词中） | 已存在，门面化后置 |
| 专家 | 人设会话档案（SessionMeta 人设 + 展示元数据） | 后置（D2） |
| **专家团** | `teams/<id>.json` 档案 + 主理人会话 + 成员子代理 | **本期** |
| 连接器 | MCP（现有 `cmx-agent-mcp` 底座） | 后置 |

### 4.2 团队档案：`<data_dir>/teams/<team_id>.json`

一团队一文件（便于导入/导出/分享），内置团队首启种子到该目录（存在不覆盖）。全文示例：

```jsonc
{
  "id": "trade-analysis-team",
  "name": "投研分析专家团",
  "avatar": "builtin:chart",            // 内置图标枚举或数据根相对路径
  "description": "8 位专业角色分 4 阶段协作完成 A 股分析：多维数据采集 → 多空辩论 → 风险评估 → 交易决策与报告",
  "tags": ["交易策略", "风险管理", "市场分析"],
  "disclaimer": "以上内容基于公开数据分析，仅供参考，不构成投资建议。",
  "leader": {
    "id": "he_zhizhou",
    "name": "何执舟",
    "title": "首席策略官",
    "prompt": "你是投研分析专家团的主理人何执舟。职责：理解用户目标 → 按团队章程拆解 → 用 task 工具派发给对应成员（subagent_type 见名册）→ 汇合结论 → 整合交付最终报告。\n团队章程（严格执行）：\n1) 多维数据采集：并行派发 zz_tuxian(技术面)、zz_jibenshi(基本面)、zz_mohuangyan(情绪面)；\n2) 多空辩论：并行派发 zz_niuzhengyang(多头) 与 zz_xiongzhenghan(空头)，各给立场论据；\n3) 风险评估：派发 zz_yankongfeng 出风险清单与对冲建议；\n4) 你本人给出交易决策与最终报告，明确输出建议方向、依据、风险与免责声明。\n纪律：不得跳过阶段；不得派发名册外的类型；成员结论须注明出处；用户任务明显简单时可在报告开头说明走了快速通道（合并 1-2 阶段）。"
  },
  "members": [
    {
      "id": "niu_zhengyang", "name": "牛正阳", "title": "多头研究员",
      "prompt": "你是多头研究员牛正阳：只陈述支持看多的证据与逻辑，引用数据出处，承认对方最强的一点。",
      "tools": { "mode": "allow", "names": ["web_search", "web_fetch", "fs_read"] },
      "model": null
    }
    // … 共 8 名成员，字段同 AgentSpec 语义
  ],
  "welcome_prompts": ["帮我分析下某公司基本面和估值", "评估这个组合的风险收益", "复盘今天的市场"],
  "max_members": 8
}
```

字段要点：

- `leader.prompt` 与 `members[].prompt` 是纯提示词；`pipeline` 不设结构化字段，**直接写成 leader.prompt 里的"团队章程"章节**（D3：描述即编排，WorkBuddy 同款）。
- `members[].tools` 语义与 `ToolSelection` 一致（`allow`/`deny`/`all`），**档案缺省 = `allow` 白名单且必须显式给**——专家团成员一律 fail-closed，不给默认全放行（红蓝审查口径延续：多角色并行若不收紧权限，审批卡会弹到用户手软）。
- `welcome_prompts` 对应 WorkBuddy"团队帮你做"三条示例，召唤后点击即发送。
- 加载校验：`id`/`name`/`leader`/`members` 非空、成员数 ≤ `max_members`（硬上限 8）、成员 `id` 全局唯一、`prompt` 非空；校验失败该文件降级跳过并备份 `.bad`（沿用 agents.json 模式）。

### 4.3 成员注册：运行时层，不进 agents.json

成员在加载时转换为 `AgentSpec`（`name = "<team_id>__<member_id>"`，`title = "牛正阳 · 多头研究员"`，`description` = 职务 + 团队名供选型），注册进共享清单使 task 工具可派发。**不写入 agents.json**——agents.json 是设置页"子智能体"分区的用户读写真源，团队成员混入会被误删/误改。`AgentRegistry` 增加运行时层：

```
rebuild(): merged = builtin + custom(agents.json) + team_specs(teams/ 目录派生)
```

成员因此出现在 task 的 `subagent_type` 枚举中——这正是需要的（主理人靠枚举派发成员），代价是普通会话的模型也能看到并派发成员类型（Qoder 同款语义：自定义 subagent 全局可见）。按会话收窄枚举（绑定团队的会话只暴露"成员 + general-purpose"）列为开放问题 §八，`TaskTool::spec()` 每步现调、改造面不大，本期不做。

## 五、执行设计

### 5.1 召唤链路（后端）

1. `SessionMeta` 增加字段 `#[serde(default)] pub persona: Option<String>`（值 = `<team_id>`；serde default 兼容旧 meta.json）。
2. 会话创建端点增加 persona 参数：校验团队存在 → `create_session` 落 meta（`persona` + 标题 = 团队名）→ 回包带团队档案（前端渲染详情/欢迎语）。会话 id 走常规前缀（现有 `subtask-` 前缀守卫不受影响）。
3. `session_system_prompt(session_id)`（`app.rs:1925`）加分支：meta.persona 命中团队 → 基座 = `leader.prompt` + 名册章节（成员 `title → type name` 对照，供主理人精确派发）+ 免责声明；**空间段落逻辑原样保留**（团队会话同样绑工作空间、同样受回合级 roots 快照约束）。`default_system` 不再叠加。
4. 每回合重建语义不变（`send_inner:1555`），人设不会因重启/换空间丢失；`PLAN_MODE`/`<task_result` 章节追加逻辑不动（在人设之上续加，互不覆盖）。

### 5.2 主理人回合行为

主理人就是一个"会派子代理的普通会话"：用户描述任务 → 模型按章程用现有 `task` 工具派发成员（前台并行或后台+队列）→ 汇合 → 整合输出最终报告（长文气泡 + 可落文件产物）。零内核改动；现有守卫（NO_DETOUR、拒绝勿绕道）、审批三模式、级联取消、过程可视化、等待队列全部自动生效。

### 5.3 成本与安全护栏

- **召唤明示**：详情弹窗与召唤确认展示"预计 N 名成员参与，消耗约为单会话数倍"（对齐 WorkBuddy 积分提示的诚实版本）。
- **规模上限**：成员 ≤ 8（`max_members` 可下调不可上调），超出拒绝加载。
- **成员权限**：白名单必须显式声明（§4.2），缺省 fail-closed；成员沿用守卫/审批全量共享父的现行语义。
- **快速通道**：章程内约定简单任务合并阶段（对齐 WorkBuddy 软件开发团队"小需求走快速模式"），由主理人判断并在报告开头声明。

### 5.4 壳端 UI（真源 `crates/cmx-agent-web/ui/`，改完 `bash sync-ui.sh` 同步桌面壳）

1. **专家团入口页**（侧栏"专家"新入口或并入现有菜单，实施时定）：卡片网格（封面图标/团队名/成员数/标签/描述截断）+ 详情弹窗 = 召唤按钮 + 描述 + 免责声明 + **成员网格**（头像 + 人名 + 职务，主理人 🛡 徽标）+ "团队帮你做"三条（点击即以该团队召唤并预填发送）。
2. **会话名牌化**：绑定团队会话内的子任务卡/回执卡标题按 `subTaskDesc` 反查链路映射为成员 `title`；团队会话在侧栏列表带徽标。回放/恢复/实时三通路沿用过程可视化方案的既有实现。
3. **导入/导出**：详情弹窗提供导出（下载 json）；支持从文件导入（校验后落 `teams/`）。热生效 = 重新加载 teams 目录（`AgentRegistry::shared` 同款即时发布）。
4. 双壳已知坑照抄备忘：Web 壳 `include_bytes` 白名单须手动加新静态资产；桌面壳须重新构建才见新 UI；浏览器缓存旧 JS 须强刷。

## 八、风险与开放问题

1. **主理人编排质量**（最大风险）：派错人/漏阶段/团员跑题全靠提示词纪律。M1 用裁剪版团队专验；守卫文案（拒绝勿绕道/NO_DETOUR）确认对成员子代理同样生效。若提示词编排不稳，升级路径 = 档案增加结构化 `pipeline` 字段做引擎级阶段状态机（E3 的名册章节改为分阶段注入），不动数据格式骨架。
2. **token 成本**：一次团队任务 ≈ N+1 个会话。已用召唤明示 + 规模上限 + 快速通道三道闸；后续可在网关 usage 上做团队维度计量（依赖网关透出 usage，现有缺口）。
3. **task 枚举膨胀**：成员类型对全部会话可见（Qoder 同款语义）。开放问题：绑定团队的会话按 persona 动态收窄 `subagent_type` 枚举（`TaskTool::spec()` 每步现调，改造面小），下期评估。
4. **设置中心"子智能体"分区与团队成员的关系**：本期成员不进 agents.json、设置页不显示；是否需要只读分组展示待拍板。
5. **命名占用**：连接器概念后续落地避开 `cmx-agent-connectors`（§三末）。
6. **组织分发**（后续独立方案）：团队档案天然适合走 `cmx-container/assets` 真源 + 门户 module 登记下发，形成 WorkBuddy 企业版"组织沉淀"的对应物；个人数据根保留覆盖能力。
