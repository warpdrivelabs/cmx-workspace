# 审批工作台前端优化方案

> 日期：2026-08-28 ｜ 模块：flow frontend ｜ 状态：实施中（M1–M4 已落地）

## 一、结论与边界

当前待办中心与办理页已经具备可用链路，但前端仍分散推断流程语义：节点状态、制单动作、意见归属、动作可用性、时区与人员显示分别散落在 `todo-center.js` 与 `task-form.js` 中，导致同一流程在不同区域呈现出不同的信息结构。

本方案只处理前端，不修改后端接口与流程引擎语义。目标是把前端收敛为三层：

1. **数据适配层**：把 instance、tasks、tokens、comments、definition 转成统一展示模型；
2. **审批展示层**：步骤条、意见记录、动作面板、人员显示、时间显示只实现一次；
3. **页面编排层**：待办中心负责找任务与轻量预览，办理页负责业务表单与审批动作。

前端可以解决展示不一致与交互粗糙问题，但不能弥补权威 timeline、动作 capability、幂等与乐观锁等后端契约缺口。方案中的适配层必须为后续后端契约升级预留边界。

## 二、现状问题

### 2.1 页面职责重叠

当前问题：

- `todo-center` 与 `task-form` 各自维护轨迹、意见、人员、时间与动作文案逻辑；
- `task-form` 的 content 与 property 区域都有机会渲染审批动作，用户可能看到两套入口；
- 待办中心右侧承载了较完整的流程详情，与办理页信息重复。

建议职责：

| 页面 / 区域 | 应承担职责 | 不应承担职责 |
| --- | --- | --- |
| 待办中心列表 | 分类、筛选、任务识别、轻量预览、打开任务 | 完整业务表单、复杂审批动作 |
| 待办中心属性区 | 单据概要、当前节点、简要步骤、最新记录 | 办理动作与长历史 |
| 办理页 content | 业务表单、业务单据、业务封装审批动作 | 平台审批按钮重复入口 |
| 办理页 property | 平台审批控制台、意见、完整流转记录 | 业务表单编辑 |

### 2.2 时间线由渲染层推断

当前根据 `tokens` 与 `tasks.some(completed)` 推导状态，在简单线性流程可用，但难以表达退回重入、并行分支、会签或签、网关与自动节点。推断逻辑必须集中在适配层，不能散落在 HTML 模板中。

### 2.3 “制单”语义依赖节点 ID

当前存在 `nodeBpmnId === 'apply'` 的兜底判断。这不是通用契约。短期可保留兜底，但必须集中到动作归一化函数；默认显示“提交”，只有上下文明确提供业务语义时才显示“制单”。

### 2.4 动作区一刀切

当前办理页容易同时展示同意、驳回、退回上一步、退回到指定节点。动作可用性应受只读模式、`console=none`、任务状态、可退目标、当前用户身份等条件控制。不可用动作应禁用并说明原因，或收入“更多动作”。

### 2.5 交互仍是调试型

当前存在 `window.prompt` 转签、`window.confirm` 确认、驳回退回意见可空、提交后固定延时关闭、busy 反馈不足等问题，适合联调，不适合审批产品主体验。

## 三、目标信息架构

### 3.1 待办中心

```text
待办中心
├── explorer：分类
├── content：待办列表
│   ├── 筛选条
│   ├── 任务卡片：单据标识 / 流程名 / 当前节点 / 业务标签 / 主动作
│   └── 加载态 / 空态 / 错误重试
└── property：轻量预览
    ├── 单据概要
    ├── 当前节点
    ├── 简要步骤条
    └── 最新一条流转记录
```

原则：

- 列表卡片主动作不超过两个；
- 转签等低频动作放入详情菜单；
- 属性区只做预览，完整历史进入办理页查看；
- 刷新后保留分类、筛选、分页与选中任务。

### 3.2 办理页

```text
办理页
├── content：业务表单 / 业务单据
└── property：审批控制台
    ├── 页签：办理｜流转
    ├── 办理页签：当前任务、意见输入、主动作、更多动作
    └── 流转页签：统一步骤条、分节点意见记录
```

当表单绑定声明 `console=none` 时：

```text
content = 业务表单自带审批动作
property = 只读流转记录
```

平台控制台与业务封装动作不得同时出现。

## 四、统一展示模型

新增纯函数适配层：

```js
buildApprovalViewModel({
  task,
  instance,
  comments,
  definition,
  currentUser,
  context,
})
```

输出：

```js
{
  meta: {
    instanceId,
    businessKey,
    definitionName,
    currentNodeName,
    formMode,
    readOnly,
  },
  steps: [
    {
      key: 'apply',
      nodeBpmnId: 'apply',
      nodeName: '发起人确认',
      status: 'completed',
      iteration: 1,
      actions: [],
    },
  ],
  unmatchedActions: [],
  availableActions: [
    { key: 'approve', label: '同意', kind: 'primary' },
    { key: 'reject', label: '驳回', kind: 'danger', commentRequired: true },
  ],
}
```

### 4.1 节点状态

| 状态 | 含义 | 展示 |
| --- | --- | --- |
| `completed` | 已完成或已离开 | 对勾 + 已完成 |
| `current` | 当前 token 所在节点 | 品牌色 + 当前 |
| `pending` | 定义中尚未到达的 userTask | 中性 + 待处理 |
| `unknown` | 数据不足 | 数据不完整 |

规则：

- 不把网关、serviceTask、endEvent 画成用户审批步骤；
- 不用静态定义伪造确定路径；
- 分支中未走的路径只能标为可能路径或不显示；
- 同一节点多次进入按 `nodeBpmnId + iteration` 分组；
- 数据不足时显示 `unknown`，不猜测。

### 4.2 动作归一化

| 原始值 / 来源 | 归一动作 | 默认显示 |
| --- | --- | --- |
| `approve` | `APPROVE` | 同意 |
| `reject` | `REJECT` | 驳回 |
| `return` | `RETURN` | 退回 |
| 空 decision + 首 userTask | `SUBMIT` | 提交 |
| 业务上下文标记制单 | `SUBMIT` | 制单 |
| 无意见 | — | （未填写意见） |

“制单”不再由渲染函数直接判断，只能进入归一化函数。

### 4.3 人员与时间

统一函数：

```js
displayActor(action) // nickName -> userName -> userId -> —
formatLocalDateTime(iso) // RFC3339 -> 浏览器本地 YYYY-MM-DD HH:mm
```

非法时间原样兜底；人员显示保留 userId 的 title 提示。

## 五、组件设计

### 5.1 ApprovalSummary

用于待办中心属性区与办理页顶部，展示单据号、流程名、当前节点、办理人、状态和关键业务字段。

### 5.2 ApprovalTimeline

统一步骤条：

```html
<ol class="approval-timeline">
  <li class="step completed">...</li>
  <li class="step current">...</li>
</ol>
```

视觉继续采用竖向 AntD Steps 风格：

- 完成：对勾；
- 当前：品牌色实心圆；
- 待处理：中性圆；
- unmatched：虚线小点，不伪造节点名；
- 当前节点带 `aria-current="step"`；
- 长节点名与长人员名可换行。

不采用 UI5 Wizard，因为它是交互式向导；不采用 IgniteUI Stepper，因为 inactive step 内容不可见，不适合展示全部意见。

### 5.3 ApprovalActionList

按节点展示动作记录：

- 操作人；
- 动作标签；
- 本地时间；
- 意见正文；
- 退回目标；
- 系统动作标识。

### 5.4 ApprovalActionPanel

办理页唯一动作区：

```text
我的意见
[ textarea ]

[ 同意 ] [ 更多 ▾ ]
```

驳回、退回、转签收入更多动作；同意保持主按钮。动作区负责校验、busy、错误提示与结果反馈。

### 5.5 ApprovalConfirmDialog

替代原生 `confirm`：

| 动作 | 对话框要点 |
| --- | --- |
| 同意 | 是否提交当前意见 |
| 驳回 | 流程是否终止，意见必填 |
| 退回 | 目标节点，意见必填 |
| 转签 | 目标人员与责任说明 |
| 撤销 | 是否终止实例，不可恢复 |
| 取回 | 回到哪个节点，需满足什么条件 |

### 5.6 ApprovalUserPicker

替代 `window.prompt`：

- 搜索用户；
- 展示昵称 / 用户名 / 组织；
- 只返回有效用户 ID；
- 提供空态与错误提示；
- 前端过滤展示字段。

## 六、请求与状态策略

### 6.1 请求

选中任务时并行请求 instance 与 comments，必要时读取 definition 缓存，并使用 request token 防止旧响应覆盖新任务。

办理页打开时并行请求实例、意见与表单上下文，生成 approval view model 后渲染。

### 6.2 加载态

- 列表：3 张任务卡骨架；
- 属性区：概要 + 3 行步骤骨架；
- 办理页：表单区 + 控制台骨架。

### 6.3 错误态

| 场景 | 处理 |
| --- | --- |
| 列表失败 | 错误条 + 重试 |
| 实例失败 | 属性区错误 + 重试 |
| 意见失败 | 历史区局部错误，不影响业务表单 |
| 动作失败 | 保留输入 + 错误提示 + 重试 |

### 6.4 刷新

- 列表刷新保留筛选与分页；
- 办理成功后通知待办中心刷新；
- SSE 只做增量提示；
- 用户正在输入意见时不自动重建 textarea。

## 七、交互规则

### 7.1 动作可用性

| 条件 | 结果 |
| --- | --- |
| 只读查看 | 不显示办理动作 |
| `console=none` | 平台不显示动作 |
| 任务已办结 | 显示已办结果 |
| 无可退目标 | 禁用退回 |
| 非办理人 / 候选 | 只显示查看 |
| busy | 全部动作禁用 |

### 7.2 意见策略

- 同意：意见可选；
- 驳回：意见必填；
- 退回：意见必填；
- 转签：原因可选但推荐填写。

后续由节点 capability 覆盖默认策略。

### 7.3 提交反馈

动作提交后进入 busy；成功后展示结果、通知列表刷新，并延迟关闭或引导关闭；失败后保留意见、解除 busy、展示服务端错误。不再无条件 `setTimeout(close)`。

### 7.4 可访问性

- 步骤条使用 `ol / li`；
- 当前节点使用 `aria-current="step"`；
- 动作菜单支持键盘；
- 对话框支持焦点管理与 Esc；
- 状态不能只靠颜色表达。

## 八、主题与样式

- 全部颜色从 `--sap*` 派生；
- 不硬编码 `#xxx` / `rgb()` / `hsl()`；
- 支持亮暗主题与 Neo 皮肤；
- 待办中心与办理页使用同一套步骤条 token；
- 不为亮暗主题各写一份样式。

统一 token：

```css
.approval-view {
  --step-size: 28px;
  --step-gap: 16px;
  --step-line-width: 2px;
  --step-title-font: 13px / 600;
  --action-font: 11px / 700;
}
```

## 九、代码组织

### 阶段一：页面内适配层

在 `todo-center.js` 与 `task-form.js` 中建立同构函数：

- `buildApprovalViewModel`
- `buildTimelineSteps`
- `normalizeAction`
- `displayActor`
- `formatLocalDateTime`

优点是快速落地；缺点是两处仍需镜像同步。

### 阶段二：门户共享运行时

Portal 注册：

```js
globalThis.__cmxFlowApprovalView = {
  buildApprovalViewModel,
}
```

native pages 优先读取全局共享实现，并保留 fallback 供独立 flow web 壳使用。

### 阶段三：专用前端模块

长期拆为：

```text
flow-approval-view/
├── model.js
├── timeline.js
├── actions.js
├── user-picker.js
└── style.js
```

由门户与 flow 独立壳共同复用。

## 十、实施计划

### M1：模型与轨迹收敛

范围：

- 建立页面内 view model；
- 统一时间、人员、动作映射；
- 删除渲染函数中的零散推断；
- unmatched 记录不再伪造成节点。

验收：简单流程正确、退回记录不丢、无英文动作、时间本地化、人员统一。

### M2：办理页动作区重构

范围：

- content / property 保持唯一动作区；
- 同意为主按钮；
- 驳回 / 退回收入更多动作；
- 意见校验；
- busy 与结果反馈。

验收：双入口不重复、驳回无意见不能提交、退回必须选择目标、失败输入不丢失。

### M3：对话框与人员选择

范围：

- 替换原生 `confirm / prompt`；
- 新增审批确认对话框；
- 新增用户选择器。

验收：无原生弹窗、转签不能手输无效 ID、危险动作有明确后果说明。

### M4：待办中心列表优化

范围：

- 卡片信息分层；
- 动作降密度；
- 空态 / 加载态 / 错误态；
- 属性区轻量化。

验收：用户能快速识别可办任务，卡片主动作不超过两个，列表错误可恢复。

### M5：共享组件与测试

范围：

- 抽共享展示模型；
- 统一主题 token；
- 建立 Playwright 用例；
- 建立镜像一致性检查。

验收：两个页面步骤条一致，亮暗主题可读，长 ID 不挤压，六份镜像一致。

## 十一、测试矩阵

| 场景 | 期望 |
| --- | --- |
| 线性审批 | 步骤顺序正确 |
| 制单后待审 | 首节点显示提交，不显示空卡 |
| 同意 | 显示同意与意见 |
| 驳回 | 显示驳回与终止结果 |
| 退回 | 同一节点可出现多轮记录 |

| 会签 | 显示多办理人与当前进度 |

| UTC 时间 | 转本地时区 |

| 暗色主题 | 无白块与低对比 |
| 键盘操作 | 菜单与对话框可操作 |

## 十二、非目标

本方案不做：

- 后端 timeline 契约重构；
- 服务端 capability 契约；
- 审批动作 API 合并；
- 乐观锁与幂等；
- webhook outbox；
- BPMN 能力扩展。

这些仍是后端演进方向。前端方案的目标是在现有数据下不伪造语义、不重复实现、不给用户误导，并为后续契约升级预留稳定适配层。

已落地内容：

- 节点进度补充时间：已完成节点取该节点最新流转时间，当前节点取任务到达时间；待办中心轻量进度与办理页完整轨迹共用同版本视图模型，节点、状态、时间、办理人保持一致。
- 统一动作、人员、时间与意见归一化；历史意见通过用户目录补显示名；时间仍转浏览器本地时区。

- 待办中心属性区收敛为轻量概要、紧凑步骤条与最新流转；分类切换会清空旧选中轨迹。
- 办理页 content 区只保留业务表单；平台审批控制台收敛到 property，并拆分「办理 / 流转」页签。
- 审批动作改为「同意 + 更多」：驳回、退回上一步、退回指定节点收入更多菜单；驳回 / 退回强制填写意见。
- 动作提交增加 busy、校验错误、成功结果与失败保留输入；退回目标选择显示「直接前驱 / 上 N 步」。
- 移除待办中心转签、撤销、取回的 `prompt / confirm`，替换为页内用户选择器与确认对话框。
- 待办卡片主动作降密度，次要动作进入更多菜单；列表增加错误态与重试。
- 样式全部从 `--sap*` / 语义变量派生，兼容亮暗主题；修正未注册的 `tray` 图标。
