# 流程：审批规则外置与身份管理前端方案

> 日期：2026-09-03　分支：cmx-rpt-flow　状态：待评审
>
> 来源：流程模块四问题调研 + 主流产品（Flowable/Camunda、钉钉/飞书审批）差距分析定论。
> 用户决策（2026-09-03）：P0 项 1/2/3 立项实施；组织上下文自动补全、集群安全（job/timer 并发）、
> 站内信通知通道三项**暂缓**，本方案不含。

## 一、背景与问题定论

### 1.1 调研定论（2026-09-03）

| # | 问题 | 定论 |
|---|------|------|
| 1 | 审批配置与流程配置未分离 | 属实。审批人/审批方式/表单绑定/抄送全部内嵌 BPMN XML 节点属性（`cmx:candidates`、`loopCharacteristics`、`cmx:formKey`、`cmx:cc`），**改审批人必须重新发布流程版本** |
| 2 | 审批挂组织机构 | 机制齐备（七种候选 user/role/position/org/orgLeader/initiator/initiatorLeader，external 模式查 cmx_user/cmx_org），但发起侧不传 org_id 致 orgLeader 空转——**暂缓修复** |
| 3 | 流程缺分组 | 已解决（definition-manager 分组面板 + group_id + /definitions/set-group，20260902 重构） |
| 4 | 表单缺审批组件 | 部分解决（cmx-flow-trail 已上收共享组件）；审批操作区未组件化、委派/加签无前端入口 |

### 1.2 身份底座缺口（本次新增确认）

- **组织机构无模型**：cmx-iam 仅有 user/role/role_group/permission 模块，无 org 模块；user.org_id 是裸字符串字段。
- **cmx_org / cmx_position / cmx_user_position 三表有查询无管理**：flowengine M4 为候选人解析自建（`cmx-flow-store-pg/src/resolver.rs`），数据只能手工 SQL 维护。
- **用户/角色后端 API 齐全（cmx-iam-api handlers：user/role/role_group/permission/rule）但门户无管理页面**。

**结论**：审批规则外置（选人引用组织/岗位/角色）依赖可维护的身份主数据，身份底座是前置工程，二者并成一个方案分批实施。

## 二、目标与范围

**P0-0 身份底座**：组织机构模型归位 IAM + 用户/角色/组织管理前端。
**P0-1 审批人规则外置**：审批人规则独立存储，改审批人不升流程版本。
**P0-2 审批策略三件套**：审批人去重 / 审批人=发起人自动通过 / 空候选策略。
**P0-3 审批动作补齐**：委派、加签（并加签）、减签前端入口 + 待办批量审批。

不在范围：代理设置（出差委托）、消息通知通道、办理人侧高亮流程图、formMode=edit 字段收紧（P1 顺延）；orgLeader 组织上下文自动补全、集群安全（暂缓）。

## 三、P0-0 身份底座设计（前置）

### 3.1 组织机构模型归位

新表落在**平台库**（IAM 侧），flowengine resolver 的 external 查询表名不变（cmx_org 等三表本就在 IAM 库，只是补上管理入口与 DDL 归属）：

| 表 | 关键列 | 说明 |
|----|--------|------|
| `cmx_org` | id, code, name, parent_id, **path**（物化子树路径）, **leader_user_id**, sort_no, archived | 与 flowengine resolver 既有查询契约一致（path 前缀匹配子树、leader_user_id 部门领导） |
| `cmx_position` | id, code, name, org_id?, archived | 岗位，可挂部门 |
| `cmx_user_position` | user_id, position_id, archived | 用户-岗位 |

DDL 真源：cmx-container `docs/sql` 平台库目录 + 幂等迁移；flowengine 侧删除自建 DDL 改为只读消费。

### 3.2 管理前端三页（门户 ui-native，走 cmx-iam-api）

| 页面 | 形态 | 复用 |
|------|------|------|
| 组织机构管理 | 左树（部门树，拖拽/增删改）+ 右卡（部门详情：负责人 leader、岗位列表） | 树组件范式同 master-list 左树 |
| 用户管理 | 列表（搜索/部门过滤）+ 新建/编辑弹窗（挂部门、挂角色、挂岗位） | admin-ui-kit 底座 + 六管理页 UI 统一范式 |
| 角色管理 | 角色列表 + 成员维护 + 权限（对接既有 permission API） | 同上 |

用户管理页须支持把用户挂到 cmx_user_position（新 API：cmx-iam-api user handler 扩展 positions 字段）。

### 3.3 验收

- 三页 CRUD 全通；组织树支持任意层级；部门领导可指引用户；
- flowengine external resolver 对新维护数据即查即得（org 子树、orgLeader、position 三链路回归测试）。

## 四、P0-1 审批人规则外置设计

### 4.1 数据模型（流程库）

```
cmx_flow_approval_rule (
  id            VARCHAR(64) PRIMARY KEY,
  def_key       VARCHAR(128) NOT NULL,   -- 流程定义 key
  node_id       VARCHAR(128) NOT NULL,   -- userTask bpmn id；'*' = 定义级默认
  priority      INTEGER      NOT NULL DEFAULT 0,   -- 多条命中取高者
  candidates    JSONB        NOT NULL,   -- [{kind,value}]，与 cmx:candidates 同构
  strategy      JSONB,                  -- 节点策略（见 P0-2），NULL = 继承定义级
  enabled       BOOLEAN      NOT NULL DEFAULT TRUE,
  effective_from TIMESTAMPTZ, effective_to TIMESTAMPTZ,  -- 时间窗（为代理/临时调整预留）
  version       INTEGER      NOT NULL,   -- 乐观锁
  updated_by / updated_at ...
)
```

设计要点：
- **叠加而非替换**：BPMN 内嵌 candidates 保留为兜底（与现版本 diff/模拟能力兼容）；命中 enabled 且在时间窗内的外置规则**覆盖**内嵌值，node 级优先于 `'*'` 定义级。
- 改规则**不触发流程定义发布**，已运行实例的下一个该节点任务即生效（新任务创建时解析）。
- 策略字段并入规则表（而非单独一张策略表），避免表碎片。

### 4.2 引擎侧改造

- 新增 `ApprovalRuleStore` trait（cmx-flow-def 或独立 crate）+ PG 实现；
- 引擎任务创建路径（候选人解析处，engine.rs resolve_all_with 调用点）前置一步：按 (def_key, node_id) 查外置规则命中则替换候选集；
- REST：`/api/flow/v1/approval-rules` CRUD + 按 def_key 列表（新接口遵循 POST + JSON body 规范，仅单条详情 GET）；
- 规则变更写审计（复用事件总线发 rule.updated 事件，订阅体系可直接消费）。

### 4.3 前端

- 设计工作台 assignee 页签增加「外置规则」提示（该节点已有外置规则时显示徽标，画布节点加标记）；
- 新页「审批规则管理」（definition-manager 内入口：选定义 → 节点规则列表 + 编辑弹窗，候选引用选择器复用身份底座的选人组件）。

### 4.4 验收

- 改审批人规则后不发布流程，新实例/下一环节即用新人；带时间窗规则到期自动失效回落内嵌值；
- BPMN 内嵌值保持不变，版本 diff 干净。

## 五、P0-2 审批策略三件套

策略存于 approval_rule.strategy（JSONB），未命中外置规则时读节点 `cmx:strategy` 扩展属性（BPMN 内声明，两处同构）：

```json
{
  "dedupe": true,                        // 审批人去重：同人在流程内多节点只审首次
  "selfAutoPass": true,                  // 审批人 == 发起人 → 自动通过（记 comment「发起人自动通过」）
  "emptyPolicy": "reject" | "autoPass" | "escalateLeader" | "error"
                                         // 候选解析为空：报错(默认,现行为) / 自动通过 / 转上级(escalate) / 挂起并告警
}
```

引擎实现点：
- **去重**：实例级已审人集合（instance variables `__approvedBy`），resolve 后过滤 + 空则按 emptyPolicy 处理；
- **selfAutoPass**：resolve 结果 == {initiator} 单人时自动 complete；
- **emptyPolicy**：现在空候选静默返回空 Vec，改为按策略分派；escalateLeader 依赖 initiatorLeader 解析（不依赖实例 org_id，不受暂缓项影响）。

前端：设计工作台 approval 页签 + 审批规则编辑弹窗各暴露三个开关/下拉。

## 六、P0-3 审批动作补齐（纯前端为主）

| 动作 | 后端现状 | 前端改动 |
|------|---------|---------|
| 委派 delegate | `POST /tasks/delegate`（handlers.rs）已有 | todo-center 卡片菜单 + task-form 审批区加「委派」（选人弹窗，标注完成后回到原办理人） |
| 加签 addsign | M4.3 API 已有（仅并加签形态） | 同上入口「加签」，多人选择 |
| 减签 | **无** | 引擎补 remove_sign API（仅移除未办理的加签人）+ 前端入口 |
| 批量审批 | complete 循环即可 | todo-center「我的待办」列表加多选 + 批量同意（逐条 complete，汇总成功/失败，意见共用） |

选人组件：新建共享选人弹窗（组织树 + 角色/岗位筛选 + 搜索，数据走 cmx-iam-api + flow dimensions），委派/加签/减签/转签/审批规则编辑统一复用——这是本批次唯一的新共享前端组件，进 cmx-data-comp。

## 八、风险与既知边界

- 外置规则与 BPMN 内嵌值**双真源**：本方案定位为「运行时覆盖，BPMN 为设计态兜底」，规则管理页须明示覆盖关系，避免管理员困惑；
- selfAutoPass 与会签（MI）叠加语义：仅当候选解析为发起人单人时触发，多实例集合中过滤发起人而非整节点自动通过；
- 暂缓的 orgLeader 空转问题：emptyPolicy=escalateLeader 走 initiatorLeader 链路不受影响；实例 org 上下文补全仍待后续批次；
- cmx_org 数据归属从 flowengine 自建表迁到 IAM 管理后，需数据迁移脚本（存量表数据搬平台库，若本就同库则只补管理入口）。
