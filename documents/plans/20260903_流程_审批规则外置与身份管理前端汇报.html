一、背景与核心结论来源：流程四问题专项调研 + Flowable/Camunda、钉钉/飞书审批对标分析

一句话结论：引擎底座已经很强，不输主流开源产品；真正的欠账在“审批业务体验层”与“身份底座”——审批人规则与流程图耦合、组织/用户/角色无管理前端。本方案以四个批次补齐，不动引擎核心架构。
  • 引擎层能力完整：20 种 BPMN 节点/事件、会签或签、退回任意节点、实例在线迁移、多租户、约 110 条 REST 端点、事件订阅三表管线（webhook/Kafka/RabbitMQ + 死信监控）——多项能力超 Camunda 社区版
  • 审批人配置全部内嵌 BPMN XML，改一个审批人必须重新发布流程版本，与钉钉/飞书“规则独立配置”的差距是最大体验缺口
  • 平台没有组织机构模型（cmx-iam 无 org 模块），流程候选人解析依赖的三张组织/岗位表有查询、无任何管理入口，数据靠手工 SQL 维护
  • 用户/角色后端 API 齐全，但门户管理前端为零页面
  • 委派、加签有后端 API 无前端入口；无批量审批；无审批人去重/发起人自动通过/空候选策略

三、四问题专项定论2026-09-02 提出 → 09-03 调研核实

#问题定论关键事实
1审批配置与流程配置是否分离未分离审批人/审批方式/表单绑定/抄送全部为 BPMN XML 节点属性，改审批人 = 改图 → 发布新版本
2审批是否挂组织机构机制有·链路断七种候选 + 部门子树/部门领导解析齐备；但发起侧不传组织上下文，部门领导（实例组织）空转。修复暂缓
3流程是否缺分组已解决分组面板 + 过滤 + 改分组已上线（20260902 重构）
4表单是否缺审批组件部分解决轨迹组件已共享化；审批操作区未组件化、委派/加签无前端入口

五、建设方案：四个批次每批独立可验收、可提交；B4 可与 B2/B3 并行

BATCH 1 · 前置
身份底座

cmx_org / cmx_position / cmx_user_position 三表 DDL 归位 IAM（含部门子树路径、部门领导）；组织树 / 用户 / 角色三个管理页（复用 cmx-iam-api 既有接口）；共享选人组件（组织树 + 角色岗位筛选 + 搜索）进 cmx-data-comp

BATCH 2
审批人规则外置

新表 cmx_flow_approval_rule（定义 key + 节点 id + 候选 JSON + 时间窗 + 乐观锁）；引擎解析时叠加——外置规则覆盖 BPMN 内嵌兜底值；规则 CRUD API + 规则管理页。改审批人不再升流程版本，下一环节即生效

BATCH 3
审批策略三件套

审批人去重（同人在流程内只审首次）/ 审批人=发起人自动通过 / 空候选四策略（报错·自动通过·转上级·挂起告警）；策略随外置规则存储，设计工作台同步暴露开关

BATCH 4 · 可并行
审批动作补齐

委派 / 加签 / 减签前端入口（后端 API 大多就绪，补减签）；待办批量同意；全部复用 B1 选人组件

关键设计决策：外置规则定位为「运行时覆盖，BPMN 内嵌值为设计态兜底」——不破坏现有版本 diff / 模拟能力，规则管理页明示覆盖关系；规则变更走事件总线发 rule.updated，既有订阅体系可直接消费做通知扩展（为暂缓的通知通道预留口子）。

六、暂缓项与风险已决策暂缓 / 需评审关注

暂缓项（2026-09-03 决策，不在本方案范围）

  • 组织上下文自动补全（发起侧传 org_id 或引擎反查）——部门领导（实例组织）空转维持现状
  • 集群安全（timer / 异步作业 / 订阅投递的多副本并发）
  • 站内信 / 邮件 / IM 通知通道

评审关注点

  • 双真源边界：外置规则与 BPMN 内嵌候选人并存，覆盖关系需在规则管理页对管理员足够显性
  • 发起人自动通过与会签叠加语义：仅单候选人场景整体自动通过，多实例集合中过滤发起人
  • 存量组织数据迁移：三表从 flowengine 自建迁为 IAM 管理，需迁移脚本与回归（flowengine external resolver 三链路）
