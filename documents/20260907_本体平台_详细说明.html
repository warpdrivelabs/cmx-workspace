1. 定位与总体架构

定位：企业本体平台（对标 Palantir Foundry Ontology）——把企业的"东西（对象）—关系—操作（动作）—计算（函数）"建模为一套可发布、可查询、可治理的元数据体系，业务数据按类型物化存储，跨对象的关系查询（Search-Around）编译成单条 SQL。

规模：Rust 后端 4 个 crate 共约 8,800 行；前端工作台 3 个页面（约 2,100 行）；图组件 1 个（约 2,100 行 TS）。服务端口 8097，API 前缀 /api/onto 与 /api/onto/v1 双前缀等价。

2.2 命名与校验（后端强制，建模必读）

  • apiName 白名单：字母/下划线开头，仅字母/数字/下划线——该规则同时是 SQL 表名/列名拼接安全的基础。
  • primaryKey、titleProperty 指定必须能在 properties 中找到。
  • 属性 apiName 不得重复；关系两端 objectTypeA/B 必须非空且已定义。
  • upsert 语义：同 apiName 重复保存=覆盖更新（不是报错）。
  • 校验专用端点 POST /object-types/validate 只验不存，返回 {valid, error}。

3. 存储设计

3.1 表全景（13 张静态 + 动态对象表）

层表说明
定义层om_object_type / om_link_type / om_interface / om_shared_property / om_action_type / om_function六类元素各一张，apiName 主键，复杂结构存 JSONB；status 建索引。
版本层om_version发布快照：version 主键 + rev 内容指纹 + snapshot JSONB，不可变。
运行层oe_action_log（动作审计）oe_outbox（副作用发件箱）om_policy（安全策略）om_source_mapping（漏斗源映射）oo_quarantine（隔离区）审计按 (action, executed_at) 建索引；发件箱按 (status,id) 建索引供 dispatcher 领取。
对象层oo_<type>（惰性建）＋ ol_edge实例表 (pk TEXT 主键, title, props JSONB, created_at, updated_at) + title 索引；超边表 (link, a_pk, b_pk, props) 联合主键 + 双向索引。
  • 惰性物化：某对象类型第一次写入实例时才创建对应 oo_<type> 表——建模零成本，写数即建表。
  • 无外键纪律：一切引用靠索引不靠 FK 约束（删对象时代码层面清边）。
  • 租户即库：表内不带 tenant 列；多租户模式按 onto_<tenant> 每库一套 schema。
  • 迁移方式：幂等 DDL 重放（启动时 ensure_schema 顺序执行 + ADD COLUMN IF NOT EXISTS 补列），无版本化 migration 框架。

4. 四大核心算法

4.1 对象集代数 → 单条 SQL（查询引擎）

查询不写 SQL，写代数树。7 种算子：

算子（op）编译结果
baseSELECT pk FROM oo_T
filter + 谓词树终端表 self-join：外层套 WHERE pk IN (内层) AND (谓词)
searchAroundSELECT DISTINCT e.对端 FROM ol_edge e WHERE e.link=$N AND e.本端 IN (内层)，direction 决定 forward(a→b)/reverse(b→a)
union / intersect / subtractSQL UNION / INTERSECT / EXCEPT；两侧终端类型不一致编译期报错
staticVALUES ($1),($2) 主键直列

谓词是 11 种类型化节点（eq/ne/gt/ge/lt/le/in/contains/isNull/and/or/not），不接受裸 SQL 片段。三跳查询示例（北区客户 → 金额 ≥1000 的订单）编译形态：

-- 参数 $1=region 值，$2=amount 值，$3=link 名（示意，实际由编译器生成）
SELECT o.pk, o.title, o.props FROM oo_Order o
WHERE o.pk IN (
  SELECT DISTINCT e.b_pk FROM ol_edge e
  WHERE e.link = $3 AND e.a_pk IN (
    SELECT c.pk FROM oo_Customer c
    WHERE c.pk IN (SELECT pk FROM oo_Customer)
      AND (c.props ->> 'region') = $1))
  AND (o.props ->> 'amount')::numeric >= ($2)::text::numeric
ORDER BY o.title, o.pk LIMIT 100
  • 防注入双保险：表名/属性名过 safe_ident 白名单（与建模 apiName 规则同源）；值一律 $N 参数绑定。
  • 数值比较双侧 ::numeric；contains 转 LIKE 且转义 %_。
  • 分页 limit 钳制 1..1000，hasMore=页满判断。

4.2 FEEL 表达式引擎（判定与求值）

能力
  • 三段式：tokenizer → Pratt 解析（完整绑定力表）→ 作用域链求值
  • and/or/not、比较、in、区间 [a..b]（开闭端）
  • if then else、for x in list return
  • some/every … satisfies 量词（短路）
  • 列表谓词过滤 list[c > 100]、下标从 1 起（负数从尾）
  • 约 28 个内置函数：floor/round/abs/min/max/sum/mean/upper/substring/contains/count/sort/append/coalesce…
纪律
  • 判定一律 fail-closed：求值出错或非布尔真 = 不通过
  • 数值统一 f64，相等比较 1e-9 容差
  • 除 0 / 类型不匹配返回 null 而非报错
  • clean-room 内嵌（不跨仓依赖规则引擎），独立微服务边界纪律
  • 使用位置：动作提交校验 validations、函数求值 body、（预留）属性约束

4.3 动作执行：事务 + 发件箱（写引擎）

动作定义四段结构：parameters（参数契约）→ validations（FEEL 校验列表）→ logic（编辑序列）→ sideEffects（副作用列表）。

① 参数校验
required 非空
→
② FEEL 校验
fail-closed 全量报错
→
③ 编辑解析
$name 替换/插值
→
④ 写侧 PEP
deny_actions 拒绝
→
⑤ 单事务提交
编辑+审计+发件箱
  • 五种编辑原子：createObject（upsert）/ modifyObject（读改写，对象须存在）/ deleteObject（连带清边）/ addLink / removeLink。
  • 参数绑定两套机制：$name 整串等于时递归替换（结构化）；内嵌插值（如 "approve_$orderId" → "approve_O-1"）。
  • 事务边界 = 整个动作：任一编辑失败全部回滚；审计日志与副作用发件箱同事务写入。
  • dry-run：只预演 + 落 status=dryRun 审计，不触库不入发件箱。
  • 发件箱消费：dispatcher 用 FOR UPDATE SKIP LOCKED 原子领取（多实例安全）→ 按 kind 投递（startBusinessProcess→flow / computeReport→report / webhook→HTTP / emitEvent→SSE / callFunction→FEEL）→ 回标 dispatched/deferred/failed。

4.4 动态安全（行级 + 列级）

  • 策略 om_policy：按 (objectType 可空=全局, subject) 匹配主体，产出 rowFilter（谓词树）+ denyMarkings + denyActions。
  • 读侧 POST /secure/object-sets/load：命中策略的行级残差谓词 AND 包一层 Filter 进编译管道（复用对象集编译器，安全即查询）；结果行按属性 marking 打 ***。
  • 写侧 PEP：动作执行前检查 denyActions，命中即拒绝并返回策略名。

7. 如何增加对象（全流程）

7.1 概念：类型 vs 实例

对象类型=模板（元数据，落 om_object_type）；对象实例=数据（落 oo_<type> 表）。先有类型才能写实例（写未定义类型直接业务错误）。

7.2 增加类型的四条路

途径做法与示例
A · 设计工作台explorer 区「+ 对象类型」→ Inspector 编辑属性（主键◇/标题⌾/必填*/索引⚡/语义类型）→ 保存。可视化、带本地校验（图组件 validate 镜像后端规则）。
B · REST APIvalidate → save 两步（完整 JSON 见下）。
C · DOC 导入POST /import/doc：entities[]（apiName/primaryKey/titleProperty/properties）+ relations[]（from/to/cardinality/role）→ 每实体一类型 + 每关系一组合关系（命名 <from>_<role>_<to>）。
D · DCT 导入POST /import/dct：{apiName, displayName, items:[{code,name}]} → 参照类型（code 主键/name 标题）+ items 批量落对象。

8. 如何结合主数据系统

8.1 分工定位

MDM（cmx-mdm :8095）是治理与发放层：变更申请（录单）→ 流程审批 → 落字典/主数据表。本体是关联与消费层：把主数据物化为参照对象，供业务对象引用、图谱钻取、动作治理。数据流向单向：MDM → 本体（回写暂无）。

8.2 通路 ①：DCT 字典导入（低频字典一次性接入）

curl -s -X POST .../api/onto/v1/import/dct \
  -H "Content-Type: application/json" -H "X-API-Key: ..." \
  -d '{ "apiName":"Currency","displayName":"币种",
        "items":[{"code":"USD","name":"美元"},
                 {"code":"CNY","name":"人民币"},
                 {"code":"EUR","name":"欧元"}] }'
# → {objectType:"Currency", seededItems:3}
# 参照类型主键=code、标题=name；字典项即对象，可进对象集过滤：
#   filter(code=USD) → 美元 ✓、欧元 ✗（e2e 实测）

输入是归一化 JSON（调用方从 cmx-model 的 DctQuery 适配），保持 onto 与模型中心解耦。字典更新后重调即幂等覆盖。

8.3 通路 ②：Funnel 源映射持续同步（主通道，推荐）

面向业务库的主数据表/字典表，三段管道：抽取（执行 sourceQuery）→ 映射校验（map_row：主键空/必填缺失即违规）→ 物化（合格 upsert 成对象，违规入隔离区）。

# 1) 目标参照类型（status=active）
curl -s -X POST .../api/onto/v1/object-types \
  -d '{"apiName":"MdmCustomer","displayName":"主数据客户","primaryKey":"id",
       "titleProperty":"name","status":"active",
       "properties":[{"apiName":"id","baseType":"string"},
                     {"apiName":"name","baseType":"string"},
                     {"apiName":"region","baseType":"string"}]}'

# 2) 源映射（多列主键 keyColumns 以 | 拼接）
curl -s -X POST .../api/onto/v1/funnel/mappings \
  -H "Content-Type: application/json" -H "X-API-Key: ..." \
  -d '{ "objectType":"MdmCustomer",
        "sourceQuery":"SELECT cust_id, cust_name, region_code FROM md_customer",
        "keyColumns":["cust_id"], "titleColumn":"cust_name",
        "propertyMap":[{"source":"cust_id","property":"id"},
                       {"source":"cust_name","property":"name"},
                       {"source":"region_code","property":"region"}],
        "required":["name"] }'

# 3) 同步（幂等 upsert；源行变化再同步即覆盖）
curl -s -X POST .../api/onto/v1/funnel/sync/MdmCustomer -d '{}'
# → {read:4, written:3, quarantined:1, mode:"full"}

# 4) 违规行处理与管道状态
curl -s ".../api/onto/v1/funnel/quarantine?objectType=MdmCustomer"   # 原始行+violations
curl -s ".../api/onto/v1/funnel/pipeline-status/MdmCustomer"
节奏建议：MDM 审批落库高峰后（或每日定时）由外部调度触发 sync——同步为全量幂等模式，天然适合"审批完成 → 刷新本体"。

8.4 通路 ③：业务单据关联（docType + DOC 导入）

  • 对象类型挂 docType:{code,name} 标明对应 MDM 单据类型（导入时自动回填，也可手工指定）。
  • POST /import/doc 把主从实体图批量建为对象类型+组合关系；子实体折叠为层块属性（array/struct + constraints 层结构），适合"已有业务模型整体进本体"。

8.5 通路 ④：动作 ↔ 治理审批流

  • 动作副作用 startBusinessProcess 直连 cmx-flowengine 起流程实例（透传 definitionKey/variables/businessKey）；对主数据对象的治理操作（停用/合并/改主）可定义成本体动作，执行即发起 MDM 审批。
  • 内置模板：objectApprove（对象审批）、consolClose（关账联动：一个动作同时起审批流+算报表）——设计工作台「从模板创建」可改。
  • 全链路留痕：execute 审计 + 发件箱投递状态可查。

8.6 推荐落地配方

1. MDM 治理流程不动（申请→审批→落库）；
2. 低频字典（币种/凭证类型/行业分类）走 DCT 导入；
3. 高频主数据（客户/物料/组织/科目）走 Funnel 源映射，指向业务库表；
4. 业务对象类型用 LinkType 引用参照对象（订单→客户、凭证→科目、物料→组织）；
5. 外部定时（cron/门户定时任务）调 sync 保持新鲜；隔离区定期人工复核；
6. 需治理的变更定义成动作：FEEL 校验 + 乐观锁写回 + 起审批流；
7. publish 固化版本 + OSDK 给下游系统生成 TS 客户端。
现状边界：同步为 M1 全量同步执行（长任务雏形，增量/异步在路线图）；无内置调度需外部触发；DCT 导入为快照式；本体→MDM 回写未内置；sourceQuery 会真实执行配置的 SQL——仅限可信管理员配置 SELECT。

9. 前端图组件 cmx-ontology-graph

9.1 定位与契约

独立仓 TypeScript Web Component（<cmx-ontology-graph>，零框架零运行时依赖，约 2,100 行/9 文件/22 个单测），与 @cmx/decision-graph 平级——本体图是一般 ER 图（可双向/自环），不是 DAG，故不共用代码只共享设计语言。

类别成员
数据入属性 data-spec（JSON）／ setSpec(def) ／ getSpec()
配置readonly（只读预览模式，隐藏锚点、缩小的布局档）
结构操作addObjectType / addInterface / addLink / delNode / delLink / autoLayout / selectNode / setAllGroups
逃生舱getModel() 返 OntologyModel（节点/边/属性/implements 全量操作 API）
事件出spec-change（任何变更带全量 def）／ type-select ／ edge-select ／ link-add（拉线落点，宿主弹速建气泡补元数据）／ link-added ／ node-add ／ node-del ／ connect-rejected（均 bubbles+composed）

图 JSON 契约（camelCase 对齐后端）：nodes[{id,kind,displayName,color,status,properties[{apiName,baseType,isPrimaryKey,isTitle,required,isIndexed,semanticType,children}],implements,groupPath}] + edges[{apiName,source,target,cardinality,roleA,roleB,sourceProperty,targetProperty}]；_layout/_edgeRoutes/_groupCollapsed 为组件私有布局态，后端忽略。

9.2 核心能力

  • 富卡片：色条+显示名+mono apiName+属性行（◇主键/⌾标题/*必填/⚡索引/语义徽标）；超 maxRows 折叠 +N；状态描边三态；业务单据层块（array/struct 子层）递归缩进渲染、整块展开不截断。
  • 基数边：有向连线+角色标签；锚点默认"属性→属性"（源外键属性可显式指定或按名称启发式猜测，靶默认主键）。
  • 正交避让布线：A* 在"有趣坐标线"网格求最短正交路径（障碍膨胀+转弯惩罚），无解兜底中线折线；自关联画环；手动拖拽线段整段平移保持正交。
  • DAM 分域折叠：按 groupPath 建嵌套可折叠容器，默认全收起——可见节点数受"已展开"约束而非总数，大图性能方案；跨容器边聚合为计数捆线。
  • 拉线建关系：从卡内任一属性行锚点拖橡皮筋线到目标锚点（26px 磁吸）→ 派 link-add 交宿主补元数据。
  • 主题：--og-* 令牌锚定门户 --sap*，UI5 亮暗自动穿透 shadow 边界，零 JS。

11. 风险与技术债（使用时规避 / 后续加固）

① subjects 越权面（高·安全）：secure_load 与动作 PEP 的注释声称"jwt 模式以令牌主体为准"，但实现是请求带 subjects 即采纳、未按鉴权模式分支——jwt 模式下调用方仍可自报主体绕过行级残差与 deny_actions。规避：生产用 jwt 时应在网关/代理层剥离调用方 subjects 头，或尽快修复为按模式分支。
② funnel 拼接 SQL 与任意 sourceQuery（高·注入面）：load_mapping/list_quarantine/pipeline_status 用字符串拼接（非参数绑定）；run_full_sync 直接执行调用方配置的任意 SQL。规避：映射配置仅限可信管理员；sourceQuery 只配 SELECT；该组端点不对普通用户开放。
③ publish 并发撞版本（中）：版本号 = MAX+1 无锁，并发发布会撞号；快照组装 N+1 查询。规避：发布操作串行化（管理动作，频率低）。
④ 删对象清边按 pk 全局匹配（中）：pk 是跨类型 TEXT，不同类型撞 pk 值会误删他类型的边。规避：类型间 pk 命名空间隔离（如带前缀）。
⑤ is_indexed 未消费（中）：实例表只建 title 索引，Filter 走 JSONB 抽取全表扫。规避：大表高频过滤属性暂用聚合/分页控制范围，等待索引物化特性。
⑥ FEEL 数值全 f64（中）：decimal 金额在判定路径有精度风险，相等比较 1e-9 容差。规避：金额判定用区间/整数分单位（分为整数）。

轻量项：策略全表拉取 Rust 过滤（量大放大）；非法 row_filter JSON 静默变空（残差失效无告警）；OpenAPI 手写未收录约 15 个新端点（以路由表为准）；SSE 无持久化（可靠投递走发件箱）；图组件 paint 全量重建（大扁平图拖拽可能掉帧，用分域折叠规避）。
