# cmx-flowengine 国内主流流程引擎对标与对抗性审查报告

> 日期：2026-09-04 ｜ 对象：`cmx-flowengine`（当前 main，R4.2 之后）
> 基准：国内主流企业级流程/审批引擎——飞书审批（含低代码平台）、钉钉审批、金蝶云苍穹流程服务云、用友 YonBIP/NC 流程平台，旁参泛微 e-cology / 致远等 OA 流程代表
> 方法：代码级事实核查（引擎 crate + 前端工作台 + DDL + 文档）× 官方公开能力基线交叉比对；审查立场为**对抗性**——先假设设计有问题，再找证据

---

## 0. 结论速览

**总体判断：引擎内核（执行语义、版本 pin、实例迁移、事件投递、可观测性）已达到国内 BPM 产品的水准线，部分点（实例迁移干跑校验、节点时效分析、ops-console）甚至优于国内 SaaS 审批产品；但"审批业务面"（审批人规则、审批操作闭环、超时策略、消息触达）与国内标杆存在系统性差距，且若干缺口是正确性风险而非功能缺失。**

三句话概括：

1. **结构性根因只有一个**：审批要素（办理人/审批方式/表单/抄送）全部内联在 BPMN XML 节点属性里，与流程结构共享同一条"改图→发版→实例 pin→人工迁移"的重管道——高频运营变更被迫走低频结构变更的流程（§4 专项展开）。
2. **正确性风险有三个**：加签不可减签（死锁）、空审批人静默兜底（任务走错人）、"或签"语义与国内惯例偏差（时效与预期不符）——这三个不是"少个功能"，是会在生产里出事的类型。
3. **触达短板最伤产品叙事**：催办仅站内留痕、无 IM/邮件/短信推送、无离岗代理规则——国内平台以"待办追着人跑"为标配，我们以"人登录门户看待办"为前提。

---

## 1. 审查范围与方法

- **代码核查**：`crates/cmx-flow-{model,bpmn,engine,def,store-pg,identity,app}` 全量；前端 `web/ui-native/` 13 个 JS（约 1.6 万行）；DDL（`cmx-flow-store-pg/src/ddl.rs` 等内嵌幂等 DDL）。
- **能力基线**：飞书帮助中心/低代码平台官方文档、金蝶云产品手册与苍穹流程服务云官方页、行业通用"中国式审批"能力集（转办/加签/减签/回退/跳转/委托/催办/撤销）交叉验证；用友 NC/YonBIP 官方文档公开面较薄，以行业通行能力集替代。
- **不评 UI 美观、不评代码风格**；只评"能力有无、语义对错、设计取舍是否站得住"。

## 4. 专项：审批配置与流程配置未分离（已知问题，点名展开）

### 4.1 现状证据

`UserTask` 节点属性（`cmx-flow-model/src/ir.rs`）目前内联承载四类审批要素，并随 BPMN XML 一起版本化：

- **办理人**：candidate 表达式（`user/role/pos/dept/orgLeader/initiator/initiatorLeader`，`candidate.rs::parse_candidate_expr`）；
- **审批方式**：`MultiInstance`（会签/或签、顺序/并行、completion_condition）；
- **表单**：`form_key` / `form_mode` / `form_fields`（本环节可写字段白名单）；
- **抄送**：节点级 `cc` 名单。

全部四项的变更都要走：改 BPMN XML → draft → validate → **publish 版本 +1**；而在途实例因 R4.1 **pin 版本**语义继续按旧 XML 跑——

> **改审批人 = 改图 = 发新版本；组织调整一次，流程定义全员发一轮版；在途单要么走旧人、要么逐个实例人工迁移。**

### 4.2 为什么这是一个结构性缺陷，而不是"用起来麻烦"

1. **变更频率错配**：审批要素的变更频率（换人、调字段权限、会签改或签）远高于流程结构变更（加节点、改路径）。把高频变更压在低频变更的重管道（图变更→校验→发版→版本管理→迁移决策）上，运营成本随组织活跃度线性增长。
2. **版本语义被污染**：版本号的语义本应是"流程结构的演进"，现在混入了"人员与表单配置的演进"。版本 diff（design-workbench 的版本对比）里混杂大量与结构无关的噪音，追溯价值下降。
3. **在途实例的两难**：pin 保证快照一致性（好），但换来的是"新审批人生效要逐个 migrate"——`instances/migrate` 面向结构变更设计（节点映射校验），拿来应对"只换个人"是杀鸡用牛刀，且要求运维逐实例操作。
4. **与扩展模型问题同根**：引擎**没有执行/任务监听器**扩展点，"节点级行为定制"的一切诉求最终都落到改 XML 发版——未分离问题因此被放大：不仅是配置项，任何定制也一样。

### 4.3 国内标杆的解法对照

| 产品 | 审批要素存放 | 变更动作 | 在途单行为 |
|---|---|---|---|
| 飞书/钉钉 | 模板内独立"规则层"（表单化配置，非图纸属性） | 纯配置编辑，规则与结构分层存储 | 发起时点快照，在途不变 |
| 金蝶苍穹 | 审批人方案/参与人规则**独立于流程模板**，模板可复用方案 | 换方案不改图 | 策略按生效时间取 |
| 用友 NC | 审批人规则函数库 + 模板引用 | 改函数/规则不发模板版 | 同上 |
| **flowengine 现状** | **全部内联 BPMN XML 节点属性** | **必须改图发版** | **pin 旧版，需人工 migrate** |

注意：**"审批人是运行时求值"这一点我们其实已经做对了**（`cmx-flow-identity/src/resolver.rs` 运行时解析表达式）——真正被冻结的是**表达式字面量与参数**（`role(经理)` 里的"经理"写死在 XML），以及会签方式、字段白名单、抄送名单。问题不在"求值时机"，在"配置的载体与版本管道"。

### 4.4 改造建议（分层）

- **方案 A（推荐）：审批策略层抽离**。新增 `cmx_flow_approval_policy`（策略表，含类型化的办理人规则/审批方式/表单字段权限/抄送）+ 独立版本与生效时间；`UserTask` 改为携带 `policy_ref`（BPMN 扩展元素 `cmx:policyRef` 兼容既有 XML）；运行时按"实例发起时点快照或最新生效"（可配，默认快照，与 pin 语义对齐）解析策略版本。改审批人 = 改策略 = 不发流程版本，自带审计与回滚。
- **方案 B（不推荐）**：保留内联，区分"结构变更/参数变更"，参数热更新不走版本——破坏快照语义，在途行为漂移不可审计，与国内标杆实践背道而驰。
- **方案 C（兜底，可并行）**：保留 migrate 面向真正的结构变更；为策略变更提供"策略 diff → 自动生成迁移计划（仅重解析候选）"的批量工具作为过渡期缓冲。
- **同根修复**：在策略层落地的同一批工作中补**任务/执行监听器**扩展点（节点进入/离开、任务创建/分配钩子），把"一切定制=改图"的通道打开。

## 5. 能力差距矩阵（对标国内标杆）

图例：✅ 有 ｜ △ 有但语义/形态打折 ｜ ❌ 无。优先级：P0=高频刚需或正确性风险；P1=高频可绕行；P2=企业级加分。

| 能力 | 国内标杆 | flowengine | 级别 |

| **表单字段联系人**（按单据里选的人/部门审批） | 标配 | ❌ | **P0** |

| 能力 | 国内标杆 | flowengine | 级别 |

| 会签（全部同意） | ✅ | ✅ 并行多实例 | — |

### 5.7 BPMN 合规面（对金蝶"遵循 BPMN 2.0"宣称的诚实自查）

已实现：用户/服务/业务规则任务、四类网关、timer/error/message 边界与中间捕获、调用活动、嵌入+事件子流程、终止结束。
**不支持且编译器显式拒绝**（`compiler.rs::is_flow_node_like`）：scriptTask、sendTask、receiveTask、manualTask、intermediateThrowEvent、complexGateway、信号事件（广播）、补偿事件、事务/adHoc 子流程、块级边界事件；**启动事件仅普通与消息**，定时/信号/错误启动显式 Unsupported（技术债 020）。
定位声明：**不追全 BPMN 2.0 合规**（国内用户实际用不到补偿/事务的大部分场景）；支持子集已显式声明于 README「能力边界（BPMN 支持子集）」一节（2026-09-04 起），API 文档侧的同步待做。

## 6. 规划不合理与设计缺陷（对抗性审查）

### 6.1 前后端契约脱节：画布可画引擎拒收的元素
前端调色板含 ScriptTask 图标，而 `compiler.rs` 对 scriptTask 显式 `Error::Unsupported`——用户在画布上画得出、发布时才失败。同类问题：调色板宣称的元素集与 `NodeKind` 19 种之间需要一次**契约测试**（前端 palette 清单 ↔ 后端 supported 清单双向快照比对）。
**建议**：由后端契约接口（如 `/definitions/validate` 已有）派生前端调色板可用项；加一条契约测试防漂移。

### 6.2 "或签"语义偏差
现实现：或签 = **顺序**多实例（逐个传，第一人通过后不再派后续），且前端已明确以"或签"命名——调色板选项 `{ key: 'sequential', label: '顺序或签', hint: '逐个办理' }`、节点徽章 `text: '或签'`（design-workbench.js / definition-workbench.js 两工作台同款）。国内惯例（飞书/钉钉）：或签 = **并发派发**给所有人、任一人通过即整体通过（其余任务自动作废/收回）。逐个传在"第一人不在线"时阻塞整单，与国内用户对"或签=快"的预期相反，同名不同义是配置误导的直接来源。
**建议**：并行多实例 + 首个完成即取消其余作用域（引擎已有 completion_condition 与 mi_scope 机制，具备实现条件）；过渡期至少把徽章与选项文案改为"依次审批（逐个办理）"，把"或签"一词留给未来的并发语义——命名必须与国内惯例对齐。

### 6.3 空审批人静默兜底，与项目 fail-fast 哲学自相矛盾
候选解析为空时 `decide_assignment` 宽容退回静态 assignee（也空则任务无办理人悬空）。本工作区刚在 Redis init 上确立了"配了就要、错了就停"的 fail-fast 裁定；同一哲学套到审批人上：**解析不出人应该是 Incident（可见、可处置），而不是静默走错或悬空**。
**建议**：空候选默认落 Incident + 可配兜底策略（自动通过/转指定人/挂起）——与飞书"审批人为空特殊流转"页对齐。

### 6.4 无监听器扩展点，定制=改图
见 §4.4。国内企业级引擎（泛微节点前后动作、金蝶审批项后动作）均有节点级钩子；我们只有 serviceTask delegate 与事后事件订阅。"任务创建后自动做某事"这类最常见诉求现在做不了。
**建议**：最小面先做**任务监听器**（created/assigned/completed 三事件 × HTTP/webhook 出口），复用 outbox 通道与订阅规则，不必新造分发机制。

### 6.5 db-per-tenant 的规模化上限
`tenancy.rs` 多租户 = 每租户派生独立库。与平台"平台库/业务库分离"哲学一致、隔离性最好，但租户数量大时（SaaS 场景）库数量爆炸、跨租户运营查询/统计需逐库扫。若 flowengine 定位是企业内部署（租户=法人/组织实体，个位数到两位数），现设计成立；若对标国内 SaaS（飞书/钉钉海量租户），上限明显。
**建议**：明确写入 README"定位与边界"：本引擎面向企业级私有部署，租户=业务实体；不做海量 SaaS 租户。有定位声明，这个设计就是合理的。

## 8. 路线图建议

**第一批（P0，正确性与结构根因）**
1. 审批策略层抽离（§4.4 方案 A）+ 任务监听器最小面（§6.4）——一个专项，一次解决 §4 与 §6.4；
2. 减签端点与前端入口（恢复被加签 SUSPENDED 的原任务）；
3. 空审批人兜底策略化（默认落 Incident，可选自动通过/转指定人）+ 审批人=发起人策略；
4. 或签改并发语义（并行多实例 + 首成收口），命名对齐国内惯例（§6.2）。

**第二批（P1，对标追平）**
6. 连续多级主管 + 表单字段联系人两类审批人规则（resolver 与 CandidateKind 扩展，前端表达式构造器加两个模板）；
7. 节点超时策略集（提醒/自动转交/自动通过可配，复用 cmx_flow_job）；自动催办；
8. 统一待办推送通道（钉钉/企微/飞书 webhook 或邮件，复用 outbox DeliveryChannel trait——基础设施已就位，只差通道实现）；
9. 重复审批人去重规则、审批人撤回已同意、批量审批、字段权限三态。

**第三批（P2，企业级加分）**
10. 票决制一等公民配置、意见征询、长期代理规则、干预日志视图、变量条件实例查询；
11. 文档工程：`docs/usage/` 各篇能力边界细化（与 README「能力边界」声明对齐）；前端调色板契约测试（§6.1）；
12. （按需）信号/补偿/消息启动事件——建议明确"不追全 BPMN 合规"的产品立场而非补齐。
