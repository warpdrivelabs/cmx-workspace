01

术语小词典：核心概念一览

LEGEND · 图例

按"画地图 → 存数据 → 查数据 → 办事搬运"四组，对平台核心术语逐一说明。

第一组 · 画地图（建模的词）
本体Ontology
那张"企业数据地图"本身：有哪些东西、什么关系，统一定义成一整套。
对象类型ObjectType
地图上的"地点种类"，即模板：客户有哪些字段、主键是什么。建一个类型≈画一个地点图例。
接口Interface
横切能力标签，不是网络接口。比如"可开票"：客户、供应商都可以挂这个标签，表示都有开票那组字段。
共享属性SharedProperty
全局标准字段：一处定义、多处引用。"创建时间"定义一次，所有类型都引用，改一处全生效。
DAM 分域域▸应用▸模块
每个类型归入三级文件夹（如"客商域▸客户管理▸客户档案"），设计器按域折叠，几百个类型图也不乱。
发布 / 版本publish / version
把整套地图定义"拍照存档"，版本号只增不减。改错了随时回看任意历史版本。
第二组 · 存数据（数据的词）
对象（实例）Object
按模板填出来的一条真实数据：客户"北方贸易"就是"客户"类型下的一个对象。
pk 主键primaryKey
对象的"身份证号"，一表内绝不重复；建关系、定位对象全靠它。
title 标题titleProperty
给人看的名字：列表里显示"北方贸易"而不是一串编号，从指定属性自动抄一份单独存。
props 属性包props JSONB
对象的"全部家当"：所有字段值塞进一个 JSON（像快递箱——pk 是单号、title 是收件人、props 是箱里的货）。所以加字段不用改数据库表。
层块array / struct
单据的"明细行"折叠在对象内部：一张订单就是一个对象，几十行明细作为嵌套数组躺在里面，不拆成几万条记录。
乐观锁expectedUpdatedAt
防两个人改同一条数据互相覆盖：提交时带上"我看到的是哪个版本"，对不上就报冲突让你刷新重来。9-08 起建类型也带这把锁。
第三组 · 查数据（道路与导航）
关系LinkType / 边
地图上的"道路"，定义在对象类型之间（客户类型—下单→订单类型，存在定义表里，带方向、基数、角色名）。按它产生的一条条实际连线（哪条数据连哪条数据）默认统一存一张边表，加关系不用建新表；声明外键落库的关系则直走对象表外键列，连边表行都不加。
对象集ObjectSet
一次查询的"导航指令"：从哪类对象出发、按什么条件过滤、顺路走到哪。最后编译成一条 SQL，一次往返出结果。
顺藤摸瓜SearchAround
从一个对象顺着关系跳到相关对象：点开"某客户"→一跳看到它名下所有订单→再一跳回到客户。
第四组 · 办事与搬运（动词）
动作ActionType
地图上的"办事按钮"：给参数 → 按规则校验 → 改哪些数据 → 办完通知谁。比如"提交退租申请"，一个定义全包，全程留痕。
FEEL表达式语言
类似 Excel 公式的简单表达式：`金额 > 0`、`单价 * 数量`。校验规则算不出 true 就直接拦下——宁误拦，不放病。
函数Function
一段可复用的计算，配置即生效不改代码。如"延误风险 = 金额大于 1000 则 0.8 否则 0.2"。支持 FEEL / Rhai 脚本 / Rust 原生三种跑法。
副作用 / 发件箱sideEffects / outbox
办完正事的"附带动作"，共 6 种：起审批流、算报表、回调外部地址、发通知、发事件、调函数。先写进"待发清单"（和数据改动同一个事务，绝不丢），后台再挨个真正发出去。
漏斗 / 隔离区funnel / quarantine
数据搬运管道：从外部表按映射规则灌进来，合格的落库，不合格的（主键空、必填缺）进"不合格品区"等人工复核，不污染好数据。
OSDKTypeScript SDK
一条命令生成给前端用的代码包：对象变 interface、查询和动作变方法，前后端字段自动对齐，不用手写。
三个"隔壁兄弟"也会被提到
DCT 是数据字典（字段标准，如币种、凭证类型）；DOC 是单据模型（主从表单定义）；MDM 是主数据管理（客户/物料等基准数据的官方来源）。它们和本体的关系见第 4 站。
02

设计思想：为什么这么造

PHILOSOPHY · 定位

定位：连接层，不是又一个业务系统

本体平台不替你记账、不替你审批、不替你算报表。MDM 管主数据"对不对"，流程引擎管"批不批"， 报表管"算数"——本体负责把它们连起来：在一个地方看全景、顺着关系查、按一个按钮办事。 对标的是 Palantir Foundry 的本体（Ontology）思路，但走的是务实路线：不搞学术化的 OWL/RDF 那一套， 追求"业务能用"而不是"论文能发"。

一芯多壳：一个大脑，多种宿主

代码分四层，依赖严格单向向下：内核（六类元模型 + FEEL 解释器，纯函数零数据库依赖）→ 落地层（PostgreSQL 存取 + 查询编译器）→ 应用核（50 多个接口、鉴权、多租户、实时广播）→ 壳（薄到只有 136 行的启动器，以及门户里的反代壳）。 好处：同一个大脑，今天挂独立服务（:8097），明天可以内嵌进别的宿主，不用重写。

五条"家规"

家规说明
apiName 是唯一锚每个类型的英文名一旦定了就不改，改中文名不影响任何代码和表名——版本之间不漂移。
生命周期三态类型像人一样编队：试验 → 激活 → 废弃，图上卡片描边颜色跟着变，一眼看出谁是正式工。
DAM 三级分域所有类型归入"域▸应用▸模块"文件夹，大图按域折叠——图大不瘫的前提。
定义与数据分家定义存 om_* 表（12 张静态表里的 7 张），数据存 oo_<类型> 动态表。改定义不动数据表，互不锁死。
发布即快照发布时对整套定义算指纹（xxhash64），拍照存档、版本号只增——出错可回溯。

三个"反常识"，也是最省钱的三个决定

① 没有图数据库

逻辑上是图，物理上就是 PostgreSQL——没引入 Neo4j 等任何新数据库。关系的定义（客户类型—下单→订单类型）存定义表； 按定义产生的实际连线（哪条数据连哪条数据）默认进一张共用的边表——一行 = 一条连线，如 {"link":"customerPlacesOrder","aPk":"1","bPk":"101"}，即"1 号客户实例 连到 101 号订单实例"。 所以加一种关系不用建任何表，运维只维护一种数据库。9-10 起另有第二种落法：声明外键落库的关系不进边表，查询直接按外键列 JOIN 对象表。

② 属性不建数据库列，全塞一个 JSON

所有字段值打包进 props 一个 JSON 大字段，物理表固定就 5 列 （pk / title / props / created_at / updated_at）。 建模时加字段纯定义层操作，一行动态表结构都不用改。代价是按字段过滤没有数据库索引——这条代价我们记在第 5 站的账上（Q1）。

③ 权限不是"事后过滤"，是"查询的一部分"——9-10 起还是一扇硬门

行级权限（哪些行你看不见）直接编译进查询 SQL；9-10 合并读侧硬门后更进一步：主链路查询（列表 / 聚合 / 钻取） 查库前先过策略——命中 deny 直接 403 拒绝、被策略管控的类型未授权默认拒绝、敏感列直接从响应里移除 （不止打码）。动作执行前还有一道"谁能点这个按钮"的强校验。不存在"先查出来再筛、筛漏了就泄露"的后门。

只留两个受控写入口
外部数据进来只走漏斗，人/系统改数据只走动作——绕过按钮直接改库被架构上禁止。 好处：每笔改动都有审计记录可查、可回放。（"本体管'机器敢不敢做'（校验+权限），流程管'人同不同意'（审批）"——这就是动作和审批流的分工。）
03

数据怎么流转：从画图到办事的六步

DATA FLOW · 动线
STEP 1建模设计工作台画类型、拉关系、配动作
STEP 2发布整套定义拍快照，版本 +1，实时广播
STEP 3灌数据手工录入 / 字典导入 / 漏斗同步
STEP 4查与钻对象浏览器拼条件、顺关系一跳跳钻取
STEP 5配动作校验规则 + 改数声明 + 副作用
STEP 6办事360 工作台点按钮，试算→执行→留痕

平台固定的 12 张静态表

不管地图上放多少东西，平台自身的家当就这 12 张表。另有按类型动态建的 oo_<类型> 数据表 和全库共用的关系连线表 ol_edge，属于"数据侧"，不在这 12 张里。 ol_edge 的行全部产生在数据时刻：动作执行"加关系/断关系"时写入或删除、 外部系统显式调 POST / DELETE /links 时写入或删除、删对象时连带清掉它参与的边； 画本体图（建模）不碰它——建模只写上面的定义表，"声明的哪两类对象之间有关系"和"数据之间实际连了线"是两回事。

组表作用
定义
7 张		om_object_type对象类型定义：有哪些字段、主键、标题字段
om_link_type关系类型定义：哪两类对象之间、什么方向和基数、两端角色名
om_interface接口定义：横切能力标签（如"可开票"）及其挂的属性集
om_shared_property共享属性定义：全局标准字段，一处定义、多处引用
om_action_type动作定义：办事按钮的参数、校验规则、改数声明、副作用
om_function函数定义：FEEL / Rhai 写的可复用计算逻辑
om_version发布版本：整套定义的快照存档，只增不改、可回看
运行
5 张		om_policy权限策略：行级过滤、列脱敏、动作禁用（allow / deny）
om_source_mapping漏斗映射：源查询 + 字段对应关系，数据搬运的规则
oe_action_log动作审计：谁在何时点了什么按钮、改了哪些数据，可查可回放
oe_outbox副作用发件箱：待投递清单，与业务改动同事务落库，后台逐条投递重试
oo_quarantine隔离区：漏斗校验不过的行先搁这儿，不污染好数据，人工复核后重放

重点一：数据表是"写时自动建"的（懒物化）

新建对象类型时并不建数据库表，只往定义表写一行；第一次往该类型写数据时才自动建物理表 oo_<类型名>（幂等，重复调不出错）。四个入口会触发建表，全是"写数据"场景： 单条写入、批量写入（传空数组可当"建表接口"用）、字典导入、漏斗同步。

两条实用结论（容易踩的坑）
① 只建了类型、从没写过数据时，浏览器里查它会报 relation "oo_xxx" does not exist—— 读路径不会顺手建表。先写一条数据（或批量接口传空数组）就能查了。
② 删除类型不删表：oo_xxx 表和数据会留下（孤儿表），用同名重建类型会接着用旧表。

重点二：一条查询是怎么跑的

查询不写 SQL，写"导航指令"——一段 JSON 的对象集代数：算子一层套一层， 最里层是出发点（哪类对象的全量），往外每层做一件事：过滤、顺关系走、或做集合运算。 例：北区客户 → 顺着"下单"关系 → 金额 ≥ 1000 的订单，两跳穿越，指令长这样： 

{
  "op": "searchAround",   // 本层做什么：顺着关系走一跳
  "link": "customerPlacesOrder", "direction": "forward",   // 走哪条关系、朝哪个方向
  "source": {              // 出发点：还是一条指令，一层层往里剥
    "op": "filter",
    "predicate": { "kind": "ge", "property": "amount", "value": 1000 },   // 金额 ≥ 1000
    "source": {
      "op": "filter",
      "predicate": { "kind": "eq", "property": "region", "value": "north" },   // 北区
      "source": { "op": "base", "objectType": "Customer" }   // 最里层：从全部客户出发
    } }
}
// 读法：全部客户 → 挑出北区的 → 顺着"下单"走到订单 → 挑出金额 ≥ 1000 的

7 种算子，每种管一件事，套娃组合出任意查询：

算子作用
base查询起点：某类对象的全部数据
filter按条件筛掉不合格的行
searchAround顺着关系走一跳、到另一端的对象——本体的灵魂算子
union两批对象合并，按主键去重
intersect取交集：两批里都有的
subtract取差集：前一批里去掉后一批也有的
static不查库，直接点名一组主键（外部带来的固定清单）

条件（predicate）共 12 种： 比较 eq / ne / gt / ge / lt / le、集合判断 in / contains / isNull、 组合 and / or / not（可嵌套成条件树）。 平台把指令编译成一条 SQL、一次往返出结果（多跳就是自动生成的嵌套子查询）。防注入双保险： 表名/字段名过白名单，所有值一律 $N 参数绑定；分页每页最多 1000 条。 聚合也有：计数、分组计数、分组求和——"各区域有多少客户"一句话的事。

重点三：点"动作"按钮后发生了什么（五道闸）

闸门检查什么说明
1参数齐不齐必填参数缺了直接拦。
2FEEL 业务规则"金额 ≥ 1000 才许改派"这类规则算不过就拒绝；规则表达式写错了也算不通过（从严）。
3解析改动把"改哪些字段、建/删哪些关系"翻译成 5 种编辑原子（建/改/删/加关系/断关系）。
4权限这个按钮配置了谁能点？没资格直接拒。
5单事务落库改动 + 审计日志 + 副作用通知同一个事务：全成或全败，绝不出现"改了一半"。

执行前可点"试算"（dry-run）：先预演一遍"会编辑 N 条、触发 M 条副作用"，不动任何真数据。 副作用由后台派发器逐条投递（多节点用 FOR UPDATE SKIP LOCKED 抢任务，不重复不遗漏），失败标失败、可重试。

动作可以声明"办完正事后附带做什么"，共 6 种选项，按需组合：

选项干什么
起审批流调流程引擎，真实创建一条流程实例——点按钮就发起审批
算报表调报表服务，真实计算并落库（如关账动作顺手算关账报表）
回调外部地址把结果 POST 给外部系统的 URL（主机白名单管控，防乱调）
发通知按模板发一条通知，页面实时收到
发事件往本体的实时广播流发消息——别的页面听到就自动刷新
调函数触发本体里配好的函数，再算一段自己的逻辑

体感数字：该往地图上放多少东西

一张单据的 props 约 1~2 KB：10 万张单 ≈ 200MB（PostgreSQL 毫无压力），百万张 ≈ 2GB（存储扛得住， 但同步耗时、JSON 过滤没索引会开始疼）。所以挑着放：

数据种类量级进不进地图
主数据 / 参照（客户、物料、币种）千 ~ 十万全进——它们就是地图的主角
关键业务实体（订单头、凭证头）万 ~ 百万挑着进——同步 SQL 加时间窗控量
单据明细行 / 分录百万 ~ 亿不进——算数交给报表，地图只留"发生过"的线索
04

与主数据（MDM）、元数据怎么结合

INTEGRATION · 结合

分工一句话

MDM 负责"治理与发放"（申请 → 审批 → 落字典，保证主数据对）； 本体负责"关联与消费"（把主数据变成可被业务对象引用、可顺路钻取的"参照点"）。 cmx-model 的 DCT（字典定义）和 DOC（单据模型）是定义来源—— 本体导入它们，而不是取代它们；导入的对象类型会带来源标记（cmxOrigin），可回溯出身。

为什么是"同步拷贝"，不是"实时去主数据查"？

三个理由：① 关系钻取要数据都在本地，才能一条 SQL 出结果（实时跨库查做不了一跳三跳的穿越）； ② MDM 挂了不该影响本体看数（故障隔离）；③ 主数据"读多写少、变更有审批流程"，慢几分钟无碍。 代价是新鲜度 = 同步间隔；要准实时，就把同步挂到"审批落库"那一刻触发（见第 5 站 T2）。

四条现成通路（都有真机验证）

通路怎么干实测数据
① 字典导入
POST /import/dct
低频字典一次性接入		 把字典（DCT）一键转成参照对象类型：主键 = 字典 code、标题 = 字典名，字典项即对象，可直接进查询过滤。字典变了重新导入即幂等覆盖。 币种 Currency：USD / CNY / EUR 三项导入，返回 {seededItems: 3}；过滤 code=USD 能查到美元、查不到欧元（e2e 通过）。
② 漏斗源映射（主通道）
POST /funnel/sync/类型
主数据持续同步		 先建类型（如 MdmCustomer），再配"源表 → 字段映射"规则（读哪张表、哪列是主键、哪些必填），触发同步：好数据进本体，坏数据进隔离区。幂等覆盖，源变了再同步一次就更新。 同步 md_customer 表：读入 4 行、写入 3 行、1 行进隔离区（name 为空被拦下），返回 {read:4, written:3, quarantined:1}。
③ 单据模型导入
POST /import/doc		 把 DOC 主从实体图（头表 + 行表）批量建成对象类型 + 组合关系，明细行折叠为层块属性——不用手工重画。业务对象用 docType 标记对应哪种 MDM 单据。 一个"订单"模型 → 订单类型 + 明细层块 + 订单_明细 组合关系，导入即得；对象类型带 cmxOrigin 来源存证。
④ 动作起审批流
startBusinessProcess		 动作的副作用直连流程引擎真实创建流程实例——对主数据的治理操作（停用/合并/改主）定义成本体动作，点按钮就发起 MDM 审批。配置页的下拉框（选哪个流程/哪张报表）由本体代理查询隔壁服务自动填充。 真机验证：本体动作真的把流程实例建出来了、真的算了报表并落库；内置模板 objectApprove（对象审批）、consolClose（一个按钮同时起关账审批 + 算关账报表）。

推荐的落地配方（七步）

MDM 治理流程不动 → 低频字典走①导入 → 高频主数据（客户/物料/组织/科目）走②漏斗指向业务库表 → 业务对象用关系引用参照对象（订单→客户、凭证→科目）→ 外部定时调同步保新鲜 + 隔离区定期人工复核 → 需要治理的变更定义成动作（校验 + 乐观锁 + 起审批流）→ 发布固化版本、OSDK 生成前端代码包。

现状边界
目前同步是全量（无增量）、手动/外部触发（平台自己不会到点干活）、单向（MDM → 本体，改了传不回去）、 ①③两条导入通道目前连调用方都没有（模型中心不会自动推、本体不主动拉、界面也无入口——见第 5 站 T5）、 字典导入是快照式；漏斗的源查询会真实执行配置的 SQL——只允许可信管理员配置、只配 SELECT。

还存在哪些问题、要补哪些课

GAPS · 缺口

先说结论：地图画好了、数据能装能查、按钮能办事还能联动审批和报表，主体是能用的（351 项测试背书）。 短板集中在三处：安全上有两扇没关严的门；自动化是"手动挡"；版本与发布链路有两个断点（9-10 巡检新发现）。下面按优先级列账。

🔴 P0 · 两扇安全门（建议最优先修）

编号问题说明与对策
S1身份可自报调用方"自己说自己是谁"仍会被采纳，绕过行级权限和动作禁令——保安不查证件。9-10 部署姿态已收紧：四份配置鉴权 off→jwt，门户链身份来自验签的委托令牌；但代码层请求自报 subjects 仍未强制忽略，口子没关完。对策不变：网关剥离 subjects + 服务端一律从令牌推导身份。
S2漏斗的 SQL 注入面数据同步有一处拼接 SQL、且源查询语句任意填——全平台唯一不走参数化的地方，门都上锁就这扇窗没关。临时对策：仅管理员可配、只配 SELECT、端点不对普通用户开放。

🟡 P1 · 自动化缺口："门修好了，搬运工没有"

各种集成的"插座"都装好了，缺主动去插电的机制——全仓一个定时任务都没有，目前是"手动挡，踩一脚动一下"。

编号缺什么说明
T1定时调度器所有同步/派发都要人点或外部调接口才动，平台自己不会到点干活。
T2MDM 审批完自动同步主数据审批通过了，还得人来点同步。在审批落库回调里加一行"调同步"就是准实时——小改造、大收益。
T3审批结果回写本体动作能把"起流程"发出去，但流程审完通过/驳回，结果不会自动回来改数据——出去的单程票，没有回程。这是闭环缺的最后一段线。
T4增量同步现在搬运是"整批替换"，不能只搬上次之后变化的，大表同步费劲。加"上次同步时间"水位线即可。
T5DOC/DCT 反向导入无人接线「从元数据建本体」的两条通道（POST /import/doc、POST /import/dct）目前没有任何调用方：模型中心源码里对本体零引用、也没有对外 HTTP 客户端——它建元数据时根本不知道本体的存在；本体为保持解耦也只被动收归一化 JSON、不主动拉模型服务（不读 cf_*/cv_*）。接口就绪但只能手工调。接线二选一：模型中心 deploy 成功后回调导入接口（push），或设计器加"从模型中心导入"按钮（pull——拉 DocMetaView/DctQuery 适配成归一化 JSON 再送）。
T7本体 → MDM 回写数据单向流动，本体里改了传不回主数据系统，目前只能靠动作起流程间接治理。

🟡 P1 · 版本与发布链路的两个断点（9-10 巡检新发现）

发布机制"只完成了存、没完成用"，外加一个自出生就看不见的按钮。git 考古结论：两者都不是谁改丢的—— 按钮首次入库（cmx-container 90802ace）就渲染在 model 区，而门户工作区外壳从其 first commit（7a49742）起就把 model 区定位为永久隐藏服务区，属设计与门户形态的错位。

编号问题说明与对策
V1 发布按钮"隐身"，界面无发布入口 「📦 发布本体」按钮和"已发布 vX · rev"版本行渲染在四区工作台的 model 区，而门户把 model 区定位为"永远不显示的服务区"（hydrate 到隐藏容器，仅作数据/API 提供方）——按钮画出来了但永远不可见。目前唯一发布入口是直调 POST /publish。修复有现成先例：照 9-10 钻取面包屑的挪法（e60f1e12），把版本行 + 发布按钮挪进 content 工具条——state.versions 装载与 doPublish 发布逻辑零改动，纯渲染位置平移。
V2 版本表"只写不读"，OSDK 取草稿出码 发布快照存进 om_version（不可变、含全量定义 JSON）后，全库唯一读它的是人工查询接口 GET /versions/{n}——没有一个消费端真正从快照取数。最典型：OSDK 生成器（/osdk/typescript）读的是草稿表，生成的 SDK 随草稿漂移、不可复现——"发布 = 冻结合同"只做了一半。对策：加 ?version= 参数，缺省取最新发布版快照出码（snapshot 结构即生成器输入，零转换），从未发布过才退草稿并在响应头警告；改动集中在 osdk_handlers.rs。注意边界：设计器读草稿表是正确的（编辑工作台必须看到未发布草稿），动作执行读草稿也是正常语义——勿一并改掉。

🟢 P2 · 记在账上的性能与正确性债

编号问题说明
Q1JSONB 查询没索引字段值都塞一个 JSON 大字段（见第 2 站的省钱决定），按字段过滤是全表翻——数据量大了会慢。字段"要建索引"的标记已能配，但物理索引还没人建。
Q2删对象可能误删别人的线清理关系边时按业务键全局匹配，不同类型撞了主键值理论上会误删。对策：主键按类型加前缀隔离。
Q3发布并发撞车两人同时点发布，版本号可能撞（取最大值+1 没加锁）。
Q4金额精度表达式计算用浮点数，算钱可能出现 0.1+0.2≠0.3 的精度尾巴。对策：金额以"分"为整数或用区间判定。
Q5杂项接口文档比实际少约 15 个端点；实时广播断线重连会丢几条消息（可靠通知走发件箱不受影响）；图谱组件超大图会整幅重绘（先用分域折叠规避）。

压根还没做的能力（对企业用户的差距清单）

性能压测功能全测了（351 项），但"1000 人同时用 / 百万级数据"的压力测试一次没做。
