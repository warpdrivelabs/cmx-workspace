结论速览

VERDICT

总体判断：引擎内核（执行语义、版本 pin、实例迁移、事件投递、可观测性）已达到国内 BPM 产品的水准线，部分点甚至优于国内 SaaS 审批产品；但「审批业务面」（审批人规则、审批操作闭环、超时策略、消息触达）与国内标杆存在系统性差距，且若干缺口是正确性风险而非功能缺失。

结构性根因 · 唯一审批要素全部内联在 BPMN XML 里

办理人 / 审批方式 / 表单 / 抄送与流程结构共享同一条「改图 → 发版 → 实例 pin → 人工迁移」的重管道——高频运营变更被迫走低频结构变更的流程（§4 专项）。

正确性风险 · 三个不是少功能，是会出事的类型

加签不可减签（死锁）；空审批人静默兜底（任务走错人）；「或签」语义与国内惯例偏差（时效与预期不符）。

触达短板 · 最伤叙事任务不会主动找人

催办仅站内留痕、无 IM / 邮件 / 短信推送、无离岗代理规则——国内平台以「待办追着人跑」为标配，我们以「人登录门户看待办」为前提。

4

专项：审批配置与流程配置未分离

KNOWN ISSUE · DEEP DIVE
点名问题

改审批人 = 改图 = 发新版本

4.1 现状证据

UserTask 节点属性（cmx-flow-model/src/ir.rs）内联承载四类审批要素，随 BPMN XML 一起版本化：办理人（candidate 表达式，user/role/pos/dept/orgLeader/initiator/initiatorLeader）、审批方式（MultiInstance 会签 / 或签 + completion_condition）、表单（form_key / form_mode / form_fields 可写白名单）、抄送（节点级 cc 名单）。全部四项的变更都要走：

改 BPMN XML→ draft→ validate→ publish 版本 +1→ 在途实例 pin 旧版→ 逐实例人工迁移
组织调整一次，流程定义全员发一轮版；在途单要么走旧人、要么逐个实例人工迁移。

4.2 为什么是结构性缺陷，不是「用起来麻烦」

  • 变更频率错配：审批要素变更（换人、调字段权限、会签改或签）远高于结构变更（加节点、改路径）。高频变更压在低频变更的重管道上，运营成本随组织活跃度线性增长。
  • 版本语义被污染：版本号本应表示「流程结构的演进」，现混入「人员与表单配置的演进」；版本 diff 里充满与结构无关的噪音，追溯价值下降。
  • 在途实例两难：pin 保证快照一致性（好），但换来「新审批人生效要逐个 migrate」——instances/migrate 面向结构变更设计（节点映射校验），应对「只换个人」是杀鸡用牛刀。
  • 与扩展模型问题同根：引擎没有执行 / 任务监听器扩展点，「节点级行为定制」的一切诉求最终都落到改 XML 发版——未分离问题因此被放大。

4.3 国内标杆的解法对照

产品审批要素存放变更动作在途单行为
飞书 / 钉钉模板内独立「规则层」（表单化配置，非图纸属性）纯配置编辑，规则与结构分层存储发起时点快照，在途不变
金蝶苍穹审批人方案 / 参与人规则独立于流程模板，模板可复用方案换方案不改图策略按生效时间取
用友 NC审批人规则函数库 + 模板引用改函数 / 规则不发模板版同上
flowengine 现状全部内联 BPMN XML 节点属性必须改图发版pin 旧版，需人工 migrate

注意：「审批人是运行时求值」这一点我们已经做对了（cmx-flow-identity/src/resolver.rs 运行时解析表达式）——真正被冻结的是表达式字面量与参数（role(经理) 里的「经理」写死在 XML），以及会签方式、字段白名单、抄送名单。问题不在「求值时机」，在「配置的载体与版本管道」。

4.4 改造建议

方案 A · 推荐

审批策略层抽离

新增 cmx_flow_approval_policy（办理人规则 / 审批方式 / 字段权限 / 抄送）+ 独立版本与生效时间；UserTask 只留 policyRef（BPMN 扩展元素 cmx:policyRef 兼容既有 XML）；运行时按「发起时点快照或最新生效」（可配，默认快照）解析。改审批人 = 改策略 = 不发流程版本，自带审计回滚。

方案 B · 不推荐

参数热更新不走版本

保留内联，区分「结构变更 / 参数变更」——破坏快照语义，在途行为漂移不可审计，与国内标杆实践背道而驰。

方案 C · 兜底可并行

迁移自动化

保留 migrate 面向真正的结构变更；为策略变更提供「策略 diff → 自动生成迁移计划（仅重解析候选）」的批量工具作过渡期缓冲。

同根修复：在策略层落地的同一批工作中补任务 / 执行监听器扩展点（节点进入 / 离开、任务创建 / 分配钩子），把「一切定制 = 改图」的通道打开。

6

规划不合理与设计缺陷

ADVERSARIAL REVIEW

点击展开每一项的证据与建议。

6.1前后端契约脱节：画布可画引擎拒收的元素›

前端调色板含 ScriptTask 图标，而 compiler.rs 对 scriptTask 显式 Error::Unsupported——用户在画布上画得出、发布时才失败。同类问题：调色板宣称的元素集与 NodeKind 19 种之间缺一张契约测试。

建议由后端契约接口（/definitions/validate 已有）派生前端调色板可用项；加一条契约测试防漂移。

6.2「或签」语义偏差›

现实现：或签 = 顺序多实例（逐个传，第一人通过后不再派后续），且前端已明确以「或签」命名——调色板选项 { key: 'sequential', label: '顺序或签', hint: '逐个办理' }、节点徽章 text: '或签'（design-workbench.js / definition-workbench.js 同款）。国内惯例（飞书 / 钉钉）：或签 = 并发派发给所有人、任一人通过即整体通过（其余任务自动作废 / 收回）。逐个传在「第一人不在线」时阻塞整单，同名不同义是配置误导的直接来源。

建议并行多实例 + 首个完成即取消其余作用域（引擎已有 completion_condition 与 mi_scope 机制，具备实现条件）；过渡期至少把文案改为「依次审批（逐个办理）」，把「或签」一词留给未来的并发语义。

6.3空审批人静默兜底，与项目 fail-fast 哲学自相矛盾›

候选解析为空时 decide_assignment 宽容退回静态 assignee（也空则任务无办理人悬空）。本工作区刚在 Redis init 上确立了「配了就要、错了就停」的 fail-fast 裁定；同一哲学套到审批人上：解析不出人应该是 Incident（可见、可处置），而不是静默走错或悬空。

建议空候选默认落 Incident + 可配兜底策略（自动通过 / 转指定人 / 挂起）——与飞书「审批人为空特殊流转」页对齐。

6.4无监听器扩展点，定制 = 改图›

见 §4.4。国内企业级引擎（泛微节点前后动作、金蝶审批项后动作）均有节点级钩子；我们只有 serviceTask delegate 与事后事件订阅。「任务创建后自动做某事」这类最常见诉求现在做不了。

建议最小面先做任务监听器（created / assigned / completed 三事件 × HTTP / webhook 出口），复用 outbox 通道与订阅规则，不必新造分发机制。

6.5db-per-tenant 的规模化上限›

tenancy.rs 多租户 = 每租户派生独立库。与平台「平台库 / 业务库分离」哲学一致、隔离性最好，但租户数量大时（SaaS 场景）库数量爆炸、跨租户运营查询 / 统计需逐库扫。若 flowengine 定位是企业内部署（租户 = 法人 / 组织实体，个位数到两位数），现设计成立；若对标国内 SaaS（飞书 / 钉钉海量租户），上限明显。

建议明确写入 README「定位与边界」：本引擎面向企业级私有部署，租户 = 业务实体；不做海量 SaaS 租户。有定位声明，这个设计就是合理的。
