# cmx-form 页面投递路由统一复用方案

> 日期：2026-08-24
> 状态：评审中（已完成 3 轮评审，见第十一章）
> 涉及仓库：cmx-container（主改造）· cmx-rulesengine · cmx-report · cmx-flowengine · cmx-model · cmx-mdm · （cmx-portalservice 仅二期评估）

---

## 一、背景与问题

CMX 六个 Rust 主应用（portal :8080 / flow :8091 / report :8092 / rule :8094 / mdm :8095 / model-center）都需要对外投递**前端页面**：

- `GET  /api/native-pages`、`POST /api/native-pages/batch`、`GET /api/native-pages/{id}`
- `GET  /api/html-pages`、`POST /api/html-pages/batch`、`GET /api/html-pages/{id}`（部分应用）

门户（portal）侧已有完整实现链：存储设施 `cmx-jsonstore` + 服务层 `cmx-form::pages::{native,html}` + HTTP 层 `cmx-common-api/handlers/portal/pages.rs`。但引擎微服务无法直接复用：

| 复用障碍 | 说明 |
|---|---|
| `cmx-jsonstore` 无 HTTP 能力 | 定位是纯存储基础设施（原子读写 / moka 缓存 / rev 锚点），无 axum 路由 |
| `cmx-form` 有 service 无路由 | 只暴露 `list_native_pages_paged()` 等 Rust 函数，Cargo.toml 无 axum 依赖 |
| 门户 HTTP 层不可引 | `cmx-common-api` 是门户专属契约层，拖出全量 handler 依赖，违背引擎 app 最小依赖原则 |
| 数据布局差异 | 引擎页面资产目录与门户不同（`web/ui-native` vs `data/native-pages`；有 `sources/` 子目录变体） |

结果是五个引擎主应用各自复制了一份"只读页面投递"实现，**共约 1730 行重复代码**，且已出现行为分叉（见下章差异矩阵）。任何契约修订（如新增字段、修 null 解析缺陷）都要改五处。

### 2.2 已发现的行为分叉（重复的代价）

1. **错误体 code 分裂**：rule/flow 的 NotFound 响应体 `{code:4,msg:...}`；mdm/model/rpt 经 cmx-api-types 输出 `{code:404,...}`。HTTP status 一致（404），body code 不一致。
2. **null 容错缺失**：mdm 版为索引行 `doc:null` 等显式 null 加了 `null_str` 反序列化兜底；flow/rule/rpt 版只有 `#[serde(default)]`（只兜缺失不兜 null），存在同源数据解析失败的潜在缺陷。
3. **batch 形态与门户不一致**：引擎 native batch 返回 `{items:[...]}`；门户自身 batch 返回 `{pages,revs,errors}` 且支持 `clientRevs` 差异同步。两套并存（本方案**不**强行合并，见 §4.4 决策 5）。

## 三、目标与非目标

### 3.1 目标

1. 页面只读投递（native + html 全部六个端点）**收敛到 cmx-container 公用库一处实现**，落点 `cmx-form` 新增 `serve` 模块。
2. 五个引擎仓删除各自副本，装配收敛为一行 `merge(...)`，净删 ~1700 行。
3. **逐字节兼容**：迁移前后各端点响应（成功体 + 错误体）保持一致，门户 F3 反代与 shell 零感知。
4. 收编过程中顺带修复 §2.2-2 的 null 容错缺陷（对 rule/rpt/flow 生效，属缺陷修复而非行为破坏）。
5. 差异（目录布局 / 是否投 html / 错误码语义）全部**配置化**，不再靠复制分叉。

### 3.2 非目标

1. **不改门户自身读写路径**：`cmx-common-api/portal/pages.rs` 与 `cmx-form::pages` 现有 save/list 函数原样保留。门户读路径切到 serve 模块列为后续独立课题——因门户 batch 响应形态（`{pages,revs,errors}`+clientRevs）与引擎形态不同，合并需先做 shell 兼容性分析。
2. 不引入 moka 缓存：引擎现状是每请求直读磁盘，保持不变（缓存作为后续优化项，不在本次范围）。
3. 不动 `/html-pages`、`/native-pages` 的 URL 与方法（既有契约，豁免 §四.6 新接口规范约束）。
4. 不做 OpenAPI 注解：现有五份副本均无 `#[utoipa::path]`，保持现状。

## 四、总体设计

### 4.1 为什么落点是 cmx-form（备选对比）

| 候选 | 结论 | 理由 |
|---|---|---|
| **cmx-form** ✅ | 采用 | crate 自述即"html_pages 相关页面资源服务"；DTO `NativePageFull` 权威定义在此；service 函数在此；只缺 HTTP 层这一块拼图。新增依赖仅 axum + cmx-api-types + cmx-utils |
| cmx-jsonstore | 否决 | 打破循环依赖而生的纯 base crate（lib.rs 文档明示定位），塞路由污染抽象 |
| cmx-common-api | 否决 | 门户专属契约层，依赖面过大 |
| 新建 cmx-page-serve | 否决（用户决策） | 可收编进既有职责匹配的 crate，无需新仓 |
| cmx-biz / platform-app | 否决 | 业务域/平台装配层，职责无关 |

依赖方向核验：五个引擎 app 现已通过 path 引用 cmx-container 多个 crate（如 mdm-app 引 cmx-biz/cmx-utils），新增对 cmx-form 的引用无方向障碍；axum 本就是各引擎 app 直接依赖。

### 4.2 模块结构（cmx-form 内新增，存量不动）

```
crates/libs/cmx-form/src/
├── lib.rs                 # 增一行 pub mod serve;
├── pages/native.rs        # 存量保留（门户写路径 + 门户布局读取）
├── pages/html.rs          # 存量保留
└── serve/                 # ★ 新增：通用页面只读投递
    ├── mod.rs             # 对外 API 面
    ├── config.rs          # PageServeConfig / NativeLayout / HtmlLayout / from_assets()
    ├── error.rs           # PageServeError（内部中性错误，2 变体）
    ├── loader.rs          # 索引/分片/源文件加载 + 安全拼接 + rev 计算
    └── routes.rs          # frontend_pages_routes<S, E>(cfg) -> Router<S>
```

### 4.3 核心 API 定义

```rust
// serve/config.rs
/// native 源文件相对 ui_dir 的布局。
pub enum NativeLayout {
    /// relPath 直接落在 <ui_dir>/ 下（rule / report / flow 现状）。
    Flat,
    /// relPath 相对 <ui_dir>/sources/ 子目录（mdm / model 现状）。
    SourcesSubdir,
}

/// html 投递开关与布局。
pub enum HtmlLayout {
    /// 不注册 html-pages 路由（rule 现状）。
    Disabled,
    /// v2 分片索引：manifest index.json + index/<domain>.pages.json。
    ShardedV2 {
        /// 源文件布局：Flat=落 html_dir 根（report/flow 现状）；SourcesSubdir=落 sources/（mdm/model 现状）。
        source_layout: HtmlSourceLayout,
    },
}

pub struct PageServeConfig {
    pub native_dir: PathBuf,
    pub native_layout: NativeLayout,
    pub html: HtmlLayout,
}

impl PageServeConfig {
    /// 按 [assets] 统一段解析目录（ConfigManager → env 直读兜底 → 默认值），
    /// 收编五份副本中逐字相同的 assets_dir() 逻辑。
    pub fn from_assets() -> Self { ... }
}
```

```rust
// serve/error.rs —— 内部中性错误（thiserror）
pub enum PageServeError {
    /// relPath 非法（越界 / 空段）。
    BadRequest(String),
    /// 页面或源文件不存在。
    NotFound(String),
}
```

```rust
// serve/routes.rs —— 唯一装配入口
/// 前端页面只读路由。E 由各引擎自持，保住各自的错误体字节：
/// - mdm/model/report：E = cmx_api_types::Error（crate 提供默认 From<PageServeError>）
/// - flow/rule：E = 各自 FlowError / RuleError（各仓补 3 行 From impl，映射回 code=4 语义）
pub fn frontend_pages_routes<S, E>(cfg: PageServeConfig) -> axum::Router<S>
where
    S: Clone + Send + Sync + 'static,
    E: IntoResponse + From<PageServeError>,
{ ... }
```

handler 成功体统一用 `cmx_api_types::ApiResp<T>`（三仓已在用，rule/flow 自持 ApiResp 与之 wire 等价——字段相同且 `pagination` 为 `skip_serializing_if = "Option::is_none"`，成功响应序列化结果逐字节一致）；错误体由 E 决定，从而**同时保住两种历史错误码语义**（§2.2-1 的分裂被显式建模而不是悄悄统一）。

### 4.4 关键设计决策（评审定稿）

| # | 决策 | 理由 |
|---|---|---|
| 1 | 不新增 crate，扩展 cmx-form | 用户决策 + 职责自洽（§4.1） |
| 2 | 错误经泛型 E 映射，不强推 cmx-api-types 错误码 | 保住"零感知"硬契约：rule/flow 的 `{code:4}` 与 mdm/model/rpt 的 `{code:404}` 都不被改变；错误码全 fleet 统一另立课题 |
| 3 | 布局差异收敛为枚举配置 | 五副本唯一实质差异就两项（sources/ 子目录、html 开关），枚举表达完备 |
| 4 | 每请求同步读盘、无缓存 | 与五副本现行为完全一致（它们就是每请求 std::fs 读）；引入 moka 会改变失效语义，留作后续优化 |
| 5 | 引擎 native batch 保持 `{items}` 形态 | shell 现网消费的就是这个形态；门户 `{pages,revs,errors}`+clientRevs 形态不并入（非目标 §3.2-1） |
| 6 | null_str 容错全布局生效 | 缺陷修复：manifest 显式 `null` 字段不再导致整分片静默清空 |
| 7 | rev 计算复用 `cmx_jsonstore::cache::content_rev` | 同算法（xxh64 seed=0 → 16hex），消灭第五份拷贝；cmx-form 已依赖 jsonstore，零新增依赖 |
| 8 | 目录越界防护沿用"分段拒绝 `..`/空段"并抽公共 `safe_join()` | 与五副本现行算法一致；`jsonstore::util::resolve_within` 语义不完全等价（允许空段），不混用 |
| 9 | 索引/分片读取失败降级空集 + tracing warn | 行为保持降级哲学，但补上五副本缺失的可观测性（静态模板 + 结构化字段，合规 AGENTS.md §二） |
| 10 | 不加 feature 门控 | cmx-form 下游（portal 等）本就有 axum，默认编译进去最简单；避免 feature 矩阵复杂度 |
| 11 | 泛型 `<S>` 保留 | 与各引擎现有 `Router<S>` 装配方式同构（现均传 `()`） |

### 4.5 各引擎装配后形态

1. 删除 `native_pages.rs` / `frontend_pages.rs` 整文件及 `lib.rs` 中 `pub mod` 声明。
2. `<app>/Cargo.toml`：新增 `cmx-form = { workspace = true }`（跨 ws path，各根 Cargo.toml 补一行 `[workspace.dependencies]`）；**迁移后核删** `xxhash-rust`（已核实 mdm-app / rule-app 中仅 native_pages 使用）。

4. rule / flow 额外：在 resp.rs 或新文件补 `impl From<PageServeError> for RuleError/FlowError`（NotFound→not_found，BadRequest→business，共 ~8 行）。

净变化估算：cmx-container +~450/-0；五仓合计 -~1730/+~120。

### 5.3 明确不动

## 七、测试计划

### 7.1 cmx-form 单元测试（tempdir 构造资产目录）

1. **loader**：Flat 与 SourcesSubdir 双布局取源码；v2 manifest+分片解析；`doc:null` 容错（回归 §2.2-2）；索引缺失/坏 JSON → 空集不 panic。

## 八、风险与回滚

| 风险 | 等级 | 缓解 |
|---|---|---|
| 成功体字段序/内容漂移破坏 shell | 高 | golden 快照 + 逐字节 diff 门禁（S0-S5 每步必过）；DTO 直接搬运现有定义不重排 |

| 回滚 | — | 每步独立提交；回滚 = revert 该仓 commit，serve 模块留存不影响存量 |

## 十一、评审记录

### R1 架构评审（crate 定位 / 依赖方向）

| 发现 | 处置 |
|---|---|
| 初稿曾考虑把路由放进 cmx-jsonstore（feature 门控 axum） | 否决：污染纯存储 base 定位 → 改落 cmx-form（决策 #1/#10 固化） |
| cmx-form 引 cmx-utils 是否拉重依赖 | 核验：cmx-utils 是平台基础配置库，五个引擎 app 与 mdm-app 均已直接依赖，无传递膨胀 |
| 二期"门户读路径也切过来"表述过强 | 降级为非目标：门户 batch 形态不同，贸然切换会破坏 shell（§3.2-1） |

### R2 兼容性评审（字节对齐硬契约）

| 发现 | 处置 |

## 十二、修订记录：R4 评审 —— 页面资产目录规范 v2（用户评审，2026-08-24）

### 12.1 修订动机

用户评审指出：布局枚举（`NativeLayout::{Flat, SourcesSubdir}`）把**磁盘布局知识固化进了代码**。
目标态应是"多应用合并单体时，拷贝页面目录 + 重新生成 index.json 即可"，因此：

1. **relPath 一律相对索引文件所在目录解析**——加载器不感知任何布局约定；
2. **每个服务在页面根下有自己名称的子目录**（如 `rule/`、`flow/`、`portal/mdm/`），index 里路径形如 `mdm/xxx.js`。

> 本节修订**取代** §4.3 的 `NativeLayout` / `HtmlSourceLayout` 与 §4.4 决策 #3。

### 12.2 页面资产目录规范 v2

```text
web/ui-native/                     # native 页资产根
├── index.json                     # 唯一索引 {"version","pages":[...]}；relPath 相对本文件
├── <svc>/                         # 服务自有页：rule/ rpt/ flow/ portal/mdm/ ...
├── <domain>/                      # 跨服务共享业务域页（如 fi/，与页面 id 域前缀一致）
└── vendor/                        # 跨服务共享构建产物（允许）

web/ui-html/                       # html 页资产根
├── index.json                     # v2 manifest {"domains":[...]}
├── index/<domain>.pages.json      # 域分片；行内 relPath 相对 ui-html 根（manifest 所在目录）
└── <domain>/...                   # 源文件同样相对 ui-html 根
```

硬约束（loader 强制）：
- relPath 相对索引文件所在目录；拒绝 `..` 越界与空段；
- 服务自有页放 `<svc>/`；共享域页沿用 `<domain>/`；共享构建件放 `vendor/`。

合并单体操作：把各服务的 `<svc>/`（及其引用的 `<domain>/`、`vendor/`）拷入目标根 →
合并各 `index.json` 的 `pages` 数组（html 合并 manifest 的 `domains` 清单）重新生成索引。零代码改动。

### 12.3 现状与迁移盘点（磁盘实勘）

| 仓 | native | html | 迁移动作 |
|---|---|---|---|
| cmx-rulesengine | ✅ `rule/ vendor/` 已合规 | — | 无 |
| cmx-report | ✅ `rpt/` 已合规 | ✅ `fi/` 相对根 | 无 |
| cmx-flowengine | ✅ `flow/` 已合规 | ✅ `fi/` 相对根 | 无 |

关键结论：mdm/model 只需把 `sources/` 这一层搬平，**index/shard 中 relPath 一个字都不用改**
（搬平后 relPath 正好指向根下真实位置）。响应字节完全不受影响，golden 对比仍逐字节一致。
