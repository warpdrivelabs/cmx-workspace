# 三类服务通信配置的关系总结：`[rpc]` / `[center_client]` / `SERVICE_REGISTRY_*`

> 日期：2026-08-22 · 依据代码现状整理（cmx-container：cmx-registry-config / cmx-rpc / cmx-plugin / cmx-service-base）
> 回答三个问题：各是什么、彼此什么关系、什么场景需要配合/可独立。

## 一、总览：一个金字塔三层

```
┌─────────────────────────────────────────────────────────────────┐
│ 第 1 层【环境变量】注册中心基础设施（SERVICE_REGISTRY_* / NACOS_*）   │
│   服务注册（把自己挂进 Nacos）· 实例缓存（查"服务名→实例列表"）·        │
│   配置中心（远程 toml 热更）                                        │
│   纯 env 驱动，init_infra() 初始化 —— 比 ConfigManager 更底层        │
└───────────────┬─────────────────────────────┬───────────────────┘
                │ 提供 GlobalServiceInstanceCache │ 提供 GlobalServiceRegistry
    ┌───────────▼──────────┐      ┌─────────────▼────────────────┐
    │ 第 2 层【toml】[rpc]   │      │ 第 2 层【toml】[center_client] │
    │ gRPC 通信子系统        │      │ 服务间调用与反代的"拨号规则"      │
    │ · 服务端：本进程对外    │      │ · 调谁：services.{key}        │
    │   暴露 gRPC 服务       │      │ · 怎么找：url 静态 / discovery │
    │ · 客户端：GlobalRpc-   │      │ · 什么协议：transport         │
    │   Client（服务发现拨号）│      │   = http | grpc（仅导入调用）  │
    │ · warmup_services 预热 │      │                              │
    └──────────────────────┘      └──────────────────────────────┘
```

一句话定位：**注册中心是"电话簿"（谁在哪），`[center_client]` 是"拨号规则"（打给谁、怎么找号码、用电话还是微信），`[rpc]` 是"微信通道本身"（gRPC 服务端 + 客户端设施）**。

## 二、各自职责速览

| | `[center_client]`（toml） | `[rpc]`（toml） | `SERVICE_REGISTRY_*` / `NACOS_*`（env） |
|---|---|---|---|
| **管什么** | 调用**目标**：每个服务键的定位与传输 | gRPC 通信**设施**：服务端端口 + 全局客户端 | 基础设施：注册、发现缓存、远程配置 |
| **谁消费** | remote_importers（菜单/权限/表单导入）、flow/report/rules 三反代壳 | gRPC 调用链（`resource_data_client()` 等）、被 gRPC 调用的一方 | 所有需要服务名→实例的组件；配置中心合并 |
| **配置粒度** | per-key（`services.{key}` 自由表） | 进程级（一套 gRPC server + client） | 进程级（本进程注册一个实例） |
| **关键项** | `services.{key} = { url \| discovery, transport }`、`default_transport` | `enabled`、`protocol = "grpc"`、`grpc.port/timeout_ms/retry_count`、`warmup_services` | `NACOS_ENABLED`（主开关）、`NACOS_NAMING_ENABLED`（注册）、`NACOS_CONFIG_ENABLED`（配置中心）、`SERVICE_REGISTRY_NAME/PORT/TYPE/GROUP/CLUSTER/WEIGHT`、`NACOS_SERVER_ADDR/NAMESPACE/USERNAME/PASSWORD` |
| **为什么在 env 不在 toml** | — | — | 它先于 ConfigManager 存在：注册中心本身要给 ConfigManager 提供远程配置源，不能依赖自己的产物 |

## 三、依赖关系：谁需要谁

**只有一条硬依赖链：`[rpc]` 和 `discovery` 定位都 → 注册中心基础设施。**

| 你配了什么 | 需要注册中心吗 | 需要 `[rpc]` 启用吗 |
|---|---|---|
| `center_client.services.{key}.url` + http（静态 HTTP） | ❌ 完全独立 | ❌ |
| `center_client.services.{key}.discovery`（HTTP 服务发现选例，含反代） | ✅（实例缓存） | ❌ |
| `center_client.services.{key}.transport = "grpc"`（gRPC 导入） | ✅（gRPC 客户端经服务发现拨号） | ✅（`GlobalRpcClient` 由 `init_rpc` 创建，未启用时报"RPC 未初始化"） |
| `[rpc] enabled = true`（做 gRPC 服务端 / 被别人 gRPC 调用） | ✅（`init_rpc` 直接取 `GlobalServiceInstanceCache::get()`） | —（它自己就是 rpc） |
| 配置中心（`NACOS_CONFIG_ENABLED=true`） | 它就是注册中心的一部分 | ❌（语义独立，只影响配置来源） |

代码依据：
- `cmx-service-base/src/rpc.rs::init_rpc`——`enabled && protocol == "grpc"` 才初始化，第一步就 `GlobalServiceInstanceCache::get()`（`init_infra` 的产物）；
- `cmx-plugin/center_client/upstream.rs::resolve_service_base`——discovery 定位查全局实例缓存（未初始化返回 `None` → 503，不 panic）；
- `remote_importers` 的 gRPC 分支——`GlobalRpcClient::is_initialized()` 未初始化直接报错。

## 四、两两关系详解

### `[center_client]` × `[rpc]`

- `center_client` 的 `transport = "grpc"` 是 `[rpc]` 客户端设施的**使用者**：导入器 `send/list` 按键分派到 `send_via_grpc`，底层走 `cmx_resource_rpc::resource_data_client()`（volo 客户端，经服务发现拨号）。
- 反向无关：反代壳（flow/report/rules）**永远 HTTP** 透明转发，`transport` 对反代键无效（配了打 warn）。
- gRPC 键必须配 `discovery`（服务名路由），配 `url` 无效（启动 warn）。

### `[center_client]` × 注册中心

- 只有 `discovery` 定位的键消费注册中心的**实例缓存**（healthy 过滤 + 按 Nacos `weight` 加权随机选例 + `http_port` 元数据优先，与 gRPC 路径 volo 加权语义对齐）。
- 门户启动时 `warm_proxy_upstreams()` 遍历 `services` 表全部非空 `discovery` 键做订阅预热（首拉填充缓存）。

### `[rpc]` × 注册中心

- **客户端方向**：gRPC 客户端经 `RegistryAwareDiscover` 从注册中心解析目标实例（`grpc.default_group/default_clusters` 参与过滤）。
- **服务端方向**：`grpc.port` 监听的本进程 gRPC 服务，要被别人调到需注册中心把该端口广播出去（注册实例的端口/`http_port` 元数据对齐实际监听端口）。
- **`warmup_services`**：启动时预订阅这批服务名、提前填充实例缓存（消除首次调用冷启动延迟）。它是 gRPC 通道自己的预热清单；`center_client` 的 discovery 键预热由 `warm_proxy_upstreams()` 负责——**两套预热各管各的通道（gRPC / HTTP），服务名重叠时订阅幂等，无冲突**。

## 五、典型部署形态（配置组合速查）

| 形态 | 注册中心 env | `[rpc]` | `[center_client]` |
|---|---|---|---|
| ① 单体全内嵌（默认） | 全关 | `enabled = false` | `services` 空表 |
| ② 三微服务 + 静态反代（当前 dev/portal-server） | 全关 | `enabled = false` | `flow/report/rules + menu/perm/form` 全配 `url`（http） |
| ③ 微服务 + Nacos 服务发现 | 开（各服务自注册：`NACOS_ENABLED=true` + `SERVICE_REGISTRY_NAME/PORT`） | 可关（纯 HTTP 反代） | 各键配 `discovery`（http） |
| ④ 中心服务 gRPC 导入 | 开 | `enabled = true`，`warmup_services` 填目标服务名 | 目标键 `{ discovery = "...", transport = "grpc" }`（或全局 `default_transport = "grpc"`） |
| ⑤ 本进程对外提供 gRPC 服务 | 开 | `enabled = true`（`grpc.port` 为对外端口） | 不相关 |

## 六、易混淆点备忘

1. **两个"Nacos 开关体系"**：`SERVICE_REGISTRY_*` 是新前缀，`NACOS_NAMING_*` 是旧前缀，同名语义取新优先（如服务名 `SERVICE_REGISTRY_NAME` > `NACOS_NAMING_SERVICE_NAME`）；主开关 `NACOS_ENABLED` 一刀切两中心，子开关 `NACOS_NAMING_ENABLED`（注册，默认 true）/ `NACOS_CONFIG_ENABLED`（配置中心）分治。
2. **三个端口别混**：`SERVICE_REGISTRY_PORT`（注册进 Nacos 时广播的端口，必须与实际监听对齐）＞ `http_port` 实例元数据（HTTP 选例优先取它）＞ `rpc.grpc.port`（本进程 gRPC 监听）。
3. **配置加载层级**：注册中心 env 先于 toml 生效；配置中心开启后 toml 值 = 本地 toml ← 远程 toml ← env（env 最高）。`[center_client]` / `[rpc]` 都可被远程配置中心覆盖。
4. **`protocol = "grpc"` 是 `[rpc]` 唯一支持的值**（其余值 warn 后跳过初始化）；HTTP REST 字段（`http_rest`）是预留占位未实现——HTTP 调用不走 `[rpc]`，走 `center_client` 自己的 reqwest。
