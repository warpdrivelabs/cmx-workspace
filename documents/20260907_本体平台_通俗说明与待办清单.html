CMX 本体平台（cmx-ontology :8097）· 通俗版

大白话版本体平台是什么、怎么用、怎么接、还欠什么

这份文档不讲术语堆砌——每个词第一次出现都配大白话和类比（地图、快递单、冰箱），覆盖：它是干嘛的、数据怎么存、主数据和第三方怎么接进来、动作/流程/校验怎么配合，最后列出代码里还没有做、但迟早要做的事。技术细节版见另外五份说明文档。

一、一句话：本体平台是干什么的

本体平台就是给企业数据画一张"地图"，并提供在地图上"导航"和"办事"的能力。

百度地图本体平台
地点（餐厅、公司）对象（客户、订单、凭证、科目）
道路（连着两个地点）关系（"客户下单"连着客户和订单）
导航："从这里出发能到哪"查询："这个客户的订单里金额超 1 万的有哪些"（顺关系钻取）
在地点上办事（预约、下单）动作（"停用这个客户"= 校验+改状态+发审批，一个按钮）

它不是又一个业务系统：不替你记账、不替你审批、不替你算报表。MDM 管主数据对不对、流程引擎管审批怎么走、报表管算数——本体负责把它们连起来，让你在一个地方看全景、顺着关系查、按一个按钮办事。

三、术语表（每个词都翻译成人话）

术语代码里叫大白话
本体Ontology那张"企业数据地图"本身：有哪些东西、什么关系，登记成一套统一定义
对象类型ObjectType地图上的"地点种类"——客户、订单这类模板。有名字、属性清单、主键，归哪个域哪个模块
对象（实例）Object按模板填出来的一条真实数据：客户"北方贸易"就是客户类型的一个对象
关系LinkType / 边地图上的"道路"：客户—下单—>订单。带方向、带基数（1 对 1 / 1 对多 / 多对多）、两端各有一个角色名（places / placedBy）
pk（主键）primaryKey对象的"身份证号"，一表内绝不重复；建关系、定位对象全靠它。统一存成字符串
title（标题）titleProperty对象的"给人看的名字"（列表里显示"北方贸易"而不是一串编号），从指定属性自动抄一份单独存
props（属性包）props JSONB对象的"全部家当"：所有业务字段塞在一个 JSON 里（快递单 = pk 是单号、title 是收件人、props 是箱子里所有的货）。字段是建模时动态定的，所以不建一堆列
层块array / struct 属性单据的"行"塞进 props 的姿势：订单的明细行折叠成一个嵌套数组——一张单据一个对象，行不单独成对象
DAM 分类dam每个对象类型归入"域▸应用▸模块"三级文件夹，前端图按此折叠，大图不乱
接口Interface横切能力标签："可定位物""可审批物"。对象说"我实现它"，图上画一条虚线。它不是网络接口，是类型上的契约
共享属性SharedProperty全局标准字段（币种、金额）：一处定义，各对象类型引用，避免各写各的
动作ActionType地图上的"办事按钮"：参数 → 规则校验 → 要改什么 → 办完通知谁，一个定义全包，全程留痕
FEEL 校验validations点按钮前系统替你把关的业务规则（"金额≥1000 才许改派"）。表达式算不出 true 就直接拒绝，数据一下不动；表达式写错了也算不通过（从严，宁误拦不放病）
副作用 / 发件箱sideEffects / outbox动作办完要通知的后续（起审批、发 webhook、算报表）。先登记后投递——对方系统挂了也不拖死你的操作，排队补发，每一步可查
函数Function一段可复用的计算（"延误风险 = 金额大于 1000 则 0.8 否则 0.2"），用 FEEL 小语言写，配置即生效
对象集 / 顺关系查ObjectSet / SearchAround导航指令："从这些客户出发，沿'下单'这条路，过滤金额≥1000"。写成代数表达式，系统编译成一条 SQL，一次往返出结果
发布 / 版本publish / version把整套定义拍照存档，版本号只增不改，随时回看任意历史版本的全貌（像代码打 tag）
三态生命周期status类型的三支队伍：试验（新建默认）→ 激活（稳定可用）→ 废弃。图卡片描边颜色跟着变
乐观锁modify + expectedUpdatedAt防两人改同一条数据互相覆盖：保存时对一下"我读的时候最后修改时间还是不是那个"，不是就返回冲突让你刷新重来
漏斗 / 源映射funnel / mapping把外部表的数据灌进本体的管道：配"读哪张表、列怎么映射、主键怎么拼"，触发同步后好数据进本体、坏数据进隔离区
隔离区quarantine同步时的"不合格品区"：主键为空、必填缺失的行连同原因放这里，人工复核，不污染主数据
参照对象reference object从主数据/字典同步进来的"标准参照点"（币种、客户主数据），业务对象引用它而不是各自存一份
OSDKosdk/typescript一键生成前端用的 TypeScript 客户端：对象变 interface，查询/动作变方法，前后端字段自动对齐
SSE 事件流events本体的"广播喇叭"：发布、动作执行等事件实时推给订阅方（刷新统计、联动页面用）

四、数据怎么存的（没有图数据库）

逻辑上是图，物理上就是 PostgreSQL 的三组表——没有 Neo4j，不引入新数据库品种：

── ① 定义层：登记"有哪些东西、什么关系"（6 张 om_* 表）──
om_object_type   客户有哪些属性、主键是谁……
om_link_type     "客户下单"是 1:N、角色叫 places……

── ② 对象数据：每种类型一张表，第一次写入时自动建 ──
oo_Customer
  pk   | title    | props (JSONB)                          | updated_at
  "1"  | 北方贸易 | {"id":1,"name":"北方贸易","region":"north"} | ...
   ↑身份证   ↑人看的名        ↑全部家当(箱子里的货)          ↑防两人打架的时间戳

── ③ 关系数据：所有关系共用这一张"边表" ──
ol_edge
  link                | a_pk | b_pk
  customerPlacesOrder | "1"  | "101"     ← 一行=一条边："1号客户 下了 101号订单"

要点三条：属性全塞 props 一个 JSON 列（字段动态定，不用改表结构）；加新关系不用建任何表（边表通吃）；不建外键（靠索引+代码维护）。"图查询"就是 SQL 里的 IN/JOIN：三跳查询也被编译成一条 SQL，数据库一次往返。

业务单据塞不塞？——能塞 ≠ 自动全塞

两个问题要分开："能不能塞"——能，一张单据一个对象，头字段平铺、明细行折叠成嵌套数组（层块），这条路是通的；"会不会自动塞"——不会，本体不会自己去业务库拉数据，不配同步就一张都不进来，塞多少由配置说了算（冰箱能放肉，但肉不会自己跑进冰箱）。

数据量级进不进
主数据/参照（客户、物料、科目）千~十万全进，没压力
关键业务实体（订单头、凭证头）万~百万挑着进（同步 SQL 加时间窗/条件）
单据明细行（分录）百万~亿不进，算数走报表系统
聚合结果（客户月度汇总）千级进，小而准

体感数字：一张单据 props 约 1~2KB，10 万张 ≈ 200MB（PG 毫无压力），百万张 ≈ 2GB（存储扛得住，但同步耗时、JSON 过滤无索引、边表 JOIN 会在"百万级"这道坎开始疼）。地图不需要存每辆车跑过的轨迹。

要同步（拷贝一份），不是查询时实时去 MDM 取。为什么：关系钻取要数据都在本地才能一条 SQL 出结果；MDM 挂了不该影响本体看数；主数据"读多写少变更有流程"，慢几分钟无碍。代价是新鲜度=同步间隔——要准实时，就把同步挂到"审批落库"那一刻触发（见待办清单 T5）。

四条现成通路：① DCT 字典导入（低频字典一键变参照对象+种子项）；② 漏斗同步（主通道：配源映射→定时同步→坏数据进隔离区，幂等可重跑）；③ 单据关联（对象类型挂 docType 标明对应哪种单据）；④ 动作↔审批流（治理闭环）。单向：MDM→本体，回写暂无。

六、第三方系统的单据怎么接进来（两条门）

姿势怎么走适合
门一：API 直推先建对象类型（一次），第三方在单据落库后调 POST /objects/{类型}/batch 推数据、POST /links 挂关系。pk 用第三方的单据号——重推=覆盖，天然防重对方有开发能力；准实时
门二：中转表+同步第三方数据先落到本体读得到的库的一张中转表（ETL/导出都行），配一条漏斗源映射，定时触发同步。脏数据自动进隔离区，SQL 里随手加时间窗控量对方是黑盒只能给数据；定时批量
代码现状：门都修好了，搬运工没有。两条门的每个端点都已实现并有真机测试（QA 脚本就是姿势一的参考实现）；但没有定时器、没有消息队列监听、没有现成连接器——cron 要自己挂，MQ 要自己消费转投。

七、本体怎么"伸手"操作外部，流程是干嘛的

本体伸手的出口只有一个：动作的副作用，共五种，全部经"发件箱"投递（先登记后发送，对方挂了不拖死你，全程留痕可查）：

副作用伸向谁大白话
webhook任意第三方往对方 URL POST 一段 JSON（有域名白名单管控）——操作第三方的直接通道
startBusinessProcess流程引擎起一条审批流，把对象 pk 当 businessKey 带过去
computeReport报表服务触发一张报表计算
callFunction本体内部调一个 FEEL 函数
emitEvent订阅方SSE 广播事件

流程（flowengine）的作用 = 治理环：本体管"机器敢不敢做"（FEEL 校验+权限），流程管"人同不同意"。停用大客户这种事，副作用走"起审批流"而不是直接 webhook 通知——审批人在待办中心看到"这是 1 号客户，金额多少"，点通过或驳回。

闭环现状（如实）：本体→流程目前是单向发起，"审批通过后自动回来改对象"的回路没有内置。两种落地姿势：先审后改（动作只起流程，通过后由流程侧回调本体 API 落实修改——MDM 变更申请就是这个模式，缺的只是"流程完成→调本体"一小段接线）；先改后审（当场改+起流程备案，适合低风险操作）。

FEEL 是国际标准 DMN 配的官方表达式语言（Camunda/Flowable/规则引擎同款），能写 amount >= 1000、amount in [100..100000]、count(items) >= 1、some item in items satisfies item.qty > 0 这类规则，外加 28 个内置函数。规则是配置不是代码——设计工作台里改完即生效，不用发版。算不出 true（含表达式写错）一律拒绝：宁误拦，不放病。

九、怎么上手（10 分钟路径，服务已在跑）

  1. 浏览器开 http://127.0.0.1:8097/——免登录建模控制台，看地图上已有什么；
  2. 门户（:8080）→ 菜单"数据平台 → 本体"→ 设计工作台：左边类型树、中间关系图、点"+ 对象类型"建一个试试；
  3. 对象浏览器：选类型看数据，点对象沿关系钻一圈；
  4. 对象工作台：选中对象，右侧"可执行的动作"按钮点一下——动作是什么就懂了。

十、三个页面操作手册（点哪里）

入口：门户（:8080）→ 菜单「数据平台 → 本体」下的三个节点。三个页面共用同一套四区布局：上=model 条、左=explorer 区、中=content 区、右=property 区。

10.1 设计工作台（建模：画地图）

建对象类型：左侧底栏「+ 对象类型」（或中间工具栏同款按钮）→ 右侧 Inspector 填显示名/apiName，属性表格里「加属性」逐行加（勾必填/主键◇/标题⌾/索引⚡，可引用共享属性、加子属性；支持批量必填/批量删除）→「保存」。左上角状态点：●未保存 / 已同步。

建关系（拉线）：鼠标按住卡片右缘的小圆点拖到目标卡片上松手 → 画布内弹出「新建关系」气泡（显示 属性连接：外键 → 主键）→ 填 apiName/显示名/基数（1:1、1:N、N:M）/双向角色名 →「创建关系」。拖回卡片自己 = 自关联层级。点连线可选中，在右侧 Inspector 改基数/角色/删除。

大图操作：工具栏「⊟ 收起」把全图按 DAM 域收成小盒（大图提速）、「⊞ 展开」、重排」重新网格布局；节点可直接拖动移位。

建动作：「+ 动作」从零配（参数→FEEL 校验→编辑规则→副作用富块：起流程/算报表/webhook），或「+ 从模板」直接拿 consolClose（关账联动：起审批流+算报表）/objectApprove（对象审批）改。Inspector 里有「试算」按钮——dry-run 预演，显示"试算通过 · 编辑 N 条 · 副作用 M 条"但不动任何数据；「执行」才真跑。

函数试算：「+ 函数」写 FEEL 函数体 → Inspector「试算」直接看求值结果。

影响面：选中一个对象类型，Inspector 显示它被哪些关系引用、影响多少对象。

发布：model 条「发布本体」→ 填摘要 → 版本号+1，快照固化（SSE 广播）。

10.2 对象浏览器（逛数据：一键查询在这）

一键查询有两种，都在这个页面：

① 过滤查询：左侧「对象集构造器」= 属性下拉 + 操作符下拉（= ≠ > ≥ < ≤ 包含 为空）+ 值输入框 → 点「加过滤」→ 中间表格立即刷新（多个条件叠 AND，条件变成小标签，点 ✕ 删除）。这就是"一键查询"的过滤器形态。

② 关系钻取（Search-Around）：中间表格点一行选中对象 → 右侧出现「关系」按钮组（每个关系一个按钮，文案如「客户下单 → 订单」）→ 点按钮 = 一键查询：中间列表整体换成相关对象，顶部记下面包屑钻取路径，选中其中一行可继续钻下一跳，model 条「← 返回」回上一跳。

典型走法：类型树（域▸应用▸模块▸单据▸类型，可 ⊟ ⊞ 折叠）选「客户」→ 表格点"北方贸易" → 右侧点「下单 → 订单」→ 表格变成他的订单 → 再点订单行 → 点反向关系回到客户。

10.3 对象 360 / 应用搭建台（办事：一键操作在这）

左侧类型下拉（按「模块 · 单据类型」分组）选类型 → 点一个对象 → 中间自动变 360 视图：属性卡 + 每个关系类型一块的相关对象（进对象即并发拉全，不用点）。

一键操作 = 右侧「可执行动作」区的 ⚡ 按钮（每个已定义动作一个）：

点「⚡ 动作名」→ 弹对话框：必填参数带红 *，提示"当前对象 类型#主键（如动作参数含对象主键，请填 xxx）"→ 填参 → 「执行」→ 绿色结果条「✔ 已执行 · 编辑 N 条 · 副作用 M 条」→ 页面自动刷新（属性/关系可能已变）。对话框里也写明"执行将真实写回对象并触发副作用"。

动作本身在设计工作台定义和试算；这里只管对具体对象执行。执行主体当前固定以管理员角色（workshop 壳）发起。

十一、需要做但还没做的（待办清单）

分三类：集成自动化缺口（这几天讨论暴露的）、安全债、性能债。优先级：P0 尽快 / P1 排期 / P2 有空。

11.1 集成与自动化缺口

优先级缺什么现状与为什么需要
P1T1 · 定时调度器全仓无任何 cron/后台任务（已实测确认）。漏斗同步只能人/外部系统手动调 POST /funnel/sync。需要：内置调度或规范"外部 cron + 管理页手动触发"双通道
P1T2 · MDM 审批完成 → 自动触发同步现在新鲜度靠人跑同步。在 MDM 审批落库的回调里加一行"调 sync"，就是准实时，小改造大收益
P1T3 · 流程审批通过 → 回写本体的回路"先审后改"闭环缺最后一段接线（流程完成事件→调本体 API 落实修改）。MDM 侧已有同款先例可抄
P2T4 · 增量同步（水位线）现在是全量读（幂等但每次全扫）。加"上次同步时间"水位，大表同步从分钟级到秒级
P2T5 · 异步任务中心代码注释原话"M1 同步执行；M2 接异步任务中心 SSE 进度/暂停/HA"。大表同步现在会占住 HTTP 请求
P2T6 · 消息队列入站无 MQ/Kafka 监听。第三方只能走 API 或落表；要 MQ 得自写消费端转投
P2T7 · 本体 → MDM 回写数据单向（MDM→本体）。本体侧发起的主数据修改变更，目前只能靠动作起流程间接治理

11.2 安全债

优先级问题现状与规避
P0S1 · subjects 越权面安全查询和动作权限的注释说"jwt 模式以令牌主体为准"，实现却是"请求带 subjects 就采纳"，没按鉴权模式分支——jwt 模式下调用方自报身份可绕过行级过滤和动作拒绝。规避：生产网关剥离调用方 subjects 头；根治是改成按模式分支
P0S2 · 漏斗拼接 SQL + 任意 sourceQuery隔离区/管道状态查询用字符串拼接（全仓唯一不走参数绑定的地方）；同步会真实执行调用方配置的任意 SQL。规避：映射配置仅限管理员、只配 SELECT、该组端点不对普通用户开放

11.3 性能与正确性债

优先级问题现状与规避
P1Q1 · JSONB 过滤无索引建模时的"是否索引"标记（isIndexed）存了但没消费，按 props 里的字段过滤是全表扫，大表高频过滤会疼。规避：过滤字段控量、走分页
P1Q2 · 删对象清边按 pk 全局匹配删对象时清边不带类型限定，pk 是跨类型的字符串，不同类型撞了值会误删别人的边。规避：各类型 pk 加前缀隔离命名空间
P2Q3 · 发布并发撞版本版本号=最大值+1 无锁，并发发布会撞号。规避：发布串行化（低频管理动作）
P2Q4 · FEEL 金额精度数值统一 64 位浮点，金额判定有精度风险。规避：金额比较用整数（以分为单位）或区间
P2Q5 · 杂项OpenAPI 文档落后路由约 15 个端点；SSE 断线丢事件（可靠通知走发件箱）；图组件大图拖拽整图重画（用分域折叠规避）

十二、一页总结

  • 是什么：企业数据的地图——对象=地点、关系=道路、查询=导航、动作=办事按钮；连接层，不是又一个业务系统。
  • 怎么存：没有图数据库，就是 PG 三组表：定义表 + 每类型一张对象表（pk/title/props/updated_at 四列，属性全在 props JSON）+ 一张公共边表；三跳查询编译成一条 SQL。
  • 塞多少：能塞 ≠ 自动全塞。主数据全进、单据挑着进（时间窗）、明细不进、聚合进；量控开关就是同步 SQL 的 WHERE。
  • 主数据：同步（拷贝）不是实时查；新鲜度=同步间隔；四条通路（DCT 导入/漏斗同步/docType/动作↔审批流）；单向。
  • 第三方：两条门——API 直推（pk 用对方单据号防重）或 中转表+定时同步；门都修好了，调度/消息这些搬运工要自己带。
  • 操作外部：只有动作副作用一个出口（webhook/起流程/算报表/函数/SSE），全走发件箱——对方挂了不拖死你。流程=人批不批的治理环。
  • FEEL 校验：点按钮前的业务规则闸门，fail-closed，配置即生效。
  • 最欠的三件事：S1/S2 两个安全口子（P0）、审批通过自动回写回路（T3）、同步的定时与增量（T1/T2/T4）。
