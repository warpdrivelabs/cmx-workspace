## 一、背景与目标

### 1.1 现状

CMXPortalManager 中的「数据库运维工作台」入口位于顶部 shellbar「集群数据源」按钮，实际 UI 全部在后端 native-page 文件 `cmx-container/data/native-pages/sources/portal/datasource/cluster-datasource.js`（2435 行）中。

该工作台已实现：
- 库门闸（page_mode: `init` / `meta_upgrade` / `conflict`）
- SSE 流式执行计划预览 → 用户审核 → 执行
- 模块矩阵（DCT / DOC / SEED 三列）+ 场景徽标（create/upgrade/current/drift/retry/none）
- 已初始化模块明细 + 可创建/升级模块矩阵 + 勾选批量执行

### 1.2 问题

1. **`docs/sql/seed/*.sql` 是手工 SQL**，后端代码完全不读取，新环境初始化需要 DBA 手工执行
2. **`data/menu-pages/**/*.json` 是菜单真源**，但需要跑 `.agents/skills/menu-generator/gen_menu_migration.mjs` 生成 `init_menu.sql` 后再手工执行
3. **`deploy_with_events` 中 `kind == "SEED"` 是纯 stub**（line 2474-2481 直接 push "skipped"），前端矩阵的 SEED 列永远显示 none
4. **MENU 在模型中心完全未出现**，无 kind 分支、无 ingest、db_state 无 menu cell

### 1.3 目标

让「数据库运维工作台」支持：
- ✅ **种子数据初始化**：业务表（字典表 `cf_*`、报表字典表 `cr_*`）的种子数据通过工作台一键部署，可重复执行
- ✅ **菜单初始化**：根据 `data/menu-pages/**/*.json` 自动同步到 `cmx_menu` 表，按 domain/application/module 增量重置
- ✅ **执行计划展示**：复用现有 SSE 流，支持预览/审核/执行/停止
- ✅ **完全弃用 SQL 文件**：工作台只操作 JSON/CSV，便于将来切换数据库（PG → MySQL/Oracle 等）
- ✅ **限定业务范围**：仅业务相关表与业务菜单；cmx 平台基础表（用户/插件/角色等）由服务启动前迁移机制建好，不在本工作台范围

### 1.4 设计原则

1. **彻底弃用 SQL 文件**——运维工作台只读 JSON/CSV，原生适配多数据库
2. **零新增表，全复用模型中心台账**——`cmx_model_module_kind` / `cmx_model_deploy_history`，新增 `kind='SEED'` 和 `kind='MENU'`
3. **统一走现有 SSE 流**——`deploy-plan-stream` → 审核 → `deploy-stream`，复用 cluster-datasource.js 已有 UI 交互

## 二、核心决策清单

| # | 决策项 | 结论 |
|---|---|---|
| 1 | 种子数据文件归属 | 转为 JSON 种子，与插件包统一 |
| 2 | SQL 文件去留 | **彻底弃用 SQL**，工作台只操作 JSON/CSV |
| 3 | 菜单初始化路径 | 后端直扫 `data/menu-pages/**/*.json` → `LocalMenuDefinitionImporter`（不走 init_menu.sql） |
| 4 | 数据落地 | 种子随业务库、菜单走平台库 |
| 5 | 执行计划 UI | 复用现有 SSE 流（plan-stream → approve → execute-stream） |
| 6 | 菜单重置颗粒度 | 按 domain/application/module 增量重置 |

| 8 | 种子版本 | **种子无版本**，用 `def_checksum`（SHA256）判断 drift |
| 9 | 工作台 UI 入口 | 在 MC_KINDS 加第 5 项 MENU，模块矩阵变 4 列 |
| 10 | Seed JSON 粒度 | 一张表一个 JSON 文件 |

### 4.2 种子 JSON 文件格式（纯数组）

```json
[
  { "code": "S", "name": "借方",     "sort_no": 1, "status": 1, "is_system": 1 },
  { "code": "H", "name": "贷方",     "sort_no": 2, "status": 1, "is_system": 1 }

```

- 顶层裸数组，与 `cmx-metadata::seed::loader` 完全对齐（`loader.rs:43-51`）
- UPSERT 列（`conflict_columns`）从 DCT meta 自动推断
- 文件名 = `table_name`，无需在文件内声明

### 4.3 UPSERT 列（conflict_columns）推断规则

```
优先级（从高到低）：
1. DCT meta 的 dictMeta.constraint.uniqueKeys（如存在，第 1 个唯一键）
2. DCT meta 的 dictMeta.codeField（如 "code"）
3. DCT meta 的 dictMeta.idField（如 "id"）
4. 退化为 []（纯 INSERT，靠表中现有唯一约束报错）
```

后端推断函数（伪代码）：
```rust
fn infer_conflict_columns(table_define: &TableDefine) -> Vec<String> {
    // 1. uniqueKeys
    if let Some(uk) = &table_define.constraints.unique_keys.first() {
        return uk.columns.clone();
    }
    // 2. code field（启发式：找名为 code 或 *_code 的字段）
    if let Some(_f) = table_define.fields.iter().find(|f| f.name == "code") {
        return vec!["code".to_string()];
    }
    // 3. id field
    if let Some(f) = table_define.fields.iter().find(|f| f.is_primary_key) {
        return vec![f.name.clone()];
    }
    vec![]
}
```

**修复现有 SQL 缺陷**：原 `cmxfico_dct_seed_data.sql` 没有任何 ON CONFLICT——纯 INSERT，重复执行会因主键/唯一约束报错。转 JSON 后通过自动 UPSERT **天然修复**，可重复执行。

### 4.4 文件 hash（checksum）计算

**粒度**：模块级聚合 hash
- 把该模块下所有 `seed/*.json` 内容按文件名排序后拼接，算 SHA256
- 写入 `cmx_model_module_kind.def_checksum`
- 同理 menu：把 `menu-pages/<d>/<a>/<m>/*.json` 聚合算 hash

```rust
fn aggregate_sha256(files: &[FileInfo]) -> String {
    let mut sorted: Vec<&FileInfo> = files.iter().collect();
    sorted.sort_by_key(|f| f.rel_path.clone());
    let mut hasher = Sha256::new();
    for f in sorted {
        hasher.update(f.rel_path.as_bytes());
        hasher.update(f.content.as_bytes());  // 原始文件内容
    }
    hex::encode(hasher.finalize())
}
```

### 5.2 cmx-model-center 改造 · 4 处改动

#### 改动 1：新增模块 `menu_pages_adapter.rs`（菜单适配器）

**职责**：把前端 `menu-pages/*.json` 格式翻译成 `MenuDefinition` 列表。

```rust
// 文件：crates/libs/cmx-model-center/src/menu_pages_adapter.rs
use cmx_core::model::module::MenuDefinition;
use anyhow::Result;

/// 解析 data/menu-pages/<domain>/<app>/<module>/*.json
/// 返回扁平化的 MenuDefinition 列表（已填 domain_code/application_code/module_code/parent_code）
pub fn parse_menu_pages_file(
    raw: &str,
    domain: &str,
    app: &str,
    module: &str,
) -> Result<Vec<MenuDefinition>> {
    let parsed: serde_json::Value = serde_json::from_str(raw)?;
    let roots = parsed
        .get("items")
        .and_then(|v| v.as_array())
        .ok_or_else(|| anyhow!("menu-pages JSON 缺少 items 数组"))?;
    let mut out = Vec::with_capacity(roots.len() * 4);
    for (sort_idx, root) in roots.iter().enumerate() {
        flatten_node(root, None, domain, app, module, sort_idx as i32, &mut out);
    }
    Ok(out)
}

fn flatten_node(
    v: &serde_json::Value,
    parent_code: Option<&str>,
    domain: &str, app: &str, module: &str,
    sort_order: i32,
    out: &mut Vec<MenuDefinition>,
) {
    let code = v.get("id").and_then(|x| x.as_str()).unwrap_or("").to_string();
    let def = MenuDefinition {
        code: code.clone(),
        name: v.get("caption").and_then(|x| x.as_str()).unwrap_or("").to_string(),
        parent_code: parent_code.map(String::from),
        description: None,
        path: None,
        icon: v.get("icon").and_then(|x| x.as_str()).map(String::from),
        component: None,
        sort_order,
        visible: 1,
        open_type: 0,
        fun_code: v.get("permissionId")
            .and_then(|x| if x.is_null() { None } else { x.as_str() })
            .map(String::from),
        definition: v.get("workspace").cloned(), // 整体 JSONB 透传
        ext_attributes: None,
        children: vec![],
        domain_code: domain.to_string(),
        application_code: app.to_string(),
        module_code: module.to_string(),
    };
    out.push(def);

    // 递归处理 children
    if let Some(children) = v.get("children").and_then(|c| c.as_array()) {
        for (idx, child) in children.iter().enumerate() {
            flatten_node(child, Some(&code), domain, app, module, idx as i32, out);
        }
    }
}
```

async fn deploy_seed_with_events(
    db_id: &str, domain: &str, app: &str, module: &str, _file: &str,
    operator_id: &str, operator_name: &str,
    tx: Option<&UnboundedSender<InitEvent>>,
) -> Result<Value> {
    // 1. 写历史 pending
    let batch_id = snowflake_id();
    insert_history_pending(batch_id.clone(), db_id, domain, app, module,
                          kind="SEED", action="seed").await?;
    send_progress(tx, "正在加载种子数据文件清单…");

    // 2. 扫描该模块 seed/*.json
    let seed_files = scan_seed_files(domain, app, module);
    if seed_files.is_empty() {
        send_progress(tx, &format!("{module} · 无种子文件，已跳过"));
        return Ok(json!({ "module": module, "kind": "SEED", "status": "skipped", "note": "无种子文件" }));
    }

    // 3. 重读 DCT/DOC 元定义 JSON 编译（第 1 档取数）
    send_progress(tx, "正在编译表元定义…");
    let table_defines = compile_all_definitions_for_module(domain, app, module)?;
    let table_map: HashMap<&str, &TableDefine> = table_defines
        .iter().map(|td| (td.name.as_str(), td)).collect();

    // 4. 构造 SeedDataConfig 数组
    let base_path = Path::new("data/meta/definitions");
    let seed_configs: Vec<SeedDataConfig> = seed_files.iter().map(|f| {
        let td = table_map.get(f.table_name.as_str());
        SeedDataConfig {
            table_name: f.table_name.clone(),
            file: format!("{domain}/{app}/{module}/seed/{}.json", f.table_name),
            conflict_columns: td.map(infer_conflict_columns).unwrap_or_default(),
            enabled: true,
        }
    }).collect();

    // 5. 前置校验：表必须已建
    send_progress(tx, "正在校验目标表是否已建…");
    for cfg in &seed_configs {
        if !table_exists(db_id, &cfg.table_name).await? {
            return Err(anyhow!("表 {} 不存在，请先部署 DCT 元定义", cfg.table_name));
        }
    }

    // 6. 执行 PgSeedDataExecutor（事务内）
    send_progress(tx, "正在写入种子数据…");
    let guard = mm.get_transaction_context().begin_with_guard(db_id).await?;
    let txn_id = guard.txn_id();
    let executor = PgSeedDataExecutor::new(db_id, Some(txn_id.to_string()));
    let summary = executor.execute_all_seed_data(&table_defines, &seed_configs, base_path).await;
    guard.commit().await?;

    // 7. ★ 只写 cmx_model_module_kind（不写 cmx_model_source）
    let module_checksum = aggregate_sha256(&seed_files);
    upsert_module_kind(
        db_id, domain, app, module, kind="SEED",
        version=NULL,
        def_checksum=module_checksum,
        table_count=seed_files.len(),
        operator_id, operator_name,
    ).await?;

    // 8. 写历史 success
    let total_rows: i64 = summary.table_results.iter()
        .map(|r| r.inserted_rows + r.updated_rows).sum();
    insert_history_success(batch_id, db_id, domain, app, module, kind="SEED",
                          action="seed", seed_rows=total_rows).await?;

    send_event(tx, "done", json!({ "status": "success", "seed_rows": total_rows }));
    Ok(json!({ "module": module, "kind": "SEED", "status": "success",
               "tables": seed_files.len(), "rows": total_rows }))
}

async fn deploy_menu_with_events(
    _db_id: &str,  // 业务库 id（菜单走平台库，这里不用）

        (kind_order(kind), *idx)
    });
    let sorted_items: Vec<&Value> = sorted.iter().map(|(_, v)| *v).collect();

## 七、执行计划与幂等

### 7.1 SSE 事件序列（SEED/MENU 沿用现有协议）

```
前端 POST /api/model/deploy-plan-stream
  ← event: connect     { db_id, batch_id }
  ← event: step        { message: "正在扫描种子文件…" }
  ← event: step        { message: "正在编译元定义…" }
  ← event: done        { plan: { results: [...], tables: N } }

用户审核 → POST /api/model/deploy-stream
  ← event: connect     { db_id, batch_id }
  ← event: step        { message: "正在写入种子数据…" }
  ← event: progress    { module, kind, status, message }
  ← event: step        { message: "正在同步菜单到平台库…" }
  ← event: progress    { module, kind, status, message }
  ← event: done        { db_state: {...最新状态回吐...} }
```

前端拿到 `done.db_state` 后自动刷新矩阵。

### 7.2 幂等保障（三层）

| 层 | 机制 | SEED/MENU 适用性 |
|---|---|---|
| SQL 文件级 | `INSERT ... ON CONFLICT DO NOTHING/UPDATE` | SEED：由 `PgSeedDataExecutor` 自动生成 UPSERT（`conflict_columns` 推断） |
| 后端事务 | 每个 kind 一个事务，失败回滚 | SEED：`guard.commit()` / 失败 drop 回滚；MENU：`LocalMenuDefinitionImporter` 内部事务 |
| 台账状态 | `cmx_model_module_kind` 按 (db_id, domain, app, module, kind) UPSERT | SEED/MENU：每次执行后更新 `def_checksum` + `status='current'` + `deployed_at` |

### 7.3 重复执行语义

| 场景 | 行为 |
|---|---|
| 首次执行 SEED（checksum 不存在） | 全量 INSERT（UPSERT 列推断），status: none → current |
| 数据未变，再次执行 SEED | UPSERT 命中相同 code，UPDATE 其余字段（幂等），status 保持 current |
| 数据文件改了，执行 SEED | 计算新 checksum，与上次不同 → 矩阵显示 drift；执行后 status: drift → current，checksum 更新 |
| MENU 同模块重新执行 | `LocalMenuDefinitionImporter` 先 `DELETE FROM cmx_menu WHERE module_code=$1` 再插入（先删后插，事务内） |
| MENU 跨模块执行 | 各自独立（不同 module_code），互不影响 |

### 7.4 错误恢复

| 错误场景 | 处理 |
|---|---|
| 表未建（SEED） | `table_exists` 前置校验失败 → 返回错误，不进入 executor |
| 列不匹配（SEED） | `PgSeedDataExecutor` 批次失败 → 自动降级逐行（`executor.rs:206-247`），单行失败收集到 `failures`，不阻断 |
| JSON 解析失败 | 适配层 `parse_menu_pages_file` 返回 `Err`，deploy_with_events 捕获后写 history failed |
| 事务失败 | RAII guard drop 自动回滚 + history 写 `failed` + `error_message` |
| 进程中断 | 历史 batch_id 状态留 `executing`，下次扫到不会自动重试（需用户手动重新触发；矩阵显示 retry） |

### 7.5 并发安全（集群部署）

按 AGENTS.md §五"无状态服务"约束：

| 风险 | 处理 |
|---|---|
| 多节点同时 deploy 同一模块 | 复用 `deploy_with_events` 现有的 Redis 分布式锁（与 DCT/DOC 同一锁机制） |
| MENU 先删后插中途被另一节点读 | `LocalMenuDefinitionImporter` 在事务内执行 `DELETE + INSERT`，事务隔离保证一致性 |
| SEED 批次内部分失败 | executor 内部降级逐行，单行失败不影响其他行（不回滚已成功行） |
| 历史记录并发写 | `cmx_model_deploy_history` 追加式（永不更新），无冲突 |

## 附录 A：决策演进史（三轮简化）

本方案在 brainstorming 过程中，对「cmx_model_source 表结构如何承载 SEED/MENU 的 hash」经历了三轮简化，最终落到 YAGNI 最简方案。

### A.1 第一版（被否决）

- 加 `table_name` 列 + 重建唯一键
- hash 粒度：表级（每张表一行）
- 写 `cmx_model_source`（每表一行）

**问题**：`table_name` 与 `source_file` 语义重叠，冗余。

### A.2 第二版（被否决）

- 不加列，用 `source_file` 进唯一键（COALESCE 兼容 DCT/DOC）
- hash 粒度：表级
- 写 `cmx_model_source`（每文件一行）

**问题**：仍需重建唯一键（DROP+CREATE INDEX），生产环境索引改动有风险。

### A.3 第三版（最终采纳）

- **零迁移、零索引改动**
- hash 粒度：**模块级聚合**
- **不写 `cmx_model_source`**（SEED/MENU 场景）
- 只写 `cmx_model_module_kind`（每模块×kind 一行）+ `cmx_model_deploy_history`（追加式）

### A.4 简化对比

| 版本 | 表/索引改动 | hash 粒度 | cmx_model_source | drift 明细 |
|---|---|---|---|---|
| 初版 | +table_name 列 + 重建唯一键 | 表级 | 写（每表一行） | 表级 |
| 第二版 | 重建唯一键（source_file） | 表级 | 写（每文件一行） | 表级 |
| **最终版** | **零改动** | **模块级** | **不写** | **模块级** |

### A.5 取舍说明

最终版牺牲了「表级 drift 定位」（用户看不出 `cf_gl_account` 还是 `cf_company` 哪个变了），换取：
- ✅ 零迁移风险（生产环境不需要执行任何表结构变更）
- ✅ 零索引性能影响
- ✅ 代码量最少
- ✅ 可后续扩展（如果将来真的需要表级粒度，再加索引也不迟）

如果实际使用中发现"必须知道哪张表变了"，可通过 `cmx_model_deploy_history.error_message` 字段（失败的表会记录）或运行时实时算文件 hash 比对（无历史依据，但能查当前态）补充。
