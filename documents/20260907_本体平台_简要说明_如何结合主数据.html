简要说明 4/4如何结合主数据

分工一句话：MDM 负责治理与发放（申请→审批→落字典），本体负责关联与消费（把主数据变成可被业务对象引用、可被图谱钻取的参照对象）。四条通路已内置。

主数据在本体侧建议以「参照对象类型」存在（code 主键 + name 标题，status=active），业务对象经 LinkType 引用它，不复制治理职责。

二、通路 ①：DCT 字典一键导入（一次性接入）

把一个 MDM 字典变成本体参照对象类型，字典项直接物化为对象：

curl -s -X POST http://127.0.0.1:8097/api/onto/v1/import/dct \
  -H "Content-Type: application/json" -H "X-API-Key: ..." \
  -d '{ "apiName":"Currency","displayName":"币种",
        "items":[ {"code":"USD","name":"美元"},
                  {"code":"CNY","name":"人民币"},
                  {"code":"EUR","name":"欧元"} ] }'
# 返回 {"objectType":"Currency","seededItems":3}
# 自动得到：主键=code、标题=name 的参照类型；字典项即对象，可直接进对象集查询/过滤
适合币种/凭证类型/行业分类等低频变化的字典。字典变了需要重新导入（幂等 upsert）。

三、通路 ②：Funnel 持续同步（推荐主通道）

面向业务库里的主数据表/字典表：配一条源映射，之后随时触发全量同步——读源 → 映射校验 → 合格 upsert 成对象，违规行进隔离区。

第一步：建目标对象类型 + 源映射

# 目标类型（主数据参照对象）
curl -s -X POST .../api/onto/v1/object-types \
  -d '{"apiName":"MdmCustomer","displayName":"主数据客户","primaryKey":"id",
       "titleProperty":"name","status":"active",
       "properties":[{"apiName":"id","baseType":"string"},
                     {"apiName":"name","baseType":"string"},
                     {"apiName":"region","baseType":"string"}]}'

# 源映射：指向业务库里的主数据源表
curl -s -X POST .../api/onto/v1/funnel/mappings \
  -H "Content-Type: application/json" -H "X-API-Key: ..." \
  -d '{ "objectType":"MdmCustomer",
        "sourceQuery":"SELECT cust_id, cust_name, region_code FROM md_customer",
        "keyColumns":["cust_id"],
        "titleColumn":"cust_name",
        "propertyMap":[ {"source":"cust_id","property":"id"},
                        {"source":"cust_name","property":"name"},
                        {"source":"region_code","property":"region"} ],
        "required":["name"] }'

第二步：触发同步 + 查看结果

curl -s -X POST .../api/onto/v1/funnel/sync/MdmCustomer -d '{}'
# → {"read":4,"written":3,"quarantined":1,"mode":"full"}

curl -s ".../api/onto/v1/funnel/quarantine?objectType=MdmCustomer"   # 违规行+原因
curl -s ".../api/onto/v1/funnel/pipeline-status/MdmCustomer"          # 抽取/映射/索引三段状态
同步是幂等 upsert：源表改一行再同步即覆盖，天然适合"MDM 审批落库后刷新本体"的节奏。多列主键用 keyColumns 多列（以 | 拼接）。

四、通路 ③：业务单据关联（DOC 导入 + docType）

  • 对象类型可挂 docType（业务单据类型引用），标明"本对象对应哪种 MDM 单据"。
  • POST /import/doc 把主从实体图（头/行）批量导入为对象类型 + 组合关系——已有业务模型不用手工重画。

五、通路 ④：动作 ↔ 治理审批流

  • 本体动作的副作用支持 startBusinessProcess（对接 cmx-flowengine）——在对象工作台对主数据对象执行动作即可发起/参与 MDM 变更审批。
  • 内置模板 objectApprove（对象审批）、consolClose（一个动作同时起审批流 + 算报表）可从设计工作台「从模板创建」直接拿来改。
  • 执行留痕：/action-logs 审计，副作用经发件箱可靠投递（失败可查 /action-outbox）。

六、推荐落地配方（六步）

1. MDM 治理保持不变（申请→审批→落字典/主数据表）
2. 低频字典用 DCT 导入一次接入；
3. 高频主数据用 Funnel 源映射接入（指向业务库表）；
4. 建业务对象类型，用 LinkType 引用主数据参照对象（如 订单→客户、凭证→科目）；
5. 外部定时（操作系统 cron / 门户定时任务）在审批高峰后调 sync 端点刷新本体（当前同步为同步执行的全量模式，无内置调度）；
6. 对需要治理的操作定义动作：FEEL 校验 + 乐观锁写回 + 起审批流。

七、现状边界（如实告知）

  • Funnel 同步为 M1 全量同步（同步执行、长任务雏形，增量/异步调度在路线图上）；大表建议错峰调用。
  • 无自动调度：需要外部定时器触发 /funnel/sync/{type}。
  • DCT 导入是快照式：字典更新后需重新调用。
  • sourceQuery 会真实执行调用方配置的 SQL——仅限可信管理员配置，建议只配 SELECT。
  • 本体 → MDM 的回写通路暂未内置（单向：MDM → 本体）。
