# cmx-sql 数据库迁移主业务库分离方案（v2）

> 日期：2026-08-19 · 仓库：cmx-container · 状态：**已实施并验证**（含 Rev2 调整）
> 关联：`docs/sql/v2/README.md`（现行结构说明）、`.agents/skills/sql-guide/SKILL.md`（维护规范）

## 一、背景与目标

旧 SQL 结构（`docs/sql/init | migrations | seed/`）存在四个问题：

1. **无主库/业务库之分**：迁移引擎只对主库执行，`md_*` 治理表被建进主库，而运行时
   `resolve_db_id` 却按业务库路由（`db_id` 头 → 业务库 → 默认库）——建库与路由不一致。
2. **扁平目录**：31 个历史迁移混在一处，无归属维度。
3. **双轨漂移**：init_ddl 快照与迁移链内容重叠且互有缺口（快照缺 20260801_001 两表等）；
   版本号冲突（两个 `20260720_001`）；多处不幂等（裸 INSERT / 裸 CREATE INDEX）。
4. **init_ddl 为破坏性重建式**（DROP+CREATE），误执行丢数据。

目标（用户已确认的三个决策）：**基线压缩**（新链每库一个幂等基线，历史留旧目录不动）、
**无损幂等**（全部 IF NOT EXISTS / ON CONFLICT）、**业务库 DDL 不补**（cf_*/cr_* 由模型
中心运行时部署，只放种子）。

## 二、新结构（Rev2 调整后）

```
docs/sql/v2/
├── README.md
├── platform/    # → 主库：cmx_ 平台表 48 张（不含流程/编码引擎表）+ 种子 + 基线迁移
└── biz/         # → 业务库：md_* 11 + mdm_activation + cmx_code_* 3 + cmx_flow_* 15 + 种子 + seeds/
```

**归属规则**（含 Rev2~Rev4 用户调整）：

1. `cmx_` 前缀 → platform；**两组例外前缀 → biz**：
   - `cmx_flow_*`（15 张流程运行态表）——与流程引擎运行时一致（`cmx-flowengine` 的
     `FLOW_DB_ID = "fico-db"` 即业务库，引擎启动还会在业务库 `ensure_schema` 自建
     这套表；旧链把它们建主库本就与运行时不符）。流程 IAM 侧表
     `cmx_org`/`cmx_position`/`cmx_user_position` 留 platform（引擎 `IAM_DB_ID = "primary"`）。
   - `cmx_code_*`（编码引擎 rule/gap/seq 三张）——运行时 code API 经 `resolve_db_id`
     回退业务库；15 条编码规则种子随迁 biz init_dml。
2. 其余前缀（`md_*`/`mdm_*`/`cf_*`/`cr_*`/`cm_*`）→ biz。其中 `mdm_activation`
   （MDM 激活映射，原 `cmx_mdm_activation` 改名）随 MDM 治理表归业务库侧，
   激活映射种子随之落 biz init_dml。

**init_ddl 与基线的两版布局**（Rev3 调整：init_ddl 禁 ALTER，遵守「表定义即终态」原则）：

- **init_ddl.sql**（面向新库手工重建与参考阅读）：每表区块
  `CREATE TABLE（终态列全）→ COMMENT（紧跟建表）→ 索引`，**无任何 ALTER**；
- **基线迁移**（= init_ddl 内容 + 各表区块内插一段「结构对齐 ALTER」+ init_dml，
  布局 `CREATE TABLE → 结构对齐 ALTER → COMMENT → 索引 → 种子`）——迁移文件是增量
  变更的载体，允许 ALTER。

**基线内对齐 ALTER 的原因**：存量库表结构可能停在旧链中途（如现网 cmxlocal 的
`mdm_activation` 缺 `subject_name_field` 列）。建表语句对已存在表是 no-op 不补列，
后续 `COMMENT ON COLUMN` / 种子 INSERT 引用缺失列即报错。对齐 ALTER（迁移链历史
`ADD COLUMN IF NOT EXISTS` 的幂等积累）放在建表后、COMMENT 前，漂移库先补列、
新库即建即过——同一份基线对「新库全量建成」和「漂移老库安全升级」都成立。

## 三、引擎升级（cmx-container）

| 文件 | 改动 |
| --- | --- |
| `cmx-database/src/migration/runner.rs` | 锁键常量 → `with_lock_key()` 可配置（双轮用不同键防互相阻塞）；`split_sql_statements` 新增美元引用（`$tag$`）感知（修复 JSONB 字面量内分号被切碎的既有缺陷）+ 8 个单元测试 |
| `cmx-database/src/manager/mod.rs` | 新增 `get_biz_db_id_opt()`（不回退默认库，供引擎区分有无业务库） |
| `cmx-platform-app/src/config/migration.rs` | 重构为双轮执行：platform（默认库）→ biz（业务库，未配置则 warn 跳过不回退）；默认目录 `docs/sql/v2`；目录拼接收敛为 `migration_round_dir()`（必须拼到 `<dir>/<轮次>/migrations` 子目录层——MigrationLoader 非递归单目录扫描，只拼到轮次层会静默漏扫，已有单测固化）；`lock_wait_timeout` 接线（默认 120 秒），死配置 `lock_timeout` 移除 |

配置同步：`cmx-container/{dev.toml, config/docker.toml, config/config_template.toml}`、
`cmx-portalservice/{dev.toml, portal-server.toml}` 的 `migration.dir` → v2；`enabled` 保持 false。

## 四、无遗漏保证（对象级覆盖核对）

脚本提取新旧全部 SQL 对象（表/索引/INSERT 目标/COMMENT）做集合 diff：

- 表 **78/78 全覆盖**；INSERT 目标、COMMENT 全覆盖
- 白名单（有意不迁，已逐项核实）：
  - 5 张死表 `cmx_plugin_nodes/features/dependencies/deployments`、`cmx_system_plugins`
    （无任何运行时代码引用，旧 init_ddl 已注释废弃）
  - 7 个改名/等价索引（如 `uk_cmx_core_application_code`→`uk_cmx_coreapplication_code`、
    `idx_cmx_module_version_history_pkg`→同名 UNIQUE 更强版）
- 过程中发现并修复的旧文件缺陷：
  - init_ddl 快照缺 `cmx_flow_biz_link`/`cmx_flow_task_comment` 两表与 `idx_version_current` → 补丁段补齐
  - init_ddl 有 3 行 `COMMENT ON TABLE md_event_log.<col>` 笔误（PG 语法错误）→ 修正为 COLUMN

## 六、存量升级指引与遗留

- 现网 cmxlocal 实测**主库并无 md_* 表**（旧链迁移从未自动执行）；主库的 13 张
  `cmx_flow_*` 表由历史手工操作产生，流程引擎实际运行数据在业务库（引擎自建）。
  切换 v2 后：确认业务库流程数据完整，主库遗留 flow 旧表可手工 DROP。
- `migration.enabled` 仍为 false；开启后首次启动将执行两库基线（对已有库为幂等
  no-op/补齐），建议先在 dev 环境开启验证后再推生产。
- 旧目录 `docs/sql/init|migrations|seed/` 原样保留为历史归档，不再维护。
- `cmx-database-pg` 下的迁移死代码副本未动（无调用方，如后续接新链路需同步双轮改造）。
