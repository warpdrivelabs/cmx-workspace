0.2 六个真新造件一览

后端①编码引擎

段序列(常量/属性/流水/日期/校验位) + 原子铸号 + 按受控组织生效。现有仅 PK 铸号(pk52)，非业务编码。

后端②匹配合并存活

分块/比较器/双阈值/字段级存活。全库零 levenshtein/jaro/soundex，是最难的核心。

后端③交叉引用+分发

xref/value-map 零命中；事件仅进程内总线无持久化。须建 outbox + delta。

前端①查重候选 UI

录入时「疑似重复候选+匹配分」列表。前端完全空白。

前端②红线 diff

变更请求字段级 old→new 对比展示。仅有算 delta 的纯函数，无展示 UI。

前端③待办/审批台

「我的待办/审批收件箱」。cmx-flow 后端 M4 就绪，缺前端消费页。

01三段式范式复用 cmx-mdm mirrors the pattern

好消息先行：MDM 的后端骨架几乎零风险——DCT/DOC/RPT 三个领域已把「model + store-pg + api」三段式范式跑通且完全一致，MDM 照抄一份 cmx-mdm-* 即可。

02编码引擎 新造① the coding engine

MDM 的业务编码（供应商码、物料码）由规则生成，防一物多码/一码多物。代码核实：cmx 现无任何业务编码能力。

🔴 缺口证据：现有只有 PK 铸号，不是业务编码
grep code_rule|流水号|number_range|serial|生成编号 命中全部是数据库主键铸号（cmx-doc-store-pg/saver.rs:1133 mint_ids_for_changeset、cmx-dct-model/lib.rs:279、cmx-utils next_pk_id）——即「给新增行分配 bigint 主键」，不是「按前缀+日期+流水段+校验位生成可读业务编码」。PG 原生 nextval 还被当默认值主动剥离（cmx-metadata/executor.rs:620）。→ 编码引擎从零新造。

2.1 要新造什么

构件工作量说明
段引擎（6 种段）中常量/属性取值/流水号/日期/校验位/分隔符，声明式 JSON（对应 MDM 方案 §15.1）
原子铸号（并发安全）小md_serial 表 + INSERT…ON CONFLICT DO UPDATE…RETURNING 行锁；可参照 pk52 的并发经验
按受控组织+条件选规则中金蝶机制：orgScope 命中 + condition 求值；务必处理"无组织上下文"兜底
三铁律落地小永不回收(作废置 frozen 不释放号段)、内码≠外码、规则版本化
✅ 可借力：pk52 铸号的并发经验直接迁移
编码引擎的原子流水号分配，与既有 cmx-utils/id/pk52.rs（52 位 JS 安全整数、原子序列+时间戳、全局单例 next_pk_id）是同类问题。并发安全的实现模式可直接迁移，只是把"全局单调"换成"按规则+重置键分组"。这不是纯从零——地基的并发经验可用。

03匹配合并存活引擎 新造② match · merge · survivorship — the hard one

这是 MDM 的心脏，也是全部缺口里最难的一件。生产黄金记录的分块→比较→裁决→合并存活流水线，cmx 代码里零基础。

🔴 缺口证据：零相似度算法
grep dedup|fuzzy|similar|soundex|查重|去重|相似 命中全是无关项：Vec::dedup() 集合去重、SQL DISTINCT ON 取最新版、名称 LIKE 模糊查询、flow 抄送去重、cmx-rust-sheet 的 xlsx 样式表去重。全库零 levenshtein / jaro-winkler / soundex / metaphone，无任何记录级匹配/相似度/存活规则。→ 整条流水线从零新造。

3.1 要新造什么（四阶段）

分块 Clustering → 比较 Comparison → 裁决 Decision → 合并存活 Merge+Survivorship 多簇键(音近+分词 编辑距离/换位/ 双阈值三向 结构re-parent + +子串,防NULL巨簇) 音近,分级非布尔 (auto/review/no) 字段级cell存活 ───────────────────────────────────────────────────────────────────── 工作量:中 工作量:中(可选AI高) 工作量:小 工作量:大(企业级最耗时)
构件难度说明（对应 MDM 方案 §16）
分块 Clustering中多簇键(Soundex/Metaphone/前N字符/税号)带优先级；护栏：NULL 巨簇、簇大小上限 500、子簇拆分并行
比较器 Comparison中编辑距离/字符换位/音近/精确；可插拔、返回分级结果(0-100%)非布尔
三向裁决小双阈值：≥automerge 自动、match~automerge 人工评审、<match 保留；组内全过护栏
合并+字段级存活大结构合并 re-parent 子实体、victim 置 merged 可 unmerge；逐字段存活(源优先/最新/最全/质量分)
🟡 可借力：cmx-job 承接批量匹配、cmx-rust 生态可自研算法
① 批量匹配作业直接接 cmx-job 任务中心（SSE 进度/暂停停止/持久化恢复/多实例 HA 全齐，cmx-job-core/store-pg/api 已 landed），黄金记录流水线作为一个 JobHandler 即可获得进度/HA/崩溃恢复；② 分块/比较算法可在 cmx-rust 生态自研（Rust crate 生态有成熟 strsim 等），或引入 crate。引擎逻辑本身仍是净新造，但运行框架（作业调度）现成。
💡 落地建议：M4 从精确匹配起步，模糊/AI 后置
存活规则"企业级规模下极难"（数十源×数百属性）。建议第一版只做精确匹配（税号/统一社会信用代码相等）+ 单一存活策略（源优先），先把「查重识别一物多码 + 自动/人工分流」闭环跑通，再逐步加模糊/AI 匹配与字段级存活。分块的护栏（NULL 巨簇、簇大小上限）必须第一版就有。

04交叉引用与分发事件 新造③ xref & delta distribution

黄金记录要「被消费」——跨系统 ID 映射（Key Mapping）与增量分发（delta）。前者零基础，后者有内存总线雏形但缺持久化。

🔴 交叉引用 md_xref —— 零命中

grep xref|source_system|key_mapping|external_id|golden_record|survivor 完全零命中。DRN 是定义引用寻址，非跨系统 ID 映射。
要新造：md_xref(源系统,源ID)→内码 + md_value_map 值映射。这是注册型 MDM「运行时组装视图」+ 合并回灌 + unmerge 的地基（MDM 方案 §11.3/§14.2）。

🟡 分发事件 —— 仅内存总线

存在进程内 EventBus（cmx-traits/event_bus/bus.rs:18 publish/subscribe，tokio spawn 异步，无持久化），web-server 启动初始化 GlobalEventBus（main.rs:135），当前唯一消费者是 job 失败告警。RPT 有 cr_report_op_log 但那是报表协同编辑专用。
要新造：内存总线之上补持久化 outbox + delta token + 重投递（MDM 方案 §19）。

4.1 要新造什么

构件状态说明
md_xref 交叉引用表新造(源系统,源引用)→内码，Active/Inactive；一内码对多源
md_value_map 值映射新造跨系统代码调和（物料组 01↔01-200）
md_event_log 事件日志新造BIGSERIAL 单调序号=delta 游标；规范模型快照
delta token 契约新造按(消费者×实体×版本)定界；28 天全量兜底
分发执行（批量/重试）复用接 cmx-job 任务中心；失败告警复用现有 job.failed 通道
内存事件总线半成品EventBus 作实时推送地基，补持久化即可

MDM 域是否需汇总说明

💡 两条落地路径（择一）
路径 A（推荐·彻底）：把 cmx-agg 作为前置依赖建出来——中立 crate，AggRule{from,to,field,toField,agg}/topo_sort/rollup，拓扑排序+逐层重算+环检测，与前端 CmxMasterSlave.addAggregation（已存在，cmx-master-slave.js:206）语义对齐，一份声明两端读。DCT/DOC/RPT/MDM 四方共享，一劳永逸。

结论：若 MDM 一期就含组织/成本中心域，建议走 A，把 cmx-agg 排进 M7 之前；若一期只做客商/物料，可暂缓。无论如何，方案文档不能把它算作"已有复用"。

18风险与关键路径 risks & critical path

18.1 关键路径

P0 ──────────→ P1 ──────────────────→ P2 ─────────→ P3 cmx-mdm三段 编码引擎 + cmx-flow接线 匹配(模糊/AI) 控件补强 +metaKind分流 + meta→表单 + 待办台 + 查重UI+评审台 + 多视图审批 + 匹配(精确) ← 最小可用 MDM 闭环在此 + 交叉引用分发 + cmx-agg(若需) ───────────────────────────────────────────────────────────── 关键路径瓶颈：匹配合并存活引擎（唯一的"大"，建议独立小组、先精确后模糊）

18.2 五个风险点

  • cmx-agg 被误当"已有"（最需纠正）：上份方案 §20 把层间汇总列为"复用 cmx-agg"，实则零代码。务必在排期时把它算作新造/前置，否则低估工作量。若一期含组织/成本中心域，它是隐藏关键路径。
  • 匹配合并存活是唯一的"大"且最难：存活规则企业级规模极难。缓解：M4 严格先做精确匹配+单一存活闭环，模糊/AI/字段级存活后置；分块护栏（NULL 巨簇、簇大小上限 500）第一版必须有，否则性能雪崩。
  • 待办/审批台是"半个缺口"但阻塞审批闭环：cmx-flow 引擎 M4 后端已就绪，纯缺前端消费页。缓解：做成通用 flow 待办台（报表/单据/MDM 共用），一次投入多处收益，别做成 MDM 专用。
  • grid 录入校验定位是体验债不是功能债：不打通也能用（弹窗逐行明细可用），但大表录入体验差。缓解：可放 P3，不阻塞最小闭环。
  • 组件三产物同步坑（megasheet 内核）：若 MDM 用到电子表格式录入，改内核要同步 demo IIFE / vendor ESM / portal dist 三产物（cmx-模块独立化方案.html:591）。但 MDM 主范式是 revo-grid + ui5-form，大概率不碰 megasheet，风险低。
🏅 一页纸总结
照《企业主数据管理平台方案》在 cmx 上开发，地基约 70% 可复用——三段式范式、cmx-flow 治理流、cmx-job 任务中心、ZmcDataSet、列级校验、CmxErrCode、bigint 铸号、compile/deploy 管线、元数据驱动表单渲染器、字段控件全家桶、lookup、主从树、四区外壳全部就绪。真新造只有六件：后端(编码引擎 · 匹配合并存活 · 交叉引用+分发) + 前端(查重候选 UI · 红线 diff · 通用待办审批台)。一个关键更正：cmx-agg 层次汇总至今零代码，必须从"复用"移入"前置新造"。关键路径瓶颈是匹配合并存活引擎（唯一的"大"，先精确后模糊分期）。其余皆为复用、接线或补强——"照方案开发"在 cmx 上是低-中风险、路径清晰的工程。
