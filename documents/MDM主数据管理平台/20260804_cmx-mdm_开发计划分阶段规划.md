## 〇、基础就绪核实结论(决定真实起点)

V3 方案假设「DCT/DOC/cmx-flow 平台骨架已就绪,MDM 是其上的独立新域」。核实结论:**假设成立**——DCT/DOC 底座生产可用,MDM 是纯新造域。cmx-flow 与 cmx-code 虽已就绪/可建,但**按本计划后置到最后**(见策略②),MVP 不依赖它们。

| 能力 | 就绪状态 | 对 MDM 的影响 |
|---|---|---|
| **DCT 主数据底座** | ✅ 就绪 | 直接复用 `/api/dct/*`(CRUD/树形/字段集/导入导出),零改造 |
| **DOC 单据底座** | ✅ 就绪(状态机弱) | 复用 `/api/doc/*`(头/行 upper_id 结构);⚠ 申请单强状态机由 MDM 自建 |
| **cmx-flow 审批引擎** | ✅ 就绪(delegate 可用) | **本计划后置到 M7**;MVP 用简单按钮审批,M7 再接 flow |
| **路由注册机制** | ✅ 就绪 | `web-server/src/routes.rs` 加一行 `.merge(MdmModule.routes())` 即接入 |
| **MDM 三个 crate** | ❌ 不存在 | M0 从零搭(仿 cmx-dct 三段式) |
| **MDM 域元数据** | ❌ 不存在 | M0 新建 `basic/dataplatform/mdm/` 目录 + DCT/DOC JSON + `mdmGovernanceFields` |
| **物理表(10 张)** | ❌ 全不存在 | M0 新建迁移 SQL |
| **cmx-code 编码引擎** | ❌ 不存在 | **本计划后置到 M8**;MVP 用随机生成,M8 再接编码引擎 |

**关键结论**:MDM 是「在已就绪底座之上新造一个域」。MVP(M0–M2)**不依赖 cmx-flow / cmx-code**,可最快跑通 V3 核心架构。真新造收敛为:**后端 3 件**(激活器 / 匹配合并 / 分发)+ **前端 4 件**(映射配置器 / 查重 / 红线 diff / 待办台),与 V3 §21 缺口分析一致。

## 一、总体策略

1. **守 V3 铁律**:`cm_*` 主数据**只存 published**,草稿一律走 CR 单据(cv_*),激活器是写入 `cm_*` 的唯一入口。
2. **最大化复用**:主数据 CRUD 走 `/api/dct/*`,CR 录入走 `/api/doc/*`,`cmx-mdm-api` 只出治理端点(激活/审计/匹配/分发)。
3. **配置驱动**:通用激活器读 `mdm_activation` 映射执行固定流程,新增主数据只加配置不改代码。
4. **策略② · 分阶段降复杂度**:<u>重依赖能力(cmx-flow 审批、cmx-code 编码)后置到最后</u>。MVP 先用**简单机制跑通主链路**:
   - 审批:MVP 用**简单按钮直接调激活接口通过**(不经 flow 多级/会签),M7 再升级为 cmx-flow 审批。
   - 编码:MVP 用**随机生成** code,M8 再替换为 cmx-code 规则编码。
   
   > 这样 MVP 的关键路径只剩「建模 → 激活器 → 简单审批落字典」,最快验证 reference 纯净。
5. **集群无状态**:激活器、匹配、分发均按无状态服务设计(激活幂等、任务可重入、状态走 DB/Redis)。

### API 设计约定(新增接口必须遵守)

> 承接根目录 `AGENTS.md` §四 全局通用规则第 5 条。

- **新增 REST 接口一律禁用 Path Variable**(路径参数 `/foo/{id}` 形式)。
- 资源标识、过滤、操作参数全部走 **query 参数**(`GET`)或 **JSON body 字段**(`POST/PUT/PATCH/DELETE`)。
- 路径里只允许**固定资源段**(`/api/mdm/activations`、`/api/mdm/events`),禁止**可变标识段**(`{id}`、`{code}`)。
- 批量 id 走 body(`{ "ids": [1,2,3] }`)。
- **只对新增接口生效**,既有接口(如 `/api/dct/entries/{id}`)不回溯改造。

> 本计划下 M0 之后所有 `/api/mdm/*` 端点均按此约定设计(见各阶段端点清单)。

## 三、各阶段详述(阶段目标 + 任务提纲)

> 以下任务为 **提纲级**(粒度到"做什么"),实现细节(文件清单/数据结构/代码骨架/验收用例)**待大阶段确认后在逐阶段细化文档中展开**。所有 `/api/mdm/*` 端点均遵守「禁用 Path Variable」约定(见 §一 API 设计约定)。

### M0 · MDM 域建模 + 三 crate 骨架 　`建域` `L`

**目标**:搭起 MDM 域的"地基"——元数据定义、物理表、三段式 crate 空壳、路由接入。本阶段结束时,MDM 域的主数据和申请单已可通过复用的 `/api/dct` `/api/doc` 进行 CRUD,只是还没有激活器。

**范围**:
- ✅ 做:`mdmGovernanceFields` fieldSet;`basic/dataplatform/mdm/` 域 DCT(cm_*)+ DOC(cv_mdm_apply*)定义 JSON;10 张物理表迁移;三 crate 空壳 + `ModuleRoutes` 接入。
- ❌ 不做:激活器逻辑、审批、匹配、分发、cmx-code。

**任务提纲**:
1. 在 `base_dct_meta_v1.json` 追加 `mdmGovernanceFields`(`lifecycle_status` 只 published/frozen/archived/merged;`published_version`),**只 4 值,无 draft**。
2. 新建域目录 `data/meta/definitions/basic/dataplatform/mdm/`,产出:
   - `dataplatform_dct_meta_v1.json`——主数据 DCT 定义(`cm_supplier` 头 + `cm_bank_account` 等明细)。**头表与明细表均为独立 DCT**,明细表通过普通列(如 `supplier_id`,无物理 FK,字段+索引)关联头表(代码库事实:DCT 的 parent_id 只支持本表自分级,跨表主从是 DOC 的能力)。
   - `dataplatform_doc_meta_v1.json`——变更请求 DOC 定义(`cv_mdm_apply` 头 + `cv_mdm_apply_line` 行,doc_type=`mdm_*_apply`/`mdm_*_change`,行表 `upper_id` 挂头表)。
3. compile 建物理表 + 新建迁移 SQL:治理表(`mdm_activation`/`md_audit`/`md_xref`/`md_value_map`/`md_merge_record`/`md_subscription`/`md_event_log`)。
4. 新建三 crate(仿 cmx-dct 三段式结构):
   - `cmx-mdm-model`(error/lifecycle 枚举/激活数据结构占位)
   - `cmx-mdm-store-pg`(各 store 空壳 + dct_accessor/doc_accessor 占位)
   - `cmx-mdm-api`(`impl ModuleRoutes for MdmModule`,`/mdm/*` 空路由)
5. `web-server/src/routes.rs` 接入 `.merge(MdmModule.routes())`;workspace `Cargo.toml` 注册三 crate。
6. **编码:随机生成占位**(M8 替换):激活器预留 code 生成插入点,M0/M1 期间用随机字符串填充(见 M1 任务)。

**交付物**:域 JSON ×2、迁移 SQL、三 crate 空壳、路由接入、`mdmGovernanceFields`。
**前置依赖**:无。
**验收标准**:`init_ddl`/迁移跑通 10 表;对 `cm_supplier` 走 `/api/dct/*` CRUD 通过(数据 lifecycle_status 默认 published);对 `cv_mdm_apply` 走 `/api/doc/*` 录入通过;三 crate 编译通过。
**风险**:DOC 申请单状态机后端弱(核实发现)→ M0 暂不强制状态机,留 M2 处理。

### M1 · 通用激活器 + 映射配置 　`新造①` `XL` **(V3 核心)**

**目标**:实现 V3.1 的心脏——通用激活器(读映射配置执行固定流程)+ UI 映射配置器 + **cm_* 写入唯一闸口**。本阶段结束时,手动触发即可把一份已审批的 CR 单据数据落进 `cm_*`(published)。**code 暂用随机生成**(通过 `CodeGenerator` trait 注入),M8 再接 cmx-code。

**范围**:
- ✅ 做:激活器固定流程七步(读 CR→读映射→头处理 create/update→明细处理→记审计→发事件占位→CR 归档);`mdm_activation` CRUD;UI 映射配置器;**随机 code 生成**(CodeGenerator trait + stub 实现);**dct_accessor 写入闸口**(cm_* 唯一入口,强制 lifecycle_status=published);**单事务原子**;**并发控制**(CR 互斥 + 乐观锁)。
- ❌ 不做:审批(留 M2)、匹配、分发消费、cmx-code、merge/block/flag_delete 分支(留 M3+)。

**任务提纲**:
1. `cmx-mdm-model/activation.rs`——纯逻辑层:字段搬运规则(头映射 + 明细映射 line_action=insert/update/delete)、create/update 分支(M1 只做这两类)、明细关联列回填(如 `cm_bank_account.supplier_id` ← 头表 cm_supplier.id,业务外键无物理 FK)。头字段映射**源端是 CR 头表的逐列字段**(name/tax_no/credit_code 等)+ `ext_attrs`(jsonb 合并),不再用 proposed_payload(V3.1)。
2. `cmx-mdm-model/codegen.rs`——**`trait CodeGenerator`**(V3.1 解耦设计):`fn generate(dict_code, ctx) -> String`。M1 提供 `RandomCodeGenerator` stub 实现(VRM- 前缀 + 随机串)。**M8 接 cmx-code 时只换实现,不改激活器主流程**。
3. `cmx-mdm-store-pg/activation_store.rs`——`mdm_activation` 配置读写(按 source_doc_type + cr_type 查映射)。
4. `cmx-mdm-store-pg/dct_accessor.rs`——**cm_* 唯一写入闸口**(V3.1 核心约束):激活器/合并器(M3)都经此写 cm_*,**强制 lifecycle_status='published'**;提供头/明细 INSERT/UPDATE。`doc_accessor.rs` 读 CR 头/行;`md_accessor.rs` 写 md_audit/md_event_log。
5. 激活器主流程(`activation.rs` + store 协作):七步固定流程;**单事务原子**(V3.1)——读CR→写cm_*→md_audit→md_event_log→CR归档全在一个 DB 事务,任一步失败整体回滚,不经 HTTP;新建走 CodeGenerator stub;含**幂等保护**(同一 CR 不重复激活)。
6. **并发控制**(V3.1):
   - **CR 互斥**:同一 `target_record_id` 同时只允许一个 approving 状态 CR(DB 唯一约束 `UNIQUE(target_record_id) WHERE doc_status='approving'`,变更场景)。
   - **乐观锁**:激活 UPDATE cm_* 时读 `published_version`,与 CR 发起时快照版本比对,不一致则报冲突需重审。
7. `md_audit` 写入(逐列字段新旧值 delta、source_cr_id、published_version+1)。
8. **`cmx-mdm-api` 端点**(禁用 Path Variable,id 走 body):
   - `GET /api/mdm/activations` —— 查映射配置列表(可选 query:`?sourceDocType=...&crType=...`)。
   - `POST /api/mdm/activations` —— 新增/更新映射配置(body:`{ activationCode, sourceDocType, crType, targetDict, headerMapping, lineMappings, codeRuleCode }`)。
   - `POST /api/mdm/change-requests/activate` —— 手动触发激活(body:`{ "crId": <id> }`)。激活器有两条触发路径(V3.1):① 审批型 CR→M2 的 ServiceTask;② 内部/手动 CR→本端点直接调用。
9. **前端:映射配置器**——左侧下拉(CR 单据 DOC 字段,含逐列字段)→ 右侧下拉(主数据 DCT 字段),点选对照自动生成 `headerMapping`/`lineMappings` JSON 存 `mdm_activation`;明细映射可配多条。

**交付物**:激活器(model+store+codegen stub+闸口)、`/mdm/activations` + `/mdm/change-requests/activate` 端点、映射配置器前端、`supplier_apply` 示例映射、dct_accessor 写入闸口、并发控制(CR 互斥 + 乐观锁)。
**前置依赖**:M0。
**验收标准**:配一份 `supplier_apply` 映射;构造一份"已审批"的 `cv_mdm_apply`(头表逐列 name/tax_no + 2 条银行账户行);`POST activate`(body `{crId}`)→ `cm_supplier`(published,v1,**随机 code**)+ `cm_bank_account`×2(`supplier_id` 关联回填到头表 id)落库;`md_audit` 有 create 记录;CR 状态置 activated;重复激活被幂等拦截;**单事务验证**(模拟中途失败,cm_*/md_audit/CR 全回滚无中间态);**闸口验证**(绕过激活器直写 cm_* 被拒);**乐观锁验证**(并发变更版本冲突报错)。
**风险**:① 映射表达力——90% 字段搬运够用,极复杂转换(<5%)需扩展点(预留 pre/post hook 字段);② 随机 code 的唯一性兜底(加唯一约束 + 冲突重试);③ CR 互斥的唯一约束需 partial unique index(`WHERE doc_status='approving'`),核实 PG 支持;④ 单事务跨多个 accessor 的事务上下文传递需复用 cmx-infra 事务管理器。

### M2 · 简单审批流转 + CR 录入台 　`前端+轻接线` `M`

**目标**:打通主链路 MVP——CR 录入→提交→**简单按钮审批通过→自动激活**→`cm_*` 落 published。**不接 cmx-flow**,审批就是"通过/驳回"两个按钮直接调接口。本阶段结束即验证 V3 核心架构闭环。

**范围**:
- ✅ 做:申请单状态机(draft→approving→approved→activated/rejected);**简单按钮审批**(直接调激活);CR 录入台/待办台前端。
- ❌ 不做:cmx-flow 多级审批(留 M7)、匹配、分发。

**任务提纲**:
1. **申请单状态机**(自建,核实发现的 DOC 弱点):在 cmx-mdm 层实现 `cv_mdm_apply.doc_status` 的状态转移与校验:
   `draft → approving → approved → activated`
   `approving → rejected`(归档)
   封禁非法跳转。**approved → activated 由激活器自动衔接**(审批通过即激活)。
2. **简单审批端点**(不经 flow,禁用 Path Variable,id 走 body):
   - `POST /api/mdm/change-requests/submit` —— draft→approving(body:`{ "crId": <id> }`)。
   - `POST /api/mdm/change-requests/approve` —— approving→approved,**随即触发激活器**→activated(body:`{ "crId": <id> }`)。
   - `POST /api/mdm/change-requests/reject` —— approving→rejected(归档,`cm_*` 全程不动)(body:`{ "crId": <id>, "reason": "..." }`)。
   > 这三个端点在 M7 被 cmx-flow 流程节点取代,但保留为"手动兜底"入口。
3. **驳回复活 = 克隆新建**(V3.1):驳回 CR **不从 rejected 直接复活**,而是基于原 CR 克隆一个新 CR(新 CR 的 `source_cr_id` 指向被驳回的旧 CR id,保留驳回留痕),新 CR 走完整 draft→approving 流程。端点:`POST /api/mdm/change-requests/clone-revise`(body:`{ "crId": <被驳回旧CR id> }`)。
4. 审批期间 `cm_*` 原值照旧(验证 reference 纯净);驳回 CR→`cm_*` 零变化。
5. **前端:CR 录入工作台**(复用 DOC 单据编辑器,头+行)+ **待办台**(我的申请 / 待审批 / 已办;每个待审 CR 带「通过」「驳回」按钮;驳回 CR 提供「修改重提」=克隆新建)。
6. E2E 联调:录入→提交→按钮审批通过→自动激活→查 `cm_*` published;驳回→克隆重提→再审批通过。

**交付物**:状态机、submit/approve/reject/clone-revise 端点、CR 录入台 + 待办台前端。
**前置依赖**:M1。
**验收标准**:完整 E2E——新建供应商 CR→提交→**点「通过」按钮**→`cm_supplier` 自动落 published(随机 code);变更 CR→审批→`cm_*` 字段更新 version+1;驳回 CR→`cm_*` 零变化;**驳回后克隆重提,新 CR source_cr_id 指向旧 CR,再审批通过落 published**;审批期间 `cm_*` 原值业务可用。
**风险**:状态机与激活的原子性(approve 内部调激活,需保证 approved→activated 一致或可重试);克隆重提的字段复制需正确(含明细行)。

> **MVP 里程碑**:M0+M1+M2 完成 = V3 核心架构闭环可演示(reference 纯净 + 激活器 + 按钮审批落字典)。建议此处设阶段评审,再决定 M3+ 投入。

### M3 · 匹配合并存活 　`新造②` `XL` **(最难)**

**目标**:实现 MDM 心脏的另一半——识别一物多码、自动/人工合并、字段级存活取值。

**范围**:分块→比较→双阈值裁决→合并存活,数据源是 `cm_*`(published 行),结果写回 `cm_*`(victim 置 merged,不硬删)。

**任务提纲**:
1. `cmx-mdm-model/match_algo.rs`——分块(多簇键+优先级)、比较、双阈值(≥95 AutoMerge / 80–94 Review / <80 NoMatch);**护栏**(NULL 巨簇、簇上限 500)。
2. `survivorship.rs`——字段级存活(源优先/最新/最全/质量分)。
3. `cmx-mdm-store-pg/match_store.rs`——`md_merge_record` 读写、`md_xref` 交叉引用维护。
4. **合并走激活器 merge 分支**(V3.1 关键修订:合并不绕开激活器,统一写入入口,事件不漏):
   - 管家在评审台确认合并 → 后台自动生成一个 **`cr_type='merge'` 的内部 CR** → 走**激活器的 merge 分支**(经 M1 的 dct_accessor 闸口)。
   - merge 分支:victim `lifecycle_status='merged'`(不硬删)、明细业务外键 re-parent 到 master.id(如 `cm_bank_account.supplier_id` 重指向)、`md_xref` 里 victim 引用标记 inactive、存活值 UPDATE 写回 cm_*、`survivorship_log` 记每字段来源、发 md_event_log。
   - **内部 merge CR 不走 cmx-flow 审批**(管家确认即生效),激活器由 merge-requests 端点**直接调用**(不经 ServiceTask)。
5. **`cmx-mdm-api` 端点**(禁用 Path Variable,参数走 body):
   - `POST /api/mdm/records/find-duplicates` —— 实时查重(body:`{ "dictCode": "supplier", "recordId": <id> }` 或匹配条件)。
   - `GET /api/mdm/merge-requests` —— 合并请求列表(可选 query:`?dictCode=...&status=...`)。
   - `POST /api/mdm/merge-requests` —— 确认合并(管家评审通过):body `{ masterId, victimIds, survivorship }` → 生成内部 merge CR → 调激活器 merge 分支。
6. **前端:查重候选 UI**——候选列表 + 置信度 + 合并决策。
7. unmerge 还原能力(`POST /api/mdm/merge-requests/undo`,body:`{ "mergeId": <id> }`):反向操作,亦经激活器 dct_accessor 写回。

**交付物**:匹配/存活算法、激活器 merge 分支、`md_merge_record`/`md_xref` 维护、查重+合并端点、查重 UI。
**前置依赖**:M1(激活器主流程 + dct_accessor 闸口,本阶段扩展 merge 分支)。
**验收标准**:注入重复供应商→识别一物多码;自动合并(≥95)与人工评审(80–94)正确分流;**合并经激活器 merge 分支**(统一入口,victim=merged、明细 re-parent、存活值正确、md_event_log 有记录);unmerge 可还原。
**风险**:匹配准确性(从精确匹配+单一存活起步);分块性能(N×N 不可行,护栏必须);merge 分支的明细 re-parent 需正确处理多明细表。

## 四、关键路径与并行机会

- **关键路径(MVP 主链路)**:`M0 → M1 → M2`。因审批简化(按钮直通)与编码简化(随机),**比接 flow/code 的原方案轻**——M2 从 L 降为 M。应优先保障,最快验证 V3 核心架构。
- **可并行**(均在 M2 之后,与 M7/M8 相对独立):
  - `M3 匹配` → `M4 管家台`(M4 依赖 M3)。
  - ~~`M5 分发`~~ **不急后置**,启动时与 M3/M4 相对独立(只依赖 M1)。
  - `M6 多域扩展` 是配置工作,可在 M2 后随时插入。
- **M7 / M8 最后做,彼此独立**:
  - M7 替换"触发方式"(审批),M8 替换"code 来源"(编码),互不依赖。
  - M8 受 cmx-code 就绪度约束(就绪前一直用随机 code)。
  - 两者都不影响 M3–M6 的匹配/多域能力,可与它们并行或在其后。
- **建议节奏**:先集中打 M0–M2 MVP → 阶段评审 → 再根据价值与资源决定 M3/M4 优先级 → M7/M8 择机收尾升级。
