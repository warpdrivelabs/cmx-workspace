00执行摘要 · V3 为什么再升级

V2 把变更请求的草稿写进 cm_* 主数据表（lifecycle_status='draft'），这违反了「主数据是权威 reference」的本质——把待办事项混进了员工档案。V3 坚守 reference 与 transaction 物理分离铁律：主数据只存 published，变更请求复用 DOC 单据走暂存，审批通过由激活器落字典。

🏅 V3 核心洞察：主数据是「成品库」，不是「车间」
主数据表（cm_*）是成品库——只放检验合格（published）的产品，下游直接取用。变更请求（CR 单据）是车间——原料加工（录入/审批）在这里进行，半成品不进成品库。审批通过=质检合格，激活器把成品从车间搬进成品库。V2 的错误是把车间和成品库混在一起（cm_* 里既有 published 也有 draft），V3 严格分离。

00b数据分类铁律：reference vs transaction V3 基石

这是 V3 一切设计的基石。主数据和变更请求是两类本质不同的数据，必须物理分离——这是 SAP MDG、Oracle、Informatica 的共同铁律。

0b.1 两类数据的本质区别

维度主数据（reference）变更请求（transaction）
性质权威真相，描述「实体是谁/是什么」流程性事务，描述「一次变更动作」
生命周期持续存在，相对稳定有头有尾，审批完就归档
谁来读全企业所有系统消费（高频）只在审批流里流转（低频）

01主数据认知与边界 what master data is — and is not

做主数据的第一步不是建库，而是把「主数据」从其它数据里精确地切出来。切错了边界，后面的治理、质量、分发全部落空。

🧬 V3 关键认知：变更请求(CR)是 transaction，不是 reference
CR 有发起人、有审批人、有状态流转、有生命周期终点（审批完归档）——它是一次变更动作的记录，本质是交易数据。把 CR 当主数据塞进 cm_* 是分类错误。V3 把 CR 归入 DOC 单据（transaction 载体），主数据 cm_* 保持 reference 纯净。

1.2 主数据的六个本质特征

① 唯一权威

全企业对同一实体只有一条黄金记录，MDM 是它的 System of Record。

② 跨域共享

被财务、供应链、销售、HR 多域反复引用。

③ 相对稳定

变化频率远低于交易数据，但一旦变影响面极大，须留痕。

④ 结构复杂

属性多、分组多、常带层次，且多语言/多视图。

⑤ 多源汇入

常同时存在于 ERP、CRM、SRM、旧系统，需匹配合并。

⑥ 需要治理

价值来自「被信任」，须有 Owner、标准、审批、质量闭环。

1.3 主数据的分层视图（头表 + 明细表）

一条主数据常不是「一张扁平表」，而是「主体 + 明细」分层——这正是 V3 用 DCT 头表 + 明细表（用业务命名的普通外键如 supplier_id 挂接）建模的基础：

主数据对象（如：供应商 = cm_supplier 头表 + 明细表） ├─ 标识层 id(内码) + code(外码) + lifecycle_status(只 published/frozen/archived/merged) ├─ 通用属性 name/简称/税号/统一社会信用… ← cm_supplier 头表自有列 ├─ 明细:银行账户(多个) ──→ cm_bank_account (supplier_id → cm_supplier.id,业务外键) ├─ 明细:资质证书(多个) ──→ cm_qualification (supplier_id → cm_supplier.id,业务外键) ├─ 明细:收货地址(多个) ──→ cm_address (supplier_id → cm_supplier.id,业务外键) └─ 层次归属 所属分类(parent_id 树,selfHierarchy) · 所属组织(scope_type/entity_id) ★ 区分两类关系: · 明细表挂头表 = 业务命名普通外键(如 supplier_id),不配 selfHierarchy · 头表自身树形(科目树/组织树)才用 selfHierarchy + parent_id(同表自引用) 两类关系并存但语义不同,不可混用

05标准与编码规则体系 standards & coding

V3 编码引擎引用独立方案 cmx-code（七段/断号补偿/反查 max），不在本次开发范围。MDM 域定义里只 codeRule.ruleCode 引用，cmx-code 就绪后，激活器在步骤3内部调用 cmx-code 生成 code（通过 mdm_activation.codeRuleCode 配置），不依赖 DCT 钩子（cmx-dct 的 write.rs 没有 before_save/after_save 钩子点）。

5.1 编码三铁律（由 cmx-code 保证）

  1. 编码即身份，永不回收：作废走冻结/归档，号段不释放（防一码多物）
  2. 内码 ≠ 外码：cm_*.id（bigint 内码）作关系锚点；code 是可读外码
  3. 规则可版本化：cmx_code_rule.valid_from/to，旧对象留旧码

06主数据全生命周期（暂存/激活分离）V3 核心

V3 根本修正 V2 把 draft 写进 cm_*，V3 严格分离：草稿在 CR 单据（暂存区），激活后才进 cm_*（激活区）。这是 SAP MDG Staging/Active 模型的直接落地。

6.1 两套状态机（彻底分离）

CR 单据状态机（暂存区 · DOC）

变更请求单据自己的生命周期，走 cmx-flow 审批：
draft 草稿→ approving 审批中→ approved 已通过
approved→激活→ activated 已激活（归档）
approving→驳回→ rejected 已驳回（归档）
rejected→克隆新建→ draft（新 CR，source_cr_id 指向旧 CR）
CR 状态存在 cv_header.doc_status，审批走 cmx-flow。
驳回后重提交：不从 rejected 直接复活，而是基于原 CR 克隆新建（保留驳回留痕，新 CR 的 source_cr_id 指向被驳回的旧 CR id），新 CR 走完整 draft→approving 流程。

主数据状态（激活区 · DCT cm_*）

主数据自己的状态，永远没有 draft/pending：
published 已发布→ frozen 冻结→ archived 归档
published→合并→ merged 已合并
cm_*.lifecycle_status，只这四个值。published=黄金记录。

6.2 新建 vs 变更：两种激活场景

定义态：新建主数据（对齐 Oracle NIR）

  1. 申请人录入 CR 单据（头存全量提议值，行存明细）
  2. 提交 cmx-flow 审批（cm_* 不动）
  3. 审批通过 → 激活器 INSERT cm_*（published, version=1）
  4. CR 状态=activated（归档）
无红线标记，产出全新对象。

变更态：修改已发布（对齐 Oracle Change Order）

  1. 申请人录变更 CR（行存 field_deltas 新旧值）
  2. 审批期间 cm_* 原值照旧（业务照常用）
  3. 审批通过 → 激活器 UPDATE cm_*（version+1）
  4. md_audit 记新旧值 delta（红线可追溯）
带红线，版本+1，全程留痕。

❌ WASM 服务编排

❌ 纯声明式 JSON

17c.2 通用激活器的固定流程（所有主数据共用）

BPMN ServiceTask 节点触发(激活器是 JavaDelegate impl) │ ├─ 1. 读 CR 单据:doc_accessor 读 cv_mdm_apply(头) + cv_mdm_apply_line(行) │ ├─ 2. 读激活映射:activation_store 读 mdm_activation(按 doc_type + cr_type) │ ├─ 3. 头处理(按 header_mapping): │ ├─ 新建(create): code=cmx-code生成(codeRuleCode) → INSERT cm_*(published,v1) │ └─ 变更(update): UPDATE cm_* SET 按映射的字段 WHERE id=target_record_id (v+1) │ ├─ 4. 明细处理(按 line_mappings,遍历 cv_mdm_apply_line): │ ├─ line_action=insert: INSERT cm_明细表(业务外键=头表id,如 supplier_id) │ ├─ line_action=update: UPDATE cm_明细表 │ └─ line_action=delete: cm_明细表 lifecycle_status='archived' │ ├─ 5. 记审计:md_audit 写 create/update 记录(新旧值,source_cr_id) │ ├─ 6. 发事件:md_event_log 追加(created/updated,供订阅方拉取) │ └─ 7. CR 归档:cv_mdm_apply.doc_status='activated'
🔒 事务边界（单事务，全流程原子）
激活器全流程（读CR → 写cm_*头/明细 → md_audit → md_event_log → CR归档）必须在单个 DB 事务里完成。激活器直接复用 cmx-infra 的事务管理器，经 cmx-mdm-store-pg 的 dct_accessor/doc_accessor/md_accessor 共用同一事务上下文，不经 HTTP。任一步失败整体回滚——不会出现"cm_* 已写但 md_audit 没记"或"CR 没归档"的中间态。
⚡ 并发控制（变更场景）
① CR 互斥：同一目标实体（target_record_id）同时只允许一个 approving 状态的 CR（DB 唯一约束 UNIQUE(target_record_id) WHERE doc_status='approving' 或查询拦截），避免并发变更打架。
② 乐观锁：激活器 UPDATE cm_* 时读 cm_*.published_version 做乐观锁——若 CR 发起时快照的版本号与当前 cm_* 的 published_version 不一致（中途被别的激活改过），则报冲突，CR 需重审（不允许盲改覆盖）。

merge 分支（合并走激活器，见 §16.3）

合并不绕开激活器：管家在评审台确认合并 → 后台自动生成一个 cr_type='merge' 的内部 CR → 走激活器的 merge 分支（victim 置 merged + 明细业务外键 re-parent + 发事件）。合并审批可简化（管家确认即生效，或配置免审批）。内部 merge CR 不走 cmx-flow 审批（管家确认即生效），激活器由 merge-requests 端点直接调用（不经 ServiceTask）。因此激活器有两条触发路径：① 审批型 CR→ServiceTask(JavaDelegate)；② 内部/手动 CR→直接调用。统一写入入口，事件不漏。

未来生效（effective_date）分支

CR 可带 effective_date（DATE，可空）。审批通过时若 effective_date > 今天，激活器记 pending（CR 状态置 approved 但不立即落 published），由定时任务到期再触发激活落字典。用于"未来生效"场景（如组织调整生效日、新科目次月启用）。集群安全：定时任务经 cmx-job 调度，集群下用分布式锁（或 SELECT FOR UPDATE + doc_status CAS：UPDATE cv_mdm_apply SET doc_status='activating' WHERE id=? AND doc_status='approved'）保证同一 CR 只被激活一次，避免多节点重复激活。

批量模式

一次 CR 可挂多行（批量新建/变更，如一次性导入 N 个供应商）。区分两种规模：
① 单 CR 内多明细行（一次录入若干条）= 单事务原子：激活器在同一事务内循环处理每行，全部成功才整体提交，任一行失败整体回滚；
② import_export 大批量装载（成百上千行）= 按 chunk 分批提交：如每批 200 行独立事务，单 chunk 失败不影响已提交 chunk，错误行写入错误表不阻断。
大批量不走单事务，避免长事务持锁。DCT import_export 批量装载也走此批量模式（生成内部批量 CR），不直写 cm_*。

22.1 风险

  • 激活器映射的表达力：90% 场景字段搬运够用；极复杂转换（<5%）可能需扩展点。缓解：mdm_activation 预留 pre/post hook 字段。
  • CR 复用 DOC 的结构适配：DOC 原为会计凭证设计，CR 借用其头/行/审批骨架但不碰借贷结构。MDM 域自定义 doc_type + fields，不污染 fi/。
  • 匹配合并是难点：M3 从精确匹配+单一存活起步；分块护栏必须有。
  • cm_* 写入收归激活器（/api/dct 对 MDM 域只读，底线）：dct_accessor 是唯一闸口，强制 lifecycle_status='published'。所有草稿必须走 CR 单据，激活器是唯一写入 cm_* published 的入口。DCT import_export 批量装载也走激活器批量模式（§17c），不直写 cm_*。
  • 引擎不认识具体域：激活器按映射配置驱动，无 if 供应商/科目分支。
🧭 V3 一页纸总结
V3 的根本修正：坚守「reference 与 transaction 物理分离」——主数据（DCT cm_*）只存 published，变更请求（CR）复用 DOC 单据走暂存，审批通过由通用激活器（读 UI 配置的映射）把单据数据落进字典。三者在 MDM 独立新域（basic/dataplatform/mdm）协同：DOC 暂存（cv_*）→ 激活器（cmx-mdm）→ DCT 激活（cm_*）。废弃 md_change_request/md_code_rule；编码引用 cmx-code。复用率 ~88%（DCT+DOC+平台骨架），真新造收敛为后端 3 件（激活器/匹配/分发）+ 前端 4 件（配置器/查重/红线/待办）。关键路径：M1 激活器 + M2 CR↔flow 接线 + M3 匹配。
