## 一、背景与目标

### 1.1 现状（M2 简单审批 = 裸桩）

- CR 状态机：`draft →(submit)→ approving →(approve=直接激活)→ activated`；`reject → rejected`（可改后重提）；`abort → aborted`（`cr_service.rs:6-10`）。
- **无审批人**：`mdm_cr_approve` 对任何调用者放行，仅状态校验（`handlers/cr.rs:81-96`）；
- **无审批留痕**：`RejectBody.reason` 反序列化后直接丢弃（`cr.rs:219-227`）；
- approve 与激活强耦合单事务（`activate.rs` 七步）；前端两处流程占位（`cr-form.js:313-317`、`cr-todo.js:33`）。

### 1.2 目标（M7）

1. CR 提交后自动发起流程实例（bizLink 绑定单据坐标）；
2. 审批人在**流程待办中心**办理（cr-form 审批视图 + task-form 统一审批控制台），后续多级/会签改 BPMN 零改代码；
3. **四眼原则（结构保证）**：流程含「发起人确认」与「审批」两个不同节点，任何 withdraw/退回的落点都不可能是审批节点；审批节点候选池=角色，且 flow 层办理授权校验（见 T0b）使申请人无法办理审批任务；
4. 流程结束后自动回写 CR：通过 → 激活器落 `cm_*`；驳回 → rejected；取消 → aborted；
5. 审批意见与**办理人**落流程任务表，cr-form 流程占位卡替换为真实审批历史；
6. 保留 M2 手动端点（approve/reject/activate）作运维兜底（默认关闭，D7）；
7. 双部署模式兼容：反代模式（当前）全功能；内嵌模式功能可用、flow 层授权与办理人留痕退化（见 §5.6 限制披露）。

### 1.3 非目标（本期不做）

- 按 docType 路由不同流程定义（扩展位见 R5）；
- 多级审批/会签的 BPMN 本身；
- 用户通知（新待办/驳回提醒，后续迭代）；
- 分发订阅（M5）；
- 「撤回后修改单据数据再重提走同一实例」——撤回即终止实例回草稿（D6），重提发新实例；
- flowengine 内嵌形态的 auth 集成（FlowModule 挂 flow auth_middleware，记 flowengine backlog，本期仅披露）。

### 2.3 部署拓扑约束（决定回写通道设计）

- **跨进程（当前反代模式）**：原 M7 规划「激活器=JavaDelegate 绑定 ServiceTask」不可行（delegate 跑在 flow-server 进程；`FLOW_DELEGATE_URL` 全局单值；进程内 delegate 无法事后注册，`engine.rs:214-224`）。改用 webhook 回调。
- **数据落点**：MDM 表库由请求头 db_id 路由（默认业务库），流程表固定 fico-db——MDM 不对流程表做 SQL 假设，一律 HTTP（亦是跨进程唯一通路）。webhook 回调内用 `resolve_db_id(None)` 定位 CR；多库路由场景列 R2。
- MDM 调流程 API：**回环 HTTP 本进程 `/api/flow/*`**——双壳透明，MDM 零感知部署模式。

### 3.2 状态机映射

| CR 状态 | 触发 | 流程侧语义 |
| --- | --- | --- |
| draft → approving | submit（抢占式条件 UPDATE，**同语句刷 update_time**，0 行=冲突拒绝） | 发起实例 + 代 confirm apply 节点（D3）；businessKey=doc_no |
| approving → activating → activated | webhook/懒同步：completed + lastDecision≠reject | 抢占（approving→activating，0 行跳过）→ `store::activate`；失败回置 approving 可重试 |
| approving → rejected | completed + lastDecision=reject | 仅当 CR=approving；改后重提发新实例 |
| approving → aborted | terminated（运维台 cancel；**载荷 state 须=TERMINATED**，拦幽灵事件） | 仅当 CR=approving |
| approving → draft | MDM 撤回端点：cancel + set draft | 与 terminated webhook 双向竞争均收敛（§3.2 D6） |
| approving（不变） | 任务级退回 reject_task | 实例仍 ACTIVE；首版双节点下 apply↔review 可退，退回 apply=回发起人重确认（语义正确） |
| — | 引擎 withdraw（「我发起的」取回按钮） | **落点=apply 节点**（流程定义保证，D3）——发起人重新确认后仍须经 review；四眼保持 |

**四眼原则论证（结构层）**：流程含 apply（直派发起人）与 review（候选池）两个节点，`first_user_task_from_start`=apply——任何 withdraw 只能回到 apply；审批动作只能发生在 review；发起人不在 review 候选（角色物化），且 T0b 授权校验拦截越权 complete。**授权层**（T0b）：complete/withdraw/cancel 校验 `tenant::current_user()`（服务端身份，不可经 body 伪造）。**管理层**：角色分离≠人员分离——admin 预分配 mdm_approver 仅为演示便利，生产须人员分离（部署约束，见 D5）。

## 四、核心设计决策

### D1. 发起通道：MDM 后端回环 HTTP + 抢占式提交 + 信封判据

submit handler 六步：

1. **抢占**：`try_set_cr_status` 条件 UPDATE `SET doc_status='approving', update_time=now() WHERE id=? AND doc_status IN ('draft','rejected')`（**必须同语句刷 update_time**——懒同步 5 分钟窗口以 submit 时刻起算；与 doc 平台 B2 乐观锁无冲突：approving 态无编辑保存并发，回退 draft 后前端重装载取新基线），0 行 → 409「单据状态已变更，请刷新」；
2. 读 CR 头；
3. **防孤儿实例**：`biz_instances` 查到 ACTIVE 实例 → 回滚抢占，409「存在未终结的流程实例」（不自动 cancel——其 terminated 迟到事件会污染新轮次，见 D2 规则 3 窗口分析；孤儿由运维台/兜底端点处理）；
4. **发起**：回环 `POST /api/flow/instances`（`X-API-Key`+`X-Delegated-User-Token`=发起人 JWT），variables=`{initiator, docNo, docType, targetDictCode, crType, subjectName}`，bizLink=`{bizTable:'cv_mdm_apply', bizId, role:'approval'}`；
5. **判据**：HTTP 2xx 且信封 code==0（flow 业务错误=200+code=1）；失败 → `try_set_cr_status` 回滚（approving→原状态）→ 502 + flow msg；
6. **代确认 apply 节点**：从发起响应 data.tasks（同步创建、视图含 `{id,nodeBpmnId,assignee,completed}`，`views.rs:96-126,221`）找 apply 节点任务 → 回环 `POST /tasks/{taskId}/complete` body `{instanceId, operator: initiator}`（以发起人身份透传其 JWT——T0b 授权下合法：apply 直派 assignee=initiator）。**幂等语义**：重试命中已办任务返回 200+code=1（TaskNotActionable）→ flow_client 归类 AlreadyDone=幂等成功（防误判为故障）。其它失败**不回滚**（优雅降级：apply 任务留发起人待办手动 complete；error 日志）。

回滚本身失败：error 日志（含 cr_id），接口返回 502。

**否决项**：前端发起（孤儿 approving，弱一致）；进程内直调 engine（破坏双壳）。

### D2. 完成回写通道：webhook 主 + 懒同步兜 + 手动兜（三层）

回写统一入口 `sync_flow_result(instance_id, event)`，**五条防御规则依序校验**：

| # | 规则 | 防什么 |
| --- | --- | --- |
| 1 | `GET /instances/{id}/biz` → bizTable≠cv_mdm_apply 或 definitionKey≠mdm_cr_approval（webhook 载荷自带 definitionKey/state 可先过滤）→ 忽略 | 其它业务流程事件 |
| 2 | **当前实例校验**：`biz_instances` 倒序第一条 instanceId ≠ 事件 instanceId → 忽略 | 旧实例（驳回/撤回前轮）迟到/重复事件污染新轮次。窗口安全：link 落库先于事件 emit（§2.1），新实例绑定时必为倒序第一条；MDM 永不自动 cancel（D1-3）消除了「cancel 与 start 之间」的错配窗口 |
| 3 | completed：`instance_variables` → lastDecision=='reject' → set rejected（仅当 CR=approving）；否则 → 抢占 activating → activate | 分流；三方并发（webhook/懒同步/手动）抢占收敛 |
| 4 | terminated：**载荷 state==TERMINATED** 且 CR=approving → set aborted | 幽灵事件（对已终态实例 cancel 的幂等 Ok 仍发事件，载荷 state=快照态≠TERMINATED 时拦截） |
| 5 | 全部规则通过才执行写动作；所有写动作走 `try_set_cr_status` 抢占 | 重复投递、多副本并发 |

### D3. 流程定义：双节点通用审批流（apply + review）

- key=`mdm_cr_approval`（由 `<process id="mdm_cr_approval">` 派生）；
- 结构：
```xml
<process id="mdm_cr_approval" cmx:withdrawPolicy="lenient">
  start → userTask(apply,  cmx:candidates="initiator",          cmx:formKey="mdm.cr.review")
        → userTask(review, flowable:candidateGroups="mdm_approver", cmx:formKey="mdm.cr.review")
        → exclusiveGateway(${lastDecision == 'reject'}) → reject: end / 默认: end
</process>
```
- **apply 直派用 `cmx:candidates="initiator"`**（关系型候选表达式）：普通 userTask 的 assignee **不做 `${}` 插值**（第三轮评审实证，`engine.rs:2180-2232` 仅多实例路径插值），写 `${initiator}` 会落成字面量断掉「待我办」/代确认授权/withdraw 口径三处；candidates 表达式经 resolver 解析为 `[initiator]` 单人 → `decide_assignment` 直派 assignee=initiator ✅；
- **`cmx:withdrawPolicy="lenient"` 必须声明**：默认 strict 下「任何环节已办结即拒取回」——MDM 代确认把 apply 置 completed 后，「取回落 apply」将恒被拒（第三轮阻断2）；lenient 允许发起人中途取回，落点=apply（`first_user_task_from_start`），发起人重新确认后仍须过 review，四眼保持。部署脚本 validate 步骤**断言**两属性存在；
- apply 节点复用同一表单绑定（撤回/取回后的重确认视图）；
- review 驳回用 complete(decision='reject')+网关；reject_task（退回）在双节点下=退回发起人重确认（语义正确）；
- 部署：BPMN 资产 `cmx-container/data/flow/definitions/mdm_cr_approval.bpmn` + 部署脚本（§5.2）；不进 flowengine 代码 seed。

### D4. 审批表单：复用 cr-form 作 content，操作交 task-form 宿主

- 绑定注册：`formKey='mdm.cr.review'`，kind='native'，nativePage='portal.mdm.cr-form'，**nativeView 留空**（回退 content）；apply/review 两节点同 formKey；
- cr-form 适配（§5.3）：装载入口**先判 `formMode==='approve'`**（短路在 mode 解析之前），忽略注入的 `mode:'task'`（须同时覆盖 `ctxGet('mode')` 与 `p.mode` 两来源）；`bizId` 优先 `crId`；approve 态=只读+diff+隐藏全部自有操作按钮（draft/rejected 与 approving 两套面板分支都处理）。

### D5. 审批人：IAM 角色 `mdm_approver` 候选池 + 部署自检 + 人员分离口径

- 迁移：`cmx_role` 加 mdm_approver + `cmx_user_role` 给 admin 预分配（幂等）——**admin 预分配仅为开发/演示便利；生产环境四眼按「人员分离」口径要求申请人与审批人非同一人（角色分离是控制层，人员分离是管理层部署约束）**；
- 候选 start 时物化——部署脚本自检角色成员 >0 否则中止；
- 后续按域/岗位路由：改 BPMN 候选表达式，代码零改。

### D6. 撤回：MDM 自有端点 = flow cancel + CR 回草稿

- `POST /api/mdm/change-requests/withdraw`：校验当前用户=CR 创建人 且 CR=approving → 查当前实例：**非 ACTIVE → 先 `sync_flow_result`（对齐状态）再按 CR 终态返回 409「流程已办结，不可撤回」**（防对已通过审批的静默丢弃）→ ACTIVE 则 flow `cancel`（body `{reason:'申请人撤回'}`）→ `set_cr_status(draft)`；
- 与 terminated webhook 双向竞争均收敛：webhook 先到→aborted 随后 draft 覆盖；draft 先行→规则 4 跳过（CR 非 approving）；
- 引擎 withdraw 不作为 MDM 撤回通道（其「回起点重办」语义在首版即 apply 节点重确认，与「回草稿改数据」诉求不符——需要改数据的走 cancel 重提）；
- 「我发起的」列表另有「撤销」（cancel）按钮：申请人撤销 → CR=aborted 终态（放弃语义，与撤回=回草稿并存）；文档注明差异。

### D7. M2 端点：保留但默认关闭

| 端点 | 处置 |
| --- | --- |
| submit | 改造（D1 六步） |
| approve/reject/activate | 新增 `[mdm.flow].manual_override_enabled`（默认 false→403）；开启时可用（明确降级操作）；Swagger 标注「兜底专用」 |
| abort | draft→aborted 保留；approving 作废走流程 cancel |
| 新增 withdraw / flow-status / flow-history | D6 / §5.1 |

### D8. 鉴权与安全

- MDM→flow（回环）：`X-API-Key` + `X-Delegated-User-Token`（发起/代确认透传发起人 JWT；其它操作透传当前用户 JWT）；
- flow→MDM（webhook）：`[auth].whitelist` 放行 `/api/mdm/flow/callback` + HMAC 验签（失败 401）；
- flow 层授权（T0b，flowengine）：withdraw 校验 current_user==body.user；cancel 校验 current_user==variables.initiator（或后续扩展运维角色）；complete 校验 current_user∈任务 assignee∪候选——**以 tenant::current_user()（服务端解 JWT）为鉴权依据，body.operator 仅作留痕**（不可经 body 伪造身份）。

### 5.4 懒同步与幂等（兜底闭环）

触发点：cr-todo 列表加载、cr-form 详情打开。

| 发现 | 动作 |
| --- | --- |
| CR=approving，实例 COMPLETED | sync_flow_result（规则 3） |
| CR=approving，实例 TERMINATED | sync_flow_result（规则 4） |
| CR=approving，无实例，update_time>5min | 回退 draft（submit 崩溃窗口 a 自愈；update_time 由 try_set 刷新=submit 时刻，10s 发起超时下 5min 窗口充分且不与进行中 submit 竞争） |
| CR=approving，无实例，≤5min | 仅报告 |
| **CR=activating，实例 COMPLETED** | **重试 activate**（幂等校验接受 activating；抢占后崩溃+webhook 重试耗尽的自愈，V2 缺口修正） |
| CR=activating，实例 TERMINATED | set aborted |
| CR=activating，其它 | 不动，标记异常（仅 manual_override 场景可见） |
| CR∈{draft,rejected,activated,aborted} | 不查不修 |

并发总述：所有状态迁移走 try_set 抢占（0 行=他人已处理）；activate 业务幂等兜第二层；webhook 重投/迟到/错配、多副本、三方并发均收敛。submit 崩溃窗口 b（draft+ACTIVE 孤儿）：重提被 D1-3 拒绝提示，运维台 cancel 后重提。

### 5.5 失败场景与补偿矩阵

| 场景 | 现象 | 补偿 |
| --- | --- | --- |
| 发起失败（含定义未发布） | submit 502（msg 含 flow 明细），CR 已回滚 | 部署后重试 |
| submit 崩溃窗口 a：approving 落库、实例未起 | approving 无实例 | 懒同步 5min 后回退 draft |
| submit 崩溃窗口 b：实例已起、状态回滚失败 | draft+ACTIVE 孤儿，重提 409 | 运维台 cancel → 重提；或 manual_override |
| 代确认 apply 失败 | apply 任务留发起人待办 | 手动 complete 即继续（非故障） |
| webhook 丢失/重试耗尽 | approving/activating 停滞 | 懒同步自愈（含 activating 重试行） |
| webhook 重复/迟到/错配/幽灵 | — | 五规则拦截 |
| 三方并发回写 | — | try_set 抢占单赢家 |
| 角色无成员 | 部署自检中止；已发起则任务不可见 | cancel 旧实例重提（候选不回填）；部署自检为主防 |
| 审批人未认领 | 任务在候选池 | 「待我认领」+ 催办 |
| 发起人撤回 | cancel + draft | terminated 迟到被规则 4/竞争收敛 |
| 发起人经「我发起的」取回（withdraw） | 实例回 apply 节点 | 发起人重确认后仍走 review（四眼保持）；「撤销」则 CR=aborted |
| activate 七步失败（抢占后） | CR 停 activating | sync 回置 approving；懒同步/webhook 重投/手动重试 |
| flow-server 宕机 | submit 502；webhook 断 | 重试；恢复后懒同步自愈 |

### 6.3 验收标准（E2E 手动场景）

1. 新建 CR → 提交 → admin 在「待我认领」看到 **review** 任务（apply 已被代确认，无感）；
2. 任务打开 = cr-form 审批视图（只读+diff，无自有按钮）+ 审批控制台；同意+意见 → CR=activated，`cm_supplier` published 数据更新，md_audit 留痕；流程历史含办理人/意见；
3. 驳回+意见 → CR=rejected；流程历史显示驳回意见；改后重提 → 新实例（历史分段）；
4. 撤回：提交后 cr-todo 撤回 → 实例 TERMINATED、CR=draft（webhook 迟到不影响）；改后重提 → 正常审批；
4b. **双向时序**：①「我发起的」取回（withdraw，落 apply）→ 再在 cr-todo 点撤回（cancel+draft）→ 正常收敛；② 先 MDM 撤回（实例 TERMINATED）→ 再在待办点「取回」→ 引擎报「实例非进行中」toast（预期行为）；
5. **四眼验证（UI 全路径）**：申请人在「我发起的」点「取回」→ 任务落 **apply 节点**（lenient 策略放行；发起人重新确认），确认后仍须 review 审批；申请人直调 complete review 任务 → T0b 授权 403；申请人（无角色）在「待我认领」看不到 review 任务；
6. 越权验证：用户 B 尝试 cancel 用户 A 的实例 → 403；
7. webhook 停用 → 审批通过后打开 cr-todo → 懒同步推到 activated；
8. 双击/并发提交 → 仅一次成功；
9. manual_override 关→403；开→可用（降级演练）；
10. 内嵌模式回归：注释 flow url 重启 → 场景 1-2 功能通（留痕办理人退化已知）；完毕恢复反代。

## 七、风险与限制

| # | 风险/限制 | 应对 |
| --- | --- | --- |
| R1 | webhook 无持久化；`instance.completed` 仅 complete_task 路径发出 | 懒同步+手动兜底；首版流程全部完成经 complete_task ✅；多级/定时扩展需 flowengine 补发射点（backlog） |
| R2 | callback 无用户头，db_id 无法还原 | callback 用默认业务库；多库路由场景暂不支持流程集成（文档标注）；懒同步在用户上下文内可覆盖 |
| R3 | cr-form 回归风险 | view 态复用+props 分支收敛一处；三态回归自查清单 |
| R4 | 一单多实例历史多段 | flow-history 分段展示 |
| R5 | 无按 docType 差异化流程 | definition_key 全局值+BPMN 网关 variables 分流；后续挂 mdm_activation（扩展位） |
| R6 | submit 两次回环往返时延 | 前端 loading；timeout 10s 为异常上界 |
| R7 | lastDecision 实例级变量多环节覆盖 | 首版 review 单审批环节决定网关 ✅；多级扩展改环节局部 decision（注记） |
| R8 | task-form「退回」在 apply→review 双节点下语义=退回发起人重确认 | 语义正确；多级后自然泛化 |
| R9 | initiator 与 flow user 口径 | 统一用户 id 字符串 |
| R10 | 集群 webhook 单地址 | 指 LB/VIP；抢占幂等多副本安全 |
| R11 | **内嵌模式授权/留痕退化**（current_user()=None → fail-open+operator 空） | 当前部署=反代（完整生效）；内嵌集成记 flowengine backlog；验收场景 10 区分验证 |
| R12 | **「人员分离」是部署约束非代码强制**（admin 演示环境=申请人兼审批人） | D5 口径说明；生产 IAM 分配时执行人员分离原则；T0b 保证「角色外人员」在 auth 生效时不能审批（auth 未启用/验签失败的缝隙见 R13） |
| R13 | T0b 授权的生效边界：**auth 中间件已挂载且委托令牌验签通过**才可信；验签失败（None）下 complete/withdraw 拒绝、cancel 放行（服务通道）；内嵌形态（auth 未挂载）整体 fail-open | AUTH_ENABLED 分层判定（§5.6）；验收场景含「伪造 body.user 被拒」；fail-open 时打 error 告警日志 |
| R14 | T0b 为 flowengine 行为变更，可能影响现有使用者（demo/测试直调 complete 不带身份） | demo :8090 未挂 auth（fail-open 不受影响）；反代模式页面办理走门户带身份→开发时验证 demo 任务办理人身份匹配；flowengine 侧补集成测试 |
| R15 | flowengine backlog（本期披露不做）：其余任务端点授权（reject/transfer/delegate/add_sign/urge/claim）、cancel 幂等幽灵事件引擎侧修复、内嵌形态 auth 集成、多级/定时流程的 instance.completed 发射点 | 记入 §5.6 披露行，后续迭代 |
