🏅 贯穿全案的核心概念：黄金记录（Golden Record）
来自各源系统的同一实物的多条记录，经匹配（Match）识别为同一对象、合并（Merge）成一条、由存活规则（Survivorship）逐字段选出最可信取值，形成一条企业唯一权威记录。在 V2 里，黄金记录不再是独立的 md_golden 表，而是 MDM 域 DCT 物理表里 lifecycle_status='published' 的那批行——它的建模、存储、查询全部复用 DCT 机制，MDM 只管「谁成为黄金记录、谁被合并、谁被分发」。

0b.1 DCT 定义 JSON 描述了什么 —— 一份完整的实体建模

以 data/meta/definitions/fi/cmxfico/gl/cmxfico_dct_meta_v3.json 为例，每个 dictionaryTables[] 元素就是一个实体的完整建模：

{
  "dictMeta": {
    "dictCode": "gl_account",           // 字典码 = 实体码
    "dictName": "总账科目",
    "dictKind": "BUSINESS",            // 业务主数据 / CLASSIFY 分类 / GROUP 分组 / RELATION 关系
    "tableName": "cf_gl_account",       // 物理表名 → compile 后 CREATE TABLE
    "idField": "id", "codeField": "code", "labelField": "name",
    "selfHierarchy": true,              // 树形字典 → 自动维护 parent_id/full_path/level_no/is_leaf
    "parentField": "parent_id",
    "codeLength": 20,
    "codeRule": { "mode":"manual", "uniqueCheck":true }  // 编码规则(声明已就位,引擎未实现=V2要补)
  },
  "fields": [                            // 本实体自有业务列
    { "name":"coa_id", "dataType":"bigint", "refDict":"coa", ... },  // 外键引用另一字典
    { "name":"account_type_code", "enumValues":[...], ... },    // 取值域
    { "name":"balance_direction", "dataType":"varchar", "fieldLength":2, "nullable":false }
  ],
  "baseFieldSet": "dictionaryCommonFields",    // 引入 id/code/name/sort_no/status 公共列
  "hierarchyFieldSet": "dictionaryHierarchyFields",// 引入 parent_id/full_path/level_no/is_leaf 层级列
  "auditFieldSet": "dictionaryAuditFields",     // 引入 create_by/time update_by/time
  "effectiveFieldSet": "dictionaryEffectiveFields",// 引入 effective_from/to 期间有效
  "uniqueKeys": [["coa_id","code"]],            // 唯一键 → 编译为物理唯一索引
  "fieldSetOrder": [...]                        // 列合并/显示顺序
}

这就是一份完整的实体建模：列/类型/长度/取值域/外键/树形/唯一键/生效期/审计全在里面。compile 时（cmx-model-deploy/src/compile.rs:316 compile_dct）把它转成 TableDefine，再由 cmx-metadata/executor.rs:411 执行真实 CREATE TABLE cf_gl_account(...)。

0b.3 后端根本没有 metaKind:MDM

🔬 全库勘探：kind 字面量统计
在 cmx-model-* 全 crate 里 grep kind 字面量，频次为：DCT×24 · DOC×19 · SEED×15 · MENU×13 · RPT×11 · BASE×9。"MDM" 与 "FLX" 作为 kind 字面量命中为 0。

01主数据认知与边界 what master data is — and is not

做主数据的第一步不是建库，而是把「主数据」从其它数据里精确地切出来。切错了边界，后面的治理、质量、分发全部落空。

1.1 三类数据的界分

数据类别定义典型例子在 cmx 里的对应
主数据
Master Data		跨系统、跨流程共享的核心业务对象，描述「业务实体是谁/是什么」客户、供应商、物料、会计科目、成本中心、组织、员工、银行DCT dictKind:BUSINESS 物理表 cf_*
交易数据
Transaction Data		描述某一时刻发生的业务活动，引用主数据销售订单、采购单、会计凭证、发货单、付款单DOC 单据 物理表 cv_*
参考数据
Reference Data		用于分类/取值约束的小型受控码表，主数据的「取值域」国家、币种、计量单位、行业分类、税码、状态码DCT dictKind:CLASSIFY/ENUM
💡 V2 修正：三类数据在 cmx 里本就由 DCT/DOC 承载
V1 把主数据当成需要「新 kind」的全新事物。但勘探表明：主数据= DCT 的 BUSINESS 字典，交易数据= DOC 单据，参考数据= DCT 的 CLASSIFY/ENUM 字典。三类数据的界分在 cmx 现有架构里早已清晰——这进一步证明 MDM 不需要新 kind，它只是给 DCT 主数据字典补上「治理能力」。

1.2 主数据的六个本质特征

① 唯一权威

全企业对同一实体只有一条黄金记录，MDM 是它的 System of Record，其它系统是消费者。

② 跨域共享

被财务、供应链、销售、HR 多域反复引用，是各系统间的「连接键」。

③ 相对稳定

变化频率远低于交易数据，但一旦变（如客户改名/合并）影响面极大，须留痕。

④ 结构复杂

属性多、分组多、常带层次（组织树、科目表、物料分类），且多语言/多视图。

⑤ 多源汇入

常同时存在于 ERP、CRM、SRM、旧系统，天然产生重复与冲突，需匹配合并。

⑥ 需要治理

其价值来自「被信任」，因此必须有 Owner、有标准、有审批、有质量闭环。

1.3 主数据的分层视图（与 DCT 分层同构）

一条主数据在 MDM 内不是「一张扁平表」，而是分层组织的。这与 DCT 的 dictMeta + fields + fieldSet 分层建模天然同构：

主数据对象（如：供应商 = cf_bus_partner DCT 字典） ├─ 标识层 id(内码) + code(外码) + status + lifecycle_status ← dictionaryCommonFields + V2扩展列 ├─ 通用属性 name/简称/税号/统一社会信用… ← fields[] 自有业务列 ├─ 分组属性 财务视图(付款条件) · 采购视图(评级) · 物流视图(地址) ← fields[] + viewGroup 分组(待补) ├─ 层次归属 所属分类(parent_id 树) · 所属组织(scope_type/entity_id) ← hierarchyFieldSet + scopeFieldSet └─ 关系 集团母子 · 客商合一 ← dictKind:RELATION 关系字典

02现状痛点与建设价值 why it always hurts

几乎所有企业的主数据问题都能归到下面六条。方案的价值主张就是逐条对治它们。

2.1 六大典型痛点

痛点表现与根因后果
一物多码
duplicate codes		同一物料/供应商在不同系统、工厂、环节有多个编码；编码位数与分类口径不一无法集中议价、成本虚高、库存失真、协同要大量人工转码
一码多物
code reuse		编码复用、废弃码回收再用，同一编码在不同时间指向不同实物历史数据错乱、审计追溯失败，比一物多码更隐蔽危险
标准不一致部门间分类/属性/命名口径各行其是，缺统一标准协同壁垒，合规与财务数据割裂，报表口径打架
质量回潮做完主数据用一两年质量又退回原状——缺质量闭环：发现不了、发现了不知找谁、改了不知对没对投入打水漂，业务重新绕过主数据自建小表
重系统轻数据先上系统后才发现底层基础数据未统筹设计系统越多，数据裂缝越大，集成成本指数上升
责任真空数据「谁都在用、没人负责」，没有 Owner 与认责机制问题无人整改，标准无人维护

2.2 价值主张（对治关系）

🎯 对业务的价值

  • 降本：消灭一物多码→采购集中议价、库存去冗余
  • 提效：一次维护多系统复用，免除跨系统人工转码
  • 合规：客商/科目口径统一，满足审计与监管报送
  • 决策：全域单一视图，报表口径一致可比

🛠 对 IT 的价值

  • 解耦：源系统只管消费，主数据集中生产
  • 可控：变更走审批留痕，可回溯可回滚
  • 可扩：新系统接入即订阅，边际成本递减
  • 提质：质量规则前置，脏数据进不来
⚠ 必须专门防范：一码多物（编码回收再用）
多数方案只盯「一物多码」，却忽略反向的「一码多物」。它源于废弃编码被回收重用。铁律：主数据编码一经启用永不回收、永不复用，废弃走「冻结/归档」而非「删除后让号段可再分配」。V2 的编码引擎（§15）与生命周期（§06）把这条钉死为不可违反的约束。

5.3 借鉴金蝶：编码规则的适用条件

🏅 按受控组织生效 + 按属性设适用条件

5.4 编码治理的三条铁律

  1. 编码即身份，永不回收：主数据编码一经启用，即便对象作废也永不复用。作废走冻结/归档，号段不释放。
  2. 内码 ≠ 外码：DCT 物理表 id（bigint 内码，pk52 铸号）作主键与关系锚点；code 是可读外码。改编码规则不动 id，关系不断裂。
  3. 规则可版本化：编码规则本身是受管对象，改规则留版本、标启停日期，旧对象保留旧码、新对象用新规则。

① 通用性：编码能力服务 DCT/DOC/MDM/任意场景，做成 MDM 专属是过度耦合；② 独立性：cmx-code 已有完整独立方案（七段/断号/反查 max/前后端协作），MDM 重复设计是浪费；③ 解耦：MDM 的核心价值是治理（生命周期/匹配/分发），编码是辅助能力，可后置；④ 兼容性：cmx-code 未就绪前 MDM 走 manual 模式照常工作，就绪后通过钩子接入零改。

15.4 编码铁律（由 cmx-code 保证，MDM 受益）

三条铁律由 cmx-code 引擎保证，MDM 域的主数据编码自动受益：① 永不回收（作废置 lifecycle_status='frozen'，号段不释放）；② 内码≠外码（关系锚在 cm_*.id bigint 内码，code 改规则关系不断）；③ 规则版本化（cmx_code_rule.valid_from/to，旧对象留旧码）。详见 cmx-code 方案 §05/§09。

fn cluster_keys(rec: &Record) -> Vec<(String, u8)> {
  vec![
    (soundex(&rec.name), 1),                  // 音近
    (metaphone(&rec.name), 2),
    (first_n(&normalize(&rec.name), 5), 3),      // 前5字符

}

enum MatchDecision { AutoMerge, Review, NoMatch }

fn decide(score: u8, cfg: &MatchCfg) -> MatchDecision {
  if score >= cfg.automerge_threshold { AutoMerge }        // 如 ≥95 自动合并
  else if score >= cfg.match_threshold { Review }         // 如 80-94 进人工队列

}

22.1 风险与取舍

  • 治理层绝不认识具体域（底线）：域数、实体、编码规则全部只存在于 DCT 定义 JSON 与治理表；cmx-mdm 引擎逐条按定义驱动，绝不为「供应商」「科目」写 if 分支。
  • 匹配合并是真正的难点：存活规则企业级规模极难。M4 从精确匹配 + 单一存活策略起步，逐步加模糊/AI；分块护栏（NULL 巨簇、簇大小上限 500）第一版必须有。
  • cmx-agg 按域决定（V2 纠正）：V1 误列为复用，V2 确认零代码。若一期含组织/成本中心分级域，cmx-agg 是隐藏关键路径，须排进 M7 之前；若只做客商/物料可缓。
  • DCT↔cmx-flow 集成是新接线点：V1 假设已有，V2 勘探确认零集成。M3 须从零建集成（CR→流程实例→审批→回写 lifecycle_status）。
  • 待办台做成通用件：cmx-flow 后端就绪缺前端消费页，建议做成通用 flow 待办台（报表/单据/MDM 共用），不止 MDM 用。
  • 内码永不复用：DCT 表 id（pk52 bigint 内码）+ code（外码）分离，作废走冻结/归档，号段不回收——防「一码多物」的架构级保证。
  • 制度先于工具：MDM 成败七分治理三分工具。平台就绪≠数据变好，必须先落「两体系一工具 + 四定 + Owner 认责」（§04）。
🧭 V2 一页纸总结
V2 的根本修正：MDM 不是新 metaKind，而是独立新域（mdm/cmxmdm/mdm），在 data/meta/definitions/mdm/ 下自建 DCT 定义和物理表（cm_*），只用 base 公共 fieldSets，不碰 fi/cmxfico/ 的任何元数据——cmxfico 的 32 张 cf_* 表是财务模块自有的，MDM 不侵入（作为「DCT 能建模主数据」的参考实例）。三段式 crate cmx-mdm-{model,store-pg,api} 作治理叠加层（生命周期/版本留痕/查重匹配存活/交叉引用/分发），不建主数据表（靠 DCT compile）。编码引擎引用独立方案 cmx-code（预留 DCT 钩子插入点，不在本次范围，cmx-code 就绪后零改接入）。主数据 CRUD/树形/导入导出/零拷贝全部复用 /api/dct/*。关键路径瓶颈是匹配合并存活引擎。业务蓝图与应用方案承接 V1（对标 SAP MDG/Oracle/用友/金蝶），技术上更贴合 cmx 真实架构。
