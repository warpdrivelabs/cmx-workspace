# CMX MDM 主数据分发订阅方案（M5 补全）

> **文档定位**：M5 分发订阅阶段的完整实施方案。基于 V3.1 设计方案 §11/§19 的分发蓝图与完成度报告（2026-08-18 复核）的现状盘点，给出消费侧全量设计：订阅管理、通道抽象（trait）、Webhook 推送、主动查询（pull）、消息中间件扩展骨架、分发引擎、监控前端。
> **日期**：2026-08-18　**状态**：**定稿**（R1–R3 三轮审查 + R5 用户确认轮，见附录 B）　**前置**：M0–M4 + M7 已交付；事件生产侧（md_event_log）已就绪。
> **决策确认**（2026-08-18 用户已定）：① 通道分期落地——本期 trait 抽象 + Webhook，Kafka/RocketMQ 留 feature 骨架后置启用，**不做 Redis Pub/Sub 与 SSE 通道**；② 事件 payload **全量快照**（fat event）；③ 值映射（D-02）**不纳入**本期；④ Webhook 目标**默认允许私网地址**（`allow_private_address=true`）；⑤ 失败通知**仅门户通知**（无邮件）；⑥ 菜单**纯 JSON + sync 脚本**路线（不留档 SQL）；⑦ **多订阅广播**——多个业务系统各自订阅全部推送（D15，不做单订阅多 URL）；⑧ snapshot 主动查询支持**全量 + 按日期段**（updatedFrom/updatedTo）；⑨ **推送顺序**：订阅内全局 event_seq 严格有序（§7.6 总述）。

## 〇、一句话结论

`md_event_log` 就是事务性 Outbox（激活器单事务写入，已就绪），本期补的是**消费侧三件套**：**订阅模型**（md_subscription 扩展）+ **通道抽象**（`DistributionChannel` trait，Webhook 首发，Kafka/RocketMQ 骨架）+ **分发引擎**（Dispatcher Worker，SKIP LOCKED 抢占、指数退避、死信、手动补发），配**两页前端**（订阅管理 + 分发监控），并以 **REST delta 拉取 + 游标登记 + 全量快照接口**服务 pull 型下游，`/mdm/publish` 桩（D-01）重定义为手动补发运维入口。

**平台基础设施盘点**（调研结论，全部有母版可复用）：

- **无** Kafka/RocketMQ/NATS 客户端依赖（需新增，本期只留骨架）。
- 多节点安全抢占模式已有母版：`cmx-job-store-pg` 的 `FOR UPDATE SKIP LOCKED`（claim_pending）。
- 出站 HTTP 客户端母版：`flow_client.rs`（OnceLock 单例 + 超时 + 鉴权头 + 信封判据）。
- HMAC-SHA256 签名协议母版：`flow_cb.rs`（`sha256=<hex>` 头，出站方向反向复用）。
- 门户通知 hub（`cmx_portal::notify`）可用于失败告警；进程内 `GlobalEventBus` 可用于低延迟唤醒 worker。
- 配置模式：`[mdm.flow]` 段母版（ConfigManager 逐键读取 + 默认值回退）。

### 1.2 目标

主数据变更（激活 created/updated、合并 merged）能以**三种模式**分发给下游消费系统：

| 模式 | 通道 | 方向 | 本期 |
|---|---|---|---|
| **推送 Push** | Webhook（MDM → 下游 HTTP 回调，HMAC 签名） | 主动 | ✅ 实现 |
| **推送 Push** | Kafka / RocketMQ（MQ 生产者） | 主动 | 🟡 trait 骨架 + feature gate，下期启用 |
| **拉取 Pull** | REST delta（`/events?since=seq`）+ 游标登记 + 全量快照 | 被动 | ✅ 实现 |

配套：订阅管理（配置化接入下游）、投递保障（at-least-once + 幂等 + 重试 + 死信）、监控运维（流水/统计/手动补发）、失败告警、对账兜底设计。

### 1.3 范围裁定（用户已确认）

- ✅ Webhook 推送通道（本期核心交付）。
- ✅ 主动查询接口（delta + ack + snapshot）。
- ✅ 消息中间件 trait 抽象 + Kafka/RocketMQ **骨架**（feature gate，默认不编译客户端依赖）。
- ❌ Redis Pub/Sub 通道（用户裁定不做）。
- ❌ SSE 实时推送通道（用户裁定不做；V3.1 §19 原提"复用 cmx-job SSE"按此裁剪，监控页用轮询）。

## 二、主流 MDM 分发机制调研与借鉴

| 平台/模式 | 机制 | 本方案借鉴点 |
|---|---|---|
| **SAP MDG · DRF**（Data Replication Framework） | 复制模型（Replication Model：目标系统+过滤+事件类型）+ Outbox + 按目标系统的发送确认与错误日志 | 订阅 = 复制模型（目标系统/字典/事件类型/过滤条件）；md_dispatch_log = 发送日志；`/publish` 重定义 = DRF 手动重发（Reprocess） |
| **SAP MDI**（Master Data Integration） | 中央事件日志 + delta token（消费端自持游标增量拉取） | `md_event_log.seq` 即 delta token；消费端自管 seq（无状态），服务端 ack 登记仅用于监控对账 |
| **Outbox 模式**（微服务事务性发件箱） | 业务事务内写事件表，异步 relay 投递，天然不丢 | md_event_log 已在激活器**同一事务**内写入（现有实现即 outbox，无需改造触发点） |
| **Webhook 惯例**（Stripe/GitHub） | 单事件单请求 + HMAC-SHA256 签名 + 时间戳防重放 + 2xx 确认 + 指数退避重试 | 信封协议照此设计；`eventId` 幂等键；重试判据按 HTTP 状态分类 |
| **Kafka 语义** | 分区键保证同 key 有序；消费组 offset 自管理；producer acks 配置 | 骨架预留 `partition_key = record_id`（同记录事件落同分区有序）；本期不实现 |
| **用友 iUAP MDM** | 分发异常主动通知（不静默失败） | 死信/连续失败 → 门户通知订阅创建人 + 监控页告警 |
| **金蝶苍穹** | 同步方案（全量/增量/定时）+ 失败重试 + 监控看板 | snapshot 全量接口（首次接入/对账修复）+ 监控页三视图（流水/事件/死信） |
| **通用对账兜底** | 周期性 count/checksum 对账 + 全量重推 | 28 天对账作业设计（M5.4，本期留接口不实现） |

**投递语义定论**：**at-least-once**（至少一次，不丢不重排——可能重复），配合**消费端按 eventId 幂等去重**。不选 exactly-once（分布式代价高，主流 MDM/Stripe 均为 at-least-once + 幂等）。

## 三、总体架构

```
┌────────────────────────── 生产侧（已就绪，本期仅增强 payload）──────────────────────────┐
│  CR 审批通过 → 激活器七步事务 ──┬─→ cm_* published（黄金记录）                            │
│                                ├─→ md_audit（留痕）                                     │
│                                └─→ md_event_log（★Outbox：created/updated/merged        │
│                                     + seq++ + payload 增强为全量快照 snapshot）          │
└──────────────────────────────────────────────────────────────────────────────────────────┘
                                          │ (事务提交)
                                          ▼
┌────────────────────────── 分发引擎 Dispatcher（本期新建，多节点安全）────────────────────┐
│  ① Fanout（扇出匹配）：扫描 seq > watermark 的新事件 → 按订阅匹配（dict_code +           │
│     event_types + filter）→ INSERT md_dispatch_log(pending)（uk 幂等，多节点无害）       │
│  ② Deliver（投递）：抢占 FOR UPDATE SKIP LOCKED 的 pending/due-failed 行 →             │
│     按订阅分组、组内按 event_seq 串行（保序）→ 通道适配器投递                             │
│  ③ 结果落库：delivered / failed(退避重试) / dead(重试耗尽或不可重试4xx)                │
│  ④ 告警：dead / 连续失败 → 门户通知（订阅创建人）+ 监控页                                │
│  触发：tick（默认 2s）+ GlobalEventBus("mdm.event.appended") 进程内即时唤醒（跨节点靠 tick 兜底）│
└──────────────────────────────────────────────────────────────────────────────────────────┘
        │ Push（订阅级选择通道）                        │ Pull（无订阅也可用）
        ▼                                            ▼
┌─ 通道适配器 trait DistributionChannel ─┐   ┌─ REST 消费接口 ─────────────────┐
│  WebhookChannel  ✅ 本期                │   │  GET  /mdm/events?since=seq    │
│   ├ HMAC-SHA256 签名（sha256=<hex>）    │   │       （已有，补 nextSince）    │
│   ├ 2xx=成功 408/429/5xx/超时=可重试    │   │  POST /mdm/events/ack   游标登记│
│   └ 4xx=配置错误不可重试                │   │  POST /mdm/records/snapshot    │
│  KafkaChannel    🟡 骨架（feature gate）│   │       （全量快照，首接/对账）    │
│  RocketMQChannel 🟡 骨架（feature gate）│   └─────────────────────────────────┘
└────────────────────────────────────────┘
                                          ▼
┌────────────────────────── 前端（本期新建 2 页）───────────────────────────────────────────┐
│  订阅管理 subscription-manager.js（列表/编辑/测试/启停/删除）                               │
│  分发监控 dispatch-monitor.js（KPI/投递流水/事件日志+游标/死信处理/手动补发，轮询刷新）        │
└──────────────────────────────────────────────────────────────────────────────────────────┘
```

**三条铁律**（承接 V3.1）：

1. **事件不漏**：md_event_log 与 cm_* 写入同事务（激活器唯一闸口保证），分发引擎只消费不生产事件——引擎宕机不影响主数据，事件不丢。
2. **引擎无状态**：Dispatcher 全部状态在 DB（watermark/dispatch_log），多节点重复扇出幂等（uk 冲突忽略）、投递抢占互斥（SKIP LOCKED），符合 AGENTS.md §五集群红线。
3. **通道可插拔**：新增通道 = 实现 `DistributionChannel` trait + 注册，分发引擎零改动（见 §六）。

## 四、核心设计决策

| # | 决策 | 结论 | 理由 |
|---|---|---|---|
| D1 | 事件形态 | **fat event**：payload 增加全量快照 | 激活器事务内已持有全部字段值，顺手写入零成本；下游零回查（主流 MDM 惯例）；拉取模式同样受益 |
| D2 | 投递语义 | at-least-once + 消费端按 eventId 幂等 | exactly-once 分布式代价高；Stripe/SAP 均此模式 |
| D3 | 投递实例 | 显式 `md_dispatch_log`（事件 × 订阅） | 重试/死信/审计/手动补发都需要落库实例；对标 DRF 发送日志 |
| D4 | 扇出时机 | 异步 Fanout（事件落库后由 worker 扫描水位） | 保持激活器纯净（outbox 边界）；订阅变更不影响已发生事件的可追投（新订阅可选补投历史，见 `/publish`） |
| D5 | 顺序性 | **严格顺序**：同订阅内，仅当某事件是该订阅"最小未完成 seq"（无更小的 pending/running/failed）时才可投递（SQL NOT EXISTS 守卫，见 §7.3）；dead/skipped/delivered 不阻塞后续 | 主数据下游（尤其 updated 连续变更）依赖顺序——重试等待期间也不能让后续事件"超车"；跨订阅/跨记录不保证；MQ 通道 P1 用 record_id 分区键延续同记录有序 |
| D6 | Webhook 批量 | **单事件单请求**（不聚合） | Stripe/GitHub 惯例；下游处理与幂等粒度清晰；性能靠引擎并发补 |
| D7 | pull 游标 | 消费端自管 seq（无状态），服务端 ack 仅登记监控 | MDI delta token 模式；服务端不维护会话状态，集群安全 |
| D8 | 失败分类 | 可重试（超时/408/429/5xx/网络）退避后重试；**不可重试（4xx 配置/协议错误）直接进 dead**（attempts 保留、last_error 标注"不可重试类错误，请检查订阅配置"） | 避免对永久性错误无意义重试占用队列；与 dead 统一为"人工介入"语义，状态机三终态（delivered/dead/skipped），failed 一律含 next_retry_at |
| D9 | 死信处理 | attempts ≥ retry_max → dead，仅人工重发/跳过 | 主流 DLQ 模式；自动重发可能风暴 |
| D10 | `/mdm/publish` 语义 | 重定义为**手动补发**（运维入口）：按订阅/seq 范围重建 pending 投递行 | 消灭 D-01 假实现；对标 DRF Reprocess；与自动分发统一走 dispatch_log |
| D11 | Redis Pub/Sub / SSE | 不做（用户裁定） | 下游集成以 Webhook/MQ/pull 为主；监控页轮询够用 |
| D12 | 值映射 | 不做（用户裁定，D-02 单独立项） | field_map 本期只做裁剪/重命名/脱敏 |
| D13 | trait/DTO 归属 | `DistributionChannel` trait + `EventEnvelope`/`DeliveryResult` 下沉 **cmx-mdm-model**（`CodeGenerator` trait 同构先例，契约归中立模型层）；dispatcher 引擎与通道实现留 **cmx-mdm-api**（`flow_client.rs` 网络客户端先例、且被 `/test` `/publish` 端点直接复用，避免 store-pg 引入 reqwest 破坏纯存储定位）；dispatch_log SQL 归 store-pg | 对齐三段分层（model=契约 / api=引擎+HTTP / store-pg=SQL）；记录取舍：dispatcher 是常驻逻辑而非 handler，放 api crate 属借 flow_client 先例的务实选择，不新建 cmx-mdm-core |
| D14 | 新订阅不追投历史 | 新订阅自启用后新事件起分发；需补投历史走「补发」（fromSeq） | 扇出水位只前进；补投是显式运维动作（有意为之、可审计） |
| D15 | **多订阅扇出（广播）** | 一个事件命中**所有**匹配的 active 订阅（dict_code + event_types + filter），逐订阅独立投递/重试/死信/监控——多业务系统各自建订阅，**全部收到推送**（用户确认 2026-08-18）；同一业务系统多个服务都要收时建多条订阅（target_sys 标识区分，如 `wms-order` / `wms-inventory`），**不做单订阅多 URL**（部分失败语义复杂，独立订阅粒度的监控/重试才可运维） | 发布/订阅广播语义（SAP DRF 多目标系统同构）；uk(target_sys,dict_code,channel) 即"每系统每字典每通道一订阅"的形态约束 |

## 五、数据模型设计

### 5.1 `md_subscription` 扩展（ALTER，现有 7 列保留兼容）

```sql
-- 迁移：20260818_001_mdm_distribution.up.sql（库内幂等：IF NOT EXISTS / CREATE ... IF NOT EXISTS，
-- 与 20260812_001/20260813_001 惯例一致；配套 init_ddl.sql 同步维护，见 §十三 M5.1）
ALTER TABLE md_subscription
  ADD COLUMN IF NOT EXISTS name           VARCHAR(128),                      -- 订阅名称（展示）
  ADD COLUMN IF NOT EXISTS description    VARCHAR(512),
  ADD COLUMN IF NOT EXISTS channel_config JSONB        NOT NULL DEFAULT '{}', -- 通道参数（结构由通道 validate_config 校验）
  ADD COLUMN IF NOT EXISTS event_types    JSONB        NOT NULL DEFAULT '[]', -- 订阅事件类型；[] = 全部(created/updated/merged)
  ADD COLUMN IF NOT EXISTS retry_max      INT          NOT NULL DEFAULT 8,    -- 最大尝试次数（含首发）
  ADD COLUMN IF NOT EXISTS timeout_ms     INT          NOT NULL DEFAULT 10000,
  ADD COLUMN IF NOT EXISTS batch_size     INT          NOT NULL DEFAULT 50,   -- 单轮该订阅最大投递数
  ADD COLUMN IF NOT EXISTS created_by     VARCHAR(64),
  ADD COLUMN IF NOT EXISTS updated_at     TIMESTAMPTZ  NOT NULL DEFAULT now();

COMMENT ON COLUMN md_subscription.channel_config IS '通道配置：webhook {url,secret,headers{}}；kafka {brokers,topic,partition_key}（骨架）';
COMMENT ON COLUMN md_subscription.channel      IS '通道 webhook/kafka/rocketmq/rest_pull';
CREATE UNIQUE INDEX IF NOT EXISTS uk_md_subscription ON md_subscription (target_sys, dict_code, channel);
-- 同目标系统同字典同通道唯一。注：若存量存在重复行，迁移前先人工去重（当前表无页面入口，风险极低）；
-- 唯一索引用 CREATE INDEX 形态（幂等可重跑）而非 ADD CONSTRAINT。
```

- `channel` 既有列复用，值域扩展为 `webhook | kafka | rocketmq | rest_pull`（`rest_pull` 型订阅不产生投递任务，仅登记 pull 消费者用于监控；其 `channel_config` 存 `{consumerId}`）。
- 既有 `filter`（JSONB）复用为过滤条件（语义见 §5.4）；`field_map` 复用为字段转换规则。
- 既有 CRUD（`upsert_subscription`）同步扩展字段与校验（`channel_config` 交通道 `validate_config`）。
- **不设** per 订阅扇出水位列：扇出水位是全局的（md_dist_watermark），订阅级"积压/滞后"由 dispatch_log 聚合（pending+failed 计数）与 stats 端点计算——避免冗余状态两处维护。

### 5.2 新表 `md_dispatch_log`（投递实例 = 队列 + 流水）

```sql
CREATE TABLE IF NOT EXISTS md_dispatch_log (
    id              BIGINT       NOT NULL,            -- 主键（应用层 snowflake，md_ 治理表惯例）
    subscription_id BIGINT       NOT NULL,            -- → md_subscription.id
    event_id        VARCHAR(64)  NOT NULL,            -- → md_event_log.id（幂等键之一）
    event_seq       BIGINT       NOT NULL,            -- → md_event_log.seq（排序/诊断冗余）
    dict_code       VARCHAR(64)  NOT NULL,
    record_id       BIGINT       NOT NULL,
    status          VARCHAR(16)  NOT NULL,            -- pending/running/delivered/failed/dead/skipped
    attempts        INT          NOT NULL DEFAULT 0,
    next_retry_at   TIMESTAMPTZ,                      -- 仅 failed 有值（到期才可被再次抢占）
    last_error      TEXT,
    http_status     INT,                              -- webhook 响应码
    response_snippet VARCHAR(512),                    -- 响应体摘要（截断）
    delivered_at    TIMESTAMPTZ,
    created_at      TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at      TIMESTAMPTZ  NOT NULL DEFAULT now(),
    PRIMARY KEY (id)
);
COMMENT ON TABLE  md_dispatch_log IS '分发投递实例（事件×订阅）：队列状态机 + 投递流水';
COMMENT ON COLUMN md_dispatch_log.id IS '主键（应用层 snowflake，对齐 md_ 治理表惯例——BIGSERIAL 仅 md_event_log.seq 非主键列有先例）';
COMMENT ON COLUMN md_dispatch_log.status IS 'pending待投/running投递中/delivered成功/failed待重试/dead死信/skipped人工跳过';
COMMENT ON COLUMN md_dispatch_log.next_retry_at IS 'failed 的下次可抢占时间（指数退避）；NULL=非 failed';
CREATE UNIQUE INDEX IF NOT EXISTS uk_md_dispatch_sub_event ON md_dispatch_log (subscription_id, event_id);  -- 扇出幂等
CREATE INDEX IF NOT EXISTS idx_md_dispatch_due   ON md_dispatch_log (status, next_retry_at);                -- worker 抢占扫描
CREATE INDEX IF NOT EXISTS idx_md_dispatch_sub   ON md_dispatch_log (subscription_id, created_at DESC);     -- 监控流水
CREATE INDEX IF NOT EXISTS idx_md_dispatch_event ON md_dispatch_log (event_id);
```

**状态机**（三终态：delivered / dead / skipped）：

```
pending ──抢占──→ running ──成功──→ delivered（终态）
   ↑                 │
   │        可重试失败(attempts<retry_max)：failed(next_retry_at=退避时间)
   └──到期再抢占─────┘
running ──可重试失败且 attempts≥retry_max──→ dead（终态，仅人工）
running ──不可重试失败(4xx 配置/协议错误)──→ dead（终态，last_error 标注"不可重试"）
running 残留(节点崩溃>10min) ──回收──→ pending（attempts+1，防崩溃循环不加计数）
dead ──人工重发──→ pending（attempts 保留累计，供诊断）
dead/failed(不可重试已并入dead) ──人工跳过──→ skipped（终态，放行决策留痕）
```

- `running` 抢占即写入；worker 崩溃残留的 running 行由**回收步骤**（tick 内先执行：`updated_at` 超过 10 分钟的 running 重置 pending 且 attempts+1）兜底——复用 cmx-job reaper 思想。
- 顺序守卫（D5）的阻塞集合 = `pending / running / failed`（三态任一存在更小 seq 即阻塞）；`delivered/dead/skipped` 不阻塞——死信人工决策期间不卡后续事件。

### 5.3 新表 `md_dist_watermark`（扇出水位）与 `md_consumer_offset`（pull 游标登记）

```sql
CREATE TABLE IF NOT EXISTS md_dist_watermark (
    key        VARCHAR(32) NOT NULL PRIMARY KEY,   -- 当前仅 'fanout'
    last_seq   BIGINT      NOT NULL DEFAULT 0,     -- 已扇出到的事件 seq
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
COMMENT ON TABLE  md_dist_watermark IS '分发引擎扇出水位（全局单行 fanout）';
COMMENT ON COLUMN md_dist_watermark.last_seq IS '已扇出处理的 md_event_log 最大 seq（无论是否命中订阅）';

CREATE TABLE IF NOT EXISTS md_consumer_offset (
    id          BIGINT      NOT NULL PRIMARY KEY,           -- 主键（应用层 snowflake）
    consumer_id VARCHAR(64) NOT NULL,                       -- 下游消费者标识（建议 = target_sys）
    dict_code   VARCHAR(64) NOT NULL,
    acked_seq   BIGINT      NOT NULL DEFAULT 0,
    acked_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
COMMENT ON TABLE  md_consumer_offset IS 'pull 消费者游标登记（监控/对账用；消费端仍应自持 seq）';
CREATE UNIQUE INDEX IF NOT EXISTS uk_md_consumer_offset ON md_consumer_offset (consumer_id, dict_code);

-- seed（幂等，符合迁移 INSERT 强制 ON CONFLICT 规范）
INSERT INTO md_dist_watermark (key, last_seq) VALUES ('fanout', 0)

```

- watermark 的 `fanout` 行在 Fanout 事务中 `SELECT ... FOR UPDATE` 独占窗口（多节点排队而非并发）；配合 dispatch uk 幂等，双保险不重不漏。
- 初始化从 0 起：存量事件（增强前的薄事件）默认**不追投**（D14）——新订阅不补历史；需要历史数据时用 `/publish` 手动补发或 `/records/snapshot` 全量拉取。

### 5.4 `filter` 与 `field_map` 语义约定（v1）

**filter**（行级过滤，事件命中才扇出）：

```json
{ "conditions": [ { "field": "status", "op": "eq",  "value": "A" },
                  { "field": "group",  "op": "in", "value": ["g1","g2"] },
                  { "field": "name",   "op": "like", "value": "华东%" } ],
  "logic": "and" }
```

- v1 支持操作符：`eq / ne / in / like`；字段取值来源为快照（`payload.snapshot`）；`logic` 仅 `and`（or 留 v2）。
- 匹配失败（字段不存在）按不命中处理并记 warn 日志。

**field_map**（列级转换，投递前应用）：

```json
{ "include": ["code","name","tax_no"],          // 空/缺省 = 全字段
  "rename":  { "code": "supplierCode" },         // 输出字段重命名
  "mask":    ["tax_no"] }                        // 脱敏：值替换为 "***"
```

- 转换在引擎侧对快照副本执行（不改 md_event_log 原始 payload——同一事件对不同订阅可不同投影）。
- 值映射（跨系统代码对照）预留 `value_map` 键位，本期不实现。

### 5.5 事件 payload 增强（写入侧，激活器改造）

```jsonc
// md_event_log.payload（fat event；activate/merge 两处写入点）
{
  "cr_id": 789, "cr_type": "create", "record_id": 456, "version": 1,
  "snapshot": { "code":"GYS0001", "name":"华东钢铁集团", "tax_no":"91...", "...": "cm_supplier 全字段" },
  "merged":   { "victim_ids": [...], "survivorship": [...] }   // 仅 merged 事件
}
```

- 快照在激活器事务内已持有（insert/update 的行数据），直接序列化写入，零额外查询。
- 合并事件快照取合并后 master 行；victim 明细放 `merged` 键（保留现追溯结构）。
- **存量薄事件兼容**：改造前写入的事件无 `snapshot`——扇出时 filter 对其跳过求值（视为命中，日志 warn），信封 `data` 透传原 payload（薄）；订阅配置了 filter 的场景建议只对增量使用，补投存量薄事件须自行承担过滤不生效。

### 7.2 Fanout（事件扇出）

```
loop tick（默认 2s）:
  BEGIN;
    SELECT last_seq FROM md_dist_watermark WHERE key='fanout' FOR UPDATE;   -- 窗口独占（多节点排队）
    SELECT id, seq, dict_code, record_id, event_type, payload
      FROM md_event_log WHERE seq > :last_seq ORDER BY seq ASC LIMIT :fanout_batch(500);
    for ev in events:
      for sub in active_subs_matching(ev):     -- dict_code + event_types + filter(对 snapshot 求值；薄事件跳过 filter)
        INSERT INTO md_dispatch_log(id, subscription_id, event_id, ...)
          VALUES (:snowflake_id, ...) ON CONFLICT (subscription_id, event_id) DO NOTHING;  -- 幂等
    UPDATE md_dist_watermark SET last_seq = :max_seq_processed WHERE key='fanout';
  COMMIT;
```

- 订阅快照（active 订阅列表）进程内缓存 **≤5s TTL**（只读准静态配置加速：DB 为准源、短 TTL、随时可失效——同字典元数据缓存性质，集群最终一致合规）。
- 进程内即时唤醒：激活器 commit 后 `GlobalEventBus.publish("mdm.event.appended", {seq})`；dispatcher 收到立即 tick（跨节点靠 tick 兜底，最终一致）。

### 7.3 Deliver（投递）

```
loop tick:
  ① 回收：UPDATE md_dispatch_log SET status='pending', attempts=attempts+1
           WHERE status='running' AND updated_at < now()-interval '10 minutes';   -- 崩溃残留；attempts+1 防崩溃循环
  ② 抢占（含严格顺序守卫 D5——同订阅只允许投递"最小未完成 seq"）：
           SELECT d.* FROM md_dispatch_log d
           WHERE (d.status='pending' OR (d.status='failed' AND d.next_retry_at <= now()))
             AND NOT EXISTS (              -- 更小 seq 未完成则阻塞（防重试期间后续事件超车乱序）
               SELECT 1 FROM md_dispatch_log d2
               WHERE d2.subscription_id = d.subscription_id
                 AND d2.event_seq < d.event_seq
                 AND d2.status IN ('pending','running','failed'))
           ORDER BY d.subscription_id, d.event_seq
           FOR UPDATE SKIP LOCKED LIMIT :deliver_batch(100);
           → 同事务置 running 并提交（抢占即生效）
           注：守卫含未到期 failed（阻塞成立，保序优先于吞吐）；delivered/dead/skipped 不阻塞；
           多节点并发下守卫条件基于已提交状态判定，锁等待串行化，无乱序窗口。
  ③ 投递：按 subscription_id 分组；组内按 event_seq 串行调用通道（跨 tick 保序由②守卫保证）；
          跨组并发（tokio::spawn，semaphore 上限 deliver_concurrency=8）
  ④ 落库：成功 → delivered(attempts+1, delivered_at, http_status, response_snippet)
          可重试失败 → failed(attempts+1, next_retry_at = now()+min(base*2^attempts, max))
          可重试失败且 attempts ≥ retry_max → dead
          不可重试失败(4xx) → dead（attempts+1, last_error 标注"不可重试类错误"）
          dead 新增/连续失败(≥3) → 门户通知（订阅创建人 + admin）
```

- **退避参数**：全局默认（`backoff_base_ms=5s`、`backoff_max_ms=30min`），订阅级 `retry_max` 覆盖次数上限。
- 投递前组装信封：从 md_event_log.payload 取快照 → `transform.rs` 应用该订阅 field_map → `EventEnvelope`。
- **手动补发**（`POST /mdm/publish`）将目标行 `UPDATE ... SET status='pending', next_retry_at=NULL`（attempts 保留累计）；补发的行同样受②顺序守卫约束，不会打乱既有顺序。

### 7.4 与 cmx-job 的关系（不注册为 JobHandler 的理由）

cmx-job 面向"有头有尾的作业"（进度/归档/重跑），分发是**常驻流式管道**——用独立 `tokio::spawn` + DB 抢占（SKIP LOCKED + watermark FOR UPDATE）实现更直接；集群安全性等价（状态全在 DB）。后续若需"分发健康作业"（对账、日报）再注册 JobHandler，二者不冲突。

### 7.5 对账兜底与事件清理（M5.4 设计预留，本期不实现）

- **对账作业**（周期建议每日）：每订阅比对 `md_dispatch_log.delivered 数/最近失败` 与 `md_event_log 计数`；pull 消费者比对 `acked_seq` 与 `max(seq)` 滞后；差异 → 门户通知 + 监控页告警区。
- **28 天兜底**：事件保留 28 天（对账窗口），超期由归档作业清理（本期不清理，防误删，仅设计）。
- **全量快照接口**（本期实现，见 §八）承担首次接入与对账修复的重推载体的角色。

### 7.6 推送顺序保证（总述，用户重点关注项）

**顺序模型**：**同一订阅内，事件按 `event_seq` 全局严格有序投递**（不止同一条记录——是该订阅所有事件的全序），跨订阅之间互不影响。这是本方案对"数据变更保证推送顺序"的承诺，由四层机制合成：

| 层 | 机制 | 位置 |
|---|---|---|
| ① 生成有序 | Fanout 按 seq 升序扫描扇出；dispatch 行天然带 event_seq 全序 | §7.2 |
| ② 抢占守卫 | 投递抢占 SQL 的 `NOT EXISTS` 守卫：某事件存在更小 seq 的未完成行（pending/running/failed 任一）即**阻塞不投递**——重试退避等待期间后续事件绝不"超车" | §7.3 ② |
| ③ 投递串行 | 同订阅组内按 event_seq 串行调用通道；跨订阅并发 | §7.3 ③ |
| ④ 终态放行 | 只有 delivered/dead/skipped 三终态解除阻塞——死信人工决策是**显式**的顺序让渡（跳过=放行后续），不静默乱序 | §5.2 状态机 |

**异常场景推演**（全部不乱序）：

| 场景 | 行为 | 结果 |
|---|---|---|
| e1 投递失败退避等待（failed 未到期） | e2 被 ② 守卫阻塞 | 下游先收 e1（重试成功后）再收 e2 |
| 投递节点崩溃（e1 running 残留） | e2 阻塞；10 分钟后回收 e1 → pending 重投（at-least-once，下游 eventId 幂等） | 顺序保持 |
| 手动补发历史事件（force 重置已投递行） | 补发行 seq 小，按全序重新插队投递 | 与首次投递同一顺序模型，不乱序 |
| 多节点并发投递 | 守卫基于已提交状态判定 + SKIP LOCKED 锁串行化，无乱序窗口 | 顺序保持 |
| e1 进 dead（重试耗尽/不可重试 4xx） | dead 是终态不阻塞，e2 立即可投 | **唯一例外**：e1 缺失由人工跳过/重发决策显式承担（监控页可见） |

**下游防御性依据**（信封自带双序号，接入文档约定）：

- `seq`：全局单调（delta token 语义）——消费端可校验连续性、发现缺口即重拉；
- `version`：记录级单调（published_version）——消费端可丢弃旧版本事件兜底（重复投递也靠 `eventId` 幂等）。

**通道间顺序语义差异**（接入文档声明）：Webhook = 订阅内全局 seq 有序（上述四层）；MQ 通道（M5.3）= **同记录有序**（`partition_key = record_id`，同记录事件落同分区天然有序），跨记录在 MQ 分区模型下不保证全序——MQ 接入方按 record 维度消费即可满足主数据场景。

## 十一、安全设计

1. **Webhook 出站签名**：HMAC-SHA256（复用 workspace 既有 hmac/sha2 依赖与 `sha256=<hex>` 协议）；secret 随机 32 位（前端生成按钮 + 后端生成兜底）；secret 存储明文于 channel_config（与 M7 webhook_secret 同级别治理；DB 访问已受平台权限约束），**API 回显掩码、不变更不覆盖**。
2. **防重放**：信封带 `X-CMX-Timestamp`；下游建议 ±5min 窗口校验（接入文档约定；MDM 侧不强依赖）。
3. **消费接口鉴权**：`/events`、`/snapshot`、`/ack` 走平台鉴权（Bearer / X-API-Key）；下游系统建议发放独立 API Key。
4. **URL 校验**：validate_config 拒绝非 http(s)；私网/回环地址**默认放行**（`allow_private_address = true`，用户确认 MDM 下游多为内网系统；外网开放部署时置 false 启用 SSRF 防护：拒 `127.0.0.0/8`、`10/8`、`172.16/12`、`192.168/16`、`169.254/16`）。
5. **审计**：dispatch_log 即投递审计（谁的重试、何时成功、响应摘要）；订阅变更走平台操作日志（handler 层现成模式）。

## 十二、集群无状态合规自检（AGENTS.md §五）

- [x] Dispatcher 无进程内业务状态：watermark/dispatch 状态全在 DB；订阅缓存为短 TTL 只读加速（准静态配置，同字典元数据缓存性质，≤5s 失效）。
- [x] 多节点安全：Fanout 窗口 `FOR UPDATE` 排队 + dispatch uk 幂等；Deliver `FOR UPDATE SKIP LOCKED` 抢占；running 残留回收作业。
- [x] `ChannelRegistry`/reqwest 单例为基础设施注册表/连接池（红线豁免项），非业务数据缓存。
- [x] 定时回收/告警在多节点下重复执行无害（回收 UPDATE 幂等；告警按 dispatch 状态变化触发）。
- [x] 无本地磁盘持久化；无登录态/会话（消费端自管 seq）。
- [x] 优雅启停：SIGTERM 时 loop 在当前 tick 结束后退出（pending 行安全留存，重启继续）。

## 十四、验收标准

1. **E2E 推送**：激活一条供应商 CR → 下游 echo webhook 收到 created 信封（HMAC 验签通过、含全量快照）→ 监控页流水 delivered；更新 → updated；合并 → merged（victim 追溯）。
2. **重试与死信**：下游返回 500 → 按指数退避重试 → 持续失败至 retry_max → dead + 门户通知 + 监控页告警 → 人工重发成功。
3. **不可重试分类**：下游返回 404 → 直接 dead（无退避重试），last_error 标注"不可重试类错误"；后续事件不被阻塞（顺序守卫终态放行）。
4. **保序**：同记录连续 3 次 update 事件，下游收到顺序与 seq 一致；**且首条投递失败退避等待期间，后续事件不超车**（下游第二次收到的一定是重试成功后的首条）——对应 §7.6 场景行 1。
5. **幂等**：手动补发重复执行 → 无重复投递（uk 冲突忽略）；多节点部署（2 实例）并发投递无重复 delivered。
6. **Pull 链路**：snapshot 全量 → events 增量（nextSince 推进）→ ack 登记游标 → 监控页游标滞后正确展示；**snapshot 按日期段增量**（updatedFrom=当月 1 号）只返回当月有变更的记录。
7. **集群**：杀掉任一节点，另一节点继续投递无中断；重启节点自动恢复。
8. **D-01 关闭**：`/mdm/publish` 返回真实补发计数，桩语义消失。
