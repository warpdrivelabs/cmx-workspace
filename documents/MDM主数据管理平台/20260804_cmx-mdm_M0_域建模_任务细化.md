## 〇、关键事实与建模决策(开始前必读)

M0 细化基于代码库核实,**有两处对 V3 方案的关键修正**,已与用户确认:

### 决策① 主数据头+明细建模:独立 DCT + 业务约定关联(用户已确认)

V3 §13.3 假设「头表 `cm_supplier` + 明细表 `cm_bank_account`(parent_id 挂头表)」都用 DCT。但代码库事实:

- **DCT 的 parent_id 只用于本表自分级树形(selfHierarchy)**,DCT 域**不支持**跨表"明细表挂头表"的物理挂接。
- 跨表主从(头+行)是 **DOC 单据**的能力(用 `upper_id`,在 `voucherSchema.relations[]` 声明)。

**落地决定(用户已选)**:头表与明细表**都是独立 DCT 字典表**(各自用 base fieldSets),明细表通过**普通业务命名外键 + 索引**(如 `supplier_id`)指向头表,**无物理 FK**(符合现有"关联字段+索引替代 FK"规约)。查询明细时按该列过滤。不依赖 DCT 引擎的跨表挂接。

> **V3.1 印证**:V3.1 设计方案已正式采纳此建模,并补充两类关系的区分:
> - **明细表挂头表** = 业务命名普通外键(如 `supplier_id`),明细表**不配 selfHierarchy**;
> - **头表自身树形**(科目树/组织树)= `selfHierarchy=true` + `parent_id`(同表自引用)。
> 两类关系并存但语义不同,不可混用。本细化文档的 supplier(头)+ bank_account(明细, supplier_id)即采用前者;若 M6 扩展科目/组织等树形主数据,则用后者。

### 决策② 编码:随机生成占位(M8 替换)

cmx-code 不存在,M0/M1 期间主数据 code 用**随机生成**。M0 阶段不建编码逻辑(code 由激活器在 M1 生成),M0 只建表结构。

### compile 机制关键事实(影响所有建表)

1. **compile 不会自动注入任何公共字段**(id/code/name/audit 列都没有)——全部来自 base fieldSet 引用。
2. 业务表(cm_*/cv_*)**由 runtime compile 建表**,不是手写 DDL。触发方式:`POST /api/model/deploy`(body 指定 kind/domain/application/module/file)。
3. **`docs/sql/init/init_ddl.sql` 是手写的平台 cmx_* 表参考脚本,不含业务表**;`docs/sql/migrations/` 目录放平台表增量。MDM 的 `mdm_activation` / `md_*` 治理表是**平台级表**,走 migrations 手写 DDL。

### 建表职责划分(M0 两类表,两条路径)

| 表类 | 例子 | 建表方式 |
|---|---|---|
| **主数据 DCT(cm_*)+ 申请单 DOC(cv_mdm_apply*)** | cm_supplier / cm_bank_account / cv_mdm_apply / cv_mdm_apply_line | 写元数据 JSON → `POST /api/model/deploy` 触发 compile |
| **治理表(平台级)** | mdm_activation / md_audit / md_xref / md_value_map / md_merge_record / md_subscription / md_event_log | 手写 `migrations/*.up.sql` |

### 关键设计点
- **顶层键名照抄真实 DCT 域**(`cmxfico_dct_meta_v3.json:1-29`):`moduleMeta` / `baseDctMetaRef` / `dictionaryTables` / `updatedAt`。

- **备选方案(若 compile 不识别自定义 *FieldSet)**:删除 `mdmGovernanceFieldSet` 行,把 `lifecycle_status`/`published_version` 两个字段直接复制到每张 cm_* 表的 `fields` 数组里(compile.rs:356 第一步合并本表 fields)。功能等价,只是没有 fieldSet 复用。**T6 先验证兜底,不通就走备选。**
- 明细表 `supplier_id` 是普通 BIGINT 列(无 refDict/无 FK),靠 `uniqueKeys: [["supplier_id","account_no"]]` 保证业务唯一性。树形/明细挂接的运行时展示由前端按 supplier_id 过滤实现。
- **doc_type 在 DOC 申请单里用 `mdm_supplier_apply` / `mdm_supplier_change`**,DCT 不涉及 doc_type。

### 关键设计点
- **顶层键名照抄真实 DOC 域**(`cmxfico_doc_meta_v2.json:1-139`):`moduleMeta` / `baseDocMetaRef` / `voucherCommonFieldSet` / `voucherSchema` / `voucherTables` / `voucherStatusFlow` / `updatedAt`。
- **`voucherTables[].documentFieldSets`**(字符串数组)是 DOC 引用 base fieldSet 的方式(compile.rs:456-464 经 `base_fieldset` 取数)。**首项必须是 `documentLevelFields`**——它是 cv_* 表获得 `id`(主键,isPrimaryKey:1)、`upper_id`、`line_no` 三列的**唯一来源**(`base_doc_meta_v1.json:561-637`)。
  - ⚠️ **切勿引用 `documentCommonFields`**:它只有 `includeFieldSets`、**没有 `fields`**(`base_doc_meta_v1.json:552-560`),而 compile 的 `base_fieldset` 只读 `.fields`、**完全不展开 includeFieldSets**(全仓 grep `includeFieldSets` 在 .rs 文件 0 命中)。引用它 = 0 列产出。本定义已删除该引用。
  - 头表对齐 cmxfico `cv_header`(`cmxfico_doc_meta_v2.json:1290`):`documentLevelFields` + `documentIdentityFields` + `documentSourceFields` + `documentLifecycleFields` + `documentTechnicalFields`。
  - 行表对齐 cmxfico `cv_acc_line`(`cmxfico_doc_meta_v2.json:1761`):`documentLevelFields` + `documentTechnicalFields`。
- **`upper_id` 不在行表 fields 里显式声明**:它由 `documentLevelFields` 注入(同上)。行表只需声明业务字段(line_type/line_action/line_payload)。
- **状态机**:`voucherStatusFlow.stateField="doc_status"`,5 状态 4 转移,对齐 M2 的申请单状态机。**注意:核实发现 DOC 后端无显式状态转移校验代码**——此状态机声明主要供前端/规则层用,后端强校验在 M2 自建(cmx-mdm 层)。**dct_accessor 写入闸口属 M1**(激活器前置组件),CR 状态机转移校验属 M2;M0 只声明 voucherStatusFlow 元数据。
- **头表字段策略(V3.1)**:主体关键字段(name/tax_no/credit_code/short_name)**逐列展开**成独立 VARCHAR 列,享受 DOC 列级校验(必填/格式/正则/唯一);扩展/动态/低频字段留 `ext_attrs` jsonb。**不再使用 `proposed_payload` 存全量**(V3 旧法已废弃)。`field_deltas` 仍保留(变更场景存字段级新旧值)。
- **`source_cr_id`**:驳回复活留痕列(M0 建列)。⚠️ 2026-08-13 起,驳回复活改走「rejected → 原单编辑 → submit 重提」(不再克隆),此列暂无写入方(预留)。
- **`effective_date`**:可空的未来生效日。审批通过时若 > 今天,激活器记 pending 不立即落 published(V3.1 新增语义)。M0 只建列,逻辑在 M1+。
- **`cr_type` 扩 5 种**(V3.1):`create/update/merge/block/flag_delete`。其中 create/update 走字段映射(激活器配置驱动);**merge/block/flag_delete 经评估暂不实现**(2026-08-13:merge 走独立 merge-requests 链路;block/flag_delete 低频按需再做)。M0 只建列(注释扩 5 种),激活器仅实现 create/update 分支。
- `line_payload`(行表)仍是 JSONB 存明细提议值——明细字段动态多样,逐列不现实。
