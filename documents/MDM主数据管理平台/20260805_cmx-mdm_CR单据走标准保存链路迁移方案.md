# CR 单据走标准保存链路 · 迁移方案

> **背景**：MDM 变更申请（CR）目前用专属接口 `POST /api/mdm/change-requests/create`（`create_cr`）落库，而不是平台标准单据保存接口 `POST /api/doc/save`。后果：
> 1. **doc_no 无法走编码引擎**——`create_cr` 把单据号写死成 `CR-{cr_id}`，元数据里声明的 `codeRule.ruleCode=MDM_GYS` 形同虚设。cmx-code（M8）已就绪却没接到 CR。
> 2. **不通用**——每来一种新单据（客户主数据 CR、物料主数据 CR……）都要在 MDM 里再写一个 `create_xxx`，与"元数据驱动"的平台理念背离。
> 3. **重复造轮子**——`create_cr` 手写了一套与 `DocSaver` 高度重叠的"写头+写行+铸号+审计+事务"逻辑，却缺了标准链路的列级校验、版本快照、乐观锁。
> 4. **潜伏 bug**——`create_cr` 的 INSERT 把前端传入的 `field_deltas` 列硬编码为 `NULL`（见 §1.4），导致变更（update）类 CR 的字段级新旧值在头表里**没存住**，激活器 update 分支拿到的 field_deltas 恒为 NULL。
>
> 本方案目标：**让 CR 保存走标准 `/doc/save`，doc_no 由 cmx-code 生成，消除专属 create_cr，保留 MDM 特有的流转/激活/克隆语义**。遵循"子代理审查 → 主代理完善 → 循环到清理"流程。

### 1.2 doc_no 写死（核心问题）

`cr_service.rs:149`：
```rust
DataValue::String(format!("CR-{cr_id}")),  // ← doc_no，完全没用 cmx-code
```
克隆用 `CR-CLONE-{new_id}`（`cr_service.rs:258`）。

而 MDM DOC 元数据 `data/meta/definitions/basic/dataplatform/mdm/dataplatform_doc_meta_v1.json:320-324` 已声明：
```json
"codeRule": { "mode": "auto", "field": "doc_no", "ruleCode": "MDM_GYS" }
```
**声明与实现脱节**——迁到标准 `/doc/save` 后，`DocSaver::mint_codes_for_changeset`（`cmx-doc-store-pg/src/saver.rs:1156-1260`）会自动读这条 codeRule 调 `GlobalCodeMinter` 铸号。

### 1.3 标准链路已就绪且通用

- **`POST /doc/save`**（`cmx-doc-api/src/handlers.rs:683-750`）：坐标走 query（`domain/application/module/file`），数据走 body（`{saveMode, changes}`），**禁用 Path Variable**，与 AGENTS.md §四 第 5 条一致。
- **元数据驱动**：`DocMetaView::parse`（`cmx-doc-model/src/meta.rs:191-243`）把 DOC 定义解析为层级模型，`apply_merge`（`saver.rs:351-430`）按拓扑序写库，**不写死任何表名/字段**。
- **cmx-code 已全局注入**：`web-server/src/main.rs:143-149` 启动时 `GlobalCodeMinter::set(CodeEngine)`，`DocSaver` 通过 `GlobalCodeMinter::get()` 调用，未注入则静默跳过（现状零影响）。
- **`DocSaver::save` 是 `pub async fn`**（`saver.rs:143`）：可被任意 crate 直接调用（MDM 可复用，也可让前端直接走 HTTP）。

### 1.4 field_deltas 丢失 bug（迁移顺带修复）

`cr_service.rs:141-142` 的 INSERT 列序：
```
列:  ..., ext_attrs(15), field_deltas(16), doc_status(17), ...
值:  ..., NULL(15),      NULL(16),        'draft'(17),   ...
```
第 16 个列 `field_deltas` 对应的值是字面量 `NULL`。前端 `cr-form.js:132-136` 在 update 模式构造的 `field_deltas` 对象，经 `buildHead()` 传到后端，但 `create_cr_inner` 的 SQL **根本没把 head 里的 field_deltas 绑进去**——位置占位是写死的 NULL。

激活器 update 分支 `activation_service.rs:131-134` 读 `cr_head["field_deltas"]`，**恒拿到 NULL**。这意味着：变更类 CR 激活后，主数据实际没按字段级 diff 更新（激活器拿到空 deltas，`plan_update` 产出的更新集为空）。这是 M1-M4 遗留的功能性 bug，本方案迁移后自动消除（标准保存按元数据列绑定，field_deltas 会正确入库）。

### 1.5 field_deltas 丢失对激活器的实际影响（已核实）

`plan_update`（`cmx-mdm-model/src/activation.rs:89-108`）逻辑：仅当 `field_deltas.as_object()` 返回 Some 时才搬运字段；为空时 header_row 只剩 `published_version`（+1）。因此 field_deltas=NULL 时，激活器 update 分支产出的更新集**几乎为空**（只 bump 版本号，不改业务字段）——**update 类 CR 激活后主数据业务字段实际不会被更新**。这是真实的功能性 bug，迁移后自动消除。

### 1.6 cv_mdm_apply 物理列约束（迁移关键约束）

`cv_mdm_apply` 表由 DOC 元数据编译生成，实际 DDL（取自 `logs/cmx-server.log.2026-08-04` 建表日志）中 **NOT NULL 无默认值**的列：
- 业务列：`doc_type`、`target_dict_code`、`cr_type`
- 结构列：`line_no`、`doc_no`、`doc_type_id`、`doc_date`、`entity_id`
- 状态列：`doc_status`
- 审计列：`create_by`、`create_time`、`delete_flag`（这 3 个标准保存自动填，见下）

标准保存对列的处理分三类（`saver.rs:957-961`）：
- **`DOC_SERVER_FILLED_COLS`** = `[create_by, update_by, delete_flag]`：仅 backfill NOT NULL 兜底，用户提供值仍校验。
- **`DOC_SERVER_REPLACED_COLS`** = `[id, upper_id, line_no, create_time, update_time]`：**完全跳过值校验**。但 ⚠️ `mint_ids_for_changeset` 只铸 `id`/重指 `upper_id`，**不铸 `line_no`、不自动填 line_no 的值**——校验虽跳过，落库时 `row_cols_vals` 不会注入 line_no → PG NOT NULL 拒收（23502）。
- 其他 NOT NULL 列（`doc_type_id`/`doc_date`/`entity_id`/`doc_status`/`doc_no`）：不在 filled/replaced 集，`validate_changeset` 会严格校验，缺失即 422。

**结论**：迁移后前端 changeset 必须显式提供这些列的值（见 §3.4 修订）。

| 头+行原子事务 | ✅ | ✅ | ✅ |
| 主键铸号 | ✅ next_pk_id | ✅ mint_ids | ✅ |

## 二、设计原则

1. **CR 保存走标准 `/doc/save`**——前端不再调 `/mdm/change-requests/create`，改调标准接口；doc_no 由 cmx-code 按 `MDM_GYS` 规则生成。
2. **MDM 特有语义保留为独立接口**——标准链路不含状态机/激活器/克隆，这些继续由 MDM 提供：
   - 流转：`submit` / `reject` / `abort`（仅改 doc_status）
   - 激活：`approve` / `activate`（调激活器，单事务落 cm_* + md_audit + md_event_log）
   - 克隆：`clone-revise`（rejected → 复制新 draft）
3. **不改标准 DOC 模块**——本方案是 MDM 单侧改造，不动 `cmx-doc-*` 任何代码（标准链路已具备所需能力）。
4. **元数据为本**——CR 字段/列校验/编码规则/状态机全部以 DOC 元数据声明为准，代码不再硬编码列序。
5. **API 禁用 Path Variable**——新接口/保留接口均遵守 AGENTS.md §四 第 5 条（参数走 body/query）。
6. **不动已激活的历史 CR**——存量数据保持原样；仅新建/克隆 CR 走新链路。

### 3.3 cmx-code 规则种子（MDM_GYS）

MDM DOC 元数据已声明 `ruleCode: "MDM_GYS"`，但 cmx-code 规则表（`cmx_code_rule`）目前**无种子数据**（规则由前端规则管理页 POST 创建）。需补一条种子规则，等价于原 `CR-{id}` 的语义但更规范：

- 规则码：`MDM_GYS`
- 段序列（七段算法）：
  - `{type:"const", value:"CR-"}` 固定前缀
  - `{type:"serial", width:6, start:1, step:1, pad:"0"}` 6 位流水，左补零（如 `CR-000001`）
- `mode: "auto"`、`use_sequence: false`（反查 max 推进）、`enable_gap: false`
- DAM 维度：`domain_code: "basic"` / `application_code: "basic_dataplatform"` / `module_code: "mdm"`

种子形式：迁移 SQL `docs/sql/migrations/20260805_002_mdm_code_rule.up.sql`（+ down）+ 同步 `init_ddl.sql`。**走 sql-guide 技能**。

> 备注：若希望保留与历史 `CR-{雪花36进制}` 相似的随机性，也可改用 `{type:"random", ...}` 段。但连续流水（serial）更符合"单据号"语义且便于排序/对账，**推荐 serial**。最终由审查/用户定。

### 3.4 前端 changeset 构造（cr-form.js 改造）

标准 `/doc/save` body 形态（merge 模式）。**⚠️ 必须提供所有 NOT NULL 列的值**（见 §1.6），否则校验报 422 或落库报 23502：

```json
{
  "saveMode": "merge",
  "changes": {
    "cv_mdm_apply": {
      "inserted": [{ "id": "t1", "fields": {
        "doc_type": "mdm_supplier_apply",
        "cr_type": "create",
        "target_dict_code": "supplier",
        "doc_status": "draft",
        "line_no": 1,
        "doc_type_id": 1,
        "doc_date": "2026-08-05",
        "entity_id": 1,
        "name": "...", "tax_no": "...", "credit_code": "...", "short_name": "..."
      } }]
    },
    "cv_mdm_apply_line": {
      "inserted": [{ "id": "l1", "upper_id": "t1", "line_no": 1, "fields": {
        "line_type": "bank_account",
        "line_action": "insert",
        "line_payload": { "account_no": "...", "bank_name": "..." }
      } }]
    }
  }
}
```

**关键约定**（对照 §1.6 物理列约束 + 标准保存列分类）：

| 列 | 来源 | 说明 |
|---|---|---|
| `id` / `upper_id` | 前端传临时值（`t1`/`l1`） | 后端 `mint_ids` 铸真号，返回 `idMap` |
| `line_no`（头+行都必传） | **前端必须传** | 在 REPLACED 集跳过校验，但 saver 不自动填值 → 不传会 23502。**头传 `1`，行表 `cv_mdm_apply_line.line_no` 同样 NOT NULL，按序 `1,2,...`** |
| `doc_no` | **前端不传** | cmx-code 铸号（在 validate 前），留空触发自动铸号 |
| `doc_status` | **前端传** `"draft"` | 标准保存不自动写状态字段 |
| `doc_type_id` / `doc_date` / `entity_id` | **前端必须传（占位值）** | NOT NULL 且不在 filled/replaced 集。⚠️ **占位值**：`doc_type_id` 传 `1`、`doc_date` 传当天、`entity_id` 传 `1`。当前 MDM 代码无 doc_type 字典联动、无 entity_id 业务主体隔离、激活器也不读这两列，故占位值短期安全；**待 M7 业务主体/单据类型字典接入后替换为真实值**（见 §九 历史遗留） |
| `create_by` / `create_time` / `delete_flag` | 后端自动填 | 在 FILLED 集，saver `apply_audit_insert` 注入（actor 从登录态注入，前端无需传） |
| `field_deltas`（JSONB） | update 模式前端传**对象** | 见下方 JSONB 约定 |
| `line_payload`（JSONB） | 前端传**对象** | 见下方 JSONB 约定 |

**JSONB 列绑定约定**（⚠️ 审查纠正）：
- 标准保存的列绑定经 `json_to_dv_typed`（`cmx-doc-model/src/codec.rs:34`）→ JSONB 列走 `json_to_dv_loose`（`codec.rs:88`）：
  - JSON **对象/数组** → `DataValue::Json(s)` → `SqlParam::Json` → ✅ PG 接受
  - JSON **字符串** → `DataValue::String` → `SqlParam::Text` → ❌ PG 拒收（`column is of type jsonb but expression is of type text`）
- **结论：`line_payload` 和 `field_deltas` 必须传 JSON 对象，不要 `JSON.stringify`**。cr-form.js 当前 `buildHead()` 已把 field_deltas 构造成对象（`cr-form.js:132-136`），符合要求；`collectLines()` 需把 line_payload 改为对象（当前已是对象，但原 create_cr 里 `lo.get("line_payload").map(|v| v.to_string())` 会序列化——那是旧链路，迁移后前端直接传对象即可）。

**响应与后续流转**：
```json
{ "code":0, "data": { "ok":true, "mode":"merge", "affected":N, "updatedAt":[...], "idMap":{ "t1": <number>, "l1": <number> } } }
```
- `idMap` 的 value 是 **JSON Number**（`Value::Number(new_id.into())`，saver.rs:1335）。CMX 主键走 `Pk52Generator`（`cmx-utils/src/id/mod.rs:85-93`），显式设计为 **52 位 JS 安全主键**（≤ 2^52 < 2^53），在 JS Number 安全区内，**不会丢精度**。前端可直接用数字，`String(idMap["t1"])` 仅作传递一致性的软约定（submit body `{crId}` 的 serde `i64` 解析能接受数字或数字字符串）。
- 保存成功后，若用户点"保存并提交"：取 `crId = idMap["t1"]`（或 `String(...)`）→ `POST /mdm/change-requests/submit {crId}`。

> **⚠️ 编辑已有 CR 的乐观锁基线刷新（审查 N1）**：`saveDocData` 的 `refreshBaselines(data.updatedAt)` + `applyIdMap(data.idMap)` 两步都包在 `if (payload.collector && ...)` 守卫内（`cmx-doc-source.js:246-255`）。**新建 CR（inserted）无需 collector**——首次保存无基线问题。但若 cr-form.js 后续支持"编辑已存在 draft CR 再保存"（updated 桶），**不刷新基线会导致下一次保存因 update_time 陈旧触发 B2 乐观锁冲突**（根层 oplock=update_time）。当前 cr-form.js 只做新建（state.mode=create/update 是 CR 的 cr_type，CR 记录本身总是新插入），故首轮无需 collector；如未来支持编辑已存在 CR，须引入 collector 或保存后用 idMap 重建状态。

### 3.5 前端调用方式：用组件库 saveDocData（而非裸 fetch）

cr-form.js 当前用裸 `fetch` + 自定义 `unwrap`。**审查已确认 native-page 可直接用组件库的 `saveDocData`**——已有 4 处反例：
- `data/native-pages/sources/fi/cmxfico/voucher-native.js:253-257`
- `voucher-native-bin.js:242-243`、`voucher-native-zmcjson.js:265-266`
- `data/native-pages/sources/portal/doc/doc-loader.js:370`

调用形态（参照反例）：
```js
const C = cmx()  // globalThis.__cmxDataComp
const result = await C.saveDocData(
  null,                                              // 第1参 null（坐标走第2参 DEF）
  { domain:'basic', application:'dataplatform', module:'mdm', file:'dataplatform_doc_meta_v1.json', dbId: state.dbId },
  { saveMode:'merge', changes, tableNames: ['cv_mdm_apply', 'cv_mdm_apply_line'] }
)
```
**收益**：
- `saveDocData` 内部已封装坐标拼参 + body 构造 + `idMap` 回填到 CmxDataSet（`packages/cmx-data-comp/src/lib/cmx-doc-source.js:201-257`）。
- 错误展示统一：`e.violations`（422 校验错误）走 `C.formatViolations(e.violations, tableNames)`，比裸 fetch 的笼统 message 更友好（反例 `voucher-native.js:263`）。
- cr-form.js 已有 `const cmx = () => globalThis.__cmxDataComp`，无需新增 import 机制。

**组件库未加载时直接报错（不降级兜底）**：若 `C.saveDocData` 不是函数（组件库 `__cmxDataComp` 未加载），**直接抛错** `throw new Error('组件库未加载，无法保存')`，不回退到裸 fetch。理由（与 T3-2 clone_revise 的 minter None 报错同一哲学）：组件库加载失败属异常配置，应显式暴露而非静默兜底掩盖——否则页面"看似能用"会让真问题潜伏、运维难发现。cr-form.js 现有的 `apiPost`/裸 fetch 代码可一并删除（不再需要）。

## 四、详细任务分解

### T1 · cmx-code 规则种子（MDM_GYS）

- **T1-1**：写 `docs/sql/migrations/20260805_002_mdm_code_rule.up.sql`——INSERT 一条 `cmx_code_rule`（rule_code=MDM_GYS, segments JSONB, mode=auto, DAM=basic/dataplatform/mdm, is_active=1）。
- **T1-2**：写对应 `.down.sql`（DELETE WHERE rule_code='MDM_GYS'）。
- **T1-3**：同步 `docs/sql/init/init_ddl.sql`（在 `cmx_code_rule` 建表之后追加同条 INSERT）。
- **验证**：`SELECT * FROM cmx_code_rule WHERE rule_code='MDM_GYS'` 返回 1 行。

### 5.1 CR 保存（改走标准）
```
POST /api/doc/save?domain=basic&application=dataplatform&module=mdm&file=dataplatform_doc_meta_v1.json
Content-Type: application/json
db_id: <可选>

{
  "saveMode": "merge",

      "inserted": [{ "id":"t1", "line_no":1, "fields": {

        "target_dict_code":"supplier", "doc_status":"draft",

      } }]
    },
    "cv_mdm_apply_line": {
      "inserted": [{ "id":"l1","upper_id":"t1","line_no":1,"fields":{
        "line_type":"bank_account","line_action":"insert",
        "line_payload": { "account_no":"...", "bank_name":"..." }
      } }]
    }
  }
}
```
- ⚠️ **NOT NULL 列必须带齐**（`line_no`/`doc_type_id`/`doc_date`/`entity_id`/`doc_status`），详见 §1.6 / §3.4。`doc_no` 不带（cmx-code 铸号）。

响应：`{ code:0, data:{ ok:true, mode:"merge", affected:N, updatedAt:[...], idMap:{"t1":<number>,"l1":<number>} } }`
- ⚠️ `idMap` 的 value 是 JSON Number（雪花 id），前端用 `String(...)` 转字符串再用，防精度丢失。

## 九、历史遗留（本方案不处理，仅记录）

**approve 状态机元数据与实现脱节**（审查 S4 发现）：DOC 元数据 `dataplatform_doc_meta_v1.json:441-454` 的 `voucherStatusFlow.transitions` 声明 `approve: approving→approved`、`activate: approved→activated`；但实现 `handlers.rs:143-162` 的 `mdm_cr_approve` 直接调激活器，状态走 `approving→activated`（跳过 approved 中态）。这是 M2-0 方案 A 的有意简化（激活器接受 approving，单事务 approving→activated）。**本方案不改动此行为**，仅记录，留待 M7（cmx-flow 审批）统一梳理状态机。

**clone_revise 未走标准链路、无版本快照**（审查 N4 发现）：T3 仅把 clone_revise 的 doc_no 铸号换成 cmx-code，仍保留手写 `INSERT...SELECT` + 逐行插入。克隆出的新 CR **不记 `cmx_doc_revision` 版本台账**（clone_revise 未调 `DocSaver::record_versions`），与新建 CR（走标准链路有版本快照）不一致。短期影响：克隆 CR 无历史版本可回溯；长期技术债：clone_revise 仍手写 SQL，未统一到标准链路。**留待后续统一改造**（可改为"读旧 CR → 构造标准 changeset → DocSaver::save"，但非本方案范围）。

**doc_type_id / entity_id 占位值**（审查 N3 发现）：§3.4 列约定表要求前端传 `doc_type_id:1`/`entity_id:1`/`doc_date:当天`，是 NOT NULL 约束下的占位值。当前 MDM 无 doc_type 字典联动、无 entity_id 业务主体隔离、激活器不读这两列，占位值短期安全。**待 M7 业务主体/单据类型字典接入后替换为真实值**（届时 cr-form.js 的 buildHead 需按字典查 doc_type_id、按登录态取 entity_id）。
