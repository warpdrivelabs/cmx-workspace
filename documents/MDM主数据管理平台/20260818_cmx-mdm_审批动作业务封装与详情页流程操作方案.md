# MDM 审批动作业务封装与详情页流程操作方案（M7.1）

> 版本：V2（决议后定稿）
> 日期：2026-08-18
> 决议（用户确认）：Q1=**全收口到 MDM**（待办中心打开 MDM 任务不挂平台 task-form 控制台）；Q2=**删除 M2 旧端点 approve/reject**（activate 保留）；Q3=**退回首版实现**。
> 背景：M7 上线后用户评审指出两项改进：① 审批/退回/取回等动作不应由前端直调流程 API，应由 MDM 后端封装（业务单据状态校验 → 业务权限校验 → 业务逻辑 → 调工作流 complete → 事件）；② 单据详情页必须有流程操作按钮，不能只提示「去流程待办中心」。
> 关联：`20260817_cmx-mdm_主数据CR审批对接流程平台方案.md`（M7 V4，已上线）。

## 一、现状与差距

| 动作 | 现状 | 差距 |
| --- | --- | --- |
| 同意/驳回 | 待办中心 task-form 控制台（前端）直调 `POST /api/flow/tasks/{id}/complete` | 无业务封装层；cr-form 详情页无操作按钮（仅提示语） |
| 退回 | task-form 直调 `POST /api/flow/tasks/{id}/reject` | 同上；且首版未在 MDM 暴露 |
| 撤回 | `POST /api/mdm/change-requests/withdraw`（MDM 封装：cancel+回草稿） | ✅ 已符合目标模式 |
| 提交 | `POST /api/mdm/change-requests/submit`（MDM 封装六步） | ✅ 已符合 |
| 状态回写 | webhook/懒同步统一入口 `sync_flow_result` | ✅ 保持不动（本方案不引入双写） |
| 待办打开单据 | 发起时 `bizLink{bizTable,bizId}` + `variables{docNo,docType,subjectName,initiator}`；待办中心 task_ctx 注入 `bizId/taskId/formMode`，cr-form 按 bizId 定位 | ✅ 自定义参数机制已存在（见 §五） |

## 二、目标分层（对齐经典「业务 ↔ 工作流」集成范式）

```
前端（cr-form 详情页）     仅传 crId + action + comment
        │ POST /api/mdm/change-requests/review
        ▼
MDM Controller             解析当前登录用户，不做事
        ▼
MDM Service（原子业务）     ① CR 状态校验（approving，防过期/重复审批）
                           ② 业务权限校验（当前用户 ∈ review 任务 assignee∪候选）
                           ③ 业务动作落位：不直接写状态——保持「回写统一入口」铁律
                              （激活/驳回的状态与审计由既有回写链完成，见⑤）
                           ④ 调工作流：POST /api/flow/tasks/{taskId}/complete
                              { decision, comment, operator=当前用户 }（透传其 JWT）
                           ⑤ complete 成功 → 主动 sync_flow_result 同步回写
                              （approve→抢占 activating→激活器；reject→rejected）
                              —— API 返回时状态已是终态，前端无需等 webhook
        ▼
流程引擎                    驱动流转（网关分流→end），webhook 照发（与⑤幂等竞争，
                           try_set 抢占保证单赢家）
```

## 三、新增 MDM 端点（cmx-container）

### 3.1 `POST /api/mdm/change-requests/review` —— 同意/驳回统一入口

body：`{ "crId": i64, "action": "approve" | "reject", "comment": "..." }`
返回：`{ crId, action, status /* 终态：activated / rejected */, instanceId }`

Service 五步见 §二。关键设计：
- ② 的前置权限校验与流程侧 T0b 授权（current_user∈assignee∪候选）是**纵深防御**——② 给业务语义错误（「您不是该单据的审批人」），T0b 是引擎层兜底；
- ⑤ 同步回写复用既有 `sync_flow_result`（五规则/幂等全继承），前端提交后刷新详情即为终态；
- 竞争：⑤ 与 webhook 并发回写由 `try_set_cr_status` 抢占收敛（已上线机制，零新增风险）。

### 3.2 `POST /api/mdm/change-requests/return` —— 退回（打回上节点重办）

body：`{ "crId": i64, "reason": "...", "targetBpmnId": "apply" /* 可选，缺省直接前驱 */ }`

Service：① approving + 实例 ACTIVE ② review 任务 + 权限（同 3.1）④ 调
`POST /api/flow/tasks/{taskId}/reject { instanceId, fromUser: 当前用户, targetBpmnId, reason }`。
退回后实例仍 ACTIVE、任务落回 apply 节点（发起人待办重确认），**CR 保持 approving 无需回写**。
语义对照：撤回=终止实例回草稿（可改数据重提）；退回=实例内打回发起人节点（流程继续、不改单据数据）。

### 3.3 `GET /api/mdm/change-requests/review-context?crId=` —— 详情页按钮数据源

返回：`{ crId, instanceId, taskId, node: "review", canReview: bool, canWithdraw: bool, state }`

- `canReview` = 实例详情的 review 任务 assignee == 当前用户，或该任务出现在
  `GET /api/flow/tasks/my?kind=claimable&assignee=当前用户` 列表（两次回环，可接受，不改 flowengine）；
- `canWithdraw` = 当前用户 == CR create_by 且 doc_status=approving；
- cr-form 装载时调用，按此渲染操作按钮。

### 3.4 既有端点不动

submit / withdraw / flow-status / flow-history / callback 原样；M2 手动端点（approve/reject/activate，
manual_override 默认关）在 review 上线后与 3.1 功能重叠——处置见 §六 Q3。

## 四、cr-form 详情页流程操作（前端）

approving 态操作面板（替换现「请到流程待办中心办理」提示）：

| 可见条件 | 按钮 | 调用 |
| --- | --- | --- |
| canReview | 意见输入框 + 【通过】【驳回】【退回】 | `POST .../review`（action 区分）×2 + `POST .../return` |
| canWithdraw | 【撤回】 | `POST .../withdraw`（已有） |

- 同人双角色（admin 演示态）两组按钮并存；
- 操作成功 → `reloadDetail()` + 流程历史卡刷新（意见即时可见）；
- 审批态（待办中心打开 formMode=approve）：content 区 cr-form 同样渲染上述按钮
  （canReview=true），与右侧 task-form 控制台**双入口并存**（见 §六 Q1）；
- 无 canReview/canWithdraw（纯旁观者）：维持只读 + 流程历史。

## 五、待办中心打开单据：自定义参数机制（现状说明，无需新开发）

发起实例时已注入双通道业务参数：
- `bizLink { bizTable: "cv_mdm_apply", bizId: crId, role: "approval" }` —— 单据坐标（引擎持久化，待办/实例反查）；
- `variables { initiator, docNo, docType, targetDictCode, crType, subjectName }` —— 业务变量（网关条件/表单展示均可消费）。

待办中心打开任务时 `task_ctx` 把 `bizId/taskId/instanceId/formMode/bizTable` 注入 cr-form props
（todo-center.js:585-601），cr-form 按 `bizId` 定位单据渲染——「提交流程时设置自定义参数、
待办经参数打开单据」链路已完整上线。如需增强（例如网关按 `subjectName` 路由不同分支、
表单按 docType 切布局），只改 BPMN/前端消费侧，机制无需动。

## 六、待讨论分歧点

**Q1 待办中心 task-form 控制台的边界**（决议：全收口）：`cmx_flow_form_binding` 加 `console`
字段——`platform`（默认，挂平台控制台，报销/付款等既有业务零变化）/ `none`（表单自带审批操作，
不挂控制台）。MDM 绑定注册声明 `console:'none'`，待办中心打开 MDM 任务时 content 全屏打开
cr-form，审批按钮（调 MDM 端点）在表单内。flowengine 侧改动：绑定表加列（迁移）+ 绑定读写带
console + todo-center.js 按绑定分支渲染。

**Q2 ③「业务逻辑」的分工**：经典范式中 Service 直接改业务状态；本架构状态落位统一在回写链
（⑤同步触发）。审批 API 返回时效果等价（状态已终态），写动作始终单入口。

**Q3 M2 手动端点处置**（决议：删除 approve/reject）：review 端点上线后与之完全重叠（区别仅是
绕过流程），删除 `mdm_cr_approve` / `mdm_cr_reject`（路由/Handler/OpenAPI/前端死代码一并清理）；
`activate` 保留作数据修复兜底（manual_override 开关继续只管它）。

**Q4 退回**（决议：首版实现）：`POST /api/mdm/change-requests/return`，详情页三键齐全。
