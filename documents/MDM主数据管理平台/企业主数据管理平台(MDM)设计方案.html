00执行摘要 · 一页总览

一句话：主数据管理（MDM）不是「再建一个库」，而是为「人、财、物、客」等核心对象建立唯一权威来源（System of Record），用治理流程保证其质量，用集成分发让全企业系统消费同一份「黄金记录」。

🎯 本方案要回答的三个问题
① 业务上——建什么、谁负责、按什么标准、走什么流程（第一部分）； ② 应用上——需要哪些能力、用哪种实现风格、如何保证质量与分发（第二部分）； ③ 技术上——数据模型、表结构、编码/匹配/合并/状态机/API 到可开发的字段级（第三部分）； 最后④ 落到 cmx 平台——不重造轮子，把 MDM 作为 metaKind 新一元长在既有统一建模平台上（第四部分）。

🏅 贯穿全案的核心概念：黄金记录（Golden Record）
来自各源系统的同一实物的多条记录，经匹配（Match）识别为同一对象、合并（Merge）成一条、由存活规则（Survivorship）逐字段选出最可信取值，形成一条企业唯一权威记录——它才是对外分发、被所有系统消费的「真相」。本方案的一切设计（模型、治理、质量、分发）都服务于「稳定地生产并守护黄金记录」这一目标。

01主数据认知与边界 what master data is — and is not

做主数据的第一步不是建库，而是把「主数据」从其它数据里精确地切出来。切错了边界，后面的治理、质量、分发全部落空。

1.1 三类数据的界分

数据类别定义典型例子特征
主数据
Master Data		跨系统、跨流程共享的核心业务对象，描述「业务实体是谁/是什么」客户、供应商、物料、会计科目、成本中心、组织、员工、银行相对稳定、被反复引用、跨系统一致性要求最高
交易数据
Transaction Data		描述某一时刻发生的业务活动，引用主数据销售订单、采购单、会计凭证、发货单、付款单量大、时效强、一次性发生，大量外键指向主数据
参考数据
Reference Data		用于分类/取值约束的小型受控码表，主数据的「取值域」国家、币种、计量单位、行业分类、税码、状态码极稳定、枚举有限、常由外部标准定义（RDM 专管，§10）
💡 一条实用判据
问三个问题：①它是否被两个以上系统/流程引用？②它是否描述一个持续存在的实体（而非一次性事件）？③它一旦错，是否会连累一片交易？三个都「是」——它就是主数据，值得进 MDM 治理。只被单系统内部使用、或纯枚举码表，不必强纳（码表归 RDM）。

1.2 主数据的六个本质特征

① 唯一权威

全企业对同一实体只有一条黄金记录，MDM 是它的 System of Record，其它系统是消费者。

② 跨域共享

被财务、供应链、销售、HR 多域反复引用，是各系统间的「连接键」。

③ 相对稳定

变化频率远低于交易数据，但一旦变（如客户改名/合并）影响面极大，须留痕。

④ 结构复杂

属性多、分组多、常带层次（组织树、科目表、物料分类），且多语言/多视图。

⑤ 多源汇入

常同时存在于 ERP、CRM、SRM、旧系统，天然产生重复与冲突，需匹配合并。

⑥ 需要治理

其价值来自「被信任」，因此必须有 Owner、有标准、有审批、有质量闭环。

1.3 主数据的分层视图

一条主数据在 MDM 内不是「一张扁平表」，而是分层组织的——这与既有厂商（SAP 的 Reuse/Attribute、Oracle 的实体+层次）一致，也天然契合 cmx 的分层建模：

主数据对象（如：供应商 Supplier） ├─ 标识层 唯一 ID（MDM 内码）+ 各源系统外码（Key Mapping）+ 状态 ├─ 通用属性 名称/简称/多语言名/税号/信用代码/统一社会信用…（全局唯一口径） ├─ 分组属性 财务视图(付款条件/税务) · 采购视图(采购组织/评级) · 物流视图(收货地址) ├─ 层次归属 所属分类(供应商类别树) · 所属集团/组织(组织树) · 集团-成员关系 └─ 关系 一供多址 · 集团母子公司 · 客商合一(同一法人既是客户又是供应商)

分组属性 = 「按业务视图分片」，正是 SAP MDG 的 reuse-area 与 cmx 分层单据「每层不同数据属性」的同构点（§20 详述）。

02现状痛点与建设价值 why it always hurts

几乎所有企业的主数据问题都能归到下面六条。方案的价值主张就是逐条对治它们。

2.1 六大典型痛点

痛点表现与根因后果
一物多码
duplicate codes		同一物料/供应商在不同系统、工厂、环节有多个编码；编码位数与分类口径不一（有的 10 位有的 12 位）无法集中议价、成本虚高、库存失真（冗余与缺货并存）、协同要大量人工转码
一码多物
code reuse		编码复用、废弃码回收再用，同一编码在不同时间指向不同实物历史数据错乱、审计追溯失败，比一物多码更隐蔽危险
标准不一致部门间分类/属性/命名口径各行其是，缺统一标准协同壁垒，合规与财务数据割裂，报表口径打架
质量回潮做完主数据用一两年质量又退回原状——缺质量闭环：发现不了、发现了不知找谁、改了不知对没对投入打水漂，业务重新绕过主数据自建小表
重系统轻数据先上系统后才发现底层基础数据未统筹设计系统越多，数据裂缝越大，集成成本指数上升
责任真空数据「谁都在用、没人负责」，没有 Owner 与认责机制问题无人整改，标准无人维护

2.2 价值主张（对治关系）

🎯 对业务的价值

  • 降本：消灭一物多码→采购集中议价、库存去冗余
  • 提效：一次维护多系统复用，免除跨系统人工转码
  • 合规：客商/科目口径统一，满足审计与监管报送
  • 决策：全域单一视图，报表口径一致可比

🛠 对 IT 的价值

  • 解耦：源系统只管消费，主数据集中生产
  • 可控：变更走审批留痕，可回溯可回滚
  • 可扩：新系统接入即订阅，边际成本递减
  • 提质：质量规则前置，脏数据进不来
⚠ 必须专门防范：一码多物（编码回收再用）
多数方案只盯「一物多码」，却忽略反向的「一码多物」。它源于废弃编码被回收重用。铁律：主数据编码一经启用永不回收、永不复用，废弃走「冻结/归档」而非「删除后让号段可再分配」。本方案的编码引擎（§15）与生命周期（§06）把这条钉死为不可违反的约束。

03主数据域全景 the domains

本方案覆盖四大域，以财务域为主，兼顾客商、物料、组织人员，并保留「全域通用建模」能力（任意新域可配置落地）。每个域给出关键实体、层次形态与责任主体。

财务域（主）

关键实体：会计科目、成本中心、利润中心、往来单位（客商财务视图）、币种、财务组织、现金流量项目、核算维度（辅助核算）。
层次：科目表（多级树）、成本中心层级、利润中心层级、组织树。
责任主体：财务共享中心 / 集团财务部。
对齐既有 fico / GL 场景，科目·成本中心·往来单位是财务共享与合并报表的底座。

客商域

关键实体：客户、供应商、（客商合一的）业务伙伴 Business Partner、联系人、银行账户、收发货地址。
层次：客户/供应商分类树、集团客户母子层级、一客多址。
责任主体：销售管理部（客户）/ 采购管理部（供应商）。
最需要匹配合并——同一法人既是客户又是供应商、集团客户合并授信。

物料域

关键实体：物料/产品、物料分类、计量单位与换算、规格型号、品牌、条码。
层次：物料分类树（多级）、产品目录、BOM 相关引用。
责任主体：供应链 / 技术部（分类与规格）。
分类模型行业化最深（用友物料精细化分类的借鉴点），与 PIM 边界相邻。

组织人员域

关键实体：法人/公司、组织架构单元、部门、岗位、员工、角色。
层次：法人层级、行政组织树、汇报线、成本中心-部门映射。
责任主体：集团管控部 / HR。
与既有 IAM（cmx 库人与组织）打通，MDM 侧管「主数据口径」，IAM 管「登录鉴权」。

🔗 关键跨域关系：客商合一 与 组织贯穿
① 客商合一（Business Partner 模型）：借鉴 SAP BP——同一法人可同时扮演客户、供应商、往来单位多个「角色（Role）」，共享一份标识与通用属性，各角色挂各自视图属性。避免「同一公司在客户表和供应商表各存一份、改名只改一边」。
② 组织贯穿：组织既是一个域，又是所有域的「受控维度」——编码规则按组织生效、数据按组织分级维护、分发按组织授权（§05/§06/§15）。

04数据治理体系 two systems + one tool · the "four-definitions"

主数据的价值来自「被信任」，而信任来自治理。业界一句共识：制度/治理必须先于工具（TIBCO EBX、DAMA-DMBOK 均强调），黄金记录非一劳永逸，无持续治理必然随时间劣化。本节给出治理的组织、制度与方法论骨架。

4.1 治理总框架：两体系一工具

参考国内主流实践（用友/金蝶及主数据管理办法通行做法），一份完整的主数据治理由「标准体系 + 保障体系 + 管理工具」三支柱构成，分别回答三个问题：

① 标准体系 依据什么

分三类标准：管理标准（定义/分类/责任）、应用标准（分类标准·编码规则·属性描述规则·提报指南）、集成服务标准（分发接口与服务口径）。每条标准附「责任部门、审批流程、启停用日期」等管理属性。→ 详见 §05。

② 保障体系 谁负责

组织与制度：数据 Owner / 数据管家（Steward）/ 认责人三级角色 + MDM 委员会 + 考核指标（KPI）。核心是「发现—分析—整改—验证」质量闭环，Owner 是整改第一责任人。→ 详见 4.3/4.4。

③ 管理工具 用什么

即本 MDM 平台：建模、编码、申请审批、清洗查重、质量监控、分发集成。工具是标准与保障体系的技术承载，不能反过来替代制度。→ 详见第二/三部分。

4.2 实施方法论：四定 + 四阶段

方案落地推荐「四定」方法论作为主线（国内集团主数据项目通行）：

定岗责· 定标准· 定流程· 定平台
阶段工作产出 / 验收
① 现状调研各系统数据摸底、梳理属性字段、识别质量问题（一物多码/一码多物量化）现状评估报告、问题清单（需业务深度配合）
② 方案设计四定：定岗责、定标准、定流程、定平台主数据管理体系设计文档（含本方案四部分）
③ 系统实现数据模型建设、期初数据清洗、接口开发联调、内部测试可运行平台、清洗后的黄金记录、联调通过
④ 上线运营用户测试、培训宣贯、上线试运行 → 长期定期质量审核、线上新增审批验收标准示例：能否自动识别一物多码、数据错误率是否下降

5.2 编码规则的六种构件

一条编码规则由若干「段（Segment）」拼接而成。参考 SAP 编号范围、金蝶苍穹编码规则、用友编码管理，段的类型收敛为六种：

① 常量段

固定前缀/后缀，如物料码首位 M、供应商 V。

② 属性取值段

取主数据某属性值或其映射，如「分类码=电子→EL」「组织码」。

③ 流水号段

自增序列，可按范围/按分组重置（0001…）。核心防重构件。

④ 日期段

年月日，如 2026/2608，用于批次类。

⑤ 校验位段

Luhn/模 11 等校验码，防止手工录入错码。

⑥ 分隔符段

可选 -/.，仅显示用，不参与唯一性。

5.3 借鉴金蝶：编码规则的适用条件

🏅 按受控组织生效 + 按属性设适用条件
金蝶苍穹的关键机制值得直接吸收：① 按受控组织生效——同一主数据在不同组织可用不同编码规则，当前登录组织落在规则的「受控组织」范围内时规则才生效；② 按单据/对象属性设适用条件——如「物料分类=原材料」走规则 A、「=成品」走规则 B。易错点（金蝶实测）：对象未设主业务组织时，不能使用设了受控组织的编码规则——方案的编码引擎须显式处理「无组织上下文」的兜底规则。

5.4 编码治理的三条铁律

  1. 编码即身份，永不回收：主数据编码一经启用，即便对象作废也永不复用（防「一码多物」，§02）。作废走冻结/归档，号段不释放。
  2. 内码 ≠ 外码：MDM 内部用稳定的系统内码（surrogate ID）作主键与关系锚点；对业务展示的「编码」是可读外码。改编码规则不动内码，关系不断裂（对齐 SAP Key Mapping、§16）。
  3. 规则可版本化：编码规则本身是受管对象，改规则留版本、标启停日期，旧对象保留旧码、新对象用新规则。

9.4 合并 vs 存活（务必区分）

合并 Merge = 结构

把识别为同一实体的多条记录并成一个容器；子实体（联系人/地址/交叉引用）重新挂到存活记录（re-parent）；victim 置「已合并」状态，不硬删，可 unmerge 还原（合规要求）。

存活 Survivorship = 取值

决定每个属性的最终真值。策略：源优先级 / 最新胜出 / 最全胜出 / 质量分驱动。字段级（cell-level）信任优于整记录排序——把多源各自最强字段组合成一条黄金记录。
✅ 存活规则的四种策略 + 三条实务
策略：① 源系统优先（如财务字段 SAP 恒胜）② 最新胜出（按最后更新时间）③ 最全胜出（空值更少者胜）④ 质量分/信任分驱动。实务：① 空值保护——高优先级源为 NULL 时用次优先级有效值，别让空值覆盖好数据；② 与 DQ 联动——通不过校验的字段自动降信任（Informatica 差异化）；③ 平局用 tie-breaker（最新/最高源）。⚠ 存活规则「听起来简单，企业级规模下极难」——数十源×数百属性时是 MDM 最耗时的设计阶段。

15编码规则引擎设计 the coding engine

编码引擎把 §05 的业务规则变成可执行的字段级设计。核心：规则由段（segment）序列组成，按受控组织+条件选规则，服务端原子铸号防重。

15.1 规则声明（JSON，进 md_code_rule.segments）

{
  "entityType": "supplier",
  "orgScope": "HQ",                     // 受控组织：此组织登录时生效(金蝶机制)
  "condition": "attrs.category == 'raw_material'", // 适用条件：按属性分流
  "segments": [
    { "type": "const",    "value": "V" },                    // ① 常量段
    { "type": "attr",     "field": "category", "map": {"raw_material":"RM"} }, // ② 属性取值段
    { "type": "date",     "format": "YYMM" },              // ④ 日期段
    { "type": "serial",   "width": 4, "resetBy": "category+YYMM" }, // ③ 流水号(按分组重置)
    { "type": "check",    "algo": "mod11" }              // ⑤ 校验位段
  ]
  // 生成示例：V·RM·2608·0001·7  →  VRM260800017
}

15.2 铸号流程（服务端原子，防并发重号）

申请编码(entityType, attrs, orgCtx) │ ├─1. 选规则：按 orgScope 命中受控组织 + condition 求值 → 唯一规则 │ └ 无组织上下文 → 兜底规则（金蝶易错点：显式处理） ├─2. 逐段求值：const/attr/date 直接算；serial 段进下一步 ├─3. 流水号原子分配： │ INSERT INTO md_serial(rule_id, reset_key, next_val) │ ON CONFLICT DO UPDATE SET next_val = md_serial.next_val + 1 │ RETURNING next_val; ← 行锁，并发安全 ├─4. 拼接 + 校验位：segments.join() + mod11(...) ├─5. 唯一性终检：UNIQUE(entity_type, code) 兜底 └─6. 返回 code（永不复用；作废走冻结不释放号段）
🏅 三条编码铁律落到字段（呼应 §05）
① 永不回收：无「删除释放号段」逻辑，作废只置 status='frozen'，md_serial.next_val 只增不减；② 内码≠外码：关系全锚在 md_golden.id（bigint 内码），code 改规则可重生成而关系不断；③ 规则版本化：md_code_rule 带 valid_from/valid_to，旧对象留旧码。

16.1 分块（Clustering）—— 生成多簇键

// 每条记录生成 N 个带优先级的簇键，只比较同簇（绝不 N×N）
fn cluster_keys(rec: &Record) -> Vec<(String, u8)> {   // (key, priority)
  vec![
    (soundex(&rec.name), 1),                  // 音近：Oracle≈Oracle Ltd 同簇
    (metaphone(&rec.name), 2),
    (first_n(&normalize(&rec.name), 5), 3),      // 前5字符
    (rec.tax_id.clone().unwrap_or_default(), 0),  // 税号：强标识优先级最高
  ].into_iter().filter(|(k,_)| !k.is_empty())     // 防 NULL 巨簇
   .collect()
}
// 护栏：簇大小上限 500（超则告警+子簇拆分并行）；比较次数上限

16.3 裁决（三向决策 + 双阈值）

// 有序规则表逐条求值，产出三向决策之一（对齐 Oracle CDM 双阈值）
enum MatchDecision { AutoMerge, Review, NoMatch }

fn decide(score: u8, cfg: &MatchCfg) -> MatchDecision {
  if score >= cfg.automerge_threshold { AutoMerge }        // 如 ≥95 自动合并
  else if score >= cfg.match_threshold { Review }         // 如 80-94 进人工队列
  else { NoMatch }                                       // <80 保留为新记录
}
// 护栏：① 组内每条都须过 automerge，否则整组转 Review
//      ② 组大小上限（默认10）③ 多候选时对最高分匹配
// 调优靠规则/分数（可预测、可审计），非黑盒算法旋钮

16.4 合并 + 存活（结构 + 取值分离）

// 合并=结构：子实体 re-parent 到存活记录，victim 置'merged'不硬删
fn merge(group: &MatchGroup, rules: &[SurvivorRule]) -> GoldenRecord {
  let master = pick_master(group, rules);          // 选存活主：源优先/最新/最全/最老
  for field in all_fields() {
    golden[field] = survivorship(field, group, rules); // 逐字段选真值(cell-level)
  }
  reparent_children(group, master.id);            // 联系人/地址/xref 移到 master
  mark_victims_merged(group, master.id);          // victim status='merged'，可 unmerge
  golden
}
// 存活策略（逐字段）：
//   source_precedence — 源系统信任分最高胜（md_xref.confidence）
//   most_recent       — updated_at 最新胜
//   most_complete     — 非空胜（空值保护：别让NULL覆盖好数据）
//   quality_score     — 通不过DQ校验的字段降信任(Informatica差异化)
✅ 字段级存活（cell-level）—— 把多源各自最强字段拼成黄金记录
存活不是「整条记录二选一」，而是逐字段选真值：名称取 CRM 的、税号取 ERP 的、地址取最新的——组合成一条谁都比不过的黄金记录。md_merge_record 记录每字段的取值来源与理由，形成可审计的存活裁决轨迹（对齐 Informatica BVT、Oracle Set Attribute Value）。

关键顺序：M0/M1 数据底座先行 → M2 编码 + M3 治理流可并行 → M4 匹配是难点核心 → M5-M7 收敛。三个新造件（编码/匹配/分发事件）是全部工程重心，其余皆复用。

22.1 风险与取舍

  • 引擎绝不认识具体域（底线，不能破）：域数、实体、属性、层次、编码规则、汇总关系全部只存在于定义 JSON；cmx-mdm 引擎逐条按定义驱动，绝不为「供应商」「科目」写 if 分支——这是 DOC 引擎已验证的通用性铁律，MDM 必须坚守。
  • 匹配合并是真正的难点：存活规则「企业级规模下极难」（数十源×数百属性）。建议 M4 从精确匹配 + 单一存活策略起步，逐步加模糊/AI；分块的 NULL 巨簇、簇大小上限务必设护栏。
  • 不要过度统一：MDM 是结构化主数据，不要套用 RPT 的 SpreadJS 自由画布 BLOB。共享的是「元模型+两模式+治理流+三段后端+四区外壳」，不是渲染内核（同 DOC/DCT 教训）。
  • 服务端计算为权威：编码铸号、匹配存活、层次汇总全部服务端为准，绝不信任前端值直接落库（防篡改、防浏览器缺陷）。
  • 内码永不复用是不可违反约束：md_golden.id bigint 内码 + code 外码分离，作废走冻结/归档，号段不回收——防「一码多物」的架构级保证。
  • 制度先于工具：MDM 成败七分治理三分工具。平台就绪≠数据变好，必须先落「两体系一工具 + 四定 + Owner 认责」（§04），否则黄金记录随时间劣化。
  • 与既有 IAM 边界清晰：组织人员域的 MDM 管「主数据口径」，cmx 库 IAM 管「登录鉴权」；复用不重造，通过 org.path 打通分级。
  • 点对点集成蔓延：坚持「规范模型 + 中央事件日志 + 本地副本」，避免退化成 N×N 点对点接口（SAP MDI 的核心教训）。
🧭 一页纸总结
这份主数据方案业务上以「两体系一工具 + 四定 + 七状态生命周期」立治理骨架，对标 SAP MDG/Oracle/用友/金蝶；应用上以「八大能力域 + 四种实现风格 + 黄金记录七步流水线」立能力全景；技术上到「md_* 字段级表结构 + 编码引擎 + 双阈值匹配 + 字段级存活 + 决策表状态机 + REST 契约 + delta 事件」可开发深度；落地上把 MDM 作为 metaKind 新一元长在既有 cmx 统一建模平台上——约 70% 复用 DCT 数据底座/cmx-flow 治理流/cmx-agg 汇总/异步任务中心分发/native-pages 四区，真正新造仅编码、匹配合并、分发事件三个领域引擎。既通用可对标，又能在自有平台低风险落地。
