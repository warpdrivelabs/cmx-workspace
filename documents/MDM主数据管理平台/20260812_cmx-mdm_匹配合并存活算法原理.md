# MDM 匹配合并存活算法原理

> 本文档讲清楚 cmx-mdm 的查重/合并/存活机制——为什么这么设计、代码在哪、SQL 怎么全表查重。
> 配套代码：`cmx-container/crates/libs/cmx-mdm/`。
>
> 日期：2026-08-12　·　适用版本：M3.5（含全库扫描查重）

---

## 一、业务背景：为什么要匹配

主数据（供应商/客户/物料）从多个系统汇入：ERP、CRM、SRM、旧系统。**同一实体被反复录入**，形成「一物多码」：

```
ERP    → 供应商「华东钢铁集团有限公司」credit_code=91310115MA1K3B2X56
CRM    → 供应商「华东钢铁集团」        credit_code=91310115MA1K3B2X56  ← 同一主体！
旧系统 → 供应商「华东钢铁」            credit_code=（空）              ← 可能也是
```

不处理的话：重复采购、对账混乱、报表失真、信用额度被绕开。

**查重的任务**：从 `cm_supplier`（已发布主数据）里找出这些重复簇，交给管家评审合并，最终只保留一条「黄金记录」。

---

## 二、核心挑战：N×N 比较爆炸

最朴素的做法：每条记录和其他所有记录两两比对。但这是 **O(N²)** 复杂度：

| 记录数 | 两两比较次数 |
|--------|-------------|
| 1,000 | 499,500（50 万） |
| 10,000 | 49,995,000（5 千万） |
| 100,000 | 4,999,950,000（**50 亿**） |

10 万条供应商就要比 50 亿次——内存和算力都扛不住。所以**必须先分块，只比「可能重复」的记录对**。

---

## 三、四阶段流水线总览

```
cm_* published 全表
        │
        ▼
① 分块（Blocking）    按簇键（credit_code 等）把记录分到同值桶
        │              只比同桶 → 比较数从 N² 降到 Σ(桶大小²)
        ▼
② 比较（Compare）     块内两两算加权相似度得分 0-100
        │
        ▼
③ 裁决（Decide）      双阈值：≥95 自动合并 / 80-94 人工评审 / <80 不匹配
        │
        ▼
④ 合并存活（Merge）   victim 置 merged + 字段级存活取值写回 master
```

**代码位置速查**：

| 阶段 | 文件 | 关键函数 |
|---|---|---|
| ① 分块 | `cmx-mdm-model/src/match_algo.rs` | `blocking()` |
| ① 分块下推 SQL | `cmx-mdm-store-pg/src/match_store/loader.rs` | `load_suspects()` |
| ② 比较 | `cmx-mdm-model/src/match_algo.rs` | `compare()` |
| ③ 裁决 | `cmx-mdm-model/src/match_algo.rs` | `decide()` |
| ④ 存活 | `cmx-mdm-model/src/survivorship.rs` | `survive()` |
| ④ 合并事务 | `cmx-mdm-store-pg/src/activation_service.rs` | `merge()` |
| 全库扫描 | `cmx-mdm-model/src/match_algo.rs` | `scan_clusters()` |
| 发现项 CRUD | `cmx-mdm-store-pg/src/scan_store.rs` | `insert_findings()` 等 |

## 四、分块（Blocking）原理

### 4.1 为什么分块能把 N² 降到接近线性

分块把「同簇键值」的记录归到一只桶，**只在桶内两两比较**。

假设 10 万条供应商，按 credit_code 分桶后：
- 大多数桶只有 1 条（无重复）→ 不参与比较
- 少数桶有 2-5 条（疑似重复）→ 桶内比 `C(5,2)=10` 次
- 极少数桶很大（如 name="张三" 几千条）→ 护栏截断

总比较数 ≈ Σ 桶内 C(桶大小, 2)，**远小于** C(10万, 2)。

### 4.2 簇键选择

簇键（cluster_keys）按**优先级序**配置：

```js
cluster_keys: ["credit_code", "tax_no", "name"]
```

每条记录取**第一个非空簇键值**作桶键：

```
记录 A: credit_code="C1" → 桶键 "credit_code:C1"
记录 B: credit_code="C1" → 桶键 "credit_code:C1"  ← 和 A 同桶！
记录 C: credit_code="" tax_no="T2" → 桶键 "tax_no:T2"  ← credit_code 空回退到次级
```

高优先级键（credit_code）是强标识——同值几乎必为同一主体；低优先级键兜底处理 credit_code 缺失的情况。

### 4.3 两个护栏

**护栏 1：NULL 巨簇防护**

如果允许空簇键进共享桶，所有 `credit_code` 为空的记录会挤进「credit_code:」一只桶——可能几万条，退化成 N²。

所以：**簇键全空的记录不进任何共享桶**（变孤儿，不参与比较）。

**护栏 2：桶上限 BLOCK_CAP = 500**

```
match_algo.rs:70  pub const BLOCK_CAP: usize = 500;
```

某桶超过 500 条时截断 + `tracing::warn`（被截记录本桶内不参与比较）。这是兜底——正常数据不会触发，触了说明该簇键区分度太低（如 name="张三"），M4 会降级到次簇键再分桶。

### 4.4 SQL 下推：全表查重怎么不爆内存（重点）

早期实现是把 `cm_supplier` 全表拉到应用层再分块：

```rust
// ❌ 旧：拉全量（几十万行爆内存）
let all = load_published(mm, db_id, "cm_supplier", &columns).await?;
let blocks = blocking(&all, &cluster_keys);
```

问题：N=几十万时，单次 query 几百 MB 结果集 + 应用层全驻留。

**新方案：把分块逻辑下推到 SQL，只拉「嫌疑记录」**（`load_suspects`）：

```rust
// ✅ 新：DB 内分块，只回传嫌疑记录
let suspects = load_suspects(mm, db_id, "cm_supplier", &columns, &cluster_keys).await?;
```

SQL 长这样（以 credit_code + tax_no 两簇键为例）：

```sql
WITH
  -- 阶段1：找出「有重复」的 credit_code 值（出现次数>1）
  s_credit_code AS (
    SELECT credit_code AS k FROM cm_supplier
    WHERE lifecycle_status='published' AND credit_code IS NOT NULL AND credit_code <> ''
    GROUP BY credit_code
    HAVING COUNT(*) > 1          -- ← 关键：只保留重复的
  ),
  -- 同理找重复的 tax_no
  s_tax_no AS (
    SELECT tax_no AS k FROM cm_supplier
    WHERE lifecycle_status='published' AND tax_no IS NOT NULL AND tax_no <> ''
    GROUP BY tax_no HAVING COUNT(*) > 1
  )
-- 阶段2：把命中任一嫌疑键的记录拉出来
SELECT DISTINCT id, credit_code, tax_no, name, update_time
FROM cm_supplier t
WHERE lifecycle_status='published'
  AND (
    t.credit_code IN (SELECT k FROM s_credit_code)
    OR t.tax_no IN (SELECT k FROM s_tax_no)
  );
```

**`GROUP BY ... HAVING COUNT(*) > 1` 是怎么找重复的？**

`GROUP BY credit_code` 按 credit_code 分组，每组里的记录 credit_code 相同。
`HAVING COUNT(*) > 1` 只保留「组内行数 > 1」的组——也就是该 credit_code 对应了多条记录，即潜在重复。

```
原始表                         GROUP BY credit_code HAVING COUNT>1
┌─────────────────────────┐    ┌──────────────────────┐
│ id=1 credit_code=C1     │    │ k=C1 (有3条，保留)    │
│ id=2 credit_code=C1     │ →  │ k=C2 (有2条，保留)    │
│ id=3 credit_code=C1     │    └──────────────────────┘
│ id=4 credit_code=C2     │    C3 只有1条 → 过滤掉（不算重复）
│ id=5 credit_code=C2     │
│ id=6 credit_code=C3     │
└─────────────────────────┘
```

然后 `WHERE credit_code IN (SELECT k FROM s_credit_code)` 把 credit_code∈{C1,C2} 的记录全拉出（id 1-5，共 5 条，而非全表 6 条 + 其他几万条）。

**效果**：几十万主数据，嫌疑块通常只有几百~几千条。应用层只对这几百条做字段级精细比较。

> **注意**：簇键是**精确等值**分块——credit_code 必须完全相等才同桶。EditDistance 字段（如 name）作簇键时，仅完全相同的名称才同桶；拼写差异（"华东钢铁" vs "华东钢铁集团"）由 `compare` 阶段的编辑距离评分兜底。

## 五、比较算法（Compare）

块内两两记录算**加权相似度得分**（0-100）。

### 5.1 公式

```
score = Σ(字段得分 × 字段权重) / Σ字段权重
```

不同字段对「同一主体」的证据强度不同：
- `credit_code`（统一社会信用代码）全等 → 几乎断定同主体（强证据）
- `name` 相似 → 重名常见（弱证据）

所以强标识字段配高权重：

```js
specs: [
  { field: "credit_code", weight: 40, kind: "Exact" },        // 强标识
  { field: "tax_no",      weight: 30, kind: "Exact" },        // 强标识
  { field: "name",        weight: 30, kind: "EditDistance" }, // 弱标识
]
```

### 5.2 字段得分两种算法

**Exact（全等）**：相等=100，不等=0。非黑即白，适合强标识字段。

**EditDistance（编辑距离）**：容忍拼写错误。

```
字段得分 = 100 × (1 - 编辑距离 / 最大长度)
```

举例（name 字段）：

| master | victim | 编辑距离 | max_len | 得分 |
|---|---|---|---|---|
| 华东钢铁集团有限公司 | 华东钢铁集团有限公 | 1 | 10 | 100×(1-1/10)=**90** |
| 华东钢铁集团 | 华东钢铁集团公 | 1 | 7 | 100×(1-1/7)≈**85** |
| 甲公司 | 乙公司 | 1 | 3 | 100×(1-1/3)≈**66** |

### 5.3 空值处理（关键设计）

**两侧均空的字段跳过**——空值不是「相同」的证据。

```
记录 A: credit_code="C1", tax_no=null,  name=null
记录 B: credit_code="C1", tax_no=null,  name=null
```

如果 tax_no 和 name 参与计算，它们「都空」会被当成「相同」加分，导致两条 credit_code 都为 C1 的记录得分虚高。但实际上 tax_no/name 都空**什么都没证明**。

所以跳过：只按 credit_code（weight=40）算 → 得分 100（C1 全等）。分母只有 40，不被空字段稀释。

### 5.4 完整举例

```
A: credit_code="C1", tax_no="T1", name="华东钢铁集团有限公司"
B: credit_code="C1", tax_no="T1", name="华东钢铁集团有限公"

字段得分：
  credit_code Exact: C1==C1 → 100，weight 40 → 贡献 100×40=4000
  tax_no      Exact: T1==T1 → 100，weight 30 → 贡献 100×30=3000
  name        EditDistance: 差1字/10字 → 90，weight 30 → 贡献 90×30=2700

总分 = (4000+3000+2700) / (40+30+30) = 9700/100 = 97 → AutoMerge
```

## 六、双阈值裁决（Decide）

把得分映射成三种决策：

```
┌─────────────────────────────────────────────────────────┐
│  score ≥ 95  │  AutoMerge  │  几乎确定同主体             │
│              │             │  credit+tax 全等+name 差一字 │
│              │             │  可自动合并（M3 仍走管家确认）│
├─────────────────────────────────────────────────────────┤
│  80 ≤ score < 95 │ Review │  疑似重复，证据不够强         │
│                  │        │  进管家工作台人工评审         │
├─────────────────────────────────────────────────────────┤
│  score < 80  │  NoMatch    │  字段差异大，不视为重复       │
│              │             │  新记录正常入库               │
└─────────────────────────────────────────────────────────┘
```

阈值 95/80 是经验值。`md_match_config` 表可按字典场景调整（`thresholds` 字段）。

## 七、存活规则（Survivorship）

合并不是简单「删掉 victim」——两条记录各有各的完整字段，要**逐字段挑出真值**写回 master。这叫存活（Survivorship）。

### 7.1 三种字段级策略

| 策略 | 含义 | 适用 |
|---|---|---|
| `MasterFirst` | master 非空用 master，否则补 victim | 默认。master 是权威源 |
| `Fullest` | 非空优先；都非空取 master | 想尽量补全空字段 |
| `Latest` | 按 update_time 取新者 | 信任最新数据 |

### 7.2 举例

```
master:  name="华东钢铁", phone="111", tax_no=null
victim:  name="华东钢铁集团", phone=null, tax_no="T1"

MasterFirst:
  name   → master 非空 → "华东钢铁"
  phone  → master 非空 → "111"
  tax_no → master 空 → 取 victim → "T1"     ← 空值补全！

Fullest:
  name   → 都非空 → master → "华东钢铁"
  phone  → victim 空 → master → "111"
  tax_no → master 空 → victim → "T1"
```

管家还可以**逐字段人工裁决**（工作台弹层：选 master / 选 victim / 手填值），覆盖算法结果。

### 7.3 留痕

每个字段的存活决策都记进 `md_merge_record.survivorship_log`：

```json
{ "fields": [
  { "field": "name", "from": "master", "value": "华东钢铁" },
  { "field": "tax_no", "from": "victim", "value": "T1" }
]}
```

后续 unmerge（还原）时可据此回溯。

## 八、合并事务（CAS 并发控制）

合并是高危操作——两条 published 主数据合并，下游系统都在消费。必须**单事务原子**+**并发安全**。

### 8.1 单事务编排（10 步）

`activation_service.rs::merge` 在一个 DB 事务内完成：

```
① lock_record(master, FOR UPDATE)     占 master 行锁，串行化交叉合并
② 读 master + victims（须 published） 校验状态
③ survive 逐字段累积                  字段级存活取值
④ victim: set_lifecycle(published→merged) + version+1（CAS）
⑤ reparent_lines（明细改挂 master）  银行账户等子表 supplier_id 改指
⑥ update_header(master, 存活值+version+1, CAS)
⑦ deactivate_xref(victim)             交叉引用置 inactive
⑧ write_audit(action=merge)           审计留痕
⑨ write_event(merged, payload)        分发事件
⑩ update_match_group(reviewed)        合并组状态流转
```

任一步失败 → 事务回滚，无中间态。

### 8.2 两道并发护栏

**护栏 1：master 行锁（FOR UPDATE）**

```
SELECT id FROM cm_supplier WHERE id = $master_id FOR UPDATE
```

两个管家同时合并同一 master → 后到者等前者提交/回滚后才拿到锁，串行化。

**护栏 2：victim 状态 CAS + version+1**

```sql
UPDATE cm_supplier
SET lifecycle_status='merged', published_version = published_version + 1
WHERE id = $victim_id AND lifecycle_status = 'published'
```

`WHERE lifecycle_status='published'` 是 CAS 期望值——victim 必须当前是 published 才能改 merged。双 merge 同时命中同一 victim → 只有一个 WHERE 命中（n=1），另一个 n=0 报错。

`published_version+1` 是第二道保险：并发的 update-CR（变更请求激活）若读到旧 version，CAS 失败回滚，避免改已合并的行。

## 九、全库扫描查重工作流（M3.5）

### 9.1 两种查重模式

| 模式 | 入口 | 场景 | API |
|---|---|---|---|
| 锚点查重 | duplicate-check（锚点模式） | 已知一条记录，找它的同伙 | `POST /mdm/records/find-duplicates`（带 recordId） |
| 全库扫描 | duplicate-check（扫描模式） | 不知道哪些重复，主动发现 | `POST /mdm/match-scan/run`（无 recordId） |

### 9.2 全库扫描数据流

```
管家点「开始扫描」
      │
      ▼
load_suspects（DB 内分块，拉嫌疑记录）
      │
      ▼
scan_clusters（应用层聚类：嫌疑记录 → 重复簇）
      │  块内两两 compare，score≥80 的聚成簇
      ▼
insert_findings（落 md_match_scan，cluster_hash 去重）
      │  相同成员集合的 pending 不重复入库
      ▼
返回 { newFindings, skipped, pendingTotal }
```

管家在工作台（steward.js「查重发现项」tab）看到 pending 列表：

```
点簇 → /mdm/match-scan/detail → 字段对比弹层
  ├─ 确认合并 → /mdm/merge-requests（带 scanId）→ scan 自动 resolved
  └─ 忽略     → /mdm/match-scan/ignore         → scan 置 ignored
```

### 9.3 cluster_hash 去重

每次扫描可能产生大量簇。如果不去重，管家没处理的簇会随每次扫描重复入库。

`cluster_hash` = member_ids 升序后 SHA256 前 32 hex 字符：

```
簇 {1, 2, 3} → 排序 [1,2,3] → SHA256 → "a1b2c3..."
簇 {3, 1, 2} → 排序 [1,2,3] → 同样的 hash
```

插入前先查 dict_code 下所有 pending 的 hash 集合，命中则跳过。**已 resolved/ignored 的簇不参与去重**——如果数据后来又重复了，会重新产生 pending 提醒管家。

## 十、md_match_scan vs md_merge_record（职责分离）

> **改名说明**：旧名 `md_match_group`（匹配组），因语义模糊（与 md_match_scan 易混）已整合为 `md_merge_record`（合并事务记录）。migration 已合并到 `20260812_001_mdm_治理表`，直接用最终名建表（不再有 RENAME 演进步骤）。

两张表是查重流程的**不同阶段载体**。一句话区分：

- **md_match_scan = 线索**（系统扫描出的「嫌疑重复」，待管家评审）
- **md_merge_record = 结案**（管家确认合并后的「实际合并记录」，留存活痕迹）

### 10.1 类比

| | md_match_scan | md_merge_record |
|---|---|---|
| 公安 | 嫌疑人名单（排查出的可疑对象） | 结案笔录（确认违法后怎么处理的） |
| 体检 | 异常项清单（哪几项指标可能有问题） | 治疗记录（确诊后用药、手术记录） |
| 电商 | 待处理工单（用户投诉，待客服判） | 处理记录（退款了/换货了，留操作日志） |

### 10.2 数据流关系

```
                    全库扫描 match-scan/run
                           ↓
                   ┌───────────────┐
                   │ md_match_scan │  ← 系统发现"这 3 条供应商疑似重复"
                   │ status=pending│
                   └───────┬───────┘
                           │ 管家评审：看字段对比 → 选 master → 确认合并
                           ↓
                   merge-requests/create
                           │
            ┌──────────────┴───────────────┐
            ▼                              ▼
   ┌──────────────────┐           ┌────────────────┐
   │ md_merge_record  │           │ md_match_scan  │
   │ status=reviewed  │           │ status=resolved│
   │ (合并事务记录)    │           │ (联动置已处理) │
   │ survivorship_log │           └────────────────┘
   │ (每字段来源留痕) │
   └──────────────────┘
```

**一条 scan 被处理 → 产生一条 merge_record + scan 联动 resolved。**

但反过来不成立：
- merge_record **不一定**来自 scan——管家在 duplicate-check（锚点查重）直接确认合并，只产生 merge_record，没 scan
- scan **不一定**变 merge_record——管家可能点「忽略」（scan→ignored），不合并

### 10.3 字段对比（体现职责差异）

| 字段维度 | md_match_scan | md_merge_record |
|---|---|---|
| **产生时机** | 系统扫描自动落库 | 管家确认合并时落库 |
| **记什么** | 发现了什么（cluster_key / 成员 / 最高分） | 怎么合并的（master 是谁 / 每字段取自哪方） |
| **master_id** | ❌ 没有（管家评审时才选） | ✅ 有（已确认主记录） |
| **survivorship_log** | ❌ 没有（还没合并，谈不上存活） | ✅ 有（逐字段 from master/victim + value） |
| **cluster_hash** | ✅ 有（防重复扫描产垃圾） | ❌ 没有（每次合并都是独立事务） |
| **status** | pending → resolved / ignored | pending → reviewed / rejected → unmerged |
| **状态语义** | 评审结论（待处理 / 已合并 / 已忽略） | 合并事务状态（待审 / 已合并 / 已驳回 / 已还原） |

### 10.4 为什么不合并成一张表

1. **去重逻辑冲突**：scan 靠 cluster_hash 去重（相同成员集合不重复入库）；merge_record 是事务记录，每次合并都该独立留痕（不能去重）。
2. **字段语义冲突**：scan 没有 master_id（管家还没选）；merge_record 必须有 master_id（已确认）。强行合并会有大量字段对其中一种状态是 NULL。
3. **生命周期不同**：scan 是短命的（评审完就 resolved/ignored，历史价值低）；merge_record 是长寿命的（合并后永久留痕，支撑 unmerge 还原、审计追溯）。
4. **产生方式不同**：scan 是系统批量扫描产生（一次扫描可能几十上百条）；merge_record 是管家逐条确认产生（一次一条）。

职责分离——scan 是「发现」，merge_record 是「执行」。

### 10.5 具体例子

场景：系统扫描发现 credit_code=C1 对应 3 条供应商记录。

```
1. 扫描落库
   md_match_scan 插一条：
     cluster_key="credit_code:C1", member_ids=[101,102,103],
     max_score=97, status=pending, cluster_hash="a1b2..."

2. 管家在工作台评审，选 id=101 作 master，确认合并
   md_merge_record 插一条（合并事务载体）：
     master_id=101, member_ids=[101,102,103], status=reviewed,
     survivorship_log={
       fields: [
         {field:"name", from:"master", value:"华东钢铁"},
         {field:"tax_no", from:"victim", value:"T1"}  ← master 空补 victim
       ],
       reparented: {cm_bank_account:[201,202,203]}  ← 银行账户改挂
     }

   md_match_scan 那条联动：
     status: pending → resolved, resolved_by=管家id, resolved_at=now()

3. 半年后管家发现合并错了，unmerge
   md_merge_record：status=reviewed → unmerged（明细指回、xref 恢复）
   md_match_scan：不变（仍 resolved，它只记"曾被处理过"）
```

整个过程中，**scan 只在评审前有用**（提醒管家"这里疑似有重复"），合并完就成历史；**merge_record 是合并的真凭据**，后续 unmerge、审计、追溯全靠它。

## 十一、已知缺口（后续增强）

1. **模糊簇键**：当前分块是精确等值（credit_code 必须完全相等）。`soundex`（音近）/前缀分块未实现——"华东钢铁" vs "华栋钢铁" 不会同桶。补需要 PG `fuzzystrmatch` 扩展。

2. **大桶降级**：某簇键（如 name="张三"）几千条时，500 截断会丢数据。M4 计划降级到次簇键再分桶。

3. **去重粒度**：当前按 member_ids 完全相等去重。数据变化（A-B-C → A-B-C-D）会重新入库。子集/超集合并留后续。

4. **ML 匹配**：当前只有 Exact + EditDistance。大规模高噪声场景的监督学习匹配未实现。
