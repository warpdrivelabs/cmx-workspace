0先看懂全景：基座、手，和四层挂件

所有 AI 助手（True Mate、Claude Code、ZCode 都一样）都可以拆开看：一个基座 + 一双手 + 四层挂件 + 若干礼盒。

图 0-1　整体架构：主对话派活，挂件供装备，工具动手，基座思考；工具地基里那枚蓝色的"远程工具"，就是能力层连接器（MCP）接进来的手；右侧插件礼盒横跨挂件与工具两层——它是打包格式，不是第九种能力（第 5 章）

地基：工具（Tool）——模型的手

大模型本体只会"想"和"说"，动不了手。让它干真活，靠的是工具调用机制：模型说"我要用某某工具、参数是这些"，助手应用替它执行，把结果喂回来，模型接着想。这一圈叫 function calling，是全行业通用的底层机制——后面九大概念里所有"会什么"，最后都落到这双手上。

  • 内置工具：应用出厂自带——读写文件、执行命令、搜索网页、派出任务等。
  • 自定义工具：把一段本地代码（函数 + 参数说明 + 执行逻辑）注册成工具，模型即可像内置工具一样调用——不需要起服务，是最轻的扩能力方式。opencode 的插件正是这么注册工具的；学术界的 OctoTools 更是把"把工具封装成标准卡片、即插即用"做成了整个框架的核心理念。
  • 远程工具：外部系统提供的工具，经 MCP 协议接入（第 6 章连接器）——查数据库、发消息、下单都属此类。

经验数据：Anthropic 多智能体工程报告的分析发现，任务效果差异有八成能被"token 花了多少"解释，工具调用次数则是另外两个关键因素之一——模型聪明之外，手多不多、用得勤不勤，直接决定活干成什么样。

引擎：Agent 循环——基座和手怎么配合

基座和工具是怎么协作干活的？靠的是 Agent 循环：获取上下文 → 执行操作 → 验证结果，三步在整个任务里不断交替——比如修 Bug 就是"读代码 → 改代码 → 跑测试 → 验证"反复转，直到通过。循环里两个角色各司其职，业界的概括很精炼：模型负责思考，工具负责执行，而扩展组件层决定能力边界。你也是循环的一部分——随时可以打断、补充上下文、换方向。上下文快满时，系统自动做压缩（删旧的工具输出、总结旧对话）；这也解释了为什么记忆和技能必须做成独立文件与条目、而不是只留在聊天里——被压缩掉的对话内容不会留下来，写得出来的才留得下（见第 4、7 章）。

四层挂件与一个礼盒

打个比方：大模型是刚入职的实习生——脑子聪明，但不了解你、没工牌、没工具、不认识公司里的系统。九大概念就是给他配的装备：

  • 角色助理 = 日常的通才助手　专家 = 工牌+人设剧本　专家团 = 拉起一个项目组　子智能体 = 幕后的外包小工
  • 能力技能 = 塞进工具箱的操作手册　连接器 = 连外部系统的电话线　插件 = 把若干装备打包成一箱的礼盒
  • 知识记忆 = 自动记录的笔记本
  • 触发命令 = 人按的快捷按钮　钩子 = 事件一响就动作的自动开关

总口诀：角色层决定"谁来干"，能力层决定"会什么"，知识层决定"记得啥"，触发层决定"何时动"，地基的工具决定"拿什么干"。下面每一章按"是什么 → 像什么 → 功能 → 与其它概念的关系"展开。

阅读提示：True Mate 首期提供前七个概念（1–7 章）；命令、钩子两个模块不在首期范围，第 8、9 章讲清概念本身与生态做法，并给出近期可用的替代方案。

1专家Expert / Persona Agent

一句话：专家 = 同一个模型大脑 + 一套固定人设（提示词）+ 指定的模型 + 挂载的技能/连接器。"召唤"专家就是开一个绑定了这套人设的新会话。

像什么

像给实习生发工牌和岗位剧本：人还是那个人（模型没变），但戴上"资深前端专家"的工牌、拿到这一岗的工具包（挂载的技能和连接器）、按这一岗的语气说话（人设提示词），干起活来就完全是那个"专家"了。

功能

  • 专家市场内置一批常用专家（资深前端专家、资深后端专家、数据分析师等），带简介与领域标签（编程 / 研发 / 数据…），可分类浏览挑选。
  • 召唤专家＝开一个绑定该人设的新会话，从第一句话起就带着专家的身份、语气与装备。
  • 支持自定义专家：不走表单，而是靠内置的"专家管理"技能对话式生成——你跟它聊"我想要一个懂白酒行业的分析师"，它把人设提示词写好、配好挂载，生成新专家。

同类实证：Octop（腾讯云开源的自托管助手平台）把同一机制做得更模板化——内置专家库启动时扫描加载、按场景切换，另配 16 型 MBTI 性格模板叠加定制提示词。"人设模板化"是专家体系的通行做法。

和其它概念的关系

专家是"面向你的入口"：你直接和它对话。它身上可以挂技能、连接器等装备；多个专家/角色组队协作就成了专家团（下一章）。

延伸一：挂的技能/连接器没装怎么办

规则是：人设照常生效，专家不会因此不能召唤；缺的装备只是"少了那只手"——影响的是这个专家的上限，不是它的存在。拆开看三层：

  • 人设（提示词）不依赖任何安装。"资深前端专家"的本体是写给模型的剧本——你是谁、擅长什么、怎么说话。这是"脑子里的事"，只要模型在，剧本就生效。哪怕一个技能、一个连接器都没装，召唤出来它依然是前端专家的口吻和专业底子。
  • 技能没装 = 手册没塞进工具箱。专家干这类活只能靠通用本事"裸做"：也能写也能答，但没有 SOP 兜着，做法可能不标准、步骤可能漏。对答问类任务影响小，对多步骤、有固定产出物的流程类任务影响明显——属于"做得好不好"的问题。
  • 连接器没装 = 电话线没拉。需要外部数据的活直接干不了——不是做得差，是没法做。设计决策：缺失的挂载明确提示而不是静默降级（fail-closed），用户始终知道"这个专家现在缺什么"。

延伸二：绑定之后能不能换专家

交互规则分两段：会话还没绑专家时，可以随时挑选专家；一旦会话绑定了专家/专家团，就不能原地换人——再选其他专家，系统会提示「切换将开启新对话」，确认后等于开一个新会话，当前对话原样保留。设计决策：人设是会话的"创建参数"，不是中途属性——技术上每回合重建提示词可以做到原地换人，但产品上不开这个口子，避免"半截对话里换了个人格"的混乱。

延伸三：召唤时的"随行清单"——专家能不能带动装备安装

专家挂着的技能、插件、连接器，安装/召唤专家时要不要一并装上？生态里的做法分三档：

  • 一键带装（Claude Code / ZCode 插件）：信任市场后安装一个包，包内技能、命令、钩子、MCP 全部就位。体验最好，但安全圈的批评很直接——这是"一次不透明的点击，同时激活了一堆会跑代码的东西"。
  • 只给清单不代装（Dify）：导入应用只提示缺哪些工具插件，要自己逐个去装；官方后来专门做了"Bundle 打包"来补这个麻烦，可见纯手动补装摩擦太大。
  • 完全不管（WorkBuddy / Trae）：装备缺失就裸跑，人设还在、能力打折，用户未必知道差在哪。

True Mate 采用"随行清单"设计，取三档之长：

  • 展示清单、一键带入：安装或召唤专家/专家团时，列出它携带的装备（技能×2、插件×1、连接器×1……），默认全选，确认即随行安装。
  • 分级对待：技能/插件/自定义工具是纯文件，随行即生效；连接器装了不等于连得上——密钥、OAuth 授权永远单独走一步，不随包分发（这是 Dify、Coze 用踩坑换来的共识）。
  • 装不进的进"待装配"清单：专家照常可用，用到缺失能力时明示（呼应延伸一的降级规则），而不是装包失败。
  • 卸载反向询问：卸专家时问一句要不要连带卸载随行装备——打包安装而不打包卸载，是同类生态被抱怨多年的坑。

2专家团Expert Team

一句话：专家团 = 一次召唤拉起一个分工明确的项目组：团长（主理人）拆解任务、成员并行作业、结果整合交付——把"多角色协作流程"做成一个可直接召唤的整体。

像什么

像叫了一次"装修全包服务"：你只对接项目经理（团长），他把活拆成设计、水电、瓦工、油漆，各工种并行开工，最后验收交付的是一个整体成果——你不需要挨个工种去聊。

功能

  • 专家团与专家同处一个市场，以内置的「交易分析团队」为例：13 个角色、5 个阶段——四维采集 → 多空辩论 → 交易决策 → 三方风险评估 → 报告，每个阶段由不同角色接棒。
  • 召唤专家团＝按流水线拉起多个角色协作，最终交付整合后的成果，而不是一堆各自为政的回答。
  • 支持自定义团队：定义团长提示词（拆解与编排逻辑）+ 成员名册（谁参与、各带什么装备）。

证据：多智能体协作值不值——Anthropic 工程报告

True Mate 团队形态的可行性，有业内最扎实的一份实证（Anthropic《我们如何构建多智能体研究系统》）：

  • 模式：主控（lead agent）分析任务、把计划存入外部记忆，并行派出 3–5 个子代理分头探索，子代理在独立上下文里翻材料、只把压缩后的要点回传，主控汇总后再决定是否加派人手——这套"主控-工人"（orchestrator-worker）模式让复杂研究的时间最多缩短 90%。
  • 收益：研究评测中，多智能体系统比单个顶级模型高出 90.2%。适合面广、可并行、信息量超出单窗口的任务（比如"列出某板块所有公司董事会成员"这类广度优先的活）。
  • 代价：多智能体的 token 消耗约为普通对话的 15 倍；不适合需要全员共享上下文、强依赖中间结果的活——报告明确指出编程类任务可真正并行的部分有限，收益打折。
  • 工程教训：给成员派单必须四要素齐全——目标、产出格式、可用工具指引、边界（与通用最佳实践的"目标 / 上下文 / 约束 / 完成标准"四要素任务输入不谋而合）；成员产出落文件、传引用，不做长对话转口播，避免层层转述的"传话游戏"失真。
  • 同类规划：Octop 的路线图把 AgentTeams（协调者自主编排多个 expert）列为核心方向——团队形态是自托管平台的共同进化方向。

对 True Mate 的含义：团队形态优先用于"调研、分析、评审"这类可拆可并行的任务（交易分析团队正是典型）；团长提示词必须写清派单四要素。

和其它概念的关系

专家团的成员就是专家/子智能体，装备来自技能与连接器，随行清单机制（第 1 章延伸三）对团队同样生效。团队消耗约为单专家的数倍，产品设计上明示消耗。

3子智能体Sub-agent

一句话：子智能体 = 主对话派出的幕后工人——在独立上下文里替主对话干活，干完只交回结果，不占主对话的"脑子"。

像什么

像你派出去的实习生：你在会议室里跟客户开会（主对话），他在隔壁查资料、跑腿、整理表格（子任务），干完敲门送进来一页摘要——会议室里始终干净。

功能

  • 子智能体不是挂在谁名下的"配置项"，而是按需派出的：主对话——日常的助理、召唤的专家、专家团的团长都一样——干活需要人手时，就从角色库挑一个拉起，在独立上下文里分头干，用完即收。
  • 内置角色库：研究员（搜网页、读文献、做总结）、资料员（收集整理、写报告）、程序员（写码调试）等。
  • 自定义子智能体按"名称、描述、图标 → 职责提示词、模型 → 工具/技能挂载 → 输出格式"定义。

规格参照：子智能体定义到什么粒度

  • Claude Code：一个 Markdown 文件 = 一个子智能体——头部声明名称、何时该用（描述）、可用工具范围、用哪个模型；正文就是它的系统提示词。主对话靠"描述"字段判断什么时候自动派活。
  • opencode：代理分主/从——主代理负责对话与编排，从代理独立执行幕后任务。
  • Anthropic 经验：子代理是"智能过滤器"——在独立上下文里翻遍材料，只回传压缩后的要点，主对话不被原始信息灌满（产出落文件、传引用的交接细节见第 2 章证据）。
  • Octop：走"双向编排"路线——出站把任务委派给 OpenCode、Claude Code、Codex 等外部编码代理（带权限门控），入站把自己暴露成 IDE 可调用的代理。子智能体的边界因此可以从内置角色外延到外部代理。

独立上下文 + 压缩回传是子智能体与普通会话的本质区别：它不是"另一个聊天窗口"，而是主对话的外挂双手。

和技能的分工（业界辨析）：技能是可复用的知识与流程，核心价值是复用；子智能体是独立执行单元，核心价值是上下文隔离。两者可以组合——派子代理干活时，让它预载相应的技能手册。

专家 vs 子智能体（最容易混的一对）

专家子智能体
面向谁面向你——你直接和它对话面向主对话——幕后接派活
存在形态市场分发的人格化角色按需派出的幕后工人，不占会话列表
典型任务咨询、写作、分析等当面协作搜集、检索、批量处理等幕后作业
先澄清一个名词：True Mate 里的「助理」是通用工作助理——类似 LobsterAI 那样的办公通才，日常什么活都接，是产品的主对话；「专家」是市场里按需召唤的专门人设。子智能体跟两者都不是"隶属"关系：谁在主对话里干活，谁就能派子智能体当幕后帮手。

4记忆Memory

一句话：记忆 = 助手跨会话记住你的机制——一条条可看、可改、可删的记录（内容 + 来源 + 时间），让助手换个对话依然认识你。

像什么

像给实习生配一本"关于你的笔记本"：每次共事他悄悄记两条（"客户喜欢简洁的汇报""每周五交周报"），下次接活先翻一遍本子，不用你从头交代。

功能

  • 提供全局记忆管理：总开关（一键关闭则不做任何记忆）+ 记忆条目列表（每条含内容、来源、时间）+ 手动添加/编辑/删除/清空。
  • 来源分两类：来自对话（助手从聊天里自动总结）与手动添加（你直接写入）。
  • 记忆默认全局生效：不管日常跟助理聊，还是召唤专家干活，都带着这些条目，不用从头交代。

延伸：记忆的四种类型（认知科学口径）

类型是什么例子
工作记忆当前对话的上下文窗口本次会话里说过的话
情景记忆经历过的事件与交互记录"上周让我改过一版方案"
语义记忆提炼出的长期事实与偏好"用户喜欢简洁直接的回答"
程序记忆做事的流程与方法就是技能与人设（第 1、7 章），不归记忆模块管

另一种分法按记忆从哪来：指令型——人写下来的规则（规范、约定、安全红线），写进项目规则文件；学习型——助手从用户纠正、偏好、失败经验里自己积累的。两类必须严格分开，免得琐碎经验污染了正经规则。True Mate 的记忆条目标注"来自对话 / 手动添加"，正是这个区分的产品化。

同类产品怎么做

  • ChatGPT：显式"保存的记忆" + 后台自动从历史聊天捡细节——覆盖广，但用户觉得有时不可预测。
  • Claude：对历史生成记忆摘要、用时显式调取——克制、可控。
  • MemGPT / Letta（开源路线）：把上下文当"虚拟内存"，agent 自己分层挪数据、编辑自己的记忆——面向开发者。
  • WorkBuddy / ZCode：条目式 + 来源标注。
  • Octop：层级记忆召回 + 全文检索，记忆随工作区整体迁移。

True Mate 定位：管好情景 + 语义两类（条目可视可改可删 + 总开关），程序记忆交给技能体系，不重复造；作用域上先做全局一层（助理与专家共用），团队共享规则将来走项目级配置，不在个人记忆里混。

和其它概念的关系

Claude Code / ZCode 里没有这种"条目式记忆"，对应物是项目级的 AGENTS.md / CLAUDE.md 规则文件 + 自动记忆库（文件形态）。True Mate 采用更产品化的做法：条目可视、可改、可删，普通用户不用碰文件。

5插件Plugin

一句话：插件 = 扩展包。它不是第九种能力，而是一种打包格式：一个插件包可以把技能、命令、钩子、自定义工具、连接器（MCP）、子智能体打成一个整体——装一个包，整套装备一次到位。

像什么

像成套工具箱。技能、连接器、命令这些是单件工具，可以一件一件单独买；插件是按工作主题配好的整套箱子——"企业尽调"一箱，打开来操作手册（技能）、电话线（连接器）、快捷按钮（命令）、帮手（子智能体）全齐了，互相配好、开箱即用。

功能

  • 插件是 True Mate 的标准分发格式：一个包 = 一份清单（manifest：包名、版本、包含物）+ 若干内容，内容是六类的任意组合：技能、命令、钩子、自定义工具、连接器（MCP 服务器）、子智能体。
  • 提供插件市场：官方插件 / 第三方插件 / 本地安装，支持搜索、安装、升级；同类还有命令行安装（Octop 的 octop plugin）与"内置预置、按需启用"两种分发形态。
  • 一次安装全部就位：包里的技能、命令、子智能体、连接器同时可用，无需逐个配置；一次卸载全部移除；每个插件有总开关，禁用即包内所有内容一起停。
  • 包内命名空间隔离：插件自带的命令、技能统一挂包名前缀——多个插件之间不撞名、不互相覆盖。
  • 装好之后，包里的每样东西与"散装"的没有区别——技能照样可全局使用、可挂载到专家，工具进工具箱，连接器照样出现在连接器列表。插件只解决"怎么分发"，不改变能力本身的用法。

内容物详解：自定义工具（Tools）

六类内容物里最容易被忽略的是"工具"——它填补了技能（教脑、不执行代码）和连接器（重接入、要授权）之间的空档：

  • 自定义工具 = 一段本地代码（描述 + 参数说明 + 执行逻辑），注册后模型就能直接调用，不需要起 MCP 服务，是轻量扩能力的首选。
  • 生态实证：opencode 的插件在代码里直接注册工具（官方插件接口就有工具注册口，含执行前后拦截钩子）；OctoTools 把"工具卡片标准化封装、即插即用"作为框架核心；Coze 对插件的官方定义就是"包含多个工具的工具集"；Dify 的四大插件类型之一就是工具提供方。
  • 对照：Claude Code 的插件没有裸工具口子，工具必须经包内 MCP 服务器间接提供。True Mate 取中间路线：自定义工具作为一等内容物，轻需求用它，重需求上 MCP。

容器与内容（插件与其它概念的根本关系）

插件（容器）技能 / 命令 / 钩子 / 工具 / 连接器 / 子智能体（内容）
是什么打包分发格式能力本身
类比整套工具箱箱里的单件工具
获取市场一键装整包可单装，也常随包而来
开关粒度整包启停、整包升级逐个挂载 / 启停

为什么要打包？（散件也能单装，还要插件干什么）

  • 成套设计：一个主题下的装备互相配合，作者已经调好（尽调的技能引用尽调的连接器），照单全收就不会装一半。
  • 一键到位：不用照着推荐清单一件件找、一件件配。
  • 统一治理：版本、更新、启停都按包管理——升级一个插件，箱内所有装备同步升级。
⚠️ 信任与治理：一键带装意味着一次点击同时激活技能、工具、钩子、连接器——安全圈对这种"一次不透明的同意"批评很尖锐。True Mate 对策：① 安装时列出包内全部内容物，装什么一目了然；② 钩子类内容默认禁用、手动开启；③ 企业/团队分发支持包白名单 + 随行连接器默认禁用。另注：也有产品把"插件"理解为应用本体的功能扩展（给内置浏览器装翻译之类）——那是同名不同义，见第 10 章对照表。

6连接器（MCP）Connector / Model Context Protocol

一句话：连接器 = MCP 生态里的"外部系统接入点"。装一个连接器，助手就能读写一个外部系统——飞书消息、GitHub issue、数据库、网页搜索……能力由对方服务器提供。

像什么

像给助手拉电话线：助手脑子再好，也够不着你公司的数据库。连接器就是那根线——接通之后，助手能"打电话"过去查询、写入、下单。MCP 则是统一的话务标准：所有系统只要按这个标准装个"总机"（MCP Server），任何支持 MCP 的助手都能接入。

功能

  • 提供连接器市场，分三块：官方、第三方、连接器工坊（自建），装一个连接器 = 接通一个外部系统，可用的动作（工具）由对方提供。
  • 连接器授权独立于安装：装了 ≠ 连得上，密钥 / OAuth 授权永远单独一步（呼应第 1 章随行清单的分级带装）。

协议底盘：MCP 的三个原语

一个 MCP 服务器能对外提供三类东西：

  • 工具（Tools）：能执行的动作——查询、写入、下单，连接器的主体。
  • 资源（Resources）：只读的数据上下文——文档、记录，供模型"翻阅"。
  • 提示（Prompts）：预置的提示词模板——正好是第 8 章"命令"的素材：MCP 服务器自带的提示模板，常被助手直接挂成斜杠命令。

行业地位

MCP 由 Anthropic 于 2024 年 11 月发布；2025 年 3 月 OpenAI 正式采纳（Agents SDK、ChatGPT 桌面端），随后 Google DeepMind 跟进，一年内成为行业事实标准——主流 AI 助手的外部工具接入全部走 MCP。学会一个，处处能用。

⚠️ 安全：装 ≠ 可信。MCP 生态已出现"工具投毒"攻击——在工具描述里藏用户看不见、模型看得见的恶意指令；还有服务器先装好、后变脸（rug pull）。True Mate 对策：连接器分区与来源审核、工具描述对用户可见、敏感动作二次确认、授权独立于安装。

7技能Skill

一句话：技能 = 一个打包的"操作手册"（SKILL.md 包）：里面写着某类任务该怎么做、分几步、注意什么。模型遇到对应场景时自己翻开手册照着做。

像什么

像给新员工发的 SOP 手册夹：《周报怎么写》《PO 审批流程》《客户投诉处理话术》。员工（模型）本身会写字会说话，但有了手册，做这类事就有章法、不掉链子。技能教的是"怎么做"（脑的方法），不是"够得着什么"（那是连接器的事）。

功能

  • 提供技能市场，分三块：推荐 / SkillHub（社区技能库）/ 套件（成组打包的技能集）。
  • 装好后全局可用，也可细粒度挂载到专家。
  • 技能还是 True Mate 的"生成器"机制：前文说的自定义专家，就是靠内置的"专家管理"技能对话式生成的——技能不光教模型做事，还能教它"造东西"。
  • 沉淀的判断标准很简单：某段提示词或流程被反复使用，它就该被沉淀成一个技能——技能是个人与团队经验的资产化形态。

技能还有进阶来源：从对话里自动蒸馏——Octop 把 Self-evolution（对话自动蒸馏成技能）、技能录制回放列入路线图，方向是"你带着干过一遍，助手自己就会了"。

解剖一个技能：SKILL.md 包与渐进披露

  • 结构：一个技能 = 一个文件夹——一份 SKILL.md（头部两行元数据：名字 + 一句话说明；正文 = 怎么做）+ 可选的脚本、模板、参考文件。
  • 渐进披露：平时只有"名字 + 一句话"常驻上下文；模型判断当前任务相关时才翻开正文；正文里链接的脚本/附件要用时才加载——三层按需加载，不撑爆上下文。这是技能设计被业界广泛认可的关键（对比：把所有说明一股脑塞进系统提示词）。
  • 技能可带脚本：手册里可以直接附带可执行的小工具（模型决定调用、环境负责执行），让"教方法"和"给家伙"合在一个包里。

各扩展的上下文成本光谱（渐进披露为什么重要）：规则文件与 MCP 服务器几乎每次请求都占上下文，成本最高；技能靠渐进披露只在相关时加载，成本低；子智能体隔离在独立上下文，主对话零负担；钩子是纯程序，不占模型上下文。什么挂"常驻"、什么挂"按需"，是扩展设计的第一课。

技能 vs 自定义工具 vs 连接器（一张表分清）

技能自定义工具连接器（MCP）
本质写给模型看的方法本地代码的手外部系统的手
执行者模型照着手册做本地执行外部系统执行
重量最轻（纯文本）轻（一段代码）重（服务 + 授权）
典型例子"写周报的 SOP""把表格转 PDF 的小函数"连上飞书 / 数据库
社区有一派观点认为"渐进披露的技能（手册+脚本）可能取代一部分 MCP"——轻需求用手册就够，重需求才上协议。True Mate 两者都保留，让作者按重量选。

8命令Command / Slash Command

一句话：命令 = 用户手动触发的"快捷按钮"——敲一个 /名字（可带参数），立刻执行一套预定义的动作或提示词，省得每次打一大段话。

像什么

像给常用操作钉在墙上的开关：一按就执行整段预编排好的流程。本质是参数化的提示词模板——模板里挖好坑，用时填坑。

功能（概念本身）

  • 斜杠触发：/名字 直接执行，参数跟在后面（如 /周报 123 high）。
  • 参数化：模板里用占位符承接输入——全量参数 + 位置参数（第 1 个、第 2 个……），一条模板服务一类任务。
  • 可厚可薄：一条命令可以只是一句快捷短语，也可以等于一条预制的标准作业流程（绑定可用工具、指定执行步骤）。

生态参照

  • Claude Code：自定义命令 = 一个 Markdown 文件（.claude/commands/），社区已沉淀上百个生产级命令集；MCP 服务器的 prompts 原语也会被宿主直接挂成斜杠命令——命令与连接器在这里打通（第 6 章）。
  • ZCode：/技能名 触发，命令与技能共用一套触发面。
True Mate 首期不设独立命令模块，近期用三个近亲方案顶住：① 快捷短语——把常用长提示词存成短语，用时一键插入；② 建议标签——一组常用任务的快捷提示（"帮我写代码 / 帮我写周报 / 翻译"等），本质是"内置命令"；③ 「模式」切换——一键切换会话行为模式，属"按钮换行为"一族；它的成熟形态是同类产品的"计划模式"：切过去后助手只做只读分析、先出方案再动手，一个模式位顶半套命令体系。

9钩子Hook

一句话：钩子 = 事件一响就自动执行的开关——在助手生命周期的固定点位（工具调用前、调用后、会话开始、提交提示词时……）自动运行预定动作，不用人守着。

像什么

像流水线上的传感器 + 机械臂：货（事件）一到某个工位，传感器一触发，机械臂自动动作——分拣、贴标、拦下次品。人不用盯在旁边。

功能（概念本身）

  • 事件位：常用点位包括"工具执行前 / 执行后""用户提交提示词时""会话开始 / 结束""子代理结束"等，覆盖助手一举一动的生命周期。
  • 确定性控制：钩子是普通程序代码，说一不二——可以在工具执行前直接拦截（例如禁止写生产库）、执行后自动格式化、会话结束时自动归档。这与提示词里写"请不要 XXX"（软约束，模型可能不听）有本质区别。

生态参照

Claude Code 的钩子体系覆盖十余个生命周期事件位，工具事件在主对话和子代理里同等触发；企业用法集中在三类：合规拦截、自动格式化、事件通知。Octop 同样把工具审批与 shell 命令护栏做成规则文件（tool_guard），与钩子同一思想。

True Mate 首期不设钩子模块。近亲方案是「定时任务」——按时间表自动执行任务，属于钩子家族里"时间触发"这一支；"事件触发"这一支首期不做。通用最佳实践也把"稳定流程进一步自动化（定时跑、事件触发跑）"列为助手成熟度进阶的一步——定时任务正是它的首期形态。设计上留口子：内核的权限守卫（危险动作默认拒绝、fail-closed）本身按钩子思想实现，后续开放"工具调用前 / 后"两个事件位即可平滑演进，无需重构。
