CMX 本体平台（cmx-ontology :8097）

简要说明 1/4本体如何设计

用六类元模型元素描述企业的"对象—关系"世界，把建模、数据、动作、安全分层落到一套可发布的不可变版本体系上。对标 Palantir Foundry 的 Ontology 概念。

一、六类元模型：本体的"词法表"

整个平台只围绕六类元素建模，全部以 apiName 为跨版本稳定标识：

元素回答的问题关键设计
ObjectType 对象类型业务世界里"有什么东西"（客户、订单、凭证…）属性列表（16 种基础类型）+ 主键 + 标题属性 + DAM 三级分类（域▸应用▸模块）+ 可挂业务单据 docType
LinkType 关系类型东西之间"什么关系"基数（1:1 / 1:N / N:M）+ 双向角色名（places / placedBy）+ 落库方式（外键/中间表）
Interface 接口横切能力契约（"可定位物""可审批物"）只声明要求的属性名集合，对象类型 implements 它，可继承
SharedProperty 共享属性全局标准字段（币种、金额…）一处定义处处引用，带语义类型
ActionType 动作类型对对象"能做什么操作"参数 + FEEL 校验 + 五种编辑原子（建/改/删对象、加/删关系）+ 副作用（起流程/算报表/webhook）
Function 函数"怎么算"（派生属性、判定逻辑）FEEL 表达式为体，输入可为标量/对象/对象集

二、五条核心设计原则

  • apiName 是唯一稳定锚——命名白名单（字母/下划线开头）从建模层一路贯穿到 SQL 表名拼接，改显示名不改 apiName，版本间不漂移。
  • 生命周期三态——experimental（试验）→ active（激活）→ deprecated（废弃）。新建默认试验态；发布固化进版本快照。
  • DAM 分域管理——每个对象类型归入 域▸应用▸模块 三级分类，前端图组件按此分域折叠，大图不瘫。
  • 定义与数据分离——六类定义存 om_* 表（元数据），实例数据按类型惰性物化为 oo_<type> 表，互不锁死。
  • 发布即快照——POST /publish 把全量定义打成带内容指纹（xxhash64）的不可变版本，版本号只增不改，可随时回看任意历史版本的本体全貌。

四、数据怎么存（PostgreSQL）

层表说明
定义层om_object_type / om_link_type / om_interface / om_shared_property / om_action_type / om_function六类元素各一张，JSONB 存属性/参数等复杂结构
版本层om_version发布快照（不可变），带内容指纹 rev
运行层oe_action_log / oe_outbox / om_policy / om_source_mapping / oo_quarantine动作审计 / 副作用发件箱 / 安全策略 / 源映射 / 隔离区
对象层oo_<type>（惰性建）+ ol_edge每类型一张实例表（首次写入时创建）；所有关系共用一张超边表，双向索引

硬纪律：不建外键（用索引替代），表内不带租户列（库即租户边界，db-per-tenant）。

五、四个核心机制（每条两句话）

① 对象集代数 → 单条 SQL

查询用 7 种算子（Base/Filter/SearchAround/Union/Intersect/Subtract/Static）组成代数树，编译成一条 SQL 执行——三跳关系查询只往返数据库一次，天然防注入（值全参数绑定）。

② FEEL 表达式引擎

内置标准 FEEL 子集解释器（for/some/every、区间、28 个内置函数），用于动作提交校验与函数求值，判定一律 fail-closed（求值失败=不通过）。

③ 动作 = 事务 + 发件箱

一次动作里的全部对象编辑、审计日志、副作用登记在同一事务提交（全成或全败）；副作用（起审批流/算报表/webhook）由 dispatcher 事后从发件箱可靠投递。

④ 动态安全（行级+列级）

策略的行级过滤谓词直接 AND 进对象集编译管道（复用同一编译器），列级按安全标记打码 ***——权限即查询的一部分，不是事后过滤。
