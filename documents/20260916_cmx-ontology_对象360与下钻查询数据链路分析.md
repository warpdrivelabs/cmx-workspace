## 0. 太长不看（一分钟版）

1. **接口只有三个核心读口**：`POST /onto/v1/object-sets/load`（查对象列表/单对象，360 属性卡用它）、`POST /onto/v1/object-sets/aggregate`（分组统计）、`POST /onto/v1/objects/links`（下钻查关系对象，360 关系区用它；20260919 起改为 POST + body 传参，老 `GET /objects/{type}/{pk}/links/{link}` 已废弃）。**所有接口必须带 `?ontology=<本体 apiName>`**（缺省 400 `ONTOLOGY_REQUIRED`）。
2. **查询不是拼 SQL，是传一棵"对象集代数树"**（JSON DSL，叫 `ObjectSet`），后端编译器把它翻译成**一条**参数化 PostgreSQL SQL。这套设计对标 Palantir Foundry 的 Object Set Service。
3. **~~只能查 jsonb 物化表~~（20260918 起过时）**：物化路径仍是 `oo_<类型>` jsonb 表；但**虚拟绑定类型已可免物化直查源库**——读路径分派器（`backend_dispatcher.rs`）按对象类型的绑定选后端：simple 树（base/filter/static）直接下推源库编译成普通宽表 SQL（`SELECT cust_id AS pk … FROM src_vcust WHERE …`），复杂树桥接为 pk 集合。数据源经 `om_data_source` 注册表接入（引用 toml 池或独立连接懒注册）。详见 §6 末尾。
4. **以后从业务库/数据平台取数：选"传查询描述，由数据侧生成查询"（描述下推），不要传拼好的 SQL**。这正是 Palantir（Object Set + Virtual Tables 查询下推）、Timbr、Trino/Starburst、Dremio 的共同做法；**这条路线的第一步已在仓内落地**（虚拟直查即"描述下推"的 PG 源特例：`ObjectSet` 子集编译下推，跨源组合桥接衔接），拼好的 SQL 只适合作为**管理态的兜底工具**（现有 Funnel 的 `source_query` 就是这个定位）。

## 1. 先搞懂三个词（打比方）

| 词 | 大白话 | 在本平台的对应物 |
| --- | --- | --- |
| **对象（Object）** | 一张"客户卡片"：主键、名字、一堆属性 | `oo_Customer` 表里的一行，属性全塞在 `props` 这个 JSON 口袋里 |
| **对象 360** | 点开一张卡片，看到它的全部：属性 + 所有关联对象 + 能对它做的动作 | 前端页面 `portal.onto.workshop`（客户 360 工作台），页面文件在 cmx-container 仓，接口在本仓 |
| **下钻（钻取）** | 顺着关系"顺藤摸瓜"：选一个客户 → 摸出他所有的订单 → 再摸出订单里的商品 | DSL 里的 `SearchAround` 操作（沿着关系类型从一批对象走到另一批对象） |

一个重要澄清：**仓里没有任何接口叫"360"或"下钻"**。前端 360 页面和对象浏览器（`portal.onto.explorer`）背后调的就是上面那三个读接口。"下钻"在代码和文档里的正式名字是 **Search-Around（关系钻取）**。

## 2. 数据存在哪：两张表看懂存储模型

要看懂 SQL，先花一分钟看懂数据长什么样。每个对象类型一张表，长这样（`oo_Customer`）：

| 列 | 类型 | 装什么 |
| --- | --- | --- |
| `pk` | TEXT 主键 | 卡片编号，如 `C001` |
| `title` | TEXT | 卡片名字，如 `华东钢铁集团` |
| `props` | **JSONB** | **所有属性塞一个 JSON 口袋**：`{"region":"华东","level":"A","amount":1200}` |
| `created_at / updated_at` | TIMESTAMPTZ | 时间戳 |

为什么用 JSON 口袋装属性？——加一个属性**不用改表结构**（零 DDL），代价是查属性要"从口袋里掏"：SQL 里写 `props ->> 'region'`（把 region 这个格子掏出来当文本）。

关系（谁和谁有联系）有两种存法：

1. **边表 `ol_edge`**（默认）：一行 = 一条关系，`(link 关系名, a_pk, b_pk, props 边属性)`。所有"通用关系"挤在这一张表里。
2. **背书（Backing）模式**：建模时声明关系其实"躺在"已有数据上，分三种——
   - `ForeignKey`：某对象的某属性本身就是对方的主键（如订单的 `customerId` 指向客户），不用另存边；
   - `JoinTable`：躺在一张现成的连接表上（左列指 A、右列指 B）；
   - `Intermediary`：躺在一张"中间对象表"上（中间对象两个属性分别存两端主键）。

这个设计直接决定了后面 SQL 的长相：**查属性 = 掏 JSON 口袋，查关系 = 按背书方式选 JOIN 姿势**。

## 3. 接口清单：参数与含义

路由真源在 `crates/cmx-onto-app/src/lib.rs`（挂 `/onto` 与 `/onto/v1` 双前缀，独立服务 :8097 直连；开发环境带 `X-API-Key: cmx_sk_dev_...` 免登录；**全部接口必带 `?ontology=<本体 apiName>`**）。

### 3.1 `POST /onto/v1/object-sets/load` —— 万能查询口（360 属性卡 / 列表 / 单对象详情都靠它）

请求体（`object_handlers.rs` 的 `LoadReq`）：

```jsonc
{
  "objectSet": { ... },     // ★核心：对象集代数树（下节详讲），描述"要哪批对象"
  "limit": 100,             // 可选，每页条数，缺省 100，服务端强制夹在 1~1000
  "offset": 0,              // 可选，翻页偏移
  "subjects": ["role:east"],// 可选，声明主体（角色/用户），读侧权限硬门用；
                            //      jwt 模式下以令牌为准，此处声明会被覆盖
  "view": "myScene",        // 可选（20260920），场景可见性口径：值场景 apiName 或 auto:<域>；
                            //      传了则终端类型必须 ∈ 场景成员，否则 409
  "include": "all"          // 可选，类型状态分层：all 或 experimental,deprecated 逗号组合；
                            //      非 active 类型缺省按 404 隐藏
}
```

响应 `data`（`ObjectPage`）：`{ objectType, rows: [{pk, title, properties}], limit, offset, hasMore }`。

**单对象详情没有专门接口**——360 页面取一个客户就是传 `{"op":"static","objectType":"Customer","primaryKeys":["C001"]}`。

### 3.2 `POST /onto/object-sets/aggregate` —— 分组统计口（浏览器分组、360 统计卡）

请求体（`AggregateReq`）：

```jsonc
{
  "objectSet": { ... },       // 同上，先圈定一批对象
  "aggregation": {            // 对这批对象做哪种统计，kind 三选一：
    "kind": "groupSum",       //   count      → 数个数
    "groupBy": "region",      //   groupCount → 按某属性分组数个数（只需 property）
    "sum": "amount"           //   groupSum   → 按某属性分组，对另一数值属性求和
  },
  "subjects": []              // 可选，同 3.1
}
```

响应：`{"count": 42}` 或 `{"groups": [{"group":"华东","count":18}, ...]}`。
（目前只有这三种聚合，没有 avg/min/max——这是已知的对标缺口。）

### 3.3 `POST /onto/v1/objects/links` —— 下钻便捷口（360 关系区；20260919 去路径化）

请求体（`LinksBody`）：`{ "objectType": "Customer", "pk": "C001", "link": "customerPlacesOrder", "view?": "…", "include?": "…" }`。

例如 `link:"customerPlacesOrder"` + `pk:"C001"` = "C001 这个客户的所有订单"。方向自动判断：源对象在关系 A 端就正向走（到 B 端），在 B 端就反向走（到 A 端）；关系两端都不是这个类型 → 404。返回结构与 3.1 相同（一页对象）。此端点额外做**场景成员校验**（对象与 link 都必须 ∈ 场景，见 `view`）。

**它只是个语法糖**：内部拼成 `SearchAround(Static([pk]), link, 方向)` 再走 3.1 的同一条编译链路。前端关系区点一下"查看订单"，实际就是调它。

### 3.4 周边接口（360 页面还会用到；20260919 全部去路径化后）

| 接口 | 用途 |
| --- | --- |
| `GET /onto/v1/object-types?q=&dam=&page=&size=` | 左栏对象类型目录（关键词/域过滤 + 分页；支持 `?view=` 场景口径） |
| `POST /onto/v1/action-types/execute`（apiName 入 body；另有 `/dry-run`、`/execute-batch`、`/check-permission`） | 360 上的"执行动作"按钮（发起流程、改数据、调函数） |
| `POST /onto/v1/secure/object-sets/load` | 安全版查询（强制走策略校验的旁路端点） |
| `POST /onto/v1/data-sources/create|update|delete|probe`、`GET /data-sources`、`GET /data-sources/schema` | 数据源注册表管理（§6 末尾虚拟直查的源头接入） |
| `POST /onto/v1/object-types/datasource/bind` / `unbind` | 对象类型 ↔ 数据源绑定/解绑（绑定即建 `om_source_mapping`） |
| 写口：`POST /onto/v1/objects/save`（body 含 objectType）、`/save-batch`、`/modify`、`/remove`；`/links/save`、`/links/remove` | 动作回写、数据维护（禁 DELETE，一律 POST + 固定段） |

**每次读都会先过一道"权限硬门"（PEP，`pep.rs`）**，发生在查库之前：

1. 命中 `deny` 策略 → 直接 403；
2. 受控类型但没授权 → 403；
3. 有授权且策略带行级约束（`row_filter`）→ **把约束作为一层 `Filter` 追加进你的对象集树**（你只能看到允许的行）；
4. 策略带脱敏标记 → 查回来之后，命中的属性列**直接从响应里删掉**（不是打码，是不出现）。

也就是说：权限不是事后过滤，而是**参与生成查询**——这点对后面第 6 节的架构讨论很重要。

## 4. 查询 DSL：`objectSet` 怎么写（下钻的正式姿势）

`objectSet` 是一棵可以无限嵌套的树（定义在 `crates/cmx-onto-model/src/objectset.rs`），`op` 是操作类型：

| op | 含义 | 字段 |
| --- | --- | --- |
| `base` | 某类型的全部对象 | `objectType` |
| `static` | 指定主键的那几个对象 | `objectType`, `primaryKeys[]` |
| `filter` | 对上游结果过滤 | `source`（子集）, `predicate`（条件树） |
| `searchAround` | ★下钻：沿关系走到相关对象 | `source`, `link`（关系名）, `direction`（forward/reverse，缺省 forward） |
| `union / intersect / subtract` | 两集合并/交/差（按 pk） | `left`, `right`（两侧必须是同一对象类型） |

`predicate`（条件树，`kind` 打头）支持：`eq / ne / gt / ge / lt / le / in / contains / isNull / and / or / not`，条件里只有**属性名 + 值**，**不接受任何裸 SQL**（这是防注入的第一道墙）。

### 例子：一个典型的"下钻查询"

> 华东区的客户 → 他们下的订单 → 其中金额 ≥ 1000 的订单

```json
{
  "objectSet": {
    "op": "filter",
    "source": {
      "op": "searchAround",
      "source": {
        "op": "filter",
        "source": { "op": "base", "objectType": "Customer" },
        "predicate": { "kind": "eq", "property": "region", "value": "华东" }
      },
      "link": "customerPlacesOrder",
      "direction": "forward"
    },
    "predicate": { "kind": "ge", "property": "amount", "value": 1000 }
  },
  "limit": 50
}
```

读法：从里往外——`base` 拿全部客户 → 第一层 `filter` 筛华东 → `searchAround` 顺 `customerPlacesOrder` 关系摸到订单 → 外层 `filter` 筛金额。**无论嵌套多少层，最终只发一条 SQL**（不存在 N+1 逐层查库）。

## 5. SQL 是怎么生成的、长什么样

### 5.1 生成流水线（四步）

代码：`crates/cmx-onto-store-pg/src/compile.rs`（编译器）+ `object_store.rs` 的 `load()`/`aggregate()`（执行）。

```
你的 JSON 请求
   │ ① 反序列化成 ObjectSet 树（类型校验在这里发生）
   ▼
权限硬门 PEP：row_filter 折入 → 树多包一层 Filter
   │ ②（20260918 起）backend_dispatcher 分派：查 om_source_mapping 绑定——
   │    物化类型 → 原样进 Compiler（下述流程）；虚拟类型 → PgDirect 下推源库（§6.1）
   │    物化路径内 resolve_links：把树里出现的所有关系名，先查 om_link_type
   │    拿到两端对象类型 + 背书方式（Edge/FK/连接表/中间对象）
   ▼
Compiler 递归编译：树 → "产出 pk 集合的一条子查询" + $N 参数列表
   │ ③ 外层再包一个 SELECT，从终端表把整行取回来，加分页
   ▼
④ cmx-database-pg（tokio-postgres）执行，参数全部绑定传递
```

编译器的两条安全纪律（`compile.rs` 开头注释写明）：

- **标识符白名单**：对象类型名、属性名、表名列名一律过 `safe_ident()`——只允许字母/数字/下划线且字母开头，`Customer; DROP TABLE x` 这类直接报错拒绝；
- **值全走参数绑定**：你传的任何值（"华东"、1000、主键列表）都变成 `$1 $2 $3` 占位符，绝不信进 SQL 文本。

一个小细节能看出工程严谨度：数值比较生成的是 `(props ->> 'amount')::numeric >= ($3)::text::numeric`——值先按文本绑定再转数字，避免 PG 把占位符推断成 numeric 类型导致驱动报错（代码注释里有完整解释）。

### 5.2 上一节那个例子，生成的真实 SQL

内层（pk 子查询，编译器产出）：

```sql
SELECT o.pk FROM oo_Order o
WHERE o.pk IN (
    SELECT DISTINCT e.b_pk AS pk FROM ol_edge e
    WHERE e.link = $2
      AND e.a_pk IN (
          SELECT o.pk FROM oo_Customer o
          WHERE o.pk IN (SELECT pk FROM oo_Customer)
            AND ((props ->> 'region') = $1)
      )
)
AND ((props ->> 'amount')::numeric >= ($3)::text::numeric)
```

外层（`load()` 再包一层取整行 + 分页）：

```sql
SELECT o.pk, o.title, o.props FROM oo_Order o
WHERE o.pk IN ( …上面整段子查询原样嵌入… )
ORDER BY o.title, o.pk
LIMIT $4 OFFSET $5
```

参数依次是：`$1='华东'`、`$2='customerPlacesOrder'`、`$3='1000'`、`$4=50`、`$5=0`。

人话翻译：**"先找出华东客户的主键 → 拿这些主键去边表对出订单主键 → 再筛金额 → 最后拿订单主键回订单表把整张卡片取出来，按名字排序取 50 张。"** 一条 SQL 干完，数据库自己优化执行计划。

### 5.3 如果关系是"外键背书"，SQL 换姿势（不碰边表）

建模时若声明 `customerPlacesOrder` 是外键背书（订单表的 `customerId` 属性指向客户），同样的请求会编译成：

```sql
-- 正向（客户 → 订单）：终端表的外键 ∈ 源主键集
SELECT DISTINCT t.pk AS pk FROM oo_Order t
WHERE t.props ->> 'customerId' IN ( …客户 pk 子查询… )
```

连接表背书 → JOIN 连接表；中间对象背书 → 查中间对象表的两个属性。四种形态的分派都在 `Compiler::emit()` 的 `SearchAround` 分支（`compile.rs` L120-175）。

### 5.4 聚合的 SQL（GroupSum 举例）

```sql
SELECT (o.props ->> 'region') AS g,
       COALESCE(SUM((o.props ->> 'amount')::numeric), 0) AS s
FROM oo_Order o
WHERE o.pk IN ( …pk 子查询… )
GROUP BY g ORDER BY s DESC
```

### 5.5 查不到表怎么办

对象表是"懒建"的（第一次写数据才建表）。所以 `load/aggregate` 对 PostgreSQL 的 `42P01`（表不存在）错误做了特判：**返回空页而不是报错**（`object_store.rs` 的 `query_or_empty`）。这就是有时查一个新类型"什么都没有但也不报错"的原因。

## 6. 问答一：现在的 SQL 是不是只能适配 PG 库的 json 物化表？

> **20260920 更新**：本节结论描述的是**物化编译器**（`compile.rs`），它至今没变、下述四个绑定点依然成立；但 20260918 方案落地后它**不再是唯一的取数路径**——虚拟绑定类型走 PgDirect 下推后端直查源库宽表，见本节末尾新增的「§6.1 虚拟直查」。

**是，而且绑得比"PG"还要再具体一层——是"本平台自建的那套 jsonb 物化布局"。** 绑定点有四个：

| # | 绑定点 | 代码位置 | 具体内容 |
| --- | --- | --- | --- |
| 1 | **表布局** | `compile.rs` `object_table()` | 表名硬拼 `oo_<类型>`，且假设列就是 `pk/title/props` |
| 2 | **属性访问方式** | `compile.rs` `prop_text()` 等 | 一律 `props ->> 'x'`（PG jsonb 专有操作符）+ `::numeric` 转型 |
| 3 | **SQL 方言** | 全文件 | `$N` 占位符、`EXCEPT` 集合运算、`::` 转型语法——PG 专用（MySQL 是 `?` 和 `EXCEPT` 不支持/语法不同，Oracle/SQL Server 又是另一套） |
| 4 | **执行驱动与连接** | `Cargo.toml` 依赖 `cmx-database-pg` | 底层 tokio-postgres，且连接固定为 `ONTO_DB_ID`（本体库，多租户按租户定位） |

推论：**业务库里一张普普通通的宽表（每列一个字段的那种），现在的编译器是查不了的**——它不会生成 `SELECT col1, col2 FROM biz_table WHERE ...`，只会生成"掏 JSON 口袋"的写法。ES、HTTP 接口、数据平台就更不用说了。

### 那现在从业务库取数是怎么解决的？——Funnel 物化通道（搬数据，不是查数据）

`crates/cmx-onto-store-pg/src/funnel_store.rs` 实现了 **O3 数据漏斗**：

1. 管理员给对象类型配一条**源映射**（`om_source_mapping` 表）：`source_db_id`（指向哪个库，可以是业务库）+ `source_query`（一条自由 SQL，如 `SELECT id, name, region FROM erp.customer`）+ 属性映射（源列名 → 本体属性名）+ 主键列/标题列 + 必填校验；
2. 执行同步：**去业务库把数据整批拉回来** → 逐行映射校验 → 合格的批量写进本体库的 `oo_<类型>` 物化表，不合格的进隔离区 `oo_quarantine`（带违规原因）；
3. 之后的 360/下钻查询**永远查本体库自己的物化表**，跟源库再无关系。

一句话：**现在是 ETL 式"把数据搬过来再查"，不是联邦式"隔着网络查过去"。** 这个模式简单可靠、查询快，但数据有延迟（同步周期决定）、本体库要存一份副本。

顺带一提：元模型早就给"数据源"留了位置——`om_object_type.datasource`（JSONB 列，DDL 注释写着"背书数据源原始 jsonb"），说明"对象类型的数据从哪来"这个概念在建模层已经存在，只是查询侧目前只认物化表。

### 6.1 虚拟直查（20260918 方案落地）：物化之外的另一条路

上面"推论"里查不了的**业务库普通宽表**，现在已经能查了——条件是把它注册成对象类型的**虚拟绑定**。读路径入口换成了**分派器**（`backend_dispatcher.rs`，方案 §5.1/§5.7）：每次读先装 `om_source_mapping` 绑定行，按 `mode` 选后端——

| mode | 后端 | 行为 |
| --- | --- | --- |
| `materialized`（默认） | 物化编译器（§5 原链路） | 整树编译成 `oo_*` jsonb SQL，行为零变化 |
| `virtual` | **PgDirect 下推**（`backend_pg.rs`） | simple 树（base/filter/static）直接下推**源库**编译——生成的是普通宽表 SQL：`SELECT cust_id AS pk, COALESCE(cust_name::text, cust_id::text) AS title, … FROM src_vcust WHERE 谓词`（只读事务 + 语句超时 + 参数绑定）；树里含 searchAround/集合运算/跨源组合时，先把"产出类型为虚拟的最大子树"整树解析成 **pk 集合**（上限 `PK_BRIDGE_MAX = 2000`），替换成 `static` 子集继续走 |

配套机制：

- **数据源注册表** `om_data_source`（管理口 `/data-sources*`）：两种形态——`config.ref` 引用 toml `[[databases]]` 已注册池，或独立连接（host/port/db/user/passwordEnv，**密码只存环境变量名**，每节点请求期懒注册成 `ontosrc_<id>` 小池；20260920 起读分派前自动做池就绪自愈，服务重启不再报"数据库不存在"）；
- **绑定**：`POST /object-types/datasource/bind` 建 `om_source_mapping`（propertyMap 源列 → 本体属性映射、主键/标题列、绑定时 probe 源结构 fail-fast）；
- **安全闸**：总闸 `onto.virtual_query = true` 才放行；绑定前置要求 authz 模式 ≠ off；读取仍过 PEP 行权限/列脱敏；
- **语义对齐**：虚拟类型的 load/aggregate 请求信封与物化完全一致（含分页、权限、场景 view），前端无感。

一句话：**§7.4 建议的"第一步：同库免物化直查"已经落地，而且比建议走得更远——源库不必是本体库本身，任何注册进来的 PG 池（含独立实例）都能直查；"跨源 SearchAround → pk 衔接"的桥接雏形也已在。**

## 7. 问答二：以后从业务库/数据平台取数——传拼好的 SQL，还是传查询描述？

### 7.1 两个方案是什么意思

**方案 A（SQL 直传）**：本体服务把查询直接拼成目标库方言的 SQL，发给业务库执行，拿结果回来。

**方案 B（描述下推）**：本体服务把查询表达成一个**与方言无关的数据查询描述**（就像现在的 `ObjectSet`/`Predicate` 树，或它的子集），传给业务系统/数据平台；**由对方自己翻译成它擅长的查询**（PG SQL / MySQL SQL / ES DSL / 接口调用），执行后返回"对象行"。

### 7.2 逐项对比

| 维度 | A：拼好 SQL 传过去 | B：传查询描述（下推） |
| --- | --- | --- |
| 接入成本 | 最低，对方不用开发什么 | 需要定义描述协议（schema 版本化）+ 对方写一个"描述→查询"的适配器 |
| **方言适配** | 每种库一套生成器，ES/接口型数据源根本不是 SQL，直接出局 | 每源一个适配器，方言差异被封装在源侧 |
| **语义映射** | 必须把本体属性名硬绑到源表物理列名，源端一改表就崩 | 描述里只出现本体属性名，源侧按映射配置翻译成列名/接口参数 |
| **权限** | 本体侧的行级权限（`row_filter`）折进 SQL 后，无法再叠加业务系统自身的数据权限；注入面大 | 权限以谓词描述传递，源侧可折入自己的查询或跑自己的 PDP；描述是类型化的，无注入面 |
| **组合能力** | 跨源下钻（A 源对象 → B 源对象）无法用一条 SQL 表达 | 可拆解成每源子描述 + 引擎侧内存衔接（这正是 Palantir 的做法） |
| **能力协商** | 无——源不支持就是报错 | 可声明"我支持下推过滤/聚合"，不支持的降级为拉取+内存过滤 |
| 治理/审计/血缘 | 差（对方只看到一坨 SQL） | 好（描述有结构，可审计"谁查了哪些对象的哪些属性"） |
| 适合谁 | 专家临时查询、管理态运维工具 | **平台级、长期、多源的数据接入** |

结论很清楚：**平台级方案选 B；A 只保留给管理态工具**（现有 Funnel 的 `source_query` 就是 A 的正确用法——管理员配的，不是终端用户查询通道）。

### 7.3 主流本体平台怎么做（调研结论）

**Palantir Foundry（本体平台的事实标杆，本仓库 DSL 注释里明言对标它）**

- 查询 API 就是 Object Set：`filter() / searchAround() / aggregate() / fetch()`，与我们 `ObjectSet` 几乎同构——**用户/前端永远只说"对象集语义"，从不说 SQL**；
- 对象类型由 **backing datasource**（背书数据源）支撑，对象是底层数据的**实时投影**而非静态拷贝；
- **Object Storage V2 支持查询下推（query pushdown）**：对象集查询被翻译后下推到底层存储执行，而不是全部拉回内存；
- **Virtual Tables（虚拟表）**：指向 Snowflake、Iceberg 等**外部平台**的"指针表"，数据不拷贝进 Foundry；对象类型可以直接背书虚拟表——对象集查询**联邦下推到外部系统**执行。
- → 一句话：**语义查询描述 → 本体服务翻译 → 下推到背书源**。它不把 SQL 发给源。

**其他代表**

| 平台/引擎 | 做法 |
| --- | --- |
| **Timbr** | 本体语义层 + 数据虚拟化：本体概念（对象/关系）映射到源表，查询生成 Trino 兼容 SQL 下推，免 ETL |
| **Trino / Starburst** | 联邦查询引擎：connector 体系对接各类源，做谓词/聚合**下推**；语义层放在引擎之上做业务语义翻译（"semantic layer on top of federation"） |
| **Dremio** | "Federated Semantics"：语义层覆盖全数据资产 + 反射缓存 + 下推，面向 AI Agent 消费场景 |
| **Apache Calcite** | "描述→多方言 SQL"的技术底座（很多引擎的规划器），证明这条路有成熟工具链 |

业界共识（含反方声音）：语义层/本体层负责**语义与治理**，查询以**结构化描述**交给联邦引擎或源侧翻译；裸 SQL 直通（raw SQL pass-through）只适合专家一次性查询——连持"语义层无用论"的 MotherDuck 也承认其治理/血缘/可移植性短板。

### 7.4 对本仓库意味着什么（现状盘点 + 建议路线）

**好消息：架构伏笔已经埋好了，不用推倒重来。**

- `ObjectStore` 本来就是 **trait（契约）**（`cmx-onto-model/src/object_store.rs`），`PgObjectStore` 只是**唯一实现**——"换个数据源"的扩展点天然存在；
- `ObjectSet`/`Predicate` 树本身就是**与存储无关的查询描述**，方案 B 需要的"协议"已经存在，缺的只是"下推协议 + 各源适配器"；
- `om_object_type.datasource` 字段已预留"背书数据源"概念，与 Palantir 的 backing datasource 对位；
- 工作区里已有**两处"描述→多后端编译"的现成先例**：cmx-data-auth 把约束 AST 编译成 SQL / 内存谓词 / ES 三种后端；modql 的 Filter/Entity 动态查询也是描述式——团队和代码库对这套模式并不陌生。

**建议分三步走（每步独立可用，不做大爆炸重构）：**

> **20260920 进展标注**：第一步已随方案 20260918 落地（§6.1）——物理布局抽象成了"绑定映射"（`om_source_mapping` 的 resource + propertyMap + 主键/标题列），且不止同库：任何注册池（含独立 PG 实例懒注册）都能直查。第三步的"跨源衔接"也有了雏形（bridge：虚拟子树整树解析 pk 集替换为 static）。第二步的"通用下推协议"（非 PG 源、能力协商）仍未做，仍是有效的下一步方向。

1. **第一步（低成本，同库直查）**：把编译器里"表布局"从硬编码抽象成**物理布局描述**（主键列 / 标题列 / 属性访问方式：jsonb 抽取 or 实体列）。同一 PG 库里已存在的业务宽表，注册成对象类型的背书源后**免物化直查**——消灭"明明数据就在库里还要搬一份"的场景。Funnel 保留给真需要副本/清洗的场景。✅ **已落地（20260918，见 §6.1）**
2. **第二步（跨库下推协议）**：定义**查询下推描述**（`ObjectSet` 子集：base/filter/predicate/分页 + 返回列映射），业务库侧实现"描述→本库 SQL"适配器（CMX 体系内可以是各微服务统一挂的一个数据查询 handler）。能力协商：源声明支持哪些谓词，不支持的整段拉回由本体侧内存过滤兜底。行级权限谓词随描述一起下推，源侧折入。
3. **第三步（数据平台/非 SQL 源 + 跨源衔接）**：ES / HTTP 接口 / 湖仓适配器；跨源 `SearchAround` 由本体侧拆解成每源子描述、按 pk 衔接（对齐 Palantir Object Set Service 的执行模型）。

**明确不建议**：把"拼好整条 SQL 跨网络传给业务库"做成产品能力。它短期最省事，但方言、权限折入、语义映射、跨源组合四个坑一个都绕不过去，而且把源库物理结构泄漏给本体服务，两边从此强耦合。
