# 跨仓页面资产与菜单归属治理方案

> 日期：2026-08-24
> 状态：评审中（R1～R3 自查完成，3 个决策点待拍板，见第八章）
> 涉及仓库：cmx-container · cmx-portalservice · cmx-model · cmx-mdm · cmx-flowengine · cmx-report · cmx-rulesengine · 根仓库（前端 workspace）

---

## 一、背景与痛点

"一芯多壳"架构落地后，五个引擎应用已能自持投递页面（前案：cmx-form::serve 统一收编）。但**页面/菜单/元数据的物理存放**仍是历史包袱：

1. 同一批页面在 **3～4 个仓库重复存在**，改一处其余不同步；
2. cmx-model 混入大量别家页面与菜单（甚至有 MDM 的页面）；
3. cmx-container 是公用库仓，却寄生着整个**门户内容数据根**（`data/` 625 个文件）；
4. 菜单真源双轨：`container/data/menu-pages` 与各引擎 `web/menu-source` 并存。

## 二、实勘发现（2026-08-24 全量扫描）

### 2.1 同一批页面现存最多四份

以 DCT/DOC 业务页（`fi.cmxfico.gl.dict* / doc* / acctws* …`）为例：

| # | 物理位置 | 角色 | 规模 |
|---|---|---|---|
| ① | `cmx-container/data/html-pages/` | **门户内容根**（dev.toml `assets.root="../cmx-container/data"`）：设计器经 :8080 save 写这里；门户读这里 | 119 文件 |
| ② | `cmx-model/data/html-pages/` | 模型中心内容根（model-server.toml `root="./data"`） | 115 文件 |
| ③ | `cmx-model/web/ui-html/` | 模型中心 serve 投递目录（上轮刚规范 v2 化） | ~117 文件 |

native 页同理（`definition/ demo/ fi/` 三组），另有 **MDM 十页三份**：`cmx-mdm/web/ui-native` ✅（唯一正确位置）、`cmx-model/web/ui-native/portal/mdm/` ❌、`cmx-model/data/native-pages/` ❌。

哈希实测（2026-08-24）：container/data 与 model/data 重叠区 **264 文件同路径同内容、0 漂移**——说明目前靠"整目录拷贝"同步，一旦某侧单独修改立即静默分叉。

## 三、归属判定原则

**原则 1（id 命名空间即主权）**：页面 id 的稳定前缀决定唯一属主，一个 id 全公司只允许存在于一个仓库。

| id / 资产前缀 | 属主 |
|---|---|
| `portal.flow.*`、`wf/cmxflow/flow/*` | cmx-flowengine |
| `portal.rules.*`、vendor 决策图 | cmx-rulesengine |
| `portal.rpt.*`、`fi/cmxfico/gl/rpt-*` | cmx-report |
| `portal.mdm.*` | cmx-mdm |
| `fi.cmxfico.gl.{dict*,doc*,acctws*,voucher*,trade*,employee…}`（DCT/DOC/模型域）、`definition/*` | cmx-model |
| `_legacy/*`（welcome 等门户壳页）、`help/*`、通知中心/服务目录 | cmx-portalservice |
| `demo/*`（dict-base/doc-base 教学演示） | ⚠️ 待拍板 D2 |

**原则 2（内容根跟着属主走）**：`assets.root` 指向本仓自己的 `data/`，公用库仓（cmx-container）运行时内容归零。

**原则 3（一份真源 + 明确派生物）**：每类资产指定唯一真源；凡副本必须是构建期生成的派生物（可随时重生成、不入 git 或 CI 校验一致）。

### 5.1 关键机制设计

#### A. 「工作区」与「投递」合一（消灭第②③份复制）

现状 model 同批页面存 `data/html-pages`（可编辑）+ `web/ui-html`（投递）两份。规范 v2 之后两者目录结构完全一致——**合并为一个目录 `web/ui-html`**：

- 读（serve 投递）：不变；
- 写（设计器保存）：服务内新增受控 save 端点（复用 `cmx-form::pages` 的 save service，数据根直接指 `web/ui-*`），或低配方案：设计器经门户反代保存、由各服务提供同样的 save 端点。

> 写盘与无状态约束：单机 dev 直写本仓目录可接受（现状即如此）；集群化时页面必须入库/对象存储，届时 save 端点换实现、读端点不变——接口先行，存储可替换。

#### B. 菜单单源化

1. 真源 = 各引擎 `web/menu-manifest.json`（flow 已是标准形态，report/rule/mdm 补齐 owner+pages 段）；
2. 聚合器：扩展现有 sync 思路（menu-generator 的 sync_menu_db.py / model-deploy seed_menu 二选一收编）——扫描五仓 manifest → upsert `cmx_menu`；
3. 删除 `container/data/menu-pages`、`model/data/menu-pages`、`{flow,report}/web/menu-source`（manifest 内嵌 menu 树即可，无需再拆 source 文件）；
4. portal `menu_pages.rs` 改为读 DB（cmx_menu 本来就是门户侧栏的数据源）。

#### C. 防漂移守护（CI 脚本 `check-asset-ownership`）

1. 扫描全部仓的 `index.json` / 分片 / manifest，建立 `page-id → [仓库…]` 倒排；
2. 任一 id 出现在 >1 仓库 → fail；
3. id 前缀不在其属主声明的清单内 → fail；
4. （可选）`packages/cmx-engine-shell` 共享包发布后，校验各引擎脚手架 hash 与包版本一致。

#### D. 独立壳脚手架共享化（二期）

`elements/base-element.js`、`index.js` 提取为根 npm workspace 包 `packages/cmx-engine-shell`，各引擎构建期拷入（派生物）。本期先只登记漂移事实，不强制。

## 十、修订记录 R4：开发期聚合工作区（用户评审，2026-08-24）

### 10.1 方向修正

用户评审否决了"立即分散回各服务仓"的目标态：**开发阶段跨六仓切换查看/修改资产太麻烦**。
修正为：

> **开发期**：全部资产放一个公共目录，按服务名子目录隔离（互不干扰、一屏可见）；
> 各服务只改 `[assets]` 配置指向自己的子目录；
> **发布期**：把 `<svc>/` 文件夹拷贝到主应用对应目录即可。

同时确认：**菜单数据归 cmx-model**（代码证实，见 10.3）。

> 本节修订取代第四章「目标态」与第五章「迁移步骤」的 S2～S5；归属判定原则（第三章）、
> 防漂移思想（§5.1-C）、决策点（第八章 D1/D2/D3）继续有效并适配新形态。

### 10.2 新目标态：统一资产工作区

各服务仅改 `[assets]` 三行（cwd = 各自仓根）：


> 与门户现状 `dev.toml assets.root="../cmx-container/data"` 同一引用模式，
> 六服务（含 portalservice）cwd 均为 cmx-container 的兄弟目录，相对层级一致。

**发布**：`scripts/publish-assets.sh <svc>` 把 `assets/<svc>/` 拷贝到对应主应用仓的
`web/` 与 `data/`（或 Docker 构建直接 COPY 工作区路径）。工作区为**唯一真源、单向流出**，
禁止反向手改服务仓副本（CI 校验一致性）。

### 10.3 菜单归属 model（代码证实）

初始化链路（实勘 deploy_seed_menu.rs / handlers/model/deploy.rs）：

```
POST /api/model/deploy {items:[{kind:"menu", domain, app, module}]}
  └─ cmx_model_deploy::deploy_menu_with_events()
       ├─ scan_menu_files(domain,app,module)   # 扫 <assets.root>/data/menu-pages/<d>/<a>/<m>/*.json
       ├─ menu_pages_adapter 扁平化为 MenuDefinition
       └─ LocalMenuDefinitionImporter::apply_menu_definitions()  # 写平台库 cmx_menu（按 module_code 先删后插）
```

要点：
1. **模型中心部署就是全平台菜单的唯一初始化入口**——flow(wf/cmxflow/flow)、
   report(fi/cmxfico/report)、gl explorer、mdm 的菜单都经它入库；
2. 扫描路径相对**运行进程的 assets.root**，故 menu-pages 必须落在
   `assets/model/data/menu-pages/`（与 model-deploy 同根）；
3. 门户侧栏运行时读 `cmx_menu` 表（DB），不直接读 JSON——JSON 仅部署输入；
4. 处置：`container/data/menu-pages` 与 `model/data/menu-pages`（二者已验证逐字节相同）
   合并为 `assets/model/data/menu-pages`；`{flow,report}/web/menu-source/` 副本删除，
   `menu-manifest.json` 保留 owner + nativePages/htmlPages 元信息段（F3 反代路由参考）。

## 十一、修订记录 R5：id 统一前缀 + data 冻结备份（用户评审，2026-08-24）

### 11.1 两条新约束

1. **container/data 不删除不修改，就地冻结为备份**——迁移一律纯拷贝；W4 原「退役清空」取消。
   model/data 同精神一并冻结（配置切换后自然失联成为备份）。
2. **模型中心页面 id 统一前缀**——归属判定从「多路径枚举」收敛为「单一前缀匹配」，
   菜单中引用的 id 同步修改。

### 11.2 现状痛点实勘（为什么必须改）

F3 反代按 id 前缀分流，但模型中心的谓词已膨胀成 **10 分支枚举**
（cmx-model-proxy/src/proxy.rs:108-121）：

```rust
id.starts_with("portal.definition.") || id.starts_with("definition.")
    || id.starts_with("portal.dct.") || id.starts_with("portal.doc.")
    || id == "portal.datasource.cluster" || id.starts_with("portal.dam.")
    || id.starts_with("demo.dict-base.") || id.starts_with("demo.doc-base.")
    || id.starts_with("fi.cmxfico.gl.dict") || id.starts_with("fi.cmxfico.gl.dct-")
    || id.starts_with("fi.cmxfico.gl.meta-model-")
```

且 model/web/ui-native 里还混着 **6 个门户自有页**（job/help/notify/system×2/display）
不在该谓词内——反代不到、只能靠门户本地数据根兜底，归属彻底模糊。

### 11.3 统一前缀方案

**目标规则：属主 = id 前缀，一服务一前缀，代码只写一行 `starts_with`。**

| 前缀 | 属主 | 状态 |
|---|---|---|
| `portal.model.` | 模型中心 | ★本次新设 |
| `portal.flow.` / `portal.rules.` / `portal.rpt.*` / `portal.mdm.*` | 对应引擎 | 已合规不动 |
| 其余（`portal.job/help/notify/system/display/*`、`demo.*`、`_legacy` 裸名） | 门户 | id 不变，仅物理归位 assets/portal/ |

**model 域改名映射（机械规则，零文件改名——relPath 与 id 解耦，规范 v2 保证）：**

| 现 id | 新 id |
|---|---|
| `portal.definition.base-dct` | `portal.model.definition.base-dct` |
| `definition.base-dct-native` | `portal.model.definition.base-dct-native` |
| `portal.dct.data-editor` | `portal.model.dct.data-editor` |
| `portal.doc.doc-loader` / `doc-service-test` | `portal.model.doc.…` |
| `portal.datasource.cluster` | `portal.model.datasource.cluster` |
| `portal.dam.registry-center` | `portal.model.dam.registry-center` |
| `fi.cmxfico.gl.voucher-native(-bin/-zmcjson)` | `portal.model.gl.voucher-native…` |

html v2 分片行：`{domain:"fi",app:"cmxfico"}` → `{domain:"portal",app:"model"}`
（module/page 保持不变）⇒ id 自动变为 `portal.model.<module>.<page>`
（如 `portal.model.gl.dictcls-explorer`）。**domain/app/module 字段与 id 前缀必须同一事务改**，
否则 list 的 domain=/app=/module= 过滤参数行为漂移。

### 11.4 引用同步清单（改 id 必改的五处）

| # | 位置 | 动作 |
|---|---|---|
| 1 | model web 索引 index.json + 各分片 pages.json | 条目 id / domain / app / module 字段批量重写 |
| 2 | menu-pages JSON（真源 `assets/model/data/menu-pages/`） | gl explorer-menu 的 `html_page`、mdm-menu 的 `native_page: portal.dct.data-editor` 等全部替换为新 id |
| 3 | `cmx_menu` 表 | **不手改**——菜单 JSON 更新后经模型中心 deploy 重部署自动重建（按 module_code 先删后插） |
| 4 | F3 反代谓词 | cmx-model-proxy 收敛为 `starts_with("portal.model.")`；flow/rpt 的业务前缀特例（`fi.cmxfico.gl.flow-*` / `rpt-designer-*`）本期不动、登记后续 |
| 5 | model 页面源码内的交叉引用 | 实勘仅 5 个文件含旧 id 字符串，逐个替换 |

另：引用 `_legacy`/`demo` 页的菜单节点（btm_view1、combo-box-demo 等裸名）随页面归门户，
菜单节点迁入门户侧菜单 JSON（同在 model/data/menu-pages 树内，域段区分）。
