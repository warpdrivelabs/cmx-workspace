# 治理表 DCT 元数据化：能力差距评估与技术债

> 日期：2026-08-20
> 涉及模块：`cmx-model-deploy`（DCT 编译层）/ `cmx-metadata`（DDL 引擎）/ `cmx-core`（模型层）/ `cmx-mdm`（治理表使用方）
> 起因：MDM 治理表（`20260812_001_mdm_治理表` 与 `20260818_002_mdm分发订阅` 两迁移，共 12 张 `md_*` 表 + `mdm_activation`）目前用 SQL 定义，评估能否改为字典元数据（DCT 定义文件 + 模型中心 deploy）方式建表；以及 `md_event_log.seq BIGSERIAL` 这类自增列元数据能否表达。
> 结论速览：**技术上大部分能力已具备，但有 3 处真实差距 + 1 个架构语义风险；建议治理表维持 SQL 定义，其中两个通用增强（列默认值、普通索引）值得独立先做。**

***

## 一、问题

1. `md_audit` / `md_xref` / `md_value_map` / `md_match_config` / `md_merge_record` / `md_match_scan` / `md_subscription` / `md_event_log` / `md_dispatch_log` / `md_dist_watermark` / `md_consumer_offset` / `mdm_activation` 这些 MDM 治理表，能否像 `cm_supplier` 等主数据表一样，用 DCT 字典元数据定义、走模型中心 deploy 建表？
2. `md_event_log.seq` 是 `BIGSERIAL` 自增列（非主键），当前字典元数据是否无法定义？

## 二、能力对照矩阵（治理表 DDL 需求 vs DCT 元数据链现状）

| 治理表需要的 DDL 特性 | DCT 元数据现状 | 结论 |
| --- | --- | --- |
| VARCHAR / TEXT / JSONB / TIMESTAMPTZ / BOOLEAN / BIGINT | 类型映射齐全（见 `cmx-metadata/src/ddl/postgres.rs:62` `map_column_type`：`DateTime → TIMESTAMP WITH TIME ZONE`、`Json → JSONB`、`Int → BIGINT`） | ✅ 支持 |
| 多形态主键（BIGINT 应用层 / VARCHAR(64) snowflake / VARCHAR 业务键如 `md_dist_watermark.key` / 复合主键） | `dictMeta.idField` 约定 + 字段 `isPrimaryKey`；支持复合 PK | ✅ 支持 |
| 字段集不强制注入 | `compile_dct`（`cmx-model-deploy/src/compile.rs:303`）的 baseFieldSet/hierarchyFieldSet 等均为**按表显式引用才合并**，治理表可只写自有字段 | ✅ 无障碍 |
| 联合唯一索引（`uk_md_dispatch_sub_event` 等） | 定义文件 `uniqueKeys: [[col,...]]`（`compile.rs:188` `unique_indexes`） | ✅ 支持 |
| 表/列中文注释 | `dictMeta.remark` → 表注释；字段 `caption` → 列注释（DDL 引擎 `postgres.rs` 生成 `COMMENT ON`） | ✅ 支持 |
| 表内 seed（`md_dist_watermark` 单行水位） | SEED deploy 通道现成（M6 主数据 seed 即此方式） | ✅ 支持 |
| **列默认值**（`DEFAULT now()` / `'{}'::jsonb` / `'[]'` / `0`——治理表几乎每表都有） | DDL 引擎**本身支持**：`ColumnDefine.default_value` 存在，`postgres.rs:292` `render_default_value` 可渲染含 `NOW()`/`CURRENT_TIMESTAMP` 的 SQL 表达式，ALTER 亦有 SET/DROP DEFAULT。但编译层 `compile.rs:165` **硬编码 `default_value: None`**，且字段 JSON 没有被读取的 defaultValue 键 | ⚠️ **差距①**：只差编译层透传 |
| **普通（非唯一）索引**（`idx_md_audit_record` 等，每表 1~4 个） | 模型层现成：`cmx-core/src/model/meta/table.rs:145` `IndexKind` 含 `Normal`。但编译层只解析 `uniqueKeys` 一种，DCT JSON 无 `indexes` 键的解析 | ⚠️ **差距②**：只差编译层解析 |
| **自增列**（`md_event_log.seq BIGSERIAL`，非主键、DB 生成、消费者按 `seq > ? ORDER BY seq` delta 拉取） | **全链路空白**：① 字段 JSON 无表达键；② 编译层不读；③ `ColumnDefine`（`table.rs:83`）无 auto_increment/identity 字段；④ DDL 引擎只会拼 `DEFAULT <表达式>`，不会创建序列对象 | ❌ **差距③** |
| DESC 索引（`idx_md_dispatch_sub ... created_at DESC`） | `IndexDefine`（`table.rs:155`）无方向概念 | ❌ 次要（去掉 DESC 功能等效） |
| 条件唯一索引（`WHERE archived = 0`） | `IndexDefine` 无谓词字段 | ❌ 治理表无此需求；`cmx_code_rule` 有（平台侧，不在本次范围） |

## 三、差距详解与解决方案

### 差距①：列默认值（编译层透传，改动小）——✅ 已实施 20260820

- **定位**：`cmx-container/crates/libs/cmx-model/cmx-model-deploy/src/compile.rs`——`field_to_column` 构造 `ColumnDefine` 时 `default_value: None` 恒定。
- **实施内容**：
  - `compile.rs` 新增 `normalize_default_value(raw, ft)`：字段 JSON `defaultValue`（兼容下划线 `default_value`，接受任意 JSON 值）按 **FieldType** 规范化为最终 SQL 表达式——数值/布尔转裸字面量（`0`、`TRUE`），字符串/日期/UUID 定界为 `'...'`（内部单引号翻倍转义），JSON 对象/数组紧凑序列化后定界（PG 对 jsonb 列字符串字面量默认值可隐式转换，无需显式 `::jsonb`）；字符串值识别为 SQL 表达式（`now()` / `CURRENT_*` / `nextval(...)` / 含 `::` / 已带引号）时原样透传作高级逃生舱；类型不匹配（INT 给 `"abc"`）warn 后忽略不中断编译。
  - **类型感知是关键**：DDL 层 `render_default_value` 是内容启发式（`"0"` 会裸输出成数字），VARCHAR 列默认值 `"0"` 若直接透传会产生非法 DDL——因此编译层按字段类型先行定界，DDL 层配合新增「首字符单引号 → 原样输出」分支（`cmx-metadata/src/ddl/postgres.rs` `render_default_value`），两层协同保证最终 DDL 正确。
  - 函数调用启发式收紧为「`(` 前必须是纯 SQL 标识符」，挡住 `N/A (备用)` 这类以括号结尾的普通文本被误判透传（有回归用例）。
  - 测试：`compile.rs::default_value_tests` 7 个用例（类型矩阵 + 端到端 `field_to_column` 透传 + 误判回归）+ `postgres.rs` render 已定界用例，全过。
- **受益面**：通用能力——普通业务字典同样需要（如 `sort_no DEFAULT 0`、`status DEFAULT 1`、`is_active DEFAULT true`、`create_time DEFAULT now()`）。

### 差距②：普通索引（编译层解析，改动小）——✅ 已实施 20260820（三阶段，见 [字典索引维护与部署更新检测改造方案](./../20260820_cmx-model_字典索引维护与部署更新检测改造方案.md)）

- **定位**：`compile.rs` `unique_indexes`（差距①实施后现为 :330）只处理 `uniqueKeys`；模型层 `IndexKind::Normal`、DDL 渲染、索引 diff、DB 内省、部署报告对普通索引**全部现成**（全链路仅缺编译入口这一环）。
- **补充发现（方案设计时探明）**：前端连 `uniqueKeys` 都没有维护 UI——只有 PK 勾选自动同步与删列清理（`portal-definition-manager.js`），业务唯一键目前只能在「JSON源码」tab 手工编辑；且 `unique_indexes` 不做列存在性校验，悬空列引用会以 SQL 报错阻断部署。另 diff 引擎的 `DropIndex` 是**真实执行**（区别于只记日志的 DropTable/DropColumn），设计期删条目 → 重新部署 → DB 索引被 DROP。
- **方案**（详见方案文档）：定义文件表级新增 `indexes: [{name?, columns:[...]}]` 键编译为 `IndexKind::Normal`（缺省名 `idx_<table>_<n>`）；前端字典定义页字段区新增「索引」tab 统一维护唯一键+普通索引（列选择弹窗、顺序敏感 chips）；删字段/改字段名联动清理与同步引用；保存前校验（悬空引用阻断、重复列序列阻断、冗余前缀告警）。分 3 期：① compile.rs 解析+校验（~0.5 天）② 前端索引 tab+联动（~1.5-2 天）③ 可选：DCT def_checksum + 部署 drift 检测。
- **受益面**：通用能力——查询密集列的普通索引目前只能建表后手工补 SQL，元数据化后随 deploy 演进；前端索引 UI 顺带补齐唯一键的空白。

### 差距③：自增列（全链路空白，真实扩展）

- **定位**：`ColumnDefine`（`cmx-core/src/model/meta/table.rs:83`）无自增字段；`FieldType` 无 serial；DDL 生成器无序列/IDENTITY 概念。
- **方案**（若实施）：`ColumnDefine` 增加 `auto_increment: bool`（serde default false）→ PG 端生成 `BIGINT GENERATED BY DEFAULT AS IDENTITY`（PG10+，语义等价 BIGSERIAL 且 ALTER 友好；优于手工 `CREATE SEQUENCE + DEFAULT nextval`）→ 幂等加列用 `ADD COLUMN IF NOT EXISTS ... AS IDENTITY`。`md_event_log.seq` 保持 DB 生成语义不变（分发 delta 拉取依赖序列单调性，**不可**改成应用层生成）。
- **依赖**：差距③不依赖①②，可独立实施；但三者为"治理表 DCT 化"的共同前置。

### 架构风险：字典目录污染（比 DDL 差距更实际）

治理表不是字典：无 dictCode 业务语义、不走 `dct_upsert` 写入（激活器/分发引擎用裸 SQL 直写 `cmx-mdm-store-pg`）、不应出现在任何字典选择器中。而 DCT 定义文件的 `dictionaryTables` 会被**字典目录全量暴露**——`activation-mapper.js` 的 `loadDictCatalog`（`cmx-container/data/native-pages/sources/portal/mdm/activation-mapper.js:118`）、`master-list`、字典数据维护页、`cr-form` 的 refDict 选择均从 `dictionaryTables` 取清单。治理表混入将使这些界面出现「审计留痕」「事件日志」等伪字典选项。若要 DCT 化，需先给 `dictMeta` 增加**内部表/隐藏字典**标记并在所有字典目录消费端过滤——又是一笔产品语义成本。

## 四、建议路线

| 路线 | 内容 | 适用条件 |
| --- | --- | --- |
| **A（推荐，现状）** | 治理表维持 `docs/sql/v2/biz/`（init_ddl + migrations，biz 轮引擎自动执行） | 引擎内部表与 Rust 代码强耦合（每次改列需同步改 `md_accessor` 等），SQL 是合理载体；v2 双库机制刚建立正好承载 |
| **B（增量增强，可独立做）** | 实施差距①②（defaultValue 透传 + indexes 键），**不迁移治理表** | 通用能力补齐，普通业务字典先受益；各约几十行改动 + 测试 |
| **C（完整 DCT 化）** | 差距①②③ + 内部表标记 + 字典目录过滤 + 12 张治理表定义迁移与存量库对齐 | 仅当希望"一切表结构皆元数据"时；收益是 deploy 统一 diff/台账/升级，代价是上述全部前置 + 迁移风险 |
