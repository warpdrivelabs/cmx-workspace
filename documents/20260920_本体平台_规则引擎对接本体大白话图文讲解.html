0三十秒版本

先建立三个角色，后面所有图都围绕它们转。

本体平台 :8097

好比企业办事大厅。对象=档案柜里的户口页（客户、订单、授信申请）；关系=档案之间的回形针；动作=办事窗口——收材料、改档案（edits）、对外发函（副作用）；函数=窗口里的小算盘；权限 PEP=窗口后的保安。

规则引擎 :8094

好比城里一家"决策图纸厂"。业务专家在画布上把判断流程画成决策图（走 decision-graph 组件），画完盖章定版（publish v3）；以后谁来问，都按同一张已盖章的图纸算，全过程留痕（决策日志）。

对接 = 装一条专线电话

本体窗口办事遇到"该不该批、该改成多少"这类判断，打电话去图纸厂按已盖章的图纸算，算完寄回来，窗口照单改档案。领导说的"对接"，就是装这条电话线。

一句话：大模型负责"听懂人话、选对窗口、填对表单"；本体负责"档案、窗口、保安"；规则引擎负责"照章办事的确定性判断"。三件套拼齐，就是"真本体"的完整故事。

1现状：两个岛，血统相同，但没有电话线

先看两边各有什么、现在是怎么"挨着却不通"的。

两边家底（白话盘点）

岛已经有什么白话解释
本体平台 对象 / 关系；动作三件套（编辑规则 logic、副作用 side_effects、函数背书 function_backing）；FEEL 子集引擎 + Rhai 沙箱；读侧 PEP + 写侧 PEP；出站专线目前只有 webhook 和"调流程引擎起审批实例"。 窗口会改档案、会发函，但窗口里的"聪明"只有两样：FEEL 像单元格里的 Excel 公式（提交校验够用），Rhai 像一段被上了锁的小程序（算个阶梯价可以，画审批路由不行）。
规则引擎 决策图建模（JDM，画布组件现成）；版本发布与历史版本；evaluate 同步试算；simulate / analyze 沙箱推演；决策测试与决策日志。 图纸厂设备齐全：能画图、能定版、能算、能预演、能审计——就差有客户上门。
断点 本体不依赖规则引擎的任何代码（"独立微服务"纪律）；跨服务只走 HTTP，而出站名单里没有规则引擎。 两个平台是同源的亲兄弟（FEEL/Rhai 内核一脉相承），但兄弟之间没装电话。
为什么这事"顺路"？因为本体已有成熟的出站模式（outbound.rs：配置键、服务间 API Key、超时、白名单、全局熄火开关），规则通道照着流程引擎那条线抄一遍模式即可，两边内核一行不用动。

2接上之后，一次动作是怎么跑的

以"提交授信申请"为例：动作的函数背书指向一张已发布的决策图。整条链路大模型完全不参与判定。

打个比方：业务员在窗口递交申请表（动作参数）。保安先查工牌（PEP），窗口发现这单要按行规判（函数背书指向图纸），于是打专线电话给图纸厂，报上材料和申请表数据（input）；图纸厂按盖了章的 v3 图纸算出"批 80 万、利率上浮 0.3"，回单寄回；窗口照回单改档案（edits 写回），全程有监控录像（决策日志 + 审计）。

3三档接法：由浅入深，每一档都独立可用

对接不是一件事，是三件递进的事。第一档一两天能通，第二档才是价值核心，第三档是平台叙事。

档1
副作用外呼

窗口办完事，顺手打个电话 改动最小 · 一两天级

动作执行编辑规则照旧走本地
→
决策图 evaluatePOST /rules/v1/…/evaluate
→
结果只转发通知 / 触发下游，不写档案

改哪里：动作 side_effects 本来就是 JSON，加一种 kind（如 runDecision）；outbound.rs 照 flow 模式加一条规则通道（ONTO_RULE_URL / API Key / 熄火开关）。适合：动作执行后通知风控、触发下游重算这类"发函"场景。

档2
编辑规则远端化
（核心价值）

窗口收材料，图纸厂算出"档案该怎么改" 写回闭环 · 中等工作量

动作提交参数 + 对象事实
→
决策图@v3 求值版本钉死，不漂移
→
输出映射成 edits与函数背书同一契约
→
写回对象属性真本体 · 写回闭环

改哪里：function_backing 扩展出"远端决策模型引用"（decisionKey + 已发布版本），本体动作解析时调 evaluate，把输出映射成 {"edits":[…],"sideEffects":[…]}——这正是 Palantir 的 Run decision rule（本体已有 Run function rule，同一契约直接复用）。价值：审批路由、定价、额度这类复杂业务策略在 decision-graph 里画、可版本化治理，本体动作只引用。

档3
规则进本体建模面

图纸厂的产品目录挂进大厅公告栏 平台能力建设 · 随 Skill 体系排期

本体工作台规则=一等资产
⇄
决策模型登记引用 / 版本 / 挂接动作
←
对象类型派生输入 schema属性 / marking / 口径

改哪里：元数据模型 + 工作台 UI + 与规则引擎的登记同步。价值：平台能力①的原文是"业务对象、关系、规则的建模与沉淀"——这一档兑现的就是"规则沉淀"，本体从此是"对象-关系-规则"三样齐全的完整本体。

再往远一步的反向档：规则引擎的输入事实改为经本体读取 API 获取（继承读侧 PEP 的行约束和列脱敏），决策结果经动作回写——规则执行天然带语义和权限，规则引擎也被拉进"数据权限切在语义层"的体系。

4四条红线：接之前先说清楚

这几条不守，对接会从"确定性护栏"退化成"新的不确定"。

① 别把所有判定都外呼

动作校验（validations）继续留在本地 FEEL——同步、低延迟、离线可测是硬要求。单点计算留给公式和小脚本；跨对象、多步、需要版本治理的业务策略才走决策图。本体函数不能退化成规则引擎的薄代理。

② 引用必须钉死版本

动作引用决策模型必须引用已发布版本快照（如 creditApproval@v3），不能"永远取最新"。否则规则引擎侧改一张图，所有本体动作的行为静默漂移——这比 bug 更可怕，因为它不报错。

③ 失败语义提前拍板

远端求值失败是 fail-closed（动作拒绝，业务办不成但不会错）还是 outbox deferred（挂起重试，与 ONTO_OUTBOUND=off 的既有语义对齐），档2 动工前定死，不许"看情况"。

④ 主体随请求走

出站请求带服务 API Key + 租户（必要时带 subjects），沿用 flow 那套服务间身份——规则引擎的决策日志才能归因到"谁在哪笔业务里触发了这次判定"，审计才闭环。
